# 看山工作台未自动加载 AGENTS.md + .agents/ 入口

> **成熟度：L1**（单次会话实战处置，2026-10-26）。升 L2 条件：在第 2 个同类场景（候选：看山不自动加载某 MCP 约定 / `.editorconfig` / CI 约定）复用「补丁 + 上报双轨」模式成功，并在文末「复用记录」回填 `reuse_count` 与场景链接。

## 1. 一句话结论

看山工作台在会话启动时只注入自有 system 上下文 + Skill 体系（`.box-agent-kanshan/skills`，经 `list_skills`/`get_skill` 加载），**不会**把项目根的 `AGENTS.md` 与 `.agents/` 自动注入上下文。Agent **能按需读取**这两处，但它们未被当作一等入口隐式生效——即「可识别 ≠ 被自动加载」。应对方式：**用户侧记忆补丁（近似自动加载）+ 产品侧上报（真正修复）双轨并行**。

## 2. 何时翻到本案例

- 用户依赖某项行业通用约定（`AGENTS.md`/`.agents/`、MCP 约定、lint/CI 约定等），但看山未原生自动加载。
- 症状：目录结构规范、文件可被工具读到，但 agent 启动时对其"隐形"，需手动提示才生效。
- 需要在"当下给用户可用改善"与"推动平台真正修复"之间同时发力。

## 4. 核心洞察（I，已过 G2：四元组完整）

### 洞察① "能读到" ≠ "被加载"
- 陈述：平台"可识别文件"与"自动消费为指令入口"是两种能力，当前只具备前者。
- 证据：F04 + F06。
- 反常识：目录结构再规范，不进注入链路就等于对 agent 隐形。
- 下次行动：显式区分"入口加载"与"文件可读"，不默认后者推导前者。

### 洞察② 记忆是平台缺失能力的用户侧补丁
- 陈述：用 core/context 记忆可模拟"自动加载约定"，但只是模型习惯约束，非平台机制。
- 证据：F08 + 反馈中标注的局限说明。
- 反常识：写进记忆看似"已解决"，实则缺口仍在平台侧，易造成"已修复"的错觉。
- 下次行动：补丁类处置必须同时留"真正修复在别处"的标记。

### 洞察③ 命令体系已就绪，缺的是"自动发现"那一跳
- 陈述：`.agents/commands/` 已是成型 slash 命令库，`/七概念` 可被正确解析执行，瓶颈仅在启动期自动发现/注入。
- 证据：F10 + F12。
- 反常识：补齐"自动加载"边际成本低、收益高——内容早已存在，只差一个探测注入步骤。
- 下次行动：上报聚焦"启动探测 + 可控注入"最小增量，而非重造命令体系。

## 5. 可复用模式（E，已过 G3：可迁移）

**模式：平台能力缺口的"补丁 + 上报"双轨处置**

- 触发场景：用户依赖某项行业通用约定，但当前平台未原生支持（不限 .agents，同样适用 MCP 约定、`.editorconfig`、CI 约定等）。
- 步骤：
  1. 用事实确认"可读但未自动生效"的边界；
  2. 用户侧补丁（记忆 / 每轮主动加载）取得近似体验；
  3. 补丁内显式标注"真正修复在平台侧"；
  4. 产出聚焦最小增量的上报文案。
- 反模式：只写记忆不上报（缺口被永久掩盖）；只上报不补丁（用户当下无改善）。
- 迁移验证：可直接套用到"看山不自动加载某 MCP/lint 约定"等任意同类场景。✅

## 7. 产品反馈（上报文案）

**标题**：支持自动识别并加载项目入口文件 `AGENTS.md` 与 `.agents/` 目录

**期望行为**：进入含 `AGENTS.md`/`.agents/` 的工作区时，平台自动发现并加载其约定（capability-registry、commands、checklists、config/spec-loader.toml 等），注入为当前会话工作规则，无需用户每次手动提示。

**背景**：`AGENTS.md` + `.agents/` 已是 Claude Code、Codex、Cursor 等主流 agent 工具的通用入口约定；用户跨工具迁移时期望看山开箱即用地消费同一套入口。

**建议最小增量**：① 启动时探测工作区根的 `AGENTS.md`/`.agents/`，存在则按约定注入；② 提供开关与与自有 Skill 体系的加载顺序/冲突规则；③ 大目录按需/摘要式加载避免上下文膨胀；④ UI 显式提示"已加载 N 个项目入口约定"。
