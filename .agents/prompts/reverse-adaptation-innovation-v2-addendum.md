# 逆向适配创新方法论·V2边界强化（补充提示词）

> **适用场景**：在执行知识沉淀（萃取E阶段）、对抗审查（V阶段）、模式入库G3质量门验证时，凡是涉及"跨领域迁移""极端用户→通用设计""从特殊群体提取方法论"等逆向适配类创新任务，必须将本补充提示词附加到标准流程之后。
> **核心修复**：修复V1版本"成功偏误"和"确认偏误"两个结构性缺陷——强制失败案例搜索、强制反目标用户/反目标场景分析、强制早期预警信号检查。

---

## 使用方式

在执行逆向适配类创新/跨领域迁移任务时，将以下提示词附加到标准萃取/审查prompt之后执行：

```
【逆向适配V2边界强化·强制检查清单】
你正在执行逆向适配类跨领域创新任务。在完成常规分析后，必须强制执行以下8项检查，每项检查未通过则必须补充对应内容，不得跳过：
```

然后逐项执行检查。

## 强制检查项（共8项）

### 检查1：成功偏误防御——强制失败案例搜索
- **要求**：不能仅引用成功案例（缘石坡道/深色模式/闭路字幕等），必须主动搜索并记录至少**1个真实工业级失败案例**
- **搜索方向**：
  - 该方法论被形式主义复制导致的失败案例
  - 技术方案绕过用户真实需求的失败案例
  - 自动化适配产生反噬效应的案例
  - 为A群体设计但伤害B群体的跨多样性冲突案例
- **记录格式**：每个失败案例必须包含：背景、失败表现、根因分析、教训
- **通过标准**：≥1个真实失败案例（非假设性场景），且根因分析具体到违反了逆向适配的哪个步骤/前提

### 检查2：确认偏误防御——反目标用户分析
- **要求**：除了分析"对谁有效"（目标用户），必须强制分析"对谁无效/有害"（反目标用户）
- **必须覆盖的反目标用户类型**（根据方法论类型至少选3类）：
  - 非专家用户（非技术用户/新手/老年人等）
  - 文化背景差异用户（中文语境vs英文语境、高语境vs低语境文化）
  - 认知风格相反用户（如ADHD友好方案对强迫症用户是否友好）
  - 任务类型相反场景（如执行类方案用于创意类任务）
  - 极端时长场景（短对话vs长对话，单次使用vs长期使用）
- **记录格式**：反目标用户 | 为什么不适用 | 如何适配
- **通过标准**：≥3个反目标用户/反目标场景，每个有具体分析而非泛泛而谈

### 检查3：8个适用前提完整性检查
V1版本5个前提 + V2新增3个前提，共8个，逐一验证：

| # | 前提条件 | 验证问题 |
|---|---------|---------|
| 1 | 源领域方法经过源群体充分验证 | 该方法是否被源社区（实际使用群体）验证有效，而非仅由外部研究者认定？ |
| 2 | 核心约束具有跨场景普适性 | 抽象出的核心约束是否在目标场景中真实存在，而非牵强类比？ |
| 3 | 适配不破坏源群体使用价值 | 改造后是否保证源群体也能获益，而非仅消费他们作为"灵感来源"？ |
| 4 | 目标用户有同类痛点但无有效方案 | 目标用户是否真的需要这个方案，还是设计者的"解决方案找问题"？ |
| 5 | 适配成本低于预期收益 | 改造和维护成本是否合理？是否存在更简单直接的替代方案？ |
| 6(V2) | **源社区验证** | 适配后的方案是否经过源社区成员的测试/反馈？（AccessiBe失败根因） |
| 7(V2) | **跨多样性冲突评估** | 是否评估了对其他多样性群体的潜在伤害？（触觉铺装矛盾根因） |
| 8(V2) | **互惠性原则** | 源群体是否能从适配后的主流产品中获益？（K联赛失败根因） |

### 检查4：早期预警信号清单
必须在方法论文档中内置7个早期预警信号，出现信号时暂停推进回到用户研究：

| 信号 | 含义 | 行动 |
|------|------|------|
| 源社区成员公开表达不适或批评 | 适配可能冒犯源群体或误解需求 | 立即与批评者对话 |
| 适配需要大量开关/例外才能被接受 | 可能过度泛化 | 缩小适用范围 |
| 用户测试发现对一部分用户造成新困扰 | 跨多样性冲突或副作用 | 识别受影响群体，重新评估 |
| 团队无法一句话说清"核心约束是什么" | 可能陷入形式主义复制 | 回到原理抽象阶段 |
| 源群体成员未参与设计或测试 | 高风险——外部视角易误解需求 | 暂停开发，邀请源群体参与 |
| 方案依赖刻板印象而非真实田野数据 | 刻板印象消费风险 | 重新做用户研究 |
| 方案被宣传为"万能解法""适用于所有人" | 过度泛化信号 | 严格定义边界条件 |

### 检查5：分层架构要求（创新/跨领域类模式强制）
- **核心层**：核心规则、黄金场景、已验证的有效场景（稳定不变）
- **扩展层**：边界场景、失败案例、预警信号、反目标用户分析（持续更新）
- **要求**：文档中必须明确区分核心层和扩展层，新发现的边界/失败案例归入扩展层，不影响核心层稳定性

### 检查6：边界场景梯度适配策略
对识别出的反目标/边界场景，不能简单标记为"不适用"了事，必须给出具体的梯度适配策略，包括：
- 轻度适配：参数调整/表述修改即可覆盖的场景
- 中度适配：需要切换子范式/附加补充规则的场景
- 重度不适配：明确标注"此场景禁止使用本模式"，并给出推荐替代模式

### 检查7：G3质量门差异化标准确认
在G3验证环节，必须根据模式类型使用不同标准：
- **执行/协作类模式**（如原子提交、CI检查）：≥2个正向迁移案例即可通过
- **创新/跨领域迁移类模式**：≥2个正向迁移案例 **+ ≥1个真实失败案例** + ≥3个反目标用户/场景分析 **+** 7个早期预警信号表，四项缺一不可

### 检查8：互惠性影响评估
对于从边缘/弱势群体提取方法论的场景，必须回答：
1. 源群体是否会因本次适配而获得实际利益？
2. 是否存在"消费"源群体困境做PR但源群体一无所获的风险？
3. 适配后的产品/方法论是否会让源群体的处境更差（如替代他们已有的工具链）？

## 反模式禁止（逆向适配类任务特有）

❌ 只举成功案例不举失败案例（成功偏误）
❌ 只分析目标用户不分析反目标用户（确认偏误）
❌ 从外部推测源群体需求而不让其参与设计/测试
❌ 宣传方案为"万能解法""适用于所有人"
❌ 用技术自动化绕过对源领域的真正理解（AccessiBe式失败）
❌ 为A群体设计但未评估对B群体的潜在伤害
❌ 将源群体作为"灵感来源"消费但不确保互惠
❌ G3验证只做正向迁移不找反例
