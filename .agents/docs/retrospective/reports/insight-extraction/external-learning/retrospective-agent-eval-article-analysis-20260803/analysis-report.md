# Agent评测体系化建设方法论深度分析报告

## 摘要

本文是孙敦灿2026年第28篇技术文章，系统阐述了AI Agent从Demo到生产可用过程中，如何构建一套完整的、工程化的评测体系。文章提出Agent评测不是上线前的简单抽查，而是将"不稳定的智能行为"持续收敛为"可发布的工程质量"的核心基础设施。全文共10章，从为什么需要体系化切入，逐层展开指标体系、数据集建设、评分机制、根因分析、优化建议、全链路闭环等核心模块，最后总结落地难点。文章核心观点包括：生产系统更关心"连续成功率"而非"至少一次成功率"；评分应以规则为主、LLM为辅、人工兜底；根因定位要追到责任模块和可修复原因；评测必须形成闭环并沉淀六类质量资产。

### 1.2 核心问题背景

- **Agent与传统软件的本质差异**：Agent的输入、输出和状态空间更开放——用户表达不可穷举，模型输出有随机性，多轮对话累积上下文，工具调用改变系统状态。
- **三道门槛**：从Demo到生产可用需要跨过：非确定性（同样输入不一定同样输出）、黑盒化（内部决策过程不透明）、错误级联放大（前一步小错在后续被放大）。
- **"跑几条case"的误区**：同一Prompt跑通一次不代表稳定可用；每次改模型、改Prompt或改工具参数都可能引入回归；存在"假阳性"问题（最终答案看起来对，但执行路径已偏离或带风险）。
- **评测的定位**：评测体系必须嵌入研发流程，不是上线前人工抽查；评测平台不只是"出分工具"，核心价值是把问题稳定转化为可执行修复，形成持续迭代闭环。

## 第二部分：核心观点深度解析

### 2.1 观点一：Agent评测必须体系化，不能靠上线前抽查

**核心论点**：Agent的本质特征决定了作坊式评测完全不够。

**关键论据**：

1. **非确定性问题**：大模型输出有随机性，同一Prompt跑通一次不代表每次都能跑通。
2. **黑盒化问题**：内部决策过程不透明，仅看最终答案无法发现过程中的风险。
3. **错误级联放大**：多步链路中前面一个小偏差会在后续被放大成严重错误。
4. **回归风险**：每次改模型、改Prompt、改工具参数都可能把原来好用的场景改坏，且不容易第一时间发现。
5. **假阳性陷阱**：有些样本最终答案看起来对，但执行路径已经偏离或带风险，这类问题在生产中迟早暴露。

**成熟评测体系需要回答三类问题**：
- 能力问题：Agent能不能做某件事？
- 质量问题：做得好不好？稳不稳定？
- 归因问题：错在哪？为什么错？怎么改？

### 2.2 观点二：指标要分层，生产系统更关心"连续成功率"

**核心论点**：不是所有指标同等重要，要分优先级，且要区分"能力上限"和"生产稳定性"。

**指标分层体系**：

| 优先级 | 用途 | 说明 |
|--------|------|------|
| P0 | 上线门禁 | 不达标不能发布 |
| P1 | 版本比较和工程优化 | 用于判断迭代是否有真实提升 |
| P2 | 体验改善和长期观察 | 不阻塞发布，但持续追踪 |

**两类成功率指标**：
- **至少一次成功率**：同一个任务跑N次，只要有一次成功就算通过。反映能力上限，说明"Agent能做到"。
- **连续成功率**：同一个任务跑N次，必须每次都成功才算通过。反映生产可靠性，生产系统更关心这个——用户不会接受"多试几次总有一次成功"。

**统计检验的重要性**：
- 版本对比不能只看分数差异，要做统计检验
- 需要给出关键指标的置信区间
- 需要判断与基线版本的差异是"真实提升/下降"还是随机波动
- 需要提前定义"最小可感知变化阈值"
- 结论：门禁不只看"差了多少"，还要看"这个差异是否超过统计噪声"

**Skill专项指标**：对于Skill密集型系统，需要补充Skill子指标：是否该触发、触发后流程是否正确、工具参数是否正确、最终产物是否可用、异常时是否能降级。

### 2.3 观点三：评分应以规则为主、LLM为辅、人工兜底

**核心论点**：评分器有明确的优先级顺序，不能迷信LLM Judge，也不能全靠人工。

**三类评分器优先级**：

| 优先级 | 评分器类型 | 适用范围 |
|--------|-----------|----------|
| 1（最高） | 规则Scorer | 能写成代码的硬条件：工具调用、状态检查、字段校验、禁用动作检查 |
| 2 | LLM-as-Judge | 语义和策略类非确定性维度：解释质量、策略妥当性、回复自然度 |
| 3（兜底） | 人工Scorer | 定标准、校准Judge、处理争议、高风险场景终判 |

**LLM Judge的正确使用方式**：
1. 不能只写"请从1到5打分"，每个分档要有可执行标准
2. 必须输出reason（判定理由），方便badcase定位和聚类
3. 需要few-shot示例，尤其要包含边界样本和判定的COT逻辑
4. 需要周期性校准，Judge与人工复核一致率达到约85%（参考值）后再进入日常自动化
5. 需要偏差治理：如果评测模型和生成答案的模型是同一个或同系列，可能偏好自己风格的回答，可以引入多个不同LLM进行对抗打分

**人工评分的正确定位**：
人工不适合承担日常全量打分，主要用于四个环节：
1. 新建评测集时确认样本的期望行为和打分标准（业务定口径）
2. 校准LLM-as-Judge（Judge无法判断依赖内部政策的问题）
3. 处理争议样本
4. 抽查高风险场景（赔付、隐私、合规、投诉升级等）

**人工评分路由机制**：
不应只由LLM Judge分数阈值决定是否进人工，而应做路由：
- 自动评分不确定时（边界分数、低置信度、reason含糊、多Judge分歧）
- 新模型/Prompt/工具Schema/业务活动上线时抽样
- 规则与LLM Judge结论冲突时

**分层筛查执行策略**：
1. **粗筛层**：规则Scorer+轻量LLM，快速识别明显通过/明显失败/存疑
2. **精判层**：完整规则+LLM Judge，确认是否badcase，输出问题分类、现象、置信度、判定依据
3. **人工复核层**：处理高风险、低置信、冲突样本、业务口径未固化的样本

**假阳性识别**：对结果看起来正确但执行路径有问题的case，要增加过程型检查（计划合理性、工具调用顺序、检索证据充分性）和风险型检查（是否有过度承诺、是否跳过必要校验、是否有合规风险）。

### 2.4 观点四：根因定位要追到责任模块和可修复原因

**核心论点**：端到端失败只是表象，根因分析必须追到具体模块、具体问题类型，并给出可执行的修复建议。

**Badcase来源通路**：
1. 离线评测集
2. 线上会话、人工质检、投诉工单、低满意度样本、版本回归失败、监控告警

两条通路最终应汇入同一个badcase任务表和同一套根因分析Pipeline。

**RCA（根因分析）五步通用链路**：

1. **证据汇总**：按sessionId/chatId/traceId/评测运行ID找到完整链路日志，汇总用户输入、Agent回复、各模块输入输出、prompt、工具调用、异常、耗时、中间产物。

2. **范围收敛**：不要对全部模块无差别排查，维护"问题现象×功能模块"映射表：
   - "答非所问"→优先看意图识别、Query改写、知识筛选
   - "过度承诺"→优先看风险拦截、回复生成
   - "订单未澄清"→优先看槽位抽取、上下文判断
   - 映射命中走确定性路径，未命中再让LLM兜底缩圈
   - 注意：映射表只用于缩小候选范围，不直接等同于最终定责

3. **分模块诊断**：对候选模块逐个读取input、output、prompt、工具返回、异常日志，输出问题摘要、关键证据、改进建议和可归结构化字段。

   举例："事实性错误"case→先看FAQ检索是否召回正确政策→再看知识检索是否保留关键片段→最后看回复生成是否忠实使用证据→定位具体失败模块。

4. **责任判定**：消费"问题现象+分模块诊断结果+根因知识库"，输出：
   - 问题分类（面向报告/看板的大类：语义理解/知识召回/工具执行/风险防控等）
   - 问题枚举（更细的失败类型）
   - 责任模块（主责+次责）
   - 修复建议
   
   三层定责策略：先用严重模块结论直接定责→再用规则引擎匹配确定性模式→最后用LLM汇总复杂链路中的责任传递关系。

5. **结构化落盘与查询**：根因结果不要只存在一次性报告里，要结构化写入任务记录，至少包括：问题分类、问题现象、问题枚举、责任层、责任模块、置信度、详细报告、修复建议。

**三层归因体系**：
- 现象层：用户/评测能直接观察到的问题（如"答非所问"）
- 模块层：具体哪个功能模块出问题（如"FAQ检索模块"）
- 责任层：最终归到哪个角色/环节负责（如"运营配置问题"、"算法需优化"、"工程需修复"、"业务需定口径"）

**Skill问题快速分流**：
- 不该触发但触发了→触发判断问题
- 该触发但没触发→触发判断问题
- 触发了但流程走错→Skill逻辑问题
- 参数构造错误→参数生成问题
- 工具执行失败→工具或外部系统问题
- 产物质量差→生成或后处理问题
- 异常未降级→容错处理问题

**根因标签体系**：标签要稳定、可统计、能指向明确owner和处理动作。示例分类：
- 语义理解类
- 知识召回类
- 工具执行类
- 风险防控类
- 对话管理类
- ...

**Badcase聚类**：同一根因、同一业务场景、同一工具、同一知识点的失败应自动聚成问题簇，报告应输出"问题簇"而非零散case列表（如"退款已发货场景中，Agent 23次跳过订单状态校验，主要集中在v1.8 Prompt"）。

### 2.5 观点五：闭环终点是资产沉淀，不是单次报告

**核心论点**：评测平台的终点不是出一份好看的报告，而是建立持续运转的质量改进机制，把线上失败持续转化为可复用的研发资产。

**评测平台九个能力模块**：
（文章有架构图，从上下文推断）用例管理、执行引擎、Trace采集、评分引擎、badcase分析、根因定位、优化建议、回归验证、资产沉淀。

**发布门禁三类信号联动**：
离线评测通过≠线上一定变好，发布阶段要联动三类信号：
1. **离线质量信号**：核心场景通过率、P0风险数、关键工具参数正确率
2. **线上体验信号**：转人工率、重复追问率、投诉率、满意度变化
3. **业务结果信号**：任务完成率、工单闭环率、退款/赔付成功率等

**回滚触发条件**：如果离线提升但线上关键信号恶化，应该触发回滚或降级。

**Trace标准要求**：
Trace输出要作为被测Agent的标准能力，不是事后补救。至少稳定记录：工具名、入参、返回值、时间戳、耗时、错误；复杂Agent还应记录计划、检索过程、Guardrail拦截等。评测环境要隔离，避免多用例共享状态导致分数不可复现。

**反馈生产（最容易被低估的一环）**：
发现问题本身不会自动带来收益，只有把问题沉淀成可复用资产，下一轮迭代成本才会下降。

**一条Badcase至少生产3类反馈**：
1. 回归用例：加入评测集，防止同类问题再次出现
2. 配置/规则/Prompt修复：直接修复问题
3. 训练数据（如适用）：用于模型微调或Skill优化

**三条反馈生产线**：
（文章有图）对应不同的处理流水线。

**反馈入库标准**（不能把所有失败都塞进回归集）：
1. 失败可复现，或至少有稳定Trace和人工确认
2. 期望行为明确，可以写成规则、Judge标准或人工验收标准
3. 根因标签清楚，能归到具体能力域或业务流程
4. 样本有代表性，能覆盖一类问题，不是一次性环境抖动
5. 已完成脱敏，符合隐私和数据合规要求

**回归集样本治理**：
- 同簇样本保留代表例，避免冗余
- P0/P1高风险样本长期保留
- 已稳定多版本通过且风险低的样本可降级为抽样集
- 线上新分布出现时，通过主动学习优先抽取低置信、高影响、新意图、新工具、新知识点样本进入人工确认

**六大质量资产库**（最终沉淀目标）：
1. 用例库（Golden Set + 各类扩展集）
2. Trace库（执行轨迹记录，用于复盘和调试）
3. 根因标签库（稳定的问题分类体系）
4. 修复建议库（针对各类问题的标准修复方案）
5. Judge校准集（用于持续校准LLM Judge的金标数据）
6. 回归集（用于版本验证的自动化测试集）

质量资产越厚，Agent迭代越不会靠个人经验和临时救火。

## 第三部分：关键概念一览

| 概念/术语 | 简要说明 |
|-----------|----------|
| **非确定性** | Agent核心特征之一，同样输入不一定产生同样输出，源于模型的随机性 |
| **错误级联放大** | 多步链路中前面一个小偏差在后续步骤中被放大成严重错误 |
| **假阳性** | 最终答案看起来正确，但执行路径已偏离或存在风险，是隐蔽的生产隐患 |
| **三道门槛** | Agent从Demo到生产需要跨过的三个本质困难：非确定性、黑盒化、错误级联放大 |
| **Golden Set（黄金评测集）** | 一组相对稳定、长期复用的核心样本，用于版本对比和发布门禁 |
| **Trace（执行轨迹）** | Agent执行过程的完整记录，包括工具调用、参数、返回值、中间产物等 |
| **Scorer（评分器）** | 对Agent执行结果进行评判的组件，分为规则Scorer、LLM-as-Judge、人工Scorer三类 |
| **四层评测维度** | 对话Agent的四个评判层次：Turn（单轮）、Session（整段会话）、Trace（执行轨迹）、Outcome（最终结果） |
| **连续成功率** | 同一个任务跑N次，每次都成功才通过，反映生产级稳定性；区别于"至少一次成功率"（反映能力上限） |
| **置信区间** | 统计指标，说明评测结果的稳定范围，避免只看单点分数做决策 |
| **最小可感知变化阈值** | 提前定义"指标至少提升/下降多少才算值得做发布判断"，避免被随机波动误导 |
| **LLM-as-Judge** | 用大语言模型作为评判者，主要用于语义和策略等非确定性维度的评分，需要校准到与人工一致率约85% |
| **Guardrail（安全护栏）** | Agent系统中的安全拦截机制，防止输出违规或高风险内容 |
| **RCA（根因分析）** | Root Cause Analysis，Badcase发生后定位根本原因的标准化流程 |
| **P0/P1/P2指标** | 指标优先级分类：P0是上线门禁（不达标不能发），P1用于版本比较和工程优化，P2用于体验改善和长期观察 |
| **分层筛查** | 评分执行策略：粗筛（规则快速分流）→精判（完整规则+LLM Judge）→人工复核（高风险/低置信/冲突样本） |
| **反馈生产** | 将线上失败转化为可复用研发资产（回归用例、配置修复、训练数据）的过程 |
| **Kappa系数** | 衡量评分一致性（Judge与人工标注一致性、多模型对抗打分一致性）的统计指标 |
| **问题现象×功能模块映射表** | 用于快速收敛根因排查范围的对照表，如"事实性错误"优先查检索和生成模块 |
| **COT（Chain of Thought）** | 思维链，LLM Judge需要包含推理过程的判定逻辑，用于few-shot示例 |
| **Skill评测** | 针对Agent内Skill单元的专项评测：是否该触发、流程是否正确、参数是否正确、产物是否可用、异常是否能降级 |

## 第四部分：写作手法与论证特点

1. **"划重点"先行**：每章开头用一句话提炼本章核心结论，降低读者认知负担，方便快速检索。

2. **反直觉破题**：开头直接打破常见认知误区——"跑几条case感觉还行远远不够"、"同一Prompt跑通一次不代表稳定可用"。

3. **分层分级思想贯穿始终**：
   - 指标P0/P1/P2三级
   - 评分器规则/LLM/人工三层
   - 评分执行粗筛/精判/人工复核三层
   - 根因归因现象层/模块层/责任层三层
   - 反馈质量不同等级处理
   用分层降低系统复杂度。

4. **方法论与工程落地紧密结合**：不仅讲"应该怎么做"的原则，还给出具体的实现路径——数据结构建议、流程图描述、判定逻辑、参考数值（如Judge一致率85%、Golden Set初始50-200条）。

5. **反模式提醒贯穿全文**：
   - "不要只看平均每轮分数"
   - "不要随机抽样线上数据做评测集（幸存者偏差）"
   - "不要只写1-5分的Judge Prompt"
   - "不要给泛化的优化建议如'优化Prompt'"
   - "不要让人工承担日常全量打分"
   - "不要对所有模块无差别排查根因"

6. **具体案例贯穿**：用"已发货订单退款，Agent未查订单状态就直接承诺退款"这个具体案例贯穿评分、根因分析、优化建议等多个章节，让抽象方法论有具体落点。

7. **闭环思维**：从第1章提出问题，到第9章闭环回到资产沉淀，形成完整的"发现→定位→修复→验证→沉淀"循环。

## 第五部分：核心要点总结（5个）

### 要点1：评测是Agent工程化的核心基础设施，不是附属环节
Agent与传统软件的本质差异（非确定性、黑盒化、错误级联）决定了"跑几条case"的作坊式评测完全不够。评测体系必须嵌入研发流程，成为持续迭代闭环的核心枢纽——它不只是"出分工具"，核心价值是把问题稳定转化为可执行修复。

### 要点2：评测体系是"分层分类"的系统工程
没有"万能指标"：要先区分Agent类型再定制评测方案；指标要分P0/P1/P2三级优先级；评分要分规则/LLM/人工三层；评分执行要走粗筛→精判→人工复核；根因分析要分现象层→模块层→责任层。对话Agent还要从Turn/Session/Trace/Outcome四个层次综合评判。

### 要点3：数据质量决定评测质量，Golden Set是核心资产
评测集不是线上数据的随机抽样（幸存者偏差会漏掉关键边缘场景），而是围绕高风险路径、关键逻辑和失败模式刻意设计出来的质量资产。建设路径：先做50-200条专家设计的高质量golden set覆盖核心路径和高风险边界，再逐步扩展分类采样集、长尾集、对抗集、线上回流集。

### 要点4：根因定位和优化建议必须"可落地、可执行、可验证"
根因定位不能停留在"Prompt不好"这类泛泛之谈，要追到具体责任模块和可修复原因；优化建议不能只说"加强训练"，必须形成标准行动项——包含失败范围、证据链、具体动作、owner、验收方式、优先级，能直接进入工单系统流转。

### 要点5：闭环的终点是资产沉淀，不是单次报告
评测的最终目的不是出一份好看的报告，而是建立"发现问题→定位根因→产出修复→验证效果→沉淀资产"的持续运转机制。一条Badcase要转化为回归用例、配置修复、训练数据三类资产；最终沉淀六大质量资产库（用例库、Trace库、根因标签库、修复建议库、Judge校准集、回归集），让Agent迭代脱离"个人经验+临时救火"模式。
