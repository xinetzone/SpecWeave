## 第一节：三条洞察（G2 PASS）

### I-1 冲刺式节奏：322 次提交 93.2% 集中于 13 天

- **陈述**：322 次提交中 300 次（93.2%）集中于 07-24 ~ 08-06 的 13 天内，单日峰值达 69 次（07-31），随后出现近 11 天低活跃（08-07 ~ 08-17），呈现"冲刺-空窗"交替的提交节奏。
- **证据**：F-004（峰值 69 次）、F-005（次高峰 41/37/32 次）、F-006（低活跃 2/1/1 次）、F-007（13 天占比 93.2%）。
- **反常识**：端午后三周即产出七成以上提交，且中间存在接近两周接近零提交的空窗——理想化的"匀速推进"并未出现，实际以爆发式冲刺为主。
- **行动**：建立提交节奏观察告警（ACT-01，采纳 V-1 修正版：空窗 ≥3 天仅记录、不强制打断），并在下个里程碑规划时将冲刺-空窗成因纳入风险评估（ACT-04，采纳 V-7）。

### I-2 质量前置：test+fix 投入（38.2%）反超 feat 投入（26.1%）

- **陈述**：test + fix 类型提交合计 123 次（38.2%），超过 feat 84 次（26.1%）；质量基线为核心模块测试覆盖率 ≥90%、一般 ≥80%、mypy 零新增告警、ruff 零错误，质量投入与功能开发并行走而非后置补课。
- **证据**：F-008（feat 84）、F-009（test 62 + fix 61 = 123）、F-024（覆盖率双基线）、F-025（mypy 零新增）、F-026（ruff 零错误）。
- **反常识**：按常规经验功能开发应占据提交主体（feat 第一），而本仓库质量类提交（test+fix）以 12 个百分点的差距高居首位，与"先功能后补测试"的常见路径相反。
- **行动**：将 test+fix 提交占比 ≥30% 设为 caffe-ffi/layers 的质量投入门禁监测指标，由 CI 输出质量投入周报（ACT-02，且纳入 G4 行动项表，采纳 V-5）。

### I-3 结构重心：caffe-ffi 单包独占 37.9% 提交

- **陈述**：scope 为 caffe-ffi 的提交达 122 次（37.9%），scope 前五合计 185 次（57.5%）；同时 libs/tvm-book、vendor/caffe、vendor/tvm-ffi 三个子模块均未初始化，"多包 monorepo"定位与实际开发重心形成剪刀差。
- **证据**：F-010（caffe-ffi 122）、F-011（前五 185，57.5%）、F-016（三子模块未初始化）、F-021（多包管理器 PDM/uv/pip 支撑多包结构）。
- **反常识**：号称多包 monorepo，但超过三分之一的提交集中在单一子包 caffe-ffi，其余若干包与三个子模块处于低频或未初始化状态——结构声量与实际投入并不匹配。
- **行动**：建立 caffe-ffi 单点风险日历，登记 API 破坏性变更窗口与外部依赖接入节点（ACT-03）；子模块初始化状态纳入季度检查节点（ACT-05，采纳 V-8）。

## 第二节：模式文档（G3 PASS）

### 模式名称：双轨演进制

- **成熟度**：L1（单案例验证，待二次案例确认升级 L2）
- **一句话定义**：在依赖生态尚不成熟的阶段，采用"内部化实现先行、外部依赖后置"的双轨策略——先在本仓库内以自研/内聚方式打通主链路，待外部依赖（上游库、子模块、标准构建工具链）成熟后再切换轨道，两条轨道按依赖成熟度渐进切换。

#### 触发边界

- 场景：monorepo 初始化与主链路打通阶段
- 适用条件：① 外部依赖存在可用性/稳定性风险（上游库未就绪、子模块未初始化、构建链不统一）；② 主链路关键路径依赖这些外部组件；③ 内部已具备替代实现（或可快速搭建内聚实现）的能力
- 不适用：已进入稳态迭代、外部依赖稳定可依赖的成熟仓库

#### 核心做法（5 步）

1. 盘点外部依赖成熟度，标记高风险的依赖轨道（子模块、上游库、构建链）
2. 对高风险依赖，先在仓库内部铺设内聚实现轨道（如自研 COW 切片路径、内部构建后端统一）
3. 以**契约（测试）先行**锁定轨道接口：先写端到端/边界测试，再推进机制实现（采纳 V-3 次序补充）
4. 渐进切换：外部依赖就绪一项、切换一项，切换以全量测试通过为准入条件
5. 记录切换台账：登记每项依赖的初始化/切换日期与验收依据，供后续审计

#### 反模式（4 个）

1. 外部依赖先行：依赖未就绪即强推接入，导致阻塞主链路（空窗期延长）
2. 双轨并行永不合轨：内部实现完成后未及时切换，长期维护两套轨道
3. 切换无验收：外部依赖就绪后未经测试即切换，引入行为漂移
4. 轨道未记录：切换过程无台账，事后无法追溯"为什么 x 用了内部实现"

#### 检验标准

- 主链路可在外部依赖缺失状态下持续演进（构建可运行、测试可通过）
- 每一轨道切换均有对应测试全量通过证据与台账记录
- 仓库骨架（构建后端、目录结构、多包管理）先行统一，再叠功能开发

#### 跨场景迁移

- **前端 monorepo**：组件库 + 业务包的初始化阶段，若图标库/UI 基础库未发版，先在仓库内以内部组件兜底，依赖发版后按接口契约切换
- **微服务架构**：核心服务依赖的上游 SDK 未稳定时，先以内部桩/适配层打通链路，上游稳定后替换为正式 SDK，以契约测试保证切换安全

#### 多案例支撑

- L1：仅 xuanspace 单案例（scikit-build-core 统一先行 → COW/Backward 机制内部实现 → 子模块后置），等待第二个案例验证后升级 L2
