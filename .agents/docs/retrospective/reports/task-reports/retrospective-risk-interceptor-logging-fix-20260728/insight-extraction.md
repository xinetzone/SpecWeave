# 洞察萃取：风险拦截器日志测试与修复

## 洞察1：CLI安全工具必须采用「默认静默+分级verbose」日志架构

**现象**：初版实现中verbose=0（默认模式）仍挂载StreamHandler，导致WARNING级诊断信息（如"风险等级CRITICAL >= 阻断阈值HIGH"）输出到stderr，在CI流水线中产生日志前缀噪音。

**本质**：CLI工具有两类输出消费者——
- **人类/CI系统**（消费stdout）：需要干净的业务结果（PASS/FAIL/拦截模板），不接受诊断日志
- **开发者/调试者**（消费stderr）：需要详细的决策过程日志

两类消费者的需求是互斥的，不能用同一个handler配置兼顾。

**可复用原则**：
1. 默认模式（无-v）：业务输出→stdout（print），诊断日志→完全静默（NullHandler）
2. -v（INFO）：关键流程节点（开始/结束/最终判定）→stderr
3. -vv（DEBUG）：完整决策链路（每个匹配、每个中间计算、每个规则触发）→stderr
4. 日志handler在verbose=0时不挂载，仅在verbose≥1时挂载格式化handler
5. 日志level在verbose=0时设为CRITICAL+1，防止任何日志泄漏

**适用场景**：所有需要集成到CI/CD流水线的CLI安全/质量门禁工具。

**反模式**：在默认模式下输出任何非业务结果信息（包括WARNING），都会在自动化消费场景中造成噪音。

## 洞察2：多模式匹配系统的展示层必须做信号去重

**现象**：`DROP DATABASE` 被两个不同的危险模式命中（模式#1"数据库删除/清空操作"和模式#10"数据库系统级修改/删除"），`rm -rf /` 因命令行中出现两次也重复命中模式#0，导致拦截模板中出现重复条目。

**本质**：规则系统的本质是"多个独立规则独立扫描同一输入"，这种设计必然导致同一输入片段被多个规则命中。这不是bug，而是规则系统的正常行为——但在**展示层**必须去重，否则用户体验混乱。

**可复用原则**：
1. 规则层保持独立匹配，不做去重（不同规则可能有不同的严重度和描述，都是有价值的信号）
2. 展示层（模板/UI/报告）必须按 `(description, matched_text)` 二元组去重
3. 去重后按严重度降序排序，截断到Top N（如5个）避免信息过载
4. 在DEBUG日志中记录去重统计（如"去重后显示5/11个信号"），便于验证去重逻辑正确性

**适用场景**：所有基于多规则/多模式扫描的检测系统（SAST/DAST/敏感信息扫描/风险拦截/Lint工具等）。

## 洞察3：可解释的权重算法优于随机/插入顺序选择

**现象**：初版使用 `next(iter(set))` 从匹配的风险类别中"随机"选择主要类别来匹配回滚方案。当filesystem和database两个类别都有CRITICAL信号时，有时选database（回滚建议是"先备份数据库"），有时选filesystem（回滚建议是"先备份文件"），结果不稳定。

**本质**：当多个候选项需要排序选择"最主要"的一个时，使用 `set` 的迭代顺序或字典插入顺序是**不可预测的**——它依赖于Python版本、哈希种子、插入顺序等偶然因素，导致相同输入可能产生不同输出。这在安全工具中是不可接受的非确定性。

**可复用原则**：
1. 使用**可解释的权重算法**替代随机/顺序选择
2. 安全领域中，**严重度平方加权**（severity²）是有效策略：CRITICAL(4)²=16, HIGH(3)²=9, MEDIUM(2)²=4，平方放大了高严重度的权重
3. 同分平局时按类别优先级（如filesystem > database > git > security > container > permissions）打破平局，而非依赖插入顺序
4. 在DEBUG日志中输出权重分布（如 `{'filesystem': 32, 'database': 32, 'git': 18}`），让决策过程完全可审计

**适用场景**：风险评估、告警去重、告警聚合、安全事件分类、任何需要从多信号中选择"最主要"项的决策系统。
