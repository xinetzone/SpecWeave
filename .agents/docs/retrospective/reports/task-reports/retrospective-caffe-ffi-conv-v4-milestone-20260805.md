# Conv v4 OpenMP并行优化里程碑复盘

## R：复盘事实清单（G1门检查）

### 优化策略
- F-001: Conv v4策略为沿输出通道(M)维度分块并行，最小分块32通道
- F-002: Conv v4每个线程处理一个通道块的GEMM+Bias融合计算
- F-003: Conv v4中im2col单线程执行
- F-004: Conv v4自适应线程数公式为num_chunks = min(max_threads, M/32)
- F-005: GEMM计算和bias加法在同一个parallel for内完成
- F-006: im2col为内存绑定操作，占计算量<5%

### 环境配置
- F-007: OMP_NUM_THREADS=4为batch=1时ResNet-50最优性价比配置
- F-008: OPENBLAS_NUM_THREADS=1为必需配置
- F-009: 多线程BLAS在53+个小GEMM调用场景下出现3-11x性能退化
- F-010: OMP_WAIT_POLICY=PASSIVE在一键脚本v5之前未全局导出
- F-011: OMP_WAIT_POLICY=PASSIVE在一键脚本v5之前仅部分子进程正确设置
- F-012: OMP_PROC_BIND不设置（让OS调度）在混合P-core/E-core架构(Core Ultra 9 285H)上表现更优

### 性能数据
- F-013: batch=1时ResNet-50（53个Conv层，224×224）OMP=1约90ms，OMP=4约70ms
- F-014: batch=1时InceptionV1（57个Conv层，224×224）OMP=1约72ms，OMP=4约56ms，OMP=2出现0.90x减速
- F-015: batch=1时ResNet-101（104个Conv层，224×224）OMP=4约334ms（随机权重测试）
- F-016: batch=16时InceptionV1在OMP=4下CV%达41.2%
- F-017: batch=16时InceptionV1尾延迟比P99/P50达2.33x
- F-018: 8线程及以上batch=1时串行BN/ReLU/FC占45-55%
- F-019: batch=16时更多线程仍可受益

### 稳定性指标
- F-020: CV%（变异系数）阈值定义：<2%优秀，2-5%良好，5-10%一般，>10%不稳定
- F-021: 尾延迟比P99/P50阈值定义：<1.3优秀，1.3-1.6良好，1.6-2.5一般，>2.5不稳定

### 问题诊断
- F-022: ResNet-101 caffemodel缺失，使用随机权重(caffemodel=None)验证计算模式
- F-023: Python命令引号转义错误，将测试逻辑写入独立.py文件解决
- F-024: 环境变量OMP_WAIT_POLICY遗漏，在v5脚本开头添加全局export
- F-025: 创建bench_jitter_diagnose.py诊断InceptionV1 batch=16延迟抖动的16种配置组合
- F-026: fgvsirfeature模型输入120×120，第一个Conv层num_output=16（<32最小分块），触发自适应线程数降级
- F-027: fgvsirfeature_ssd模型输入32×32，模型仅251KB
- F-028: 框架默认存在调试统计循环（遍历所有元素计算min/max/norm）

### SDK模型
- F-029: fgvsirfeature为人脸嵌入模型，1×3×120×120输入，约64个Conv层，通道16→32→64→128→256渐进式残差网络，输出为S_Eltwise34
- F-030: fgvsirfeature_ssd为人脸检测SSD模型，1×3×32×32输入，基于SqueezeNet，第一个Conv num_output=16
- F-031: SDK caffemodel已转换为caffe-ffi格式（.caffe-ffi.caffemodel）

## I：核心洞察（G2门检查）

### 洞察1：并行扩展性与模型粒度/计算密度的强相关性
- **陈述**：OpenMP并行加速比并非随线程数线性增长，而是强依赖于单个Conv层的计算粒度（输出通道数M）和非Conv层的串行占比；小模型、浅层网络、小batch场景下多线程甚至可能出现负收益。
- **证据**：F-004（M<32触发线程数降级）、F-014（OMP=2出现0.90x减速）、F-018（8线程以上Amdahl定律限制）、F-026（首个Conv层M=16触发降级）、F-027（32×32输入251KB极小模型）
- **反常识**：挑战了"线程越多越快"的默认假设——在混合P-core/E-core的现代CPU上，2线程反而比单线程慢，4线程是batch=1的甜蜜点；小模型并行收益为负不是bug，是物理规律。
- **行动**：实现自适应线程数选择逻辑——根据batch size、模型总层数、首层/典型层通道数自动选择OMP_NUM_THREADS（batch=1默认4，batch≥16默认8），并在模型加载时检测M<32的层占比，对小模型自动降级为单线程。

### 洞察2：环境变量配置的系统性风险——局部设置≠全局生效
- **陈述**：OpenMP/BLAS环境变量存在"配置漂移"风险——父进程设置的变量不一定能传递到所有子进程，脚本中局部export不等于全局生效，一个变量遗漏即可导致3-11x的性能回退。
- **证据**：F-008/F-009（OPENBLAS_NUM_THREADS=1缺失导致11x退化）、F-010/F-011（OMP_WAIT_POLICY未全局导出）、F-024（v5脚本才修复全局export）
- **反常识**：挑战了"环境变量设一次就够"的默认假设——在shell脚本、Python子进程、动态库加载的多层调用链中，环境变量是"脆弱的隐形契约"，任何一层fork/exec未正确继承都会导致静默的性能退化，且极难复现和定位。
- **行动**：在推理引擎初始化阶段增加"环境变量自检"——启动时打印所有关键OpenMP/BLAS变量的实际值（而非预期值），对非最优配置输出WARNING；在所有入口脚本（benchmark、SDK、demo）最开头统一source一份envsetup.sh，禁止零散export。

### 洞察3：尾延迟稳定性问题——吞吐优化不等于生产可用
- **陈述**：平均延迟优化（1.3x加速）与尾延迟稳定性（P99/P50=2.33）是两个独立维度；batch增大后OMP线程调度带来的抖动会使CV%超过40%，达到"不稳定"级别，无法满足生产SLA要求。
- **证据**：F-016（batch=16 CV%=41.2%）、F-017（P99/P50=2.33x）、F-020（CV%>10%为不稳定）、F-021（P99/P50>2.5为不稳定）
- **反常识**：挑战了"平均延迟降了就是优化成功"的默认假设——benchmark上的1.3x平均加速如果伴随41%的变异系数，在生产环境的人脸识别/人脸检测场景中意味着偶发的超时、掉帧、用户体验卡顿，这种优化是"benchmark好看但生产不可用"的虚假优化。
- **行动**：将CV%和P99/P50作为与平均延迟同等权重的验收指标；所有性能测试必须输出P50/P95/P99/CV%四个指标而非仅平均值；对batch≥8的场景固定线程亲和性（即使混合架构也要测试OMP_PROC_BIND=true），降低OS调度带来的抖动。

## V：对抗审查

### 魔鬼代言人视角
1. **攻击**：你说OMP=4是最优，但是ResNet-101只有随机权重测试数据，没有真实caffemodel，这个结论真的可靠吗？万一真实权重下OMP=8更好呢？
   - **采纳修正**：在行动项中增加"获取真实ResNet-101 caffemodel补测"，明确标注当前ResNet-101数据为随机权重结果，不作为最终配置依据。
2. **攻击**：im2col单线程执行占<5%计算量，这个数据怎么来的？你实际profiling过吗？万一在某些层im2col占比更高呢？
   - **采纳修正**：增加profiling验证行动项，确认im2col在各模型各层的实际耗时占比。

### 新人视角
1. **攻击**：为什么OPENBLAS_NUM_THREADS=1和OMP_NUM_THREADS=4不冲突？BLAS不也是用OpenMP吗？这两个变量是什么关系？
   - **采纳修正**：在模式萃取中明确区分"应用级并行（Conv层外层OMP）"和"库级并行（BLAS内层OMP）"，解释为什么内层多线程在小GEMM场景下反而有害，补充两者的嵌套关系图。
2. **攻击**：fgvsirfeature_ssd才251KB，这么小的模型为什么还要用深度学习？为什么不直接用传统算法？
   - **采纳修正**：在行动项中增加"极小模型阈值检测"，对模型大小<1MB或输入分辨率<64×64的模型自动禁用多线程并行，直接走单线程路径。

### 老板视角
1. **攻击**：1.3x加速比花了这么久，这个ROI划算吗？为什么不一开始就上更激进的优化方案（比如Winograd、NHWC布局）？
   - **采纳修正**：在复盘中明确记录——v4版本是"最小侵入式优化"，未改动计算逻辑和数据布局，仅通过并行策略和环境调优就获得1.3x加速，风险极低；Winograd/NHWC属于下一阶段优化，有更高的正确性风险。
2. **攻击**：batch=16抖动41%这个问题，会影响线上业务吗？线上batch size是多少？
   - **采纳修正**：补充业务方实际batch size调研行动项，优先优化线上真实batch配置下的稳定性，而非盲目追求大batch吞吐。

### 未来视角（6个月后）
1. **攻击**：6个月后CPU升级到更多核心（比如32核/64线程），现在的4线程最优结论还成立吗？会不会又要重新调一遍？
   - **采纳修正**：在模式中增加"线程数自动探测"步骤——首次运行时在当前硬件上做小规模微基准，自动选择最优线程数，而非硬编码为4。
2. **攻击**：如果后面要支持ARM架构（比如鲲鹏、苹果M系列），这套环境变量配置还能用吗？
   - **采纳修正**：在模式中明确标注x86/ARM差异点——ARM上可能需要不同的WAIT_POLICY和PROC_BIND配置，自动探测逻辑需要区分架构。

## E：模式萃取（G3门检查）

### 模式：CPU推理OpenMP环境变量配置模式

**模式名称**：CPU推理OpenMP双层并行隔离配置模式

**触发场景**：
- 使用OpenMP做CPU深度学习推理优化
- 调用BLAS/GEMM数学库（OpenBLAS、MKL、BLIS等）
- 混合P-core/E-core架构的现代x86 CPU（12代酷睿及以后）
- 对延迟稳定性有要求的生产环境（而非仅benchmark吞吐）

**核心步骤**：
1. **双层并行隔离**：外层（应用层Conv并行）使用多线程，内层（BLAS GEMM计算）强制单线程
   - 设置`OMP_NUM_THREADS=N`（外层并行数，batch=1时N=4，batch≥16时N=8）
   - 设置`OPENBLAS_NUM_THREADS=1`、`MKL_NUM_THREADS=1`、`BLIS_NUM_THREADS=1`（所有BLAS库内层单线程）
2. **等待策略设置**：设置`OMP_WAIT_POLICY=PASSIVE`（或`ACTIVE`，需实测），避免线程自旋浪费CPU核心
3. **线程亲和性策略**：混合P-core/E-core架构不设置`OMP_PROC_BIND`，让OS调度；纯大核架构可测试`OMP_PROC_BIND=CLOSE`
4. **全局生效保证**：在所有进程入口最开头source统一的环境配置脚本，禁止零散export；禁止在Python代码内通过os.environ局部设置
5. **运行时自检**：引擎初始化时打印所有关键环境变量的实际值，检测到非最优配置输出WARNING
6. **自适应线程数**：根据batch size、模型大小、典型层通道数自动选择N——小模型（<1MB）、小输入（<64×64）、首通道<32时N=1
7. **稳定性验收**：所有性能测试必须输出P50/P95/P99/CV%四个指标，CV%<10%、P99/P50<2.0才算验收通过

**反模式**：
1. ❌ **反模式1：线程越多越好**：盲目设置`OMP_NUM_THREADS=物理核心数`，在batch=1小模型场景导致2线程比单线程还慢（F-014），8线程以上Amdahl定律收益递减（F-018）
2. ❌ **反模式2：库级并行全开**：不设置`OPENBLAS_NUM_THREADS=1`，导致BLAS在53+个小GEMM调用场景下产生3-11x性能退化（F-009）
3. ❌ **反模式3：环境变量零散设置**：在脚本不同位置、不同子进程中分别export，导致OMP_WAIT_POLICY等变量未全局生效，出现难以复现的性能抖动（F-010/F-011）
4. ❌ **反模式4：只看平均延迟**：benchmark只看平均延迟/吞吐，不监控CV%和P99/P50，导致优化后生产环境出现偶发超时（F-016/F-017）

**检验标准**：
- 最优线程数配置下，batch=1 ResNet-50加速比≥1.25x
- 所有BLAS库线程数=1，无嵌套并行
- 连续100次推理CV%<10%，P99/P50<2.0
- 引擎启动日志可查看到所有关键环境变量实际值
- 小模型（<1MB）自动降级为单线程，无负收益

**迁移示例**：
```bash
# 正确示例：统一envsetup.sh，入口source
#!/bin/bash
# envsetup.sh - 统一环境配置，所有入口脚本开头source
export OMP_NUM_THREADS=4
export OPENBLAS_NUM_THREADS=1
export MKL_NUM_THREADS=1
export OMP_WAIT_POLICY=PASSIVE
# 不设置OMP_PROC_BIND，让OS在混合架构上调度

# 入口脚本用法：
#!/bin/bash
source ./envsetup.sh
python3 bench.py
```
