# 洞察萃取

## 核心洞察（3条）

### 洞察1：CLI安全工具的"默认静默+分级verbose"日志模式是最佳实践

**观察**：check-risky-commands.py设计了四级日志控制：
- 默认（无-v）：WARNING级别，只在等级升级时输出警告，正常结果无日志
- `-v`（INFO）：显示评估开始/结束、最终判定结果、信号数量
- `-vv`（DEBUG）：显示每个正则模式的命中详情、匹配文本、初始等级、升级规则触发原因
- `-vvv`（TRACE/level 5）：显示未命中的模式（最详细，用于调试正则）

**本质**：CLI工具的日志设计本质是"**信息分层**"问题：
- CI/pre-commit场景需要干净输出（只有PASS/FAIL），不能有噪声
- 调试误报时需要看到决策链的每一步
- 两者之间还有"想知道结果但不需要细节"的中间场景
- stderr/stdout分离确保日志不会污染正常输出（如管道场景）

**可复用性**：适用于所有检查类CLI工具（lint、security scan、quality gate等）。
**反模式**：默认输出大量调试信息、日志和结果混在stdout、没有分级控制。

### 洞察2：安全拦截工具必须是"白盒"——决策过程全程可追踪

**观察**：risk_interceptor.py的日志追踪了完整的决策链：
1. 消息长度、提取到的命令数量
2. 每个操作模式扫描结果（命中/未命中、匹配文本、等级、类别）
3. 每个上下文关键词扫描结果
4. 信号汇总（操作信号+上下文信号统计）
5. 初始最高等级（来自单个信号最大值）
6. 等级升级规则检查（≥2个HIGH→CRITICAL、CRITICAL+生产环境→CRITICAL）
7. 最终等级、主要风险类别、回滚方案匹配
8. 拦截模板生成过程

**本质**：安全工具的**可信度**来自可解释性：
- 如果安全工具是黑盒，用户不知道"为什么被拦截"，会倾向于跳过检查（`--no-verify`）
- 详细日志让用户理解拦截原因，反而提高配合度
- 误报排查必须能看到"哪个正则匹配了哪段文本"，否则无法修复正则
- 等级升级规则必须显式日志化，否则无法理解"HIGH为什么变CRITICAL"

**可复用性**：适用于所有安全/质量拦截工具（敏感信息检测、并发安全检查、模式质量门等）。
**反模式**：只输出"检测到风险"但不说明具体原因、黑盒评分无法解释、决策规则隐式硬编码。

### 洞察3：质量门的"差异化标准"设计——按模式类型应用不同检查强度

**观察**：模式V2质量门设计了差异化检查：
- **执行/协作类模式**（如code-review-checklist、atomic-commit）：只做基本结构检查（标题、章节、迁移案例），不强制失败案例
- **创新/跨领域类模式**（如reverse-adaptation-innovation、action-first-output-paradigm）：强制V2检查——≥1个失败案例（error阻断）、≥3类反目标用户（error阻断）、预警信号（warn）、边界条件（warn）
- 通过`INNOVATION_TYPE_KEYWORDS`正则自动识别模式类型，无需人工标注

**本质**：质量门的本质是**风险与成本的平衡**：
- 执行类模式是经过验证的最佳实践，失败案例已经被充分记录，不需要每次新增都强制失败案例
- 创新类模式是从少量案例中提炼的，存在"成功偏误"和"确认偏误"的高风险，必须强制反向检查
- 差异化标准避免了"一刀切"导致的过度约束（执行类模式被要求写不存在的失败案例）
- error级阻断提交 vs warn级提示的区分，平衡了"必须做"和"建议做"

**可复用性**：适用于所有分层质量检查场景（代码review checklist、文档质量门、测试覆盖率要求）。
**反模式**：所有类型统一标准、不区分风险等级、warn和error没有区别。

## 5-Whys根因分析（为什么本次开发效率较高）

1. **Why**：开发过程顺利，2个原子提交一次通过pre-commit？
   → 因为遵循了先做功能开发、再测试验证、再提交的流程
2. **Why**：功能开发中遇到的问题（NameError、logger配置）都能快速定位修复？
   → 因为Python的错误栈清晰，且使用了语法编译验证（py_compile）在提交前发现问题
3. **Why**：没有出现大的设计返工？
   → 因为V2改进建议在分析报告中已经明确了需求（失败案例、反目标用户、四步拦截模板），开发前理解清楚了
4. **Why**：需求清晰？
   → 因为i-have-adhd文章V2分析做了对抗审查（成功偏误+确认偏误攻击），明确了缺失项

   → 因为它强制要求"找反面证据"，打破了"只看成功案例"的认知闭环
