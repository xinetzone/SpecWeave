## 一、任务背景与目标

### 初始需求

用户要求使用 seven-concepts-cmd 技能，对 `d:\spaces\SpecWeave\projects` 和 `d:\spaces\SpecWeave\apps` 两个文件夹的边界进行系统性探索与分析，明确功能职责划分、数据交互方式及依赖关系，并在此基础上对 `AGENTS.md` 和 `.agents/` 文件夹进行全面优化。

## 三、关键决策记录

### 决策 1：apps/ 区域需要独立 AGENTS.md

**背景**：探索发现 vendor/ 和 projects/ 都有自己的 AGENTS.md，但 apps/ 缺失。

**选项分析**：
- A. 不创建，让 apps/ 直接遵循根规范 → 破坏结构对称性，apps 内应用无路由入口
- B. 创建简化版 AGENTS.md，仅包含路由表 → 符合现有模式，维护成本低
- C. 创建完整规范体系（roles/rules/workflows）→ 过度设计，apps 内应用可按需扩展

**决策**：选择 B，创建与 projects/vendor 对称的入口路由文件。

**依据**：
- 遵循"嵌套优先"路由原则，保持三层架构一致性
- 渐进式披露：入口文件只做路由，详细规范由应用自行决定是否建立
- 参考 projects/AGENTS.md 和 vendor/AGENTS.md 的成熟模式

### 决策 2：重构启动协议覆盖全部三区域

**背景**：原启动协议步骤 2.1 只判断 vendor/ 区域，apps/ 和 projects/ 未被覆盖。

**选项分析**：
- A. 保持现状，在步骤 2.0 任务类型预检中补充 → 路由逻辑分散，不符合"嵌套优先"原则
- B. 重构步骤 2.1，按顺序判断 apps/projects/vendor 三区域 → 统一路由判断逻辑
- C. 新增步骤 2.2 专门处理 apps/projects → 增加协议复杂度

**决策**：选择 B，重构步骤 2.1 为统一的三区域判断流程。

**依据**：
- 保持启动协议的简洁性，所有子区域路由判断集中在一处
- 明确"三层路由体系"概念：SpecWeave → 子区域 → 子应用/子项目/子模块
- 退出子区域后恢复 SpecWeave 路由，避免路由状态污染

### 决策 3：添加四大顶层区域对比表

**背景**：三区域（.agents/apps/projects/vendor）的管理方式、版本控制、可修改性差异需要明确说明。

**选项分析**：
- A. 不添加，靠各区域 AGENTS.md 自行说明 → 全局视角缺失，边界不清晰
- B. 在根 AGENTS.md 添加对比表格 → 一目了然，全局边界清晰
- C. 在独立文档中详细说明 → 入口文件缺少关键信息，违背渐进式披露

**决策**：选择 B，在根 AGENTS.md 添加对比表格。

**依据**：
- AGENTS.md 作为最高优先级入口，应包含最核心的边界信息
- 表格形式信息密度高，适合快速查阅
- 明确标注各区域"是否可直接修改"，避免误操作 git submodule

## 四、遇到的问题与修复

### 问题 1：apps/ 缺少 AGENTS.md 入口文件

**现象**：三区域结构不对称，apps/ 应用无统一路由入口。

**根因**：项目演进过程中，apps/ 作为后来新增区域，未同步建立与 projects/vendor 对称的路由体系。

**修复**：设计并创建 apps/AGENTS.md，包含应用路由表、区域性质说明、边界声明、跨应用调用规范。

**验证**：与 projects/AGENTS.md、vendor/AGENTS.md 结构对比，确认对称性完整。

### 问题 2：启动协议仅覆盖 vendor/ 区域

**现象**：智能体在 apps/ 或 projects/ 目录下工作时，无法正确触发子区域路由。

**根因**：初始启动协议设计时只考虑了 vendor flexloop 场景，未扩展到全部子区域。

**修复**：重构启动协议步骤 2.1，按 apps → projects → vendor 顺序判断，建立统一三层路由体系。

**验证**：添加四大区域对比表，明确各区域入口；逻辑覆盖所有工作目录场景。

### 问题 3：apps/ 与 projects/ 边界不清晰

**现象**：两者都是代码目录，但管理方式本质不同（同仓库 vs submodule），文档中未明确说明。

**根因**：边界定义只存在于隐式约定中，未显式文档化。

**修复**：
- 在 apps/AGENTS.md 中添加"区域性质"章节，明确 apps/ 是主仓库内置应用（同仓库直接管理），projects/ 是第一方子项目（git submodule 自主管理）
- 在根 AGENTS.md 对比表中明确标注管理方式、版本控制、是否可直接修改

**验证**：通过阅读文档可明确区分两类目录的操作规范。

### 问题 4：链接检查脚本未扫描目标文件

**现象**：初次运行链接检查时未发现新增文件中的链接，因为路径参数不正确。

**根因**：使用默认路径扫描，未指定新创建的文件。

**修复**：调整命令直接指定要扫描的文件，使用 --auto 标记配合原子提交流程。

**验证**：手动验证所有新增链接格式正确，相对路径有效。
