# 可复用模式沉淀与行动建议（E阶段）

## 一、可复用架构模式

### 模式 1：三层路由协议（Three-Layer Routing Protocol）

**问题**：在多层嵌套的工作区结构中，智能体如何知道当前应该遵循哪套规范？

**解决方案**：建立统一的三层路由判断流程：

```
第一层：SpecWeave 根路由（AGENTS.md）
  ↓ 判断当前工作目录所在区域
第二层：子区域路由（apps/AGENTS.md | projects/AGENTS.md | vendor/AGENTS.md）
  ↓ 判断具体子应用/子项目/子模块
第三层：子模块路由（如 apps/zhujian-wudao/AGENTS.md）
```

**适用场景**：
- 具有多个同构子区域的 monorepo 或多项目工作区
- 需要根据工作目录动态切换规范上下文的 AI 智能体系统
- 任何"入口→子入口→具体模块"的分层路由场景

**实现要点**：
1. 每层入口文件必须包含"路由表"——子模块名称到入口文件的映射
2. 路由判断是数据驱动的（遍历路由表），而非硬编码条件分支
3. 退出子区域后必须恢复上层路由状态
4. 新增子区域/子模块时，只需在上层路由表中添加一行

**模式成熟度**：✅ Level 3 - 已在本次任务中验证，可直接复用

**沉淀位置**：建议归档至 `.agents/docs/retrospective/patterns/architecture-patterns/three-layer-routing-protocol.md`

### 模式 2：对称目录结构设计（Symmetric Directory Structure）

**问题**：新增目录/区域时，如何确保架构一致性，避免"特殊例外"累积成技术债务？

**解决方案**：为同构区域定义"最小结构模板"，所有区域必须满足该模板：

```
<region>/
├── AGENTS.md          # 必须有：区域入口路由
├── .agents/
│   └── README.md      # 必须有：元数据容器说明（即使为空）
└── README.md          # 建议有：区域概览，包含智能体入口引用
```

**对称检查表**（新增区域时必过）：

- [ ] 该区域是否有自己的 AGENTS.md 入口文件？
- [ ] AGENTS.md 是否包含：区域性质说明、子模块路由表、边界声明？
- [ ] 上层路由表是否已注册该区域入口？
- [ ] 根 AGENTS.md 的四区域对比表是否需要更新？
- [ ] context-routing.md 是否需要添加该区域的任务类型路由？
- [ ] 该区域的 README.md 是否包含智能体入口引用？

**适用场景**：
- 多区域/多模块架构的初始设计
- 新增顶层目录时的架构评审
- 架构重构时的对称性校验

**反模式**："这个目录暂时不需要 AGENTS.md，先这样吧"——结构债务的开始。

**模式成熟度**：✅ Level 3 - 已在本次任务中验证（apps/ 补齐对称结构）

**沉淀位置**：建议归档至 `.agents/docs/retrospective/patterns/methodology-patterns/governance-strategy/symmetric-directory-structure.md`

### 模式 3：入口对比表模式（Entry Comparison Table Pattern）

**问题**：多个同构区域有不同的约束、管理方式、版本控制策略，如何让用户/智能体一眼看清差异？

**解决方案**：在顶层入口文件中放置一个高密度对比表，一行一个区域，一列一个关键维度：

```markdown
| 目录 | 用途 | 管理方式 | 版本控制 | 是否可直接修改 | AGENTS.md入口 |
|---|---|---|---|---|---|
| .agents/ | ... | ... | ... | ... | ... |
| apps/ | ... | ... | ... | ... | ... |
| projects/ | ... | ... | ... | ... | ... |
| vendor/ | ... | ... | ... | ... | ... |
```

**设计原则**：
1. **列维度选择**：选择最容易出错、最需要明确的维度（而不是所有维度）
2. **单元格简洁**：用 ✅/❌ 图标 + 短语，避免长段落
3. **边界信息优先**："是否可直接修改"这类权限/约束信息必须在表中
4. **入口链接**：最后一列必须是对应 AGENTS.md 的链接，形成导航闭环

**适用场景**：
- 顶层入口文件（如根 AGENTS.md）
- 多个并列组件/区域的差异说明
- 权限矩阵、环境差异矩阵等

**模式成熟度**：✅ Level 3 - 已在本次任务中验证有效

**沉淀位置**：建议归档至 `.agents/docs/retrospective/patterns/methodology-patterns/document-architecture/entry-comparison-table.md`

### 模式 4：启动协议自检清单（Startup Protocol Checklist）

**问题**：智能体/人在开始工作前，如何确保已经完成了必要的上下文加载，不会因为"凭经验"而跳过关键步骤？

**解决方案**：在启动协议末尾设置一个强制自检清单，用复选框形式列出必须确认的项目：

```markdown
## 步骤 3.5（自检·必做）

加载 Skill 或开始生成产出物之前，逐项确认：
- □ 当前任务类型是否命中 vendor 方法论资产？...
- □ 是否已完成内容敏感度预检？...
- □ 是否已读取上下文路由表中所有相关入口？...
- □ 是否有相关 Skill 应被加载？...
- □ 若在子区域内，是否已读取对应区域 AGENTS.md？...
```

**设计原则**：
1. **动作导向**：每条以动词开头，问"你是否做了 X"，而非"X 是否重要"
2. **全覆盖**：覆盖启动流程中所有不可逆决策点（加载错规范、放错路径都很难回滚）
3. **可审计**：自检清单本身就是执行记录，出问题时可以回溯哪一步漏了

**适用场景**：
- 任何多步骤工作流的入口点
- AI 智能体的 system prompt 启动序列
- 高风险操作前的确认步骤

**模式成熟度**：✅ Level 4 - 已在项目中广泛应用，本次进一步完善了子区域检查项

## 二、方法论文档更新建议

### 建议 1：更新 context-routing.md，添加"新增区域检查清单"

**优先级**：高

**位置**：`.agents/context-routing.md`

**内容**：在文档末尾添加"新增顶层区域 SOP"，包含模式 2 中的对称检查表，明确新增 apps/projects/vendor 之外的第五个区域时必须完成的步骤。

---

### 建议 2：在 capability-registry.md 中注册"三层路由协议"

**优先级**：中

**位置**：`.agents/capability-registry.md`

**内容**：将三层路由协议注册为系统能力，标记其成熟度为 Level 3，关联本次复盘报告作为参考案例。

---

### 建议 3：为 AGENTS.md 模板添加"区域性质"章节

**优先级**：中

**位置**：`.agents/templates/` 下的 AGENTS.md 模板（如存在）

**内容**：所有区域级 AGENTS.md 必须包含"区域性质"章节，明确说明：
- 该区域与其他区域的本质区别
- 管理方式（同仓库直接管理 / git submodule / 其他）
- 是否可直接修改
- 默认遵循哪套规范

---

### 建议 4：在开发规范中添加"架构对称检查"步骤

**优先级**：中

**位置**：`.agents/docs/development-standards.md`

**内容**：在提交前检查项中添加：如果本次变更涉及新增/重命名顶层目录，必须执行架构对称检查，确保四区域结构保持对称。

## 四、验证与度量

### 本次优化的成功度量

| 度量维度 | 优化前 | 优化后 |
|----------|--------|--------|
| 有 AGENTS.md 的顶层区域 | 2/3（projects、vendor 有，apps 无） | 3/3（全覆盖） |
| 启动协议覆盖区域数 | 1/3（仅 vendor） | 3/3（全覆盖） |
| 顶层区域对比说明 | 分散在各处，不集中 | 统一对比表，一目了然 |
| apps/ 应用路由信息 | 无（需要逐个目录查看） | 集中路由表，10 个应用一目了然 |
| 跨区域边界定义 | 隐式约定，依赖经验 | 显式文档化，四区域对比清晰 |

### 未来验证点

1. **新智能体首次进入 apps/ 目录**：能否在不依赖人工指导的情况下，通过 apps/AGENTS.md 正确路由到目标应用？
2. **新增第五个顶层区域时**：能否按照新增区域 SOP 完成对称结构建立，而不需要再次重构路由协议？
3. **apps/ 下应用建立独立 .agents/ 时**：能否通过更新路由表完成接入，不需要修改启动协议逻辑？

## 五、经验迁移建议

本次提炼的模式可迁移到以下场景：

| 迁移目标场景 | 可复用模式 | 适配要点 |
|-------------|-----------|----------|
| 多环境配置管理（dev/staging/prod） | 对称目录结构 + 入口对比表 | 每个环境有独立配置入口，顶层对比表列差异 |
| 微服务架构文档 | 三层路由协议 | 服务→模块→组件三层路由，每个服务有入口文档 |
| CI/CD 多阶段流水线 | 启动协议自检清单 | 每个阶段开始前有强制检查项 |
| 插件系统/扩展点架构 | 数据驱动路由原则 | 插件注册表驱动路由，新增插件不改核心逻辑 |
| 多语言/多地区产品文档 | 对称结构 + 对比表 | 每个地区有对称文档结构，顶层对比表列差异 |
