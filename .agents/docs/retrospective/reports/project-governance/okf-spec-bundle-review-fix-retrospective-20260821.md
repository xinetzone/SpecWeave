## 三、洞察环节

### 3.1 关键发现（3 条核心洞察，每条含四元组）

**洞察 1：信任元数据的"真实性"优先级高于"形式完备性"**
- **陈述**：OKF 允许 `machine-confirmed` 信任层级，但前提是该 `process:<id>` 可由独立第三方复核；只填 `verified` 字段而不登记进程，是自证其说的戳记而非信任凭证。
- **证据**：为确立可复核语义，需额外登记 47 行进程文档（F: 新增 seven-concepts-v.md），并统一 20 处 `verified.by` 指向（F2/F3）。
- **反常识**：字段填充齐全 ≠ 信任真实。没有可复核的进程定义，元数据越"完备"越具误导性（P1 正是假知产真伪装）。
- **行动**：凡使用 `machine-confirmed` 信任层级，必须登记对应进程并给出独立复现路径与核验记录。

**洞察 2：溯源自包含使知识包获得脱离宿主仓库的自洽性**
- **陈述**：`sources[].resource` 指向外部 URL 时，bundle 一旦脱离仓库即失去溯源能力；改为 bundle 内引用后自包含、可分发、可离线校验。
- **证据**：P2 提交将 18 个内容文档的 resource 与脚注改为 `references/okf-spec.md`，grep 确认 19 处引用一致（F8）。
- **反常识**：指向"更权威的外部源"看似更可信，实则牺牲可移植性；自包含引用 + 单一权威信源登记，才是可分发知识包的正确形态。
- **行动**：新建/迁移知识包时执行"溯源自包含"预检，所有资源引用优先 bundle-relative。

**洞察 3：语义无关的环境编码问题成为标准化交付的隐藏摩擦点**
- **陈述**：PowerShell 默认 GBK 编码导致 `git commit -m` 中文乱码，需借助 UTF-8 临时文件 + `-F` 规避。
- **证据**：终端 `git log` 对中文提交显示乱码（如 `淇′换鍏冩暟鎹`）；过程需多次构造提交消息文件（F12）。
- **反常识**：与内容语义无关的编码问题，却成为跨平台中文仓库的标准交付摩擦点。
- **行动**：凡涉及中文提交统一使用带 UTF-8 处理的提交封装（`git-commit-utf8.py`），避免裸 `git commit -m`。

### 3.2 规律认知

```
信任元数据真实化规律：
信任值 = 字段值(✓) × 可复核性(✓)　　※ 两者缺一，machine-confirmed 即降级为自证

溯源自包含规律：
可移植性 = 资源引用自洽(✓) × 权威信源唯一(✓)　　※ bundle 可脱离宿主分发

原子提交规律：
可审计性 = 单一职责(✓) × 独立验证(✓) × 时间连续(✓)
```
