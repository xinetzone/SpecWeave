# 代码优化入门指南考核测试题

> 🎯 **目的**：验证新成员对代码优化安全方法论的掌握程度
> ⏱️ **答题时间**：30分钟
> ✅ **通过标准**：正确率≥80%（选择题≥16/20，场景题≥3/4）
> 📋 **形式**：闭卷，答题后可查阅指南核对答案

## 一、单项选择题（每题4分，共80分）

### 基础概念

**1. 以下哪个是开始优化前最重要的第一步？**
- A. 直接改代码，快速看到效果
- B. 建立性能基线，保留原有代码路径
- C. 写好设计文档，评审通过再动手
- D. 选一个最酷的优化算法用上

**2. Knuth说"过早优化是万恶之源"，这句话的正确理解是？**
- A. 永远不要优化代码，等用户投诉再说
- B. 没有profile数据证明是瓶颈前，不要凭感觉优化
- C. 优化代码是邪恶的，应该追求代码简洁而非性能
- D. 项目最后阶段再做优化

**3. 关于"分阶段优化"，以下哪个说法是正确的？**
- A. 只要分阶段就安全，不需要额外检查
- B. 分阶段本身不保证安全，每个阶段通过质量门验证才安全
- C. 分阶段会增加工作量，应该一次性完成
- D. 分阶段只适用于大型项目，小项目直接改就行

**4. 以下哪个是"数学等价场景"的最佳例子？**
- A. 把循环里的`i++`改成`++i`（性能微优化）
- B. Split层只有1个输出时，输出Tensor和输入Tensor是同一个，零拷贝数学上100%正确
- C. 用快速排序替代冒泡排序

**5. 双开关回退策略中的"运行期开关"主要用于什么场景？**
- A. 编译时验证优化是否正确
- B. 线上出问题时即时回退，不需要重编译
- C. 开发阶段调试用
- D. 单元测试中控制分支覆盖

## 二、场景分析题（每题5分，共20分）

### 场景1

你接手了一个项目，发现`Blob`类有以下代码：

```cpp
// 原有代码
void* Blob::mutable_cpu_data() {
    return data_;
}

// 新同事优化后
void* Blob::mutable_cpu_data() {
    if (use_count_ > 1) {  // 新增COW逻辑
        DeepCopy();
    }
    return data_;
}
```

**问题**：
1. 这个优化有什么风险？（2分）
2. 应该怎么做更安全？（3分）

**问题**：

### 二、场景分析题参考答案

**场景1参考答案**：
1. 风险：这是**隐式行为变更**——原有调用mutable_cpu_data()的地方可能只是拿到指针但不写（很多代码会拿non-const指针但实际只读），现在会无意中触发DeepCopy导致性能下降，且bug很难定位；同时没有回退开关。
2. 安全做法：
   - 保留原有`mutable_cpu_data()`语义不变（不触发COW）
   - 新增显式方法如`cpu_mutable_data_cow()`（或遵循const-correctness：const `cpu_data()`只读、non-const `cpu_mutable_data()`触发COW）
   - 加编译期+运行期双开关
   - 先迁移少量调用点验证

**场景2参考答案**：
1. 风险：23个文件一次性改动，一旦出bug无法二分定位是哪个Layer的问题；没有回退开关的话出问题只能整体回滚；CI通过不代表边界case都覆盖了。
2. 正确推进方式：
   - Phase 0：保留原有路径，加开关
   - Phase 1：先只改Split一个Layer（数学等价N=1场景），加完整测试
   - Phase 2：验证COW机制稳定
   - Phase 3：每个PR改1-3个Layer，逐步迁移
   - 每个Phase结束后跑完整测试，做回退演练

**场景3参考答案**：
1. 防止方式：不要只在群里/wiki里说"PATH太长会出错"——这是被动的，新人还是会踩。应该写**预检脚本**主动检测，构建前自动运行。
2. 具体做法：
   - 在verify_build.ps1或check_env.py中加PATH长度检测
   - 接近32KB限制时输出WARNING并给出修复建议（conda clean --all）
   - 集成到CMake配置阶段或构建脚本第一步，自动运行
   - 同时预检其他常见Windows问题（DLL缺失、vcvars环境等）

**场景4参考答案**：
1. 问题：**过度设计**，违反核心洞察1（优先复用框架已有机制，不要重复造轮子）。ObjectPtr已经是侵入式引用计数的智能指针，直接别名赋值就能实现零拷贝，不需要自定义。
2. 正确做法：
   - 直接使用ObjectPtr/ShareData()做别名赋值实现共享
   - 代码量减少80%以上，且天然生命周期安全
   - 参考模式：ffi-intrusive-refcount-zerocopy（见 [../../patterns/code-patterns/ffi-intrusive-refcount-zerocopy.md](../../patterns/code-patterns/ffi-intrusive-refcount-zerocopy.md)）
