# 默认范围收敛·显式放开：边界可控的遍历与搜索设计模式

## 模式概述

在设计爬虫、递归扫描器、批量查询、授权系统等「潜在无限扩散」行为时，不应把「最大范围」当作默认行为，而应采用**默认收敛 + 显式放开**的边界控制：默认行为收敛到最小合理范围（seed 路径段、当前目录、只读、最小权限），仅当用户通过显式参数（flag/opt-in 开关）才放开边界。

**核心洞察**：凡是「无参数就可能扩散失控」的操作，默认值应设为「最小充分范围」而非「最大能力」。默认收敛能保护用户免受无意识扩散的副作用（bundle 体积爆炸、token 消耗失控、权限泄漏、结果噪声）；显式放开则让高级用户在明确知情的前提下可控地扩展边界。

该模式由 okf-kit v0.3.3 的爬取 scope 实践验证（单案例，L1 待验证）。

**术语说明**：scope（作用域）＝爬取/遍历被允许覆盖的范围边界；seed URL＝用户提供的起始网址；BFS（广度优先遍历）＝从起点逐层向外扩展访问相邻节点的算法；默认收敛＝不传参数时就主动缩小范围；显式放开＝必须用明确参数才能扩大边界。

## 问题现象

遍历/搜索类功能常见的前置门槛失败模式：

1. **无边界全量扩散**：爬虫/扫描器默认爬整站、扫全目录，用户只想爬 `/docs/` 却得到整个域名，bundle/结果体积爆炸
2. **扩散失控**：BFS/递归遍历没有范围上限，遇到环状链接或深层目录时跑飞、卡死
3. **默认过宽暴露**：查询/授权默认给最大范围或最大权限，用户无意识中扩大了暴露面
4. **默认范围不透明**：范围边界对用户隐蔽，用户不知道「默认到底会被访问多少东西」

根因：设计时以「最大能力」作为默认假设，把「放开」当作常态、「收敛」当作例外，而不是默认把边界收到「绝大多数用户真正需要的最小范围」。

## 核心设计模型

### 默认范围的分层语义

| 维度 | 默认行为（收敛） | 显式放开（扩展） |
|------|----------------|-----------------|
| **定义** | 不传任何参数时，收敛到最小充分范围 | 传明确参数后，边界才被扩大 |
| **okf-kit 案例** | 默认只爬 seed URL 的路径段（如 `/docs/`） | 传 `--all-paths` 才爬整个域名 |
| **用户心智** | 「安全、可控、不越界」 | 「我明确要更多，为副作用负责」 |

### 判断方法

对每个可能扩散的行为问一句：**「如果用户不传任何参数、不读任何文档，默认行为会不会跑到比用户预期更远的地方？」** 如果答案是「会」，说明默认范围过宽，需要收窄。

### 两个设计支点

1. **默认收敛**：把默认值设为「最小充分范围」——既不窄到多数用户每次都要手动放开（失去默认充分性），也不宽到会无意识扩散（失去边界可控性）
2. **显式放开**：边界扩张必须通过明确、可发现的参数（如 `--all-paths`、`--recursive`、`--allow-all`）触发，且在放开时让副作用可感知（如提示「将抓取 N 个页面」）

## 与现有模式的区分

模式库中存在多个「默认/收敛」思想的相邻模式，但本模式处理的是「边界范围」这一独立维度：

| 模式 | 分层维度 | 核心问题 |
|------|---------|---------|
| **zero-config-core-enhancement**（零配置核心·可选增强降级） | 前置凭据/配置维度 | 核心功能零配零凭据可用，增强功能可选并降级 |
| **agent-knowledge-graph-navigation**（Agent知识图谱导航） | 知识导航维度 | 分层导航知识，其「导航深度≤3层」是本模式在知识跳转上的一个具体应用 |
| **default-scope-explicit-expansion（本模式）** | 边界范围维度 | 默认收敛到最小范围，显式参数才放开边界 |

**核心区别**：本模式针对「遍历/搜索/查询/授权的边界」——默认多宽才算安全、如何显式放宽。`zero-config-core-enhancement` 处理「配置门槛」维度（会不会被 Key/配置挡住），本模式处理「范围边界」维度（会不会跑得太远）。两者同属「默认保守、显式扩展」的设计哲学，但一个管「能不能用」，一个管「会不会越界」。

## 标准实施步骤

### 步骤1：识别潜在无限扩散行为

- 列出所有「无显式边界就可能跑飞」的操作：BFS 遍历、递归目录扫描、链接跟随、批量查询、授权授予
- 这些操作是本质上的「图遍历」或「集合展开」，天然需要边界约束
- 同时识别遍历中可能触发无限循环的环状结构（如符号链接回环、页面相互引用），作为默认收敛的补充——环路防护应纳入默认行为

### 步骤2：确定「最小充分范围」

- 观察/推断绝大多数用户真正需要的默认范围（如多数人只想爬指定子路径而非整站）
- 修剪标准：默认范围=「刚够完成典型任务」的最小集合，「最小编译集」即可安全驱动。操作性界定：找一个「不传参数完成的典型任务」，若其默认范围是该任务所需范围的两倍以上，则默认过宽

### 步骤3：默认收敛到最小充分范围

- 零参数时主动收窄：爬虫默认 scope 到 seed 路径段、扫描器默认只扫描当前目录、查询默认只读、授权默认最小权限
- 保证「不传参数就安全」，副作用可控

### 步骤4：提供显式放开参数

- 提供明确、可发现的扩张参数（`--all-paths` / `--recursive` / `--allow-all`）
- 放开时让副作用可感知：如「当前将抓取 N 个页面，确认继续？」

### 步骤5：默认范围透明化

- CLI help、README 明确写明「默认范围」与「如何放开」
- 默认边界对用户可见，而非隐藏的魔法默认值

## 反模式（不要这么做）

- ❌ **反模式1：默认全量范围**——默认就爬整站、扫全目录、返回全部结果，用户零参数即扩散失控。后果：bundle 爆炸、token 消耗失控、结果噪声淹没有效信息。应默认收敛到最小充分范围

- ❌ **反模式2：默认范围不可见**——默认边界对用户隐蔽，用户不知道「默认会访问多远」。后果：用户误判副作用，以为「只爬了指定的」，实际「爬了整个域名」。应在 help/文档中明示默认范围

- ❌ **反模式3：放开无副作用提示**——`--all` 后静默放开，不告知将访问的范围/数量。后果：用户在不知情的情况下承受海量抓取/扫描的代价。放开时应提示预期副作用

- ❌ **反模式4：缺放开参数**——想扩展边界却只能改代码或改配置文件，无显式参数。后果：高级用户被迫绕过默认值，反而引入不可控改动。应提供标准放开参数

- ❌ **反模式5：最小范围过窄不充分**——默认范围收得过窄，多数用户每次都要手动传放开参数才能完成典型任务。后果：失去「默认充分」的意义，默认值流于形式。应在「最小」与「充分」之间取得平衡

## 实战案例

### 案例1：okf-kit v0.3.3 爬取 scope（2026-08-18，主验证案例）

**来源**：[okf-kit Wiki 七概念执行报告 · 洞察3](../../../../../docs/knowledge/learning/03-agent-platforms-tools/okf-kit-wiki/seven-concepts-report.md#L66-L70)

okf-kit（OKF 的 Python 实现，v0.3.3）的源码研读确认了「默认 scope 收敛」在真实爬虫中的落地：

1. **默认路径段 scoping**：爬取默认按 seed URL 的路径段自动限制范围——用户传 `https://site/docs/` 就只爬 `/docs/` 子树，而非整站
2. **显式放开**：`--all-paths` 参数才放开边界到整个域名
3. **效果**：避免了 BFS 无边界扩散到整个域名，控制了知识 bundle 的体积

这是本模式的主验证案例，当前为单案例（L1 待验证）。

### 同构先例（未计入 validation_count，作为原则佐证）

- **`find` 命令**：默认不跟随符号链接（`-L` 才跟随），默认不限制深度（`-maxdepth` 可选）——「默认收敛避免环路扩散但允许遍历完整子树，显式放开穿越链接、显式约束深度」
- **`rsync` 命令**：默认不跟随符号链接（`-l` 才复制链接本身）、不递归（`-r` 才递归子目录）——「默认不递归收敛到当前目录，显式递归才下钻」
- **`wget` / `curl` 命令**：默认只抓取指定 URL，不跟随页面内链接扩张——「默认收敛到用户明确指定的资源，显式 `-r` 递归才跟随链接」

这三个先例说明「默认收敛 + 显式放开」是成熟 CLI 生态的通用直觉，但尚未在本项目内形成独立验证案例，故本模式保持 L1。

## 适用边界

### 适用场景

- ✅ 爬虫 / 站点镜像：默认 scope 到 seed 路径，避免爬爆全站
- ✅ 递归目录扫描 / 文件系统遍历：默认当前目录，`--recursive` 才递归
- ✅ 批量数据查询 / 导出：默认受限条数，`--all` 才全量
- ✅ 授权 / 权限系统：默认最小权限，显式申请才扩大
- ✅ 任何「无参数就可能扩散失控」的 CLI / API

### 不适用场景 / 需权衡场景

- ❌ 必须是全量、无边界保留的场景（如整站审计、全量备份）——本质要求「全」，默认收敛反而违背目标
- ⚠️ 需用户明确知情同意的扩散操作（如隐私数据抓取）：不仅需显式参数，还需二次确认或合规审查
- ❌ 默认充分性要求极高、且副作用可忽略的只读查询：过度收敛会徒增用户负担

## 检验标准

| 维度 | 检验点 |
|------|-------|
| 默认收敛 | 零参数时行为收敛到「最小充分范围」，无扩散失控 |
| 显式放开 | 边界扩张必须通过明确参数触发，不靠魔法默认 |
| 范围透明 | help/文档明示默认范围与放开方法 |
| 副作用可感知 | 放开时提示预期范围/数量，用户知情 |
| 充分性平衡 | 默认范围既不空泛（太宽）也不鸡肋（太窄） |
| 环路防护 | 遍历遇到环状结构时不跑飞、不死循环 |
