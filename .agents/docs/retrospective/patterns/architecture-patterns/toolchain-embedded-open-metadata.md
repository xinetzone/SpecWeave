# 工具链嵌入开放元数据：可追溯开放文档的生产级保障

> ⚠️ **成熟度：L1-draft（单案例待验证）** — 本模式基于单个七概念分析会话萃取，尚未在≥2个独立项目中验证，采用前请先做小范围PoC。

## 模式概述

结构化文档工具（Sphinx/MDX）解决"怎么写文档"，OKF原则解决"文档归谁、怎么开放、怎么协作"——两者的组合不是技术集成，而是**将开放知识的社会/法律层协议嵌入文档生产工具链**，让文档从产出那一刻就具备开放属性和可追溯性。该模式不绑定特定文档工具，Sphinx扩展和MDX remark/rehype插件均可实现。

## 问题现象："公开"不等于"开放"

很多项目把文档放上网就认为"开放了"，但实际上缺少关键要素：

| 问题 | 表现 | 后果 |
|------|------|------|
| **无机器可读许可** | 只有根目录一个LICENSE文件，文档页内没有许可标注 | 搜索引擎/AI爬虫无法判断使用权限；用户需要翻到根目录才知道许可 |
| **贡献者溯源缺失** | 文档没有贡献者信息，或者手动维护容易过时 | 无法正确归属贡献；新用户不知道该找谁问问题 |
| **知识孤岛** | 文档中的专业术语没有链接到开放知识图谱 | 读者需要自己搜索术语含义；无法跨文档发现关联知识 |
| **许可不一致** | 代码用MIT但文档没标注，或者不同章节许可冲突 | 法律风险；用户不清楚哪些内容可以复用 |
| **变更历史不可追溯** | 只有git历史但文档本身没有版本/变更信息 | 读者不知道文档最后更新时间、改了什么 |

## 核心反常识

> **开放不是"把文档放上网"就完了——没有机器可读的许可声明、没有贡献者溯源、没有与其他知识的互联，那只是"公开"不是"开放"。真正的开放文档需要工具链层面保证开放属性不丢失。**

手动维护开放元数据几乎一定会出错（遗漏、过时、不一致），必须由构建工具在生产环节自动注入。

## 解决方案：三层元数据嵌入

### 整体架构

| 层 | 组件 | 实现方式 | 职责 |
|----|------|---------|------|
| **许可层** | 许可声明+机器可读元数据 | Sphinx指令/角色 或 MDX组件 | 标记内容许可，构建时生成CC0/CC-BY等许可徽章和RDFa/JSON-LD元数据 |
| **溯源层** | 贡献者网络+变更历史 | git历史提取 + 构建时注入 | 从git log自动生成贡献者名单、最后更新时间、变更记录 |
| **互联层** | 开放知识链接 | 术语自动链接插件 | 文档中的专业术语自动链接到Wikidata/DBpedia等开放知识库 |

### 双实现路径

**路径1：Sphinx扩展集（Python生态）**

- 自定义Sphinx指令支持标记内容许可范围（文件级/章节级）
- 构建钩子从git历史提取贡献信息，生成可视化贡献者网络
- 构建器扩展支持JSON-LD输出，包含许可、作者、关键词等元数据
- 术语角色自动链接到开放知识图谱

**路径2：MDX插件集（JS生态）**

- remark插件：解析Markdown时提取许可标记，注入元数据
- rehype插件：HTML生成时插入贡献者信息、许可徽章、知识图谱链接
- React组件：`<License>`、`<Contributors>`、`<TermLink>`等可复用组件

### 嵌入粒度指南

| 粒度 | 适用场景 | 推荐 |
|------|---------|------|
| **仓库级** | 整个项目文档统一许可 | README + 每个页面页脚自动注入（默认） |
| **文件级** | 不同文件许可不同 | 文件frontmatter标注，构建时读取 |
| **章节级** | 文档内部分内容使用不同许可 | 指令/组件标记（仅在确有必要时使用） |
| **行级** | - | ❌ **不推荐**：过度细粒度治理，形式主义大于实质 |

## 核心公理

1. **工具链保障原则**：开放元数据必须由构建工具自动生成，不能依赖作者手动维护——手动维护必然遗漏和过时
2. **默认开放原则**：默认情况下文档采用与代码一致的开源许可，特殊情况才需要显式覆盖
3. **机器可读优先**：每个开放属性（许可、作者、来源）都要有机器可读的格式（JSON-LD/RDFa），不只是人能看懂的文字
4. **许可粒度匹配原则**：许可粒度与贡献粒度匹配——文件级许可足够，不需要行级

## 反模式（不要这么做）

- ❌ **反模式1：行级/段落级许可强制嵌入**：把许可信息标到每一行文字，变成政治正确式的形式主义，作者写作负担重且无实际法律价值
- ❌ **反模式2：手动维护贡献者名单**：在文档里手动写"贡献者：张三、李四"，新人加入或有人退出时忘记更新
- ❌ **反模式3：只有根目录LICENSE**：文档页面内没有任何许可信息，用户需要翻到仓库根目录才能看到
- ❌ **反模式4：链接到不可信的知识库**：自动术语链接到内容质量参差不齐的网站，而非Wikidata等经过社区治理的开放知识库
- ❌ **反模式5：忽略许可兼容性**：自动链接的内容许可与本文档许可不兼容，造成法律风险

## 适用场景

- 开源项目官方文档（需要正确的许可声明和贡献者归属）
- 开放政府数据文档（需要机器可读的元数据和开放许可）
- 开放教育资源（OER）（需要明确的复用许可和来源追溯）
- 公共知识平台（需要与开放知识图谱互联）
- 技术书籍/规范文档（需要贡献者信息和版本变更记录）

## 不适用场景

- 企业内部私有文档（不需要开放许可和公共知识互联）
- 需要保密的商业文档（不适用开放模式）
- 个人笔记/草稿（过度工程，普通Markdown足够）
- 博客/营销内容（没有结构化开放需求）

## 检验标准

做完之后怎么知道做对了？
1. **许可机器可读**：用Google结构化数据测试工具能检测到正确的许可信息
2. **贡献者自动更新**：新增贡献者合并PR后，文档贡献者名单自动更新，无需手动修改
3. **默认行为正确**：新建文档不需要任何配置就自动带上正确的许可和基础元数据
4. **写作体验不降级**：作者不需要学习复杂的许可语法，默认行为就是对的
5. **术语链接准确**：自动链接到Wikidata等知识库的词条是正确的，没有错误匹配

## 实现检查清单

- [ ] 构建工具自动从项目LICENSE读取许可信息，注入到每个文档页
- [ ] 从git历史自动提取贡献者信息，生成贡献者名单
- [ ] 生成JSON-LD/RDFa等机器可读元数据
- [ ] 许可信息在HTML页面上有可视化展示（徽章/页脚声明）
- [ ] 支持文件级frontmatter覆盖默认许可（可选）
- [ ] 术语自动链接到开放知识图谱（可选，质量保证前提下）
- [ ] 不强制作者手动写许可信息，默认行为正确
- [ ] 没有行级/段落级许可标记（避免形式主义）
- [ ] 多许可场景下有清晰的粒度边界标识

## 与其他模式的关系

- **document-as-queryable-api.md**：互补关系——本模式解决开放属性的工具链嵌入，文档即可查询API模式解决结构化查询；两者结合就是洞察4的三者全组合基础
- **provenance-driven-trust.md**：思想同源但领域不同——溯源驱动信任是无人值守系统的通用信任基础设施，本模式是开放文档领域的溯源具体应用
- **metadata-layering.md**：架构基础——本模式的三层元数据嵌入基于元数据分层模式
- **markdown-to-knowledge-graph.md**：知识互联层可以基于该模式实现

## 迁移验证（跨场景示例）

本模式不仅适用于技术文档：
- **学术论文预印本**：自动注入CC-BY许可、作者信息、基金资助信息、与DBLP/ORCID等学术知识库互联
- **政府公开数据文档**：自动注入开放政府许可、数据提供部门、更新频率、与data.gov等开放数据门户互联
- **开源设计资源**：设计系统文档自动注入CC0许可、设计师贡献信息、与设计知识库互联
