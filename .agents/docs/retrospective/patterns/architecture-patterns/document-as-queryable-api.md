# 文档即可查询API模式

> ⚠️ **成熟度：L1-draft（单案例待验证）** — 本模式基于单个七概念分析会话萃取，尚未在≥2个独立项目中验证，采用前请先做小范围PoC。

## 模式概述

结构化文档工具（Sphinx/MDX等）与GraphQL的组合价值不在于"用GraphQL动态获取数据渲染文档"，而在于**将文档本身作为可查询的图结构数据暴露**——文档不是给人看的静态HTML，而是有类型、可遍历、可编程查询的知识图API，HTML只是其中一种渲染输出。生产层可在Sphinx（Python生态，多格式出版）与MDX（JS生态，交互式组件）之间二选一，核心洞察不变。

## 问题现象

传统技术文档/知识系统的典型痛点：

1. **文档与代码不同步**：API改了文档没更新，开发者踩坑
2. **机器无法消费知识**：AI agents、IDE插件、CLI工具无法结构化查询文档内容，只能爬取HTML做NLP解析
3. **多维度检索困难**：无法回答"给我所有返回值包含User类型的API方法"这类结构化查询
4. **重复维护**：人类可读文档和机器可读API Schema是两份独立内容，容易不一致
5. **静态文档灵活性不足**：传统静态站点只能按预定义导航浏览，无法按用户需求动态筛选/组合内容

## 解决方案（核心架构）

### 三层分层架构

| 层 | 组件 | 职责 | 技术选型 |
|----|------|------|---------|
| **生产层** | 结构化文档工具 + 扩展 | 人类友好的知识创作、结构化标记、版本控制 | Sphinx+扩展（Python生态）**或** MDX+remark/rehype插件（JS生态） |
| **接口层** | GraphQL | 机器友好的知识查询、类型安全、自我描述（introspection） | GraphQL Schema从文档AST自动生成 |
| **渲染层** | 多格式输出 | HTML（人类阅读）、JSON（机器消费）、PDF/ePub（出版） | Sphinx构建器 / React组件 |

### 双实现路径

**路径1：Sphinx扩展路径（Python生态，适合多格式出版）**

两种组合模式：
- 🔨 **构建时组合**：Sphinx构建时从doctree提取文档元数据，生成静态GraphQL Schema文件（schema.gql）+ 静态查询响应，适合纯静态站点
- ⚡ **运行时组合**：Sphinx扩展启动轻量GraphQL服务器，支持对文档内容的运行时遍历查询，适合需要复杂筛选的文档站

**路径2：MDX嵌入式路径（JS生态，适合交互式文档，开发体验最佳）**

- 🧩 **嵌入式组合**：通过MDX插件生成GraphQL Schema，文档中直接使用`<Query>` React组件执行查询并渲染结果，天然支持交互式文档站

### 生产层工具选型对比

| 维度 | Sphinx (reStructuredText) | MDX (Markdown + JSX) |
|------|--------------------------|---------------------|
| **生态** | Python生态，老牌文档工具 | JS/React生态，现代前端 |
| **内容格式** | reStructuredText（强语义标记） | Markdown + JSX组件 |
| **结构化能力** | doctree是强类型AST，完整的指令/角色/交叉引用系统 | Markdown AST（MDAST）较弱，但可通过JSX组件嵌入任意交互逻辑 |
| **GraphQL集成** | 需要写扩展/构建器，区分构建时/运行时 | ⭐ 可直接在文档中写GraphQL查询组件，运行时获取数据渲染 |
| **多格式输出** | HTML/LaTeX/ePub/PDF/man page等十几种，出版级质量 | 主要输出HTML，PDF/ePub需额外工具链 |
| **开发者动量（2026）** | 稳定但增长缓慢，Python社区和官方文档主流 | 增长强劲，Docusaurus/Next.js/Astro等现代文档站首选 |
| **选型建议** | Python项目、需要PDF/多格式出版、技术书籍/官方规范文档 | JS项目、需要交互式组件、仅需HTML输出、面向前端开发者 |

## 核心公理（第一性原理）

1. **结构化AST即图结构**：Sphinx的doctree、MDX的MDAST等结构化文档AST天然具备图结构特征（节点+交叉引用边），可直接映射为GraphQL类型系统
2. **知识双消费方**：文档的消费方不仅是人类读者，还有机器（AI agents、IDE工具、自动化脚本），两者同等重要
3. **单一知识源原则**：同一知识源应该同时提供人类可读视图和机器可查询接口，而不是维护两份分离的内容（避免同步问题）
4. **渲染与数据分离**：HTML/PDF等只是渲染格式，知识的本质是结构化数据，查询接口应该独立于渲染格式

## 反模式（不要这么做）

- ❌ **反模式1：运行时GraphQL服务器查询静态文档内容**：对于纯静态文档站，用客户端搜索（Algolia/Meilisearch/Lunr.js）比维护一个运行时GraphQL服务器简单10倍，ROI更高，不要杀鸡用牛刀
- ❌ **反模式2：小型项目过度工程**：博客、营销内容站点、小型项目文档不需要GraphQL层，普通Markdown+静态站点生成器足够，复杂度会吃掉所有收益
- ❌ **反模式3：只做GraphQL不维护人类可读文档**：机器接口不能替代人类阅读体验，必须两者共存——文档首先要让人看得舒服，API层是附加价值不是替代
- ❌ **反模式4：为了"API化"而牺牲写作体验**：不要要求作者手写GraphQL Schema或学习复杂的标记语法，Schema必须从文档写作过程中自动生成，写作体验优先

## 适用场景

- 大型API平台文档（需要按类型/参数/返回值多维度检索）
- 框架/类库官方文档（IDE/CLI工具需要查询文档元数据）
- 需要多维度检索的知识库/开发者门户
- AI原生知识库（AI agents需要程序化消费知识）
- 技术书籍/规范文档（需要同时提供HTML阅读和API查询）

## 不适用场景

- 小型项目文档（<50个页面）：过度工程，ROI为负
- 博客/营销类内容站点：没有结构化查询需求
- 团队不具备GraphQL维护能力：需要额外学习成本
- 纯写作场景（不需要程序化查询）：传统静态站点足够

## 检验标准

做完之后怎么知道做对了？
1. **单一来源验证**：修改文档内容后，GraphQL查询结果和HTML页面同步更新，不需要手动维护两份内容
2. **典型查询可用**：能回答"列出所有已废弃的接口及替代方案"、"给我所有返回User类型的API方法"这类结构化问题
3. **introspection正常**：GraphQL接口能自我描述，工具可以自动发现文档结构
4. **写作体验不降级**：作者用熟悉的reStructuredText/Markdown写作，不需要学习新概念
5. **性能可接受**：构建时方案无运行时开销；运行时方案响应时间<200ms

## 迁移验证（跨场景示例）

本模式还能应用于非技术文档领域：
- **法律法规文档**：结构化法律条文通过GraphQL暴露，支持"找出所有提到'连带责任'的条款及相关司法解释"
- **学术论文知识库**：结构化论文元数据+引用关系通过GraphQL查询，支持"列出所有引用了这篇论文的方法章节"
- **企业合规手册**：合规条款+适用场景+处罚标准通过GraphQL关联，支持"找出所有适用于财务部门的合规要求"

## 与其他模式的关系

- **Markdown→知识图谱自动化生成（markdown-to-knowledge-graph）**：本模式是知识图谱在文档API领域的垂直应用，知识图谱模式侧重可视化，本模式侧重程序化查询
- **三层解析生成器（three-layer-parser-generator）**：本模式的"从AST生成GraphQL Schema"属于解析→生成范式
- **渐进式披露规范（progressive-disclosure）**：文档API支持按查询深度返回内容，是渐进式披露在机器接口层的体现

## 行动建议（PoC方向）

如果要验证本模式，建议从以下小切口入手：
1. **MDX路径优先**：用Docusaurus+MDX+GraphQL做一个最小可行原型，在文档中嵌入简单的`<Query>`组件，开发体验最佳
2. **先做构建时方案**：不要一开始就上运行时GraphQL服务器，先从构建时提取元数据生成静态Schema开始，复杂度低
3. **选一个真实痛点**：不要为了组合而组合，先找一个现有文档系统中确实存在的检索痛点（如"找所有废弃接口"）来验证价值
