# 透明拦截器中间件模式

> 在调用链中插入**透明代理层**增强功能，不修改调用源和调用目标的实现，实现横切关注点与业务逻辑的完全解耦。

## 核心思想

```
┌──────────┐     ┌─────────────┐     ┌─────────────┐     ┌──────────┐
│  Client   │────▶│ Middleware  │────▶│ Middleware  │────▶│  Target  │
│ (调用源)  │◀────│    M1       │◀────│    M2       │◀────│ (服务端) │
└──────────┘     └─────────────┘     └─────────────┘     └──────────┘
                   日志/监控           缓存/重试
                   不感知M1存在       不感知M2存在
```

**关键洞察**：横切关注点（日志、缓存、认证、重试、压缩、审计等）散落在业务代码中是架构腐化的根源。通过透明拦截器将这些关注点从业务逻辑中剥离出来，统一在中间件层处理，调用两端完全不需要知道中间件的存在。

## 为什么重要（Why）

### 不使用此模式的问题

1. **关注点混杂**：业务代码中充斥着日志、缓存、重试等样板代码，核心逻辑被淹没
2. **修改侵入性**：要加一个新的横切功能（如审计），需要修改N个业务模块
3. **一致性差**：每个模块各自实现横切逻辑，行为不一致、bug重复出现
4. **难以测试**：横切逻辑与业务逻辑耦合，单元测试需要mock大量依赖
5. **上线风险高**：修改横切行为需要改业务代码，引入回归风险

### 使用此模式的收益

1. **零侵入**：源和目标不需要任何修改即可获得新能力
2. **可插拔**：中间件可以按需启用/禁用/替换，不影响业务
3. **可组合**：多个中间件串联形成处理管线，顺序可配置
4. **单一职责**：每个中间件只做一件事，易于开发和测试
5. **可观测**：统一的中间件层提供全局观测点（日志/metrics/trace）

## 模式结构（How）

### 中间件标准接口

```
         ┌─────────────────────────────────────────┐
         │           Middleware Interface           │
         │                                         │
 Request │  + handle(request, next): response       │
────────▶│      1. 前置处理（修改/增强request）       │
         │      2. 调用 next(request) 获取响应        │
         │      3. 后置处理（修改/增强response）      │
 Response│      4. 返回处理后的response              │
◀────────│                                         │
         └─────────────────────────────────────────┘
                   │
                   ▼ next() 调用下一个中间件
```

### 核心特性

| 特性 | 说明 |
|------|------|
| **透明性（Transparency）** | 调用源和目标都不需要感知中间件存在，接口契约保持一致 |
| **双向拦截（Dual Interception）** | 可以同时处理请求方向（入站）和响应方向（出站） |
| **短路能力（Short-Circuit）** | 中间件可以选择不调用next()直接返回响应（如缓存命中） |
| **链式组合（Chainable）** | 多个中间件按顺序串联，形成洋葱模型处理管线 |
| **顺序敏感（Order-Sensitive）** | 中间件执行顺序影响结果（如认证必须在日志之后？） |

### 洋葱模型（Onion Model）

请求从外到内穿过各层中间件，响应从内到外返回：

```
    请求方向
      │
      ▼
┌───────────┐
│  Middleware 1  │  ← 最先收到请求，最后收到响应
│  (日志/监控)    │
├───────────┤
│  Middleware 2  │
│  (认证/鉴权)    │
├───────────┤
│  Middleware 3  │  ← 最后收到请求，最先收到响应
│  (缓存/重试)    │
├───────────┤
│   Target/Handler │  ← 实际业务逻辑
└───────────┘
      │
      ▼
    响应方向
```

## 适用场景（When）

### ✅ 适用场景

| 场景类型 | 具体示例 | AI场景示例 |
|---------|---------|-----------|
| **缓存** | 响应缓存、请求去重 | LLM调用结果缓存、重复问题去重 |
| **日志/监控** | 访问日志、性能指标、分布式追踪 | Token用量统计、调用链追踪、成本监控 |
| **认证/鉴权** | 身份验证、权限检查、配额控制 | API Key轮换、速率限制、多模型路由鉴权 |
| **重试/降级** | 失败重试、熔断、fallback | LLM API限流重试、模型降级（GPT-4→GPT-3.5） |
| **数据转换** | 请求/响应格式转换、压缩/解压 | 上下文压缩、prompt模板注入、响应格式标准化 |
| **审计/合规** | 请求/响应录制、敏感数据脱敏 | 对话内容审计、PII脱敏、合规记录 |
| **流量控制** | 限流、排队、负载均衡 | LLM请求排队、并发控制、多provider负载均衡 |

### ❌ 不适用场景

- **核心业务逻辑**：中间件处理横切关注点，不放业务逻辑
- **有状态的业务流程**：跨多个请求的业务状态不应在中间件中维护
- **需要强类型契约变化**：如果中间件会改变接口契约，透明性就被破坏，应该用适配器模式

## 实施步骤

### Step 1：识别横切关注点

列出系统中哪些功能是横切多个模块的、不属于核心业务逻辑的：
- 所有API调用都需要日志？→ 日志中间件
- 所有LLM调用都要统计token？→ 计量中间件
- 重复请求可以缓存？→ 缓存中间件

### Step 2：定义统一中间件接口

根据你的技术栈选择标准形式：

| 技术栈 | 典型接口形式 |
|-------|------------|
| Express/Koa (Node.js) | `(req, res, next) => {}` |
| gRPC Interceptor | `(call, method, next) => {}` |
| Java Servlet Filter | `doFilter(request, response, chain)` |
| Python WSGI/ASGI | `__call__(environ, start_response)` |
| Go HTTP middleware | `func(http.Handler) http.Handler` |
| Axios Interceptor | `request.use(config => config)` |

### Step 3：按洋葱顺序组装中间件链

典型顺序（从外到内）：

```
1. 请求ID生成/Trace上下文注入  ← 最外层，确保所有下游都有trace
2. 访问日志/请求录制           ← 记录原始请求
3. 认证/鉴权/限流             ← 尽早拒绝非法请求
4. 缓存读取                   ← 命中则短路返回
5. 重试/熔断/降级             ← 保护下游服务
6. 数据转换/压缩/注入         ← 请求预处理
7. [实际业务调用/Target]
8. 数据转换/解压/后处理       ← 响应后处理
9. 缓存写入                   ← 缓存结果
10. 响应日志/metrics采集       ← 记录最终响应
```

### Step 4：确保透明性

中间件必须遵守透明性原则：
- **不改变接口签名**：输入输出类型必须和Target一致
- **不引入副作用泄漏**：中间件自己的状态不应该影响业务逻辑
- **异常透明**：中间件可以捕获异常做增强，但最终应该按契约传递或抛出

## AI/LLM 场景特殊价值

中间件模式在AI应用中尤为重要，因为LLM调用有独特的横切关注点：

| AI特有横切关注点 | 中间件实现方式 |
|----------------|-------------|
| **Token成本控制** | 统计每次调用的token用量，超预算时拒绝或降级 |
| **Prompt注入防护** | 前置中间件扫描/清洗用户输入 |
| **上下文管理** | 自动注入对话历史、系统提示、RAG检索结果 |
| **响应结构验证** | 后置中间件验证LLM输出是否符合JSON schema，不符合则自动重试修复 |
| **多模型路由** | 根据请求特征路由到不同模型（快/慢/便宜/贵） |
| **缓存层** | 缓存相似请求的LLM响应，减少重复调用 |
| **人工审核插入点** | 在特定条件下将请求/响应转给人工审核 |
| **幻觉检测** | 后置中间件对LLM输出做事实核查 |

### Headroom Proxy 具体实现参考

Headroom就是此模式的典型应用——在LLM API调用链中插入Proxy中间件：

```
┌──────────────┐     ┌───────────────────┐     ┌──────────────┐
│  LLM Client  │────▶│  Headroom Proxy   │────▶│  LLM API     │
│ (OpenAI SDK) │◀────│  (透明中间件)      │◀────│ (OpenAI/GPT) │
└──────────────┘     ├───────────────────┤     └──────────────┘
                     │  • 上下文压缩     │
                     │  • 对话记忆管理   │
                     │  • Token用量统计  │
                     │  • 请求/响应缓存  │
                     │  • 工具调用路由   │
                     └───────────────────┘
                     Client使用标准OpenAI SDK
                     完全不感知Proxy存在
```

**关键设计**：Headroom Proxy暴露和OpenAI API完全一致的接口，因此Client可以零修改切换——只需要改API endpoint。这就是透明性的完美体现。

## 反模式

### 反模式1：胖中间件（God Middleware）

**表现**：一个中间件里塞了日志、缓存、认证、重试N种功能

**问题**：违背单一职责，难以测试和复用，修改其中一个功能影响其他

**修正**：拆分成多个薄中间件，每个只做一件事，通过组合实现复杂行为

### 反模式2：顺序依赖隐式化

**表现**：中间件之间有隐含的执行顺序依赖，但没有文档或强制机制

**问题**：新同事调整中间件顺序导致隐蔽bug（如缓存层放在认证层前面，未认证请求也能命中缓存）

**修正**：明确文档化中间件顺序；考虑用类型系统或builder模式强制正确顺序

### 反模式3：破坏透明性

**表现**：中间件修改了请求/响应的契约（如把JSON返回改成了XML），导致上游/下游崩溃

**问题**：调用方的接口假设被打破，透明性不复存在

**修正**：中间件可以增强但不能改变核心契约；如果必须改变，用显式的适配器模式而非中间件

### 反模式4：中间件内做业务决策

**表现**：在认证中间件里写业务权限逻辑（如"如果用户是VIP就跳过某些检查"）

**问题**：业务逻辑散落到中间件层，业务规则变更需要改中间件

**修正**：中间件只做通用横切逻辑；业务决策下沉到业务层或使用策略模式注入

### 反模式5：过度中间件化

**表现**：把所有逻辑都做成中间件，连纯业务逻辑也包装成中间件

**问题**：调用链过深，调试困难，性能损耗，架构复杂化

**修正**：中间件只处理真正跨模块的横切关注点；业务逻辑放在Handler/Service层

## 与相关模式的关系

| 相关模式 | 关系 |
|---------|------|
| **代理模式（GoF Proxy）** | 中间件是代理模式的结构化、可组合扩展。单一代理是中间件的特例（一层） |
| **装饰器模式（GoF Decorator）** | 中间件链本质是装饰器模式的链式应用；洋葱模型就是装饰器嵌套 |
| **责任链模式（GoF Chain of Responsibility）** | 中间件链是责任链的变体，每个中间件可以选择处理或传递 |
| **面向切面编程（AOP）** | AOP是中间件思想的语言级实现；中间件是AOP在架构层面的应用 |
| **经典模式优先复用启发式** | 本模式是"经典CS思想跨领域复用"的典型案例——HTTP中间件→AI Harness |
| **内容感知路由** | 路由中间件是内容感知路由模式的一个应用场景 |
| **可逆设计保障** | 审计/录制中间件天然提供了可逆性（可重放请求） |
| **扩展四步法** | 开发新中间件本身可以走扩展四步法流程 |

## 模式选择决策树

```
需要给多个模块添加一个通用功能？
  │
  ├─ 这个功能是核心业务逻辑吗？
  │    └─ 是 → 不要用中间件，放在业务层
  │
  ├─ 需要修改调用源/目标的接口吗？
  │    └─ 是 → 不要用透明中间件，考虑适配器模式
  │
  ├─ 这个功能是横切关注点吗（日志/缓存/认证/监控等）？
  │    └─ 是 → ✅ 使用透明拦截器中间件模式
  │         ├─ 只有一个拦截点 → 单一中间件
  │         └─ 有多个横切关注点 → 中间件链（洋葱模型）
  │
  └─ 不确定？→ 先在一个地方实现，重复出现2-3次再提炼为中间件
```

## 总结

透明拦截器中间件模式是软件架构中最基础也最有价值的模式之一：

> **当你发现自己在多个地方写着类似的日志/缓存/重试代码时，不要复制粘贴——做一个透明中间件。**

这在AI应用开发中尤其重要：LLM调用天然有大量横切关注点（token计量、缓存、prompt注入防护、多模型路由、重试降级），用中间件模式组织这些能力，可以让核心业务代码保持纯净，同时让横切能力可插拔、可测试、可复用。

**一句话记忆**：**横切关注点不进业务代码——透明中间件是它们的归宿。**
