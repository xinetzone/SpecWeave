# 知识资产「萃取→归档→删除」生命周期闭环模式

> 对应模式：KNOWLEDGE-LIFECYCLE-CLOOP-001 知识资产生命周期闭环模式
>
> **适用场景**：临时知识库/研发工作区（如 chaos）中的目录完成了使命，需要安全处置其价值，避免"直接删除丢失价值"或"永不清理堆积垃圾"。
>
> 本模式定义临时知识资产从"价值识别"到"安全清源"的完整闭环，确保每次临时知识库目录的处置不是一次性消耗，而是成为正式知识库（如 SpecWeave）的能力增量，同时保持工作区整洁。

---

## 流程总览

```
临时知识库目录（如 chaos/docker）
    ↓
[1] 萃取（Extraction）→ 按标准模板识别并沉淀可复用模式
    ↓
[2] 归档（Archive）    → 更新索引、交叉引用、链接验证
    ↓
[3] 确认使命完成（Confirm）→ 由用户确认价值已完整转移
    ↓
[4] 删除源（Deletion）→ 安全清理源目录，保留空目录即可
    ↓
[5] 复盘沉淀（Retrospective）→ R→I→E 记录完整过程
```

---

## 核心原则

| 原则 | 说明 |
|------|------|
| **萃取先于删除** | 先划转价值再清源，避免"删了才发现有价值"的不可逆损失 |
| **标准模板萃取** | 每个模式含触发场景/反模式/检验标准/迁移示例，保证可迁移性 |
| **反模式对等** | 每个模式提炼 ≥3 个反模式，防范"萃取不完整" |
| **交叉引用防重复** | 萃取前检索既有模式库，避免创建重复模式 |
| **用户确认门禁** | 删除源前必须由用户/负责人确认"使命完成"，不擅自处置 |
| **删除后复盘** | 处置完成后做 R→I→E 复盘，反哺方法论本身 |

## 阶段详解

### 阶段1：萃取（Extraction）

**目标**：将临时知识库目录中的可复用价值转换为正式可迁移模式。

| 步骤 | 动作 | 产出 |
|------|------|------|
| 1.1 | 分析目录内容，识别可复用模式 | 模式清单 |
| 1.2 | 检索既有模式库，排除重复 | 差异化清单 |
| 1.3 | 按标准模板逐个萃取（触发场景/核心做法/反模式/检验标准/迁移示例） | code-patterns / methodology-patterns 文档 |
| 1.4 | 标注成熟度（L1-draft 单案例 / L2 双案例 / L3 可复用） | 成熟度字段 |

**验收标准**：
- [ ] 每个模式含触发场景、核心做法、≥3 反模式、检验标准、迁移示例
- [ ] 成熟度标注客观（validation_count 与 L 级匹配）
- [ ] 与既有模式无重复，有交叉引用

### 阶段2：归档（Archive）

**目标**：将萃取成果接入正式知识库，使其可被发现。

| 步骤 | 动作 | 产出 |
|------|------|------|
| 2.1 | 更新目录 README 索引 | 索引新增行 |
| 2.2 | 建立模式间交叉引用 | related_patterns 双向链接 |
| 2.3 | 运行链接校验脚本 | 无断链 |
| 2.4 | （可选）注册到 capability-registry | 可被发现 |

**验收标准**：
- [ ] 索引已更新
- [ ] check-links 无断链
- [ ] 模式间交叉引用有效

### 阶段3：确认使命完成（Confirm）

**目标**：由用户确认价值已完整转移，授权删除。

**关键动作**：向用户展示萃取成果，询问处置方式（归档/删除/仅标记）。**不擅自删除**。

### 阶段4：删除源（Deletion）

**目标**：安全清理使命完成的源目录。

| 步骤 | 动作 | 说明 |
|------|------|------|
| 4.1 | 删除源文件 | 用 DeleteFile 逐个删除 |
| 4.2 | 清理空目录 | 空目录不追踪，可保留或手动清理 |
| 4.3 | 确认子模块状态 | 若在 git 子模块内，确认删除后状态符合预期 |

**注意**：删除前确保阶段1萃取已完整完成，不留"半成品源"。

### 阶段5：复盘沉淀（Retrospective）

**目标**：记录完整过程，反哺方法论。

按 R→I→E 执行：事实采集 → 洞察提炼 → 导出建议，生成复盘报告归档至 `reports/knowledge/`。

## 反模式（不要这么做）

### ❌ 反模式1：直接删除不萃取

```bash
# 删除临时知识库目录，未先划转价值
rm -rf chaos/docker
```
**后果**：目录中的可复用价值（如容器优化模式）永久丢失，下次遇到同类问题从零开始。

### ✅ 正确做法
先萃取价值进正式知识库，再清源。

### ❌ 反模式2：萃取不完整

```bash
# 只记录"操作步骤"，未提炼反模式/检验标准/迁移示例
写一篇"如何删除chaos目录"的笔记
```
**后果**：沉淀的是"这次怎么做的"而非可迁移模式，无法在其他领域复用。

### ✅ 正确做法
按标准模板萃取，含反模式对等、检验标准、跨领域迁移示例。

### ❌ 反模式3：不与既有模式库去重

```bash
# 发现已有类似模式，仍新建一份
新建 knowledge-lifecycle...md # 与 vendor-lifecycle-governance 未做差异区分
```
**后果**：模式库滋生重复资产，降低可发现性。

### ✅ 正确做法
萃取前检索既有模式库，明确差异化边界，用关联引用而非复制。

### ❌ 反模式4：未确认就删除

```bash
# 未获用户确认，擅自删除目录
DeleteFile chaos/docker/*
```
**后果**：可能删除了仍有价值的半成品源，不可逆。

### ✅ 正确做法
删除源属高风险操作，必须由用户显式确认"使命完成"。

### ❌ 反模式5：删除后不复盘

```bash
# 删完即止，不记录过程
rm -rf chaos/docker  # 结束
```
**后果**：处置过程的一次性经验未沉淀，方法论自身无法演进。

### ✅ 正确做法
处置完成后做 R→I→E 复盘，反哺方法论。

## 检验标准

做完之后怎么知道做对了？

1. **价值完整转移**：源目录的可复用价值全部沉淀至正式知识库，无遗漏
2. **模式可迁移**：每个萃取模式含触发场景/反模式/检验标准/迁移示例
3. **归档可发现**：索引已更新，链接无断链，交叉引用有效
4. **删除经确认**：删除源前已获用户显式确认
5. **工作区整洁**：使命完成的源目录已清理，不留半成品
6. **过程可追溯**：复盘报告已归档，方法论可演进

## 迁移示例

| 领域 | 萃取产物 | 归档位置 | 删除目标 |
|------|---------|---------|---------|
| 容器/研发资源 | code-patterns（docker/conda） | code-patterns/ | chaos/docker |
| 供应商治理 | methodology-pattern | governance-strategy/ | chaos/vendor |
| 临时脚本 | code-patterns（脚本模板） | code-patterns/ | chaos/scripts |
| 调研笔记 | methodology-pattern | learning/ 或 methodology-patterns/ | chaos/research |

### 跨领域迁移
- **代码仓库技术债**：先在正式代码库沉淀可复用模块，再删除实验分支
- **临时文档**：关键结论转入正式 wiki，再清空临时草稿文件夹
- **实验数据**：分析结论沉淀为报告，原始临时数据按留痕策略归档或清理
- **组织知识管理**：离职交接先沉淀知识库，再回收临时账号
