# 强约束语言自检启发式

## 速查表（核心层）

| 维度 | 内容 |
|------|------|
| **一句话** | 写规则类文档时系统性搜索强约束词（必须/禁止/绝不），逐条追问反例，柔化有例外的规则 |
| **触发条件** | 撰写规范、指南、checklist、规则、操作手册等约束性文档；模式入库前；提示词/模板同步时 |
| **铁律** | **多检查点原则**——强约束自检至少执行3次：源文件V阶段→模式入库前→提示词/模板同步时 |
| **核心数** | 4步流程、4个固定攻击视角、3个检查点、2类柔化模式 |

---

## 一、问题现象

规则类文档中的强约束语言存在两类典型问题：

1. **过度约束**：用"必须/禁止"表述有例外的规则，导致执行者在例外场景机械执行产生反效果。例如"禁止使用子代理"在简单任务中合理，但在≥5子任务的复杂场景中反而降低质量。
2. **约束不足**：用"尽量/适当"等模糊语言表述关键规则，导致执行者没有可执行标准，规则形同虚设。
3. **一次自检不够**：源文件V阶段修正了强约束后，下游萃取产物（模式文档、提示词模板）不会自动同步修正——本次审计发现action-first模式入库后仍有2处"必须"，5-Whys预防措施中也残留强约束词（P0-08）。

根本问题：强约束词是规则文档中最容易造成执行偏差的元素，但缺乏系统性的自检流程；且V→E回环缺失导致源文件修正后下游产物不同步。

## 二、核心思想

```
强约束可信度 = 反例搜索充分度 × 例外明确度 × 多检查点覆盖率
```

约束性规则的有效性不在于"写得多严格"，而在于"使用者知道何时遵守、何时可以偏离"。好的约束是"默认推荐+显式列举例外"，而非不分场景的绝对命令。

**核心原则**：
1. **默认为主，例外为辅**：大多数场景使用默认推荐表述，例外场景显式列举
2. **多检查点**：一次自检不足以覆盖所有下游产物，必须在多个关键节点重复执行
3. **攻击视角固定化**：V阶段攻击强约束边界时使用固定视角，而非随意寻找反例

## 三、核心步骤（4步）

### Step 1：Grep搜索强约束词

使用搜索工具扫描文档中的强约束关键词：

**强约束词清单**：
| 类别 | 关键词 |
|------|--------|
| 绝对命令 | 必须、禁止、绝不、一定、绝对、永远不、只能 |
| 全称量词 | 所有、全部、任何、一切、一律、毫无例外 |
| 否定绝对 | 不能、不得、不可、不允许、不准 |
| 英文（含中英文混合文档）| MUST、MUST NOT、SHALL、SHALL NOT、NEVER、ALWAYS |

**输出**：列出所有命中位置（文件+行号+原句），形成强约束清单。

### Step 2：逐条追问反例

对清单中每个强约束，追问4个固定攻击视角：

| 攻击视角 | 追问问题 |
|---------|---------|
| ①非目标用户 | 这个约束对非目标用户群体（如新手/非技术用户/其他角色）是否成立？ |
| ②极端/边缘场景 | 在极端条件下（时间压力/资源不足/紧急情况）这个约束是否仍然适用？ |
| ③规则冲突 | 这个约束与其他规则/原则是否存在潜在冲突？冲突时优先级如何？ |
| ④创意/探索场景 | 在创意写作、头脑风暴、探索性研究等需要发散的场景中，这个约束是否抑制产出？ |

**判定标准**：
- 如果4个视角下**均无反例**→保留强约束（属于真正的硬规则，如安全红线）
- 如果**存在反例**→进入Step 3柔化
- 如果**不确定是否有反例**→标记为"待验证"，添加注释说明需后续验证

### Step 3：柔化有例外的规则

根据反例类型选择柔化模式：

**柔化模式A：默认推荐+显式例外**

适用场景：规则在大多数情况下成立，少数场景例外。

```
修改前：禁止在撰写模式文档时跨目录选择风格锚点
修改后：默认在同目录选择风格锚点；跨目录选择仅在同目录无合适锚点时使用，须记录理由
```

**柔化模式B：条件触发式**

适用场景：规则仅在特定条件下成立。

```
修改前：模式入库后必须执行强约束自检
修改后：当模式文档包含规则/约束类内容时，入库前应执行强约束自检
```

**柔化模式C：建议性表述**

适用场景：最佳实践但非硬性要求。

```
修改前：必须使用Mermaid流程图展示核心步骤
修改后：建议使用Mermaid流程图展示核心步骤，有助于读者快速理解流程
```

### Step 4：V阶段攻击边界

对抗审查阶段专门攻击强约束的适用边界。除Step 2的4个视角外，额外检查：

1. **跨文档一致性**：该约束与项目中其他文档的类似规则是否一致？（如不同文档对"必须"的使用强度是否统一）
2. **可执行性**：约束是否有可检查的判定标准？"尽量简洁"无法检查，"单段不超过5行"可以检查。
3. **违反后果**：如果违反该约束，会产生什么后果？后果严重程度是否匹配约束强度？（轻微后果不应使用"禁止"级约束）

## 四、多检查点执行时机

强约束自检必须在以下3个关键节点各执行一次（不可只执行一次）：

| 检查点 | 时机 | 检查范围 | 原因 |
|--------|------|---------|------|
| **CP1：源文件V阶段** | 分析报告/源文档完成V审查后 | 仅源文件 | 源文件是萃取的基础，源头修正效率最高 |
| **CP2：模式入库前** | 新模式文档写入patterns目录前 | 新模式文档 | E阶段从源文件萃取时，V阶段对源文件的修正不会自动传播到模式文档 |
| **CP3：提示词/模板同步时** | 创建或更新prompts/、commands/、templates/下的关联文件时 | 新创建/更新的提示词/模板 | 提示词模板可能独立于模式文档更新，残留v1.0强约束表述 |

**检查流程**：每个检查点重复Step 1-3（Grep→追问→柔化），Step 4（V阶段攻击边界）仅在CP1和CP2执行。

## 五、已知失败案例

### 失败案例1：V→E修正回环缺失导致强约束残留（本次审计P0-08）

- **场景**：V1阶段修正了analysis-report.md中的强约束问题，但萃取后的action-first-output-paradigm.md仍保留2处"必须"；5-Whys根因分析的预防措施中也使用了"强制""绝对不能""必须"等强约束词
- **根因**：只有CP1检查（源文件V阶段），缺少CP2（模式入库前）检查
- **修正**：柔化为"增加""不应假设""应再执行一次"等非绝对表述
- **教训**：必须执行多检查点，不能假设源文件修正后下游产物自动同步

### 失败案例2：提示词模板未同步v2.0规则（本次审计P1-01）

- **场景**：action-first-output-paradigm-addendum.md（提示词模板）仍使用v1.0的强约束表述，7处"必须/禁止"未同步v2.0的边界场景和柔化规则
- **根因**：缺少CP3检查点（提示词/模板同步时未执行自检）
- **状态**：列为P1待修复
- **教训**：提示词模板是模式的"执行载体"，模板中的强约束直接影响AI输出，必须在同步时自检

## 六、反模式

| 反模式 | 表现 | 后果 |
|--------|------|------|
| 一次自检完事 | 只在源文件V阶段做一次Grep就认为完成 | 下游模式文档和提示词残留强约束 |
| 回避"必须"用模糊词 | 把所有"必须"改为"尽量/适当"，导致规则无执行标准 | 规则形同虚设，执行者无判定依据 |
| 不找反例直接柔化 | 遇到"必须"就改为"建议"，不追问反例 | 真正需要强约束的安全规则被弱化 |
| 只搜中文不搜英文 | 在中英文混合文档中只搜中文强约束词 | MUST/MUST NOT/NEVER等英文强约束词遗漏 |
| Grep后不逐条检查 | 搜到强约束词后不逐条分析，批量替换 | 真正的硬规则被错误柔化 |

## 七、保留强约束的正当理由

以下场景可以保留强约束（不柔化），但须在文档中说明理由：

1. **安全红线**：可能导致数据丢失、安全漏洞、生产事故的操作（如"禁止直接在生产环境执行未测试的DELETE语句"）
2. **法律合规**：法律法规、许可证要求的硬性规定
3. **不可恢复操作**：如git push --force、DROP TABLE等不可逆操作
4. **项目铁律**：经项目团队共识确立的不可违反的约定（如"禁止提交.env文件到版本控制"）
