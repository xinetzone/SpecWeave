# 机制组合互斥预检模式（Mutual-Exclusion Composability Precheck）

## 触发场景

- 计划**叠加使用两个各自独立有效的机制**（安全措施、优化手段、修复方案）以求"双保险"
- 两个机制作用于**同一对象/同一资源**（同一文件、同一目录树、同一请求上下文）
- 组合方案来自直觉（"两个都是好东西，一起用更好"），而非文档明确支持组合
- 典型句式：「先做 A 兜底，再做 B 双保险」「A 保险，B 再保险一层」

**适用于**：任何资源型机制组合决策——文件系统属性+离线工具、备份+清理、中间件包装、双重锁、缓存+直写。

**不适用于**：机制作用在不同对象（天然无冲突）；官方文档明确声明组合语义（如分层防御中各层独立失效）；单一机制已满足验收标准（无需组合）。

## 问题本质（组合性谬误）

**「各自有效」不蕴含「组合有效」**。两个机制单独测试都通过，但它们可能在同一实现层竞争同一资源语义：

1. **作用层冲突**：sparse 是 NTFS 文件属性（在线元数据），compact 是离线文件重写——两者对"文件如何变小的"给出互斥答案，前者直接堵死后者的前置条件
2. **作用域冲突**：备份的目的是保护数据，清理的作用域若包含备份位置，则清理"成功地"摧毁了备份（自噬）
3. **语义冲突**：中间件包装期望上下文语义透传，但两套框架的上下文模型不兼容，包装层产生微妙的数据丢失

共同结构：**直觉按"收益叠加"模型组合（1+1=2），实际是"资源竞争"模型（1+1<1）**——不仅组合失败，还引入了"A 成功带来的状态恰好是 B 的阻断条件"的隐藏耦合（sparse 属性 → compact 拒绝）。

## 核心步骤（组合前四查）

1. **查作用层**：两个机制分别作用在哪一层（文件属性层/文件内容层；请求进入前/响应返回后）？同层大概率竞争
2. **查互斥声明**：两机制文档中搜索 "exclusive/mutual/互斥/不能同时/前置条件"——错误语义往往早有文档（diskpart 报错「文件不能是稀疏文件」即显式互斥声明）
3. **最小组合探针**：在可回滚环境（快照/副本）上先组合跑一次最小验证，观察是否出现「A 成功后 B 报错」的时序相关失败
4. **设计解锁路径**：若探针失败，确认冲突状态是否可逆（`fsutil sparse setflag <file> 0` 即 sparse→compact 的解锁钥匙），并记录解锁成本

## 反模式

| 反模式 | 后果 | 实证 |
|--------|------|------|
| ❌ 双保险直觉直接堆叠，跳过组合验证 | A 的成功状态阻断 B，组合彻底失败 | F-019→F-024 |
| ❌ 组合失败后弃用其一，不查解锁路径 | 误以为"只能用 A"，永久损失 B 路径的收益 | F-025 前的认知盲区 |
| ❌ 报错只看字面（"文件被占用"），不追问第二层原因 | 停在表层错误，错过真正的互斥约束 | F-023→F-024 连环坑 |
| ❌ 清理操作不先确认保护对象的位置在作用域外 | 备份被清理自噬 | 项目记忆：清理-保护域隔离 |
| ❌ 用包装层桥接两套语义不同的框架 | 微妙的上下文数据丢失，排查代价极高 | 项目记忆：koa-connect 教训 |

## 失败案例（防成功偏误）

| # | 案例 | 组合意图 | 实际结果 | 教训 |
|---|------|---------|---------|------|
| 1 | sparse + diskpart compact（20260828） | sparse 在线缩 + compact 离线兜底 | compact 报「不能是稀疏文件」，双保险变零保险 | 需 fsutil 清标志解锁；组合前四查可完全避免 |
| 2 | 备份目录置于清理树内（项目记忆） | 备份保护 + 目录清理 | 清理脚本删除备份，保护机制自毁 | 作用域审查：保护对象必须在清理作用域之外 |
| 3 | koa-connect 包装 Express 中间件（项目记忆） | 复用 Express 生态 + Koa 应用 | ctx.state 数据微妙丢失，最终被迫原生重写 | 语义桥接不是组合，是翻译损耗；探针期发现即止损 |

> 三个案例的共同点：组合决策耗时为零（直觉直发），失败后修复成本高昂（服务双停+三轮攻坚 / 备份数据不可恢复 / 重写中间件层）。

## 不适用/反目标/边界场景（≥3类，防确认偏误）

| 类别 | 场景 | 不适用原因 |
|------|------|-----------|
| 反目标1 | 机制作用在不同层且无状态耦合（如 WAF + 应用层校验） | 分层防御的组合语义是"串联独立失效"，不共享前置条件 |
| 反目标2 | 官方文档明确支持组合（如 RAID1 + 定期快照） | 组合语义已被设计者验证，预检冗余 |
| 反目标3 | 单一机制已满足验收标准 | 叠加第二机制只增加复杂度与故障面，无论是否互斥 |
| 边界1 | 互斥仅在特定时序出现（A 完成后 B 才失效） | 探针必须覆盖"A→B"与"B→A"两种顺序 |
| 边界2 | 冲突状态不可逆（A 破坏 B 的输入数据本身） | 解锁路径不存在，组合决策是单向门，必须前置预检 |
| 边界3 | 组合收益远高于探针成本 | 可跳过四查直接全量验证，但失败需准备完整回滚方案 |

## 早期预警信号（≥5个）

| 信号 | 判定阈值 | 含义 |
|------|---------|------|
| 计划中同时出现两个"安全/回收/优化"动词作用于同一对象 | 例：转属性+重写文件 | 进入组合前四查 |
| 工具报错含「不能/不允许/要求非…」句式 | 显式前置条件声明 | 大概率互斥约束，查文档 |
| A 成功后 B 失败，B 单独测试曾通过 | 时序相关失败 | A 的状态是 B 的阻断条件 |
| 文档出现 exclusive / 互斥 / 不可同时 / 忽略先前设置 | 机制语义层声明 | 直接放弃组合或查解锁 |
| 两个机制来自不同抽象层的工具但操作同一物理资源 | 例：NTFS属性工具 + 块级重写工具 | 作用层冲突高危 |

## 跨场景迁移

| 场景 | 机制A | 机制B | 互斥本质 |
|------|-------|-------|---------|
| 磁盘回收（本案例） | sparse 属性 | diskpart compact | 在线元数据 vs 离线重写，A 是 B 的前置条件违反 |
| 数据保护 | 备份到子目录 | 父目录递归清理 | 作用域包含保护对象 |
| Web框架 | Koa 应用 | Express 中间件包装 | 上下文语义模型不兼容 |
| 数据库 | 乐观锁 | 悲观锁混用 | 同一行锁语义竞争 |
| 版本控制 | git sparse-checkout | 部分克隆过滤器叠加 | 工作区视图语义竞争（需按版本验证） |

**本质**：组合前问一句——**"A 成功后的世界，B 还能运行吗？"** 收益叠加是直觉，资源竞争是现实；预检四查的成本恒小于组合失败的返工成本。
