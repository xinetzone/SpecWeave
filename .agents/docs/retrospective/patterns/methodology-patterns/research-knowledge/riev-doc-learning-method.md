# RIEV文档学习法

## 触发场景

- 当需要学习外部文档（钉钉文档、官方教程、产品指南、网页文章等）并沉淀为结构化可复用知识时
- 当需要把零散的原始资料转化为面向用户的学习指南/操作手册时
- 当需要保证学习笔记的事实准确性、结构清晰性、可行动性时
- 适用于：产品学习、技术文档研读、培训材料消化、竞品分析
- 不适用于：纯娱乐性阅读、无需沉淀的快速浏览、已经高度结构化的标准教材

## 核心做法

### R（Retrospective 事实采集）
1. 只记录客观事实，不加入主观判断、因果推断、个人评价
2. 所有信息标注来源URL/文档，对截断/不确定内容诚实标注"待确认"
3. 对原文中的主观形容词（如"极速"、"核心"），如果是官方slogan加引号标注，否则改为客观描述
4. 数字、链接、步骤必须准确记录，关键数字核对一遍
5. 文件命名：`01-facts.md`，存放于项目目录

### I（Insight 洞察提炼）
1. 从事实中提炼洞察，每个洞察必须使用**现象-本质-影响-建议**四元组结构：
   - 现象：客观发生了什么（来自R阶段）
   - 本质：这件事背后的底层逻辑/原因
   - 影响：做对了怎么样，做错了怎么样（正面+负面）
   - 建议：具体可执行的行动步骤
2. 洞察按优先级/类别分组（如高危风险、关键要点、效率技巧等）
3. 避免空洞的"要注意XX"，必须说清楚"注意什么、为什么注意、不注意会怎样、具体怎么做"
4. 文件命名：`02-insights.md`，存放于项目目录

### E（Extraction 萃取指南）
1. 将事实和洞察整合为面向最终用户的结构化指南（README.md作为主文档）
2. 开头必须有**30秒快速上手**区块，告诉读者：是什么、第一步做什么、核心资源、重要提醒
3. 标准章节结构：
   - 产品/主题定位
   - 新用户/入门者权益/准备
   - 分步骤核心流程（配表格：步骤+做什么+示例+为什么）
   - 场景/功能总览（配表格）
   - 进阶功能详解
   - 避坑指南（坑点+现象+怎么避免，表格形式）
   - 官方资源汇总
   - 特定人群建议（如大使推广建议、开发者建议等）
   - 快速行动清单（checkbox形式，今天就能做的事）
4. 关键信息必须完整：官网URL、注册入口、必备链接一个都不能少
5. 口语化表达改为书面语："造完"→"用完"，"瞎写"→"随意编写"

### V（Validation 对抗审查）
1. **新手视角审查**：假设你是完全不懂的新手，看完文档是否知道第一步去哪里、做什么？
2. **挑错视角审查**：检查数字是否准确、链接是否可访问、是否有逻辑矛盾、是否有错别字
3. **目标用户视角审查**：如果你是目标用户（如推广大使），推广建议/操作指引是否实用？
4. 发现问题后回到对应阶段修复（事实错误回R、洞察问题回I、结构问题回E）
5. 修复后重新验证，直到所有问题解决

### 归档收尾
1. 将R阶段（01-facts.md）和I阶段（02-insights.md）移动到`archive/`子目录
2. 主目录只保留最终指南（README.md），保持用户视角简洁
3. 如果引用了其他文档/规则，在frontmatter的source字段标注来源
4. 更新文档版本号（修复问题后升级小版本号）

## 质量门校验标准
- **G1（事实门）**：R阶段文件无"因为/所以/导致/核心/极速"等因果词和主观形容词，纯客观描述
- **G2（洞察门）**：每个洞察都有完整的现象-本质-影响-建议四元组，无空洞建议
- **G3（指南门）**：新手看完知道第一步做什么、去哪里做；关键URL/链接完整；有避坑指南和行动清单

## 反模式（不要这么做）

- ❌ **反模式1：跳过V阶段直接发布**
  - 现象：生成完README就认为完成了
  - 后果：事实错误（如Design mode 3级错写为5级）、关键信息缺失（如官网URL）、无来源断言（如二次点击规则未标注），导致误导用户
  - 纠正：必须经过至少一轮三视角审查才能发布

- ❌ **反模式2：事实和主观判断混写**
  - 现象：R阶段就写"这个功能非常好用"、"核心优势是XX"
  - 后果：事实和观点纠缠，后续I阶段无法准确提炼洞察，容易出现认知偏差
  - 纠正：R阶段只记"是什么"，不写"好不好"、"重要不重要"

- ❌ **反模式3：不归档中间产物**
  - 现象：主目录同时放01-facts.md、02-insights.md、README.md
  - 后果：用户打开目录不知道该看哪个，中间过程文件干扰最终阅读
  - 纠正：完成后将R-I文件移入archive/，主目录只留README.md

- ❌ **反模式4：洞察没有四元组结构**
  - 现象：只写"要注意二次点击"、"记得省积分"
  - 后果：读者不知道为什么要注意、不注意会怎样、具体怎么做，可执行性差
  - 纠正：每个洞察必须完整回答：发生了什么→为什么→有什么影响→具体怎么做

- ❌ **反模式5：缺失关键行动信息**
  - 现象：指南写"先去注册"但不写注册网址；写"用官方链接"但不写在哪里获取
  - 后果：读者看完知道要做什么但不知道去哪里做，卡在行动第一步
  - 纠正：V阶段新手视角审查必须确认"第一步去哪里、点哪个按钮、输入什么"都写清楚了

- ❌ **反模式6：单阶段追求完美**
  - 现象：R阶段就想把最终指南写好，边记事实边润色最终文档
  - 后果：事实采集混入主观内容，阶段边界模糊，一旦发现理解错误需要全部重写，返工成本高
  - 纠正：严格按R→I→E→V顺序执行，每个阶段只做该阶段的事，完成一个阶段再进下一个

## 检验标准

做完之后怎么知道做对了？
1. **事实准确**：V阶段审查未发现数字错误、链接错误、事实错误
2. **行动清晰**：找一个完全不了解该主题的人，看完30秒快速上手后知道第一步去哪里做什么
3. **避坑完整**：至少列出3个最容易踩的坑，且每个坑都有明确的规避方法
4. **结构整洁**：主目录只有README.md一个核心文件，中间产物都在archive/
5. **可复用性**：另一个有类似需求的人（如另一个产品的大使）可以照着这个结构快速产出自己的学习指南

## 迁移示例

这个模式还能用在什么其他场景？

- **场景1（技术学习）**：学习一个新框架/库的官方文档
  - R：通读官方文档，记录API、核心概念、快速开始步骤
  - I：提炼关键洞察（如"这个框架的核心是响应式"、"新手最容易在XX配置上踩坑"）
  - E：整理成团队内部的快速上手指南
  - V：找一个没接触过该框架的同事试读，看能不能跑通Hello World

- **场景2（读书/报告）**：研读一本专业书籍或行业研究报告
  - R：摘录核心观点、数据、案例
  - I：提炼对自己工作的启发、可迁移的方法
  - E：整理成读书笔记/分享PPT大纲
  - V：检查是否歪曲了作者原意，关键引用是否准确

- **场景3（培训学习）**：参加线下/线上培训课程
  - R：记录课程内容、讲师观点、案例演示
  - I：提炼可立即应用到工作中的方法、待验证的假设
  - E：整理成培训总结和行动清单
  - V：对照课件检查记录是否准确，行动项是否具体可执行

- **场景4（竞品分析）**：研究竞争对手的产品
  - R：记录竞品功能、定价、用户流程、界面截图
  - I：提炼竞品设计思路、优势劣势、可借鉴点
  - E：整理成竞品分析报告和产品建议
  - V：验证功能描述是否准确，不要因为自己的偏好歪曲竞品实际体验
