# 示例优先对齐模式（Example-First Alignment）

> 开始任何新类型任务前，先花5分钟找到并研究现有成熟示例，再开始创作。比从零猜测格式/结构/风格效率高5-10倍，且保证一致性。

## 核心思想

```
┌─────────────────────────────────────────────────────────┐
│         错误方式：从零开始（Guess First）                  │
│                                                         │
│  拿到任务 → 自己猜格式/风格 → 写出来 → 不对 → 反复修改    │
│              "应该是这样吧？"    试错N次     浪费大量时间   │
│                                                         │
│  问题：                                                                │
│  • 隐性规范靠猜，试错成本高                              │
│  • 风格不统一，每次产出不一致                            │
│  • 重复踩别人已经踩过的坑                                │
└─────────────────────────────────────────────────────────┘
                          vs.
┌─────────────────────────────────────────────────────────┐
│         正确方式：示例优先（Example First）                │
│                                                         │
│  拿到任务 → 找成熟示例 → 对齐结构/风格 → 填充内容        │
│              (5分钟)      (理解范式)     (专注内容本身)  │
│                                                         │
│  收益：                                                                │
│  • 格式对齐隐性成本→0，专注内容创作                      │
│  • 风格天然一致，无需额外规范                            │
│  • 站在前人肩膀上，避免已知陷阱                          │
└─────────────────────────────────────────────────────────┘
```

**关键洞察**：格式/结构/风格的对齐是创作活动中最大的隐性成本之一。成熟示例提供了"什么是好的"的具象参照，消除了反复试错的浪费。**找参考是效率提升的第一杠杆**——5分钟找示例，节省1-2小时试错。

## 为什么重要（Why）

### 从零开始的隐性成本

1. **格式猜测成本**：不参考示例时，大脑需要同时处理"写什么内容"和"用什么格式"两个认知任务，认知负荷翻倍
2. **试错迭代成本**：第一次写出来格式不对，反复修改调整，浪费时间
3. **风格不一致成本**：每次从零猜测导致产出风格不统一，增加阅读者认知负担
4. **已知陷阱踩坑成本**：前人已经遇到并解决过的问题，从零开始意味着重走弯路
5. **质量天花板低**：没有参考时，产出质量受限于个人经验；有成熟示例时，可以快速达到示例的质量水平

### 示例优先的收益

| 收益维度 | 从零开始 | 示例优先 |
|---------|---------|---------|
| **启动速度** | 慢（需要先想格式） | 快（格式已确定，直接填内容） |
| **首次通过率** | 低（格式/风格经常不对） | 高（对齐成熟示例，一次通过） |
| **质量基准** | 个人经验天花板 | 成熟示例质量基准 |
| **风格一致性** | 每次可能不同 | 天然一致 |
| **认知负荷** | 内容+格式双重负担 | 只关注内容创作 |
| **学习效率** | 自己摸索，慢 | 通过示例快速学习领域规范 |

## 实施步骤（How）

### Step 1：判断任务类型

问自己：这是一个**我之前做过的、有明确模板的**任务吗？
- 如果是 → 直接用已知模板，不需要找新示例
- 如果不是（新类型/新格式/新领域）→ 进入Step 2

### Step 2：花5分钟搜索成熟示例

搜索目标：找到本项目或业界已经做过的、被认可为"好的"同类产出物。

**搜索来源优先级**：

| 优先级 | 来源 | 搜索方法 |
|-------|------|---------|
| 1（最高） | **本项目内已有同类产出** | Grep/Glob搜索类似文件，找最成熟的那个 |
| 2 | **同团队/同组织的产出** | 团队共享文档/知识库/代码仓库 |
| 3 | **业界公认的优秀范例** | GitHub high-star项目、官方文档、经典著作 |
| 4 | **AI生成参考** | 让AI给一个标准格式模板（最后选项，需验证质量） |

**搜索关键词技巧**：
- 找文件：搜文件扩展名+目录（如`*.md`在`docs/`下）
- 找模式：搜相关标签/ID/frontmatter字段
- 找最近成功案例：按修改时间排序，看最近被review通过的产出

### Step 3：分析示例结构（3分钟）

拿到示例后，不要直接复制，先快速分析：

| 分析维度 | 看什么 |
|---------|-------|
| **整体结构** | 有哪些章节？顺序是什么？哪些是必须的，哪些是可选的？ |
| **格式规范** | 标题层级？frontmatter字段？代码块格式？表格格式？引用方式？ |
| **命名约定** | 文件命名？ID命名？标题命名？术语用法？ |
| **风格特征** | 正式/口语化？简洁/详细？有没有固定的开头/结尾？ |
| **与我任务的差异** | 示例和我的任务有什么不同？哪些部分需要调整？ |

### Step 4：以示例为模板开始创作

- **结构复用**：直接复用示例的章节结构和格式，填入自己的内容
- **风格对齐**：模仿示例的语言风格、表达方式、详略程度
- **差异调整**：对于示例没有覆盖的部分，参考示例的风格一致性地扩展
- **不要过度原创**：格式/风格层面不要追求"创新"，一致性比独特性更重要

### Step 5：完成后快速验证

- 对比示例检查格式是否一致
- 如果示例中有checklist，用同样的checklist自检

## 适用场景（When）

### ✅ 强烈推荐使用

| 场景 | 为什么示例优先效果最好 |
|------|---------------------|
| **新类型文档创作** | 第一次写某种类型的文档（如复盘报告、模式文件、Spec文档） |
| **结构化配置文件** | TOML/YAML/JSON配置，字段和格式有严格要求 |
| **代码模块新增** | 在现有项目中新增同类型模块/文件（如新增一个Pattern） |
| **PR/MR提交** | 参考项目的PR模板和已合并的优秀PR |
| **API接口设计** | 参考项目中现有API的风格、命名、错误处理模式 |
| **测试用例编写** | 参考现有测试的结构、命名、断言风格 |
| **报告/复盘写作** | 参考之前高质量的报告结构 |
| **新建项目/模块** | 参考业界同类型优秀项目的目录结构和组织方式 |

### ❌ 不需要刻意找示例

- 重复性高的日常任务（已经有肌肉记忆）
- 创造性/探索性工作（艺术创作、新算法设计、架构创新本身）
- 极其简单的单文件任务（如修改一个错别字）

## 反模式

### 反模式1：傲慢式从零开始

**表现**："我不需要看别人的，我自己能想出来"——不屑于参考示例，觉得参考是"没水平"

**问题**：
- 高估自己的格式猜测能力，低估隐性规范的复杂度
- 重复发明轮子，浪费时间在已经解决的问题上
- 产出风格与项目不一致，给reviewer造成困扰

**修正**：成熟的工程师不是"什么都自己想"，而是"善于站在前人肩膀上"。参考示例不是能力不足，是专业素养。

### 反模式2：盲目复制不思考

**表现**：找到示例后直接复制粘贴，连里面的具体内容都忘了改，或者把不适用的部分也照搬

**问题**：
- 复制了错误的内容（如示例中的占位符/示例数据没替换）
- 示例的特定场景约束不适用当前任务，照搬导致问题
- 不理解为什么用这种格式，下次还是不会

**修正**：Step 3的"分析示例结构"是必须的——理解为什么这样组织，而不是无脑复制。保留结构和风格，替换内容；对于不适用的部分，在理解意图的基础上调整。

### 反模式3：找最差的示例当参考

**表现**：随手找了一个最近看到的文件就当参考，但那个文件本身质量很差或不符合最新规范

**问题**：
- 垃圾进垃圾出——参考差的示例，产出也差
- 学习到错误的模式

**修正**：花时间找**好的**示例——优先找：（1）被review过并合入的；（2）最近更新的（规范可能已演进）；（3）核心维护者写的；（4）被其他文件引用最多的。

### 反模式4：示例依赖症

**表现**：任何任务都要找示例，找不到就完全无法开始；即使是简单任务也要先找参考

**问题**：
- 找示例本身变成拖延的借口
- 对于简单任务，找示例的时间超过直接做的时间
- 丧失独立判断能力

**修正**：设置时间盒——找示例最多花5分钟，找不到就用最简格式先做，做的过程中再调整。只有对质量/一致性要求高的复杂任务才值得深入找示例。

### 反模式5：形式大于内容

**表现**：花大量时间对齐格式风格，却忽略了内容质量本身

**问题**：格式再漂亮，内容空洞也是没有价值的

**修正**：示例优先的目的是**消除格式对齐的隐性成本，让你专注于内容**。格式对齐是手段，不是目的。格式对了之后，精力应该放在内容质量上。

## 一句话行动指南

> **开始新类型任务前，先花5分钟找一个成熟示例放到旁边，对着它的结构写内容。这5分钟会给你带来10倍回报。**

**记忆口诀**：**先找范例，再填内容；对齐结构，专注质量。**
