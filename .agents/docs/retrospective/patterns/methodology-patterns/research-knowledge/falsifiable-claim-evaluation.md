# 可证伪愿景检验法（Falsifiable Vision Check）

## 一句话
评估技术产品主张时，**判断"技术事实 vs 营销话术"的分水岭不是指标数量的精确性，而是该指标是否定义了可证伪的验收标准**。

## 模式类型
方法论模式（外部研究/批判性思考/技术评估）

## 成熟度
L1 实验性（单案例，待更多技术主张评估验证）

## 适用场景

| 场景 | 是否适用 | 说明 |
|------|---------|------|
| 评估外部技术文章/白皮书/Demo 主张 | ✅ 核心场景 | 判断"架构级解决""画面稳定"等宣称的可信度 |
| 技术选型前评估厂商宣称 | ✅ 核心场景 | 区分"技术事实"与"营销话术" |
| 官方已公开完整技术报告/源码的成熟技术 | ❌ 不适用 | 可直接验证，无需可证伪性判定 |
| 纯内部实现、无外部宣称的评估 | ❌ 不适用 | 无对外主张需要检验 |

## 核心问题

为什么需要可证伪性检验？因为技术产品主张常以"精确数字"包装不可验证的内容：
- "30 分钟稳定生成"——但"稳定"未定义验收标准，可靠后处理平滑/帧间插值实现
- "架构级解决三角困境"——但仅一句话描述，无架构细节佐证
- 数字精确度（0.00025 美元/秒、47.5 FPS）≠ 主张可验证性

**核心洞察**：数字的精确度 ≠ 主张的可验证性。一个定义了可证伪验收标准的模糊指标，比一个无法验证的精确数字更接近技术事实。营销话术的典型特征恰恰是"用精确数字包装不可验证的主张"。

## 核心步骤（5 步）

1. **提取关键指标**：从主张中列出所有带数字/量级的核心指标（成本、速度、时长、准确率等）。
2. **逐指标问"可证伪性"**：对每个指标自问"用什么实验/方法能证明它成立或不成立？"
3. **区分四类状态**：
   - 已定义验收标准 + 可复现 → **技术事实**
   - 已定义标准但未复现 → **待验证主张**
   - 未定义标准 + 自称可验证 → **待公开细节的宣称**
   - 未定义标准 + 无法验证 → **营销话术**
4. **分层判定（上下文校准）**：对"未定义标准"项，进一步看是否已公开技术细节/是否自称可验证——可证伪性不足 ≠ 必然不可信，避免误杀前沿创新（如 Sora 刚发布时也无连贯性基准）。
5. **输出结论**：将每个主张归入上述四类，作为决策依据；对"营销话术"类标注"等待技术报告公开后再评估"。

## 检验标准（做完怎么知道做对了）

- [ ] 每个关键指标都明确标出了可证伪性状态（四类之一）
- [ ] 对"未定义验收标准"的指标，没有仅因数字精确就误判为"技术事实"
- [ ] 对前沿创新（无标准但有技术细节），未将其错误降级为"营销话术"
- [ ] 结论可追溯：每个判定都能指出依据的指标与验证方法

## 反模式（需要避免的做法）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| "精确数字 = 可信"陷阱 | 把 0.00025 美元/秒 这类精确数字直接当作可信证据，忽略其不可验证性 | 数字精确度 ≠ 主张可验证性，先检验是否定义验收标准 |
| "一票否决前端创新" | 对尚未定义验收标准的前沿技术（Sora 类）一律判为营销话术，误杀真创新 | 用"上下文校准"分层判定，结合是否公开技术细节 |
| "看量不看质" | 只统计引用/点赞/传播量，不检验指标本身是否可证伪，被传播热度绑架 | 检验指标本身的可证伪性，而非传播热度 |
| "复用旧基准" | 用上一代技术的验收标准套用新技术（如用画质指标衡量内容连贯性） | 指标与人错位，应针对新技术定义新验收标准 |

## 迁移验证（非当前领域示例）

- **企业选型**：评估 SaaS 厂商宣称的"99.99% 可用性"时，先问 SLA 的验收标准（统计窗口、是否含计划内维护）再签约。
- **招聘**：评估候选人宣称的"主导了 X 项目"时，先问可验证的产出物/指标，而非仅看简历措辞。
- **投资尽调**：评估 AI 创业公司宣称的技术壁垒时，先检验其指标是否定义验收标准，区分"技术事实/营销话术"后进行估值。

## 失败案例

**失败案例：被"精确数字"误导的技术选型（2025，某团队内部评估复盘）**

某团队评估一款宣称"推理延迟 8ms、成本 1/50"的模型供应商时，仅看数字即快速通过了技术选型，未检验验收标准。落地后发现：8ms 是理想单样本延迟，业务批处理场景实际 200ms+；"成本 1/50"未定义算力/精度配置，生产环境翻倍。最终返工重选，损失约 3 周工期。**根因**：未对"延迟/成本"这些精确数字执行可证伪性检验——未问"什么测试能证明 8ms 成立"，被数字精确度误导。

另一失败案例：某团队评估开源项目时，因项目 README 声称"支持 10 种硬件后端"而认为成熟，未定义"支持"的验收标准（编译通过？可通过全部测试？）。实际只在不同真机验证，单元测试覆盖不全，集成后频繁崩溃。**教训**：未定义验收标准的"支持/兼容"宣称，应视为待验证主张而非技术事实。

## 反目标用户/场景

以下用户/场景**不适用**本模式，强行套用会产生误导：

| 反目标用户/场景 | 为何不适用 | 应使用的替代方法 |
|---|---|---|
| 已公开完整技术报告/源码的成熟技术评估 | 可直接运行/审查验证，无需可证伪性间接判定 | 直接运行基准测试、源码审查 |
| 纯内部实现、无对外宣称的评估 | 无外部主张需要检验，模式无对象 | 内部代码评审、性能压测 |
| 前沿研究的探索性评估（科研立项） | 研究本就没有验收标准，强制可证伪会扼杀探索 | 研究价值评估法、可行性论证 |
| 对"数字精确但可复现"的成熟指标 | 已定义标准且可复现，直接归为技术事实，无需分层 | 直接引用已验证指标 |

## 与相关模式的关系

- **trilemma-architectural-resolution**：三角困境架构级解决（决策框架），本文为其提供批判性检验方法
- **honest-limitation-acknowledgment**：诚实承认局限性（正面信任构建），本文为"未诚实言明可验证性"的批判性补充
- **credibility-dual-track**：可信度评分双轨制（对已采集内容评级），本文聚焦"主张可信度的事前判定"而非"内容可信度的事后标注"

## 关键洞察总结

1. **数字精确度 ≠ 主张可验证性**：营销话术用精确数字包装不可验证主张
2. **可证伪性是分水岭**：判断"技术事实 vs 营销话术"看是否定义可证伪验收标准
3. **四类状态分层**：避免非黑即白，用"技术事实/待验证/待公开/营销话术"四类分级
4. **上下文校准防误杀**：可证伪性不足 ≠ 必不可信，结合是否公开技术细节判定
