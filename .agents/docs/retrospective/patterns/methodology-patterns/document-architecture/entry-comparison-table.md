# 入口对比表模式（Entry Comparison Table Pattern）

## 模式类型
文档模式（信息架构/高密度呈现/边界清晰化）

## 成熟度
L3 可复用级（已在四区域对比表实践中验证，信息架构可直接复用）

## 问题陈述

当系统包含多个同构实体（区域、组件、环境、角色、权限等）时，差异说明面临以下问题：

**问题1：信息分散**
- 每个实体的说明在各自的文档里
- 想了解"A和B有什么区别"需要读两遍文档再自己对比
- 关键差异（比如权限边界）在分散阅读中容易遗漏

**问题2：信息密度低**
- 用段落文字描述：".agents是AI智能体规范容器，由主权区直接维护，直接纳入版本控制，可以修改，入口是..."
- 读者需要从文字中提取结构化信息，认知负担高
- 关键约束（如"禁止修改"）被淹没在段落中，不够醒目

**问题3：边界不集中**
- 每个文档说自己的规则，但没有一个地方展示"全局边界视图"
- 新智能体/新人需要花很长时间才能建立全局认知
- "我能不能改这个目录"这类高频问题需要反复查阅不同文档

**反面示例**（段落式描述）：
> 我们有四个顶层目录。首先是.agents目录，这是AI智能体的规范容器，里面放着roles、rules、workflows这些东西，是主权区直接维护的，直接纳入版本控制，所以是可以修改的，它的入口是.agents/README.md。然后是apps目录...（继续写300字）

## 解决方案

在顶层入口文件中放置一个高密度对比表，遵循以下设计原则：

### 对比表设计原则

**原则1：行是实体，列是维度**
- 每一行：一个同构实体（区域、组件、环境等）
- 每一列：一个关键对比维度（选择最容易出错、最需要明确的维度）

**原则2：单元格简洁**
- 用 ✅/❌ 图标 + 短语，禁止长段落
- 关键约束（如"禁止本地修改"）用加粗或图标突出
- 单元格内容控制在15字以内

**原则3：边界维度优先**
- 最容易出错、影响最大的维度必须放在前面
- 权限类维度（"是否可修改"）必须包含
- 入口链接类维度（"AGENTS.md入口"）必须包含在最后一列形成导航闭环

**原则4：链接闭环**
- 最后一列必须是对应入口文档的链接
- 读者看完对比可以直接点击进入感兴趣的实体详情

### 标准模板（顶层区域对比表）

```markdown
| 目录 | 用途 | 管理方式 | 版本控制 | 是否可直接修改 | AGENTS.md入口 |
|---|---|---|---|---|---|
| `.agents/` | AI 智能体规范容器 | 主权区直接维护 | 直接纳入版本控制 | ✅ 可修改 | [.agents/README.md](.agents/README.md) |
| `apps/` | 主仓库内置应用工作空间 | 同仓库直接管理 | 直接纳入版本控制 | ✅ 可修改 | [apps/AGENTS.md](apps/AGENTS.md) |
| `projects/` | 第一方自有子项目 | git submodule 管理 | 通过 gitlink 追踪 | ❌ 不可直接修改（走子项目流程） | [projects/AGENTS.md](projects/AGENTS.md) |
| `vendor/` | 第三方依赖 | git submodule 管理 | 通过 gitlink 追踪 | ❌ 禁止本地修改 | [vendor/AGENTS.md](vendor/AGENTS.md) |
```

### 适用的对比维度参考

根据场景选择合适的维度，不要超过6-7列（太多反而失去高密度优势）：

| 场景 | 推荐维度 |
|------|---------|
| **目录/区域对比** | 目录名、用途、管理方式、版本控制、是否可修改、入口链接 |
| **角色权限对比** | 角色、查看权限、编辑权限、审批权限、管理权限、说明文档 |
| **多环境对比** | 环境、用途、数据来源、部署方式、访问权限、配置入口 |
| **能力/特性对比** | 特性、版本A支持、版本B支持、备注、文档链接 |
| **状态对比** | 状态、含义、允许的操作、下一步动作、说明 |

### 对比表放置位置

| 位置 | 适用场景 |
|------|---------|
| **根 AGENTS.md 核心区域** | 顶层实体对比（如四区域对比表），这是最重要的全局边界信息 |
| **区域 AGENTS.md 开头** | 该区域内子模块的对比 |
| **README.md 概览章节** | 面向人类读者的功能/特性对比 |
| **独立规范文档中** | 多个方案/选项的对比分析 |

**关键原则**：对比表应该放在入口文档的"第一眼"位置（启动协议之后、详细内容之前），不要藏在文档末尾。

## 适用场景

| 场景 | 适用度 | 说明 |
|------|--------|------|
| 顶层入口区域对比 | 核心场景 | 本次验证场景（四区域对比表），效果显著 |
| 角色权限矩阵 | 核心场景 | RACI等权限模型天然适合表格呈现 |
| 多环境配置差异 | 核心场景 | dev/staging/prod配置对比 |
| 功能/特性对比 | 推荐 | 版本差异、多方案选型对比 |
| 状态机状态说明 | 推荐 | 每个状态的含义和允许操作 |
| 组件/服务目录 | 适用 | 微服务列表、插件列表概览 |
| 只有2-3个差异极大的实体 | 不适用 | 差异太大时表格会很稀疏，用段落更好 |
| 超过10个实体 | 谨慎使用 | 行太多时考虑分组或拆分多个表 |
| 维度超过7个 | 谨慎使用 | 列太多时考虑拆分维度到多个表 |

## 反模式警示

| 错误做法 | 后果 | 正确做法 |
|---------|------|---------|
| 单元格写长段落 | 失去高密度优势，和普通文字没区别 | 单元格控制在短语级别，详细说明在表格下方补充 |
| 列太多（8列以上） | 信息过载，读者抓不住重点 | 只选最关键的6-7个维度，其他维度放在详情文档 |
| 省略入口链接列 | 看完对比无法导航，形成信息孤岛 | 最后一列必须是链接，形成"看对比→点进去"闭环 |
| 只列"有什么"不列"不能做什么" | 关键约束（权限边界）不醒目 | 权限/约束类维度必须包含，用❌图标突出禁止项 |
| 表格之后没有补充说明 | 表格无法表达上下文和例外情况 | 表格下方可以加1-2段文字说明例外情况和注意事项 |
| 对比表不随实体更新 | 过时信息误导读者，比没有更糟 | 新增/删除实体时必须同步更新对比表（加入级联检查） |
| 用自然语言重述表格内容 | 冗余，表格已经说清了 | 表格后只补充表格无法表达的信息，不要重复 |

## 信息密度对比

| 呈现方式 | 四区域说明所需字数 | 关键约束醒目度 | 全局视图 | 导航闭环 |
|---------|------------------|---------------|---------|---------|
| 纯段落文字 | ~300字 | 低（淹没在文字中） | 差（需要自己整合） | 无 |
| 列表 | ~150字 | 中 | 一般 | 可能有 |
| **对比表** | **~80字** | **高（图标+加粗）** | **好（一眼看全）** | **有（最后一列链接）** |

## 与其他模式的协同

- **三层路由协议**：对比表是第一层路由的核心组件，展示"有哪些区域可以路由到"
- **对称目录结构**：对比表天然要求所有同构实体都出现在表中，不对称立即暴露——如果新加了一个区域但对比表没加行，评审时一眼就能发现
- **三层入口设计**：AGENTS.md面向AI，对比表的结构化信息AI也容易解析提取；README.md面向人类，对比表的高密度呈现人类读起来也高效

## 验证来源

- **验证1：根AGENTS.md四区域对比表（2026-07-24）**：将四区域的用途、管理方式、版本控制、修改权限、入口链接浓缩在8行表格内，信息密度比原段落式描述提升约4倍，边界定义一目了然
- **验证2：apps/AGENTS.md应用路由表（2026-07-24）**：10个应用的路由信息在一张表中，包含AGENTS.md入口、.agents/状态、说明，智能体路由时查表即可
