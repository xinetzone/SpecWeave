# 裸URL自动链接包裹（Bare URL Autolink Wrap）

## 模式类型
方法论模式 / 文档架构

## 成熟度
L1 实验性（1 次案例：mermaid-wiki 14 处正文裸 URL 包裹，10 个文件）

## 适用场景
当 Markdown 文档正文中需要规范 URL 表达形式时套用：
- 文档中存在**未被任何 Markdown 语法包裹的裸 URL**（如 `https://mermaid.live/`）
- 需要将与 URL 相关的**渲染意图**分类，决定哪些该包裹、哪些必须保持原样
- 对一批文档做 URL 格式统一，避免无脑全局替换破坏非正文内容

## 问题本质

同一段 `http(s)://...` 文本在 Markdown 中的**正确表达形式取决于渲染意图**，而非"它是不是一个 URL"。将 URL 按出现位置分类，可得到五种互斥的渲染意图：

| 出现位置 | 渲染意图 | 正确表达 | 是否包裹 `<...>` |
|---|---|---|---|
| 正文行内（段落/列表） | 可点击链接 | `<url>` 自动链接 | ✅ 是 |
| YAML/TOML frontmatter `source:` 等 | 元数据，非正文渲染 | 保持原样 | ❌ 否 |
| 代码块（import/CDN/命令示例） | 原样展示代码 | 保持原样 | ❌ 否 |
| 反引号行内代码（`` `url` ``） | 展示代码/路径，非链接 | 保持原样 | ❌ 否 |
| 含 `<占位符>` 的 URL 模板 | 格式示意，非真实链接 | 保持原样 | ❌ 否 |

**核心洞察**：判断"是否包裹"不取决于 URL 本身，而取决于它**是否作为正文中可点击的链接被渲染**。命名/格式类的批量决策，必须做"决策前三查"（查权威文档、查现有实例、查本质目标）——先用正则扫描全景，再按意图分类，只改目标类。

## 核心做法

1. **Grep 全景扫描**：用 `https?://` 正则搜索目标目录，列出所有 URL 出现位置（文件、行号、上下文）。
2. **渲染意图分类**：对照上表，将每处 URL 归入五类之一（正文 / 元数据 / 代码块 / 反引号 / 占位符模板）。
3. **仅包裹正文类**：只对"正文行内可点击裸 URL"用 `<url>` 包裹。
4. **保持其余类原样**：元数据、代码块、反引号、占位符模板一律不动。
5. **复核零残留**：修改后重新 Grep，确认正文无遗漏、非正文无误改。

## 快速套用决策

当遇到一个 URL 时，按以下顺序问自己：

```
这是正文段落/列表里要作为链接展示的 URL 吗？
├─ 是 → 用 <url> 包裹（自动链接）
└─ 否 → 它属于哪种？
    ├─ frontmatter 元数据 → 保持原样
    ├─ 代码块 / 反引号内 → 保持原样（它是代码，不是链接）
    └─ 含 <占位符> 模板 → 保持原样
```

## 反模式（不要这么做）

- ❌ **无脑全局正则替换所有 `http(s)://`**：会破坏 frontmatter `source:`、代码块 import、反引号内 URL 的语义，属于"误杀"。
- ❌ **对反引号/代码块内 URL 也包 `<>`**：`<>` 与行内代码/代码块的"原样展示"意图冲突，造成双重包裹或渲染异常。
- ❌ **包裹含 `<占位符>` 的 URL 模板**：如 `https://.../syntax/<名称>.html`，`<>` 是占位符语法，再包一层会冲突。
- ❌ **只改不复核**：修改后不重新 Grep，遗留正文裸 URL，格式不统一未被发现。

## 检查清单

- [ ] 正文所有可点击 URL 均被 `<url>` 包裹
- [ ] frontmatter `source:` 字段、代码块内 URL、反引号包裹 URL 均未被改动
- [ ] 含 `<占位符>` 的 URL 模板保持原样
- [ ] 全目录重新 Grep 后，正文无遗漏的裸 URL

## 迁移示例

- **代码批量格式化**：统一某类代码风格（如 JSON 字段引号、import 顺序）时，先分类目标上下文，只改目标类，保留字符串字面量/注释/模板原样，改后全量复核。
- **数据清洗**：只处理目标字段（如解析日期），保留 ID、时间戳等元数据字段原样，避免"一改全改"污染非目标字段。
- **跨领域文档审核**：任何"统一某种文本格式"的批量任务，都遵循"先分类→只改目标类→保持其余原样→全量复核"的意图驱动流程。

## 与现有模式的关系

- `scripted-batch-correction.md`：解决"是否用脚本批量替换"的决策；本模式解决"同一类文本在不同上下文应如何表达"的规范分类。二者互补——批量替换前需先按本模式分类意图。
- `fact-statement-consistency-loop.md`：本模式的"修改一处→搜索同类→统一修正→复核"闭环与其一致。
- `blockquote-code-block-rendering-fix.md`：同为 Markdown 渲染上下文相关的格式修复模式。
