# 分层缓存模式（Layered Caching Pattern）

## 模式类型

方法论模式

## 成熟度

L2 已验证（GitHub Copilot、Kapden等多个案例验证）

## 适用场景

- 多轮对话系统（智能客服、聊天机器人）
- 代码助手（系统提示、工具定义重复发送）
- Agent框架（工具schema、系统提示每轮重复）
- 任何有大量重复前缀/重复内容的场景
- 请求之间存在可复用内容的场景

**不适用于**：一次性请求、无任何重复内容的场景、内容极度动态无法缓存的场景。

## 问题背景

LLM推理中，系统提示词、工具定义、few-shot示例、历史对话等内容在每轮请求中重复发送，这些重复内容每轮都要重新计算prefill（O(n²)复杂度），成本高且延迟大。单一缓存层要么命中率低，要么内存开销大。分层缓存通过不同层级、不同粒度、不同生命周期的缓存组合，最大化复用率。

核心思想：越上层速度越快、容量越小、命中率越高；越下层反之。这是计算机科学中经典的分层思想在LLM领域的具体化。

## 核心规则

### 规则1：Layer 1 - 系统提示层（必做，实施难度极低）

- 将prompt重构为：`[静态前缀] + [动态后缀]`结构
- 静态前缀包括：系统提示、工具定义schema、few-shot示例、安全规则
- 动态后缀包括：用户当前输入、动态上下文、实时数据
- 静态前缀放在最前面，利用Prompt Caching/APC自动缓存
- 关键约束：静态前缀一旦确定不要随意修改，修改会导致缓存失效
- 缓存切换必须在自然边界（新会话、/compact后）

### 规则2：Layer 2 - 会话记忆层（对话/Agent场景必做，实施难度中等）

- 不把完整对话历史每轮都发送
- 采用分层记忆架构：
  - 即时层：最近N轮（3-5轮）原文保留
  - 工作记忆层：提取的实体/状态/关键信息结构化存储
  - 长期记忆层：更早的历史用摘要表示
- 同一session内的KV缓存自动复用（引擎层自动处理）
- 阈值触发自动压缩：token使用达到窗口70-80%时自动摘要

### 规则3：Layer 3 - 语义相似层（高重复场景推荐，实施难度中等）

- 对用户输入做embedding
- 在语义缓存中查找相似度>阈值（如0.95）的历史请求
- 命中则直接返回缓存的响应（或经过简单校验后返回）
- 客服/FAQ场景这一层命中率可达42%+（Kapden案例）
- 需要设置严格的相似度阈值和过期策略，避免错误回答复用

## 三层缓存架构

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 3: 语义相似层（Semantic Layer）                       │
│  生命周期：天-周，粒度：完整请求/响应，匹配：语义相似度       │
│  存储：向量数据库+Redis，命中率：20-40%，命中收益：100%节省  │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: 会话记忆层（Session Layer）                       │
│  生命周期：会话内，粒度：对话历史摘要/实体状态，匹配：同会话  │
│  存储：会话存储+KV缓存，命中率：50-80%，命中收益：80-90%节省│
├─────────────────────────────────────────────────────────────┤
│  Layer 1: 系统提示层（Prefix Layer）                        │
│  生命周期：跨会话全局，粒度：系统提示/工具定义/静态示例       │
│  匹配：精确前缀匹配，存储：推理引擎APC/Prompt Caching        │
│  命中率：70-95%，命中收益：90%成本+50-80%TTFT降低          │
└─────────────────────────────────────────────────────────────┘
```

## 效果数据（行业经验估算，实际效果以测量为准）

| 缓存层 | 典型命中率 | 命中收益 | 实施难度 |
|--------|-----------|---------|---------|
| Layer 1 系统提示层 | 70-95% | 前缀部分成本-90%，TTFT-50-80% | 极低（重构prompt即可） |
| Layer 2 会话记忆层 | 50-80% | 历史部分成本-90%，长会话token-60-80% | 中（需要摘要/实体提取） |
| Layer 3 语义相似层 | 20-42% | 命中请求成本-100%，整体-20-40% | 中（需要向量数据库） |
| **三层组合** | **综合收益** | **整体成本降低60-85%，TTFT降低50-80%** | |

**典型案例验证**：
- GitHub Copilot：扩展提示缓存是"最大单一杠杆"，正确结构化prompt即可获得90%折扣
- Kapden客服：语义缓存命中率42%是成本降低的关键杠杆（月费$92K→$22K）
- Himanshu 7天优化：提示缓存是Day2-3的核心动作，单这一项即带来显著收益

## 实施检查清单

- [ ] Prompt是否已重构为"静态前缀+动态后缀"结构？
- [ ] 静态前缀是否放在最前面且不随意修改？
- [ ] 对话历史是否采用分层记忆架构（即时层+工作记忆+长期记忆）？
- [ ] 是否设置了token阈值自动触发摘要压缩？
- [ ] 高重复场景是否启用了语义缓存，且相似度阈值≥0.95？
- [ ] 缓存TTL设置是否合理（静态内容长TTL，动态内容短TTL）？
- [ ] 是否有缓存预热策略应对冷启动？
- [ ] 是否有缓存雪崩防护（过期时间加随机偏移）？

## 反例警示

| 错误做法 | 后果 |
|---------|------|
| 缓存内容放错位置：动态内容放静态前缀前面 | 每次前缀变化缓存无法命中 |
| 模型切换破坏缓存：在对话中间切换模型 | KV缓存全部失效 |
| 语义缓存阈值过低：为提高命中率调低相似度 | 错误回答复用引发事故 |
| 忽略缓存预热：冷启动阶段缓存命中率0 | 高峰期性能差、超时错误 |
| 缓存不设过期：知识库/工具定义更新后缓存不失效 | 返回过时信息 |
| 所有缓存同时过期 | 缓存雪崩，请求全部打穿到后端 |

## 缓存预热与TTL策略

- **冷启动阶段（0-30分钟）**：命中率0-30%，需要发布后自动预热+灰度发布
- **稳定阶段命中率预期**：客服场景70-85%，通用对话50-70%，代码助手60-80%
- **静态内容（系统提示、工具定义）**：TTL长（24小时+），发布时主动失效
- **动态内容（用户数据）**：TTL短（5-30分钟）或主动失效
- **缓存键设计**：静态前缀放开头，移除无关变化因素（如request_id），规范化prompt空格换行

## 迁移验证（跨领域可复用性）

分层缓存是计算机科学中经典的架构模式，可迁移到：

1. **CPU L1/L2/L3缓存架构**：L1对应Layer 1（核心本地、最快、最小、命中率最高），L2对应Layer 2，L3对应Layer 3
2. **CDN分层缓存架构**：浏览器本地缓存→CDN边缘节点→源站/中心缓存，TTL和失效策略完全通用
3. **数据库多级缓存架构**：应用本地缓存→分布式缓存（Redis）→数据库Buffer Pool，缓存穿透/击穿/雪崩问题通用
