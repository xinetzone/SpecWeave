# 源码→OKF 对抗性更新工作流

## 模式类型

方法论模式 / AI协作 / 知识沉淀

## 成熟度

L1 已验证（1次验证，2026-08-24 invocations v4.1.0 源码对账更新）

## 模式概述

当既有 OKF 知识包（bundle）需要对照**本地 vendor 源码的最新版本**做一致性更新时，采用「源头复基线 → 对抗性对账 → 漂移分类 → 定向修复 → 落盘核对」五步链路，**只修改确认漂移的文档，绝不因重新生成而破坏已准确的内容**。区别于一次性生成（source-code-to-okf-wiki-workflow），本模式的核心是"对账增量更新"：先建立新版本的事实基线，再逐文件与 vendor 源码交叉验证，将差异分类为"确定性漂移 / 疑似漂移 / 无问题"，仅修复漂移点，最后用 `git diff` 核对所有变更真实落盘。

## 问题现象

1. **全量重写破坏准确性**：bundle 大多内容从旧版本源码产出，重写会丢失已验证的准确信息，引入新错误。
2. **"看起来合理"的漂移难以察觉**：如配置键 `packaging.find_opts` 归属错误——它真实属于 `checks.blacken`，但放在 packaging 配置块里"看起来合理"，不逐文件对账会漏检。
3. **源码路径漂移**：文档声称的 vendor 源码路径与实际不符（如少了 `tools/` 目录层级），读者照路径找不到源码。
4. **修复不闭环**：只改正文不同步 `verified` frontmatter / 变更日志，审计链断裂，下次无法追踪。
5. **误报完成**：修复后不做 `git diff`/磁盘核对，变更实际未写入磁盘却上报"已完成"。

## 解决方案

### 步骤1：复基线（R Update）

- 核对 vendor 版本（pyproject.toml `version`），确认真实模块清单，**明确记录不存在的模块**（如 `packaging/version.py`）。
- 产出 `facts.md`，每条事实注明源码路径与行，零推测。

### 步骤2：对抗性对账（V）

- 遍历 bundle 全部文件，收集所有模块/任务/函数签名/配置键引用。
- 对每个引用用 Grep/Read 在 vendor 源码逐项核对存在性与归属；**配置键要核对所属模块**（不只是存在，还要在正确的 `ns.configure` 块内）。
- 输出 `review-report.md` 到 spec 目录，逐文件给结论。

### 步骤3：漂移分类

| 类别 | 定义 | 处理 |
|------|------|------|
| 确定性漂移 | 与源码明确不符（路径、伪造配置键） | 必须修复 |
| 疑似漂移 | prose 层单复数/书写不一致 | 顺手修正 |
| 无问题 | 引用与源码一致 | 不改动 |

### 步骤4：定向修复（Fix）

- 仅编辑确认漂移的文件，保持其余准确文件原样。
- 同步更新受影响文档的 `verified` 字段、新增 vendor 本地信源条目、在 `log.md` **追加**变更记录（不改写历史）。
- 构造性漂移对照同 bundle 其它正确文档（如 05 的 find_opts 由 02-checks-formatting 正确归属反证）。

### 步骤5：落盘核对（Verify）

- 用 `git status`/`git diff` 核对所有变更真实写入磁盘，确认修改文件集合与预期一致。

## 适用场景

- ✅ **依赖升级后对账既有知识库**：bundle 基于老版本源码，需要对齐到新版。
- ✅ **对抗性质量审查既有文档**：怀疑文档与真实源码存在漂移，需逐文件确认。
- ✅ **复用 vendor 方法论资产做目标项目优化**：先对账既有 bundle，再引入到项目。

- ❌ **全新知识包的首次生成**：无既有内容需要保留，应走 source-code-to-okf-wiki-workflow 全量链路。
- ❌ **快速纠单个笔误**：仅一处明显拼写错误时，直接改即可，不需要完整五步。
- ❌ **源码与文档都未变更**：无触发条件，不应无意义地"对账"。

## 反目标用户/场景

> 本模式为"增量对账"而设计，**不做全量重写、不做事实臆造、不做无代价全面审查**。以下三类用户/场景若强行套用会适得其反，请先重新评估其真实诉求。

### 反目标1：期望"零维护自动同步"的用户

- **特征**：想一次性对完后再也不用管，把 bundle 数据源直接镜像 vendor 源码。
- **为何不适用**：本模式输出的是"漂移报告 + 定向修复"，不替代后续维护；源码一变仍需再跑一轮对账，且 vendor 演进不会自动回写 bundle。强行套用会因"对完仍要继续盯"而失望。
- **替代**：走自动镜像/生成器（若 bundle 支持），或明确接受手动周期性对账的成本。

### 反目标2：只想"快速改一处拼写/标点"的维护者

- **特征**：仅发现一处笔误，希望立刻改完收工，不想走完整五步流程。
- **为何不适用**：完整对账（遍历 22 文件 + Grep 逐项 + 报告 + 落盘核对）对单点笔误是过重成本，产出报告反而造成噪音。
- **替代**：直接定位修改，顺手同步 `verified`，可跳过对账与报告步骤。

### 反目标3：把"对账"当作"AI 全量重写"的投机者

- **特征**：借"对账更新"名义，诱使 AI 无视既有准确内容整体重新生成 bundle，以图"更新更好"。
- **为何不适用**：全量重写是本模式明确反对的反模式1，会破坏已验证事实并引入新虚构，与本模式"只改确认漂移处"的纪律根本冲突。
- **替代**：若有充分理由重写，应按 source-code-to-okf-wiki-workflow 全量链路全新生成并重新验证。

## 实际案例

invocations v4.1.0 bundle 22 文件对账（2026-08-24）：
- 确定性漂移 2（源码路径 L47 写错、`packaging.find_opts` 伪造配置键）+ 疑似漂移 1（`ci.sudo.group`→`groups`）
- 无问题 19，核心 API 引用全部忠实
- 修复 3 处 + 更新 verified + log 追加后，`git diff` 确认 6 文件修改 + 1 新文件 tasks.py 全部落盘

## 失败案例

- **场景**：未经对账直接相信 bundle 的源码路径，未用 `invocations.__file__` 实测，D1 路径漂移险些漏检。
- **教训**：源码路径必须运行时实测，不能照抄文档。

## 早期预警信号

| 预警信号 | 可能问题 | 建议行动 |
|---|---|---|
| 文档出现 `ns.configure` 里"存在但归属错误"的键 | 配置键漂移 | 核对键所属模块 |
| 声称的源码路径不指向实际目录 | 路径漂移 | 用 `__file__` 实测 |
| 修复后 `git status` 与预期文件集合不符 | 变更未落盘或误改 | 用 git diff 核对 |

## 反模式

### 反模式1：全量重写 bundle 做"更新"

不逐文件对账，直接把整个 bundle 用 AI 重新生成一遍。破坏已验证的准确内容，还引入新虚构。**正确做法**：只定向修复确认漂移的文件。

### 反模式2：只验证 API 存在，不验证归属

Grep 到配置键存在就认为正确，不检查它是否在正确的 `ns.configure` 块内。漏检 `packaging.find_opts`（真实归属 `checks.blacken`）。**正确做法**：对配置键核对所属模块，并用同 bundle 正确文档反证。

### 反模式3：假定文档中的源码路径正确

不实测，直接沿用文档路径。漏检 D1 路径漂移。**正确做法**：用 `module.__file__` 运行时实测路径。

### 反模式4：修复不动 verified/log

正文改了但 `verified` 字段不更新、`log.md` 不追加，审计链断裂。**正确做法**：同步更新 verified、新增信源条目、append 变更记录。

### 反模式5：修复后不核对落盘

凭过程描述自认为"已完成"，不做 `git diff`。**正确做法**：用 `git diff`/`git status` 核对变更真实写入磁盘（修复即闭环铁律）。

### 反模式6：改写 log.md 历史记录

把历史生成日志直接改掉以消除错误。**正确做法**：log.md 是 append-only 变更日志，用新条目记录本轮更新与修正。

## 检验标准

| 维度 | 检验点 |
|---|---|
| 复基线 | 版本、真实模块清单、不存在的模块均明确记录 |
| 对账 | 逐文件给结论，配置键核对所属模块 |
| 漂移分类 | 确定性/疑似/无问题三类明确区分 |
| 修复 | 仅改漂移点，verified/log 同步，log 只 append |
| 落盘 | git diff/status 确认修改集合与预期一致 |
| G3（模式） | 含触发场景、核心步骤、反模式（≥6）、迁移验证 |

## 跨场景迁移

- **任意依赖升级后对账**：把 vendor 换成新版依赖，同样五步对账既有 OKF bundle。
- **知识库 API 差异核对**：检查既有方法与新库 API 签名初始值的差异。
- **项目优化引入 vendor 能力**：先对账确认 bundle 准确，再决定是否把它引入目标项目。
