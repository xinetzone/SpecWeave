# 多子项目生态→OKF知识束归并生成模式

## 模式类型

方法论模式 / AI协作 / 知识沉淀

## 成熟度

L1 已验证（1 次验证：2026-08-29 Tongyi-MAI 5 子项目→3 束；形式化了 protobuf 姊妹仓拆束与 containers 多仓多束两次非正式先例）

## 模式概述

当"源码学习"对象不是一个仓库，而是**一个目录下的多个子项目生态**（实现代码仓 + 网站/论文仓 + 博客站混合）时，直接套用单仓版[源码阅读→OKF Wiki生成工作流](./source-code-to-okf-wiki-workflow.md)会面临四个新问题：束粒度如何归并、多路事实如何编号不冲突、网站型项目如何避免虚构实现、多束产出的三级索引如何同步。本模式在五阶段链路（R→I→E→V→C）之上补充**归并决策、并行编排、编号前缀、信源红线、计数口径**五项生态级机制。核心价值：一次会话产出覆盖整个生态的多束知识包，且事实可溯源、束间关系清晰、索引计数准确。

## 触发场景

满足以下任一条件时适用本模式，否则用上游单仓模式：

| 特征 | 判定 |
|---|---|
| 源码根下有 ≥2 个独立子项目（各有自己的 README/构建体系） | ✅ 生态归并 |
| 子项目中混有"仅网站/Paper/博客"形态（无实现代码） | ✅ 必须用（涉及非实现仓处理） |
| 单仓但双语/双层（如 tiktoken） | ❌ 用上游模式（按层拆分 R 阶段） |
| 单仓超大 monorepo 按主题拆事实 | ⚠️ 参考上游 protobuf 案例，无需束级归并 |

## 核心步骤

### 步骤1：子项目盘点与归并决策树

对每个子项目按**信源类型**分类，决定束归属：

1. **实现代码仓**（有 src/、构建配置、可运行测试）→ 独立成束，源码精读
2. **网站/论文仓**（仅静态站、README、Paper、leaderboard 数据）→ 两条路径：
   - 与某实现仓强相关 → 并入该束成一"设计精读"概念篇（如 Tongyi-MAI 的 Qwen-UI-Agent 网站并入 mobilepa-bench 束）
   - 自成知识域（如独立基准设计）→ 独立成束，**全文明示"该仓为网站/论文资产，非实现代码仓"**（引用 README 原文为证）
3. **博客/构建产物**（重定向 stub、自动生成站）→ 不成篇，仅在 references/ 登记存在性与 URL 字面标题
4. 归并产出束清单 + 每束的 facts 文件映射（一束可对多份 facts）

### 步骤2：按束拆分并行事实采集（R 阶段）

- 每个事实采集 Sub-Agent 负责 1~2 个子项目，产出 `facts-<repo>.md`，**各自从 F-001 独立编号**
- 上下文传递靠**文件**（facts/insights 落盘于 `.trae/specs/<change-id>/`），不靠对话记忆——并行代理间零共享上下文
- 每路采集附硬性规则：零推测、逐条路径、末尾模块覆盖核对表
- 多路可完全并行（无依赖），规模参考：Tongyi-MAI 3 路并行共 206 条

### 步骤3：合并编号台账（防冲突）

I/E 阶段某束需要引用多份 facts 时，合并台账采用**主信源沿用原编号 + 次信源改前缀编号**：

```
A 部分：F-001~F-032（MobilePA-Bench，原编号沿用）
B 部分：WEB-A-01~WEB-A-24（Qwen-UI-Agent 网站，改前缀，逐条标注 facts-websites.md 原编号映射）
```

禁止两份 facts 直接拼接（F-001 重复）或重新全局重编（溯源断裂）。

### 步骤4：统一知识地图与束间关系（I 阶段）

- 每束 3-5 个洞察四元组，另设"跨束关系"小节：模型实现束 ↔ 评测环境束 ↔ 基准设计束的角色分工
- 知识地图明确每篇 concepts 的文件名、覆盖 F-xxx 编号范围、束内学习路径

### 步骤5：按束并行批量生成（E 阶段）

- 每束一个 Sub-Agent，**束内仍严格信源先行（references/→concepts/→examples/→index 最后写）**
- 每个代理只允许写自己的束目录（防串写）；跨束互链按蓝图预先落位（`../<bundle>/index.md`），并行束互相未落盘时先行写入、V 阶段复核

### 步骤6：三级索引同步

生成完成后一次性更新：分组索引（新束条目+toctree 行）→ 域索引（组束数）→ 总索引（total_bundles、域束数、说明文字）。**所有计数编辑前强制重读文件取当前值**（防陈旧快照，见上游反模式10），并按"逐域标题行重新核算"复核。

### 步骤7：跨束验证（V 阶段）

在上游单束检查清单（结构/frontmatter/链接/Grep API 验证）之上追加：

- 跨束互链矩阵：N 束两两互链的存在性与方向（单向互链需声明）
- 多束数字一致性抽查：同一数字在不同束/索引中的口径一致（如榜单分数注明出处文件与版本）
- 三级索引计数与实际目录树一致（`invoke gates.all` 收口）

## 反模式

### 反模式1："用 Grep 匹配行数当成员计数，无统计口径"

统计"类有多少方法"时直接把 `Grep "def "` 的输出行数当方法数。后果：嵌套函数、继承方法、重载注释被计入（Tongyi-MAI 实测 AndroidController Grep 35 行→实际实例方法 32 个，且文档自身分组清单 7+10+2+4+2+7=32 与标题 35 自相矛盾才暴露）。**正确做法**：计数类事实必须写明统计口径（"class 级 def，含 __init__，不含嵌套函数/不含 __init__.py"），并在 V 阶段用文档内部分解式清单交叉验证总数。

### 反模式2："多份 facts 文件直接拼接台账"

合并多个子项目的 facts 时沿用各自编号直接拼接。后果：F-001 重复、文档引用无法唯一定位。**正确做法**：主信源沿用原编号，次信源改前缀编号（WEB-A-01）并保留原编号映射。

### 反模式3："把网站/论文仓当实现仓写"

对仅有静态站与 README 的仓库，凭"常见架构"虚构其实现细节（如虚构评测脚本、虚构数据库）。后果：整束可信度崩塌且无从 Grep 验证。**正确做法**：R 阶段明确登记"该仓为网站/Paper 资产，非实现代码仓"（引 README 原文），文档只写站点结构、技术栈、声明的数据事实。

### 反模式4："对不可达信源硬抓正文"

博客/文档正文是 JS 渲染重定向 stub（如 Notion meta-refresh）时，反复尝试抓取甚至凭标题补写正文。**正确做法**：零推测红线——仅登记 stub 存在性与 URL 字面标题，正文零引用；确需正文则改用浏览器自动化抓取并升级信源，不可凭标题推断。

### 反模式5："多信源数据不一致时混用数字"

同一指标在不同信源文件中收录范围不同（如 leaderboard.json 与 HTML 表格收录模型不同、分数口径不同），文档里混用且不注出处。**正确做法**：每个数字标注出处文件+版本（"出自 paper_v5 Table 1，v1.5"）；台账须登记信源间差异事实，提示"两信源不可混用"。

### 反模式6："三级索引只更新分组层"

新束只写进分组索引，域索引/总索引计数不更新。后果：计数漂移、BFS 导航断头、质量门失败。**正确做法**：分组→域→总三级同步，每级编辑前重读当前值，收口跑 `invoke gates.all`。

## 检验标准

| 维度 | 检验点 |
|---|---|
| 归并决策 | 每个子项目有明确束归属与信源类型标注；网站型项目有"非实现仓"声明 |
| R 阶段 | 按束拆分的多份 facts 编号独立无冲突；并行代理只写各自文件 |
| I 阶段 | 知识地图含跨束关系小节；每篇文档有 F-xxx 覆盖范围 |
| E 阶段 | 束内信源先行、批次≤7、index 最后写；跨束互链按约定路径 |
| V 阶段 | 跨束互链矩阵全通过；计数有口径且经分解式清单交叉验证；三级索引计数与目录树一致 |
| 收口 | `invoke gates.all` 零失败；两仓库（子模块→主仓库）原子提交 |

## 实际案例

Tongyi-MAI 生态（2026-08-29）：

| 阶段 | 产出 | 关键指标 |
|---|---|---|
| 归并 | 5 子项目 → 3 束（mai-ui / mobile-world / mobilepa-bench） | 2 个实现仓独立成束；网站+基准合并；博客 stub 仅登记 |
| R | 3 路并行采集，4 份 facts 共 206 条 | 各路独立编号，零推测 |
| I | insights.md 332 行，15 个四元组 + 跨束关系 | 20 篇 concepts 蓝图 |

| C | 三级索引 283→286；gates.all 零失败 | 子模块 d67de37b + 主仓库指针原子提交 |

## 失败案例

### 案例：AndroidController 方法数"Grep 35 行"vs 实际 32 个（Tongyi-MAI 实践）

**背景**：R 阶段采集 MobileWorld 源码事实时，事实 F-050 记录"AndroidController 包含 35 个方法"——该数字来自 `Grep "def "` 的输出行数。E 阶段生成的 `05-runtime-controller.md` 沿用了"35 个方法"的表述。

**发现过程**：V 阶段独立验证时，验证代理将文档中的方法逐个 Grep 核对后尝试复现 35 的总数，发现文档自身的分组清单（7+10+2+4+2+7=32）与标题"35 个方法"自相矛盾；逐一核对 Grep 输出发现 35 行中含 2 个嵌套函数（`is_file_empty` 出现在两个方法内部），class 级 def 共 33（含 `__init__`），实例方法 32。

**根因分析**：
1. R 阶段把 Grep 工具的输出行数直接当作成员计数，未写明统计口径
2. 采集代理与生成代理是两个独立上下文，生成代理只会引用事实数字、不会复核——错误随文件传递且被"信任"两跳
3. 单靠 Grep 行数无法区分嵌套函数/继承成员，总数型事实缺少可分解的验证途径

**修复**：以源码为准将 35→32，同步修复概念文档标题与正文、束根 index 导航行、束内 facts 台账与 spec 目录原始台账共 6 处；并固化"计数带口径+分解式清单交叉验证"规则（本模式反模式1／上游反模式14）。同轮 V 阶段共发现 17 处同类计数偏差（任务场景目录 8→10 等），全部按源码修复。

**教训**：多跳传递链路（R 采集→E 生成→V 验证）中，总数型事实必须在采集时写明口径，否则错误会被后续每一跳放大为"已确认事实"；文档内部自相矛盾是暴露此类错误的最有效信号，V 阶段应主动做分解求和核对。

## 不适用场景与反目标用户

### 不适用场景

- ❌ **单仓项目（最常见的误用）**：学习对象是单个仓库时，束级归并、编号前缀、跨束互链全是无用开销——直接用上游 [source-code-to-okf-wiki-workflow.md](./source-code-to-okf-wiki-workflow.md)，仅在其"姊妹仓/双层库"边界场景参考对应迁移案例。
- ❌ **纯文档批量转换（无源码）**：对象是已有 Markdown 文档集/报告/笔记而非源码时，R 阶段源码事实采集无对象——改用 [batch-docs-to-okf-bundle-conversion](../concepts/batch-docs-to-okf-bundle-conversion.md) 模式。
- ❌ **子项目间无知识关联的松散合集**：目录下各子项目分属不相干领域（如一个杂烩 tools 目录）时，强行归并为"生态"会产生虚假的跨束关系与牵强的互链——应各自独立立项（各自 spec）分别生成。
- ❌ **超大规模且子项目数 >10 的生态（边界场景）**：并行 Sub-Agent 路数过多会导致索引合并与 V 阶段跨束验证成本超线性增长——应分批会话执行（如按域分 2~3 个会话，每会话 ≤5 束），总索引更新遵循重读计数纪律。

### 反目标用户

- **赶时间的浅层了解者**：只想知道"这个生态是做什么的"，3 束 45 文件的产出远超需求——读一篇文章或 README 即可。
- **不要求事实溯源的营销文案写手**：本模式的零推测红线、计数口径、信源登记对营销材料是纯开销，其目标是传播速度而非可验证性。

### 适用边界与前提条件

- 前提：子项目可本地访问全部信源（源码/README/数据文件）；既有 OKF 基础设施（分组索引、toctrees 质量门、提交钩子）
- 并行 Sub-Agent 数量建议 ≤4；单份 facts 文件 ≤150 条（超出继续按主题拆分）

## 早期预警信号

| 预警信号 | 可能问题 | 建议行动 |
|---|---|---|
| 文档内"总数"与分组清单求和不一致 | 计数口径错误（反模式1） | 立即重查源码，写明口径后全面复检同类计数 |
| 两份 facts 出现相同编号 F-xxx | 台账合并未做前缀隔离（反模式2） | 引入前缀编号并保留原编号映射 |
| 网站/论文型束出现"框架源码/脚本实现"类描述 | 把非实现仓当实现仓写（反模式3） | 删除虚构段落，改登记站点结构与 README 声明 |
| 某信源反复抓取失败或内容与标题不符 | 信源是重定向 stub（反模式4） | 仅登记存在性，禁止凭标题补写正文 |
| 同一指标在不同文档中数值不同 | 多信源混用未注出处（反模式5） | 每个数字标注出处文件+版本，台账登记差异 |
| 分组索引已更新但总索引计数仍是旧值 | 三级索引只更新一处（反模式6） | 按"逐域标题行重新核算"补齐并跑 gates.all |
| 并行生成代理写入了其他束的目录 | 越权写入/蓝图未隔离 | 立即回滚该文件，约束代理"只写自己束目录" |

## 迁移验证

- **protobuf（2026-08-28，上游工作流内）**：姊妹仓 protobuf/protobuf-ci 拆为同组两束，是本模式"拆束+分组索引承载生态关系"的非正式先例；本模式将其中的归并决策与索引同步形式化。
- **containers（2026-08-28）**：7 仓多束生成及其 52 项 toctree 门禁失败修复，佐证本模式反模式6与上游反模式11。
- **可迁移场景**：monorepo 多模块文档化、公司多产品线知识库、paper+code 混合生态（如 benchmark 官网+框架仓）。
