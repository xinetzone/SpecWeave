# 上下文生命周期分层管理模式

## 模式概述

设计多智能体系统的上下文注入机制时，**不同类型的指令/规范/约束应该有不同的生命周期管理策略**，从全程在场到按需加载到懒加载到隔离执行到代码硬护栏，形成一条从"信任模型判断力"到"代码确定性执行"的连续光谱。不要将所有内容都塞进全局入口文件，也不要将安全约束只写在提示词中期盼模型自觉遵守。

本模式的配套决策框架是"事实-流程-护栏-隔离任务"四象限分类法（见本复盘洞察3）：四象限回答"是什么类型的内容"，五层光谱回答"用什么生命周期管理"。

## 问题现象

Agent系统上下文管理不当的常见症状：

1. **全局入口文件膨胀**：AGENTS.md/CLAUDE.md越来越长，token占用越来越大，真正关键的约束被淹没在细节中，模型在长会话中遵循率下降
2. **安全护栏仅靠提示词**："禁止rm -rf"、"写文件后必须格式化"这类约束只写在提示词中，模型在压力/长上下文/提示注入场景下会违反
3. **流程性规范污染全局**：部署步骤、发布流程、review checklist这类只有特定场景才需要的内容全程在场，浪费token且干扰注意力
4. **主会话承担脏活**：搜索30个文件、翻日志、批量对比这类会产生大量中间结果的任务由主会话执行，中间结果污染上下文导致后续任务质量下降
5. **所有约束同权重**："应该考虑代码可读性"和"绝对不能删除生产数据库"被同等对待，模型无法区分建议和强制约束

这些问题的共同根因是：**假设所有指令的重要性、使用频率、确定性要求都是一样的**，用单一的生命周期策略（通常是"全程放在提示词中"）管理所有类型的上下文。

## 解决方案：五层生命周期光谱

```
信任模型 ←————————————————————————————————————————→ 机制保障（确定性）

第一层：全局事实  →  第二层：局部规则  →  第三层：懒加载技能  →  第四层：隔离执行  →  第五层：代码硬护栏
全程在场          按需出现（路径限定）  调用时加载            独立窗口            事件触发代码执行
提示词级          提示词级             提示词级              独立上下文          代码级（不可绕过）
低确定性          低确定性             中确定性              中确定性            绝对确定
```

### 第一层：全局事实（Global Facts）

**放置内容**：
- 项目目录结构
- 核心构建/测试命令
- 基本编码规范
- 跨场景通用的背景知识

**生命周期**：全程在场，每次会话启动时加载
**确定性要求**：低——依赖模型参考，不需要强制执行
**典型实现**：CLAUDE.md、AGENTS.md、README.md
**反模式警惕**：不要把流程步骤、检查清单、操作指南放在这一层——这些不是"事实"，是"流程"

### 第二层：局部规则（Scoped Rules）

**放置内容**：
- 特定目录下的文件约定
- 特定模块的编码规范
- 特定子项目的特殊要求
- 路径限定的约束

**生命周期**：进入对应目录/路径时才加载
**确定性要求**：低——同全局事实，但作用范围限定
**典型实现**：Rules（路径限定）、子目录AGENTS.md、.cursorrules（带目录匹配）
**设计价值**：避免全局文件膨胀，只在相关上下文中出现局部约定

### 第三层：懒加载技能（Lazy-loaded Skills）

**放置内容**：
- 多步操作流程（部署步骤、发布流程、review流程）
- 特定任务的检查清单
- 专用工具的使用指南
- 只有执行特定操作时才需要的完整说明

**生命周期**：用户触发/任务匹配时才加载，用完从上下文移除
**确定性要求**：中——模型应该遵循流程，但流程本身是提示词级的
**典型实现**：Skills、Slash Commands、按需加载的工具文档
**设计价值**：流程性内容不常驻上下文，需要时才提供完整说明，大幅节省常驻token

### 第四层：隔离执行（Isolated Execution）

**放置内容**：
- 大规模搜索（30+文件）
- 日志分析/审计
- 批量对比研究
- 会产生大量中间结果的探索性任务
- 需要客观验证的审查任务

**生命周期**：在独立子代理/独立上下文窗口中执行，只返回最终结论，中间过程不污染主会话
**确定性要求**：中——执行过程仍依赖模型，但结果返回后主会话看不到中间垃圾
**典型实现**：Subagents、独立工作区、分支验证
**设计价值**：解决单上下文窗口的三大缺陷——偷懒（任务边界明确）、自我偏好（独立窗口无认知惯性）、目标漂移（每个子任务窗口小、目标清晰）；同时防止中间结果污染主上下文

### 第五层：代码硬护栏（Code-level Guardrails）

**放置内容**：
- 绝对禁止的操作（rm -rf /、删生产库、提交密钥）
- 必须执行的动作（写文件后格式化、提交前跑测试、删除后必须确认）
- 安全关键约束
- 合规要求

**生命周期**：事件触发，代码级执行，不依赖模型判断力
**确定性要求**：绝对——代码执行不看模型"想不想"遵守，触发条件满足就强制执行/阻止
**典型实现**：Hooks（PreToolUse/PostToolUse事件拦截）、Git pre-commit hooks、CI强制检查、静态分析工具
**设计价值**：安全关键约束从"提示词建议"下沉到"代码强制执行"，彻底解决长上下文中提示词遵循率衰减问题

## 决策框架：五层选择标准

| 内容特征 | 应该放在哪一层 | 判断标准 |
|---------|---------------|---------|
| 这是不变的事实，所有场景都需要知道 | 第一层（全局事实） | "做任何操作都可能需要参考这个" |
| 这是事实，但只有在特定目录/模块才相关 | 第二层（局部规则） | "只有做X目录下的工作时才需要知道这个" |
| 这是操作流程/步骤，不是事实，只有做特定操作时才需要完整步骤 | 第三层（懒加载技能） | "不需要一直记住怎么做，但做的时候需要完整指南" |
| 这会产生大量中间结果，不需要看过程只需要结论 | 第四层（隔离执行） | "搜索/探索/试错过程会产生很多垃圾，只要最终结果" |
| 这个约束绝对不能违反，违反后果严重 | 第五层（代码硬护栏） | "违反了就出事故，绝对不能依赖模型记得" |

## 设计原则

1. **光谱思维，非二元分类**：五层不是五个孤立的桶，而是连续光谱——层与层之间可以有中间形态（如临时追加的system prompt位于3-4层之间）
2. **向右下沉原则**：当一个约束在低确定性层（提示词层）反复被违反，应该考虑向右下沉到更高确定性层（代码层）。反复出现的问题不是"模型不够聪明"，是放置层级错了
3. **token预算意识**：第一层和第二层的内容是常驻开销，必须精简；第三层和第四层的内容是按需开销，可以详细；第五层是代码，不占模型上下文token
4. **单一职责**：每层只放适合该层生命周期的内容，不要跨层乱放——特别是不要用第一层（全局文件）承载第三层（流程）或第五层（护栏）的功能
5. **失败代价匹配层级**：约束被违反的代价越大，越应该放在右侧高确定性层级

## 反模式

### 反模式1：全局文件大杂烩

```
AGENTS.md包含：
  - 目录结构 ✓（第一层，合适）
  - 编码规范 ✓（第一层，合适）
  - 完整的代码提交流程（15步） ❌（第三层，应该做成Skill）
  - 完整的PR review checklist ❌（第三层，应该做成Skill）
  - "禁止提交密钥到git" ❌（第五层，应该用pre-commit hook或CI检查）
  - "部署前必须跑完整测试套件" ❌（第五层，应该用Hook或CI强制）
  - "搜索文件应该用ripgrep而非grep -r" ❌（第三层，技能提示）
```

**问题**：全局文件膨胀到500+行，常驻token占用大，真正关键的信息被淹没，安全约束只靠提示词不可靠。

**正确做法**：按五层框架拆分，流程类做成Skills按需加载，安全类做成Hooks/CI强制执行。

### 反模式2：护栏提示词化

```
在AGENTS.md中写：
"⚠️ 绝对禁止：不要执行rm -rf命令！不要删除生产数据库！"
```

**问题**：这是第五层的内容，却放在第一层。在长会话、提示注入、模型压力大时，这类提示词约束会被忽略。

**正确做法**：用PreToolUse Hook拦截危险命令，用数据库权限控制保护生产库，用CI检查防止密钥提交——让代码强制执行，而非期盼模型自觉。

### 反模式3：主会话干脏活

```
主代理自己执行：
"搜索所有.ts文件，找出包含TODO注释的，统计分布，分析哪些模块债务最多"
```

**问题**：搜索过程会产生大量文件路径、代码片段、中间统计结果，全部进入主会话上下文，污染后续任务的注意力。

**正确做法**：委派给子代理在独立窗口执行，只返回最终统计报告和分析结论。

### 反模式4：所有约束一个权重

```
所有约束都用同样的语气和格式：
"建议保持代码简洁"
"绝对不能删除用户数据"
```

模型无法区分"建议"和"强制"，在注意力有限时会选择性忽略——可能刚好忽略的是最不能忽略的那条。

**正确做法**：通过分层体现权重——建议类在提示词层，强制类在代码层；不需要靠"语气强烈"来强调，靠放置层级决定确定性。

## 迁移验证

### 验证案例1：Claude Code官方设计（来源案例）

Claude Code的8种上下文注入机制完美符合五层光谱：
- 第一层：根CLAUDE.md（全程在场的事实）
- 第二层：子目录CLAUDE.md/Rules（路径限定的局部规则）
- 第三层：Skills（懒加载的流程）
- 第四层：Subagents/Dynamic Workflows（隔离执行）
- 第四层半：Output Styles/System Prompt Append（高权重但仍是提示词级）
- 第五层：Hooks（事件触发代码执行）

官方设计验证了本模式的有效性——Anthropic作为Agent系统设计者，经过大量实践后选择的就是这种分层架构。

### 验证案例2：SpecWeave项目实践（复用案例1）

SpecWeave项目已有部分分层实现：
- 第一层：AGENTS.md（全局事实+路由）
- 第三层：Skills门面（懒加载命令集）
- 第四层：Subagents（任务委托隔离执行）
- 第五层：阶段守卫（Hooks，部分代码级检查）

本案例验证了模式可在开源项目中落地，且在持续演进中（本次知识沉淀后子代理规范进一步强化了第四层的任务粒度原则）。

### 验证案例3：子代理截断问题解决（复用案例2）

本次复盘中发现的子代理输出截断/偷懒问题，根因就是违反了第四层"隔离执行"的原则——将3个分析任务合并委派给一个子代理，导致单窗口任务粒度过大触发Agentic laziness。

按照本模式修正后：
- 单个Task委派给一个子代理（任务粒度符合第四层原子性要求）
- 分析类任务使用四要素模板明确边界（减少完成边界模糊）
- "事不过二"兜底策略（第二次失败后主会话兜底，不无限重试）

修正后新委派的子代理返回完整内容的概率显著提升，验证了分层原则在具体问题解决中的指导价值。

## 适用场景

- ✅ 设计AI Agent系统的上下文注入/提示词管理架构
- ✅ 重构现有Agent配置文件膨胀问题
- ✅ 审查现有规范体系，识别"放错层"的内容
- ✅ 为新的Agent功能选择合适的上下文注入方式
- ✅ 评估Agent系统可靠性，识别"护栏仅靠提示词"的风险点
- ❌ 简单的单轮对话机器人（不需要分层，直接用系统提示词即可）
- ❌ 纯代码编写任务（不涉及Agent系统设计时不需要考虑）

## 边界与选型

**何时需要严格五层**：
- 复杂Agent系统（如Coding Agent、Research Agent）
- 多场景、多用户、多任务的通用Agent平台
- 有安全/合规要求的生产环境Agent

**何时可以简化**：
- 个人使用的简单Agent（两层就够：全局提示词+必要时手动加载上下文）
- 单一场景专用Agent（三层：全局+技能+子代理）
- 原型验证阶段（先堆在全局文件，跑通后再重构分层）

**分层重构优先级**：
1. 最高优先级：将第五层（安全护栏）从提示词下沉到代码
2. 次高优先级：将第三层（长流程）从全局文件拆分为Skills
3. 最后优化：第一层和第二层的拆分（全局膨胀问题影响效率但不影响安全）
