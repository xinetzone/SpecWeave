# 行动优先Agent输出模式（Action-First Output Paradigm）

## 模式类型

方法论模式

## 成熟度

L2 已验证（i-have-adhd项目9400+ Star实践验证 + SpecWeave二次验证复盘审查）

## 适用场景

- AI编码助手、命令行工具等高频工具性交互场景
- Bug修复、代码修改、命令执行、环境配置等"告诉我怎么做"的任务
- 用户目标是快速获取可执行方案、立即开始行动而非理解原理
- 时间敏感型操作、高频重复任务、低风险可逆操作
- 专家用户+常规任务组合场景

## 问题背景

传统AI对话遵循"解释-结论"的自然语言叙事结构：先铺垫背景、分析问题、推导方案，最后给出结论。这种结构在知识学习、方案讨论等场景是合适的，但在编码调试、命令执行等高频工具性场景中存在严重问题：
- 关键答案隐藏在段落中间，用户需要在冗余铺垫中搜寻
- "问得好！""希望这有帮助！"等程序化客套话增加认知噪音
- 多轮对话后上下文断裂，用户需要翻阅历史记录回忆"我们说到哪了"
- 离题建议（如修复Bug后主动建议升级依赖）分散注意力
- 用户在注意力最集中的初始接触阶段被迫处理低价值铺垫内容

## 核心规则

### 规则1：答案第一行，结论前置

回复第一行默认直接呈现可执行内容（命令、路径、代码片段、核心结论），解释内容放置于答案之后。提供具体量化的时间估计（如"大约15分钟"），默认不使用"一会儿""很快"等模糊表述——例外：短平快单轮交互（2轮以内）且用户未询问时间预期时，时间估计可省略。

### 规则2：步骤编号，单步单动作

多步任务采用1-2-3数字编号列出，每一项仅包含单一动作。合并可合并环节，去掉多余步骤。步骤数量控制在7±2个工作记忆容量范围内，超过10个步骤时按阶段分组。

### 规则3：每轮重述进度，卸载用户记忆负担

每一回合开头明确告知用户当前所处阶段、已完成操作内容、待解决问题清单。对话中断后恢复时，首轮回复自动包含完整任务状态回顾。用户无需翻阅历史记录即可继续工作。

### 规则4：压制离题和客套，信噪比最大化

完成当前任务前默认不提及其他无关任务。移除"问得好！""希望这有帮助！"等程序化开场和收尾语句。建议数量大于5条时，自动区分"现在做"和"以后做"分类。默认每一句话聚焦与当前任务直接相关的信息价值——例外：人际互动中适度寒暄有助于建立信任；非技术用户前3轮对话保留适度礼貌用语；创意发散阶段允许离题探索（需主动切换范式）。

## 操作流程

混合范式黄金结构（大多数场景的最优默认）：

```
【首屏核心区】（30秒内可读完）
├─ 核心结论/答案/命令（第一行）
├─ 关键进度/状态（如需要）
└─ 立即要做的1-3个行动项

【中间详细区】（用户按需阅读）
├─ 详细操作步骤（编号，单一步骤）
├─ 关键注意事项/风险提示
└─ 预期结果/验证方法

【可选补充区】（用户深入时阅读）
├─ 原理解释/设计思路
├─ 备选方案/trade-off分析
├─ 延伸阅读/参考资料
└─ 💡 额外建议（现在做/以后做分类）
```

范式切换判断流程：
1. 判断用户核心意图："做"→行动优先，"懂"→解释优先
2. 判断操作风险等级：低风险→行动优先，高风险→解释优先+确认
3. 判断用户-任务熟悉度：专家+常规→极致行动优先，新手+新任务→解释优先

## 反模式/反例警示

| 反模式 | 后果 |
|--------|------|
| 纯行动优先零解释，高风险操作直接给命令无确认 | 用户在未理解后果的情况下执行危险操作（如删除生产数据库） |
| 强制所有场景都第一行给答案，情感支持场景也直接给方案 | 用户感到冷漠无情，破坏信任关系 |
| 进度重述过于冗长，每轮都输出完整状态清单 | Token消耗增加，高频交互时打断心流 |
| 机械压制一切离题，发现严重风险也不提醒 | 错过关键风险预警，造成更大损失 |
| 中文语境完全移除"好的""收到"等短语 | 失去"确认收到指令"的沟通功能，显得生硬无礼 |

## 正例

i-have-adhd项目激活后的输出示例：
```
运行 npm install jsonwebtoken@latest，然后编辑 src/auth.ts:42。

【当前进度】修复JWT依赖漏洞 | 已完成：定位漏洞位置 | 待完成：升级依赖、验证修复

步骤：
1. 执行 npm install jsonwebtoken@latest 升级依赖（大约1分钟）
2. 打开 src/auth.ts:42，将 require('jsonwebtoken') 改为 import 语法
3. 运行 npm test 验证所有测试通过
4. 执行 npm run build 确认构建成功

💡 额外建议：
- 【现在做】检查 package.json 中其他依赖是否也有安全更新
- 【以后做】考虑配置 npm audit 自动检查

执行完第一步后告诉我结果，我会继续指导后续步骤。
```

对比传统输出：
```
问得好！这个问题我来帮你分析一下。
首先，让我了解一下你的项目结构...
（三段上下文铺垫）
...所以你需要运行 npm install jsonwebtoken@latest，然后编辑 src/auth.ts:42。
（中间夹带依赖升级建议）
...希望这能对你有所帮助！如果还有其他问题随时问我。
```

## 弹性提示

### 文化差异
- 中文语境下"好的""收到"等短语不仅是客套，还承担"确认收到指令"的沟通功能，不宜完全移除
- 面向企业客户、非技术管理者时，适度的上下文铺垫是专业素养的体现
- 首次接触新用户的前3轮对话，可保留适度礼貌用语建立信任

### 破规场景（必须主动打破规则）
1. **用户情绪崩溃/表达负面情绪**：先共情回应再解决问题
2. **高风险不可逆操作**（删除数据、生产环境修改）：先前置风险说明、回滚方案，获得确认后再给命令
3. **用户明确要求"先解释一下""我们先聊聊"**：尊重用户意愿，切换到解释优先模式
4. **发现严重风险/阻塞问题**：即使"离题"也应立即提醒，标注"⚠️ 重要风险提示"——轻微风险（不影响当前任务执行的小问题）可记录到"以后做"建议中，不必打断当前流程

### Token成本提示
- 进度重述等规则本身会增加Token消耗，短平快单轮交互（2轮以内）可省略重述
- 高频连续交互（如逐行调试）可简化为极简状态提示（如"→ 继续修改X文件"）
- 实际Token节省幅度需按场景测量，不要假设行动优先一定省Token

### 非技术用户场景边界（V2补充）
- 非技术用户（产品经理、设计师、业务用户）面对代码片段/命令行路径可能产生畏难情绪，首屏除了核心结论外，建议增加1-2句"这是什么/为什么需要"的极简上下文
- 时间估计（"大约1分钟"）对非技术用户可能不准确——他们不知道npm install在自己机器上需要多久，建议改为"这是一个简单操作，完成后告诉我结果"而非量化时间
- 单步单动作对专家用户高效，但对非技术用户可能显得 condescending（居高临下），可适当合并相关步骤并增加"为什么做这一步"的微型说明
- 范式判断关键：如果用户提问中包含"什么是""为什么""帮我理解""你觉得"等探索性词汇，即使内容涉及技术，也默认切换到解释优先

### 多轮长对话场景边界（V2补充：10轮以上）
- 规则3（每轮进度重述）在超过10轮的长对话中会产生"进度疲劳"——用户开始忽略进度块，反而增加认知负担
- 长对话中进度状态变化频繁，"已完成/待完成"清单容易过时或自相矛盾
- 建议调整：(a)5轮以内：完整进度重述；(b)5-15轮：极简进度提示（如"【阶段3/5：执行修复】"）；(c)15轮以上：仅在用户询问进度或对话中断恢复时才重述
- 长对话中Token成本显著累积——进度重述可能占总Token的30-40%，需主动监控
- 长对话往往出现分支、回退、转向，黄金三层结构的线性假设被打破，需允许非线性的探索性回复

### 创意写作/头脑风暴场景边界（V2补充）
- 结论前置在创意发散阶段是有害的——过早给出结论会锚定思维，抑制创意探索
- "单步单动作"与创意流的非线性特征根本冲突——创意需要跳跃、联想、并行思考
- "压制离题"在创意场景中是危险的——大量创意突破来自意外的离题联想（serendipity）
- 信噪比最大化在创意场景不适用——"冗余"的探索、类比、闲聊是创意生成的燃料
- 建议切换为"探索优先"范式：首屏呈现思考方向/待探索问题列表而非结论；中间呈现多个并行思路而非编号步骤；离题不主动压制但标记"💡 这是一个岔路思路"；最后才在可选补充区给出收敛建议

### 高风险决策场景边界（V2补充）
- 现有"高风险=解释优先+确认"的破规场景是正确的，但存在执行风险：行动优先的肌肉记忆可能导致在完成风险评估之前就输出行动指令
- 编号步骤暗示虚假确定性——高风险场景中正确答案可能是"现在不要做任何操作""我们需要先收集更多信息"而非1-2-3步骤
- "大约X分钟"制造虚假时间预期——高风险决策不应被时间估计催促
- 7±2步骤限制可能过度简化复杂决策——涉及法律、财务、生产环境的操作可能需要更多前置分析步骤
- 高风险信号清单：(a)涉及"删除/清空/重置/force"等不可逆操作关键词；(b)涉及生产环境/真实资金/法律后果；(c)用户描述模糊但操作影响范围大；(d)操作需要管理员/root权限且影响多人
- 高风险场景下的输出模板：⚠️风险提示→回滚方案→确认请求→（用户确认后才给出操作步骤）

## 迁移验证（G3质量门）

本模式可迁移到非Agent输出场景：

1. **技术文档写作场景**
   - 应用方式：所有技术文档采用"TL;DR（太长不看）→ 快速开始→ 详细说明→ 附录"结构，文档开头直接给出结论、核心命令、快速开始步骤，背景介绍和原理解释放在后续章节
   - 例子：API文档首屏直接给出"3步快速上手"（安装→初始化→调用示例），认证原理、错误码详解等放在后面章节

2. **PPT汇报场景**
   - 应用方式：汇报PPT采用"结论先行"结构，每页标题直接给出该页核心结论（而非"项目背景""进展情况"等中性标题），第一页PPT直接给出最终结论和行动建议，详细数据和分析过程放在后面
   - 例子：项目进度汇报首页标题不是"Q3项目进展汇报"，而是"Q3进度：整体延期2周，建议追加1名前端开发"，后面再附详细原因分析和数据支撑

3. **工作邮件沟通场景**
   - 应用方式：工作邮件第一自然段直接写明"需要对方做什么、截止时间、为什么重要"，背景介绍和详细说明放在后续段落。超过3个行动项时用编号列出，并标注优先级
   - 例子：邮件开头不是"您好，关于上周讨论的项目..."，而是"您好，请在本周五前审核并回复附件中的方案，该方案需在下周一上线评审使用。详细方案说明如下：..."

## 与现有模式关系

- **output-behavior-specification.md**：该模式提供了Agent输出行为约束的通用四维模型（任务/流程/产出/行为），本模式是行为约束维度在工具性交互场景下的具体落地范式，提供了可直接使用的规则集和黄金结构
- **progressive-context-disclosure.md**：该模式控制"给Agent输入多少信息"（输入端的渐进式披露），本模式控制"Agent给用户输出多少信息、以什么顺序"（输出端的结论前置+分层展开）。两者从输入输出两端共同优化认知负荷和Token利用率
- **constraint-driven-creativity.md**：本模式中的"压制离题和客套""单步单动作"本质上是约束驱动创造力在输出沟通领域的体现——通过格式约束聚焦核心信息传递
