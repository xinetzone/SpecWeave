# 质量-成本动态平衡模式（Quality-Cost Dynamic Balance Pattern）

## 模式类型

方法论模式

## 成熟度

L2 已验证（GitHub Copilot、Zomato等多个案例验证）

## 适用场景

- 优化过程中需要平衡token成本和输出质量
- 不同用户/场景对质量要求不同（VIP用户vs免费用户）
- 不同任务复杂度需要不同压缩率
- 需要上线优化但又担心质量下降
- A/B测试框架完善、需要数据驱动决策的团队

**不适用于**：零容忍质量下降的极端高风险场景（如医疗诊断、法律判决），此类场景应优先保证质量不做激进优化。

## 问题背景

token优化本质是在"成本-质量-延迟"三维空间中找帕累托最优点，但实际中常见两个极端：要么不做任何优化（成本过高），要么"一刀切"用同样的压缩率/同样的模型（简单任务用大模型浪费，复杂任务用小模型质量差）。质量-成本动态平衡通过A/B测试+阈值调优+自适应路由，实现"在满足质量约束的前提下最小化成本"。

数学形式化：min C s.t. Q ≥ Q_min, L ≤ L_max（在质量和延迟约束下最小化成本）。

## 核心规则

### 规则1：建立质量基线和护栏

- 建立"黄金测试集"（≥200条，覆盖典型场景和边缘case）
- 定义质量护栏指标（不可接受的底线）：
  - 任务准确率保持率ARR > 95%（通用场景）或 > 99%（高风险场景）
  - 幻觉率增幅 < 3%（绝对值）
  - 用户满意度CSAT不下降（统计显著）
- 建立全上下文无优化基线，作为对比基准

### 规则2：梯度实验绘制权衡曲线

"压缩率-质量"曲线存在三个关键区域：
- **0-30%压缩：免费午餐区**，质量几乎不损失，应该做
- **30-60%压缩：权衡区**，质量缓慢下降，按需选择
- **>60%压缩：悬崖区**，质量断崖下跌，避免进入

操作步骤：
- 选择3-5个压缩率/模型级别梯度点（如0%、25%、50%、75%压缩，或小/中/大模型）
- 在相同测试集上运行每个梯度
- 测量每个点的：token减少率、质量保持率、延迟变化
- 绘制"压缩率-质量"曲线，找到"甜点区"（帕累托前沿）

### 规则3：建立三级路由/阈值体系

**任务复杂度分级**：
- Tier 1（简单任务，约60%请求）：分类、提取、是/否判断、格式化 → 小模型（Haiku/mini/Flash）+ 高压缩率
- Tier 2（中等任务，约30%请求）：摘要、内容生成、常规问答 → 中等模型（Sonnet/GPT-4o）+ 中压缩率
- Tier 3（复杂任务，约10%请求）：复杂推理、代码生成、歧义问题 → 大模型（Opus/GPT-5）+ 低压缩/不压缩

**用户分级（可选）**：
- VIP/企业用户：大模型+低压缩，体验优先
- 付费用户：中等模型+中压缩，平衡
- 免费用户：小模型+较高压缩，成本优先

**分级压缩率建议**：
- 高风险/高价值场景：压缩率0-30%，质量优先
- 通用场景：压缩率30-50%，平衡质量成本
- 低价值/非关键场景：压缩率50-70%，成本优先

**自动降级机制**：小模型输出置信度低时自动升级到大模型重试，质量低于阈值时自动降低压缩率。

### 规则4：A/B测试验证上线

- 流量分组：对照组（基线）50%，实验组（优化方案）50%
- 用户级分流（同一用户始终在同一组，避免体验不一致）
- 灰度发布：1% → 5% → 20% → 50% → 100%
- 每个阶段至少跑24小时，完整周度周期（7天）
- 同时监控：主要指标（成本）+ 护栏指标（质量/错误率/满意度）

### 规则5：持续监控和动态调优

- 实时监控成本和质量指标看板
- 设置质量告警：质量低于阈值自动告警/回滚
- 定期重新跑梯度实验（模型更新、场景变化后最优可能改变）
- 建立"优化反弹"监控：成本悄悄涨回时及时发现

## 三级模型路由效果对比（行业经验估算）

| 策略 | 成本降低 | 质量影响 | 推荐程度 |
|------|---------|---------|---------|
| 静态大模型（无优化） | 0% | 质量最高 | 仅高风险场景 |
| 静态小模型（一刀切） | 60-80% | 复杂任务质量下降10-30% | ❌ 不推荐 |
| 三级模型路由 | 40-60% | 质量保持率>97% | ✅ 所有场景推荐 |
| 三级路由+自适应压缩 | 60-75% | 质量保持率>95% | ✅ 成熟团队推荐 |
| 三级路由+用户分级+动态调优 | 70-85% | 不同层级用户质量达标 | ✅ 大型团队推荐 |

**典型案例验证**：
- GitHub Copilot：每个token优化都经过A/B实验验证，"小胜累积而非大跃进"，任务成功率不下降
- Himanshu 7天优化：60%任务走Haiku（小模型），仅15%走Opus（大模型），质量差异可忽略但成本差10-60倍
- Zomato Zia：混合模型大小策略，不同组件用不同规模模型，CSAT提升2倍

## 实施检查清单

- [ ] 是否建立了≥200条的黄金测试集？
- [ ] 是否定义了明确的质量护栏指标（ARR、幻觉率、CSAT）？
- [ ] 是否已做梯度实验并绘制"压缩率-质量"曲线？
- [ ] 是否实现了三级模型路由，按任务复杂度分配？
- [ ] 压缩率是否控制在60%以内（非低价值场景）？
- [ ] 是否有自动降级/升级机制（置信度低时升级模型）？
- [ ] A/B测试是否用户级分流、灰度发布、跑满7天？
- [ ] 是否有实时质量监控和告警？

## 反例警示

| 错误做法 | 后果 |
|---------|------|
| 一刀切策略：所有场景/所有用户用同样模型同样压缩率 | 要么浪费要么质量差 |
| 只看成本不看质量：为省token无底线压缩 | 质量断崖式下跌用户流失 |
| 不做A/B测试全量上线：没有对照组 | 无法判断质量变化，出问题回滚慢 |
| 一劳永逸思维：上线后不持续监控 | 模型更新/业务变化后最优解改变但配置不更新 |
| 分流粒度错误：请求级分流 | 同一用户看到不同效果，体验不一致 |
| 高风险场景高压缩（医疗/法律/金融） | 可能造成严重后果 |

## 迁移验证（跨领域可复用性）

质量-成本平衡本质是"约束优化"问题，在多个工程领域有完全同构的模式：

1. **音视频码率自适应（ABR）领域**：建立质量阈值（VMAF>90）→ 梯度实验（码率-质量曲线）→ 动态码率分级（根据网络切换1080p/720p/480p），Netflix/YouTube的ABR算法完全是这个模式
2. **网络QoS流量控制领域**：定义SLA（语音<150ms）→ 测量负载-延迟曲线→ 流量分类标记（DSCP），高优先级保障带宽
3. **图片/视频压缩质量调节领域**：定义质量阈值（SSIM>0.9）→ Q值-质量曲线→ 按场景选压缩级别（缩略图高压缩，原图低压缩）
