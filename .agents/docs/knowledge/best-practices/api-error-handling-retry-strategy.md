# API 错误处理与重试策略

> 通用 API 集成的错误处理与重试规范：先约定标准响应结构，再按 HTTP 状态码与应用错误码分级处理，最后对可重试错误采用分层退避策略。来源为 ListenHub 系列 skill 的共享实现。

**沉淀来源**：`chaos/flexloop/.agents/skills/shared/common-patterns.md`

---

## 一、标准响应结构契约

所有 API 响应遵循以下格式：

```json
{
  "code": 0,
  "message": "",
  "data": { ... }
}
```

- `code: 0` = 成功
- 非零 `code` = 错误（见下方应用错误码表）
- 调用方应先检查 `code`，再检查 HTTP 状态码，两者配合判断

---

## 二、HTTP 状态码处理表

| 状态码 | 含义 | 处理动作 |
|--------|------|----------|
| 200 | 成功 | 解析响应体 |
| 400 | 请求参数错误 | 检查参数 |
| 401 | API Key 无效 | 重新检查 `LISTENHUB_API_KEY` |
| 402 | 余额不足 | 告知用户充值 |
| 403 | 禁止访问 | 无该资源权限 |
| 429 | 触发限流 | 指数退避，延迟后重试 |
| 500/502/503/504 | 服务端错误 | 最多重试 3 次 |

---

## 三、应用错误码表

部分错误通过响应体中的 `code` 字段体现（非 HTTP 层）：

| 错误码 | 含义 |
|--------|------|
| 21007 | 用户 API Key 无效 |
| 25429 | 应用层限流 |

**注意**：应用错误码与 HTTP 状态码是两套体系，需同时检查。例如 25429 属应用层限流，与 HTTP 429 同样需要退避处理。

---

## 四、重试策略

采用分层重试，不同错误类型使用不同间隔与次数：

| 错误类型 | 重试策略 |
|----------|----------|
| **429 限流** | 等待 15 秒后重试（指数退避） |
| **5xx 服务端错误** | 最多重试 3 次，间隔 5 秒 |
| **网络错误** | 最多重试 3 次 |

**实现要点：**

- 指数退避适用于 429：首次等待 15s，之后可随重试次数递增等待时长。
- 5xx 重试 3 次、每次间隔 5s，避免对不可恢复的服务端故障无限重试。
- 网络错误（连接失败、超时等）同样重试 3 次。
- 重试需保证幂等——GET 查询天然幂等；POST 提交类请求需确认服务端有去重/幂等机制，避免重复创建资源。
