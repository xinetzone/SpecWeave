# 模型微调与蒸馏

模型层面的优化通过改变模型本身或推理方式来降低单次推理成本，这类技术通常需要模型训练或专用推理框架支持，但能带来根本性的效率提升，适合大规模部署场景。

## 技术清单

### 1. LoRA/QLoRA参数高效微调（Parameter-Efficient Fine-Tuning）

**原理说明**：全参数微调需要更新模型所有参数（如70B模型有700亿参数），成本极高。LoRA（Low-Rank Adaptation）冻结预训练模型权重，在Transformer注意力层插入可训练的低秩矩阵A和B（秩r通常为4-32），仅训练这两个小矩阵（参数量约为原模型的0.1%）。训练完成后可将BA合并到原权重中，推理时无额外开销。QLoRA在此基础上对基础模型进行4-bit量化（NF4格式），进一步将显存需求降低50%以上，使得消费级GPU（如24GB显存的3090/4090）也能微调大模型。微调后的模型在特定任务上指令遵循能力更强，可以使用更短的提示词达到相同效果，间接节省token。

**本质路径映射**：减少（小模型替代效应）+ 复用（基础模型能力复用）

**适用场景**：领域适配（如医疗、法律、代码领域）；特定任务优化（分类、提取、格式转换）；指令遵循能力提升；需要缩短提示词的场景；有领域标注数据的场景。

**实施难度**：中-高。需要准备领域数据集、选择合适的秩r和目标模块、调优训练超参数，但Hugging Face PEFT库已大幅降低实施门槛。

**预期效果范围**：训练成本降低90%+（相比全参数微调），特定任务提示词可缩短30-60%，任务准确率提升5-15%。

**优点**：
- 训练成本极低（单卡即可完成7B模型微调）
- 推理无额外开销（可合并权重）
- 一个基础模型可挂载多个LoRA适配器（多任务）
- 效果接近全参数微调（差距<1-2%）

**缺点**：
- 需要领域标注数据（通常100-1000条高质量数据）
- 超参数调优（r、alpha、目标模块）需要经验
- 通用能力可能略有下降（灾难性遗忘）
- 数据质量决定微调效果上限

**注意事项**：
- 目标模块优先选择q_proj和v_proj（注意力层查询和值投影）
- 秩r并非越大越好，8-32通常是最优区间
- QLoRA训练时注意冻结层的归一化统计量
- 保留部分通用数据缓解灾难性遗忘
- 必须在验证集上评估，避免过拟合

### 2. 知识蒸馏（Knowledge Distillation）

**原理说明**：知识蒸馏将大模型（教师模型）的"暗知识"（Dark Knowledge）迁移到小模型（学生模型）中。不仅学习教师模型的最终输出（硬标签），更学习教师模型输出的概率分布（软标签）——软标签包含了类别间的相似性信息（如"猫"和"狗"的概率都很高说明它们相似）。任务特定蒸馏进一步优化：使用教师模型生成大量领域数据，然后在这些数据上训练小模型。蒸馏后的小模型在特定任务上可达到大模型90%+的性能，但推理成本仅为大模型的1/10-1/100。

**本质路径映射**：减少（小模型直接降低计算量）

**适用场景**：高并发在线服务；特定任务规模化部署；边缘设备部署；对延迟敏感的场景；成本敏感的大规模应用。

**实施难度**：高。需要设计蒸馏策略、准备蒸馏数据、训练学生模型、进行精度对齐。

**预期效果范围**：推理成本降低70-95%（模型参数缩小10-100倍），特定任务性能保留85-95%。

**优点**：
- 小模型推理速度快、成本低、延迟低
- 软标签比硬标签携带更多信息
- 蒸馏后的模型可独立部署，无需教师模型
- 可结合量化进一步提升效率

**缺点**：
- 蒸馏训练成本高（需要大量教师模型推理）
- 通用能力通常不如教师模型
- 蒸馏过程复杂，需要精心设计损失函数
- 学生模型架构选择影响最终效果

**注意事项**：
- 温度系数（Temperature）调节软标签平滑度，通常取2-5
- 同时使用软标签损失和硬标签损失（加权组合）
- 任务特定蒸馏效果优于通用蒸馏
- 先在大模型上验证任务可行，再蒸馏到小模型
- 蒸馏数据的多样性决定学生模型泛化能力

### 3. 小模型路由（Model Routing / Cascade）

**原理说明**：不是所有请求都需要最强的大模型。模型级联（Model Cascade）架构设置路由分类器，先尝试用最小、最快、最便宜的模型处理请求，只有当小模型置信度低（或输出质量不达标）时，才升级到更大的模型。成本分级策略根据任务复杂度路由：简单问候/格式化任务用小模型（如GPT-3.5-turbo、Llama-3-8B），复杂推理/创作任务用大模型（如GPT-4o、Claude-3.5-Sonnet）。路由逻辑可基于规则（关键词分类）或训练专门的路由分类器模型。

**本质路径映射**：减少（简单请求用小模型）

**适用场景**：多任务混合系统；用户请求复杂度差异大的场景；高并发客服系统；分级服务场景。

**实施难度**：中。需要设计路由策略、评估小模型能力边界、实现级联回退逻辑。

**预期效果范围**：整体推理成本降低30-60%，复杂任务质量影响<5%。

**优点**：
- 无需模型训练，仅需架构设计
- 成本节省立竿见影
- 保持大模型处理复杂任务的能力
- 可动态调整路由策略

**缺点**：
- 路由错误会影响用户体验（小模型处理不了复杂问题）
- 增加系统复杂度（多模型管理）
- 需要持续评估路由准确率
- 延迟可能增加（小模型失败后再调用大模型）

**注意事项**：
- 保守路由：不确定时升级到大模型，避免质量下降
- 异步路由：小模型处理时同时流式输出，大模型做兜底校正
- 建立小模型能力边界评估集
- 记录路由决策日志，持续优化路由规则
- 对关键业务请求直接走大模型

### 4. 推测解码（Speculative Decoding）

**原理说明**：LLM解码是内存带宽受限的过程——每次生成一个token都需要从显存读取整个模型权重。推测解码利用这一特性：用一个快速的小模型（草稿模型）一次性推测生成K个候选token（如4-8个），然后用大模型（目标模型）一次性并行验证这K个token。验证通过的token直接接受，第一个不匹配的token位置重新采样，后续token丢弃。由于并行验证K个token的成本与生成1个token相当（主要是内存读取成本），当草稿模型准确率足够高时，可实现2-3倍的解码加速，且输出与纯大模型生成完全一致（无质量损失）。Medusa等方案通过在大模型上添加多个预测头实现自推测，无需额外草稿模型。

**本质路径映射**：复用（并行验证替代串行生成）

**适用场景**：自回归生成场景；对延迟敏感的在线服务；长文本生成；高并发推理服务；使用vLLM/TGI等推理框架的场景。

**实施难度**：中。需要支持推测解码的推理框架（vLLM已原生支持），选择或训练匹配的草稿模型。

**预期效果范围**：解码速度提升1.5-3倍（无质量损失），接受率通常为60-80%。

**优点**：
- 理论上无损加速（输出分布与原模型完全一致）
- 无需重新训练大模型
- 长输出场景加速效果明显
- vLLM等框架已原生支持

**缺点**：
- 需要额外的草稿模型（或Medusa头）
- 草稿模型质量直接影响加速比
- 短生成场景收益有限
- 增加显存占用（同时加载两个模型）

**注意事项**：
- 草稿模型应与目标模型同架构、同词表
- 草稿模型规模通常为目标模型的1/10-1/5
- K值（推测长度）并非越大越好，4-8通常最优
- Medusa方案需要微调预测头，适合自有模型
- 批处理场景下加速比可能下降

### 5. 量化（Quantization）

**原理说明**：量化通过降低模型权重和激活值的数值精度来减少内存占用和计算量。常见精度包括：FP32（32位浮点，训练用）、FP16/BF16（16位浮点，推理标准）、INT8（8位整型）、INT4（4位整型，如AWQ、GPTQ、NF4）。4-bit量化可将模型体积缩小75%，同时显著提升推理吞吐量——因为内存带宽是推理瓶颈，更小的模型意味着每次权重读取更快。现代量化技术（AWQ、GPTQ）通过校准数据集保护关键权重，4-bit量化下质量损失通常<2%。FP8是最新的平衡点，在NVIDIA H100等新GPU上有原生硬件加速，兼顾速度和精度。

**本质路径映射**：压缩（权重量化降低内存带宽需求）

**适用场景**：模型部署；GPU显存受限场景；高吞吐量推理服务；边缘部署；所有生产部署场景。

**实施难度**：低-中。vLLM、llama.cpp等框架支持一键量化，AWQ/GPTQ有现成工具链。

**预期效果范围**：模型体积减少50%（INT8）-75%（INT4），吞吐量提升2-4倍，质量损失<5%（校准良好时<2%）。

**优点**：
- 实现简单，成熟工具链支持
- 推理速度和显存收益立竿见影
- 可与其他技术（LoRA、推测解码）叠加
- 无需重新训练模型（PTQ后训练量化）

**缺点**：
- 极端量化（如2-bit、3-bit）质量损失明显
- 量化校准需要少量代表性数据
- 某些量化格式对硬件有要求
- 激活值量化比权重量化更困难

**注意事项**：
- 优先选择AWQ或GPTQ进行4-bit量化（优于RTN）
- 量化校准数据应与实际推理数据分布一致
- BF16是训练和推理的安全默认选择
- FP8在H100及更新GPU上优先考虑
- 量化后必须在任务验证集上评估质量

### 6. 结构化剪枝（Structured Pruning）

**原理说明**：剪枝移除模型中"不重要"的参数或结构。非结构化剪枝移除单个权重（生成稀疏矩阵），但难以在通用硬件上获得实际加速；结构化剪枝移除整个注意力头、MLP层通道、甚至整个Transformer层，直接减小模型规模，在标准硬件上即可获得速度提升。剪枝标准通常基于权重幅值、Hessian信息（二阶导数衡量参数重要性）、或激活值统计。剪枝后通常需要少量微调（稀疏微调）恢复精度。结构化剪枝可将模型参数减少30-50%，同时保持大部分性能。

**本质路径映射**：减少（直接移除冗余参数）

**适用场景**：模型压缩部署；边缘设备部署；极致成本优化场景；有微调能力的团队。

**实施难度**：高。需要选择剪枝策略、执行剪枝、进行稀疏微调，流程复杂且容易出错。

**预期效果范围**：模型参数减少30-50%，推理速度提升30-80%，质量损失3-8%（微调后可恢复部分）。

**优点**：
- 直接减少模型计算量
- 结构化剪枝无需特殊硬件支持
- 可与量化结合进一步压缩
- 可针对特定任务优化剪枝策略

**缺点**：
- 剪枝流程复杂，技术门槛高
- 非结构化剪枝实际加速有限
- 剪枝后微调需要数据和计算资源
- 过度剪枝导致质量显著下降

**注意事项**：
- 结构化剪枝优先于非结构化剪枝
- 逐层剪枝而非一次性全局剪枝
- 剪枝后必须进行微调恢复精度
- 使用Hessian信息（如OBS方法）比幅值剪枝更准确
- 优先剪枝冗余的注意力头（多数模型有20-30%可剪枝）

### 7. 多LoRA服务（Multi-LoRA Serving）

**原理说明**：当需要为多个任务/客户部署微调模型时，传统方式是为每个LoRA部署一个独立的模型实例，GPU利用率极低。多LoRA服务技术（如vLLM的Multi-LoRA、S-LoRA）在GPU上只加载一份基础模型权重，通过动态切换LoRA适配器来处理不同任务的请求。基础模型权重在所有LoRA请求间共享，仅需维护小体积的LoRA权重（每个几十MB），GPU显存利用率提升一个数量级，可同时服务数百个不同的微调任务。

**本质路径映射**：复用（基础模型权重共享）

**适用场景**：多租户SaaS服务；多任务系统；为多个客户提供定制模型服务；LoRA适配器数量多的场景。

**实施难度**：中。需要支持多LoRA的推理框架（vLLM、Text Generation Inference）。

**预期效果范围**：GPU利用率提升5-20倍（相比独立部署），服务密度数量级提升，单LoRA额外开销<5%。

**优点**：
- 极大提升GPU资源利用率
- 支持动态加载/卸载LoRA适配器
- 基础模型更新可惠及所有LoRA
- 部署和运维成本大幅降低

**缺点**：
- 批处理调度更复杂
- 不同LoRA的请求混合批处理可能引入延迟抖动
- 对推理框架要求高
- LoRA适配器过多时切换开销增加

**注意事项**：
- 所有LoRA必须基于同一基础模型
- 设置LoRA适配器缓存池，热数据常驻显存
- 批处理时注意LoRA ID的路由正确性
- 监控不同LoRA的流量分布，调整批处理策略
- 使用LoRA权重合并技术减少运行时开销

## G2质量门：核心洞察四元组

**现象**：模型层面优化存在明显的"采纳分层"——量化被几乎所有生产系统采用（采纳率>80%），LoRA微调在有数据团队中广泛使用，而知识蒸馏、结构化剪枝的实际生产采纳率不足20%。推测解码在主流推理框架（vLLM）支持下正在快速普及，但小模型路由的架构设计多数团队仍停留在"规则分流"的初级阶段。

**根因**：模型优化的采纳门槛与技术复杂度成正比。量化几乎"开箱即用"且收益明确；LoRA有成熟工具链（PEFT）且训练成本可承受；但蒸馏和剪枝需要完整的ML工程能力（数据、训练、评估、部署全流程），且失败成本高（训练几周的模型可能不达标）。更深层的原因是：多数团队缺乏"模型效率"作为一等公民的工程文化——优化只在成本告警时才被动进行，而非架构设计阶段主动考虑。

**影响**：模型层面优化是规模化部署的必经之路。单纯依靠提示词和上下文优化能将成本降低30-50%，但要实现80%+的成本降低以支撑大规模商业化，必须结合模型优化。只做应用层优化不做模型优化的系统，在业务规模增长到一定程度后必然遭遇成本墙。反过来，只做模型优化不做应用层优化也是低效的——应用层优化ROI更高，应该优先实施。

**建议**：按照"投入产出比由高到低"的顺序分层实施模型优化：（1）第一优先级：量化（BF16/FP16 → AWQ 4-bit），几乎零成本获得2-4倍吞吐量；（2）第二优先级：多LoRA服务，如需要微调多个任务，使用vLLM的Multi-LoRA而非独立部署；（3）第三优先级：推测解码，启用vLLM的speculative decoding配置获得1.5-3倍延迟降低；（4）第四优先级：小模型路由，建立分类器将简单请求分流到小模型；（5）第五优先级：LoRA微调，有数据时对核心任务微调以缩短提示词；（6）最后才考虑蒸馏和剪枝，这两项需要专门ML团队投入。模型优化必须建立量化基准：每次优化前后对比吞吐量、延迟、质量三个指标，避免"为优化而优化"。
