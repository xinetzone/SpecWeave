# Token优化可复用最佳实践模式

> 本文档萃取5个经过多案例验证的可复用模式，每个模式包含触发场景、核心问题、解决方案、本质路径映射、效果数据、反模式、G3迁移验证。

## 模式索引

| 模式ID | 模式名称 | 本质路径 | 适用场景 | 迁移验证领域 |
|--------|---------|---------|---------|-------------|
| P-001 | 渐进式优化模式 | 减少→复用→压缩分层递进 | 所有场景（通用） | CPU缓存优化、数据库查询优化、网络传输优化 |
| P-002 | 分层缓存模式 | 复用（多层级缓存架构） | 客服/对话/代码助手 | CPU L1/L2/L3缓存、CDN分层缓存、数据库多级缓存 |

## 模式P-001：渐进式优化模式

### 模式名称与ID
**名称**：渐进式优化模式（Progressive Optimization Pattern）
**ID**：P-001
**抽象层级**：L2（方法论级）

### 触发场景（什么时候用）
- 新系统刚上线，需要快速降本但又不能影响业务
- 已有系统成本过高，但不知道从哪开始优化
- 团队资源有限，需要按ROI优先级逐步投入
- 优化过程需要持续验证质量，不能一步到位大改
- 月API费用从几百到几万美金的各种规模团队

### 核心问题（解决什么问题）
面对数十种token优化技术，团队容易陷入两个极端：要么什么都不做（觉得优化太复杂），要么一开始就上最复杂的方案（微调、蒸馏、自建RAG），结果投入大量资源却收效甚微或引入质量问题。渐进式优化通过"先易后难、每步验证、小步快跑"的方式，确保每一步投入都有可衡量的收益。

### 解决方案（核心步骤，5步以内）

**步骤1：可观测性先行（0.5天）**
- 接入成本监控网关（Helicone/Langfuse/Portkey）
- 识别Top 5花费项：哪个函数/哪个接口/哪类用户花费最多
- 建立基线：当前平均token数、成本、质量指标

**步骤2：Quick Wins速赢（1-2周）**
- 所有接口设置max_tokens限制（根据场景设合理值）
- 重构prompt为"静态前缀+动态后缀"结构，启用Prompt Caching
- 精简系统提示词（去除冗余修饰、重复说明）
- 升级到现代推理引擎（vLLM）启用PagedAttention和连续批处理
- 这一步预期收益：成本降低50-70%

**步骤3：场景化质量优化（2-4周）**
- 根据场景选择对应技术：
  - 客服/FAQ → 添加语义缓存+意图分流
  - 代码助手 → 工具懒加载+动态上下文
  - RAG场景 → 检索替代全量注入+语义分块
  - Agent场景 → 自动上下文压缩+工具输出过滤
- 每添加一项技术，A/B测试验证质量不下降
- 这一步预期收益：在步骤2基础上再降本20-40%

**步骤4：高级规模化优化（1-3月）**
- 当Quick Wins和场景化优化完成后，再考虑：
  - 三级模型路由（简单→小模型，复杂→大模型）
  - LoRA微调核心任务（缩短提示+提升效果）
  - 会话状态机/工作流（任务型Agent场景）
- 只有当月调用量>100万token或ROI>3时才投入
- 这一步预期收益：在步骤3基础上再降本30-50%

**步骤5：持续监控迭代（长期）**
- 建立成本看板，监控每日token消耗趋势
- 定期审计（每月）：识别新的浪费点
- 根据业务变化调整优化策略

### 本质路径映射
```
减少（步骤2：精简提示词、max_tokens）
  ↓
复用（步骤2：缓存、步骤3：场景缓存、步骤4：路由复用小模型）
  ↓
压缩（步骤3：上下文压缩、步骤4：状态机/微调）
```
按"减少→复用→压缩"三大本质路径的ROI顺序递进：先做投入最小收益最大的"减少"，再做"复用"，最后才做"压缩"和高级方案。

### 效果数据（基于前面案例的量化预期）

| 阶段 | 累计成本降低 | 所需时间 | 质量影响 | 案例验证 |
|------|-------------|---------|---------|---------|
| 基线 | 0% | - | - | - |
| 步骤2完成 | 50-70% | 1-2周 | 无损失或轻微提升 | 所有9个案例均验证 |
| 步骤3完成 | 70-85% | 2-4周 | 质量保持90%+，部分场景提升 | Kapden(76%)、Himanshu(87%)、Copilot |
| 步骤4完成 | 85-95% | 1-3月 | 质量保持或提升 | 批处理场景(95%)、蒸馏场景(90%+) |

**典型案例验证**：
- Himanshu 7天优化：严格按此模式Day1审计→Day2-3缓存→Day4路由→Day5压缩→Day6重试，7天成本降低87%（$4800→$620）
- GitHub Copilot：官方博客明确提到"token效率提升通常不是一个大改动，而是持续的小改进流"

### 反模式（什么情况下不要用、常见错误）
- ❌ **反模式1：一步到位思维**：一开始就上微调/蒸馏/自建RAG，投入3个月结果不如Quick Win一周的收益
- ❌ **反模式2：跳过可观测性**：不接监控就开始优化，不知道钱花在哪，优化了也无法衡量效果
- ❌ **反模式3：质量不验证**：每一步优化不做A/B测试，质量下降了还不知道，直到用户投诉
- ❌ **反模式4：做完就不管**：优化上线后不持续监控，"优化反弹"——省的钱悄悄涨回来

### G3迁移验证（还能用在哪些其他场景）

本模式本质是"按ROI分层递进优化"，这是通用系统优化方法论，可迁移到：

1. **CPU缓存优化领域**：
   - 步骤1：性能profiling找到热点函数（对应可观测性）
   - 步骤2：算法优化/循环展开等简单优化（对应Quick Wins）
   - 步骤3：数据结构优化/缓存对齐（对应场景化优化）
   - 步骤4：多线程/向量化/SIMD等高级优化（对应高级优化）
   - 步骤5：持续性能监控

2. **数据库查询优化领域**：
   - 步骤1：慢查询日志分析（对应可观测性）
   - 步骤2：添加索引/避免SELECT *（对应Quick Wins）
   - 步骤3：查询重写/分库分表（对应场景化优化）
   - 步骤4：读写分离/缓存层（对应高级优化）
   - 步骤5：持续慢查询监控

3. **网络传输优化领域**：
   - 步骤1：网络抓包/带宽监控（对应可观测性）
   - 步骤2：启用gzip压缩/连接复用（对应Quick Wins）
   - 步骤3：CDN缓存/资源合并（对应场景化优化）
   - 步骤4：HTTP/2/QUIC协议升级（对应高级优化）
   - 步骤5：持续性能监控

## 模式P-002：分层缓存模式

### 模式名称与ID
**名称**：分层缓存模式（Layered Caching Pattern）
**ID**：P-002
**抽象层级**：L2（方法论级）

### 触发场景（什么时候用）
- 多轮对话系统（智能客服、聊天机器人）
- 代码助手（系统提示、工具定义重复发送）
- Agent框架（工具schema、系统提示每轮重复）
- 任何有大量重复前缀/重复内容的场景
- 请求之间存在可复用内容的场景

### 核心问题（解决什么问题）
LLM推理中，系统提示词、工具定义、few-shot示例、历史对话等内容在每轮请求中重复发送，这些重复内容每轮都要重新计算prefill（O(n²)复杂度），成本高且延迟大。单一缓存层要么命中率低，要么内存开销大。分层缓存通过不同层级、不同粒度、不同生命周期的缓存组合，最大化复用率。

### 解决方案（核心步骤）

**架构：三层缓存架构**

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 3: 语义相似层（Semantic Layer）                       │
│  生命周期：天-周，粒度：完整请求/响应，匹配：语义相似度       │
│  存储：向量数据库+Redis，命中率：20-40%，命中收益：100%节省  │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: 会话记忆层（Session Layer）                       │
│  生命周期：会话内，粒度：对话历史摘要/实体状态，匹配：同会话  │
│  存储：会话存储+KV缓存，命中率：50-80%，命中收益：80-90%节省│
├─────────────────────────────────────────────────────────────┤
│  Layer 1: 系统提示层（Prefix Layer）                        │
│  生命周期：跨会话全局，粒度：系统提示/工具定义/静态示例       │
│  匹配：精确前缀匹配，存储：推理引擎APC/Prompt Caching        │
│  命中率：70-95%，命中收益：90%成本+50-80%TTFT降低          │
└─────────────────────────────────────────────────────────────┘
```

**步骤1：Layer 1 - 系统提示层（必做）**
- 将prompt重构为：`[静态前缀] + [动态后缀]`结构
- 静态前缀包括：系统提示、工具定义schema、few-shot示例、安全规则
- 动态后缀包括：用户当前输入、动态上下文、实时数据
- 静态前缀放在最前面，利用Prompt Caching/APC自动缓存
- 关键约束：静态前缀一旦确定不要随意修改，修改会导致缓存失效
- 缓存切换必须在自然边界（新会话、/compact后）

**步骤2：Layer 2 - 会话记忆层（对话/Agent场景必做）**
- 不把完整对话历史每轮都发送
- 采用分层记忆架构：
  - 即时层：最近N轮（3-5轮）原文保留
  - 工作记忆层：提取的实体/状态/关键信息结构化存储
  - 长期记忆层：更早的历史用摘要表示
- 同一session内的KV缓存自动复用（引擎层自动处理）
- 阈值触发自动压缩：token使用达到窗口70-80%时自动摘要

**步骤3：Layer 3 - 语义相似层（高重复场景推荐）**
- 对用户输入做embedding
- 在语义缓存中查找相似度>阈值（如0.95）的历史请求
- 命中则直接返回缓存的响应（或经过简单校验后返回）
- 客服/FAQ场景这一层命中率可达42%+（Kapden案例）
- 需要设置严格的相似度阈值和过期策略，避免错误回答复用

### 本质路径映射
- **核心路径：复用（Reuse）**——所有层都是避免重复计算
- Layer 1：精确前缀复用（O(n²) prefill → O(1) 缓存读取）
- Layer 2：会话内KV复用（历史轮次从输入→缓存，成本1/10）
- Layer 3：语义结果复用（完整请求从计算→直接返回，成本0）

### 效果数据（基于前面案例的量化预期）

| 缓存层 | 典型命中率 | 命中收益 | 实施难度 |
|--------|-----------|---------|---------|
| Layer 1 系统提示层 | 70-95% | 前缀部分成本-90%，TTFT-50-80% | 极低（重构prompt即可） |
| Layer 2 会话记忆层 | 50-80% | 历史部分成本-90%，长会话token-60-80% | 中（需要摘要/实体提取） |
| Layer 3 语义相似层 | 20-42% | 命中请求成本-100%，整体-20-40% | 中（需要向量数据库） |
| **三层组合** | **综合收益** | **整体成本降低60-85%，TTFT降低50-80%** | |

**典型案例验证**：
- GitHub Copilot：扩展提示缓存是"最大单一杠杆"，正确结构化prompt即可获得90%折扣
- Kapden客服：语义缓存命中率42%是成本降低的关键杠杆（月费$92K→$22K）
- Himanshu 7天优化：提示缓存是Day2-3的核心动作，单这一项即带来显著收益

### 反模式（什么情况下不要用、常见错误）
- ❌ **反模式1：缓存内容放错位置**：动态内容放静态前缀前面，导致每次前缀变化缓存无法命中
- ❌ **反模式2：模型切换破坏缓存**：在对话中间切换模型，导致KV缓存全部失效
- ❌ **反模式3：语义缓存阈值过低**：为了提高命中率调低相似度阈值，导致错误回答复用引发事故
- ❌ **反模式4：忽略缓存预热**：冷启动阶段缓存命中率0，没有预热策略导致高峰期性能差
- ❌ **反模式5：缓存不设过期**：知识库/工具定义更新后缓存不失效，返回过时信息

### G3迁移验证（还能用在哪些其他场景）

分层缓存是计算机科学中经典的架构模式，本模式是其在LLM领域的具体化，可迁移到：

1. **CPU L1/L2/L3缓存架构**：
   - Layer 1对应L1缓存：核心本地、速度最快、容量最小、命中率最高（指令/数据缓存）
   - Layer 2对应L2缓存： per-core、速度中等、容量中等（核心共享）
   - Layer 3对应L3缓存：跨核共享、速度较慢、容量最大（对应语义层跨请求）
   - 原理完全一致：越上层速度越快容量越小命中率越高，越下层反之

2. **CDN分层缓存架构**：
   - Layer 1对应浏览器本地缓存：静态资源本地缓存，命中最快
   - Layer 2对应CDN边缘节点：区域边缘缓存，命中率高，延迟低
   - Layer 3对应源站/中心缓存：回源前的最后一层，跨区域共享
   - 缓存失效策略、TTL设置、命中率计算逻辑完全通用

3. **数据库多级缓存架构**：
   - Layer 1对应应用本地缓存（Caffeine/Guava）：进程内，最快
   - Layer 2对应分布式缓存（Redis）：跨实例共享，中等速度
   - Layer 3对应数据库本身缓存（Buffer Pool）：数据库层缓存
   - 缓存穿透/击穿/雪崩问题和解决方案完全通用

## 模式P-003：质量-成本动态平衡模式

### 模式名称与ID
**名称**：质量-成本动态平衡模式（Quality-Cost Dynamic Balance Pattern）
**ID**：P-003
**抽象层级**：L2（方法论级）

### 触发场景（什么时候用）
- 优化过程中需要平衡token成本和输出质量
- 不同用户/场景对质量要求不同（VIP用户vs免费用户）
- 不同任务复杂度需要不同压缩率
- 需要上线优化但又担心质量下降
- A/B测试框架完善、需要数据驱动决策的团队

### 核心问题（解决什么问题）
token优化本质是在"成本-质量-延迟"三维空间中找帕累托最优点，但实际中常见两个极端：要么不做任何优化（成本过高），要么"一刀切"用同样的压缩率/同样的模型（简单任务用大模型浪费，复杂任务用小模型质量差）。质量-成本动态平衡通过A/B测试+阈值调优+自适应路由，实现"在满足质量约束的前提下最小化成本"。

### 解决方案（核心步骤）

**步骤1：建立质量基线和护栏**
- 建立"黄金测试集"（≥200条，覆盖典型场景和边缘case）
- 定义质量护栏指标（不可接受的底线）：
  - 任务准确率保持率ARR > 95%（通用场景）或 > 99%（高风险场景）
  - 幻觉率增幅 < 3%（绝对值）
  - 用户满意度CSAT不下降（统计显著）
- 建立全上下文无优化基线，作为对比基准

**步骤2：梯度实验绘制权衡曲线**
- 选择3-5个压缩率/模型级别梯度点（如0%、25%、50%、75%压缩，或小/中/大模型）
- 在相同测试集上运行每个梯度
- 测量每个点的：token减少率、质量保持率、延迟变化
- 绘制"压缩率-质量"曲线，找到"甜点区"（帕累托前沿）
  - 0-30%压缩：免费午餐区，质量几乎不损失，应该做
  - 30-60%压缩：权衡区，质量缓慢下降，按需选择
  - >60%压缩：悬崖区，质量断崖下跌，避免进入

**步骤3：建立三级路由/阈值体系**
- **任务复杂度分级**：
  - Tier 1（简单任务）：分类、提取、是/否判断、格式化 → 小模型 + 高压缩率
  - Tier 2（中等任务）：摘要、内容生成、常规问答 → 中等模型 + 中压缩率
  - Tier 3（复杂任务）：复杂推理、代码生成、歧义问题 → 大模型 + 低压缩/不压缩
- **用户分级**（可选）：
  - 免费用户：可以接受稍高质量损失，成本优先
  - 付费用户：平衡质量和成本
  - VIP/企业用户：质量优先，可接受更高成本
- **自动降级机制**：质量低于阈值时自动升级模型/降低压缩率

**步骤4：A/B测试验证上线**
- 流量分组：对照组（基线）50%，实验组（优化方案）50%
- 用户级分流（同一用户始终在同一组，避免体验不一致）
- 灰度发布：1% → 5% → 20% → 50% → 100%
- 每个阶段至少跑24小时，完整周度周期（7天）
- 同时监控：主要指标（成本）+ 护栏指标（质量/错误率/满意度）

**步骤5：持续监控和动态调优**
- 实时监控成本和质量指标看板
- 设置质量告警：质量低于阈值自动告警/回滚
- 定期重新跑梯度实验（模型更新、场景变化后最优可能改变）
- 建立"优化反弹"监控：成本悄悄涨回时及时发现

### 本质路径映射
- **减少（Reduce）**：通过模型路由，简单任务用小模型减少计算
- **压缩（Compress）**：通过自适应压缩率，不同任务不同压缩程度
- **核心是"动态"**：不是静态配置，而是根据任务/用户/质量反馈实时调节
- 数学形式化：min C s.t. Q ≥ Q_min, L ≤ L_max（在质量和延迟约束下最小化成本）

### 效果数据（基于前面案例的量化预期）

| 策略 | 成本降低 | 质量影响 | 典型场景 |
|------|---------|---------|---------|
| 静态小模型（一刀切） | 60-80% | 复杂任务质量下降10-30% | 不推荐 |
| 三级模型路由 | 40-60% | 质量保持率>97% | 所有场景推荐 |
| 三级路由+自适应压缩 | 60-75% | 质量保持率>95% | 成熟团队推荐 |
| 三级路由+用户分级+动态调优 | 70-85% | 不同层级用户质量达标 | 大型团队推荐 |

**典型案例验证**：
- GitHub Copilot：每个token优化都经过A/B实验验证，"小胜累积而非大跃进"，任务成功率不下降
- Himanshu 7天优化：60%任务走Haiku（小模型），仅15%走Opus（大模型），质量差异可忽略但成本差10-60倍
- Zomato Zia：混合模型大小策略，不同组件用不同规模模型，CSAT提升2倍

### 反模式（什么情况下不要用、常见错误）
- ❌ **反模式1：一刀切策略**：所有场景/所有用户用同样模型同样压缩率，要么浪费要么质量差
- ❌ **反模式2：只看成本不看质量**：为了省token无底线压缩，质量断崖式下跌用户流失
- ❌ **反模式3：不做A/B测试全量上线**：没有对照组无法判断质量变化，出问题回滚慢
- ❌ **反模式4：一劳永逸思维**：上线后不持续监控，模型更新/业务变化后最优解改变但配置不更新
- ❌ **反模式5：分流粒度错误**：请求级分流导致同一用户看到不同效果，体验不一致

### G3迁移验证（还能用在哪些其他场景）

质量-成本平衡本质是"约束优化"问题，在多个工程领域有完全同构的模式：

1. **音视频码率自适应（ABR）领域**：
   - 对应步骤1：建立质量阈值（如VMAF>90为可接受）
   - 对应步骤2：梯度实验（不同码率对应的质量曲线）
   - 对应步骤3：动态码率分级（根据网络状况切换1080p/720p/480p）
   - 对应步骤4-5：实时监控带宽/缓冲，动态调整码率
   - Netflix/YouTube的ABR算法完全是这个模式

2. **网络QoS流量控制领域**：
   - 对应步骤1：定义不同业务SLA（语音<150ms延迟，视频可容忍更高）
   - 对应步骤2：测量不同负载下的延迟/丢包率曲线
   - 对应步骤3：流量分类标记（DSCP），高优先级流量保障带宽，低优先级流量在拥塞时丢弃
   - 对应步骤4-5：实时拥塞控制（TCP拥塞控制算法就是动态平衡）

3. **图片/视频压缩质量调节领域**：
   - 对应步骤1：定义可接受的质量阈值（如SSIM>0.9）
   - 对应步骤2：不同压缩质量因子（Q值）对应的质量-体积曲线
   - 对应步骤3：根据场景选择压缩级别（缩略图高压缩，原图低压缩）
   - WebP/JPEG的质量参数调节、CDN图片动态压缩都是这个模式

## 模式P-004：按需加载懒加载模式

### 模式名称与ID
**名称**：按需加载/懒加载模式（Lazy Loading / On-Demand Loading Pattern）
**ID**：P-004
**抽象层级**：L2（方法论级）

### 触发场景（什么时候用）
- 代码助手/IDE插件（MCP工具多，工具定义本身占大量token）
- Agent/智能体（多工具调用，不需要一开始加载所有工具）
- RAG系统（不需要一开始把所有文档都塞进上下文）
- 长上下文场景（大部分上下文信息当前步骤用不到）
- 任何"预加载了大量可能用不到的信息"的场景

### 核心问题（解决什么问题）
传统方式是"预加载所有可能需要的信息"：代码助手每轮发送所有MCP工具定义，Agent每轮加载所有工具schema，结果是工具定义就占55,000 tokens（MindStudio数据），大部分工具当前轮根本用不到。按需加载的核心是"初始只给元数据，真正需要时才加载完整内容"，从"预加载全量"转向"动态发现按需拉取"。

### 解决方案（核心步骤）

**步骤1：元数据与完整内容分离**
- 将资源分为两层：
  - **轻量元数据层**：名称、一句话描述、类型、ID——这部分初始加载
  - **完整内容层**：参数schema、详细说明、示例、代码——这部分按需加载
- 代码助手MCP示例：
  - 初始发送：工具名称+一句话描述（约100 token/工具）
  - 需要调用时：加载完整参数schema（约500-2000 token/工具）

**步骤2：渐进式披露架构**
- 三层渐进式加载：
  - Level 0（启动时加载）：核心元数据（名称、描述）
  - Level 1（相关时加载）：当前任务可能相关的资源详细信息
  - Level 2（需要时加载）：真正要调用/使用时才加载完整内容
- Cursor实践："少给前置细节，让Agent按需拉取相关上下文"

**步骤3：长输出文件化而非截断**
- 工具返回、命令输出、历史对话等长内容不要直接截断
- 写入临时文件，给Agent文件引用和读取能力
- Agent可以先看tail/head（末尾/开头），需要时再读取完整内容
- 这保留了完整信息可追溯，又不填满上下文窗口

**步骤4：动态上下文发现**
- 不预先决定哪些上下文相关
- 提供搜索/检索能力，让Agent根据当前任务主动拉取相关信息
- 代码助手场景：基于编辑文件、打开标签、轻量嵌入模型自动选择最相关文件

### 本质路径映射
- **核心路径：减少（Reduce）**——避免在上下文中加载当前用不到的token
- 不是压缩，而是"不加载"——根本就不把没用的token送进来
- 这比"加载了再压缩"更高效，因为从源头避免了O(n²)计算
- 对比：全量加载O(n) → 按需加载O(k)，k是实际需要的token，k << n

### 效果数据（基于前面案例的量化预期）

| 应用场景 | 全量加载token | 按需加载token | 节省比例 | 案例验证 |
|---------|--------------|--------------|---------|---------|
| MCP多工具场景（10+工具） | ~55,000 tokens | ~5,000-15,000 tokens | 46.9%+ | Cursor官方博客 |
| 长工具输出（10K tokens） | 10,000 tokens（截断丢失） | ~200 tokens（文件引用） | 98%+ | Cursor动态上下文 |
| 代码库上下文 | 全量文件加载 | 相关文件按需拉取 | 60-80% | GitHub Copilot |
| Postman技能加载 | 4,760 tokens（全量） | 1,930 tokens（渐进式） | 60% | Postman官方插件 |

**典型案例验证**：
- Cursor：MCP场景总Agent token降低46.9%，统计显著，"MCP数量越多节约越多"
- GitHub Copilot：工具搜索（Tool Search）模式，初始仅发送轻量元数据，参数schema在需要时才加载
- Postman Claude Code插件：渐进式披露，最大技能触发减轻60%（4,760→1,930 tokens）

### 反模式（什么情况下不要用、常见错误）
- ❌ **反模式1：需要时找不到**：按需加载机制设计不好，Agent不知道有这个工具/资源，该用的时候没加载
- ❌ **反模式2：加载太频繁**：每个小步骤都重新加载，来回加载的开销反而更大
- ❌ **反模式3：元数据不清晰**：元数据描述不清楚，Agent无法判断什么时候该加载什么
- ❌ **反模式4：文件化但不给读取能力**：把长内容写文件了，但Agent没有读取文件的工具/权限，等于白做
- ❌ **反模式5：简单场景过度设计**：工具少（<5个）、上下文短的场景，全量加载更简单，按需加载增加复杂度反而不值

### G3迁移验证（还能用在哪些其他场景）

懒加载/按需加载是计算机科学中经典设计模式，可迁移到：

1. **操作系统虚拟内存管理**：
   - 对应步骤1：虚拟地址空间（元数据）vs 物理页帧（完整内容）
   - 对应步骤2：按需分页（Demand Paging）——不预先把所有程序加载到内存，访问时才触发缺页中断加载
   - 对应步骤3-4：工作集模型，只保留当前需要的页面在内存，不常用的换出到磁盘
   - 这是虚拟内存的核心设计，和LLM上下文按需加载原理完全一致

2. **网页前端资源加载**：
   - 对应步骤1：路由配置/Manifest（元数据）vs 实际JS/CSS代码（完整内容）
   - 对应步骤2：代码分割（Code Splitting）+ 路由懒加载——访问对应路由才加载对应JS chunk
   - 对应步骤3：图片懒加载——初始只加载视口内图片，滚动到才加载其他
   - 对应步骤4：动态import()——真正需要时才加载模块
   - React/Vue的懒加载、Intersection Observer API都是这个模式

3. **微服务架构服务发现**：
   - 对应步骤1：服务注册中心的服务元数据（服务名、地址、接口列表）
   - 对应步骤2：客户端不预先连接所有服务，调用时才发现和建立连接
   - 对应步骤3-4：按需调用、熔断降级——不预先加载所有客户端stub
   - 微服务的按需发现、gRPC反射调用都是同模式应用

## 模式P-005：分层分治MapReduce模式

### 模式名称与ID
**名称**：分层分治MapReduce模式（Divide and Conquer MapReduce Pattern）
**ID**：P-005
**抽象层级**：L2（方法论级）

### 触发场景（什么时候用）
- 超长文档处理（法律合同100K+ tokens、代码库、书籍、研报）
- 批量内容处理（大量文档需要摘要/分析）
- 超过模型单次上下文窗口的任务
- "Lost in the Middle"问题明显的长上下文场景
- 不需要一次性理解全文的任务（检索问答、分点摘要）

### 核心问题（解决什么问题）
面对超长文档（100K+ tokens），即使模型支持大上下文窗口，也存在三个问题：(1) O(n²)复杂度导致成本是4K文档的25倍（n=100K是n=4K的25倍，计算量是625倍）；(2) "Lost in the Middle"导致中间部分注意力下降30%+；(3) TTFT首token延迟高（与上下文长度成正比）。分层分治通过"拆分→并行处理→递归归并"，将大问题拆解为小问题解决。

### 解决方案（核心步骤）

**步骤1：语义分块而非固定大小切割**
- 不要按固定token数切分（这会切断语义）
- 在自然语义边界拆分：段落、章节、标题、页面
- 结构化文档（Markdown/HTML/PDF）按原生结构拆分
- 分块大小建议：
  - 事实查询类：256-512 tokens，15%重叠
  - 分析摘要类：1024-2048 tokens 或 页级分块
- NVIDIA测试显示15%重叠比例是甜点，金融文档页级分块准确率最高（0.648）

**步骤2：Map阶段并行独立处理**
- 将每个chunk独立发送给LLM处理
- 根据任务类型处理每个chunk：
  - 摘要任务：每个chunk生成本地摘要
  - QA任务：每个chunk提取与问题相关的信息
  - 信息提取：每个chunk提取实体/关系/关键点
- Map阶段可以并行执行（chunk之间无依赖），大幅提升吞吐量
- 每个chunk的处理可以用小模型（因为任务简单明确）

**步骤3：Reduce阶段递归归并**
- 将Map阶段的输出（各chunk摘要/提取结果）收集起来
- 如果归并后仍超过token限制，递归执行Reduce：
  - 第1层Reduce：合并N个chunk摘要 → 章节级摘要
  - 第2层Reduce：合并章节摘要 → 文档级摘要
  - 建议递归深度≤2-3层，避免信息逐层丢失
- 保持层次结构（如ToM树状MapReduce），保留文档原生语义关系

**步骤4：按需检索分流（可选但推荐）**
- 不需要对整个文档摘要时，不要跑全量MapReduce
- 先用检索（RAG）找到与问题相关的chunks
- 只对相关chunks做处理，无关chunks直接跳过
- 事实查询类任务这一步可以减少80-90%工作量

### 本质路径映射
- **减少（Reduce）**：单个chunk从O(n)→O(k)，k是chunk大小，k << n
- **压缩（Compress）**：Map阶段每个chunk压缩为本地摘要，Reduce阶段归并为全局摘要
- **复用（Reuse）**：Map阶段并行处理复用计算资源，chunk更新只重处理变化部分
- 复杂度变化：全量处理O(n²) → MapReduce O(k·n/k)² = O(n²/k)，k越大收益越大
- 100K文档用2K chunk分块：计算量降低约50倍，成本降低70-85%

### 效果数据（基于前面案例的量化预期）

| 文档大小 | 全量处理成本 | MapReduce处理成本 | 成本降低 | 信息保留率 |
|---------|-------------|------------------|---------|-----------|
| 10K tokens | 基线（1x） | ~0.3x | ~70% | 95%+ |
| 50K tokens | 25x（相对4K） | ~4x | ~84% | 92%+ |
| 100K tokens | 100x（相对4K） | ~15x | ~85% | 90%+ |

**典型案例验证**：
- LLM×MapReduce框架：100K文档处理从100K+ tokens降到15K-30K tokens，70-85%降低
- ToM树状MapReduce（arXiv:2511.00489）：构建DocTree保持层次语义，比线性MapReduce质量更高
- Yellow.ai W-RAC：LLM仅做分组决策不做生成，分块阶段成本降低一个数量级（~90%）

### 反模式（什么情况下不要用、常见错误）
- ❌ **反模式1：固定大小切分语义**：不按段落/章节边界，在句子中间切断，导致每个chunk语义不完整
- ❌ **反模式2：递归层数过多**：超过3层归并导致信息逐层丢失，摘要的摘要的摘要最后什么都没了
- ❌ **反模式3：所有任务都MapReduce**：短文档（<10K tokens）直接处理即可，分块开销大于收益
- ❌ **反模式4：不需要摘要也硬做摘要**：事实查询只需要检索相关片段，不需要全文档MapReduce
- ❌ **反模式5：忽略重叠比例**：chunk之间没有重叠，导致边界处信息丢失，15%重叠是经验甜点

### G3迁移验证（还能用在哪些其他场景）

MapReduce是分布式计算经典范式，可迁移到：

1. **Hadoop/Spark大数据处理领域**：
   - 对应步骤1：InputSplit数据分片（HDFS块大小，按行/格式拆分）
   - 对应步骤2：Map阶段并行处理每个分片，输出中间键值对
   - 对应步骤3：Shuffle+Reduce阶段归并结果，多级Reduce Tree
   - 这就是Google MapReduce原始论文的范式，逻辑完全一致

2. **图像/视频分块处理领域**：
   - 对应步骤1：大图像分块（如8x8块用于JPEG压缩，或医学图像分块处理）
   - 对应步骤2：每个块独立处理（压缩、特征提取、AI推理）
   - 对应步骤3：拼接融合结果，处理块边界重叠区域
   - 卷积神经网络的滑动窗口、图像金字塔也是分治思想

3. **大规模数值计算/线性代数领域**：
   - 对应步骤1：大矩阵分块（Block Matrix）
   - 对应步骤2：每个块独立计算矩阵乘法/分解
   - 对应步骤3：结果块拼接为最终矩阵
   - 高性能计算（HPC）中的矩阵分块算法、分布式线性代数完全是这个模式
