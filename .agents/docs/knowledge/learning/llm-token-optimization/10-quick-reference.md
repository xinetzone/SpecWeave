# Token优化快速参考卡（3分钟速查）

> 🎯 **本文档是前台视图**：假设读者只有3分钟，提供最核心、最可操作的信息。完整论证、详细步骤、案例数据请阅读后台文档。

---

## ⚡ 核心数据一眼记

| 事实 | 数据 | 记忆口诀 |
|------|------|---------|
| 自注意力复杂度 | O(n²)，上下文翻倍计算量翻4倍 | 长度翻倍，计算×4 |
| 输出vs输入价格 | 输出token是输入的3-8倍 | 输出最贵，控制输出 |
| 缓存命中价格 | 缓存输入仅为普通输入的10% | 能缓存就缓存 |
| Quick Wins收益 | 1-2周可降本50-70% | 先做简单的，别搞复杂 |
| 目标状态 | 成熟系统成本降低85-95% | 渐进式，持续迭代 |

## 🛤️ 三大本质路径（记住这三个就够了）

| 路径 | 一句话 | 优先做 | 典型技术 |
|------|--------|--------|---------|
| **减少（Reduce）** | 根本就不送没用的token | ✅ 最先做 | max_tokens、精简提示、截断、模型路由 |
| **复用（Reuse）** | 算过的不要再算 | ✅ 必做 | KV缓存、前缀缓存、语义缓存、vLLM |
| **压缩（Compress）** | 用更少token说同样的事 | ⚠️ 最后做 | 摘要、语义压缩、蒸馏、实体提取 |

**实施顺序**：减少 → 复用 → 压缩（按ROI从高到低）

---

## 🚀 P0速赢（今天就能做，成本立降30-50%）

- [ ] **设置max_tokens**：所有接口设合理输出上限，防无限生成
- [ ] **升级vLLM**：从Transformers Pipeline换vLLM，吞吐提升5-10倍（自托管）
- [ ] **重构提示词**：静态前缀（系统提示/工具定义）放最前面，启用Prompt Caching
- [ ] **精简系统提示**：去除冗余修饰、重复说明（但别为省几个token牺牲效果——缓存后只贵10%）
- [ ] **接入监控**：Helicone/Langfuse/Portkey看钱花在哪了

---

## ❌ 绝对不能做（5条P0禁令）

| 编号 | 禁令 | 一句话理由 |
|------|------|-----------|
| C-001 | 不能为省token牺牲不可接受的质量 | 省的钱不如用户流失损失大 |
| C-002 | 不能裸用Transformers Pipeline上线 | 比vLLM贵5-10倍，吞吐低 |
| C-007 | 语义缓存阈值不能低于0.9 | 会命中错误答案引发事故 |
| C-012 | 不能不设max_tokens | 一次幻觉就能产生巨额账单 |
| C-020 | 不能不做灰度全量上线优化 | 出问题影响所有用户，回滚慢 |

## 📊 三维权衡（决策时问自己）

```
min(成本)  s.t.  质量 ≥ Q_min, 延迟 ≤ L_max
```

每次优化决策前问三个问题：
1. **质量够吗？** 比基线下降不超过3-5%（或在可接受范围内）
2. **延迟可接受吗？** TTFT、TPOT满足业务SLA
3. **ROI划算吗？** 投入的人力时间，多久能省回来？

## 📈 四阶段实施路线图

| 阶段 | 时间 | 做什么 | 累计降本 |
|------|------|--------|---------|
| **阶段1：快速见效** | 1-2周 | P0速赢项 + 基础缓存 + 基础截断 | 40-60% |
