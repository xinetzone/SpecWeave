# 提示词工程优化

提示词工程优化是最直接、投入产出比最高的token节省手段，无需修改模型架构或基础设施，仅通过优化输入提示的结构和内容即可实现显著的token节省。

## 技术清单

### 1. 精简提示词（Prompt Pruning）

**原理说明**：通过去除冗余修饰词、合并重复指令、删除礼貌性用语（如"请"、"谢谢"、"你好"等）和解释性铺垫，直接减少输入token数量。研究表明，大多数提示词中存在30-50%的冗余token，这些token不影响模型理解任务意图，但会显著增加成本和延迟。精简的核心原则是"只保留模型完成任务必需的信息"。

**本质路径映射**：减少

**适用场景**：所有LLM应用场景，尤其是高并发API调用场景；系统提示词优化；批量处理任务。

**实施难度**：低。仅需人工审查提示词或使用简单的规则过滤器即可实施。

**预期效果范围**：token减少20-40%，质量影响<3%。

**优点**：
- 实施成本极低，无需技术改造
- 立竿见影，无需额外计算资源
- 不影响模型输出格式和结构

**缺点**：
- 过度精简可能导致指令歧义
- 需要人工审查，难以完全自动化
- 节省比例有上限，通常不超过50%

**注意事项**：
- 保留关键约束条件（如格式要求、否定指令）
- 避免删除领域专有名词和关键实体
- 精简后需进行质量回归测试

---

### 2. 结构化输出（Structured Output）

**原理说明**：通过JSON Schema、强制格式模板、输出长度限制等方式，约束模型输出格式，减少模型生成的解释性文字、过渡语句和冗余表述。结构化输出使模型直接生成目标格式内容，避免"让我思考一下"、"以下是我的回答"等无关token。研究表明，强制JSON格式输出可减少输出token 30-60%。

**本质路径映射**：减少

**适用场景**：API集成场景；数据提取任务；需要机器解析输出的场景；批量处理任务。

**实施难度**：低-中。可通过API参数（如response_format）或提示词约束实现。

**预期效果范围**：输出token减少30-60%，质量影响<5%（解析准确率反而提升）。

**优点**：
- 输出格式一致性高，便于下游处理
- 显著减少无关解释性文字
- 降低幻觉风险（格式约束引导模型聚焦内容）

**缺点**：
- 灵活性降低，不适合开放式创作
- 格式约束过强可能导致内容截断
- 部分旧模型不支持原生JSON模式

**注意事项**：
- 提供明确的字段定义和示例
- 设置合理的max_tokens防止输出截断
- 对于复杂结构，提供1-2个输出示例

---

### 3. Few-shot示例优化（Few-shot Example Optimization）

**原理说明**：通过精简示例内容、选择最具代表性的示例、缓存示例前缀三种方式优化few-shot学习。研究表明，多数few-shot提示中存在冗余示例——3-5个高质量示例的效果往往优于10个以上低质量示例。示例选择应覆盖输入空间的多样性，而非简单堆叠数量；同时，将示例放在提示词前部可利用前缀缓存机制。

**本质路径映射**：减少 + 复用

**适用场景**：分类任务；格式转换任务；需要特定输出风格的场景；指令遵循能力要求高的任务。

**实施难度**：中。需要对示例质量进行评估和选择，可借助相似度检索实现动态示例选择。

**预期效果范围**：提示token减少30-70%，质量影响<5%（精选示例可能提升效果）。

**优点**：
- 减少示例数量不降低甚至提升效果
- 动态示例选择可适应不同输入
- 示例前缀可被缓存复用

**缺点**：
- 示例选择需要领域知识
- 动态选择增加检索开销
- 过少示例可能导致泛化能力下降

**注意事项**：
- 示例格式保持一致，减少格式说明token
- 使用占位符而非完整长文本作为示例
- 定期评估示例集的代表性，移除冗余示例

### 4. 思维链压缩（Chain-of-Thought Compression）

**原理说明**：传统思维链（CoT）要求模型展示完整推理过程，消耗大量token。压缩技术包括：精简CoT（只保留关键推理步骤）、自洽性替代（用多次采样替代长推理链）、分步验证（将长推理拆分为多个短步骤）。核心思想是：推理token是手段而非目的，应在保证答案正确的前提下最小化推理过程的token消耗。

**本质路径映射**：压缩 + 减少

**适用场景**：数学推理；逻辑推理；复杂决策任务；多步问题求解。

**实施难度**：中-高。需要设计推理压缩策略，可能需要微调或特殊提示技巧。

**预期效果范围**：推理token减少40-70%，质量影响5-10%（需权衡准确率与成本）。

**优点**：
- 显著减少推理过程的token消耗
- 分步验证可提升可解释性和错误定位
- 自洽性方法可并行化，降低延迟

**缺点**：
- 过度压缩可能导致推理错误
- 分步执行增加API调用次数
- 效果因任务类型差异较大

**注意事项**：
- 关键推理步骤不可省略（如数值计算）
- 对高风险任务保留完整推理链
- 监控压缩后的准确率变化，设置阈值回退

---

### 5. 系统提示词优化（System Prompt Optimization）

**原理说明**：系统提示词通常在多轮对话中保持不变，是前缀缓存的最佳候选。优化包括两个层面：一是精简系统指令本身，去除冗余描述；二是合理组织系统提示词结构，将静态内容放在最前面以最大化缓存命中率。主流LLM服务商（OpenAI、Anthropic、Google）均对缓存token提供10-25%的价格折扣。

**本质路径映射**：减少 + 复用

**适用场景**：所有使用系统提示词的场景；多轮对话应用；高并发API服务；Agent系统。

**实施难度**：低。组织提示词顺序、精简指令即可。

**预期效果范围**：系统提示token减少20-50%，缓存命中后成本降低75-90%。

**优点**：
- 缓存折扣显著降低成本
- 不影响对话功能
- 实施简单，收益持续

**缺点**：
- 缓存命中率依赖于请求模式
- 动态系统提示无法充分利用缓存
- 不同服务商的缓存机制存在差异

**注意事项**：
- 将静态内容（角色定义、规则）放在提示词开头
- 将变量内容（用户问题、动态数据）放在末尾
- 避免在静态部分插入变量，否则破坏缓存连续性

---

### 6. 指令优先级排序（Instruction Prioritization）

**原理说明**：当提示词包含多条指令时，按优先级排序并移除低优先级指令，或使用条件指令（如"如果X，则Y；否则忽略Z"）避免无关指令被处理。模型注意力是有限的，过多指令会稀释关键指令的权重，同时增加token消耗。指令优先级确保在token预算紧张时保留最重要的约束。

**本质路径映射**：减少

**适用场景**：复杂Agent系统；多约束条件任务；token预算严格受限的场景。

**实施难度**：中。需要梳理指令依赖关系和优先级。

**预期效果范围**：指令token减少15-30%，关键指令遵循率提升。

**优点**：
- 提升关键指令的遵循率
- 在token紧张时优雅降级
- 提示词逻辑更清晰

**缺点**：
- 优先级判定需要人工梳理
- 条件指令增加提示词复杂度
- 可能遗漏边缘情况的处理

**注意事项**：
- 安全相关指令永远是最高优先级
- 使用编号列表明确优先级顺序
- 测试边缘情况，确保降级策略正确

---

### 7. 负面提示优化（Negative Prompting）

**原理说明**：传统负面提示使用"不要做X"、"避免Y"等否定表述，这类表述token效率低——模型需要处理否定语义，且容易出现"否定忽略"现象。优化方式包括：使用正面表述替代（"只输出Z"替代"不要输出X、Y"）、使用禁止词列表（结构化的黑名单）、设置输出边界（如"最多3句话"）。正面指令比否定指令的token效率高40%以上。

**本质路径映射**：减少

**适用场景**：内容生成约束；格式约束；安全护栏场景；风格控制。

**实施难度**：低。将否定表述转换为肯定表述即可。

**预期效果范围**：约束token减少30-50%，约束遵循率提升10-20%。

**优点**：
- 正面指令更易被模型理解和执行
- 减少否定词带来的语义混淆
- 约束效果更好

**缺点**：
- 某些约束难以完全用正面表述
- 复杂黑名单需要结构化存储
- 需要转换思维方式

**注意事项**：
- 安全约束仍需保留否定形式作为双重保险
- 避免双重否定造成理解困难
- 使用示例说明期望行为比单纯禁止更有效

## G2质量门：核心洞察四元组

**现象**：提示词工程优化是所有token优化手段中门槛最低、见效最快的方法，大多数团队仅通过提示词优化即可实现30-50%的成本节省，但实际生产中超过60%的LLM应用未进行系统的提示词token审计。

**根因**：提示词冗余的本质原因是开发者以"人类沟通习惯"编写提示词，而非以"token效率"为目标。礼貌用语、解释性铺垫、重复指令在人类沟通中是礼貌和清晰的体现，但对LLM而言是纯粹的token浪费。同时，提示词通常由产品或业务人员编写，缺乏token成本意识。

**影响**：提示词优化的投入产出比（ROI）是所有优化手段中最高的——无需架构改造、无需模型训练、无需基础设施投入，仅通过审查和重构提示词即可获得显著收益。但提示词优化的节省上限较低（通常不超过60%），无法解决根本性的规模成本问题，需要与其他技术组合使用。

**建议**：建立提示词token审计流程作为开发标配：新提示词上线前必须经过token计数和精简审查；系统提示词必须组织为"静态前缀+动态后缀"结构以利用缓存；建立提示词版本管理，持续迭代优化；将token效率纳入提示词评估指标，而非只看效果指标。
