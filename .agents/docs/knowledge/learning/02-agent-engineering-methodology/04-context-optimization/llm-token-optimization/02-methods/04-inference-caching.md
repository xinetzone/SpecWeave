# 增量推理与缓存

缓存与增量推理技术是推理引擎层面的核心优化，通过复用已计算的中间结果避免重复计算，在不改变输出结果的前提下降低延迟和成本。这类技术是现代LLM推理框架（vLLM、SGLang、TensorRT-LLM）的基础能力。

## 技术清单

### 1. KV缓存优化（KV Cache Optimization）

**原理说明**：Transformer自回归生成时，每生成一个新token都需要对所有历史token计算注意力。如果不缓存，生成N个token需要O(N²)次注意力计算——第1个token计算1次，第2个计算2次，第N个计算N次。KV缓存将每一层的Key和Value张量存储起来，生成新token时只需要计算新token与历史缓存KV的注意力，将计算复杂度从O(N²)降低到O(N)。标准KV缓存是所有现代推理框架的基础，没有KV缓存就没有实用的LLM推理。KV缓存的内存开销公式为：`batch_size × seq_length × num_layers × 2 × hidden_dim × precision_bytes`，70B模型在8K上下文、batch=32时KV缓存可达640GB。

**本质路径映射**：复用（复用历史token的KV计算结果）

**适用场景**：所有LLM推理场景；自回归生成；任何使用Transformer解码器的场景。

**实施难度**：低。Hugging Face Transformers、vLLM等框架默认启用KV缓存，无需手动实现。

**预期效果范围**：解码速度提升10-100倍（相比无缓存），内存开销为模型权重的0.5-2倍（视上下文长度而定）。

**优点**：
- 基础优化，所有推理框架默认支持
- 无质量损失，纯计算复用
- 效果显著，是LLM实用化的前提
- 无需修改模型或提示词

**缺点**：
- KV缓存内存开销大，随上下文长度线性增长
- 长上下文和大batch时容易OOM（显存不足）
- 传统预分配方式内存浪费严重
- 不同请求之间无法共享缓存

**注意事项**：
- 使用use_cache=True（默认开启），不要在代码中关闭
- 监控KV缓存内存占用，设置合理的max_model_len
- 批处理大小受KV缓存内存限制，而非模型权重大小
- 不同模型架构的KV缓存布局可能不同
- 注意KV缓存的精度（FP16/BF16）与模型权重一致

### 2. 前缀缓存（Prefix Caching / Prompt Caching / APC）

**原理说明**：系统提示词、工具描述、 few-shot示例等内容在多个请求间往往是重复的。前缀缓存（vLLM称为Automatic Prefix Caching/APC，OpenAI称为Prompt Caching，Anthropic也支持相同机制）检测不同请求间共享的前缀token序列，复用这些前缀的KV缓存块，避免重复计算。vLLM通过哈希每个KV块及其前缀来识别可复用块，使用全局哈希表管理物理块的共享。主流服务商对缓存命中的token提供10-25%的价格折扣，延迟降低50%+。关键是将静态内容放在提示词开头，变量内容放在末尾，以最大化前缀匹配长度。

**本质路径映射**：复用（跨请求复用共享前缀的KV缓存）

**适用场景**：多轮对话（系统提示词共享）；Agent系统（工具描述共享）；RAG系统（固定文档块重复查询）；批处理任务（相同指令模板）；高并发API服务。

**实施难度**：低。vLLM启用`--enable-prefix-caching`参数即可；OpenAI/Anthropic API自动支持，只需合理组织提示词顺序。

**预期效果范围**：缓存命中token成本降低75-90%（服务商折扣），TTFT（首token延迟）降低50-80%，系统提示词场景命中率可达80%+。

**优点**：
- 无需修改模型，启用配置即可
- 同时降低成本和延迟
- 跨请求自动共享，无需手动管理
- vLLM等开源框架已原生支持

**缺点**：
- 缓存命中率取决于提示词组织方式
- 动态插入变量会破坏前缀连续性
- 缓存需要显存/内存存储，有容量限制
- 不同服务商的缓存TTL和策略不同

**注意事项**：
- 静态内容（系统提示、角色、规则）放最前面
- 变量内容（用户问题、动态数据）放最后
- 避免在静态部分插入变量，否则前缀断裂
- 监控缓存命中率指标，优化提示词组织
- 缓存命中时服务商可能仍按标准token计费（但速度更快）

### 3. PagedAttention（vLLM内存优化）

**原理说明**：传统KV缓存为每个请求预分配连续的显存块（按最大序列长度预留），但大多数请求远达不到最大长度，导致60-80%的KV缓存内存因碎片和过度分配而浪费。PagedAttention借鉴操作系统虚拟内存和分页机制：将KV缓存分割为固定大小的块（Block，通常存储16-64个token的KV），块可以存储在非连续的物理显存中，通过块表（Block Table）维护逻辑位置到物理位置的映射。序列增长时按需分配块，序列结束时释放块，内存浪费降低到4%以下。PagedAttention是vLLM的核心创新，直接带来2-4倍的吞吐量提升。SGLang的RadixAttention在PagedAttention基础上增加了前缀树结构进一步优化共享。

**本质路径映射**：复用（通过分页消除内存碎片，提升batch并发度，间接提升吞吐量）

**适用场景**：高并发推理服务；变长序列处理；vLLM/SGLang/TensorRT-LLM等现代推理框架；生产环境部署；GPU显存受限场景。

**实施难度**：低。使用vLLM作为推理引擎即自动启用PagedAttention，无需额外配置。

**预期效果范围**：KV缓存内存浪费从60-80%降低到<4%，吞吐量提升2-4倍，支持更大batch和更长上下文。

**优点**：
- 几乎消除KV缓存内存浪费
- 吞吐量提升显著（2-4倍）
- 支持更大并发和更长上下文
- 与前缀缓存自然兼容
- vLLM开箱即用

**缺点**：
- 块表管理有少量开销
- 需要专门的推理框架支持（非原生Transformers）
- 块大小需要调优
- 与某些高级功能（如自定义注意力）兼容性需验证

**注意事项**：
- 使用vLLM而非原生Hugging Face Pipeline进行生产部署
- block_size通常设为16（vLLM默认），无需修改
- 设置合理的gpu_memory_utilization（0.85-0.95）
- 连续批处理（Continuous Batching）与PagedAttention配合使用效果最佳
- PagedAttention是前缀缓存的基础，两者同时启用

### 4. 增量解码与预填充优化（Incremental Decoding / Chunked Prefill）

**原理说明**：LLM推理分为两个阶段：预填充（Prefill）阶段处理整个输入prompt，计算密集型但可并行；解码（Decode）阶段逐token生成，内存带宽受限。传统调度将预填充和解码请求混在一起，长预填充会阻塞解码请求，导致TTFT（首token时间）和TBT（token间时间）都很高。优化包括：（1）分块预填充（Chunked Prefill）：将长prompt分成多个chunk，间歇执行预填充和解码，避免长预填充阻塞解码；（2）预填充/解码分离：预填充和解码运行在不同GPU集群上，KV缓存通过高速网络迁移；（3）增量预填充：多轮对话中，新输入只需要追加到已有KV缓存后，无需重新处理完整历史。这些优化将TTFT和吞吐量同时改善。

**本质路径映射**：复用（增量预填充复用已有KV缓存）

**适用场景**：多轮对话（增量预填充）；长prompt处理（分块预填充）；高并发生产环境；对TTFT敏感的交互场景；大规模推理服务。

**实施难度**：中。需要vLLM/SGLang等支持分块预填充的推理框架，分离式部署需要架构设计。

**预期效果范围**：TTFT降低30-70%（长prompt场景），多轮对话预填充计算量减少80%+（复用历史KV），GPU利用率提升20-40%。

**优点**：
- 显著改善首token延迟（TTFT）
- 多轮对话避免重复计算历史
- 提升GPU利用率和整体吞吐量
- 减少解码请求的阻塞

**缺点**：
- 分块预填充需要调度器支持
- 预填充/解码分离增加系统复杂度
- 跨GPU迁移KV缓存需要高速网络（NVLink/InfiniBand）
- 调度逻辑复杂，可能引入新的延迟问题

**注意事项**：
- 启用vLLM的--enable-chunked-prefill参数
- 多轮对话中正确传递past_key_values或使用conversation API
- 分块大小需根据prompt长度分布调优
- 分离式部署适合超大规模场景，中小规模单卡vLLM即可
- 监控TTFT和TBT两个指标，确保两者都在合理范围

### 5. 语义缓存（Semantic Cache）

**原理说明**：精确缓存（缓存精确匹配的请求）命中率很低，因为用户提问的措辞千变万化。语义缓存将请求转化为向量嵌入，通过向量相似度检索找到语义相近的历史请求，如果相似度超过阈值则直接返回缓存的回答，无需调用LLM。语义缓存分为两级：（1）精确匹配缓存（hash key），处理完全相同的重复请求；（2）语义相似度缓存（向量检索），处理措辞不同但语义相同的问题。语义缓存特别适合客服、问答等高重复率场景，常见问题（FAQ）的命中率可达40-70%。GPTCache是开源的语义缓存实现。

**本质路径映射**：复用（复用语义等价请求的历史回答）

**适用场景**：客服系统；FAQ问答；高重复率查询；企业内部知识库问答；成本敏感的高并发场景。

**实施难度**：中。需要集成向量数据库、嵌入模型、相似度阈值策略和缓存失效机制。

**预期效果范围**：缓存命中请求成本降低100%（无需调用LLM），整体成本降低20-60%（取决于请求重复率），延迟降低90%+（直接返回缓存）。

**优点**：
- 命中请求完全消除LLM调用成本
- 响应延迟极低（毫秒级）
- 可显著降低高流量场景成本
- 对用户透明，不改变交互方式

**缺点**：
- 语义相似≠答案相同，可能返回错误答案
- 需要嵌入模型和向量数据库，增加系统复杂度
- 缓存失效和一致性管理复杂
- 创意类、个性化场景命中率低
- 阈值设置困难：过高命中率低，过低错误率高

**注意事项**：
- 必须设置答案相似度校验（不仅看问题相似度）
- 高风险场景（金融、医疗）禁用或保守使用
- 设置合理的TTL（缓存过期时间）
- 记录缓存命中日志，持续监控准确率
- 精确缓存+语义缓存两级架构
- 对个性化请求（如包含用户ID）做缓存键隔离
- 提供"重新生成"机制，允许用户绕过缓存

### 6. KV缓存压缩与量化（KV Cache Compression/Quantization）

**原理说明**：KV缓存通常以FP16/BF16精度存储，内存开销大。KV缓存量化将KV值降低到INT8或INT4精度存储，读取时反量化，可将KV缓存内存减少50-75%。与权重量化不同，KV缓存是动态的（随请求变化），需要更谨慎的量化策略。最新研究如Joint Encoding提出跨请求KV块融合：将不同请求中相似的KV块编码为共享表示，实现最高4.38倍的KV缓存压缩率，精度损失可忽略，在vLLM上吞吐量提升约40%。KV缓存驱逐策略也是重要优化：当显存不足时，优先驱逐引用计数为0且最近最少使用（LRU）的块。

**本质路径映射**：压缩（KV值低精度存储）+ 复用（跨请求相似KV块共享）

**适用场景**：超长上下文场景；高并发服务；GPU显存紧张；KV缓存成为瓶颈的场景。

**实施难度**：中-高。需要支持KV量化的推理框架（vLLM支持KV cache quantization），跨请求KV融合是前沿研究。

**预期效果范围**：KV缓存内存减少50%（INT8）-75%（INT4），吞吐量提升20-50%，质量损失<2%（INT8时）。

**优点**：
- 直接减少KV缓存内存占用
- 支持更长上下文和更大batch
- 可与PagedAttention、前缀缓存叠加
- INT8 KV量化已在vLLM中可用

**缺点**：
- KV量化可能带来轻微质量损失
- 反量化有少量计算开销
- 跨请求融合技术尚不成熟，生产落地少
- 精度越低，质量风险越高

**注意事项**：
- 优先使用INT8 KV量化（质量损失可忽略）
- INT4 KV量化需充分测试质量影响
- 使用vLLM的--kv-cache-dtype fp8或int8参数
- 结合LRU驱逐策略管理有限的KV缓存空间
- 监控质量指标，确保量化不引入明显退化

### 7. 请求批处理优化（Continuous Batching / Dynamic Batching）

**原理说明**：静态批处理（Static Batching）等待一组请求凑齐后一起推理，导致GPU空闲等待、尾部延迟高。连续批处理（Continuous/In-Flight Batching，vLLM默认启用）在请求级别调度：每当一个请求完成生成，立即从等待队列中加入新请求填补空位，无需等待整个batch完成。迭代级调度（Iteration-Level Scheduling）在每个解码步都可以调整batch组成，实现GPU近乎100%利用率。连续批处理是推理吞吐量提升的关键技术之一，与PagedAttention配合构成现代推理引擎的核心。

**本质路径映射**：复用（提升GPU利用率，减少空闲等待，降低单位请求成本）

**适用场景**：所有高并发在线推理服务；API服务；生产环境部署；请求到达率不稳定的场景。

**实施难度**：低。使用vLLM等现代推理框架默认启用连续批处理，无需额外配置。

**预期效果范围**：GPU利用率从30-50%提升到80-95%，吞吐量比静态批处理提升5-10倍（结合PagedAttention），尾部延迟降低。

**优点**：
- GPU利用率大幅提升
- 无需等待凑batch，降低排队延迟
- 自适应不同请求率
- vLLM等框架默认支持

**缺点**：
- 调度逻辑复杂（框架已处理）
- 不同生成长度的请求混合可能导致少量浪费
- 需要合理设置max_num_batched_tokens等参数

**注意事项**：
- 使用vLLM/SGLang/TensorRT-LLM等现代推理框架
- 调优max_num_seqs（最大并发序列数）和max_num_batched_tokens
- 启用--enable-chunked-prefill避免预填充阻塞解码
- 监控GPU利用率，目标保持在80-95%
- 长输出请求和短输出请求混合部署可提升整体利用率

## G2质量门：核心洞察四元组

**现象**：推理引擎层面的优化（PagedAttention、连续批处理、前缀缓存）是所有优化中"最划算"的——不需要修改模型、不需要修改提示词、不需要改变应用逻辑，仅通过升级推理框架（从原生Transformers到vLLM）即可获得5-10倍的吞吐量提升。但实际生产中仍有大量团队使用Flask/FastAPI包装原生Transformers进行部署，完全没有利用这些现代推理引擎优化。语义缓存概念热门但实际落地率不高，多数团队停留在简单的精确缓存层面。

**根因**：推理引擎优化存在"知识鸿沟"——应用开发者通常熟悉LLM API和Prompt工程，但对推理系统内部原理（KV缓存、批处理、内存管理）了解不足，不知道PagedAttention等技术的存在或其重要性。"能跑就行"的心态导致部署时选择最简单的方案，而非最高效的方案。语义缓存落地难的原因是"正确性焦虑"——团队担心缓存返回错误答案，不敢激进使用，又缺乏有效的缓存质量监控机制。

**影响**：推理引擎优化是LLM基础设施的"免费午餐"——同样的硬件，使用vLLM比原生Transformers多服务5-10倍的请求。这意味着如果正确使用推理引擎，GPU硬件成本可以直接降低80-90%。反过来，不使用现代推理引擎是最大的成本浪费——相当于花10倍的钱买GPU，却只获得1倍的服务能力。前缀缓存和语义缓存则是"锦上添花"，在高并发场景下可再降低30-70%的成本。

**建议**：生产部署必须使用现代推理引擎，禁止裸用Transformers Pipeline做服务：（1）第一优先级：将所有推理服务迁移到vLLM（或SGLang/TensorRT-LLM），启用PagedAttention和连续批处理，这是收益最大的单一优化（5-10倍吞吐量）；（2）第二优先级：启用自动前缀缓存（--enable-prefix-caching），合理组织提示词结构（静态在前，动态在后）；（3）第三优先级：启用分块预填充改善TTFT；（4）第四优先级：对高重复率场景（客服、FAQ）实施语义缓存，但必须有答案校验和人工抽检机制；（5）第五优先级：KV缓存量化（INT8）进一步提升并发。建立推理监控看板：吞吐量（tokens/s）、TTFT、TBT、GPU利用率、缓存命中率，这些指标是推理效率的"体检表"。
