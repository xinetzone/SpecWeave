# 多轮对话管理

多轮对话管理专门针对对话式AI场景，解决对话历史随轮次增长导致的token线性膨胀问题。这类技术平衡对话连贯性与token效率，是聊天机器人、AI助理、客服系统的核心基础能力。

## 技术清单

### 1. 历史截断策略（History Truncation）

**原理说明**：最基础的对话管理策略，当对话历史超过预设阈值时，丢弃部分历史消息。截断方式包括：（1）固定轮数截断：保留最近N轮对话（如最近5轮用户-助手交互，共10条消息）；（2）Token预算截断：按token计数截断，保留最近的消息直到达到token上限；（3）混合策略：永远保留系统消息和重要消息（如用户明确的约束条件），其余按时间截断。截断策略简单易实现，但"关键信息在早期被截断"是最常见的故障模式。Microsoft Semantic Kernel的Truncation reducer即采用此策略。

**本质路径映射**：减少

**适用场景**：简单聊天机器人；轻量客服；短对话为主的应用；成本极度敏感场景；快速原型验证。

**实施难度**：低。按轮数或token数计数截断即可，LangChain的ConversationBufferWindowMemory提供开箱实现。

**预期效果范围**：对话上下文token稳定控制在预算内，简单闲聊场景质量影响<5%，复杂多约束任务可能丢失关键信息。

**优点**：
- 实现极其简单，零额外计算开销
- Token消耗可预测，便于成本控制
- 延迟为零，不增加处理时间
- 无幻觉风险（保留原文）

**缺点**：
- 粗暴截断可能丢失早期关键约束和决策
- "AI健忘症"：用户提到过的偏好被遗忘
- 无法处理跨多轮的指代消解（如"它"指什么）
- 重要信息与寒暄一起被丢弃

**注意事项**：
- 系统消息（system prompt）永远保留，不可截断
- 保留包含用户明确偏好、约束、目标的消息
- 不要单纯按消息条数截断，结合token计数更准确
- 对截断的消息记录日志，便于排查"健忘"问题
- 截断阈值不宜过小（建议至少保留最近3-5轮）

### 2. 摘要记忆（Summary Memory）

**原理说明**：不直接丢弃旧消息，而是用LLM将旧对话历史压缩为结构化摘要，用摘要替代原始旧消息放入上下文。常见实现包括：（1）滚动摘要（ConversationSummaryMemory）：每次新消息到来时，更新摘要，将新信息合并到已有摘要中；（2）摘要缓冲混合（ConversationSummaryBufferMemory）：最近N轮保留原文，更早的消息压缩为摘要，兼顾精确性和压缩率；（3）层级摘要：对不同时间段的对话生成不同粒度的摘要。MT-OSC等研究表明，良好的对话压缩可在10轮对话中减少72%的token，同时保持或提升准确率。

**本质路径映射**：压缩

**适用场景**：长对话系统；咨询型产品；客服机器人；个人助理；Agent任务执行；多轮协作场景。

**实施难度**：中。需要摘要模型（可用小模型）、摘要格式模板、摘要更新逻辑。LangChain和Semantic Kernel均提供内置实现。

**预期效果范围**：长期对话token减少50-80%，关键信息保留率80-90%（取决于摘要质量）。

**优点**：
- 压缩比高，支持超长对话
- 保留语义信息而非单纯丢弃
- 摘要缓冲混合兼顾近期精确性和长期记忆
- 成熟框架支持，实现不难

**缺点**：
- 摘要本身消耗token（摘要模型调用成本）
- 可能遗漏数字、日期、否定条件等细节
- 存在摘要幻觉风险（摘要模型虚构信息）
- 异步摘要可能增加感知延迟
- 摘要错误会持续累积（每次更新都可能引入偏差）

**注意事项**：
- 使用结构化摘要模板（目标/约束/已完成/待办），而非自由文本
- 关键业务字段（金额、日期、审批结论）单独存储，不依赖摘要
- 使用小模型（如GPT-3.5-turbo、Llama-3-8B）做摘要，控制成本
- 摘要触发基于token阈值，而非每轮都摘要
- 定期（如每10轮）重置摘要，避免错误累积
- 保留原始对话日志，摘要仅用于上下文传递

### 3. 实体提取与状态跟踪（Entity Extraction & State Tracking）

**原理说明**：从对话中持续提取关键实体和状态信息，存储在结构化的"记忆槽"（Slot）中，而非保留原始对话文本。实体类型包括：用户偏好（如"我喜欢邮件沟通"）、关键事实（如"这是企业账户"）、任务状态（如"已确认订单号123"）、待办事项、约束条件等。每次对话时，将结构化实体状态与最近几轮原文一起传入上下文。状态跟踪（Dialog State Tracking, DST）是任务型对话系统的经典技术，确保关键信息不会因为对话长度而丢失。Microsoft Azure文档中建议的3轮滚动窗口+重要性过滤即采用此思路——保留包含明确偏好、关键上下文、决策结论的轮次。

**本质路径映射**：压缩 + 减少

**适用场景**：任务型对话；客服系统（订单查询、退换货等）；表单填充场景；需要记住用户偏好的个人助理；流程化任务处理。

**实施难度**：中-高。需要定义实体schema、实现实体提取逻辑（可用LLM或NER模型）、设计状态更新规则。

**预期效果范围**：对话状态token减少70-90%，关键实体召回率>90%，任务完成率提升。

**优点**：
- 结构化记忆精确可靠，无幻觉
- 关键信息永不丢失（除非主动删除）
- 便于程序读取和操作（如检查是否已收集必填信息）
- Token效率极高（几个字段即可替代数百token对话）
- 可跨会话持久化

**缺点**：
- 需要预先定义实体schema，灵活性差
- 非结构化信息（如用户情绪、隐含意图）难以提取
- 实体提取可能出错或遗漏
- 开发和维护成本高于摘要
- 不适合开放式闲聊场景

**注意事项**：
- 实体schema由任务驱动，只提取与任务相关的实体
- 区分会话级实体（本次对话有效）和用户级实体（长期记忆）
- 实体提取使用低温度（temperature=0）保证一致性
- 允许用户查看和编辑已提取的实体（"我之前说我喜欢邮件，改回电话吧"）
- 实体冲突时（用户说法变了）以最新表述为准
- 不要试图提取所有信息，聚焦高价值实体

### 4. 会话状态机与工作流压缩（State Machine & Workflow Compression）

**原理说明**：对于流程化任务（如客服工单处理、订餐、预约等），对话本质是在预定义工作流中推进。与其传递完整对话历史，不如跟踪当前所处的状态节点和已收集的参数。状态机定义对话的各个阶段（如"验证身份"→"查询订单"→"处理退款"→"确认满意度"），每个状态只需要该状态相关的信息，而非全部历史。工作流压缩将对话转化为状态转移，上下文从"完整对话"变为"当前状态+已收集参数"，token效率极高。LangGraph等框架专门为有状态的多轮Agent设计，原生支持状态机模式。

**本质路径映射**：压缩 + 减少

**适用场景**：流程化客服；任务型对话；表单填充；多步骤业务流程；Agent任务编排；可预定义流程的场景。

**实施难度**：高。需要设计状态机/工作流，定义状态转移条件和每个状态的所需信息，开发量较大。

**预期效果范围**：流程化对话token减少80-95%，任务完成率提升，流程一致性高。

**优点**：
- Token效率极高（状态+参数替代完整对话）
- 流程可控，不会偏离预定轨道
- 易于调试和问题定位
- 可插入Human-in-the-loop审批节点
- 业务指标可量化（转化率、完成率）

**缺点**：
- 灵活性差，无法处理流程外的请求
- 前期设计成本高，需要梳理完整业务流程
- 不适合开放式、探索性对话
- 状态机维护成本随业务复杂度增长
- 用户可能试图"跳出流程"导致处理失败

**注意事项**：
- 从高频、标准化的流程开始试点，不要试图覆盖所有场景
- 设计"兜底"状态处理流程外请求（转人工、通用问答）
- 每个状态的输入参数明确列出，只传入必要信息
- 使用LangGraph等框架降低状态机实现复杂度
- 记录状态转移日志，分析用户在哪一步流失
- 允许用户回退到上一状态（"我刚才说错了，重新来"）

### 5. 动态上下文窗口（Dynamic Context Window）

**原理说明**：固定大小的窗口要么浪费token（简单任务也用满窗口），要么丢失信息（复杂任务窗口不够）。动态上下文窗口根据当前任务复杂度、问题类型、可用token预算动态调整上下文大小：（1）简单问候/确认类问题只需要最近1-2轮；（2）事实型问答根据问题检索相关历史片段；（3）复杂推理/决策任务扩大窗口甚至使用完整摘要；（4）token预算紧张时自动提高压缩率。动态调整需要一个"上下文管理器"（Context Manager）来评估每轮对话的信息需求，智能选择保留哪些内容。这是对话管理的高级形态，结合了截断、摘要、实体提取多种策略。

**本质路径映射**：减少 + 压缩（自适应调整压缩策略）

**适用场景**：多任务混合对话系统；复杂度差异大的用户请求；成本敏感且需要保证质量的场景；企业级对话平台。

**实施难度**：高。需要实现上下文管理器策略，可能需要小模型做路由决策，调优复杂度高。

**预期效果范围**：平均token减少40-70%，相比固定窗口策略，复杂任务质量损失<5%，简单任务成本更低。

**优点**：
- 兼顾成本和质量，按需分配token
- 简单问题成本极低，复杂问题保证信息充足
- 自适应不同对话场景
- 是前几种策略的智能组合和升华

**缺点**：
- 实现复杂度高，策略调优困难
- 路由决策本身消耗少量token
- 策略错误可能导致简单问题也用大窗口（浪费）或复杂问题窗口不足（丢信息）
- 可解释性差，难以排查"为什么这个上下文被选/被弃"

**注意事项**：
- 从简单规则开始：先按问题关键词/分类路由，不要一开始就上ML路由
- 设置token预算上下限，避免极端情况
- 记录上下文选择决策日志，便于分析和调优
- 保守策略：不确定时宁多勿少，质量优先于成本
- 动态策略之上叠加兜底机制（如token超限自动触发摘要）

### 6. 角色消息分离与优先级标记（Message Separation & Priority Tagging）

**原理说明**：并非所有对话消息价值相同。将消息按来源和重要性分类：（1）系统消息（最高优先级，永不丢弃）：角色定义、规则、安全约束；（2）开发者消息（高优先级）：工具描述、工作流指令；（3）关键用户消息（高优先级）：用户目标、偏好、约束、决策；（4）工具返回消息（中优先级）：API结果、检索内容（可能已处理）；（5）普通对话（低优先级）：寒暄、确认、过渡语句、重复表达；（6）助手回复（中低优先级）：模型之前的回复通常可从用户消息中推断。截断或压缩时，按优先级从低到高处理，低优先级消息先被压缩/丢弃。这种策略确保最有价值的信息最后才被牺牲。

**本质路径映射**：减少（智能选择减少哪些内容）

**适用场景**：所有多轮对话系统；Agent系统（包含工具调用）；消息类型多样的复杂对话。

**实施难度**：低-中。在消息结构中添加优先级/类型字段，压缩策略按优先级排序。

**预期效果范围**：相比无差别截断，关键信息保留率提升30-50%，相同token预算下对话质量更高。

**优点**：
- 实现简单，收益显著
- 不依赖LLM判断，规则即可实现
- 确保最重要的信息始终被保留
- 可与其他策略（截断、摘要）组合使用

**缺点**：
- 优先级标注需要开发规范
- 部分消息的重要性需要动态判断（不是所有用户消息都同等重要）
- 过于复杂的优先级体系增加维护成本

**注意事项**：
- 消息创建时即标注类型和优先级，不要事后判断
- 安全相关指令永远最高优先级
- 用户的最终指令/问题优先级高于历史讨论
- 助手的长回复可大幅压缩（保留结论即可）
- 工具返回结果只保留关键字段，丢弃原始大JSON

### 7. 异步后台压缩（Asynchronous Background Compression）

**原理说明**：对话压缩（摘要、实体提取）如果在用户请求的关键路径上同步执行，会增加响应延迟。异步后台压缩将压缩操作放在用户思考间隔或闲时执行：当用户发送消息后，系统处理当前请求（使用未压缩的上下文保证响应速度），同时在后台异步压缩更早的对话历史，压缩完成后更新上下文缓存，下一轮请求即可使用压缩后的上下文。MT-OSC框架即采用此设计——Condenser Agent在后台异步压缩，不打断用户体验。更激进的策略是在检测到用户输入停顿（如5秒无输入）时预压缩。

**本质路径映射**：压缩（将压缩开销移出关键路径）

**适用场景**：对响应延迟敏感的对话系统；实时聊天应用；用户体验优先的产品；高并发场景。

**实施难度**：中。需要异步任务队列、上下文版本管理、压缩状态跟踪。

**预期效果范围**：压缩带来的延迟开销从用户感知路径中消除（减少500-2000ms延迟），压缩率与同步压缩相同。

**优点**：
- 用户感知延迟为零，不影响响应速度
- 可以使用更好（但稍慢）的压缩模型/算法
- 闲时计算资源利用率高
- 用户体验与token效率兼得

**缺点**：
- 首次请求时还未压缩（第一轮无收益）
- 增加系统复杂度（异步任务、状态同步）
- 快速连续对话可能在压缩完成前就已堆积
- 需要处理压缩失败/超时的降级策略

**注意事项**：
- 当前轮使用最新上下文（哪怕未压缩），保证响应速度
- 后台压缩任务设置超时，避免长时间阻塞
- 压缩完成后原子性更新上下文，避免并发问题
- 快速连续对话时跳过压缩，避免资源竞争
- 新会话前几轮无需压缩，等达到token阈值后启动

## G2质量门：核心洞察四元组

**现象**：多轮对话管理的实践呈现"三阶段"分化：（1）入门阶段——简单截断，开发最快但"AI健忘症"频发；（2）进阶阶段——摘要记忆，LangChain/LlamaIndex开箱即用，但摘要幻觉和细节丢失是常见痛点；（3）成熟阶段——结构化实体+状态机，但实施成本高，多数团队因业务流程梳理困难而止步。动态上下文窗口和异步压缩等高级策略仅有少数头部团队实施。

**根因**：对话管理的本质矛盾是"记忆完整性"与"token经济性"的权衡。简单截断偏向经济性但牺牲完整性；状态机偏向完整性但灵活性差、实施成本高；摘要试图平衡两者但引入幻觉风险。更深层的问题是：多数团队将对话管理视为"工程细节"而非"核心产品能力"，在架构设计阶段未给予足够重视，等到用户抱怨"AI健忘"时才打补丁，导致架构割裂。另一个根因是缺乏标准化的对话质量评估指标——团队知道token花了多少，却不知道"对话质量下降了多少"。

**影响**：对话历史管理是对话式AI的"地基"。地基不牢，上层应用越复杂问题越严重：长对话中AI反复询问用户已回答过的问题，忘记用户之前表达的偏好，丢失关键约束条件，这些体验问题直接导致用户流失。token成本只是显性成本，用户体验下降导致的流失是隐性成本，后者往往远大于前者。好的对话管理能同时降低token成本和提升用户体验，是双赢的优化。

**建议**：采用"分层对话记忆架构"而非单一策略：（1）即时层：最近3-5轮对话保留原文（保证近期对话精确性）；（2）工作记忆层：结构化实体槽存储关键事实、偏好、状态（永不遗忘关键信息）；（3）长期记忆层：更早对话压缩为结构化摘要（保留语义概览）；（4）流程层：对可流程化的任务使用状态机管理（替代自由对话）。优先级标记作为所有层的基础——系统消息和关键用户消息始终保留。摘要必须使用结构化模板（目标/约束/已完成/待办），禁止自由文本摘要。建立对话质量评估：除了token成本，还应监控"重复询问率"、"关键信息召回率"、"任务完成率"等体验指标。异步压缩作为性能优化最后实施，优先保证功能正确。
