# 第一性原理分析

## 本质问题：Token计费的计量经济学

从第一性原理思考，Trae IDE的Token消耗问题本质是：

1. **上下文窗口是全量发送的**：每次LLM调用，系统都会把当前上下文窗口内的所有内容重新发送一遍——包括系统提示、所有规则、所有启用的MCP工具定义、完整的历史对话、读取的文件内容。
2. **静态输入是沉默的固定成本**：你添加的每一条规则、每启用一个MCP、每安装一个Skill，都会变成每次请求必交的"过路费"，无论这个任务是否需要它。
3. **输出只是冰山一角**：AI生成的代码/回答只占Token消耗的小部分（紫色区域），输入（蓝色+橙色区域）才是成本主体。

## 四个根本认知错位

用户常见的错误直觉来自四个认知错位：

| 错误直觉 | 事实真相 |
|---------|---------|
| "让AI少说点话就能省Token" | 输出占比最小，压缩输出只能省5-10%；减少输入能省30-70% |
| "规则越多AI越听话，多多益善" | 长规则AI遵守率反而下降，同时增加30-60%静态成本，得不偿失 |
| "一个对话聊到底方便" | 历史对话中90%是无效的试错日志、工具返回、中间思考，有效信息被稀释，既贵又让AI变笨 |
| "最贵的模型效果最好" | 80%的简单任务用轻量模型就能搞定，效果差异小于5%，成本差3-5倍 |

## 核心杠杆原理

根据上述本质，Token节省的三大杠杆：

1. **减少静态负载**：把每次请求都要带的"固定行李"减重——精简规则、关闭不用的MCP/Skills
2. **控制动态膨胀**：不要让历史对话无限增长，子任务完成即清空
3. **分级匹配资源**：简单任务用便宜模型，不要"大炮打蚊子"

这与LLM应用Token优化的三大路径（减少→复用→压缩）思想一致，但在Trae IDE场景下具体表现形式不同——这里的"复用"主要靠"新对话+精准引用"而非Prompt缓存。
