# 模块1：Agent评测方法论概述

## 1.1 什么是Agent评测体系化建设

**Agent评测**（Agent Evaluation，通俗解释：系统地给AI智能体"体检打分"，而不是简单跑个分）是指用一套结构化的流程、指标与工具，可靠地衡量一个Agent在真实任务中的能力、效率、安全性与商业价值，并据此驱动持续改进的完整工程实践。

**体系化建设**（Systematic Construction）区别于"临时跑个benchmark"之处在于：它不是一次性的、孤立的、单一维度的"应试"，而是把评测当成一项**可持续运转的质量基础设施**来设计——有明确的目标锚定、有稳定的指标体系、有可复现的执行环境、有配套的迭代闭环。

> **适用对象说明**：本教程同时适用于不同规模的团队。成熟团队可按八阶段完整建设；**中小团队**（如5人以下）不必追求体系完备，可优先参考模块4的"轻量起步路径"，用现成平台快速建立最小闭环，再逐步扩展。

> **一句话界定**：Agent评测不是"跑个分"，而是建立"能真实反映价值、可重复、能驱动改进"的质量闭环。（出自本项目第一性原理分析，见 [附录：F/I阶段分析](../appendices/first-principles-and-insights.md)）

Agent评测体系化建设建立在六条不证自明的公理之上（详见附录），其中三条直接定义本模块的讨论基础：

- **公理 A1（价值锚定）**：评测必须锚定真实的价值需求，脱离业务价值的评测是无意义的分数游戏。
- **公理 A4（闭环驱动）**：评测的价值在于驱动改进，无迭代回路支撑的评测是静态的、会折旧的资产。
- **公理 A6（多源互证）**：单一评测信号易受偏差污染，可靠判断需多源交叉互证。

## 1.2 为什么需要体系化评测

### 1.2.1 从"模型评测"到"Agent评测"的范式跃迁

传统的模型评测（如MMLU、GSM8K）衡量的是模型的**知识储备与单步推理**能力。而Agent评测面对的是**端到端的任务执行**——涉及工具调用、多步规划、记忆管理、错误恢复。一个在单步基准上得分很高的模型，完全可能在真实Agent工作流中因工具调用错误、长程规划失误而表现糟糕。

> **关键事实**：AgentBench 覆盖操作系统、数据库、知识图谱、数字卡牌游戏、横向思考等 8 个真实交互环境，正是为了衡量端到端执行能力（F-006）。

### 1.2.2 评测的四大业务价值

| 价值 | 含义 | 通俗解释 |
|---|---|---|
| **质量保障** | 在发布前拦截缺陷，避免"带病上线" | 上线前先"过体检"，不合格就返工 |
| **迭代指引** | 用数据定位薄弱环节，指导优化方向 | 不是拍脑袋改，而是拿报告说"该改哪" |
| **风险控制** | 识别安全、合规、越权等底线风险 | 挡住会"闯祸"的操作，守住红线 |
| **信任建立** | 用可复现的证据向用户与合规方证明可靠性 | 让用户敢用的前提是"测过、可信" |

### 1.2.3 不评测的真实代价

不做体系化评测，团队往往陷入三种困境：**"感觉好用"**（依赖主观印象，无法量化）、**"分数虚高"**（采信单一分数，忽视数据污染与奖励黑客）、**"越改越坏"**（无回归评测，优化一处另一处退化却无感知）。这些代价的根因，正是G1/G2质量门识别出的"用错误的方式评测并采信了错误的结论"。

## 1.3 评测能力成熟度模型（0-5级）

为了帮助团队定位自身所处阶段，我们定义一个评测能力成熟度模型（Evaluation Maturity Model, EMM）。它从**目标锚定、指标完备、执行可复现、产出闭环**四个维度综合评估：

| 级别 | 名称 | 特征 | 典型表现 |
|---|---|---|---|
| **L0** | 无评测 | 完全靠感觉 | 上线靠"看起来不错"，事故靠人肉救火 |
| **L1** | 单点跑分 | 偶然跑一两个benchmark | 有分数无体系，跑完即弃，分数不可解释 |
| **L2** | 指标化评测 | 建立指标体系，重复执行 | 有指标、有脚本，但离线孤立、无业务锚定 |
| **L3** | 体系化评测 | 目标-指标-资产-流程齐全 | 有评测计划、数据集、执行管线、人工校准 |
| **L4** | 闭环化评测 | 评测驱动迭代，接入CI/CD | 每次变更自动回归，数据指导优化决策 |
| **L5** | 生产级评测 | 在线监控+持续治理 | 生产实时质量指标、告警、评测资产定期治理 |

> **使用建议**：先定位自己处于哪一级，再规划"跳一级"的改进路径。成熟度不是越高越好到极致——L3以上的投入需要匹配业务规模（呼应公理 A5 成本约束）。

## 1.4 四个最常见的认知误区

### 误区1："评测分数越高 = Agent越好"

**真相**：分数与真实价值之间存在系统性鸿沟。数据污染可致性能虚高 6%-40%（F-049）；奖励黑客指Agent学会"作弊式应试"而非真正完成任务（F-045）。高分可能只是"恰好对上了测试集"。

**对策**：任何分数，都要同时提供"过程可复现性"与"真实场景验证"两层证据，并结合业务价值解读。

### 误区2："LLM-as-Judge可以完全替代人工评测"

**真相**：LLM-as-Judge高效但存在4种固有偏差——位置偏差、冗长偏差、自我增强偏差、推理局限偏差（F-040）。完全依赖它会同时放大裁判偏差与成本。

> **澄清**："不能完全替代人工"指**不能放弃人工校准兜底**，而非"不能用自动化"。OpenAI、Similarweb 等大厂之所以大量使用 LLM-as-Judge（见模块5），正是因为遵循了"自动化跑量 + 人工抽检校准"的互补范式——这与本误区并不矛盾。

**对策**：自动化评测与人工校准是互补关系而非替代关系（F-027）。按固定比例人工抽检校准，并记录校准偏差率作为体系健康度。

### 误区3："评测是一次性活动，交付一份报告就完事"

**真相**：数据污染、评测漂移、环境变化会让评测资产随时间贬值（F-047/F-049）。评测是**持续的质量闭环**，而非一次性的跑分报告。

**对策**：将评测接入CI/CD流水线（F-026），定时审查并更新评测资产，建立生产监控反馈回路（F-029）。

### 误区4："指标越多就评测得越全面"

**真相**：指标过多会导致成本爆炸、注意力稀释，违背公理A5（成本约束）。没有北极星指标的指标体系，无法告诉你"到底好不好"。

**对策**：建立1-2个北极星指标，配合分层指标体系（核心指标+辅助指标），并明确每个指标的计算方法与参考阈值。

## 章节小结

本模块界定了Agent评测体系化建设的本质——**建立可信的价值判断与持续改进闭环**，而非"跑个分"。它连接了四大业务价值（质量保障、迭代指引、风险控制、信任建立），提供了定位自身的成熟度模型（0-5级），并剖析了四个最常见的认知误区。理解了"为什么"与"是什么"，下一页将进入**核心框架对比**，回答"用什么评测"。
