# seven-concepts-cmd 实操避坑指南

> 本指南基于一次真实任务（用 `seven-concepts-cmd` 产出《Agent评测方法论》Wiki 教程 + 知乎文章）的复盘提炼。不空谈理论，只讲"实操中真的会踩的坑"和"怎样避免"。

---

## 一、先判断：这事该不该用方法论编排？

方法论编排不是万能药。**第一步不是动手，而是判断场景**。用错场景，比不用更糟。

| 场景 | 该不该用 | 链路 |
|---|---|---|
| 里程碑复盘 / 总结 | ✅ 用 | R→I→E→C |
| 系统性知识 Wiki / 教程 / 方法论库 | ✅ 用 | R→F→I→E→V |
| 复杂问题根因分析 | ✅ 用 | I→F→V→C |
| 重构 / 拆分大文档 | ✅ 用 | I→F→A→V→C |
| 写便签、回邮件、随手记 | ❌ 别用 | 直接写 |
| 纯操作手册（按步骤即可） | ❌ 别用 | 直接写先例 |

> **本任务教训**：方法论编排适合"重知识资产"。我这次明知成本更高，仍选择走 R→F→I→E→V 全链路，换来的是"可追溯、可迁移、经得起质疑"。**如果只是随手记，别硬套——那是过度工程。**

## 二、五大高频坑（每个都真实踩过）

### 坑 1：跳过场景识别，直接全链路执行

**现象**：不管任务是轻是重，都硬走完 R→I→E→C→A→F→V 七个概念。
**后果**：轻量任务被拖慢，产出过度设计。
**正确做法**：先判定 5 种场景之一，按决策树选 2-7 个概念。轻量场景 2-3 个概念即可。

### 坑 2：质量门不通过还硬推进（GIGO）

**现象**：事实清单还没厘清（G1 没过），就急着分析原因。
**后果**：基于错误事实的错误洞察 → 不可复用的伪模式。垃圾进垃圾出。
**正确做法**：G1-G4 是硬关卡。不过就**返回当前阶段修复**，不推进到下一步。

### 坑 3：V 在 F 之前执行

**现象**：还没做第一性原理推导，就先对抗审查。
**后果**：攻击的是旧方案而非新方案，无法验证 F 推导的正确性。
**正确做法**：**先有方案，再攻击**。V 必须在 F 之后。

### 坑 4：表演式对抗审查

**现象**：V 阶段输出"写得很棒，没有问题"之类的客套话。
**后果**：质量门虚设，缺陷漏到读者/用户面前。
**正确做法**：审查意见 ≥5 条且具体，至少采纳 2 条做实质修订。**真挑毛病、真修改。**

> **本任务教训**：我给知乎文章做对抗审查时，故意找"会误导读者"的点——结果真找到 4 条 P1 意见（七概念 vs 五概念链路没讲清、缺指令环境背景、缺成品快照、工具依赖性）。这 4 条如果不改，文章对读者是有歧义的。

### 坑 5：Windows 中文乱码 / 原子提交混多个变更

**现象**：PowerShell 直接 `git commit -m "中文"` 乱码；一个提交混进重构+新功能+文档。
**后果**：提交信息不可读、无法回滚/cherry-pick。
**正确做法**：用 UTF-8 方案（git-commit-utf8.py 或 `git commit -F`）；三查暂存法，**单一职责**，一次只做一件事。

## 三、质量门实战检查清单

每一道门都是"质量拦截"，别放水：

- [ ] **G1（R 产出）**：事实 ≥20 条；无"因为/所以/导致"因果词；可验证、可追溯、无主观评价。
- [ ] **G2（I 产出）**：洞察 ≥3 条；每条含「陈述+证据（F-xxx）+反常识+行动」四元组；有反常识点，不是"正确的废话"。
- [ ] **G3（E 产出）**：模式含「触发场景+核心步骤+反模式（≥3）+检验标准+迁移示例」；多案例支撑或标注"单案例待验证"。
- [ ] **G4（C 产出）**：行动项单一职责、可独立验证、有 Owner、有时间节点、可回滚。
- [ ] **V 门**：四视角覆盖（魔鬼/新人/老板/未来）；意见 ≥5 条；采纳 ≥2 条；**F 之后 V 不可跳过**。

> **核心心法**：没有质量门，方法论编排就退化成了"聊天"。门的作用是防止"垃圾进、垃圾出"——这道流水线，每一关都不能放水。

## 四、本次任务的真实踩坑复盘（供对照）

| 阶段 | 真实踩的坑 | 怎么避免 |
|---|---|---|
| R 事实清单 | 事实清单过长，容易混入"观点" | 强制 G1：删掉所有因果词，只留客观陈述 |
| F 公理 | 公理与前文事实的对齐容易脱节 | 每条公理回引 F-xxx 事实编号，形成证据链 |
| I 洞察 | 容易产出"评测很重要"式正确的废话 | G2 强制四元组，逼出反常识点和具体行动 |
| E 撰写 | 深度与可读性失衡（术语艰深） | "三层表达"：通俗解释 + 表格/图 + 深度层 |
| A 原子化 | 交叉引用断链、frontmatter 不统一 | 用 finalize-atomization 脚本 + check-links 跑一遍 |
| V 审查 | 容易"自我表扬"走过场 | 四视角真挑刺，记录修订前后对比，至少改 2 条 |

## 五、一分钟快速自查表

开始前问自己：
1. 这任务属于哪类场景？该用几个概念？
2. 我是否已经有干净的"事实清单"（G1）？
3. 我的"洞察"有没有反常识点和具体行动（G2）？
4. 我是否做过对抗审查，且真的改了东西（V）？
5. 交付前是否跑过链接/格式/命名检查（G4）？

> 如果 5 个问题都能干脆地回答"是"，那这次方法论编排大概率是合格的。
