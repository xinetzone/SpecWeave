# 用方法论编排，而不是靠灵感：我如何用 seven-concepts-cmd 产出了一整部 Wiki 教程

> 复盘一次"方法论驱动创作"的真实过程：不是靠灵感、不是靠经验，而是用一套可编排的方法论链路，稳定地产出一部有据可依、有洞察深度、经得起对抗检验的 Wiki 教程。

---

## 一、先说一个反直觉的事实

我刚刚完成了一部[《Agent评测方法论》Wiki 教程](README.md)，包含六大模块、53 项关键指标、8 个行业案例、22 条 FAQ，外加一份完整的创作过程记录和一篇面向知乎的科普文章。

但我要坦诚地说：**这部教程不是"写"出来的，而是"编排"出来的。**

听起来像绕口令，但这是句大实话。区别在于——

- 靠灵感写：想到哪写到哪，结构凭感觉，内容靠记忆，写完很难说清"为什么这么设计"。
- 靠方法论编排：先有事实、再有本质、再有洞察、然后才动笔，每一步有产出、有质量门把关，**每一步都能回答"为什么"**。

两者的差别，就像"凭手感做菜"和"按菜谱加复用工序"——前者可能偶尔惊艳，但不可复制；后者也许不那么惊艳，但**稳定、可复现、可迁移**。

而让我实现"编排式创作"的，正是一条简单到极致的指令：

```
Use Skill: seven-concepts-cmd
```

> 补充一句背景：这是我（作为 AI 协作者）在 AI 编程工具 Trae 里执行的一条指令，用来唤出"方法论编排"技能。如果你没有这个工具环境，**手动按 R-I-E-C-A-F-V 的步骤走，效果是一样的**——技能只是把方法论做成了可调用的流程，方法论本身不依赖任何工具。

在往下读之前，先给你看一眼"成品长什么样"，免得你觉得我在空谈。这部 Wiki 教程的目录骨架是这样的：

| 模块 | 内容 | 附图 |
|---|---|---|
| 模块1 | 方法论概述：本质、价值、成熟度模型、4个误区 | 入门 |
| 模块2 | 核心框架对比：HELM/MT-Bench/AgentBench 等6大框架 | 进阶 |
| 模块3 | 关键指标体系：能力/效率/安全/人本，53项指标 | 进阶 |
| 模块4 | 八阶段实施步骤 + 0-8周落地清单 | 实践 |
| 模块5 | 8个行业案例（OpenAI/LangChain/Nubank 等） | 实践 |
| 模块6 | 常见问题解答：22条 FAQ | 参考 |

外加 4 份附录（63条事实清单、F/I分析、创作过程记录、对抗审查记录）和 1 份术语表。下面，我就讲这套"骨架"是怎么被一步步编排出来的。

这篇文章，就是复盘这次"方法论编排"的完整过程——它到底做了什么、为什么有效、以及它教会了我什么。

## 二、先给"方法论编排"祛个魅

别被"方法论编排"四个字吓到。它背后是一套叫 **R-I-E-C-A-F-V** 的七概念方法论。一次只记一个字母即可：

| 缩写 | 概念 | 一句话人话 |
|:---:|---|---|
| R | Retrospective 复盘 | 先把事实捞干净，再谈观点 |
| I | Insight 洞察 | 找到问题的根，而不是停留在表面 |
| E | Extraction 萃取 | 把这次的经验，提炼成下次能用的方法 |
| C | Atomic Commit 原子提交 | 一次只交付一件事，可回滚、可验证 |
| A | Atomization 原子化 | 大块头拆成小单元，别想一次吞下 |
| F | First Principles 第一性原理 | 剥掉默认假设，从本质重新搭 |
| V | Adversarial Review 对抗审查 | 自己挑自己的毛病，找反例 |

这七个字母，不是七个孤立的技巧，而是**一条有顺序的链路**。正如烹饪里"先备菜、再下锅、后调味"的顺序不能乱，七概念的执行顺序也不能乱：

- **R 必须在 I 之前**——事实没厘清就分析原因，会得到基于错误事实的错误洞察。
- **I 必须在 E 之前**——没想清"为什么"就总结"怎么做"，是经验主义。
- **V 必须在 F 之后**——先有方案再攻击，不能攻击一个不存在的东西。
- **C 是所有变更的终点**——有产出，最终都要原子化交付。

而 `seven-concepts-cmd` 这个"方法论编排"技能的价值，恰恰在于**它替你管住了这条链路**——自动识别场景、选择链路、串联质量门。你不需要记七个概念，只需要说"按七概念走"，它就知道该先做什么、后做什么、哪些环节不能省。

## 三、核心：一部 Wiki 教程是怎么被"编排"出来的

下面是我这次任务的真实过程。我把它拆成五个阶段，对应五概念链路 **R → F → I → E → V**。你会发现，**动笔（E）其实是整个流程里很靠后的一步**——前面四步，都是在为"写"做地基。

> 小提示：七概念里还有 **C（原子提交）** 和 **A（原子化）**，它们发生在交付阶段——我们把教程拆成原子文件、逐个原子提交，是为了保证可回滚、可验证。这次核心创作走的是 R→F→I→E→V 五步，A 和 C 在下半段收尾。

### 阶段 1｜R（复盘）：先有 63 条事实，再有观点

很多人写教程，第一步就动笔。方法论编排不这么干——第一步是**采集事实**。

我围绕"Agent评测体系化建设方法论"这个主题，系统收集了 25 个权威来源（学术论文、官方文档、企业技术博客），按"框架→指标→流程→案例→挑战→数据集"六类整理，最终沉淀出一份 **63 条客观事实清单**，每条编号（F-001 到 F-063）且可追溯到原始出处。

这一阶段有**一道硬性质量门 G1**：

> 事实清单里不许出现"因为""所以""导致"这类因果词，只许客观描述。

为什么这么苛刻？因为"事实"和"观点"一旦混在一起，你就分不清哪些是客观依据、哪些是主观推断——后面所有的洞察都会建立在"沙子上"。

**R 阶段教会我的**：好的创作，先做事实的"搬运工"，再做观点的"建筑师"。顺序不能反。

### 阶段 2｜F（第一性原理）：为什么是六大模块？不是拍脑袋

有了事实，下一步不是动笔，而是**从本质重构框架**。

Agent 评测的表面问题是"怎么打分、怎么跑 benchmark"，但本质问题其实是"**如何可信地判断 Agent 是否真正满足用户与业务的价值观需求**"。这个界定本身就颠覆了"跑个分"的直觉。

然后，我把评测体系拆解到不可再分的最小单元——评测目标、测试用例、评分标准、执行器、分析器、迭代回路——并从中提炼出 **6 条不证自明的公理**（价值锚定、单一事实源、能力可测、闭环驱动、成本约束、多源互证）。

关键来了：**Wiki 的六大模块，不是拍脑袋定的，而是从这 6 条公理自下而上"推导"出来的**。

- 方法论概述 ← 公理"价值锚定 / 单一事实源"
- 核心框架对比 ← 公理"行为测量的载体选择"
- 关键指标 ← 公理"度量与取舍"
- 实施步骤 ← 公理"闭环驱动 / 成本约束"
- 行业案例 ← 公理"价值锚定实证"
- FAQ ← 公理"避坑与落地"

**F 阶段教会我的**：一个结构如果能从本质推导出来，它就是必然的、可复用的；如果只是凭感觉排列，换个主题就废了。这也是为什么这套 Wiki 的骨架能迁移到任何主题。

### 阶段 3｜I（洞察）：「评测很重要」是句正确的废话

框架搭好了，但如果只写"评测很重要、评测要系统化"，读者会立刻关掉页面——因为这是**正确的废话**。

要避免废话，方法论编排给的是一道**强制四元组**：每条洞察必须包含「陈述 + 证据 + 反常识 + 行动」四件套，缺一不可。

- **陈述**：清晰的结论性判断
- **证据**：回引 R 阶段的事实编号（F-xxx），可追溯
- **反常识**：它挑战了什么默认假设
- **行动**：具体可执行的建议

比如我提炼的洞察之一是：**"LLM-as-Judge 不能完全替代人工，但也不能全盘否定"**——表面上自相矛盾，实则挑战了"AI 打分=省人工"和"AI 打分=不可信"两种极端默认假设。既有证据（F-xxx），有反常识点，也有"部分使用+人工校准"的具体行动。

**I 阶段教会我的**：洞察的质量，取决于有没有"反常识点"。一句"评测很重要"没有信息量，一句"评测分数越高≠产品越好，因为可能被奖励黑客钻空子"才有价值。

### 阶段 4｜E（内容撰写）：动笔，但每一步都有据可查

终于到动笔了。但此前的 R/F/I 三阶段，早已让"写"变成一件有据可依的事：

- **每个关键论点回引事实编号**（F-xxx），形成"论点→证据"的可追溯链条。
- 采用**"三层表达"**平衡深度与可读性：专业术语附通俗解释（评测指标=考试分数）、用表格和 Mermaid 图降低理解成本、保留公式与参考阈值满足专业读者。
- 模块 3 因覆盖 50+ 指标，拆分为"总览 + 能力 + 效率 + 安全 + 人本与商业"5 个文件，避免单文件过大。

**E 阶段教会我的**：当观点都有事实支撑、结构都是推导出来的时候，"写"反而成了最轻松的一步——你只是在把已经想清楚的东西，翻译成读者能懂的语言。

### 阶段 5｜V（对抗审查）：自己挑自己的毛病

写完 *不是* 结束。方法论编排的最后一步，是**对抗审查**——用四个视角主动攻击自己的产出：

- 🔴 **魔鬼代言人**：找反例、找幸存者偏差。结果真的找到了——8 个案例全是成功的大厂案例，是幸存者偏差，会误导中小团队。
- 🟢 **新人**：找看不懂的地方、找"然后呢"。发现全篇缺一个"从零到一"的最小评测示例。
- 🟠 **老板**：问 ROI、问见效时间。发现没有量化投入产出，老板无法判断值不值得做。
- 🔵 **未来**：问会不会过时。

最终收集了 **17 条意见**，按 P0-P3 分级，**采纳了 5 条**做了实质性修订（保留 5 条修订前后对比），比如补了"轻量起步路径"、补了"最小评测 Hello World"、澄清了"LLM-as-Judge 部分使用 vs 完全替代"。

**V 阶段教会我的**：**表演式审查是自欺欺人**。如果对抗审查只输出"写得很好"，那这道门就形同虚设。真正有效的对抗审查，是自己真的去挑毛病、并真的去改。

## 四、五道质量门：为什么"没有门"的复盘只是聊天

这套方法论最容易被低估、却最关键的部分，是它的**质量门（G1-G4 + V 门）**。

| 门 | 卡在哪 | 一句话 |
|:---:|---|---|
| G1 | 事实无因果词 | 事实不干净，后面全崩 |
| G2 | 洞察四元组完整 | 没反常识的洞察是废话 |
| G3 | 模式可迁移 | 不能复用的模式是自嗨 |
| G4 | 行动项原子化 | 不能独立交付=没闭环 |
| V 门 | 对抗审查有实质 | 不真挑刺=走过场 |

**方法论编排与随手分析的区别，就在于这些门。** 没有质量门，"复盘"就变成聊天，"洞察"就变成吐槽，"萃取"就变成总结。每一道门都是前一阶段产出的"质量拦截"，防止**垃圾进垃圾出（GIGO）**：

- 事实没厘清就分析 → 基于错误事实的错误洞察；
- 洞察不完整就萃取 → 沉淀出不可复用的伪模式；
- 没对抗审查就交付 → 缺陷漏到读者面前。

这次的 Wiki 教程能实现"63 条事实 → 6 条公理 → 3 条洞察 → 六大模块 → 经 17 条审查意见检验"，靠的就是这道流水线上每一关都不放水。

## 五、冷静一下：这套方法不是万能的

上面听起来很美好，但我要诚实地说几个**边界**——这也是对抗审查让我想明白的：

1. **它不是"一键生成"的魔法**。`seven-concepts-cmd` 管的是"流程有章法"，不是"内容自动长出来"。事实要自己收集、本质要自己想、洞察要自己提炼。工具编排的是节奏，不是替你思考。
2. **轻量任务不需要走全链路**。写一张便签、回复一封邮件，不需要 R→F→I→E→V 五阶段。这套链路适合**系统性、重专业性、要复用的知识产出**（教程、方法论库、研究报告），不适合随手记。
3. **它治不了"没想清楚"**。如果对主题本身没有积累，方法论只能帮你把"没想清楚"暴露得更早，而不能替你"想清楚"。
4. **有真实的成本**。完整走一遍五阶段 + 五道质量门，比"直接写"慢。但换来的，是内容可追溯、结构可迁移、经得起质疑——**这个投入在"重知识资产"上是值得的**。
5. **它不依赖特定工具**。seven-concepts-cmd 只是把方法论做成了技能；没有它，你用一张表格建事实清单、用四格表写洞察、请三位同事当"魔鬼代言人"，走的仍是同一条路。工具让流程更顺，但方法论本身是"免费的"。

## 六、创作经验与心得：三条最想分享的体会

复盘完整个过程，抛开方法论框架本身，我提炼出三条**最想对做内容的人说**的心得：

### 心得一：先攒够"事实子弹"，再扣动"观点扳机"

我见过太多创作者（包括曾经的我自己）——观点很精彩，但你一问"依据呢？"，就答不上来。这次的教训是：**让观点慢一点，让事实先到位**。63 条事实清单看起来笨拙，但它让后面所有的"我认为"都有了"据我所查"的底气。

### 心得二：反模式比正确做法更有价值

对抗审查阶段，最有价值的产出不是"哪些地方写得好"，而是"哪里差点误导读者"。**幸存者偏差、LLM-as-Judge 的矛盾、缺最小示例**——这些"差点犯错"的地方，比十句表扬更能提升内容质量。做内容，要主动找"哪里会误导人"，而不是找"哪里很棒"。

### 心得三：过程记录，是内容创作的"第二层资产"

这次我额外产出了一份[完整的创作过程记录](appendices/creation-process-record.md)——每个阶段的思考过程、决策依据、挑战与解决。**这份记录本身的价值，不亚于教程正文**：

- 它让读者能"跟着思路走"，而不是只看结论；
- 它让这个方法可被复盘、可被萃取成模式；
- 它让我下次做类似的事，有据可依，而不是从零摸索。

做事的过程中，顺手记录"为什么这么做"，是回报率极高的投资。

## 七、结语：把"创作"从玄学变成工程

回到开头那个反直觉的事实：这部 Wiki 教程不是"写"出来的，而是"编排"出来的。

方法论编排给到我的，不是"文采"，而是**确定性**——一种"我知道这一步为什么这么走、下一步该做什么、做完怎么验证"的确定感。它把"创作"这件看起来靠灵感、靠状态、靠运气的玄学事，变成了一条**有事实、有本质、有洞察、有质量门**的工程流水线。

如果你也经常：
- 写出来的内容"感觉哪不对"，却说不出哪不对；
- 明明有积累，却组织不出有深度的结构；
- 交付的东西自己都不敢让它接受质疑；

那么，下次不妨试试一条简单的指令：

```
Use Skill: seven-concepts-cmd
```

然后，让方法论替你把"创作"的节奏管住。剩下的，交给你的积累与表达。

毕竟，**灵感决定上限，方法论决定下限。真正顶尖的创作者，是把方法论内化成肌肉记忆——让灵感在稳定的轨道上飞。**
