# V阶段：四视角对抗审查与内容修订

> 本文件是七概念方法论 **V（对抗审查）阶段** 的产出物。对 Wiki 教程全部内容（模块1-6及附录）进行四视角对抗审查，汇总意见并按 P0-P3 分级，采纳 ≥3 条进行实质性修订，记录修订前后对比。通过 V 门。

---

## 一、审查目标与范围

- **审查对象**：模块1-6 全部正文 + 附录（事实清单/F-I分析/创作记录）+ 术语表。
- **审查视角**：🔴魔鬼代言人、🟢新人、🟠老板、🔵未来。
- **审查目标**：暴露逻辑漏洞、认知盲区、可读性障碍、商业落地风险、时效性风险。

---

## 二、🔴 魔鬼代言人视角（逻辑攻击）

> 目标：挑刺、找反例、质疑因果关系、找幸存者偏差。

| 编号 | 攻击点 | 具体问题 | 分级 |
|---|---|---|---|
| D1 | 幸存者偏差 | 模块5的8个案例全部是"成功案例"，且都是大厂（OpenAI/AWS/IBM）。没有失败案例，读者会被误导以为"大厂范式=值得复制"。中小团队直接照搬的成本与可行性存疑。 | P1 |
| D2 | 因果倒置 | 模块1误区2说"LLM-as-Judge不能完全替代人工"，但模块5 cases中 OpenAI/Similarweb 都大量用 LLM-as-Judge。表面看自相矛盾——需要澄清"完全替代"与"部分使用"的区别，否则读者困惑。 | P1 |
| D3 | 阈值缺乏依据 | 各指标"参考阈值"（如任务完成率≥90%、幻觉率≤5%）缺少出处与统计依据。这些数字是经验值还是权威来源？若只是臆测，会误导读者当"标准"用。 | P2 |
| D4 | 过度概括 | 模块2对比表把"HELM=模型选型、AgentBench=泛化"等标签化，但框架边界实际模糊（如 AgentBench 也可测对话）。标签化可能限制读者理解框架的多面性。 | P2 |
| D5 | 公理自明性存疑 | 公理 A3（能力可测）声称"一切评测归根结底是对行为的测量"，但存在不可直接测量的能力（如创造性、长期策略），该公理是否成立？ | P3 |

## 三、🟢 新人视角（可读性攻击）

> 目标：找看不懂的术语、找"然后呢"、要求 Hello World 示例。

| 编号 | 攻击点 | 具体问题 | 分级 |
|---|---|---|---|
| N1 | 术语门槛 | 模块3.6 安全指标出现"提示注入""越狱""供应链攻击"等术语，新人读者可能看不懂，缺通俗解释。 | P2 |
| N2 | "然后呢"断层 | 模块3总览讲了北极星指标，但没给"我拿到指标后具体怎么建看板/跑起来"的下一步指引，读者读到感觉"知道了但不会做"。 | P2 |
| N3 | 缺最小示例 | 全篇没有"构建一个最小评测（如评测一个客服Agent）"的端到端 Hello World 示例，新人难以建立"从零到一"的完整认知。 | P1 |
| N4 | 术语表跳转 | 正文引用术语（如"奖励黑客"）没有链接到术语表，读者需手动去 glossary 找，体验割裂。 | P3 |

## 四、🟠 老板视角（ROI攻击）

> 目标：问 ROI、问企业能否用、问风险、问什么时候见效。

| 编号 | 攻击点 | 具体问题 | 分级 |
|---|---|---|---|
| B1 | 投入产出不清 | 八阶段流程看起来投入大（数据集、环境、人工校准、监控），但没量化"投入多少人力/时间/成本"与"收益多少"。老板无法判断是否值得做。 | P1 |
| B2 | 见效时间模糊 | 模块4的0-8周清单给了时间线，但没说"第几周能看到可量化的收益信号"，老板缺少阶段性的信心锚点。 | P2 |
| B3 | 风险缺失 | 没提"评测体系建设失败/半途而废"的风险场景（如团队建了体系但不用、数据污染导致误判决策），低估了落地的组织阻力。 | P2 |
| B4 | 中小团队适用性 | 全篇以成熟团队/大厂为隐含对象，没有明确"5人以下小团队/预算有限"的轻量起步路径。 | P1 |

## 五、🔵 未来视角（时效性/二阶效应攻击）

> 目标：问会不会过时、问二阶效应、问缺失的拼图。

| 编号 | 攻击点 | 具体问题 | 分级 |
|---|---|---|---|
| F1 | 框架时效性 | 模块2的6大框架（2022-2024）到2026年部分可能过时或更新，未说明"如何跟踪框架演进"。 | P2 |
| F2 | 二阶效应 | 未讨论"评测体系被滥用"的二阶效应（如团队追求指标分而忽视真实价值、评测数据被游戏化），与公理A1的初衷可能背道而驰。 | P2 |
| F3 | 缺失拼图 | 未覆盖"多模态Agent评测""具身/实时交互Agent评测"等新兴方向，知识库可能快速老化。 | P3 |
| F4 | 评测资产治理 | 提到数据污染/评测漂移但未给出"评测资产定期治理的运维机制"（如版本、退役、更新节奏）。 | P2 |

## 七、采纳的修订（≥3条，含修订前后对比）

根据"🔴critical全修、🟡≥30%修"原则，本次**采纳 5 条 P1 意见**进行实质性修订：

### 修订1（采纳 D1）：补充"中小团队落地"与轻量路径

- **修订前**：模块4只有通用八阶段与8周清单，隐含对象是大团队。
- **修订后**：在模块4增设"轻量起步路径"小节——建议5人以下团队先垂直跑通"规划→执行→校准→分析"最小闭环，用现成平台（LangSmith等）而非自建，控制首期投入。
- **位置**：[模块4 八阶段实施步骤](../04-implementation/04-implementation-overview.md)。

### 修订2（采纳 D2）：澄清"LLM-as-Judge 部分使用 vs 完全替代"

- **修订前**：模块1误区2仅说"LLM-as-Judge不能完全替代人工"，与模块5大厂大量使用LLM-Judge看似矛盾。
- **修订后**：在误区2补充说明——"不能完全替代"指**不能放弃人工校准兜底**，而非"不能用自动化"；大厂做法正是"自动化跑量+人工抽检校准"，与本误区并非矛盾。
- **位置**：[模块1 方法论概述](../01-overview/01-methodology-overview.md) 误区2。

### 修订3（采纳 N3）：补一个端到端最小评测示例

- **修订前**：全篇无"从零到一构建最小评测"的完整示例，新人缺乏整体认知。
- **修订后**：在模块4新增"最小评测Hello World"——以"客服Agent评测"为例，走通"定义任务→建5个用例→跑LLM-Judge→人工抽检→出报告"的完整链路。
- **位置**：[模块4 八阶段实施步骤](../04-implementation/04-implementation-overview.md)。

### 修订4（采纳 B1）：补充投入产出与收益信号

- **修订前**：八阶段只讲做法，未量化投入与收益。
- **修订后**：在模块4落地清单中标注"每阶段的人力/时间投入量级"与"可量化收益信号"（如第5周产出首份评测报告、第8周接入CI后每次变更自动回归）。
- **位置**：[模块4 八阶段实施步骤](../04-implementation/04-implementation-overview.md)。

### 修订5（采纳 B4）：明确"中小团队"定位

- **修订前**：教程未明确目标团队规模。
- **修订后**：在模块1开篇"目标读者"处补充说明——本教程同时适用于中小团队，提供轻量起步路径（呼应修订1）。
- **位置**：[模块1 方法论概述](../01-overview/01-methodology-overview.md)。

## 九、审核修订阶段的挑战与取舍

- **挑战1：不同视角意见冲突**。魔鬼代言人（D1）认为"全是成功案例是幸存者偏差"，未来视角（F2）认为"应讨论评测被滥用"——两者都指向"内容偏正面"。取舍：优先采纳魔鬼代言人与老板视角（D1/B1/B4），因为它们直接关系到"读者是否被误导"与"是否可落地"，而未来视角的 P2/P3 意见记录为迭代 TODO。
- **挑战2：修订范围控制的度**。17条意见若全采纳会导致内容膨胀、偏离主线。取舍：遵循"P0全修、P1采纳、P2部分采纳、P3记录"的分级原则，只对 5 条 P1 做实质性修订，避免过度修改破坏原有结构。
- **挑战3：如何证明修订真实有效而非表演式**。取舍：每条修订都记录"修订前/修订后/位置"三要素，确保可追溯、可验证，而非笼统说"已改进"。
