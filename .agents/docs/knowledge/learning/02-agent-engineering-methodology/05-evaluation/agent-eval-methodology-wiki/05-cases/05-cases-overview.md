# 模块5：8个行业案例分析

> **方法论视角**：本模块按"背景/做法/成果/经验教训/可复用要点"五要素解析 8 个企业案例。若需按场景视角（Coding Agent/RAG Agent/多工具/多Agent 协作）阅读评测实践与反模式，请参阅 [工程手册 · 第7章 行业实践案例](../../agent-evaluation-wiki/07-industry-practices.md)。

> 本模块通过 8 个真实企业案例，展示 Agent 评测方法论在不同领域、不同场景的落地形态（基础事实见 F-030~F-037）。每个案例按"背景/做法/成果/方法论映射/反模式/可复用要点"六要素解析，其中**方法论映射**将案例回映到公理体系（A1-A6）、四维指标与八阶段，**反模式**提炼可规避的落地陷阱，帮助读者提炼适用于自身场景的做法。

## 5.1 OpenAI：AutoEval 自动化评测管线

- **背景**：OpenAI 需要大规模评测其产品级 Agent，在自动化效率与人工准确性之间取得平衡。
- **做法**：自建 AutoEval 评测管线，将 LLM-as-Judge 与人工抽检结合（F-030）。评测管线模式在 2024 年官方博客《How we evaluate our agents》公开（F-007）。
- **成果**：形成可落地、可复现的产品级评测范式（F-007），成为业界评测工程化的参考样板。
- **方法论映射**：核心是**公理 A6（多源互证）**——自动化打分与人工抽检双信号交汇，避免单一 LLM 裁判偏差（F-040）；同时呼应**公理 A5（成本约束）**，用自动化跑量控制成本、人工校准保准确；落在八阶段"自动化执行→人工校准"（阶段④⑤）。
- **反模式**：若完全信任自动化打分而省略人工校准，会同时放大 LLM-as-Judge 的 4 种偏差（位置/冗长/自我增强/推理局限，F-040），得到"看似高分实则失真"的结论——这正是公理 A2（单一事实源）所否定的不可信依据。
- **可复用要点**：评测管线工程化 = 自动化跑量 + 人工兜底校准。适用于有规模评测需求、且能承担一定人工抽检成本的团队；校准比例需结合 A5 成本约束动态设定。

## 5.2 LangChain：LangSmith 评测与追溯一体化

- **背景**：LangChain 需要为其 Agent 框架使用者提供评测能力，降低评测门槛。
- **做法**：LangSmith 平台提供评测与追溯（Tracing）一体化功能，支持数据集管理与回归测试（F-031）。
- **成果**：评测与可观测性打通，用户可追踪每次执行的完整轨迹，实现"测到什么"与"为什么"可对照。
- **方法论映射**：核心是**公理 A2（单一事实源）**——将评测结果与执行轨迹（过程事实）关联，保证判断可追溯、可复现；同时呼应**公理 A4（闭环驱动）**，回归测试实则是把评测嵌入迭代回路，支撑持续改进；落在八阶段"自动化执行→数据分析"（阶段④⑥）。
- **反模式**：若评测与执行过程割裂、只记录最终分数而丢弃轨迹，则无法定位失败根因——这正是公理 A2 否定的"不可追溯判断"，也对应 F-050 揭示的长程误差累积问题（缺过程数据无法分步归因）。
- **可复用要点**：评测数据与执行轨迹关联，便于归因分析。适用于需要诊断"Agent 为何失败"的复杂任务场景；追溯设计的核心是"记录什么"要有 schema，避免数据爆炸违背 A5 成本约束。

## 5.3 Similarweb：数据提取 Agent 的人工校准

- **背景**：Similarweb 用 Agent 做数据提取，输出用于下游分析，需保证数据准确性。
- **做法**：使用 LLM-as-Judge 评测数据提取 Agent，并通过人工校准纠偏（F-032）。
- **成果**：兼顾自动化效率与数据准确性，避免纯自动化评测带来的质量偏差。
- **方法论映射**：核心是**公理 A6（多源互证）**——LLM 裁判自动评分 + 人工抽检校准双源交叉；同时呼应**公理 A2**，数据型任务以"数据是否正确"这一客观事实为锚，而非主观印象；落在八阶段"自动化执行→人工校准"（阶段④⑤）。
- **反模式**：内容提取类任务若完全依赖 LLM 裁判，会放大推理局限偏差（F-040）——LLM 对"提取结果是否与源数据一致"的判断本身可能出错，导致错误数据被误判为正确。
- **可复用要点**：数据型 Agent 评测 = LLM 自动评分 + 人工抽检校准。适用于以数据准确性为核心指标的场景；人工校准的抽样应聚焦高风险数据（如金额、日期、实体），而非均匀抽样，以提升校准信息增益。

## 5.4 Nubank：金融场景的安全与合规

- **背景**：Nubank 是金融科技公司，Agent 涉及资金流转与敏感数据，风险极高。
- **做法**：在金融场景强调安全与合规 KPI，执行严格权限控制与审计（F-033）。
- **成果**：守住金融底线，满足强监管要求，避免因安全疏漏造成资金与合规损失。
- **方法论映射**：核心是**公理 A1（价值锚定）**——评测目标直接锚定"资金与隐私安全"这一最高价值需求；安全维度采用完整分层框架（如 IETF 4 层 55 项，F-015），对应四维指标中的**安全维度**；落在八阶段"评测规划"（阶段①）即把安全设为目标基线。
- **反模式**：若把安全当成"加分项"而非"一票否决底线"，会在资金敏感操作上出现漏检——这正是公理 A1 否定的"脱离核心价值的评测"，安全指标权重过低会让 Agent 在高压场景下失控。
- **可复用要点**：强监管领域按完整安全框架评测，安全是一票否决项。适用于金融/政务/医疗等受监管场景；落地时需将安全指标接入上线门禁，形成硬性拦截而非事后复盘。

## 5.5 AWS：Motorway 的 Bedrock AgentCore 监控

- **背景**：AWS 需要为云上 Agent 提供从开发到生产的评测与监控能力。
- **做法**：使用 Bedrock AgentCore 进行评测与监控（F-034），将评测结果接入生产告警。
- **成果**：云原生环境下的评测与生产监控一体化，形成在线质量闭环。
- **方法论映射**：核心是**公理 A4（闭环驱动）**——评测与生产监控打通，让评测信号持续驱动线上改进；同时呼应**公理 A3（能力可测）**，生产环境的真实行为是能力测量的最终载体；落在八阶段"生产监控"（阶段⑧，闭环终点）。
- **反模式**：若评测只在离线环境进行、不与生产监控打通，会因环境/用户/模型漂移导致离线结论失真——正对应 F-029 揭示的"生产监控是评测闭环终点"；只做离线评测而忽略在线反馈，会让评测资产随时间贬值（对应洞察 3）。
- **可复用要点**：生产监控是评测闭环的终点。适用于已上线、需持续保障质量的 Agent；落地时设定质量阈值告警，将线上异常自动回流为待复评测用例，形成"A4 闭环驱动"的自增强回路。

## 5.6 JPMorgan：金融数据 Agent 的准确性与可追溯

- **背景**：JPMorgan 金融数据 Agent 处理高价值数据，容错率极低，错误代价高昂。
- **做法**：评测强调准确可靠与可追溯，设置高精度阈值与审计日志（F-035）。
- **成果**：满足金融级准确性与审计要求，为每次输出提供可追责的依据。
- **方法论映射**：核心是**公理 A2（单一事实源）**——高精度阈值保证"判断基于客观事实"，审计日志保证"判断可追溯、可复现"；同时呼应**公理 A1（价值锚定）**，容错率极低是价值需求的直接体现；落在八阶段"评测规划→数据分析"（阶段①⑥）。
- **反模式**：若为追求通过率而调低精度阈值，或不做审计追溯，会埋下"高价值错误"隐患——这正是公理 A2 否定的不可靠依据；金融场景中不可追溯的输出在审计时无法自证，代价远超通过率收益。
- **可复用要点**：金融数据评测 = 高准确率阈值 + 全链路可追溯。适用于容错率极低、需审计追责的高价值场景；落地时精度阈值应基于业务风险设定，而非凭经验随意取值。

## 5.7 Harvey：法律 AI 的专业正确性复核

- **背景**：Harvey 面向法律行业，其输出直接影响法律决策，需专业正确。
- **做法**：评测强调专业正确性，由人工律师复核（F-036），而非仅靠自动化指标。
- **成果**：守住法律专业性与合规底线，提升客户对 AI 输出的信任度。
- **方法论映射**：核心是**公理 A6（多源互证）**——自动化初筛 + 领域专家复核双源交叉，弥补 LLM 裁判在专业判断上的局限；同时呼应**公理 A1（价值锚定）**，专业正确性直接锚定法律价值需求；对应四维指标中的**能力维度（专业正确性）**与**人本维度（专家信任）**；落在八阶段"人工校准"（阶段⑤）。
- **反模式**：专业领域若完全自动化评测、无领域专家把关，会放大 LLM 裁判的推理局限偏差（F-040），把"看似专业实则错误"的输出判为正确——涉及法律/医疗等专业领域时，错误代价极高。
- **可复用要点**：专业领域评测 = 自动化初筛 + 领域专家复核。适用于法律/医疗/金融等强专业领域；落地时专家复核比例需结合 A5 成本约束与风险等级分层设定（高风险输出全量复核、低风险抽样）。

## 5.8 IBM：JudgeIt 自动化多维度评测平台

- **背景**：IBM 需要规模化评测各类 Agent，分散评测导致能力无法沉淀复用。
- **做法**：自研 JudgeIt 评测平台，实现自动化多维度评测（F-037），统一评测基础设施。
- **成果**：企业级评测基础设施，支持多场景复用，评测资产沉淀为组织能力。
- **方法论映射**：核心是**公理 A5（成本约束）**——平台化通过规模化摊薄单次评测成本；同时呼应**公理 A4（闭环驱动）**，平台将评测流程标准化，便于持续迭代与回归；对应四维指标中的**效率维度（评测成本）**；落在八阶段"资产构建→迭代优化"（阶段③⑦）。
- **反模式**：若各团队各自为政、评测散落各处，会导致能力无法沉淀、重复建设——违背公理 A5（成本约束）与 A2（单一事实源）；无统一平台的评测体系难以支撑规模化与标准化。
- **可复用要点**：评测平台化，沉淀可复用的评测资产。适用于多团队、多 Agent 的规模化组织；落地时平台应抽象出"统一评测 DSL + 共享用例库 + 标准报告"，避免平台演变为无法扩展的"另一套流程"。

## 5.9 案例对比与启示

| 企业 | 领域 | 核心做法 | 方法论映射（公理） | 可复用要点 |
|---|---|---|---|---|
| OpenAI | 通用产品 | AutoEval 自动化管线+人工抽检 | A6 多源互证 / A5 成本约束 | 自动+人工互补 |
| LangChain | 框架平台 | 评测+追溯一体化 | A2 单一事实源 / A4 闭环驱动 | 评测与轨迹关联 |
| Similarweb | 数据提取 | LLM裁判+人工校准 | A6 多源互证 / A2 事实源 | 数据型Agent人工校准 |
| Nubank | 金融科技 | 安全合规KPI+严格审计 | A1 价值锚定 | 安全一票否决 |
| AWS | 云平台 | AgentCore评测+监控 | A4 闭环驱动 / A3 能力可测 | 评测与监控打通 |
| JPMorgan | 金融数据 | 高精度阈值+审计日志 | A2 单一事实源 / A1 价值锚定 | 准确+可追溯 |
| Harvey | 法律 | 专业正确性+律师复核 | A6 多源互证 / A1 价值锚定 | 专家人工把关 |
| IBM | 企业平台 | JudgeIt多维评测平台 | A5 成本约束 / A4 闭环驱动 | 评测平台化 |

**跨案例启示**：
1. **自动与人工互补**是普遍范式（OpenAI/Similarweb/Harvey），本质是公理 A6 多源互证——任何单一评测信号都不可全信。
2. **强监管领域**（金融/法律）安全与专业正确性优先（Nubank/JPMorgan/Harvey），本质是公理 A1 价值锚定——评测目标锚定最高价值需求。
3. **评测与监控/追溯打通**是闭环关键（LangChain/AWS），本质是公理 A4 闭环驱动——评测的价值在驱动持续改进而非一次性跑分。
4. **规模化组织选择平台化**（IBM），本质是公理 A5 成本约束——通过平台摊薄评测成本、沉淀资产。

## 章节小结

8 个案例展示了评测方法论在不同领域的落地形态。共性规律是三句话：**自动与人工互补**（A6 多源互证）、**价值锚定**（A1，强监管领域安全与专业优先）、**闭环驱动**（A4，评测与监控/追溯打通）、**成本约束**（A5，规模化平台化）。差异在于不同领域对安全、准确、专业、成本四个维度的权重取舍。读者应结合自身场景提取可复用要点，而非照搬某一家做法。下一模块汇总常见问题，帮助规避落地中的典型坑。
