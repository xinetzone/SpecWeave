# Git 百度网盘同步 - 坑点与反模式

本文档是七概念方法论中 V（对抗审查/Villain）阶段的产出。我们从四个对抗视角系统性攻击已设计的 Git+百度网盘同步方案，发现潜在问题、边界情况和失败场景，并给出加固措施。

## 🔴 高严重性坑点（可能导致数据丢失/仓库损坏）

---

### 坑点 1：跨设备锁是"弱信号"而非强锁——同步延迟窗口的竞态条件

**场景描述**：
设备 A 获取锁后开始 push，但锁文件需要几秒到几分钟才能通过网盘同步到设备 B。设备 B 在此期间检测不到锁，同样获取锁并执行 push，导致两个设备并发写入裸仓库。

**为什么危险**：
- Git 裸仓库不是为并发写入设计的，并发 push 可能导致：
  - `refs/heads/main` 引用被覆盖，提交丢失
  - `objects/pack/` 下的 pack 文件同时写入产生冲突副本
  - pack 文件不完整，仓库无法 clone/fsck
- 这不是"可能发生"，而是**最终一致性模型下的物理限制**，锁机制文档虽然已承认但低估了实际发生概率
- 新手看到"有锁机制保护"就放松警惕，反而比没有锁更危险（虚假的安全感）

**正确做法/预防措施**：
1. **文档加固**：在 README 最显眼位置用红色警告框强调："锁是辅助手段，不是防弹衣。核心纪律仍是：同一时间只在一台设备操作"
2. **脚本加固**：push 前增加一个"冷静期"检查——获取锁后额外等待 5-10 秒，再次确认没有新出现的锁文件
3. **操作纪律**：push 前**主动**在其他设备上确认没有正在进行的操作（例如通过企业微信/口头确认），不要依赖锁检测
4. **检测加固**：脚本检测到锁文件存在时，即使是刚出现的，也应该中止并提示用户确认

**是否需要修改已有文档/脚本**：✅ 需要
- 文档：README.md、04-locking-mechanism.md 需要强化警告
- 脚本：git-sync-push 需要增加获取锁后的二次确认等待

### 坑点 2：备份与主数据在同一故障域——网盘挂了备份也没了

**场景描述**：
用户严格遵守了"每次 push 自动备份"的规则，所有 bundle 备份都存放在 `<SyncRoot>/backups/` 目录下。但百度网盘账号被封、网盘服务故障、或者同步目录被误删时，裸仓库和备份**同时丢失**。

**为什么危险**：
- 文档中提到了"3-2-1 备份原则"但没有强制执行，自动备份全部在同一同步空间
- 月度"永久备份"如果用户忘记手动复制到网盘外，等于没有冷备份
- bundle 文件本身也是通过网盘同步的，如果同步机制导致 bundle 损坏（如下文坑点 6），备份链全部失效
- 用户误以为"有备份就安全"，实际上只是多了一份同步的副本

**正确做法/预防措施**：
1. **文档加固**：在 09-backup-recovery.md 中用红色警告强调："**网盘中的 backups 目录不是真正的备份，只是同步副本**"
2. **脚本加固**：git-backup 脚本增加一个 `-ColdStorage` 参数，自动复制一份到用户指定的网盘外目录（如 `~/git-cold-backups/`）
3. **强制提醒**：git-doctor full 检查时，如果发现最近 30 天没有网盘外的冷备份，输出 ERR 级警告而非 INFO
4. **默认配置**：setup-git-config 脚本提示用户配置冷备份路径，不配置则每次 push 后输出警告

**是否需要修改已有文档/脚本**：✅ 需要
- 文档：09-backup-recovery.md 需要重新定义"备份"概念
- 脚本：git-backup、git-doctor 需要增加冷备份检查

### 坑点 3：git gc 执行过程中被网盘同步——半完成状态传播到所有设备

**场景描述**：
用户在某台设备上手动执行 `git gc`（或 Git 自动触发 gc），gc 过程中会：
1. 创建大量临时文件（`tmp_pack_*`、`.tmp`）
2. 重写/删除旧的 pack 文件
3. 重写 `packed-refs`

如果此时百度网盘正在同步，可能捕获到中间状态：新 pack 文件写了一半、旧 pack 已删除但新 pack 还没写完、`packed-refs` 被截断。这种半损坏状态会同步到所有设备。

**为什么危险**：
- 现有脚本的"临时文件检测"只在 push/pull 前检查，但 gc 可能在用户不知情时自动触发（Git 会在某些操作后自动 gc）
- gc 产生的临时文件模式可能不在现有检测列表中
- 半完成的 gc 状态传播后，所有设备的仓库都进入"看似能用但 fsck 报错"的状态
- 更糟的是，git gc 会删除 unreachable 对象，如果中断可能导致对象丢失

**正确做法/预防措施**：
1. **脚本加固**：在所有写操作（push、gc 相关）前，暂停网盘同步（如果百度网盘 CLI 支持），或者在裸仓库检测到 gc 临时文件时阻止所有操作
2. **文档加固**：明确禁止手动在裸仓库上执行 git gc；工作仓库执行 gc 前必须先停止网盘同步，gc 完成并验证 fsck 后再恢复
3. **Git 配置加固**：setup-git-config 脚本设置 `gc.auto=0` 禁用自动 gc，由用户在受控时机手动执行
4. **检测加固**：git-doctor 增加对 gc 残留临时文件的检测（`tmp_pack_*`、`*.tmp` 在 objects/pack/ 下）

**是否需要修改已有文档/脚本**：✅ 需要
- 文档：08-performance-optimization.md、09-backup-recovery.md 需要增加 gc 安全规范
- 脚本：setup-git-config 需要禁用自动 gc；git-doctor 需要检测 gc 残留

### 坑点 4：操作系统休眠/睡眠中断 push 过程——锁未释放且仓库状态不一致

**场景描述**：
用户在笔记本上执行 git-sync-push，push 到一半（Git 正在写入裸仓库、或脚本正在等待网盘同步）时合上笔记本盖子，系统进入睡眠/休眠。唤醒后：
1. 锁文件残留在本地（但可能还没同步到云端）
2. 裸仓库可能处于半写入状态
3. 脚本进程被挂起/终止
4. 用户以为 push 完成了，在另一台设备开始工作

**为什么危险**：
- 现有超时机制是 30 分钟，但如果笔记本睡眠几小时后唤醒，超时判断基于文件的 `acquired_at` 时间戳，而不是进程实际运行时间
- 如果系统时钟在睡眠/唤醒过程中有调整（例如 NTP 同步跳时），超时计算可能完全错误
- 半写入的裸仓库状态可能在唤醒后被网盘继续同步，把损坏传播出去
- 锁文件在本地残留但云端没有，其他设备看不到锁

**正确做法/预防措施**：
1. **脚本加固**：
   - 脚本开头检测系统是否从睡眠中恢复（比较启动时间和当前时间，或检测时间跳变）
   - push 过程中定期写入"心跳"到锁文件（例如每 30 秒更新一个 `last_heartbeat` 字段）
   - 唤醒后检测到心跳超时，立即输出严重警告，中止所有操作
2. **文档加固**：明确警告"笔记本合盖前必须确认 git-sync 已完成并返回命令行"
3. **电源管理**：建议用户在执行同步操作时设置电源计划为"不睡眠"

**是否需要修改已有文档/脚本**：✅ 需要
- 文档：05-daily-sync-workflow.md、10-troubleshooting.md 需要增加电源管理警告
- 脚本：锁机制需要增加心跳检测

### 坑点 5：百度网盘对 .exe/.dll 等二进制文件的病毒误报与隔离

**场景描述**：
仓库中包含编译产物、可执行文件、或第三方工具的 .exe/.dll 文件。百度网盘的安全扫描可能误报这些文件为病毒，自动：
1. 隔离文件（不删除，但不允许下载/同步）
2. 重命名文件（加 `.bak` 或移到隔离目录）
3. 删除文件（极端情况）
4. 阻止包含此类文件的目录同步

这导致某些 Git 对象文件（如果对象恰好以特定字节序列开头）也可能被误判隔离。

**为什么危险**：
- Git 对象文件是二进制的，特定 SHA1 前缀的对象可能包含"病毒特征码"
- 隔离是静默发生的，用户可能直到 clone 时才发现"对象缺失"
- 被隔离的文件不会出现在冲突副本中，脚本检测不到
- 所有设备同步到"缺文件"的状态，从表面看目录结构正常，但 fsck 报 missing blob

**正确做法/预防措施**：
1. **文档加固**：强烈建议仓库中不要提交 .exe/.dll 等可执行文件，使用 .gitignore 忽略编译产物
2. **脚本加固**：git-doctor 增加"对象完整性校验"——定期枚举所有 reachable 对象，检查对应的文件是否存在
3. **配置建议**：在百度网盘客户端中将 git-sync 目录添加到"安全扫描白名单"（如果有此功能）
4. **预防为主**：大二进制文件考虑使用 Git LFS 或不纳入版本控制

**是否需要修改已有文档/脚本**：✅ 需要
- 文档：08-performance-optimization.md 需要增加二进制文件处理建议
- 脚本：git-doctor 需要增强对象完整性校验

### 坑点 6：bundle 备份文件本身因同步冲突损坏——备份链断裂

**场景描述**：
每次 push 后创建 bundle 文件，bundle 文件是单一大文件（类似 pack 文件）。如果恰好在 bundle 文件写入过程中网盘同步，或者两台设备同时创建 bundle（竞态），可能导致：
1. bundle 文件被截断（写了一半就被同步）
2. 产生 bundle 文件的冲突副本
3. bundle 文件被部分覆盖

虽然脚本执行了 `git bundle verify`，但 verify 是在本地写入完成后执行的——如果本地写入时文件还没被网盘碰过，verify 能通过，但之后网盘同步过程中文件可能损坏。

**为什么危险**：
- 用户"每次 push 都备份"，以为备份链安全，但实际上最近的 N 个 bundle 可能都已损坏
- 灾难发生时去恢复，发现所有 bundle 都 verify 失败
- bundle 文件是单一大文件，比 pack 文件更大，同步冲突概率更高
- 现有文档没有警告"bundle 也需要验证"

**正确做法/预防措施**：
1. **脚本加固**：
   - bundle 先写入临时文件名（`.bundle.tmp`），verify 通过后再原子重命名为最终文件名
   - 定期（git-doctor full 时）对 backups 目录下**所有** bundle 执行 `git bundle verify`，不只是刚创建的那个
2. **文档加固**：在 09-backup-recovery.md 中增加"定期验证备份可用性"章节，建议每季度随机抽一个 bundle 做恢复测试
3. **多份副本**：重要仓库的 bundle 备份不要只存一份在网盘中，见坑点 2

**是否需要修改已有文档/脚本**：✅ 需要
- 文档：09-backup-recovery.md 需要增加备份验证流程
- 脚本：git-backup 需要原子写入；git-doctor 需要批量验证所有 bundle

### 坑点 7：静默数据损坏——位翻转/磁盘错误未被及时发现

**场景描述**：
由于磁盘坏道、内存位翻转、网盘传输错误等原因，某个 Git 对象文件的某几个 bit 发生翻转。Git 的 SHA1 校验虽然能检测到这种损坏，但：
1. 损坏可能在裸仓库中存在很久，直到某次 fsck 或访问该对象时才发现
2. 损坏的对象同步到所有设备后，原来正确的版本被覆盖
3. 如果损坏的对象在一个旧提交中，可能几个月都不会被访问到

**为什么危险**：
- 这是"静默损坏"——没有明显症状，直到需要恢复时才发现
- 现有方案依赖 git-doctor 手动运行，如果用户忘记每周执行，损坏可能长期存在
- 网盘同步会把错误版本"胜利"到所有设备，正确版本丢失
- 位翻转在消费级硬件上概率虽低，但不是零

**正确做法/预防措施**：
1. **脚本加固**：git-sync-pull 每次拉取后自动执行轻量级 fsck（`git fsck --no-dangling`，只检查 error/fatal，忽略 dangling/unreachable）
2. **文档加固**：强调"每周 git-doctor full 不是可选，是必须"
3. **监控加固**：git-doctor 可以记录上次全量 fsck 时间，超过 2 周则输出 ERR
4. **硬件建议**：重要项目考虑使用 ECC 内存、SSD 开启端到端数据保护（但这超出脚本范围）

**是否需要修改已有文档/脚本**：✅ 需要
- 文档：07-health-check.md 需要强化 fsck 频率要求
- 脚本：git-sync-pull 增加轻量级完整性检查；git-doctor 记录检查时间

### 坑点 8：设备时钟不同步导致锁超时判断错误

**场景描述**：
锁超时判断基于 `acquired_at` 时间戳与"当前时间"的差值。如果：
- 设备 A 的时钟快了 1 小时
- 设备 B 的时钟慢了 30 分钟
- 或者设备从睡眠唤醒后 NTP 同步导致时间跳变

可能导致：
- 正常持有的锁被误判为超时（时钟慢的设备认为锁已超时）
- 真正超时的锁被误判为正常持有（时钟快的设备认为锁刚获取）

**为什么危险**：
- 超时是自动强制解锁的依据，误判超时可能在正常操作过程中解锁，导致并发
- 现有锁机制使用 ISO8601 带时区格式，但时区解析在不同平台可能有差异
- 虚拟机/WSL 的时钟经常不同步

**正确做法/预防措施**：
1. **脚本加固**：
   - 初始化时检测系统时钟是否合理（例如与文件 mtime 对比，或检测时间跳变）
   - 锁超时判断增加"宽容期"——超过超时时间 2 倍才自动清理，1-2 倍之间只警告不自动解锁
   - 记录锁文件的本地 mtime 作为辅助判断依据，不完全信任 JSON 内的时间戳
2. **文档加固**：要求所有设备开启自动时间同步（NTP）

**是否需要修改已有文档/脚本**：✅ 需要
- 脚本：lock-utils 需要增强超时判断逻辑

### 坑点 9：多设备使用相同 hostname 导致 device_id 冲突

**场景描述**：
device_id 生成规则是 `<hostname>-<os>-<seq>`，例如 `laptop-win-01`。如果用户：
- 两台电脑都是公司统一镜像安装，hostname 都是 `DESKTOP-ABC123`
- 重装系统后使用了相同的 hostname
- 克隆虚拟机后没有修改 hostname

两台设备会生成相同的 device_id，锁机制误以为是"同一设备"。

**为什么危险**：
- 同 device_id 的锁会被认为是"自己持有"，可能误删其他设备的锁
- 锁日志无法区分是哪台设备操作的
- pid 检查只在同设备有效，跨设备 pid 可能重复但被误判为"同进程"

**正确做法/预防措施**：
1. **脚本加固**：
   - device_id 生成时增加额外的熵源（例如 MAC 地址哈希、系统盘 UUID、或首次运行时生成随机 UUID）
   - 不要仅依赖 hostname + os + seq
   - 检测到 devices.json 中已有相同 hostname+os 但其他属性不同（如不同 MAC）时，自动增加 seq
2. **文档加固**：初始化时提醒用户确认 hostname 唯一，或在新设备首次运行时警告检测到重复 hostname

**是否需要修改已有文档/脚本**：✅ 需要
- 脚本：lock-utils 的 device_id 生成逻辑需要改进

### 坑点 10：.gitattributes 在 clone 后才生效——首次跨平台换行符混乱

**场景描述**：
`.gitattributes` 文件是仓库内容的一部分，在 clone 完成后才存在于工作区。第一次 clone 时：
1. Git 使用全局的 `core.autocrlf` 设置
2.  checkout 完成后 `.gitattributes` 才出现
3. 但此时文件已经按错误的换行符配置 checkout 了
4. 执行 `git status` 显示大量文件被修改

**为什么危险**：
- 新用户在 Windows 上 clone 了一个由 Linux 用户创建的仓库，立即看到"所有文件都被修改了"
- 用户可能不知所措，或者直接 `git add . && git commit -m "fix line endings"` 把换行符混乱提交上去
- setup-git-config 虽然配置了 core.autocrlf，但如果仓库本身有 `.gitattributes` 应该以仓库为准

**正确做法/预防措施**：
1. **脚本加固**：clone-repo 脚本在 clone 完成后，如果仓库有 `.gitattributes`，自动执行一次 `git reset --hard HEAD` 重新 checkout 文件，确保 `.gitattributes` 生效
2. **文档加固**：在跨平台配置文档中说明这个"冷启动"问题，给出手动修复命令
3. **预防为主**：register-repo 时检查是否有 `.gitattributes`，没有的话建议添加

**是否需要修改已有文档/脚本**：✅ 需要

### 坑点 11：百度网盘客户端更新/重新安装后同步目录被重置

**场景描述**：
百度网盘客户端自动更新，或者用户重新安装客户端后：
- 之前配置的同步目录列表丢失
- 需要重新选择"同步空间"目录
- 用户可能错误地选择了一个新的空目录作为同步目录
- 或者客户端把旧同步目录重新同步一遍，产生大量冲突

更糟的是，客户端更新后可能：
- 改变同步算法
- 临时暂停同步但没有提示
- 重置某些高级设置（如选择性同步）

**为什么危险**：
- 用户几个月不用某台设备，打开后客户端静默更新，同步目录配置丢失
- 用户重新配置时可能选错目录，导致本地工作仓库的 remote 指向错误位置
- 脚本检测不到"网盘客户端配置已重置"这种情况

**正确做法/预防措施**：
1. **脚本加固**：所有脚本执行前先验证 SyncRoot 目录结构是否完整（是否有 repos/、locks/、meta/ 等子目录，是否有 VERSION 或标记文件），如果结构异常立即中止并警告
2. **文档加固**：说明"百度网盘客户端更新后必须首先检查同步目录配置"
3. **初始化标记**：init-sync-dir 脚本创建一个 `.syncroot-marker` 文件（内容为版本号），脚本运行前检查该文件存在且版本匹配

**是否需要修改已有文档/脚本**：✅ 需要
- 脚本：所有脚本增加 SyncRoot 完整性校验
- 文档：05-daily-sync-workflow.md 增加客户端更新后的检查步骤

### 坑点 12：Windows 路径含中文/空格/特殊字符导致脚本失败

**场景描述**：
用户把同步目录放在 `D:\我的文档\百度网盘\git sync\` 这样的路径下，路径包含：
- 中文字符
- 空格
- 可能还有 `&`、`(`、`)` 等特殊字符

虽然脚本应该正确引用路径，但：
- PowerShell 中某些情况下引号处理不当
- Bash 脚本中路径含空格时 `cd` 或其他命令可能失败
- Git 接收路径参数时某些边缘 case 处理不对
- 调用 cmd.exe 或外部命令时引号传递可能丢失

**为什么危险**：
- 新用户倾向于使用默认的"百度网盘"安装目录（中文路径）
- 错误表现为"找不到路径"、"参数错误"等模糊的错误信息
- 用户不知道是路径问题，排查困难
- 某些脚本可能在含空格路径下部分工作部分失败，产生不一致状态

**正确做法/预防措施**：
1. **文档加固**：Quick Start 中明确要求"同步路径不要包含中文和空格"，给出反例和正例
2. **脚本加固**：init-sync-dir 脚本检测路径是否包含中文/空格/特殊字符，如果有输出警告或拒绝执行
3. **测试加固**：所有脚本增加路径含中文/空格的测试用例
4. **路径规范化**：脚本内部统一使用绝对路径，所有传递给外部命令的路径都正确转义

**是否需要修改已有文档/脚本**：✅ 需要
- 文档：README.md 的 Quick Start 需要强调路径要求
- 脚本：路径参数处理需要审计和加固

### 坑点 13：force-unlock 被滥用成为"常规操作"

**场景描述**：
用户遇到锁被占用就直接 force-unlock，不确认持有者状态：
- "有锁？force-unlock 一下就好了"成为肌肉记忆
- 不看警告信息，直接输入 YES
- 30 分钟超时太长，等不及就 force-unlock
- 甚至把 force-unlock 加入自己的"日常同步流程"，push 前先 force-unlock

**为什么危险**：
- 这彻底破坏了锁机制的保护作用
- 比没有锁还糟——没有锁用户会小心，有锁但随意解锁给了虚假的安全感
- 文档中虽然警告了 force-unlock 是危险操作，但没有从流程上阻止滥用
- 脚本中的确认输入"YES"太容易被机械输入

**正确做法/预防措施**：
1. **脚本加固**：
   - force-unlock 增加"冷却期"——锁持有不足 5 分钟时拒绝强制释放（除非明确指定 `-IReallyWantToBreakThings`）
   - force-unlock 要求输入完整的持有者 device_id 或 hostname 进行二次确认（不只是输入 YES）
   - 记录所有 force-unlock 操作到一个专门的日志文件（`logs/force-unlock-audit.log`），包含时间、操作人、原因（如果用户愿意输入）
   - git-doctor 检查 force-unlock 审计日志，如果最近 7 天有超过 3 次 force-unlock，输出严重警告，提示用户"你在滥用 force-unlock"
2. **文档加固**：把 force-unlock 的警告级别从"注意"提升到"危险"，给出"什么时候才应该 force-unlock"的明确 checklist

**是否需要修改已有文档/脚本**：✅ 需要
- 文档：04-locking-mechanism.md 强化 force-unlock 的使用门槛
- 脚本：force-unlock 需要增加防滥用机制

### 坑点 14：百度网盘冲突文件名模式多样——现有检测可能遗漏

**场景描述**：
百度网盘产生的冲突副本文件名不只是 `xxx (1).txt` 或 `xxx (冲突版本).txt`，根据版本不同可能有：
- `xxx (来自 DESKTOP-XXX).txt`
- `xxx (冲突副本 1).txt`
- `xxx - 副本.txt`
- `xxx - Copy.txt`
- 隐藏的临时文件 `~$xxx`
- 不同语言版本的网盘可能用不同语言的"冲突版本"

现有 check-conflicts 脚本可能只匹配了部分模式，遗漏其他冲突文件。

**为什么危险**：
- 未被检测到的冲突文件可能被 Git 读取到
- HEAD 或 packed-refs 的冲突副本如果没被检测到，Git 可能读到错误版本
- 用户以为"没有冲突"，实际已有冲突文件存在

**正确做法/预防措施**：
1. **脚本加固**：扩充冲突文件检测模式列表，至少覆盖：
   - `* (*)*`（带括号的）
   - `* - 副本*`、`* - Copy*`
   - `~$*`（Office 临时文件模式）
   - `*.tmp`、`*.part`、`*.bak`
2. **启发式检测**：如果同一目录下有两个文件名高度相似（除了后缀部分完全相同），报告为疑似冲突
3. **文档**：在 check-conflicts 文档中列出所有检测模式，并说明"不可能覆盖所有情况，发现异常文件名要人工检查"

**是否需要修改已有文档/脚本**：✅ 需要
- 脚本：check-conflicts 需要扩充检测模式

### 坑点 16：大文件/二进制文件 delta 压缩导致 pack 膨胀和同步冲突

**场景描述**：
用户提交了大量二进制文件（图片、PDF、编译产物、数据集），Git 对这些文件做 delta 压缩：
- 每次修改二进制文件，pack 大小增长超过文件本身大小
- pack 文件越来越大，每次 push 都要上传巨大的 pack
- 大 pack 文件同步过程中产生冲突的概率指数级上升
- 网盘同步大文件时容易中断，留下半完成文件

**为什么危险**：
- 仓库越来越大，同步越来越慢，用户体验恶化
- 大文件冲突后恢复困难（bundle 也很大）
- 用户可能因为"太卡了"放弃这套方案回到 U 盘传代码

**正确做法/预防措施**：
1. **文档加固**：08-performance-optimization.md 已涉及但需强化，明确给出"什么文件不应该提交"的清单
2. **脚本加固**：register-repo 和 git-sync-push 检测大文件（>10MB），输出警告建议用 Git LFS 或忽略
3. **默认配置**：提供标准的 .gitignore 模板，包含常见编译产物/二进制文件模式

**是否需要修改已有文档/脚本**：🟡 部分需要
- 文档已有相关内容，可进一步强化
- 脚本可增加大文件警告

### 坑点 17：日常维护成本高——用户可能放弃治疗

**场景描述**：
方案要求的日常维护包括：
- 每天：开机 pull、关机前 push
- 每周：git-doctor full 检查
- 每月：手动冷备份
- 每季度：备份恢复测试
- 随时：注意锁状态、等待同步完成、不要强制解锁

半年后用户可能：
- 忘记 git-doctor 这回事
- 觉得"反正没出过问题"就跳过等待直接操作
- 几个月不做冷备份
- 最后回到"用 U 盘拷代码"或者干脆花钱买 GitHub Pro

**为什么危险**：
- 不是技术问题，是**人的问题**——流程越复杂，遵守率越低
- 维护不足导致问题发生时没有准备，从"小问题"演变成"数据灾难"

**正确做法/预防措施**：
1. **降低维护负担**：把能自动化的都自动化——git-sync 时自动做轻量级检查，系统启动时自动 pull（可选）
2. **提醒机制**：git-doctor 可以记录上次运行时间，如果超过 2 周，在 git-sync 时自动提示"距离上次健康检查已超过 2 周，建议运行 git-doctor"
3. **预期管理**：文档中坦率承认这套方案的维护成本，明确告知"这不是零维护方案"
4. **退出策略**：明确告诉用户什么时候应该放弃这套方案（见下文），不要硬撑

**是否需要修改已有文档/脚本**：✅ 需要
- 文档：本文档下一章明确给出"放弃条件"
- 脚本：增加定时提醒（但不要太烦人）

## 反模式清单——这些做法绝对禁止

| 反模式 | 为什么禁止 | 正确做法 |
|--------|-----------|----------|
| ❌ 看到锁就 force-unlock | 彻底破坏锁保护，大概率导致并发冲突 | 先等 30 分钟超时，再联系持有者确认 |
| ❌ 直接操作 repos/ 目录下的文件 | 绕过所有保护机制，容易误删/改错 | 所有操作通过脚本，不要手动进 repos/ |
| ❌ push 后立即关机/合盖 | 网盘还没同步，锁可能没释放，状态不一致 | 等脚本返回"同步完成"再操作 |
| ❌ 用 -NoWait 跳过同步等待 | 以为"push 成功就完事了"，实际裸仓库还在同步 | 不要用 -NoWait，除非你明确知道后果 |
| ❌ 在多台设备上同时执行 git-sync | 竞态条件，即使有锁也可能冲突 | 同一时间只在一台设备操作 |
| ❌ 把 bundle 备份当成唯一备份 | 备份和主数据在同一故障域 | 每月复制到网盘外冷存储 |
| ❌ 提交 .exe/.dll/编译产物 | 可能被网盘误报隔离，pack 膨胀 | 用 .gitignore 忽略，必要时用 Git LFS |
| ❌ 手动执行 git gc（尤其是裸仓库） | gc 过程中同步导致半损坏状态传播 | 禁用自动 gc，手动 gc 前停网盘同步 |
| ❌ 同步路径含中文/空格 | 脚本边缘 case 可能失败 | 使用纯英文、无空格路径 |
| ❌ 跳过 git-doctor 每周检查 | 静默损坏无法及时发现 | 每周一次，雷打不动 |
| ❌ force push 到 baidu remote | 覆盖历史，其他设备的提交丢失 | 禁止 force push，用 --force-with-lease 并提前备份 |
| ❌ 百度网盘客户端更新后直接用 | 同步目录配置可能重置 | 更新后首先检查同步目录配置正确 |

## 方案的已知局限——坦率承认这套方案做不到什么

本方案不是银弹，它**无法**解决以下问题，使用前请知悉：

1. **无法提供强一致性保证**：基于网盘的最终一致性模型，从物理上无法做到 100% 无并发。锁是纪律辅助，不是分布式事务。
2. **无法替代服务器端保护**：没有 pre-receive hook、没有分支保护、没有权限控制，任何能接触到同步目录的人都可以 force push 破坏历史。
3. **无法处理实时多人协作**：两个人同时编辑同一个文件，仍然需要手动解决冲突，不会像 CRDT 那样自动合并。
4. **无法防止百度网盘本身的故障**：账号被封、服务停止、数据被审查删除等平台级风险，本方案无能为力。
5. **无法在 10GB 以上大仓库上良好工作**：大仓库的 pack 文件大、同步慢、冲突概率高，建议拆分仓库或使用专业托管。
6. **无法零维护**：需要定期健康检查、冷备份、遵守操作纪律，不是"装好就不用管"的方案。
7. **跨平台换行符/权限/大小写问题无法 100% 消除**：即使有 .gitattributes 和正确配置，边缘情况仍可能出现。
8. **无法防止用户自己误操作**：`rm -rf`、`git reset --hard`、`git push -f` 等危险命令，脚本只能警告无法阻止。

## 什么时候应该放弃这套方案改用专业托管

如果出现以下任一情况，**强烈建议迁移到专业 Git 托管平台**（GitHub/GitLab/Gitea/Gogs 等）：

| 信号 | 说明 |
|------|------|
| 👥 协作者超过 3 人 | 多人物理上无法做到"同一时间只在一台设备操作"的纪律 |
| 📦 单仓库超过 5GB | 大文件同步体验差，冲突恢复成本高 |
| 🔒 需要代码审查/PR 流程 | 网盘方案没有任何代码审查能力 |
| 🚨 半年内出现 2 次以上需要从 bundle 恢复的事故 | 说明这套方案的维护成本已经超过收益 |
| 💼 商业项目/公司代码 | 代码是核心资产，不值得为省服务器钱冒数据丢失风险 |
| 🤝 需要 CI/CD、Issue 追踪、Wiki 等功能 | 专业托管是完整生态，网盘只是文件同步 |
| 😫 你已经记不清上次做冷备份是什么时候 | 说明维护负担已经超过你的承受能力，应该用更省心的方案 |
| 🚫 百度网盘同步速度经常 < 100KB/s | 同步太慢，严重影响工作效率 |
| ⚠️ 你的工作要求合规/审计 | 网盘同步无法提供访问日志、审计追踪等合规能力 |

**迁移是正常的，不是失败**。这套方案的定位是"个人/小团队在特定阶段的低成本方案"，当需求超出它的能力边界时，迁移到专业托管是正确的选择，不要硬撑。

## 总结

这套 Git+百度网盘同步方案在"零成本、无需服务器、个人多设备同步"这个特定场景下是可行的，但它有明确的能力边界和使用前提：

> **这套方案能用，但你必须清楚它的风险，并愿意承担维护成本。**

它不是"装好就不用管"的 Dropbox 式体验，也不是 GitHub 那样的专业服务。它要求用户理解 Git 的工作原理、遵守操作纪律、定期维护备份。如果用户做不到这些，出问题是迟早的事。

对抗审查的目的不是否定方案，而是让方案的使用者：
1. 在问题发生前就知道可能出什么问题
2. 知道怎么预防这些问题
3. 知道问题发生后怎么恢复
4. 知道什么时候应该放弃这套方案选择更合适的工具

**了解风险，才能驾驭风险。**
