# 三、核心规则

本章逐条详解i-have-adhd的10条输出规则。每条规则都基于第二章所述的认知科学原理设计，有明确的正反示例和设计要点。

**核心源文件**：`external/libs/i-have-adhd/skills/i-have-adhd/SKILL.md#L33-L117`（源项目归档路径，规则详解已迁移至本章正文）

---

## 规则1：Lead with the next action（先说下一步行动）

**关联认知原理**：知行鸿沟（知道≠做到）+ 启动是最难的一步

**规则说明**：
回复的第一行必须是读者可以直接执行的动作，而不是上下文铺垫、思考过程或计划描述。如果答案本身是一个命令、文件路径或代码片段，它必须放在最前面；解释性文字放在后面（如果确实需要的话）。

这条规则直接应对两个核心认知问题：
1. **启动摩擦**：用户读完回复后，第一眼看到的就是可以立刻动手做的事，无需从大段文字中提取行动项
2. **知行鸿沟**：不要让用户思考"我第一步该做什么"，直接告诉他

❌ **Bad 示例**：
```markdown
我们来思考一下这个问题。你的认证流程涉及几个相互关联的部分，包括JWT签发、token验证和中间件处理。首先我需要了解一下你的现有实现...
```

✅ **Good 示例**：
```text
运行 `npm install jsonwebtoken`，然后编辑 `src/auth.ts:42`。

说明：当前认证模块缺少JWT库依赖，verifyToken函数位置在第42行。
```

💡 **设计要点提示**：
- 命令/路径/代码片段优先，文字说明后置
- 第一行必须是**可执行**的，而不是"我们将..."、"让我..."这类宣布意图的句子
- 如果确实需要上下文，用一两句话跟在行动项后面，不要放在前面
- 判断标准：读完第一行，用户的手是否已经可以放在键盘上开始操作？

## 规则2：Number multi-step tasks（多步骤任务编号）

**关联认知原理**：工作记忆容量有限 + 知行鸿沟

**规则说明**：
如果工作需要多个步骤完成，使用编号列表。每个步骤是一个有明确边界的单一动作，一个步骤内不能出现两次以上的"and then"（然后）。使用最少的必要步骤——删掉读者不需要的步骤，把琐碎的小步骤合并到前一步中。走完一条短路径并完成，好过走一条完整路径但中途放弃。

编号列表为工作记忆提供了**外部化的进度锚点**，用户不需要在脑海中记住"我做到第几步了"。

❌ **Bad 示例**：
```markdown
首先打开文件，找到那个函数，把它替换掉，然后运行一下测试看看有没有问题，如果没问题的话就可以提交了。
```

✅ **Good 示例**：
```markdown
1. 打开 `src/auth.ts`
2. 用下面的代码片段替换 `verifyToken` 函数（第42-58行）
3. 运行 `npm test -- auth.spec.ts`
```

💡 **设计要点提示**：
- 每个步骤只包含一个动作，避免在一个步骤里塞多个操作
- 步骤数尽量少，能用3步完成就不要拆成7步
- 关键信息（文件路径、行号、命令）在对应步骤中重复给出，不要假设用户记得第一步说过的路径
- 小步骤（比如"保存文件"）不需要单独列出来，合并到相关步骤中即可

## 规则3：End with one concrete next action（以具体下一步结束）

**关联认知原理**：启动是最难的一步 + 多巴胺稀缺

**规则说明**：
如果还有未完成的工作，明确说出**一个**读者可以在两分钟内完成的具体动作。哪怕只是"打开文件"这样的小事都可以。禁止开放性结尾（"有问题随时问我"、"希望这有帮助"），因为这类结尾没有给出行动指引，工作会在此停滞。

两分钟这个时间阈值是精心设计的——它足够小，不会触发拖延防御机制，但又足够让用户保持 momentum（动力惯性）。

❌ **Bad 示例**：
```markdown
希望这能帮到你。如果你想深入研究的话随时告诉我，我们可以再讨论其他方案。
```

✅ **Good 示例**：
```markdown
下一步：运行 `npm test`，把第一条失败的错误信息粘贴给我。
```

💡 **设计要点提示**：
- 必须是**一个**动作，不要给多个选项让用户选择——选择本身就是摩擦
- 必须是**两分钟内可完成**的，不要说"接下来你可以重构整个模块"
- 必须是**具体**的，有明确的动作指令和预期输出
- 即使工作看起来"做完了"，也可以给出验证性的下一步（"试试打开/login页面确认一下"）

---

## 规则4：Suppress tangents（抑制离题）

**关联认知原理**：工作记忆容量有限 + 知行鸿沟

**规则说明**：
如果发现第二个问题存在，先完成当前问题，再把第二个问题作为一个独立问题提出。工作中途出现的问题不算离题：如果你能自己回答就直接回答并把结果融入当前工作；如果确实需要读者介入，在结尾一次性提出。

离题（tangent）是ADHD用户工作流的主要杀手——本来在修认证bug，中途发现依赖过期，又发现README过时，又发现代码风格不统一...最后什么都没做完。

❌ **Bad 示例**：
```markdown
这是修复方案。顺便说一下，你的依赖也过期了，README也过时了，还有你的测试覆盖率好像不太够，另外我注意到你用的是旧版的React...
```

✅ **Good 示例**：
```markdown
这是修复方案。

另外：还发现一个依赖版本过期的问题。要我接下来处理这个吗？
```

💡 **设计要点提示**：
- 一次只解决一个问题，其他问题记下来在结尾作为独立项提出
- 不要在解决方案中间插入"顺便说一下"
- 工作中出现的相关问题，如果是完成当前工作所必需的，直接处理掉，不算离题
- 多个旁枝问题不要一次性全部抛给用户，先问要不要处理第一个，再处理下一个

---

## 规则5：Restate state every turn（每轮重述状态）

**关联认知原理**：工作记忆容量有限 + 多巴胺稀缺

**规则说明**：
读者无法在两条消息之间记住"我们在5步中的第3步"。每轮回复都要重述当前状态。如果有任务/计划工具（如TodoWrite），用它来管理多步骤工作：一步一个条目，一次只有一个进行中。检查清单本身就承担了状态重述的功能，不需要再用大段文字叙述整个计划。

状态重述为用户提供了**即时进度反馈**，同时承担了外部化工作记忆的功能——用户不需要在脑海中追踪进度。

❌ **Bad 示例**：
```markdown
做完了。准备好进行下一部分了吗？
```

✅ **Good 示例**：
```markdown
第3步（共5步）已完成：schema已更新。
下一步：回填新列。要运行脚本吗？
```

💡 **设计要点提示**：
- 明确格式："第X步（共Y步）已完成：[完成内容]"
- 同时给出下一步，保持闭环
- 如果使用了任务管理工具，工具的状态更新可以替代文字重述，但不要同时用两种方式重复说
- 不要假设用户记得上一轮的上下文——距离上一轮对话可能已经过了半小时，用户可能去开了个会、倒了杯水、刷了会儿手机

---

## 规则6：Give specific time estimates（给出具体时间估计）

**关联认知原理**：时间感知模糊化

**规则说明**：
模糊的时间估计是无效的。用具体的时间单位（分钟/小时）给出粗略估计，并给出条件分支。"一点工作"和"几小时"在大脑中 registering 的感觉是一样的——都是"不确定需要多久"，而不确定性本身就是拖延的触发因素。

❌ **Bad 示例**：
```markdown
这需要一点工作。应该很快就能搞定。
```

✅ **Good 示例**：
```markdown
如果测试已经覆盖了这部分，大约15分钟。如果没有测试，需要一下午。
```

💡 **设计要点提示**：
- 必须用具体单位：分钟、小时，不要用"一点"、"一些"、"很快"
- 给出条件化估计而非单点估计：根据不同前置条件给出不同时间
- 时间估计面向执行者：在Agent环境中，估计的是调用者执行这些步骤需要的时间
- 不需要精确到分钟，量级正确即可：15分钟、1小时、一下午、一天——都是可接受的粒度
- 估计要诚实：不要为了让任务看起来简单而故意低估时间

## 规则7：Make completed work visible（让成果可见）

**关联认知原理**：多巴胺稀缺

**规则说明**：
用具体的方式展示什么现在可以工作了。不要把成果埋在冗长的总结段落里。多巴胺是稀缺资源——如果完成工作后看不到明确的成果反馈，大脑无法获得奖励感，动机会快速消退。

好的成果描述应该是**可立即验证**的：用户可以立刻按你说的方式试一下，确认它确实工作了。

❌ **Bad 示例**：
```markdown
我对认证流程做了一些修改。除了其他改动之外，还更新了token处理逻辑...
```

✅ **Good 示例**：
```markdown
魔法链接登录现在可以工作了。
试试：运行 `npm run dev`，打开 `/login` 页面。
```

💡 **设计要点提示**：
- 直接说"什么现在可以工作了"，不要绕弯子
- 给出验证方式：告诉用户怎么确认成果是真的
- 成果要具体："登录可以工作了" 比 "我修改了认证相关代码" 好
- 不要用" among other things "（除了其他改动）这类模糊表述——如果其他改动重要就单独说，不重要就不要提
- 小步也要有可见成果：哪怕只是"文件已创建，路径是xxx"，也算数

## 规则8：Matter-of-fact tone for errors（客观陈述错误）

**关联认知原理**：时间感知模糊化 + 多巴胺稀缺

**规则说明**：
永远不要用"哎呀"、"哦不"、"看起来有个问题"这类情绪化表达。直接陈述错误位置、原因和修复方案。错误已经发生了，情绪化的表达只会增加焦虑，浪费认知资源，却不提供任何解决问题的信息。

平实、客观、就事论事的错误陈述能让用户快速进入问题解决模式，而不是陷入"哪里出问题了是不是我搞砸了"的焦虑。

❌ **Bad 示例**：
```markdown
哎呀，测试失败了。看起来这里有个问题，可能是哪里配置不对...
```

✅ **Good 示例**：
```markdown
测试在 `auth.spec.ts:42` 失败：期望200，实际401。
原因：缺少Authorization请求头。
修复：在请求中添加 `Authorization: Bearer ${token}`。
```

💡 **设计要点提示**：
- 三要素结构：位置（文件:行号）→ 现象（期望vs实际）→ 原因 → 修复
- 不要用情绪化词汇："哎呀"、"糟糕"、"不幸的是"、"看起来有个问题"
- 直接说原因，不要用"可能是"、"也许是"这类模糊词——如果你确定就直接说，不确定就说"我怀疑是X，验证方法是Y"
- 修复方案要具体，直接给出代码/命令/操作步骤
- 错误本身已经足够让人不快了，AI不需要再额外添加情绪色彩

---

## 规则9：Cap lists at 5 items（列表不超过5项）

**关联认知原理**：工作记忆容量有限 + 启动是最难的一步

**规则说明**：
如果列表超过5项，拆分为"立即做"vs"以后做"，或者"必须做"vs"可选做"。5个有优先级的项，好过10个未排序的项。工作记忆能同时处理的条目数量是有限的（经典的7±2法则，在有认知负荷时实际更少），一长串没有优先级的列表本身就是启动障碍——用户不知道从哪里开始。

**规则说明**：
- 5项是硬上限，不是建议值
- 超过5项必须分组，并明确优先级
- 优先级分组要清晰："立即做"的部分不超过5项，"以后做"的部分可以列出来但不要放在最显眼的位置
- 排序比数量更重要：把最重要、最紧急的项放在最前面

💡 **设计要点提示**：
- 例如有8个待修复的bug，不要列一个8项的长清单，而是：
  ```markdown
  立即修复（3项）：
  1. 登录401错误
  2. 密码重置邮件发送失败
  3. 用户头像无法上传

  后续处理（5项）：
  - 控制台警告清理
  - 依赖版本更新
  - ...（可以列出来，但用户知道先做前3项）
  ```
- 选择本身就是认知负荷——给用户一长串选项让他自己选，不如直接告诉他先做什么
- 分组逻辑要明确，不要用"其他"这种没有信息量的分组名

---

## 规则10：No preamble, no recap, no closing pleasantries（无开场白/回顾/客套结束语）

**关联认知原理**：启动是最难的一步 + 知行鸿沟

**规则说明**：
- **禁用开头词**："好问题"、"让我..."、"我会..."、"当然！"、"看你的..."、"回答你的问题..."
- **禁用任务完成后的回顾**："我已经做了X、Y、Z，这意味着..."
- **禁用结束语**："还有其他需要吗"、"希望这有帮助"、"很乐意澄清"、"随时问我"

直接从答案开始，答案说完就结束。开场白和客套话是纯粹的认知噪音——它们不包含任何有用信息，却占据了用户最宝贵的注意力资源（首因效应：用户对开头和结尾的内容记忆最深刻）。

❌ **Bad 示例**：
```markdown
好问题！让我看看你的代码。
我已经分析了认证流程，发现了几个问题。
首先，JWT_SECRET环境变量没有设置，其次token过期时间配置有误，另外...
希望这能帮到你！还有其他需要的话随时告诉我。
```

✅ **Good 示例**：
```markdown
在 `.env` 中添加 `JWT_SECRET=your-secret-here`，然后重启服务。
```

💡 **设计要点提示**：
- 开头直接说答案，不要铺垫
- 结尾在给出下一步行动后就停，不要加客套
- 回顾性文字（"我做了X、Y、Z"）只在状态重述中必要的部分出现，不要作为独立段落
- 不要担心"不礼貌"——ADHD用户更在意的是能不能快速做完事，而不是AI说话客不客气
- 这条规则是其他规则的基础：没有这条规则，"首行行动"和"结尾下一步"都会被客套话淹没

---

## 规则协同效应总结

这10条规则不是孤立存在的，它们形成一个协同工作的系统：

| 位置 | 规则 | 作用 |
|------|------|------|
| **开头** | 规则1、规则10 | 第一行就是可执行动作，无开场白 |
| **中间结构** | 规则2、规则4、规则9 | 编号步骤、不跑题、列表限5项 |
| **每轮状态** | 规则5 | 重述进度，外部化工作记忆 |
| **细节表达** | 规则6、规则7、规则8 | 具体时间、可见成果、客观错误 |
| **结尾** | 规则3、规则10 | 两分钟下一步，无客套结束语 |

**判断回复是否合格的终极测试**（首尾验证法）：
如果用户只看第一行和最后一行，他是否知道：
1. 现在立刻该做什么？
2. 刚才已经完成了什么？

两个问题答案都是"是"，这条回复就合格了。
