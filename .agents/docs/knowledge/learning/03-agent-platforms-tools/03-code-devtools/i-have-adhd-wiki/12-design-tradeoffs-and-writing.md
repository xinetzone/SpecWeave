# 十三、设计取舍与技术写作借鉴

> **【SpecWeave 方法论补充】** 本章对 i-have-adhd 项目的四个关键设计决策进行中立的 trade-off 分析，并提炼其介绍文章的写作技巧，为 Agent Skills 开发者和技术写作者提供可复用的借鉴。

---

## 13.1 四个关键设计决策的 Trade-off 分析

i-have-adhd 的设计中没有绝对的"正确答案"，每个决策都是针对核心目标（解决高频交互痛点、追求最大化传播）的合适选择。

### 13.1.1 决策一：不改推理只改输出

**决策内容**：不试图改变AI模型的推理能力本身，仅通过提示词规则调整输出格式和结构。

**优势**：
- 兼容性极强：不依赖特定模型版本或微调，适用于多种Agent
- 风险可控：不触及AI核心能力，"改坏了"最多回到啰嗦状态
- 实现成本极低：无需训练、无需微调，单个SKILL.md文件即可
- 效果可预测：输出格式优化直观可见

**潜在局限**：
- 治标不治本：无法解决AI推理过程本身的冗余和错误
- 依赖提示词遵循能力：规则效果取决于模型对提示词的遵循程度
- Token节省有上限：复杂问题的长思考链Token不会显著降低
- 错误更快到达用户：直接输出减少了"在铺垫中发现问题"的缓冲

**适用条件**：目标是提升交互效率而非提升AI能力；模型本身推理质量已达标；需要快速落地低成本验证；面向高频重复任务场景。

### 13.1.2 决策二：例外场景保留灵活性

**决策内容**：在核心规则之外明确定义6种例外场景，允许特定条件下打破格式约束。

**优势**：
- 避免规则僵化：预设"逃生舱"防止特殊场景反效果
- 安全兜底：高风险操作的例外本质是安全机制
- 用户体验平衡：共情、创意、解释场景保留灵活性
- 降低抵触情绪："默认如何、例外如何"而非"必须如何"

**潜在局限**：
- 例外判断依赖模型：边界模糊时可能误判
- 增加规则复杂度：用户需记忆更多内容
- 可能被滥用：例外定义不精确时AI借口回到啰嗦
- 枚举不完备：6种不可能覆盖所有场景

**适用条件**：规则应用场景复杂多样；存在高风险场景；用户群体异质性高；规则违反成本不高。

### 13.1.3 决策三：纯文本SKILL.md实现

**决策内容**：整个项目仅用单个纯文本Markdown文件实现，无代码、无编译、无依赖。

**优势**：
- 采用门槛极低：安装仅需两行命令，分发成本趋近于零
- 可审计可修改：纯文本任何人都能读懂修改
- 跨平台兼容：不绑定特定平台/语言/运行时
- 维护成本极低：单文件版本管理、PR审核简单
- 零运行时依赖：离线环境也能使用

**潜在局限**：
- 功能表达力受限：无法实现动态感知、个性化配置等高级功能
- 规则执行无强制力：完全依赖模型自觉遵守
- 无法A/B测试、收集使用数据、灰度发布
- 调试困难：无日志无工具，难定位是提示词问题还是模型问题

**适用条件**：问题本身简单清晰；追求最大化传播；社区驱动迭代；概念验证（POC）阶段。

### 13.1.4 决策四：MIT协议开源

**决策内容**：采用MIT协议——最宽松的开源协议之一，允许自由使用、修改、分发、商用。

**优势**：
- 最大化传播和采用：低门槛鼓励企业和个人自由使用
- 社区贡献友好：宽松协议让更多人愿意贡献
- 商业兼容：无GPL"传染性"顾虑
- 符合极简定位：与"单文件零依赖"定位一致
- 降低法律认知成本：最广为人知的协议之一

**潜在局限**：
- 无法强制衍生作品开源：可fork后闭源商业化
- 缺乏专利保护：专利风险场景保护弱于Apache 2.0
- 贡献者权益保护弱
- 无法控制项目分叉
- 不适用于商业化目标

**适用条件**：项目目标是公共受益而非商业盈利；追求最大化采用率；小工具/配置类项目；社区生态优先。

## 13.2 四个决策的核心设计哲学

这四个决策共同服务于一个核心目标：**最小化采用摩擦，最大化传播范围**。

| 决策 | 设计原则 |
|------|---------|
| 不改推理只改输出 | YAGNI（You Ain't Gonna Need It）——解决最痛的点，不做多余的事 |
| 例外场景保留灵活性 | 规则是默认值不是枷锁——聪明的默认值+明确的逃生舱 |
| 纯文本单文件 | 分发成本趋近于零——两行命令能搞定就不要三行 |
| MIT协议开源 | 最大化公共受益——让好想法传播比控制它更重要 |

## 13.3 原文写作风格特点分析

i-have-adhd 的介绍文章是一篇高效的开源项目推广文，其写作手法值得所有技术写作者学习。

### 13.3.1 特点一：口语化叙事，场景代入感强

文章全程第一人称口语化写作，像朋友聊天一样描述痛点，没有生硬术语和说教感。开篇从共同痛点切入，用日常语言描述使用AI时的烦躁感：

> "经常用 Claude Code 的朋友应该都有这个感觉。它什么都好，就是太爱说话了。你让它改一个函数，它就会先说一句'问的好'，然后铺垫三段上下文……答案藏在第三段的中间，要自己去找。"

没有"用户体验痛点""交互效率"这类抽象词汇，而是"太爱说话了""答案藏在第三段中间""真的会让人头疼"这种每个人都能感同身受的表达，瞬间建立情感连接。

### 13.3.2 特点二：对比式呈现，效果直观可见

介绍产品效果时全程采用"之前vs之后"对比结构，先描述旧体验多糟糕，再展示用了之后多好，用代码块直接展示真实输入输出：

```
# After（使用后）
运行 npm install jsonwebtoken@latest，然后编辑 src/auth.ts:42。
```

"先讲痛点→再给方案→直接展示对比效果"的结构，让读者30秒内理解产品价值，不需要读长篇功能介绍。

### 13.3.3 特点三：诚实披露局限，不做过度承诺

专门用一节"不过有几点也得提一下"主动说明边界和局限：

> "它并没有改变AI的推理能力，只是改变了输出格式。AI不会因此变得更聪明……规则有6种例外情况可以打破……不是死板的格式化。"

主动说清楚"不做什么""边界在哪里"，反而让读者觉得产品靠谱、有清晰边界。9400+ Star与这种诚实沟通方式不无关系。

### 13.3.4 特点四：结构极简，层层递进

文章结构非常简单：痛点→效果演示→原理说明→安装方法→注意事项→总结，共6个小节，每节只讲一件事，符合手机碎片化阅读节奏：

- （无标题开头）直接讲痛点
- "来看看实际用起来是啥样"——效果演示
- "它到底是怎么做到的"——原理解释
- "想试的话，装起来很简单"——安装教程
- "不过有几点也得提一下"——注意事项
- "写在最后"——总结+开源地址

## 13.4 技术开源项目写作可借鉴的四条技巧

### 技巧一：痛点前置，从共同体验切入而非功能罗列

**核心方法**：开头不要先讲"我做了一个项目，有A/B/C三个功能"，而是先讲目标用户共同经历的痛点场景，用具体细节唤起共鸣，然后自然引出产品作为解决方案。

**为什么有效**：技术人每天看大量项目介绍，"功能列表"开头很难引起兴趣。从痛点切入，先回答"为什么我需要这个"，再回答"是什么"，符合认知决策顺序。

### 技巧二：效果优先，用真实对比代替抽象描述

**核心方法**：介绍效果时不说"极大提升效率""输出更加简洁"这类抽象形容词，直接放"使用前vs使用后"真实对比——UI项目放截图，CLI/工具放代码块/终端输出，让效果自己说话。

**为什么有效**：技术用户最务实，"Show, don't tell"。一百句"很简洁"不如一段对比输出。

### 技巧三：诚实讲局限，主动划清边界增加可信度

**核心方法**：主动、明确说明产品"不做什么""有什么局限""什么场景下不适用"。局限说明放在优点介绍之后，位置显眼。

**为什么有效**：开源项目读者大多是有经验的开发者，天然知道没有银弹。只讲优点不讲缺点，读者反而打折扣。主动讲局限，让人觉得作者靠谱。

### 技巧四：安装极简，把"快速开始"压缩到最少步骤

**核心方法**：安装和快速开始做到极致精简，两行命令能搞定就不要三行。"复制→粘贴→运行"三步以内看到效果。

**为什么有效**：技术用户耐心有限，安装5步以上大部分人会关掉页面。降低"第一次看到效果"的门槛，是获得采用的关键。

## 13.5 项目核心优势总结

1. **认知友好设计精准击中痛点**：4条规则直击高频AI交互四大痛点，背后有认知科学原理支撑
2. **极简实现低摩擦采用**：单个SKILL.md、零依赖、两行命令安装、一个命令激活
3. **边界清晰保留灵活性**：明确定义6种例外场景，承认规则不完备性
4. **逆向适配创新路径可复用**：开创"极端用户人因工具→通用AI设计"创新范式
5. **诚实沟通建立信任**：主动说明局限，不做过度承诺

---

## 13.6 可改进空间

1. **动态适应性不足**：纯文本提示词无法实现用户状态感知、个性化配置
2. **中文语境适配缺失**：原始设计面向英文语境，未考虑中文礼貌用语特殊功能
3. **破规指导可操作性待加强**："何时破规、如何优雅破规"仍高度依赖模型能力
4. **非技术用户场景未覆盖**（V2补充）：原始设计隐含"技术专家用户"假设
5. **长对话场景体验待优化**（V2补充）：固定格式在10轮以上产生"进度疲劳"
