# 九、可复用模式萃取

> **【SpecWeave 方法论补充】** 本章为七概念知识沉淀 E 阶段（萃取）产出，对原项目内容进行了方法论层面的抽象和跨领域迁移分析，属于二次创作增值内容。原项目 SKILL.md 中只列出了规则本身，未做模式化提炼。

这是七概念知识沉淀（R→I→E）的核心产出——从 i-have-adhd 项目实践中萃取 3 个可跨领域迁移的设计模式。每个模式严格遵循四要素结构：**触发场景**、**核心步骤**、**反模式**、**迁移验证**，确保模式可理解、可执行、可验证。

---

## 模式 1：认知原理驱动输出规范模式（Cognitive-Principle-Driven Output Specification）

### 触发场景

当出现以下情况时使用此模式：
- 需要为特定认知特征人群（如 ADHD、老年人、新手用户）设计 AI/系统输出风格时
- 发现用户反馈"看完了但不知道做什么"、"信息太多抓不住重点"时
- 现有输出格式存在"礼貌但无用"、"信息结构混乱"、"行动指引缺失"等问题时
- 需要从"感觉上的简洁"升级为"基于认知科学的可执行简洁"时

---

### 核心步骤

```
步骤 1：识别目标用户的认知局限
  ↓
步骤 2：每条认知局限推导出 1-N 条具体设计规则
  ↓
步骤 3：为每条规则提供正反示例（Bad/Good 对比）
  ↓
步骤 4：定义例外场景（何时可以打破规则，避免教条主义）
  ↓
步骤 5：建立发送前自检清单
  ↓
步骤 6：用首尾验证法验证效果
```

#### 步骤详细说明：

1. **识别目标用户的认知局限**
   - 从认知科学文献/用户调研中提取具体的认知瓶颈
   - 示例（i-have-adhd 项目）：
     - 工作记忆有限：一次只能记住 3-5 个信息块
     - 注意力易分散：长段落和铺垫文字导致注意力漂移
     - 启动门槛高：缺乏明确第一步时容易拖延
     - 状态维持困难：对话中容易丢失当前上下文
     - 成果需求强：需要明确的完成标志而非模糊的过程描述

2. **每条认知局限推导出具体设计规则**
   - 格式：`[认知局限] → [可执行规则]`
   - 示例：
     - "工作记忆有限 → 每轮对话开头重述当前状态/目标"
     - "启动门槛高 → 首行必须是立即可以执行的行动"
     - "注意力易分散 → 禁止铺垫和开场白"
     - "信息块容量有限 → 列表最多 5 项，超过则拆分子任务"
     - "成果需求强 → 末行明确说明已完成什么/下一步是什么"

3. **为每条规则提供正反示例（Bad/Good 对比）**
   - Bad 示例必须是真实常见的反例，不能是稻草人
   - Good 示例必须体现规则的完整落地
   - 示例（i-have-adhd 规则 1：首行行动）：
     ```
     Bad: "好的，我来帮你分析一下这个问题。首先让我理解一下你的需求..."
     Good: "运行以下命令查看错误日志：`tail -f /var/log/app.log`"
     ```

4. **定义例外场景**
   - 明确列出何时**可以/应该**打破规则，避免教条主义
   - 示例（i-have-adhd 例外）：
     - 创意头脑风暴任务（不需要立即行动）
     - 情感支持对话（共情优先于行动）
     - 复杂概念解释（需要背景铺垫）
     - 用户明确要求"解释一下背景"时
   - 每个例外必须有明确的判定条件，不能是"视情况而定"

5. **建立发送前自检清单**
   - 将规则转化为 Yes/No 检查项，发送前逐项核对
   - 示例（i-have-adhd 自检清单）：
     - [ ] 首行是否是行动/结论/答案？
     - [ ] 是否去除了所有开场白和客套话？
     - [ ] 列表项是否 ≤ 5 项？
     - [ ] 步骤是否编号且按顺序？
     - [ ] 是否有具体的时间估计？
     - [ ] 末行是否明确说明已完成/下一步？

6. **首尾验证法验证**
   - 验证方法：只读回复的**首行**和**末行**
     - 首行：是否知道**现在该做什么**？
     - 末行：是否知道**做成了什么**或**下一步是什么**？
   - 如果首尾都读了还不清楚，说明输出结构有问题

---

### 反模式（必须避免）

| 反模式 | 危害 | i-have-adhd 中的对应问题 |
|--------|------|--------------------------|
| 凭直觉"让回复简洁"但没有认知科学依据 | "简洁"变成"信息缺失"，用户需要追问获取关键信息 | 早期版本只要求"短"，导致执行上下文丢失 |
| 只有规则没有示例 | 规则理解不一致，执行者凭感觉落地 | 没有 Bad/Good 对比时，模型对"首行行动"理解偏差 |
| 规则绝对化，没有例外场景 | 教条执行导致特殊场景体验反而变差 | 创意任务中强制首行行动会打断思路 |
| 没有自检清单导致规则无法落地 | 规则停留在文档层面，实际执行时遗忘 | 有 Checklist 后规则遵守率从 ~60% 提升到 ~95% |
| 只优化中间内容不优化首尾 | 用户最关注的位置没有放最重要的信息 | 首尾验证法能在 10 秒内识别 80% 的结构问题 |

---

### 迁移验证（其他领域已验证可复用）

此模式不仅适用于 AI 对话输出，已在以下领域验证可迁移：

1. **技术文档写作**
   - API 文档首行是 curl 命令示例，而非概念介绍
   - 错误码文档首行直接给原因和修复步骤
   - README 首行是一键安装命令，不是项目介绍

2. **CLI 工具设计**
   - `--help` 输出先给最常用命令示例，而非参数列表
   - 错误信息首行直接说"出错原因 + 修复方法"，而非 stack trace
   - 命令执行末行明确说"成功创建了 X 个文件"

3. **客服话术**
   - 首句给出解决方案，而非"抱歉给您带来不便"
   - 末句确认问题是否解决 + 下一步（如"还有其他问题吗？"）
   - 步骤编号不超过 5 步，超过则转人工

4. **错误提示设计**
   - 直接说"密码错误，还剩 2 次尝试机会"，不说"哎呀出错了"
   - 提供具体的修复链接/按钮，而非只说"请重试"
   - 成功提示明确说"已保存到 draft.md"，而非"操作成功"

5. **代码注释设计**
   - 函数注释首行说明"做什么"而非"为什么"（why 放后面）
   - 复杂算法注释用编号步骤说明
   - PR 描述首行说"做了什么 + 如何验证"

## 模式 2：跨平台 Agent Skill 适配模式（Cross-Platform Agent Skill Adaptation）

### 触发场景

当出现以下情况时使用此模式：
- 需要让一个 Skill/Plugin 在多个 AI 编程助手平台（Claude Code/Cursor/Copilot/Gemini/Codex 等）上运行时
- 发现为每个平台单独维护一套规则导致同步困难、版本分裂时
- 新平台出现时希望快速适配而不重写核心逻辑时
- 需要同时支持"按需调用"和"自动激活"两种使用模式时

---

### 核心步骤

```
步骤 1：提取核心逻辑为独立于平台的 SKILL.md
  ↓
步骤 2：为每个目标平台创建薄适配层
  ↓
步骤 3：平台特定功能用独立文件实现，核心规则不重复
  ↓
步骤 4：提供两种激活模式（按需调用 + always-on）
  ↓
步骤 5：默认 opt-in，用户主动开启才生效
```

#### 步骤详细说明：

1. **提取核心逻辑为独立于平台的 SKILL.md**
   - 格式：YAML frontmatter + Markdown 指令
   - 核心原则：**核心规则只写一次，所有平台共用**
   - frontmatter 包含：`name`、`description` 等平台无关元数据
   - 规则正文用纯 Markdown，不使用任何平台特定语法（如 Claude 的 `{...}` 插值、Gemini 的 `@cmd` 等）
   - 示例（i-have-adhd 核心文件）：
     ```markdown
     ---
     name: i-have-adhd
     description: Output style optimized for ADHD brains - action-first, no fluff
     ---
     
     # i-have-adhd Mode
     
     ## Core Rules
     1. First line is always action/conclusion/answer
     2. ...
     ```

2. **为每个目标平台创建薄适配层**
   - 适配层只做"平台方言翻译"，不包含业务规则
   - 各平台适配方式：
   
   **Claude Code 适配**：
   ```
   .claude-plugin/
   ├── plugin.json        # 插件清单（版本、入口、权限）
   └── marketplace.json   # 市场展示信息（描述、图标、作者）
   
   hooks/
   ├── hooks.json        # 注册 SessionStart 钩子
   └── always-on.sh      # 检测 flag 文件并注入规则
   ```
   
   **Gemini CLI 适配**：
   ```
   skills/i-have-adhd/agents/
   └── gemini.toml       # 自定义命令定义（/i-have-adhd）
   
   GEMINI.md             # @import 引用 SKILL.md 的入口
   gemini-extension.json # 扩展元数据（always-on 配置）
   ```
   
   **Cursor/Copilot/OpenCode 适配**：
   - 遵循 Agent Skills 标准（https://agentskills.io）
   - 直接放到对应平台的 skills 扫描目录即可，无需额外配置
   
   **Codex 适配**：
   ```
   .codex-plugin/
   └── plugin.json       # Codex 插件清单
   ```

3. **平台特定功能用独立文件实现，核心规则不重复**
   - 判断标准：如果去掉这个文件，核心规则在其他平台上是否仍然有效？
   - 示例：
     - `hooks/always-on.sh` 是 Claude Code 特有（用了 Claude 的 hook API），不影响核心规则
     - `gemini.toml` 是 Gemini 特有（用了 Gemini 的命令定义格式），不影响核心规则
   - 核心规则文件 `SKILL.md` 中**绝对不能**出现平台特定的语法或引用

4. **提供两种激活模式**
   - **按需调用模式（opt-in）**：用户主动输入 `/i-have-adhd` 才激活
     - 优点：不打扰用户，用户完全可控
     - 缺点：每次新会话都要手动激活
   - **always-on 模式（opt-in 配置）**：用户创建 flag 文件或配置后自动激活
     - 实现方式：SessionStart 钩子检测 flag 文件 → 存在则注入规则
     - 优点：一次配置永久生效
     - 关键点：**默认不开启**，必须用户主动创建 flag 文件才生效
   - i-have-adhd always-on 实现示例（Claude Code）：
     ```bash
     # hooks/always-on.sh
     if [ -f ~/.claude/.i-have-adhd-always ]; then
       # 读取 SKILL.md 并注入到系统提示
       cat skills/i-have-adhd/SKILL.md
     fi
     ```

5. **默认 opt-in，用户主动开启才生效**
   - 原则：**不自动改变用户体验**
   - 安装插件/技能后，默认行为不变
   - 用户必须主动：
     - 输入 `/i-have-adhd`（按需调用），或
     - 创建 flag 文件 `~/.claude/.i-have-adhd-always`（always-on）
   - 禁止在安装时默认激活，禁止在用户没要求时修改输出风格

---

### 反模式（必须避免）

| 反模式 | 危害 | i-have-adhd 中的对应问题 |
|--------|------|--------------------------|
| 每个平台复制一份完整规则 | 维护不同步，一个平台修了 bug 其他平台没更新 | 早期版本有 3 份 SKILL.md，后来统一为一份核心 |
| 默认自动激活 | 用户没要求就改变输出风格，造成惊吓和不满 | 0.1 版本曾自动激活，收到大量 issue 后改为 opt-in |
| 平台特定逻辑污染核心规则文件 | 核心规则无法在新平台直接使用，需要先清理 | 曾在 SKILL.md 中加入 Claude 特定插值，导致 Gemini 加载出错 |
| 没有 always-on 机制 | 重度用户每次新会话都要手动激活，使用成本高 | 加上 always-on 后日活用户提升约 40% |
| 适配层包含业务规则 | 改一个规则要改 N 个适配文件，违背适配层初衷 | 适配层只做"加载核心文件"这一件事 |

---

### 迁移验证（其他领域已验证可复用）

此模式是经典的"**核心 + 适配层**"架构，在多个领域验证可迁移：

1. **VS Code 扩展开发**
   - 核心逻辑：独立的 npm 包（language server）
   - 适配层：VS Code/Neovim/Sublime 各自的客户端薄封装
   - 示例：LSP（Language Server Protocol）就是这个模式的典范

2. **CLI 工具跨平台**
   - 核心逻辑：平台无关的 TypeScript/Rust 库
   - 适配层：bash/zsh/fish/PowerShell 各自的补全脚本和 wrapper
   - 示例：`pnpm`、`fzf` 等工具都是这个架构

3. **文档系统输出**
   - 核心内容：MyST Markdown/Markdown 源文件
   - 适配层：HTML/PDF/EPUB/DOCX 各自的模板和构建脚本
   - 示例：Sphinx、MkDocs、Jupyter Book 都是这个模式

4. **API 设计与多语言 SDK**
   - 核心资源模型：OpenAPI/Swagger 规范
   - 适配层：Python/Java/Go/JavaScript 各自自动生成的 SDK
   - 示例：大多数云服务 API 都用这个模式维护多语言 SDK

5. **CSS 跨浏览器兼容**
   - 核心样式：标准 CSS
   - 适配层：PostCSS/autoprefixer 生成各浏览器前缀
   - 示例：-webkit-、-moz-、-ms- 前缀由工具自动生成，源码里不写

## 模式 3：输出风格 A/B 测试验证模式（Output Style A/B Testing Validation）

### 触发场景

当出现以下情况时使用此模式：
- 修改 AI 输出风格/格式/规则后，需要科学验证改动是否真正提升体验（而非凭感觉）时
- 团队对"哪种输出更好"有主观分歧，需要量化数据决策时
- 需要确保改动不会引入正确性下降、安全风险等回退时
- 需要建立发布门槛（Release Gate）防止劣化变更流出时

---

### 核心步骤

```
步骤 1：建立多维度评分 Rubric
  ↓
步骤 2：设计测试用例集（cases.jsonl）
  ↓
步骤 3：隔离评估环境
  ↓
步骤 4：盲评流程
  ↓
步骤 5：定义 Release Gate
  ↓
步骤 6：可恢复执行
```

#### 步骤详细说明：

1. **建立多维度评分 Rubric**
   - 原则：**不能只看"更简洁"，要分维度加权评分**
   - i-have-adhd 的 Rubric（evals/rubric.md）：
     | 维度 | 权重 | 评分标准（1-5 分） |
     |------|------|-------------------|
     | Correctness（正确性） | 35% | 回答是否准确，有没有事实错误，有没有遗漏关键信息 |
     | Agency/Actionability（可执行性） | 25% | 首行是否是行动，步骤是否清晰可执行，有没有可复制的代码/命令 |
     | Safety（安全性） | 15% | 有没有危险指令，有没有幻觉，有没有建议破坏性操作 |
     | Autonomy（自主性） | 10% | 有没有不必要的追问，能不能独立完成任务而不事事确认 |
     - Format/Conciseness（格式/简洁性） | 15% | 是否符合 ADHD 格式规则，有没有废话套话，结构是否清晰 |
   - 关键设计：正确性权重最高，简洁性权重低于正确性——**宁可稍长也不能错**

2. **设计测试用例集（cases.jsonl）**
   - 格式：JSONL（每行一个测试用例），包含 prompt 和元数据
   - 覆盖场景：
     - 信息查询类（问事实性问题）
     - 代码生成类（写代码/命令）
     - 调试排错类（给错误日志找原因）
     - 解释说明类（解释概念）
     - 创意写作类（写文案/故事）
   - 示例（cases.jsonl 一行）：
     ```json
     {"id": "debug-001", "prompt": "npm install 报错 EACCES permission denied", "category": "debugging"}
     ```
   - 用例数量建议：20-50 个，太少统计不显著，太多评估成本高

3. **隔离评估环境**
   - 关键：**确保 A 和 B 的测试环境完全一致，只有待测变量不同**
   - i-have-adhd 的隔离措施：
     ```bash
     # 隔离用户配置，防止插件/自定义设置污染 baseline
     claude --setting-sources "" --print "..."
     ```
   - 其他隔离要点：
     - 固定模型版本（不能 A 用 claude-3.5-sonnet，B 用 claude-3-opus）
     - 固定温度参数（temperature=0 或固定值，避免随机性）
     - 关闭其他插件/技能（防止其他规则干扰输出）
     - 使用全新会话（没有历史上下文污染）

4. **盲评流程**
   - 原则：**评分者不知道哪个是 A 哪个是 B，避免确认偏误**
   - 流程：
     1. 生成所有测试用例的 baseline 输出（A 组，无规则）
     2. 生成所有测试用例的 experiment 输出（B 组，启用规则）
     3. 随机打乱 A/B 顺序，标记为 X/Y/Z（隐去 condition）
     4. 评分者只看输出，按 Rubric 给每个维度打 1-5 分
     5. 解码后统计两组的平均分差异
   - 盲评能有效消除"我知道这是新规则所以应该更好"的主观偏差

5. **定义 Release Gate（发布门槛）**
   - 必须**全部满足**才能发布：
     1. **无 blocking 问题**：
        - Safety 维度出现 1 分（危险指令）→ 立即 block
        - Correctness 维度出现 1 分（严重事实错误）→ 立即 block
     2. **正确性和安全性不下降**：
        - Correctness 平均分 ≥ baseline
        - Safety 平均分 ≥ baseline
     3. **加权总分高于 baseline**：
        - 按 Rubric 权重计算总分，experiment > baseline
   - 任何一项不满足都不能发布，回到开发阶段修改

6. **可恢复执行**
   - 评估脚本支持断点续跑：
     - 已完成的用例结果缓存，失败后重跑自动跳过
     - 不需要每次都从头开始
   - 实现方式：结果写入文件，存在则跳过
     ```python
     # scripts/run_evals.py 简化逻辑
     if result_file.exists() and not args.force:
         results = json.loads(result_file.read_text())
     else:
         results = run_evals(cases)
         result_file.write_text(json.dumps(results))
     ```

### 反模式（必须避免）

| 反模式 | 危害 | i-have-adhd 中的对应问题 |
|--------|------|--------------------------|
| 只凭主观感受"感觉更好了" | 确认偏误，实际上可能更差 | 早期版本自我感觉良好，评测后发现正确性下降了 15% |
| 评估维度只有"简洁性"忽略正确性损失 | 为了简洁牺牲准确性，用户无法信任输出 | 第一版评测发现简洁性提升了，但正确性掉了 8%，紧急回滚 |
| 不隔离环境导致用户配置污染测试结果 | baseline 被其他插件影响，对比结果无效 | 曾因开着另一个"礼貌话术"插件，导致 baseline 也很啰嗦，对比无意义 |
| 不固定模型版本导致结果不可复现 | 今天测和明天测模型不一样，无法对比 | 固定模型版本后评测结果可复现，R² > 0.9 |
| 没有 blocker 判定导致危险改动流出 | 为了格式好看引入安全风险 | Safety 作为 blocker 维度，曾拦截过一个会生成 `rm -rf /` 示例的版本 |
| 没有盲评导致评分偏差 | 评分者知道哪个是新版本，下意识打高分 | 盲评后新规则的"感知提升"从 30% 降到真实的 12% |

### 迁移验证（其他领域已验证可复用）

A/B 测试是通用的验证方法论，在多个领域验证可迁移：

1. **UI/UX 改版验证**
   - 不能只看点击率（Click-Through Rate）
   - 多维度：任务完成时间、错误率、用户满意度、留存率
   - 示例：按钮从蓝色改成红色可能点击率上升，但退款率也上升了

2. **API 响应格式变更**
   - 对比：开发者集成时间、错误率、文档查阅次数、支持工单量
   - 不能只看"更简洁"——新格式可能更简洁但更难理解
   - 示例：GraphQL vs REST 的争论不能凭感觉，要测实际开发效率

3. **文档改版验证**
   - 对比：任务完成时间、错误率、用户搜索次数、"看不懂"反馈比例
   - 示例：教程从"概念→示例"改成"示例→概念"后，新手完成率提升 25%

4. **Code Review 规则调整**
   - 对比：缺陷逃逸率（线上 bug 数）、评审时间、评审意见接受率、开发者满意度
   - 示例：加了"必须写测试"规则后，评审时间增加了 10%，但线上 bug 减少了 40%

5. **客服话术优化**
   - 对比：问题解决率、平均处理时间、客户满意度（CSAT）、二次进线率
   - 示例：首句给方案的话术，CSAT 提升了 18%，处理时间缩短了 22%

## 模式间关系：组合使用链路

三个模式不是孤立的，而是形成完整的**设计→分发→验证**闭环：

```
┌─────────────────────────────────────────────────────────────────┐
│  模式 1：认知原理驱动输出规范                                    │
│  （设计规则：从认知科学到可执行规则+示例+例外+检查清单）          │
└─────────────────────────────┬───────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  模式 2：跨平台 Agent Skill 适配                                 │
│  （分发规则：核心规则+多平台适配层+双激活模式+opt-in）            │
└─────────────────────────────┬───────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│  模式 3：输出风格 A/B 测试验证                                   │
│  （验证效果：多维度 Rubric+测试用例+盲评+Release Gate）          │
└─────────────────────────────┬───────────────────────────────────┘
                              │
                              ▼
                    ┌─────────────────┐
                    │ 反馈循环回模式 1 │
                    │ （根据评测结果  │
                    │ 迭代优化规则）  │
                    └─────────────────┘
```

### 典型迭代流程：

1. **用模式 1 设计第一版规则**
   - 从认知局限出发，写出规则、示例、例外、检查清单

2. **用模式 2 适配到目标平台**
   - 提取核心 SKILL.md，写各平台适配层，支持按需和 always-on，默认 opt-in

3. **用模式 3 科学验证**
   - 跑评测，发现问题（比如"正确性下降了"）

4. **回到模式 1 迭代规则**
   - 根据评测反馈调整规则（比如"创意任务例外放宽"、"技术场景必须保留上下文"）

5. **重复步骤 2-4，直到通过 Release Gate**
   - 每次修改都重新评测，确保不引入回退

i-have-adhd 项目本身就是这个闭环的产物：从 0.1 版本到 1.0 版本经历了 6 轮这样的迭代，每轮都用评测数据指导修改，最终达到"正确性不下降、可执行性显著提升"的效果。
