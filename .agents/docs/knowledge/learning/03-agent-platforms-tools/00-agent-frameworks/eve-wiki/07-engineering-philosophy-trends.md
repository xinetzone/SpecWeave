# 07 工程化理念与趋势洞察

本章从工程哲学与行业趋势的视角解读 Eve：为什么"能跑"的 Demo 不等于"能管"的生产 Agent；Agent 竞争重心正在从模型能力转向工程底座；以及 Vercel 如何把前端工程化经验迁移到 AI 领域。这是理解 Eve 定位与价值的关键一章。

## 1. "Demo 关注能不能跑，生产关注能不能管"的工程哲学

### 1.1 Demo 很容易做出来

现在做出一个 Agent Demo 已经不难：写一段系统提示词（system prompt，即给模型的前提设定，定义其角色与行为边界）、准备几个工具、调用模型在"思考—调用工具—读取结果—继续思考"的循环（agent loop）中运行，一个能查数据、搜网页、操作文件的 Agent 很快就能跑起来。

### 1.2 放进真实业务，问题立刻出现

但一旦把 Demo 放进真实业务，问题马上出现——这些问题正是 Demo 掩盖下的生产问题：

- 一个任务跑了半小时，中途进程重启怎么办？
- Agent 等用户批准时，连接要一直挂着吗？
- 模型生成的脚本，敢不敢直接在应用服务器上执行？
- 查询日志可以自动做，回滚生产版本是不是也能自动做？
- 同一个 Agent 要接 Web、Slack 和 API，是不是每个入口都要重写一套？
- Agent 做错以后，怎么知道它当时看到了什么、调用了什么工具？
- 改了一句 instructions，怎么确认旧能力没有悄悄退化？

### 1.3 关键判断：这些问题靠"优化 Prompt"解决不了

这些生产问题没有一个能靠"再优化一下 Prompt"解决。过去大家要自己把模型 SDK、工作流引擎、任务队列、状态存储、沙箱、OAuth、审批页面、日志系统和评测框架一件件拼起来。Demo 代码可能只有几百行，但包住它的生产基础设施却很容易膨胀成另一个项目。

因此可以得出一个核心结论：**Demo 里最重要的是"能不能跑"，生产环境里最重要的是"能不能管"**。真实 Agent 的核心问题从来不是能不能循环，而是这个循环能不能在失败、等待和发布过程中保持正确状态。

## 2. Agent 工程化趋势：从模型竞争到工程底座竞争

### 2.1 底层技术栈分层

为了理解 Eve 的定位，可以把底层技术栈分为三层：

| 层次 | 代表性组件 | 解决的问题 |
|------|-----------|-----------|
| 模型与 AI SDK | 大模型、AI SDK | 怎么调用模型、流式输出（streaming，即结果分块实时返回）和工具（tool calling，模型调用外部工具的机制） |
| Agent Loop | 各种 Agent 库 | 怎么观察、行动、获得反馈并继续 |
| Eve | 工程底座 | 这个 Agent 如何持久运行、安全执行、接入业务并进入生产 |

Eve 并没有发明大模型、Tool Calling、工作流、沙箱或 OAuth，而是试图把 Agent 项目反复出现的结构固定下来——就像 Next.js 当年把路由、构建、渲染、数据获取和部署放进一套有明确约定的框架一样。

### 2.2 趋势判断：Agent 开发进入框架化阶段

**Agent 开发开始进入框架化阶段**。以前拼的是谁的模型更强、谁的 Prompt 更花、谁的 Demo 更炫；接下来真正拉开差距的，可能是工程化能力——能不能稳定运行、能不能安全执行、能不能追踪每一步、能不能接入团队系统、能不能像正常软件一样测试、部署和回滚。

### 2.3 Vercel 内部数据佐证

Vercel 内部数据可以佐证这一趋势：

- 超过 100 个 Agent 在生产环境运行；
- 数据分析 Agent 每月处理超过 30000 个问题；
- 一年前由 Agent 触发的 Vercel 部署不到 3%，现在已经接近 29%，Vercel 预计很快会有一半部署来自 Agent。

### 2.4 理性看待

Eve 已提出一套很有 Vercel 风格的 Agent 工程答案，但能否成为事实标准，还要看开发者是否愿意把真实 Agent 放上去跑。截至写作时，Eve 仍处于 beta 阶段，框架、API、文档和行为都可能变化。

## 3. 前端工程化经验向 AI 领域迁移的洞察

### 3.1 Vercel 的标志性打法：把复杂管理变成文件约定

Vercel 最擅长的打法，是把复杂的工程问题变成文件约定——"文件系统即作者接口"（The filesystem is the authoring interface）。开发者熟悉的目录结构、文件名、目录约定，本身就是一种强约束的工程抽象。

### 3.2 前端开发者熟悉的路径在 Eve 中一一对应

前端开发者熟悉的路径，在 Eve 中几乎一一对应：

| 前端惯例 | Eve 中的对应 |
|---------|-------------|
| 目录结构 | Agent 目录（filesystem-first） |
| TypeScript | 用 TypeScript 定义工具 |
| Markdown | 用 Markdown 定义指令与技能 |
| Git | 版本管理、diff 审查 |
| Preview Deploy | 对不同版本建立 Preview 环境 |
| CI | 持续集成校验 |
| Vercel Deploy | 一键部署到生产 |
| Slack/GitHub/Linear Channel | 多渠道接入 |

Next.js 把页面、路由、接口、渲染、部署串起来；Eve 想把模型、工具、知识、审批、沙箱、评测、部署串起来。

### 3.3 "一个 Agent 就是一个目录"

"一个 Agent 就是一个目录"意味着：Agent 的角色、工具、技能和入口都落在普通文件里，可以进入 Git 做版本管理、通过 Pull Request 审查、看到 instructions 修改前后的 diff、对不同版本建立 Preview 环境、出问题时回滚到上一个提交。

### 3.4 核心洞察

核心洞察在于：**Agent 被当成一个正常的软件项目来管理，而不是藏在某个控制台里的一堆配置项**——这是它和很多低代码 Agent 平台最不一样的地方。

## 4. 本章小结

Eve 的工程理念可以概括为三点：

1. **把 Agent 当作正常软件项目管理**：用文件约定替代复杂配置，让 Agent 进入 Git、PR、Preview、回滚等标准软件流程；
2. **Agent 工程化趋势是从模型竞争转向工程底座竞争**：比拼的是稳定运行、安全执行、追踪、接入、测试、部署与回滚等工程能力，而非单纯模型或 Prompt；
3. **对前端开发者而言，Eve 把 Agent 开发带进了熟悉的前端工程体系**：目录 + TypeScript + Markdown + Git + Deploy，降低了进入门槛，也带来了可审计、可回滚的生产保障。
