# 09 FAQ 与最佳实践

## Part A：常见问题 FAQ

### 大类 1：产品与计费

**【问题】免费额度与按量计费如何计算？**

AgentKit Cloud 模式提供新用户首月免费额度：包含 10,000 次 Runtime 调用、5GB Memory 存储、10GB Knowledge 向量存储，超出部分按调用次数和存储容量阶梯计费。Local 模式完全免费，仅需承担本地基础设施成本；Hybrid 模式仅对使用的云端治理服务（Identity/Observability/Evaluation）按量计费。建议前 2 周先用 Local 模式验证业务，评估日均调用量后再切换到 Cloud 模式做成本测算。

**【问题】Local/Hybrid/Cloud 模式成本差异？**

三种模式的成本构成差异显著：Local 模式为纯硬件成本（服务器/数据库），适用于日均调用 <1,000 次的验证阶段；Hybrid 模式为本地硬件 + 云端治理服务费（约占 Cloud 模式总费用的 30%~40%），适用于有数据合规要求的金融/政府场景；Cloud 模式为全托管按量付费，单 Agent 日均调用破万后 Serverless 弹性成本优势显著，总体 TCO 约为自建 Local 模式同规模的 60%~70%。

**【问题】工具调用次数和模型费用是分开的吗？**

是的，AgentKit 计费与火山方舟模型计费完全独立。AgentKit 仅按 Runtime 调用次数、Memory/Knowledge 存储容量、Observability 日志量、Evaluation 评测次数收取平台服务费；模型 Token 消耗由火山方舟单独计费（在方舟控制台查看账单）。工具调用本身不额外收费，但 Gateway 调用外部 REST API 产生的第三方 API 费用由第三方服务方收取。

**【问题】企业版与社区版有哪些功能差异？**

VeADK 开源 SDK 三语言版本（Python/Go/Java）完全免费无功能限制，企业版差异主要在平台侧治理能力：Identity 模块高级功能（自定义 IdP 集成、属性级鉴权策略引擎）、Observability 高级功能（自定义告警规则、90 天以上日志留存、跨租户聚合分析）、Evaluation 高级功能（自动化发布闸门、A/B 实验流量分割）、以及专属技术支持和 SLA 保障（99.9% 可用性承诺）。

### 大类 2：开发与接入

**【问题】存量 REST API 接入要做哪些改造？**

存量 REST API 接入 AgentKit 原则上无需改造业务代码：第一步导出 OpenAPI/Swagger 规范文件（YAML/JSON）；第二步在 Gateway 控制台导入该文件，系统自动生成 Tool 定义（名称/描述/参数 Schema）；第三步配置鉴权方式（API Key / OAuth2 / 自定义 Header）并做连通性测试。对于无 OpenAPI 文档的老系统，可手动在 Gateway 控制台填写 Tool 配置（请求 URL、Method、参数映射模板）。建议接入初期先开启"只读模式"禁止写操作，验证稳定后再逐步开放。

**【问题】MCP Server 和 REST→Tool 两种接入方式如何选择？**

选择遵循「先快速跑通，再渐进优化」原则（对应洞察5）：阶段一全部存量接口用 REST→Tool 转换一键接入（1~2 天完成），Identity 层先配置只读权限白名单，快速验证业务流程；阶段二用 Observability 调用数据筛选 Top 20% 高频接口（日均调用 >100 次），逐个改造为 MCP Server 获得流式响应、结构化错误码、更优性能。改造评估三指标：调用频率、响应延迟要求（P95 > 2s 优先流式 MCP）、错误处理复杂度。

**【问题】非火山方舟自定义模型是否支持？**

支持。VeADK 通过 LiteLLM 兼容层支持接入任意主流模型供应商（OpenAI / Anthropic / 智谱 AI / 月之暗面 / 本地部署模型等），在 Harness 配置中指定 LiteLLM 的 model endpoint 和 API Key 即可切换。建议通过配置文件或环境变量管理模型 endpoint，避免代码硬编码，后续可在 Session 内动态热切换模型。Cloud 模式下自定义模型接入需在 Identity 中配置出站白名单，确保网络可达。

**【问题】现有 LangChain/LlamaIndex 项目如何迁移？**

VeADK 与主流框架生态完全兼容：LangChain Tool 可直接包装为 AgentKit Tool（使用 `@app.tool` 装饰器 + LangChain Tool 调用内部实现）；LlamaIndex 索引可直接对接 Knowledge 模块的自定义检索接口。迁移路径建议：① 保留现有 LangChain/LlamaIndex 业务逻辑代码；② 用 VeADK 的 `@app.entrypoint` 替换原有入口函数；③ Gateway 接入复用原有 REST Tool；④ Local 模式验证通过后再逐步启用 Identity/Observability/Evaluation 治理能力。

### 大类 3：运行与运维

**【问题】冷启动慢怎么优化？**

冷启动优化分三个层面：代码层面（① 减少 `@app.entrypoint` 启动时的重型依赖加载，大模型客户端/数据库连接改为懒加载；② 避免启动时全量加载知识库索引，按需分片载入）；平台层面（① Cloud 模式配置"预热实例池"保持 N 个常驻实例，新请求直接命中热实例；② Hybrid 模式本地 Runtime 使用常驻进程而非每次冷启动）；数据库层面（Memory/Knowledge 使用连接池 + Redis 缓存热点会话数据，减少 DB 查询）。优化后典型冷启动时间可从 5~10s 降至 <1s。

**【问题】会话记忆会无限增长吗？上限和清理策略？**

不会无限增长，Session 与 Memory 遵循独立的生命周期策略（对应洞察3）：Session 数据（短期记忆）默认 TTL 为 7 天，超过 24 小时未继续对话自动归档，超过 TTL 自动删除（可在配置中自定义 TTL）；Memory 数据（长期记忆）有写入闸门（自动去重 + 质量打分），默认单租户 Memory 存储上限为 100GB（企业版可扩容），超过 3 个月未被召回的 Memory 条目自动降权转入冷存储。建议每月执行一次「知识半衰期」审计，清理过时或错误的 Memory 条目。

**【问题】Serverless 模式下如何做故障排查？**

Serverless 模式排障依赖 Observability 全链路 Trace：第一步在 APMPlus 控制台按 Trace ID 定位异常请求（或按用户 ID / 时间范围 / 错误码搜索）；第二步查看 Trace 五大环节（模型调用 / Runtime 执行 / Gateway Tool / Knowledge 检索 / Memory 读写）各节点的耗时、状态码、输入输出摘要；第三步若某环节异常，点击跳转 TLS 日志详情查看上下文。常见异常 90% 可通过 Trace 定位根因，剩余 10% 需拉取容器 stdout/stderr 日志分析（Cloud 模式在控制台「运行日志」标签页查看）。

**【问题】多 Agent 场景如何防止跨 Agent 权限穿透？**

A2A 多 Agent 场景必须在 Gateway 层为每个 Agent 分配独立的 Tool 访问白名单（对应洞察2落地建议2）：① 每个 Agent 在 Identity 中有独立身份标签，区别于人类用户和其他 Agent；② Gateway 配置「Agent-用户-工具」三维权限矩阵：A Agent 只能调用白名单内 Tool，即使通过 B Agent 转发请求，Gateway 仍校验原始 Agent 身份；③ 禁止 Agent 之间互相调用敏感写操作 Tool，如需跨 Agent 传递写操作，必须通过中间审批 Agent 附加人类二次确认。

### 大类 4：安全与合规

**【问题】用户数据和知识库数据会被模型训练使用吗？**

不会。火山引擎 AgentKit 遵循「数据所有权归属客户」原则：用户输入输出数据、Session/Memory/Knowledge 存储数据默认仅用于服务当前客户业务流程，不用于任何模型训练或产品改进。如需启用「使用客户数据微调专属模型」，必须经过客户书面授权并签署补充协议，且微调后模型仅在客户专属实例中部署，不会与其他租户共享。建议在合规审计中导出数据处理流程图并留存客户授权记录。

**【问题】Agent 调用内部系统日志如何做合规审计？**

合规审计日志由 Gateway + Observability 双模块联动生成：① Gateway 作为所有外部系统调用的统一入口，自动记录每次 Tool 调用的请求参数、响应摘要、状态码、调用方 Agent ID、鉴权结果、Trace ID；② TLS 日志服务持久化存储上述日志，默认留存 ≥90 天（金融/医疗行业可配置 ≥180 天）；③ 审计后台支持按用户 ID、时间范围、Tool 名称、会话 ID 多维度组合检索，日志采用 Append-only 写入模式，写入后哈希校验防止篡改。建议每季度对审计日志做一次抽样合规检查。

**【问题】多租户数据隔离原理？如何验证？**

Cloud 模式多租户采用「逻辑软隔离 + 配置硬隔离」双层机制：逻辑层所有数据访问强制透传租户 ID 字段，数据库查询自动注入 `WHERE tenant_id = ?` 条件，跨租户查询直接返回 403；配置层每个租户有独立的 Runtime 命名空间、独立的 Memory/Knowledge Schema、独立的 Identity 权限边界。验证方法：构造 10+ 条跨租户访问测试用例（使用租户 A Token 查询租户 B 会话记录、知识库条目、工具调用日志等），全部拦截即为隔离生效。强合规场景可升级为硬隔离（每个租户独立 Runtime 实例）。

**【问题】如何预防 Prompt 注入攻击？**

多层防御体系：① 输入侧护栏：Identity 模块配置敏感词拦截、典型 Prompt 注入模式检测（角色扮演忽略系统提示、编码后恶意指令等），对抗测试用例 ≥10 条全部拦截；② Gateway 权限约束：遵循最小权限原则，即使 Prompt 注入成功，Agent 也只能调用白名单内有限工具，无法触及敏感写操作；③ 输出侧校验：高风险领域（金融/医疗）启用事实幻觉检测和合规输出校验。建议每月更新对抗测试用例集（参考 OWASP LLM Top 10），并在 Evaluation 模块中纳入回归测试。

## Part C：4 条架构决策最佳实践

### 1. 存量系统接入：先 REST 快速跑通，再 MCP 深度优化

**实践要点（对应洞察5 + P-LEGACY-AI-UPGRADE-002）：**
1. 先按「调用频率 × 业务价值」将存量 API 分 ABC 三级，优先接入 A 级（Top 20% 高频+高价值）
2. 阶段一用 Gateway REST→Tool 转换 1~2 天批量接入，Identity 层先配置只读权限白名单
3. 阶段二用 Observability 调用数据筛选 Top 20% 高频接口，按「调用频率>100次/天、P95延迟>2s、错误码>3种」三指标评估 MCP 改造优先级
4. MCP 改造采用灰度切换：新旧双轨并行观察 ≥3 天，错误率无上升再切流 100%
5. 敏感写操作接口（创建/修改/删除）全程保留「人类二次确认」网关拦截

### 2. 部署路径：Local 调试 → Hybrid 预发 → Cloud 生产三阶段渐进

**实践要点（对应洞察4）：**
1. 第一阶段 Local 模式：VeADK 本地 SDK + Platform 服务 mock，零配置快速验证 Entrypoint→Tool→Output 业务逻辑（耗时 1~3 天）
2. 第一天起所有配置（镜像仓库、Platform endpoint、AK/SK）通过环境变量或 `cli config` 统一管理，代码零硬编码
3. 第二阶段 Hybrid 预发：本地 Runtime + 云端 Identity/Gateway/Observability/Evaluation，单独执行 `cli config` 配置并做三项 Platform 服务连接性预检
4. 第三阶段 Cloud 生产：通过 `cli launch` 一键构建部署，发布前执行 12 项检查清单
5. 每阶段切换后保留至少 3 天并行观察期，核心指标（错误率/延迟/成本）无劣化再推进下一阶段

### 3. 工具治理：从 0 开始建立 Tool Registry

**实践要点（对应洞察2治理外环优先原则）：**
1. **命名规范**：Tool 名称统一 `{域}_{动作}_{对象}`（如 `crm_query_customer`），描述中必须包含业务含义、参数约束、典型调用示例三要素
2. **元数据完整**：每个 Tool 在 Registry 中登记：负责人、所属系统、超时阈值、重试策略、幂等性标记、SLA 等级、敏感级别（读/写/高危）
3. **权限矩阵**：建立「Agent 角色 × 人类用户角色 × Tool 白名单」三维权限映射表，遵循最小权限原则，写操作工具单独审批
4. **超时熔断**：所有 Tool 默认超时 30s、幂等 Tool 最多 2 次指数退避重试、5 分钟错误率 >30% 自动熔断返回降级响应
5. **版本管理**：Tool 升级须向后兼容，破坏性变更需创建新版本（`_v2` 后缀），旧版本保留 3 个月过渡期后下线
6. **定期审计**：每月扫描 Registry，移除 90 天内零调用 Tool，更新调用率 Top 20% Tool 的 MCP 改造优先级

### 4. 质量闸门：新功能上线前必须通过 Eval 50 条 + 通过率阈值

**实践要点（对应洞察2 Evaluation 绑定发布闸门）：**
1. 评测集结构：核心场景 20 条（覆盖 80% 高频用户诉求）+ 边缘场景 20 条（边界条件/异常输入/长上下文）+ 对抗场景 10 条（Prompt 注入/越权/幻觉诱导）
2. 通过率标准：整体 ≥90% 且核心场景 ≥95%，任一类场景低于阈值即拦截发布
3. 自动化绑定：Evaluation 流程嵌入 CI/CD Pipeline，PR 合入或版本发布前自动触发评测，分数未达标自动打回并生成失败用例报告
4. 持续扩充：每发现 1 例线上生产 Bug，对应补充 2 条评测用例（1 条精确复现 + 1 条同类泛化），形成「生产 Bug → 评测集扩充 → 防回归」正循环
5. 版本对比：新版本评测结果必须与上一稳定版本做横向对比，核心场景准确率下降 >2% 即使绝对通过率达标也需人工复核
