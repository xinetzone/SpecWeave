# 平台提审合规预检 Skill

> 萃取自 2026-10-26 微信小程序提审被拒实战：代码审核未通过，原因为
> 「小程序内涉及收集『选中的照片或视频信息』相关接口或组件，请通过接口完善【用户隐私保护指引】后再重新提审」。
> 本 Skill 把「提审会不会被拦」从一次试错，变成**提交前就能跑出结论**的本地检查。

## 1. Skill ID

`platform-review-precheck`

## 2. 功能描述

平台的提审拦截是**逐项比对**：

```
本次提审版本的隐私接口调用情况  ⊆  已填写的《用户隐私保护指引》所声明的「处理的信息」类型
```

任一类型缺失 → 拦截；协议为空 → 直接拦截。

这意味着**协议清单的唯一事实来源是代码**——不是你以为用了什么，而是你实际调了什么。
本 Skill 把这条链路做成三个本地动作：

| 动作 | 脚本 | 回答的问题 |
|---|---|---|
| **提取调用面** | `scan_privacy_calls.py` | 代码实际调了哪些隐私接口 → 必须声明哪些信息类型 |
| **对账** | `check_declaration_alignment.py` | 声明面覆盖调用面了吗？授权兜底接了吗？有死项吗？ |
| **生成声明草稿** | 人工誊写（模板见 references） | 协议正文怎么写才能过审 |

> **为什么必须用脚本而不是人肉核对？** 因为审核比对的是「接口 → 信息类型」的**映射**，
> 而不是接口名本身。`wx.chooseMedia` 和 `wx.chooseImage` 都映射到「收集你选中的照片或视频信息」——
> 人肉看接口名容易漏掉「多个接口映射到同一类型」和「组件型调用（`open-type="getPhoneNumber"`）
> 不在接口清单里」这两类。

> **为什么映射表要写进脚本常量、而不是每次查文档？** 因为审核是**逐项比对**，
> 差一个类型就整单被拦；而查文档是人工动作，改代码的人未必会想到去查。
> 把表固化成常量后，「改代码 → 跑扫描器 → 拿到必声明清单」成为一条可重复的流水线。

> **为什么区分 strong / weak / gone 三级？** 因为静态分析判不了运行时上下文：
> `input type="nickname"` 存在不代表用户真填过。**误报比漏报更伤**——
> 满屏告警的工具会被直接弃用。所以只有结构上必然触发拦截的（缺声明/缺兜底/无协议）才判 FAIL。

## 3. 何时使用

- **提审被拒**，错误信息里出现「涉及收集 XXX 相关接口或组件，请完善【用户隐私保护指引】」；
- **提审前**自检：想避免用一次提审机会去试错；
- 改动了**隐私相关调用**（新增 `wx.chooseMedia`、加了 `open-type="getPhoneNumber"` 按钮），
  需要确认声明面是否要同步；
- 审查别人提交的小程序代码，判断**能不能过审**。

**不适用**：功能逻辑正确性、性能、安全渗透、以及不涉及平台审核规则的普通代码质量审查。

## 4. 核心步骤

1. **扫描调用面**：`python scripts/scan_privacy_calls.py <项目根>` →
   列出全部隐私接口调用点 + 必须声明的「处理的信息」类型清单。
   ⚠️ 脚本会先做**项目类型判定**（D0）：不是微信小程序工程会明确提示换手段，不会硬跑。
2. **对账**：`python scripts/check_declaration_alignment.py <项目根>` → 五道门 D0~D4：
   - **D0** 目标是微信小程序工程（不适用则停，别硬套）
   - **D1** 声明面覆盖调用面（FAIL 即被拦截项）
   - **D2** 声明面无死项（声明了但没调，多余声明会被追问）
   - **D3** 隐私接口有授权兜底（`onNeedPrivacyAuthorization` / `requirePrivacyAuthorize`）
   - **D4** 平台侧声明文件存在且非空
3. **补声明**：按扫描输出，在仓库内维护一份《用户隐私保护指引》草稿
   （建议 `docs/privacy-declaration.md`），模板见 `references/declaration-template.md`。
4. **补兜底**：在 `app.js` 注册 `wx.onNeedPrivacyAuthorization`，
   在调用点前用 `wx.getPrivacySetting` + `wx.requirePrivacyAuthorize` 显式校验。
5. **誊到平台**：提审时在**管理 → 版本管理 → 提交代码审核 → 信息填写页面**（入口2）
   把草稿内容填进平台的隐私协议表单——**仓库里有文件不等于平台已声明**。
6. **固化**：把 D1~D4 写成项目内的回归断言（可参考
   `apps/jieban-zhilv-mp/tests/structure.test.js` 的「隐私合规面」段）。

## 5. 五道门的判据

| 门 | 判据 | 级别 |
|---|---|---|
| **D0** | 目标是微信小程序工程（`project.config.json` 的 `compileType=miniprogram`，或 `app.json`+`app.js`） | FAIL |
| D1 | 代码调用的每个隐私接口所映射的信息类型，都出现在声明文本中 | FAIL |
| D2 | 声明中的每个类型都有对应调用（无死项） | WARN |
| D3 | 检出隐私接口调用时，全仓存在授权钩子 | FAIL |
| D4 | 仓库内存在《用户隐私保护指引》声明文件且非空 | FAIL |

> **为什么要有 D0**：本 Skill 的映射表与声明格式**只对微信小程序成立**。
> 在非小程序项目上强行跑，会输出「必须在《用户隐私保护指引》中声明」这种无意义的结论——
> 那是**虚假通用性**：看起来通用，实际换个平台就全错。
> D0 拦在所有门之前，先确认适用再检查。

**分级原则**：静态分析判不了「这个接口在本项目里是否真被触发」，
也分不清 `input type="nickname"` 是否真被用户填过。
因此凡结论依赖运行时上下文的，一律标 WARN 要求人工确认；
只有**结构上必然触发拦截**的（缺声明 / 缺兜底 / 无协议）才判 FAIL。
**误报比漏报更伤**——满屏告警的工具会被直接弃用。

## 6. 反模式（均来自真实教训）

1. ❌ **把「代码里没报错」当作「能过审」**
   实测：开发者工具里 `wx.chooseMedia` 正常工作，测试全绿，HTTP 实测全通，
   提审照样被拦。→ **本地可测的面 ≠ 平台审核的面**，前者再全也覆盖不到后者。
2. ❌ **协议里写了「我收集了照片」就以为声明了**
   实测：平台比对的是**接口映射出的标准类型名**（「收集你选中的照片或视频信息」），
   自己写「收集你选中的照片」不算数。→ 按官方措辞写，别自造表述。
3. ❌ **只声明不兜底**
   实测：声明齐了但没接 `wx.requirePrivacyAuthorize`，
   用户未同意时接口**静默失败**——不抛错、不回调，用户只看到「点了没反应」。
   → 声明（平台侧）与兜底（代码侧）是两件事，缺一不可。
4. ❌ **只兜底不声明**
   实测：授权钩子接了、弹窗也弹了，但协议里没声明该类型 →
   平台直接禁用对应接口，授权同意也没用。→ 两侧都要做。
5. ❌ **以为 SDK 生成的隐私清单就是平台声明**
   实测：云服务 SDK 会在项目根生成 `.<applicationId>.privacy.json`（描述云端侧采集的
   `Album` / `PhoneNumber` / `UserInfo`）——那是**云服务侧**的清单，
   与**微信平台侧**的《用户隐私保护指引》是两套东西，名字都叫 privacy 但互不相认。
   → 平台声明必须单独维护。
6. ❌ **用 `saveImageToPhotosAlbum` 的经验套 `chooseMedia`**
   实测：「相册（仅写入）」与「选中的照片或视频信息」是**两个不同的类型**，
   只声明前者不声明后者，仍会被拦。→ 逐个接口查映射表，别类推。

## 7. 检验标准（做完怎么知道做对了）

1. **扫描器退出码 0 或仅 WARN**：无 FAIL 级未声明项。
2. **对账器 FAIL=0**：D1~D4 全过（退出码 0）。
3. **协议文本命中官方措辞**：声明中出现的类型名与扫描器输出完全一致。
4. **授权兜底可验证**：模拟 `getPrivacySetting` 返回 `needAuthorization: true`
   时，调用点走拒绝分支并给出可读提示，不静默失败。
5. **回归断言在 CI 里**：改坏声明面或删掉兜底，测试必须红。

## 8. 迁移示例（非本领域）

- **App Store 审核**：把「调了哪些受管控 API」与「App Privacy Nutrition Labels 声明了什么」
  做同样的对账；标签缺项同样在**提交时**被拒，而不是上架后。
- **企业微信自建应用**：可信域名未配置 → 接口调用被拒；
  对账轴从「隐私类型」换成「域名白名单」，方法论同构。
- **政务小程序**：额外叠加「内容安全审核 API 未接入」类硬性要求，
  可在同一对账器上增加第二张表。

## 9. 脚本

| 脚本 | 作用 | 退出码 |
|---|---|---|
| `scripts/scan_privacy_calls.py <根目录>` | 提取隐私接口调用面，输出必须声明的信息类型清单 | 有 FAIL → 1 |
| `scripts/check_declaration_alignment.py <根目录>` | 断言 D0~D4 | 有 FAIL → 1 |
| `scripts/selftest.py` | 对内置前后对照夹具自检两个工具 | 失败 → 1 |

常用参数：
- `--json` 机器可读输出；
- `--declaration <路径>` 指定声明文件（默认自动探测仓库内含「隐私保护指引」的文件）；
- `--only D1,D2` 只跑指定门；
- `--verbose` 打印命中行原文。

## 10. 安全检查清单

执行本 Skill 前逐项确认：

- [ ] 目标是小程序/应用**提审前或被拒后**的合规检查（不是功能逻辑审查）
- [ ] 已知本次提审的**平台**（微信 / App Store / 企业微信），映射表对得上
- [ ] 扫描范围包含**全部源码目录**（wxml/js/json 都在内，组件型调用只在 wxml 里）
- [ ] 已确认声明文件位置（默认探测；多份声明时用 `--declaration` 显式指定）
- [ ] **只读检查**：本 Skill 不写平台后台、不提交提审，誊写动作由人执行
- [ ] 已把「本地无法自测的面」（协议是否已在平台生效）单独列为待人工确认项

**幂等性**：本 Skill 的两个脚本**全部只读**，不修改任何文件、不写任何平台状态。
重复执行结果一致，可安全挂 CI。

## 12. Gotchas

- **别把 `wx.` 前缀写死在匹配里**：项目常有封装层，调用形态可能是 `cloud.chooseMedia()`；
  扫描器用「可选 `wx.` 前缀 + 紧跟左括号」匹配，但**只登记在官方映射表里的接口名**——
  宁可漏报不可虚报。
- **别放宽到裸函数名**：实测一个非小程序项目里的 `function pick(){ return chooseMedia({...}) }`
  被误报成 `wx.chooseMedia`——**误报比漏报更伤**，满屏假警报的工具会被直接弃用。
  微信隐私接口在代码里一律写作 `wx.<api>`，扫描器因此**强制要求 `wx.` 前缀**。
- **别在非小程序项目上跑这个 Skill**：映射表与声明格式都只对微信小程序成立（D0 门拦截）。
  换个平台就得换映射表与声明模板——通用的是「对账」这个动作，不是这张表。
- **别在注释里找调用点**：注释中的 `wx.chooseMedia` 会让「调用点早于授权兜底」的顺序断言恒为假。
  判定顺序前先剥注释。
- **别用方法定义处的索引做顺序断言**：`ensurePrivacyAuthorized()` 的**定义**一定在**调用**之前，
  拿定义处索引判断「先授权后调用」会得到错误结论。用调用形态（如 `this.xxx()`）匹配。
- **别把「仓库里有声明文件」当作「平台已声明」**：D4 只管仓库侧；
  真正生效要誊到 mp 后台的提审入口2。两者是**两份内容**，不是一份。
- **别漏组件型调用**：`open-type="getPhoneNumber"` / `open-type="chooseAvatar"` /
  `input type="nickname"` 不在接口清单里，但在审核比对范围内。
- **别把已回收接口当普通隐私接口**：`wx.getUserProfile` / `wx.getUserInfo` / `open-type="userInfo"`
  已被官方回收，命中应报 FAIL（不可用），而不是「去补声明」。
