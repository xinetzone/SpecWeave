# 实证案例：微信小程序提审被拒（2026-10-26）

## 1. 事件

小程序「道德大师兄」代码发布审核未通过。

**审核原文**：

> 你的小程序"道德大师兄"，提审时间 2026-10-26 14:30:58，代码发布审核未通过，原因如下：
> 1:小程序功能不符合规则:
> (1):你好，小程序内涉及收集"选中的照片或视频信息"相关接口或组件，
> 请通过接口完善【用户隐私保护指引】后再重新提审。

**判读**：拦截项是**一个类型**——「收集你选中的照片或视频信息」，
按官方映射表对应 `wx.chooseImage` / `wx.chooseMedia` / `wx.chooseVideo` 三个接口。
即：代码调了选图接口，但《用户隐私保护指引》里没有这一条。

## 2. 为什么本轮才发现

上一轮（`sc-20261026-jieban-zhilv-milestone`）对这个项目做了：

- 46 个非图片文件 / 6096 行源码逐行审阅
- 27 条对抗审查发现（两轮，含 2 条 P1）
- 数据面 HTTP 实测（业务列 200 / `select=owner_id` 401 / RPC 200）
- 回归测试 32/32 + 46/46 全绿
- 萃取可复用 Skill `public-value-audit`

**全部通过，但提审被拒。**

原因不在执行质量，而在**审查面本身选错了**：
上一轮的所有验证都落在「**运行时数据面**」——
这个面能自测、能复现、能写进 CI。
而平台审核落在「**声明面**」——这个面：
- 不在代码里，在 mp 后台的表单里；
- 本地无法观测（协议填没填、填全没填全，本地跑一百遍测试都看不到）；
- 唯一的观测手段是**提交一次提审**。

**自测可达面 ≠ 平台审核面。** 这是本次最核心的一条。

## 3. 同型缺陷在本地项目中的实证

用本 Skill 的扫描器扫 `apps/jieban-zhilv-mp`（结伴之旅）：

```
[FAIL] wx.chooseMedia → 收集你选中的照片或视频信息
      pages/signup/signup.js:165
```

**同一个拦截类型，在另一个项目里已经存在。**
说明这不是「道德大师兄」这一个项目的偶发问题，
而是**只要用了选图接口就会命中**的通用形态。

## 4. 根因拆解

| 层级 | 现象 | 根因 |
|---|---|---|
| 表层 | 协议缺「收集你选中的照片或视频信息」 | 没填或填不全《用户隐私保护指引》 |
| 中层 | 填了也不知道要填 | 不知道「接口 → 信息类型」存在**官方映射表** |
| 中层 | 填了协议也不生效 | 协议在 mp 后台，仓库里没有任何痕迹，**改代码时无从感知需要同步** |
| **深层** | 上一轮 27 条对抗审查发现无一命中 | **审查面只覆盖运行时数据面**，声明面被整体漏掉 |

深层这条是本次最有价值的发现——
它不是「这次漏填了」，而是**「审查清单里没有这一项」**。

## 5. 整改内容（结伴之旅）

### 5.1 代码侧补授权兜底

新增 `utils/privacy.js`：

- `getPrivacySetting()` —— 查询用户是否已同意
- `requirePrivacyAuthorize(onGranted, onDenied)` —— 调用前显式校验，失败转可读提示
- `registerPrivacyAuthorization()` —— 在 `app.js` 的 `onLaunch` 注册平台授权响应

改造 `pages/signup/signup.js`：

```js
const granted = await this.ensurePrivacyAuthorized()
if (!granted) {
  return
}
// ... wx.chooseMedia(...)
```

**顺序铁律**：授权兜底必须**早于**隐私接口调用。
顺序反了等于没兜底——`ensurePrivacyAuthorized` 定义在方法上方，
但 `this.ensurePrivacyAuthorized()` 的**调用**必须在 `wx.chooseMedia` 之前。

### 5.2 声明侧补协议草稿

新增 `docs/privacy-declaration.md`，按官方板块结构写全，
并附「信息类型 ↔ 代码位置」对照表（由扫描器生成，防漂移）。

### 5.3 补回归断言

`tests/structure.test.js` 新增「隐私合规面」段（4 条）：

1. 存在平台侧隐私声明文件
2. 隐私声明覆盖代码调用的隐私接口
3. 隐私接口调用前有授权兜底（`utils/privacy.js` + `app.js` 双点）
4. 隐私接口调用点已接入授权兜底（**顺序断言**）

第 4 条在实现时踩了两个坑，都写进了 Skill 的 Gotchas：

- 用方法**定义**处的索引做顺序判断 → 恒为真（定义总在调用前）；
- 注释里出现的 `wx.chooseMedia` 被当成调用点 → 顺序恒为假。
  正确做法：**先剥注释再匹配**，且用调用形态（`this.xxx()`）定位。

## 6. 整改后验证

```
$ python .agents/skills/platform-review-precheck/scripts/check_declaration_alignment.py apps/jieban-zhilv-mp
[PASS] 平台侧声明文件存在（D4）
[PASS] 声明面覆盖调用面（D1）
[WARN] 声明面存在无调用对应的条目（D2）
[PASS] 隐私接口调用存在授权兜底（D3）
FAIL=0  WARN=1
```

D2 的 WARN 是**真实且正确**的：`手机号` 与 `昵称、头像` 由云服务 SDK 的
`signInWithWechat` 链路取得，不走 `wx.getUserProfile`，
静态扫描器看不到——这类结论依赖运行时上下文，按分级原则标 WARN 要求人工确认，
而不是判 FAIL。

回归：`format.test.js` **32/32**、`structure.test.js` **50/50**（46 + 4 新增）。

## 7. 可迁移结论

1. **本地可测的面 ≠ 平台审核的面**——提交前必须有一道「本地无法验证的面」的检查。
2. **协议清单的事实来源是代码**，不是开发者的记忆或意图。
3. **声明（平台侧）与兜底（代码侧）是两件事**，缺一不可：只声明则用户拒绝时静默失败，
   只兜底则平台直接禁用接口。
4. **改名不等于改名**：SDK 生成的 `.<appId>.privacy.json` 与 mp 后台的
   《用户隐私保护指引》名字都含 privacy，语义完全不同。
5. **审查清单要显式列出「本地不可自测的面」**——否则它永远排在验证范围之外。
