# 证据矩阵与结论边界

## 先写待验证命题

将“这个建议合理”拆为可核实的命题，例如：存在重复执行步骤、某条用户纠正改变了目标、某工具失败后确实复跑、现有某目录未发现覆盖功能。每个命题独立判定，不用总印象代替证据。

| 命题 | 来源定位 | 直接证据 | 判断 | 缺口/范围 |
|---|---|---|---|---|
| 用户更改目标路径 | sessionId / revision / messageId / user text | 必要的最小片段 | 已证实或未知 | 仅证明当时需求 |
| 某次编辑失败 | sessionId / messageId / tools 索引 / output 区间 | 原始报错 | 已证实 | 错误原因是否明确 |
| 修改后验证通过 | 同一快照或注明跨 revision 的操作与复跑定位 | 原始结果、退出码及样本范围 | 已证实/部分证实 | 是否在最后修改之后 |
| 没有已有 Skill 覆盖 | 搜索工具输出及实际目录范围 | 搜索范围与结果 | 局部支持 | 未搜目录不能包含在结论中 |

推荐 JSON 与助手摘要放在“待验证命题/线索”栏，不放在“直接证据”栏。用户说“成功了”可证明用户的反馈，但不能替代缺失的测试记录。

## 推荐前提与后续消息对照

先登记推荐明确引用的时间或快照；未提供时写“推荐基准未知”，不要用读取时间冒充生成时间。再按消息顺序和可用时间戳定位后续变化，同一会话的 revision 仅用于辨别快照，不跨会话比较大小。

逐项记录“原命题 → 原依据 → 后续证据 → 当前修正”，保留仍成立的前提。每项写明审计截至哪个已读快照；若后续历史未返回、字段截断或任务仍在执行，标注不能判断的部分，不补写最终结果。

下表是合成命题，不是真实会话记录；实际使用时用完整来源定位替换“早期/后续”等文字。

| 推荐原命题 | 推荐基准/原依据 | 后续消息/工具定位 | 已证明的状态 | 当前修正 | 缺口/范围 |
|---|---|---|---|---|---|
| 方案尚无人要求推进 | 早期仅有助手建议 | 后续用户要求细化清单 | 已要求细化 | 不再描述为无人要求推进 | 未明确确认全部条件，效果未知 |
| 只有待确认提案 | 早期无执行授权或产物 | 后续用户授权、写入及对应校验 | 指定产物已交付并通过所列校验 | 更新交付状态，保留早期阶段事实 | 不证明实际使用或商业效果 |
| 已确认整套方案 | 用户仅确认一个交付格式 | 后续用户拒绝其中的服务条件 | 局部确认、局部拒绝 | 按对象拆分，不保留整体确认结论 | 其余条件仍待确认 |
| 没有验证结果 | 早期只有方案 | 后续实际样本、指标和结果记录 | 已有范围明确的实测 | 按结果写支持、不支持或仍不确定 | 不外推到未覆盖人群、时间或指标 |

## 状态边界与合成正反例

将方案提出、用户要求细化、明确确认、产物交付和效果验证分别登记；这是证据类别，不是自动递进的等级。为每项标注已证实、部分证实、被后续撤回或证据不足，并附对象与范围；没有证据的状态保持未知。

| 合成观察 | 合理判定 | 错误判定 |
|---|---|---|
| 助手提出诊断方案，用户尚未回复 | 方案已提出；用户态度、交付、效果未知 | 用户已认可 |
| 用户要求细化交付清单并生成模板 | 已要求继续细化；不能推定价格、成本与服务条件均获确认 | 整套方案已确认且商业验证成功 |
| 用户明确确认仅生成 Markdown，不要发布 | 确认限于指定格式和生成动作；发布未授权 | 可以发布、提交或迁移目录 |
| 工具显示文件写入成功，但必要检查未执行 | 产物已写入；校验与交付验收状态单列 | 完成交付且验证通过 |
| 同一产物写入后，约定格式和引用检查通过 | 已证明该产物及所列检查；效果仍未知 | 模板交付证明客户转化有效 |
| 用户称效果很好，没有样本或指标记录 | 用户正向反馈已证实；独立效果证据不足 | 客观效果验证通过 |
| 实测记录有样本、时间范围、指标和对照，结果未达预定目标 | 已做效果验证，但该次结果不支持成功声明 | 有实测即验证成功 |
| 早期“仅提案”，后续已有确认与交付 | 保留时序并修正当前状态 | 全会话仍只有提案，或早期也已完成 |
| 后续消息撤回旧方案，改为另一交付物 | 旧确认不再代表当前选择；新交付另核实 | 用早期确认覆盖后续拒绝 |
| 一个来源已交付，另一个来源仍在运行或被截断 | 分来源、分产物标注截至已读快照的状态 | 一个完成就等于所有来源全部完成 |

> **为什么？** 用户态度、产物完成度和实际效果回答不同问题；逐项更新才能同时避免低估后续进展和夸大成功。

## 技能源可写性、工作流写能力与已观察执行

以下为合成观察，不是真实会话记录。三轴分别取证，任何一项都不能替代另一项。

| 合成观察 | 合理判定 | 错误判定 |
|---|---|---|
| 推荐称“已调用技能都是只读”，但某技能正文含写入步骤 | 该“只读”最多描述工作流；源可写性与覆盖范围另行核实 | 因此这些技能源可编辑，或因此必须新建 |
| 某交付技能会写产物，其源位于项目 `.agents/skills/` | 工作流会写；源可编辑，但能否并入取决于覆盖范围与用户意图 | 写入型技能不能承载只读审计 |
| 用户把新建目标从用户级技能根改为 `.agents/skills` | 目标目录以用户指令为准，重新探查该路径 | 沿用推荐默认路径 |
| 历史会话中确有文件写入且工具成功 | 已观察执行含写入 | 该写入已获当前授权，或技能源因此可改 |
| 会话调用了 CLI 内置或镜像技能 | 可调用不等于可编辑 | 调用过就可以修改源文件 |

> **为什么？** 推荐里的“只读”“已有技能”多为工作流描述；把它直接当作创建/更新资格，会把源可编辑性与覆盖范围这两个真正判据挤掉。

## 定位规则

优先使用：来源 `sessionId` → 快照 `revision` 和输入文件 `snapshotSha256` → `messageId/turnId` → JSON pointer → 字符 `[start,end)`。缺少 ID 时明确注明，仅用当前快照索引定位，不伪造 ID。

- `messages/3/tools/2/output` 表示保存 JSON 里的第四条消息、第三个工具输出；它不是源会话的第四个用户回合。
- 文件目录所含会话 ID 可能属于调用者，只有文件内 sessionId 能说明该 JSON 声称的来源。
- 主会话中的工具输出可能引用另一会话。登记“主来源 → 内嵌引用 → 是否独立读取”，未读取的只称为内嵌预览。
- 已读边界可写“最近 N 回合、工具输出已开启、单条预算 X、hasMoreBefore=true；另有两条截断，未覆盖更早历史”。这些数值须来自实际调用和返回，不能从脚本计数推测。
- 扩窗后先比较 `messageId/turnId` 集合：集合扩大才算覆盖推进；集合不变而只有字段变长，只能写“同一批消息内容变深”；集合不变且 `hasMoreBefore=true`，写“扩窗停滞、更早前缀不可达”。
- 暂存路径可用于当次私域排查，不能成为通用文档的永久依赖。

## 失败与修复链

按时间或 turnId 排列，但不要假设每条助手消息对应一个完整回合：

1. 用户期望和当前阶段。
2. 工具尝试与直接输出。
3. 原因：输出明确说明 / 证据支持的推断 / 尚未确认。
4. 修复动作的可见证据。
5. 最后修改后的复跑、范围及真实结果。
6. 未解决项，以及为何不影响或仍阻断当前结论。

如果命令未保存在工具对象中，写“命令参数不可见；输出显示……”，不要补写一个合理命令并称它为历史命令。若后来自己复现，另列“本次复现”，不能混进历史证据。

## 合成示例：候选不等于失败

以下数字和标识仅用于说明判定，非真实会话样本或回归结果。

| 观察 | 合理判定 | 错误判定 |
|---|---|---|
| Bash 状态 completed，输出 Exit code: 1 | 工具返回了结果，业务命令是否符合预期仍需核对 | completed 所以测试全过 |
| 缺陷注入测试预期 exit 1，实际 exit 1 且精确计数一致 | 该负向测试验证了检测行为 | 整项工作失败 |
| 输出讨论 error handling，解析器将其列为关键词候选 | 阅读上下文后排除误报 | failures 数量就是实际错误数 |
| 先出现 65/100，修改后工具输出 100/100 | 已读证据支持该次评分改善 | 证明全仓质量和所有资源都通过 |
| 用户当时要求换目录 | 当时的需求发生变化 | 本次也可以迁移文件 |
| 扩窗到上限，messageId 集合与上次相同，hasMoreBefore=true | 覆盖未推进；更早历史不可达 | 已扩窗所以读全了 |
| hasMoreBefore=false，但 output 含截断提示 | 窗口前无更多历史，内容仍不完整 | 全文已读完 |

## 建议输出格式

```text
结论：成立 / 部分成立 / 证据不足 / 与证据矛盾。
范围：已读取的来源、窗口/快照与仍存在的截断。
时效：推荐基准（或未知）→ 后续证据 → 截至已读快照的逐项修正。
证据：逐项命题、来源定位、最小必要片段和判断。
状态：方案提出 / 要求细化 / 明确确认 / 产物交付 / 效果验证，分别列证据与范围。
纠正与失败链：用户纠正 → 原始失败 → 修复 → 复跑。
缺口：未读历史、参数不可见、未检查产物或未覆盖范围。
下一步：最小补证动作；如涉及写入，单独给出范围并等待确认。
```

最后区分“有依据提炼流程”与“提炼出的 Skill 已验证可用”。前者来自会话取证；后者还要求真实落盘、资源检查和必要的脚本实测。仅出现一份推荐 JSON，二者都不能直接成立。
