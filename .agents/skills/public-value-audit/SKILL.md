## 2. 功能描述

把「这个值会不会泄露用户」从一个靠直觉的判断，变成**三张清单的交叉定位**：

| 清单 | 内容 | 回答的问题 |
|---|---|---|
| **A 公开面清单** | 哪些表/列/接口/文件对「非所有者」可见 | 谁能看到什么 |
| **B 标识列清单** | 哪些值承载或内嵌用户标识（uid、openid、工号、手机号、邮箱…） | 什么算「敏感值」 |
| **C 值域构造方清单** | 每个公开值由谁拼出来（服务端 / 客户端 / 脚本 / 调用方入参） | 值域能不能被收窄 |

**三张清单的交叉点就是泄露面**：
`A ∩ B` = 授权面直接发了标识；
`A ∩ (B 内嵌于 C 的调用方入参)` = 值域由调用方决定，授权面挡住了列也挡不住值。

### 术语（第一次用请先看这里）

| 词 | 含义 |
|---|---|
| **取值域** | 某个对外可见的值在系统里**所有可能取到的值的集合**。取值域封闭 = 这个集合能被一条正则或一条服务端常量表达式完全描述；取值域由调用方决定 = 调用方能把它换成任意别的值 |
| **RLS（行级安全）** | Postgres 在表上附加的逐行可见性规则（`CREATE POLICY`）。它与列级授权是**两层独立机制**：列管「能看哪些列」，RLS 管「能看哪些行」。本 Skill 的判定依赖二者同时成立 |
| **`WITH CHECK`** | RLS 策略里约束**新增/修改行**的条件；对应的 `USING` 约束**读取**哪些行 |
| **`proacl`** | `pg_proc` 的访问权限清单列，形如 `{authenticated=X/…,service_role=X/…}`；`X` = EXECUTE |
| **`prosrc`** | `pg_proc` 的函数体源码列；**含尾换行**，与磁盘逐字比对时磁盘侧要补 |
| **`SECURITY DEFINER`** | 函数以**定义者（表属主）**的权限执行，调用方的列级授权不适用于其内部 SQL——这正是「服务端拼装」能落地的机制，也意味着**授权面必须靠 REVOKE EXECUTE 收口，而不是靠函数体自己判断** |

### 收口三件套（缺一不可）

1. **服务端拼装** —— 目标值由服务端拼出，调用方**不传**该参数
   → 值域从「任意」变成「服务端定义的有限集合」；
   ⚠️ 注意：拼进去的片段（如 slug）**不得承载标识**，且它可能可枚举——
   收口目标是「值里不含标识」，不是「值不可猜」；
2. **列级授权** —— `REVOKE SELECT ON TABLE t` 后只 `GRANT SELECT (业务列)`，
   标识列不进授权清单（RLS 策略内部求值不需要列级授权，已实测成立）；
3. **客户端白名单逐列对齐** —— 客户端 `select()` 的列 ⊆ 服务端列级授权清单，
   双向断言防漂移（否则请求到未授权列会**整表**失败，不是少一个字段）。

## 3. 何时使用

- 新增或修改了**对外可读的表列**，不确定里面装的东西会不会暴露用户；
- 发现某列「看起来无害」但值里嵌了标识（如 `shared/<uid>/activities/x.png`）；
- 写 RPC 时不确定返回值会不会把整行（含未授权列）回传；
- 评审别人提交的「已加列级授权」类修复——**要检查是否只挡了列、没挡住值**；
- 定期审计：把本 Skill 的断言器挂进 CI，防止整改后回退。

**不适用**：纯前端展示逻辑审查、第三方库内部实现审计、与标识外泄无关的一般代码质量审查。

## 4. 前置条件与降级路径

> ⚠️ **不满足前置条件时，脚本会给你「全绿」假信号**——所以这一节必须先读。

**前置条件**（三条都要满足，脚本的判定才成立）：

1. 数据授权面以 **Postgres GRANT / RLS** 表达（脚本不连数据库，只解析仓库里的 `.sql`）；
2. 对外角色名是 `anon` / `authenticated`（其它角色名需改脚本里的 `PUBLIC_ROLES`）；
3. 授权面真源在**仓库内的 `.sql` 文件**里（`schema.sql` / 迁移目录 / 拆分脚本）。

**不满足时的降级路径**：

- 本 Skill 的**方法部分（§4 六步 + `references/audit-method.md` 三张清单）与技术栈无关**，照做即可；
- 但**两个脚本的判定不适用**，此时**不要**引用其退出码作为「已通过」的结论——
  只把它当「把候选位置圈出来」的辅助；
- **自检方法**：先造一条**故意的**违规（如给 `anon` 授权一个含 `owner_id` 的表），
  确认工具能报出来；报不出来 = 工具不覆盖你的栈，**不是你的栈安全**。
  另：脚本对**空目录**会返回退出码 3（工具未生效），不会假装通过。

**本 Skill 默认只报告、不修改任何文件或云端资源**。任何收口动作都需你逐条确认后手工执行。

## 5. 核心步骤

> **执行顺序（工具先行，清单后填）**：先跑两个脚本拿到候选位置，用输出当清单 B/C 的**初稿**，
> 再回读这些文件补齐清单 A（授权面用 `references/audit-method.md` §1 的三条 SQL 实查），
> 最后做第 4 步交叉定位。
> 原因：清单 C（值域构造方）的判据「入参能控制公开列的值」正是 H6/I3 的判定口径——
> **脚本输出的每一条 H6 就是清单 C 的一行**，而不是第 4 步才用的东西。

1. **列 A（公开面）**：逐个数据出口列清单——表级/列级 `GRANT`、对外 RPC、公开文件路径、
   公开 API 响应体、Webhook、日志。明确「谁是所有者、谁不是」。
2. **列 B（标识列）**：登记标识列词典（默认 25 项，见脚本 `DEFAULT_IDENTIFIERS`）。
   ⚠️ **区分「本人标识」与「他人标识」**：某列装的是调用者自己的 uid 且该行只有本人可见 → 不是泄露面。
3. **列 C（值域构造方）**：对每个公开值追到源头——服务端常量拼的、还是入参带进来的？
   **入参带进来的 = 值域由调用方决定**（最容易被漏掉的一类）。
   ⚠️ 但「入参决定」≠「泄露」：**关键是该入参是否承载标识**——
   `p_slug`（被 `^[a-z0-9-]{1,64}$` 约束）不承载标识；`p_owner_uid` 承载。
4. **交叉定位**：按上面两张交叉表输出泄露面清单，每条注明「授权面挡不住」还是「授权面已挡」。
5. **收口**：按下面 6 步操作清单执行。
6. **固化**：把结论写成可回归的不变量断言（`check_public_value_invariants.py` 的 I1~I7），挂进 CI。

### 收口操作步骤（按序做，缺一步会漏）

1. **定位写入点**：用扫描器找「入参写进公开列」的全部函数体（H6/I3），逐个确认「这个值是谁拼的」。
   判定口诀：**「这个值，调用方能换成任意别的吗？」能 → 值域不封闭。**
2. **新建 canonical 写入函数**：目标路径由服务端常量拼出，调用方只传**形状受约束**的入参
   （如 slug，需 `p_slug !~ '^[a-z0-9-]{1,64}$'` 校验）。
   函数 `RETURNS TEXT`（不返整行），`LANGUAGE plpgsql SECURITY DEFINER SET search_path TO 'public'`。
3. **同批废旧入口**：`REVOKE ALL ON FUNCTION <旧>(…) FROM PUBLIC;` +
   `REVOKE ALL ON FUNCTION <旧>(…) FROM anon, authenticated, service_role;` +
   `DROP FUNCTION IF EXISTS <旧>(…);`。
   ⚠️ **先 DROP 再 REVOKE 会报错**（对象已不存在）。
4. **改授权面**：`REVOKE ALL ON TABLE t FROM anon, authenticated;` →
   `GRANT SELECT (<业务列逐列列出>) ON TABLE t TO anon, authenticated;`
   （标识列不进清单；RLS 内部求值不需要列级授权，已实测成立）。
5. **改客户端**：`select()` 的列集 ⊆ 服务端授权清单（否则整表 42501，不是少一个字段），双向断言防漂移。
6. **同批验证**：列出旧函数的**全部调用方**（客户端 / 运维脚本 / CI），确认在新角色下仍可达；
   再在新角色下跑一次功能验证。
   **授权面变更与功能验证必须同批交付，不允许拆成两批**（见「权限收紧双查」模式）。

## 6. 适用条件与不适用边界

**适用**：值由服务端存储并对外可读的系统（PostgREST/RLS、自建 API、对象存储元数据表、
ORM 暴露的模型层）。典型栈：PostgreSQL + PostgREST + RLS + 私有对象存储。

**不适用**：
- 值只存在于**调用者自己可见**的范围内（如本人私有目录下的对象路径 + 行级隔离到本人）→ 无泄露面；
- 标识已**单向不可逆**（如哈希、只展示前 4 位的工号）→ 不在本 Skill 范畴；
- 第三方 SDK/库内部实现 → 用其自身文档核对，不做源码级断言。
  ⚠️ 但 H3（客户端请求标识列）的判定**依赖 PostgREST 语义**（`?select=` 白名单列），
  非 PostgREST 后端需人工确认；因此 H3 已被降级为**中危**而非高危。

## 7. 反模式（均来自本项目真实教训）

1. ❌ **只把列从客户端拿掉，就当作不泄露了**
   实测：客户端白名单去掉 `owner_id` 后，访客仍可 `GET ?select=owner_id` 直查。
   → 安全边界必须在**服务端授权面**，客户端白名单只是第二道防线。
2. ❌ **只挡列、不挡值**
   实测：`cover_path` 是业务列、必须公开，但它的值里嵌了 owner uid → 同一张表两列可见性不一致。
   → 授权面挡住了 `owner_id`，却从 `cover_path` 这条路把它又发了出去。
3. ❌ **把「值看起来不敏感」当作放行理由**
   实测：运营账号的 uid 是数字串，但它仍是**用户标识**，且会随归属人变化而泄漏 openid 形态。
   → 判断标准不是「值本身敏感吗」，而是「它是不是标识」+「谁能读到」。
4. ❌ **RPC 返回整行 `SETOF <表>`**
   实测：`RETURNS SETOF activities` 一旦被授予终端角色，`owner_id` 就从响应体漏出。
   → 改成只返回路径/标量。（`RETURNS <复合类型>` 是同一语义的另一种写法，同样要改。）
5. ❌ **收紧权限时只看「能不能」，不看「谁还在调」**
   实测：把函数收归 `service_role` 后，其函数体依赖 `auth.uid()`（该角色下为 NULL）直接抛错，
   运维链路当场断掉。→ 收紧 EXECUTE 前必须同步核查调用方，并验证新形态下功能仍可用。
6. ❌ **把「值域由入参决定」当成正常设计**
   判定标准：入参能控制公开列的值 → 该列的取值域由调用方决定 → 除非这正是意图
   （如本人私有目录），否则一律改为服务端拼装。
7. ❌ **把「服务端拼装」当成「值域不可猜」**
   实测：`shared/_application/activities/<slug>.png` 里的 slug 在公开的 `activities` 表里可枚举。
   → 收口目标是「值里不含标识」，不是「值不可猜」；不可猜性要靠预签名 URL，不靠路径设计。
8. ❌ **收口只做一半，忽略收口制造的新风险**
   实测：把主图从「按用户分目录」迁到「应用级命名空间」后，存储侧变成 namespace-wide 可读，
   而 slug 可枚举 → 未发布活动的主图在存储层可被直接读到（**表级 RLS 被绕过**）。
   → 收口三件套要补第四件：**读授权面对齐**——存储侧读授权必须与表侧 RLS 同粒度。

## 8. 检验标准（做完怎么知道做对了）

1. **匿名可见性**（手工）：拿只有公开凭据的会话，逐个公开列取真实值并逐字检查——
   **输出里不应出现任何标识片段**（含被拼进路径里的）。
2. **值域封闭性**（手工）：公开的路径型列，其值集合应能用一条正则/一条服务端常量表达式完全描述
   （如 `^shared/_application/activities/[a-z0-9-]+\.png$`）；出现第二段变量即未收口。
3. **授权面对账**（手工）：`information_schema.column_privileges` 中对外角色的列清单里**没有**标识列。
4. **断言器全绿**（自动）：`check_public_value_invariants.py` 的 FAIL 计数为 0；
   WARN 项逐条确认过行级隔离语义（WARN 依赖 RLS 语义，静态分析判不了）。
5. **回归对抗**（自动）：`selftest.py` 全绿——它验证的是「工具本身没坏」，
   包括 p115 夹具必须被判 FAIL（这是 P1-15 的真实形态）。
6. ⚠️ **以上 1~3 条目前仍是手工步骤**，两个脚本只覆盖「授权面 + 值域构造方 + 字面量形态」，
   **不能**替代对真实数据值的检查（见 §10 已知边界）。

## 9. 跨领域迁移示例（⚠️ 均为未验证的假设）

> 这三条示例**未经第二个案例验证**，且**当前扫描器不支持其形态**
> （路径前缀词典里没有 `teams`，标识词典里没有 `employee_no`/`工号`）。
> 迁移前请先用 §4 的方法手工核对，**不要**指望脚本直接报出来。

- **SaaS 工单系统**：工单表有一列 `assignee_path = teams/<员工工号>/queue`，
  工单对全公司可见 → 工号可被枚举。收口：改成 `teams/_shared/queue`，
  由服务端按工单类型拼装；员工归属单独存一列且不下发。
- **Git 托管平台的公开仓库**：仓库的 `default_branch_ref` 里曾带提交者用户名；
  改用稳定引用名 + 服务端映射后，克隆日志不再暴露推送者标识。
- **埋点与日志**：把 `user_id` 拼进静态资源文件名并放在公开 CDN 目录 → CDN 目录列表即可枚举用户。
  收口：资源名用随机内容哈希，标识只留在受控的映射服务里。

### 规则与不变量对照

| 规则 | 检出 | 不变量 |
|---|---|---|
| H1 | 对外表只有表级授权（隐含所有列） | I6 |
| H2 | 对外列级授权清单含标识列 | I1 |
| H3 | 客户端字段白名单含标识列（**中危**：判定依赖 PostgREST 语义） | I5 |
| H4 | 标识值出现在路径/URL 拼接处 | —（提示性） |
| H5 | RPC 返回整行/复合类型 | I4 |
| H6 | 路径型公开列的值域由调用方入参决定 | I3 |
| H7 | 字面量路径内嵌标识段 | I7 |
| — | 客户端请求列超出服务端授权清单 | I2 |

### 已知边界（工具覆盖不到的地方，务必人工复核）

- **不检查实际数据值**：脚本只做源码形状分析。「公开值里到底有没有标识」需要取真实值人工核对
  （§8 检验标准 1~3）。
- **不解析中间变量传递链的完整语义**：只做 4 轮赋值传播；`INSERT` 形态支持，但多级嵌套仍可能漏。
- **只按 `.sql` 扩展名解析 SQL**：`.ts` / `.js` 里内嵌的 SQL 模板会给出显式告警，但不逐条解析。
- **不解析角色组间接授予**：`GRANT <role> TO anon` 这类链静态不可判定，会报中危要求人工确认。
- **`PUBLIC` 视为对外**：`GRANT … TO PUBLIC` 隐含包含 anon/authenticated。
- **`SELECT *` 语义**：不模拟 `*` 展开，但列级授权下 `select=*` 会整表 42501（已实测）。
- **`.sql` 里的函数体只按 dollar-quote 标签捕获**（`$$` / `$fn$` 等均支持）。

### 分级与豁免原则

- **高** = 结构上即可判定为缺陷（授权清单直接含标识列、客户端主动请求、表级授权、
  值域由承载标识的入参决定、字面量含标识）；
- **中** = 取决于运行期语义（RLS 行隔离、值是否本人所有、值的实际可见性）；
- **已豁免** = 脚本在同项目内检测到该表有 **RLS 行级隔离到本人**（策略 `USING` 含 `auth.uid()`），
  或用 `--allow-row-isolated <表名>` 显式登记。
  ⚠️ 豁免**表名写法**：写 `registrations` 或 `public.registrations` 均可（已归一化）；
  写错名字会**静默失效**，用 `--json` 看 `waived` 计数确认，或看输出里的「未匹配任何已发现的表」告警。

## 12. Gotchas

- **别把「客户端不读 X」当闭环**：它只是第二道防线，真实边界在服务端授权面。
- **别把扫描器的 WARN 当漏洞**：WARN 依赖 RLS 语义，静态分析判不了；
  逐条确认后显式登记豁免，而不是删规则。
- **别用 `^` 锚点匹配 SQL 参数列表**：参数常写在一行
  （`p_slug TEXT, p_path TEXT`），按行首匹配会整条规则失效——按逗号切分后逐项比对。
- **别用非贪婪 `([^;]*?)\)` 捕获 RLS 的 `USING (...)`**：会把 `auth.uid()` 的右括号吃掉，
  导致行隔离检测永远为 0 → 所有本该豁免的项都被报成高危。
- **别用 `strip("()")` 去掉列清单的括号**：前导空格会让左括号留下，
  首个列名变成 `(id` → 「客户端请求列 ⊆ 服务端授权」这条不变量恒不触发。
- **别把注释里的 `<uid>` 当代码命中**：扫描前先剥离 `//`、`/* */`、`--` 注释，否则散文会造成大量误报。
- **别让局部变量遮蔽 argparse 的命名空间**：在 `main()` 里把循环变量命名成 `args`
  会让 `args.json` 变成字符串。
- **别用行级 `GRANT` 授权后忘记收回 `PUBLIC`**：Postgres 建函数时默认把 EXECUTE 给 PUBLIC，
  仅 `REVOKE ... FROM PUBLIC` 收不回「先前显式授予」的定向授权，需再 `REVOKE ... FROM anon, authenticated`。
- **列级授权下，请求未授权列会让整表失败**（不是少一个字段）：
  实测 `select=id,owner_id` 与 `select=*` 都返回 42501。
  ⇒ 客户端白名单必须与服务端授权清单**逐列对齐**，并加双向断言。
- **表名归一化**：SQL 侧常写 `public.activities`，客户端侧写 `activities`——
  不归一化，「客户端请求列 ⊆ 服务端授权」这条永远不触发。

## 15. 安全检查清单（逐项确认）

> 本 Skill 默认**只读**：两个脚本只解析文件、只打印结论，不写磁盘、不连数据库、不改云端。
> 下列清单用于**人工收口**阶段的逐项确认（每一项都要有证据，不是打勾了事）。

- [ ] 清单 A 已从**活库授权面**取数（`column_privileges` / `proacl` / `pg_policies` 三条 SQL），不是只读客户端代码
- [ ] 清单 B 已登记本项目的标识列**别名**（creator / operator / assignee / employee_no…），不只登记 `owner_id`
- [ ] 清单 C 已逐个公开值追到构造方，区分「服务端常量拼」与「调用方入参带进来」
- [ ] 每个「调用方入参」已判定**是否承载标识**（名字像标识 / 路径型无形状约束 → 承载）
- [ ] 每个对外角色的列级授权清单里**没有**标识列
- [ ] 客户端 `select()` 的列集 ⊆ 服务端列级授权清单（否则整表 42501，不是少一个字段）
- [ ] 对外 RPC 不返回含标识列的整行 / 复合类型
- [ ] 公开路径型列的**取值域**能被一条正则完全描述（出现第二段变量即未收口）
- [ ] 收口后的**存储侧读授权**与表侧 RLS 同粒度（收口可能把「行级受限」变成「命名空间可读」）
- [ ] 收口涉及的授权变更与**新角色下的功能验证**同批交付（收紧 EXECUTE 前已列出全部调用方）
- [ ] 断言器 `FAIL 0`；`WARN` 项已逐条确认行隔离语义并显式登记豁免（不是删规则）
- [ ] `selftest.py` 全绿（工具本身没坏）

### 幂等性

两个工具**天然幂等**：只读解析 + 打印，不产生任何副作用，重复运行结果一致。
`--allow-row-isolated` 重复传入不累积状态。
**因此本 Skill 不需要「确认后再执行」的操作门**——它压根不执行写操作。

### 为什么这样设计（关键决策的 Why）

- **为什么把「值域」而不是「字段」作为审计单位**：字段是授权面的单位，值是泄露面的单位。
  本 Skill 的来源案例正是「授权面已挡住字段、值却从另一处漏出」——以字段为单位审计必然漏。
- **为什么分级要分「高危/中危/已豁免」而不是二分**：静态分析判不了「这张表的行是否对他人可见」，
  也分不清「响应里的标识是本人还是他人」。硬判会误报，**满屏告警的工具会被直接弃用**；
  静默放行更糟——所以静态判不了的必须显式标出并要求人工确认，而不是替人做决定。
- **为什么要求「工具自检」而不是只信文档**：本 Skill 的工具自身出过 8 处真实缺陷
  （含两处导致不变量恒不触发、两处导致行隔离检测恒为 0）。
  没有对照夹具与自检，这些缺陷会一直「看起来在工作」。
- **为什么默认只读、收口动作交给人**：授权面变更一旦改错，故障点往往不在改动的那一行
  （见「权限收紧双查」）。由人逐条确认后执行，工具只负责把位置指出来。
