# 读后写前漂移恢复

本技能只处理一个时刻：**方案已获批，但落盘时文件已经不是你读到的那一份**。它不负责对账归属、作用域证明或会话取证，只负责把已获批的改动安全地落到新版本上。

## 1. 为什么需要一个专门流程

从「读」到「写」之间隔了方案编写与用户确认，这段窗口里共享工作树可能被另一个会话改动。此时三种失败的代价依次升高：

| 失败方式 | 表现 | 代价 |
|---|---|---|
| 覆盖他人工作 | 用读到的旧版本整文重写 | 并发会话的提交变成未提交丢失或半截 |
| 重复新增 | 照原方案加一节，但现盘已有同名小节 | 文件出现两套口径，后续读者无法判断哪份有效 |
| 版本回退 | 沿用方案里的目标版本号 | 版本单调性被破坏，登记面与镜像对不上 |

> **为什么不能靠「写入工具报错」兜底？** 写入工具只在 `old_string` 不匹配时失败；一旦并发改动恰好避开了被匹配的片段，写入会**成功**并静默覆盖。判定必须发生在写入前，不能依赖写入后的报错。

## 2. 适用边界

| 任务 | 使用本技能 | 交给谁 |
|---|---|---|
| 写入失败或成功后发现文件已被并发改写，需要继续落地 | 是 | — |
| 只读判断「谁改了、改动归谁、还剩什么没做」 | 否 | `shared-edit-commit-reconciliation` |
| 改前改后哈希基线、证明只碰了获批文件 | 否 | `skill-update-contract-and-scope-audit` |
| 核实来源会话里的历史过程与失败原因 | 否 | `chat-session-evidence-audit` |
| 新建 Skill 的落点、键集与验收 | 否 | `skill-creator`、`repo-native-skill-frontmatter-contract` |
| 提交隔离与共享索引 | 否 | `scoped-commit-shared-worktree` |
| 随包脚本的深度夹具设计 | 否 | `skill-bundled-script-validation` |

## 3. 判定：先把信号分类，再动手

遇到下列任一信号，立即停止本会话对该路径的后续写入：

- 写入工具报 `Failed to edit, 0 occurrences found for old_string`。
- 目标文件 `mtime`、大小或 `sha256` 与方案基线不符。
- frontmatter 版本行或正文标题集合发生变化。
- 用户级路径在会话期间变成目录联接或符号链接，指向另一份权威副本。

**先分类，不要先重试**。`0 occurrences` 至少有三个原因：

| 原因 | 判别证据 | 处置 |
|---|---|---|
| 内容被并发改写 | 版本行、标题集合或哈希变化 | 进入第 5 节恢复流程 |
| 空白/转义不匹配 | 哈希与标题集合均未变，仅局部空白不同 | 定点修正 `old_string` 后重试 |
| 目标路径被替换 | `kind` 从目录变成联接，或 `realpath` 指向别处 | 按新路径重读，重新确认写入面 |

> **为什么重试不是处置？** 内容漂移后加长 `old_string` 仍然匹配不到，或者在别处命中错误片段；两种情况都会把一次明确的漂移伪装成一次转义问题。

## 4. 写前低成本复核

首次 Edit 之前，用基线快照比对一次，比事后回滚便宜：

```bash
REPO="$(git -C D:/spaces/SpecWeave rev-parse --show-toplevel)"
python "$REPO/.agents/skills/stale-read-edit-reconciliation/scripts/probe_drift.py" \
  --path "<目标文件>" --baseline "<方案基线 json>"
echo "PROBE_EXIT=$?"
```

- `0`：与基线一致，按已批准方案写入。
- `1`：检出漂移或目标缺失，**不要写入**，进入第 5 节。
- `2`：用法或 IO 错误，先修调用，不要把 `2` 当作「无漂移」。

基线由方案阶段生成，并写明「方案依据的版本号与时间」：

```bash
python ".../probe_drift.py" --path "<目标文件>" --write-baseline "<基线 json>"
```

> **为什么基线要落盘而不是记在上下文里？** 上下文会被压缩，记忆里的「我读过 v1.3.0」无法被复核；落盘基线能回答「当时到底读到哪一版」。

## 5. 恢复六步

### S1 冻结

停止本会话对该路径的所有写入，不停止其他会话。记录触发信号原文与当前时间。若已部分写入，记录已写入的片段，不要用回滚掩盖。

### S2 重读现盘

完整重读当前文件，不要只读被匹配的片段。同时记录：`kind`（普通文件/联接/符号链接）、`realpath`、`size`、`sha256`、版本行、标题集合。脚本一次给全。

### S3 标题级差集

把方案的改动点映射到标题，与现盘标题集合求差：

| 差集结果 | 含义 | 处置 |
|---|---|---|
| 方案条目在现盘已有同名小节且内容覆盖 | 已被并发会话完成 | 从方案删除该项 |
| 现盘有同名小节但只覆盖部分要点 | 部分覆盖 | 只补缺失要点，不重写整节 |
| 现盘新增了方案里没有的小节 | 并发产出的新内容 | 保留，不删不改，除非用户明确要求 |
| 现盘与方案在同一结论上相反 | 真冲突 | 停手，向用户报告两版差异并请裁决 |

> **为什么按标题而不按全文 diff？** 全文 diff 会把并发会话的排版、措辞和新增段落混成噪声，掩盖「哪几条已覆盖、哪几条还缺」这个唯一需要决策的问题。

### S4 裁剪方案

按 S3 的结果重写改动清单，只保留缺失项。裁剪后的清单必须能逐条对应到现盘的具体位置，并显式列出「因已覆盖而删除」的条目。

### S5 版本顺延

从现盘版本号顺延，而不是复用方案里的目标版本：

- 现盘 `1.4.0`，方案原本写 `1.4.0` → 落地 `1.5.0`。
- 现盘已经是被并发升到的版本，继续 +1，不回退、不并号。
- 同时更新变更记录表与正文里的版本引用，避免文内自称与实际版本不一致。

> **为什么版本号必须从现盘读？** 方案里的目标版本在获批时就已被占用；沿用它会制造两个不同内容、同一版本号的副本，登记面与镜像无法对齐。

### S6 写入、复跑门禁、回报

按裁剪后的清单定点写入，不回写整文。写入后：

1. 幂等复查：写入每个条目前先确认目标锚点尚不存在；同一裁剪清单重复执行不应产生第二份小节。
2. 回读实际文件，确认没有重复标题、文内版本一致。
3. 复跑该包的质量门与链接门，并在门禁结果变化时区分「本次引入」与「既有债务」。
4. 在交付说明中写明并发事实，不要只报「已完成」。

## 6. 停手条件

出现以下任一项，停止写入并交回用户，不自行裁决：

- 现盘与方案在同一结论上相反，或删除了方案依赖的前提小节。
- 目标文件在两次重读之间仍在变化（哈希连续不同）。
- 路径类型变化导致写入面改变，例如从普通文件变成指向另一仓库的联接。
- 已写入的片段与现盘内容冲突，且无法通过只补缺失项收敛。

## 7. 验证

| 检查 | 期望 |
|---|---|
| `probe_drift.py --path <目标> --baseline <新基线>` | 写入后重新生成基线并比对，无意外漂移 |
| 标题唯一性 | 同一语义小节只出现一次 |
| 版本单调 | 落地版本高于方案基线版本与并发版本 |
| 质量门 | 该包实际得分与退出码，不用「已写入」代替 |
| 链接门 | 断链与警告计数，含 frontmatter 路径 |
| 文件范围 | 只改动获批文件；并联接路径不算新副本 |

## 8. 报告契约

| 项 | 必须写 |
|---|---|
| 并发事实 | 何时发现、现盘版本、路径形态（普通/联接） |
| 方案基线 → 落地版本 | 例如 `1.3.0 → 1.5.0`，并注明中间被并发占用 `1.4.0` |
| 裁剪结果 | 因已覆盖而删除的条目、只补缺失的条目 |
| 写入范围 | 实际改动文件清单，是否只补缺失项 |
| 门禁 | 原始命令、数值、退出码 |
| 未验证 | 未执行的检查与原因 |

> **为什么不写清裁剪结果就是失真？** 读者会以为方案被原样执行；下一次维护会照着旧方案再改一遍已被覆盖的内容。

## 9. Gotchas

1. **`0 occurrences` 不等于空白问题**：先比哈希、版本、标题，再考虑转义；顺序反了会把漂移误判成格式问题。
2. **同 inode 不代表没变**：原地覆写文件时 inode 不变；判断是否变化用哈希与 mtime，不要用 inode。
3. **两个路径同 inode 说明是同一份文件**：用户级路径与仓库路径同 inode、同大小，通常意味着目录联接；此时「改用户级」就是「改仓库工作树」。
4. **mtime 可能被粗粒度文件系统抹平**：以 `sha256` 为主判据，mtime 只作辅助。
5. **不要用 shell  heredoc 整文覆盖来「修复」失败**：那会把并发新增内容一起抹掉，且不再有冲突报错。
6. **「只补缺失」不是重写整节**：部分覆盖时保留现盘已有句子，只插入缺的要点。
7. **不得删除并发新增小节**：它可能属于另一个已获授权的任务；删除等于替别人回滚。
8. **版本号不能沿用方案目标**：即使方案里的数字看起来「还没发布」，现盘占用即视为已占用。
9. **多文件要逐个判定**：一个文件漂移不代表另一个也漂移，反之亦然；脚本按文件各跑一次。
10. **方案里「不动登记面」的结论可能已过时**：并发会话可能已顺带登记，重读后要核对，而不是照旧执行「不登记」。
11. **门禁基线也会漂移**：质量分或断链数变化要归因到本次引入还是既有债务，不能一句「门禁通过」带过。
12. **不要为了过通用校验器删掉仓库原生字段**：那是另一把尺子，删字段会让质量门掉分。
13. **夹具与真实文件分开**：验证脚本行为时用临时目录，不要拿正在被并发写的真实文件当试验品。

## 10. 安全检查清单（逐项确认）

- [ ] 触发信号已分类，未用「加长 old_string 重试」代替判定
- [ ] 已重读现盘并记录路径形态、哈希、版本、标题集合
- [ ] 已求标题级差集，并显式列出「已覆盖/部分覆盖/新增/冲突」四类结果
- [ ] 冲突项已停手交回用户，未自行裁决
- [ ] 方案已裁剪，只保留缺失项，未删除并发新增内容
- [ ] 裁剪清单可重复执行而不产生重复小节（幂等）
- [ ] 版本号从现盘顺延，文内版本引用同步
- [ ] 写入后已回读，标题无重复、无整文回写
- [ ] 质量门与链接门已实跑并记录退出码
