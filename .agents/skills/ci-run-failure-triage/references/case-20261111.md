## 二、红项原文

`--log-failed` 输出 91.0 KB / 534 行并落盘。在落盘文件上按 `✗|::error|exit code` 定位到：

```
✗ 校验失败：2 项
  - [规模数字矛盾] doc/index.md: 出现 [731]，与总索引 732 不一致；须同步为 732 或改为量级表述
  - [规模数字矛盾] README.md: 出现 [729]，与总索引 732 不一致；须同步为 732 或改为量级表述
Process completed with exit code 1.
```

同一次输出里，前三个门禁已经通过：

```
UTF-8 检查通过: 13219 个文件均为有效 UTF-8。
toctree 检查通过: 全部 index.md 引用有效，所有内容文档均可达。
bundles 总索引对账通过: 9 域 / 64 组 / 732 束，frontmatter、计数行、节标题、分组表、toctree 五面一致。
```

> 关键信号：**总索引自身是自洽的（732）**，红的是「对外声明面」与它的对账。这直接把修复范围锁定在 README 与 doc/index，而不是目录树或 toctree。

## 三、本地复现

```bash
cd projects/awesome-okf-xs
python scripts/check-bundles-index.py   # 9 域 / 64 组 / 732 束，退出码 0
python scripts/check-asset-baseline.py  # ✗ 校验失败：2 项，退出码 1
```

条目文字与远端逐字一致 → 判定为真失败·内容类。

## 四、根因

`b7bfcdce` 新增 3 个 bundle（jishu 域），只同步了 `doc/bundles/index.md` 的 frontmatter 与五面计数，
未同步两个人类可读声明面：

- `README.md`：5 处 `729`（shields badge、概述句、`当前实际值` 行、清单提示、九域表合计行）；
- `doc/index.md`：2 处 `731`（首段与「关于知识包」段）。

同时 README 九域表的 `技术（jishu）` 行写着 `528`，而总索引 jishu 节是 `537`——即使把合计行改成 732，
该表也会自相矛盾（各域之和 ≠ 合计）。

## 七、一处必须记录的伪失败

本地跑 `pytest tests/unit` 时 `test_doc_parallel_extensions_okf.py::test_target_exts_load` 失败，
报 `sphinx_tippy` 未加载。

判定为**伪失败**，依据：

1. 失败 job 的 steps 只执行 `test_no_future_annotations.py`，不含该文件；
2. 本机未安装 `sphinx_tippy`，属环境差异；
3. `.github/workflows/gates-selftest.yml` 的 `on.paths` 不含文档路径，本次推送不会触发它。

因此不修改该测试、不补依赖、不纳入本次修复范围，但在交付说明里如实登记。

## 九、可迁移结论

1. **多面声明的一致性门禁，报错会同时给出「真源值」与「违规值」**——先读真源值，再决定改哪一侧；
2. **同一文件里的多处声明必须同批改**，只改 badge 不改合计行会让门禁继续红；
3. **表格的「合计」行与分域行必须一起改**，否则得到一张自相矛盾的表，即使门禁不再报错；
4. **本地红项要先对照 workflow 的 `run:` 行**，再决定是否纳入范围；
5. **门禁已存在时，预防措施写「已有门禁覆盖」并指名是哪条检查**，不新增第二层同类门禁。
