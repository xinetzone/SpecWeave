# 门禁取数手册：计数、残差、共享文件与提交批次

> 配套 [SKILL.md](../SKILL.md) §5 第 2/5/6 步与 §7。核心纪律：**所有数字只从现跑输出取，不从摘要、日志或上一轮结论取。**

## 一、取数命令与精确退出码

```bash
cd <subproject>
for s in check-toctrees check-bundles-index check-utf8 check-asset-baseline; do
  python scripts/$s.py >/dev/null 2>&1; echo "$s exit=$?"
done
for s in check-toctrees check-bundles-index check-utf8 check-asset-baseline; do
  out=$(python scripts/$s.py --self-test 2>&1); echo "$s self-test exit=$? :: $(echo "$out" | tail -1)"
done
```

**不要**用 `python scripts/check-x.py | tail -20; echo $?` 判断成败：管道后的 `$?` 是 `tail` 的退出码。实测中资产基线门明确打印「✗ 校验失败：1 项」，但包装成管道后取到的却是 0。要分开设取，或用 `PIPESTATUS[0]`。

2026-11-06 一次真实取数：

| 门 | 输出 | 精确退出码 |
|---|---|---|
| `check-toctrees` | 全部 index.md 引用有效，所有内容文档均可达 | 0 |
| `check-bundles-index` | 9 域 / 64 组 / 718 束，五面一致 | 0 |
| `check-utf8` | 12963 个文件均为有效 UTF-8 | 0 |
| `check-asset-baseline` | 1 项「行尾归一失效」，残差 `+302365`；未报「规模数字矛盾」 | **1** |
| 四个 `--self-test` | 规则均可命中 | 0 / 0 / 0 / 0 |

> **为什么连「通过」也要带退出码？** 因为「通过」是助手复述，退出码是工具输出。会话压缩后复述会漂移，命令与码不会；这正是区分证据等级的最小成本手段。

## 二、计数漂移处理

同一里程碑内 `total_bundles` 基线可多次变化（712 → 713 → 714 → 715 → 718），原因通常是并行会话在途 bundle 补齐了根 `index.md`，目录树才把它计入 1 束。

处理顺序：

1. 现跑 `check-bundles-index.py`，读取它给出的域/组/束数；
2. 与当前工作区 `git status` 对照，识别哪些是并行会话在途内容；
3. 按「目录树地面真值」同步索引，不按日志里记过的目标值同步；
4. 报告中把数字标注为「`<日期>` 现跑快照」并附取数命令，不写成长期结论。

> **为什么不能「沿用上次算好的目标值」？** 因为目标值是在当时的目录树状态下推导的；在此期间并行会话添加或补齐了别的 bundle，推导前提已经变了。前提变了，结论就要重算。

## 三、共享文件的精确替换

- 未持有文件完整最新内容时，**禁止整文件覆盖**共享索引（`README.md`、总索引、首页、域索引）；用定点替换。
- 已重读全文并确认无误时，整文件写入同样可行。精确替换是降低冲突面的手段，不是唯一正解。
- 判定「无需改」时也要落一条记录，避免下一个会话误以为漏接线。
- 不得为了回避冲突而把自己该改的投影面留空。

## 四、残差归属定量

资产基线门报「行尾归一失效」时，先做量级对比再谈归属，不要直接归咎于自己或他人：

```bash
# 本轮改动字节
git diff --stat -- <本束目录>
find <本束目录> -name "*.md" -newer <基准> -printf "%s\n" | awk '{s+=$1} END{print s}'
```

真实判定样例：本束未提交/未跟踪文件合计 75448 字节（73.7 KiB），而残差约 292 KiB；且其中多为替换型修改而非净增。结论：残差由并行会话在途内容主导，脚本自身要求「先提交或 stash 工作区变更再复跑」，按惯例不代修他方 WIP。

三条禁令：

1. 不改写基线数字让门变绿；
2. 不刷新快照 / 基线来消除漂移；
3. 不把「未报规模数字矛盾」写成「基线门通过」。

## 五、提交批次判定

提交批次 = **让所有门禁同时自洽的最小文件集合**。判定流程：

1. 列出全量门禁及其读取的共享文件；
2. 找出这些共享文件当前投影到的所有在途改动（含并行会话的 bundle）；
3. 若只提交其中一部分会让任一门失去自洽，就把批次扩展到覆盖全部投影；
4. 向用户说明「为什么不能只提交自己这一束」，再单独请求提交授权。

真实案例：一次「提交」请求最终以 3 个 bundle 的自洽批次落盘（52 个 `.md`、3740 行新增、33 行删除），而不是单 bundle 提交；父仓随后单独提交 gitlink 指针。

> **为什么父仓指针要单独一步？** 父仓只记录 gitlink 值，子模块工作区的 `-dirty` 不写入该值。子项目提交与父仓指针提交是两个仓、两次授权，混在一起会让可复现性说明失真。

## 六、并行会话纪律

- 每次续接都从磁盘回读入口契约，不依赖内联副本或会话摘要；
- 每次写共享索引前重查 `git status`；
- 不代修、不删除、不 stash 他方在途内容；
- 门禁红项如实记录归属与复跑条件，不宣称「全绿」；
- 提交 / 推送 / 登记一律单独授权，历史会话里的「同意」只证明当时授权。

## 七、已知环境限制（如实登记）

- `invoke` 可能因缺 `invocations` 包元数据无法加载；按仓库惯例直接运行 `scripts/` 下与 `gates.*` 同一实现的官方脚本，并在报告里写明。
- `pytest` / `sphinx` 未安装时，红线门与构建无法执行，标「未验证」而非「通过」。
- 归类门若历史基线本就红，写「未新增违规」而非「已通过」；同时给出基线违规数。
- `check-skill-quality.py` 的 `--score` 只输出分数，验收要显式 `--threshold 100` 且取退出码。
