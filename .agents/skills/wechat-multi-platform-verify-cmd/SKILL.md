# 公众号文章多平台核验与发布证据包 Skill

> 萃取自 2026-10-23 公众号「千问Go! 我的应用」文章核验实战：1 篇成稿 + 5 个平台取证 → 落成 8 件证据文件。本技能把「一篇已成稿文章对外发布前，先到多个平台核一遍文中事实」这件重复动作，固化成可重复执行的六步流程与固定输出契约。

## 1. Skill ID

`wechat-multi-platform-verify-cmd`

## 2. 功能描述

把一篇已成稿的公众号文章，转成一份**带证据链的发布物**：逐条抽出文中可证伪的事实主张，为每条主张找到分层信源，把每个平台的原文摘录单独存档，再产出一张主张×来源的比对台账，让「这句话凭什么这么写」可追溯、可复核、可交付。

核心能力：

1. **主张抽取**：区分可外部证伪的主张与作者自述、评价性表达，只抽前者
2. **信源分层**：一手官方源 / 官方陈列源 / 独立媒体 / 二手聚合，四级不可混用
3. **取证通道决策**：静态页直取、搜索快照正文、浏览器通道三条通道的适用边界
4. **同源转载检测**：多家媒体口径一致 ≠ 多源验证，按 1 个信源计
5. **冲突裁决**：官方文档 > 官方陈列 > 独立媒体 > 二手聚合，差异写进台账不写掉
6. **红线检查**：价格、邀测状态、营销承诺三类主张各有独立的核验门

> **为什么核心是「主张×来源」而不是「抓几个页面」？** 抓页面只能得到一堆原文，读者无法判断哪句被证实、哪句没人证。核验的交付物是**判定与证据的映射**，原文摘录只是它的证据列。实战中 5 份原文摘录全对，但仍有一条主张（云端 Pro 调用四家平台数据）只有同源转载背书——没有台账，这个缺口看不见。

## 3. 何时使用本技能

### 3.1 三级触发信号分级（Keyless 渐进披露）

| 层级 | 信号 | 判定与动作 |
|---|---|---|
| T0 | 弱信号 | 用户提到「文章要发」「发之前看看有没有错」「这是转载的原文吗」——上下文有文章但没明说核验。回复中提示本技能可用，是否执行由用户定 |
| T1 | 中信号 | 用户提到「核验」「事实核查」「对比几个平台」「这条数据哪来的」但未指明文章。追问定位成稿文件与目标平台 |
| T2 | 强信号 | 用户明确要求「核验这篇文章」「生成核验台账」「检查发布前的事实」「出一份多平台核验报告」——直接进入第 6 节六步流程 |

### 3.2 适用边界

适用：

- 一篇已成稿的公众号/头条/订阅号文章，准备对外发布或投稿前的事实核验
- 已有文章但缺证据链，需要补齐「主张—来源—结论」三段映射
- 同一篇稿件要发多个平台，需要确认各平台口径一致

不适用：

| 场景 | 交给他 |
|---|---|
| 知乎编辑器自动填充、发布、话题补加 | `zhihu-article-publish-cmd` |
| 公众号文章/技术博客转 OKF 知识包 | `wechat-public-okf`、`blog-article-to-okf-wiki` |
| 文章正文撰写、润色、结构设计 | `doc-writing-guide`、`doc-coauthoring` |
| 网页/UI 的视觉验收与截图评审 | `ui-screenshot-review`、`local-screenshot-qa` |
| 稿件的多平台分发搬运本身 | 本技能只核验事实，不负责分发与搬运 |

> **为什么不把「发布」也做进来？** 核验与发布是两种风险：核验产出的是可复核的判定，发布产出的是不可撤销的外部可见动作。把两者塞进一个技能，会让「顺手发了」绕过确认门。本技能在第 6.4 节交付待发清单，发布由用户另行触发。

## 4. 输入与输出（I/O Parameters）

### 4.1 输入

| 输入 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| 成稿文件 | 文件路径 | 是 | 无 | 公众号正文。Markdown 或 HTML 均可；HTML 需先转出正文 |
| 目标平台 | 文本 | 否 | 按信源分层自动选 | 用户已指定核验平台时按指定，否则由第 6.2 节决策树给出候选集 |
| 证据包输出目录 | 目录路径 | 否 | 与成稿同级新建 `<成稿名>-verify/` | 已存在时走幂等分支，不覆盖 |
| 发布窗口 | 日期 | 否 | 无 | 影响「时间节点」类主张的判定基准 |

### 4.2 输出（固定三件套 + 可选存档）

```
<证据包目录>/
├── article.md            # 成稿正文（原件，只读不改）
├── verify-<平台>.md      # 每平台一份：原文摘录，不写评价
└── verify-ledger.md      # 主张×来源比对台账 + 裁决结论 + 遗留风险
    page.html             # 可选：原始页面存档，保留取证时点
```

| 文件 | 内容约束 | 不可做 |
|---|---|---|
| `article.md` | 成稿正文原样 | 不得删改正文，即使发现里面有平台 UI 噪声 |
| `verify-<平台>.md` | 该平台原文摘录，保留标题、时间戳、署名、版权声明 | 不得写入评价、结论、自己的话 |
| `verify-ledger.md` | 一行一主张的判定表 + 冲突裁决 + 遗留风险清单 | 不得省略「无法证实」的主张 |

> **为什么摘录文件里一个字评价都不许写？** 摘录是证据，掺进判断就失去了「原文」的属性——一旦有人质疑结论，证据文件必须能一字不改地回到源页面。判断全部集中在台账，冲突时改台账而不是改摘录。

## 5. 方案选择决策树

### 5.1 取证通道决策树

```
需要取某个平台的原文？
├─ 静态可读页（官网首页、官方文档、官方市场/产品动态页）
│   └─ 直取通道：web_fetch → 从 meta description / SEO 兜底区块取正文
│       ├─ 返回了完整正文 → 直接摘录
│       └─ 返回的是前端框架 JSON 噪音 → 降级到浏览器通道或改用该页的 meta/SEO 兜底文本
├─ 媒体稿页（财经/行业媒体、转载稿）
│   └─ 优先：web_search 的 content 快照（已是正文，无导航噪音）
│       └─ 快照不全（正文折叠/付费墙）→ 浏览器通道 query text 展开全文
├─ JS 渲染 / 反爬 / 需登录态
│   └─ 浏览器通道：打开 → query(text) 读取正文 → 截图存档
└─ 数据在第三方 App/Connector 内（企业后台、数据库）
    └─ mcode-tools connector 发现并调用，不用网页检索冒充
```

> **为什么官方页优先用直取而不是浏览器？** 官方站的 SEO 兜底区块（title + description + 首段）本身就是给核验准备的稳定锚点，且不受前端改版影响；实测秒悟官网直取返回的 SEO 文本与历史取证文件逐字一致，而页面其余部分是 1.7 万 token 的前端配置 JSON，信噪比极低。媒体稿反过来——直取会带进大量导航与推荐位噪音，搜索快照反而更干净。

### 5.2 信源分层决策树

```
某条主张该信谁？
├─ 产品能力主张（支持 X / 可生成 Y）
│   └─ 官方产品页 / 官方文档功能页（L1）
├─ 价格、额度、套餐档位、计费规则
│   └─ 官方定价或计费文档页（L1，且必须专页而非首页）
├─ 发布事件、上线状态、时间节点
│   └─ ≥2 家独立媒体（L3），或 1 家媒体 + 1 家官方陈列页（L2）
├─ 生态集成（接入谁、调用谁的什么数据）
│   └─ 官方集成页（L1/L2）+ 独立媒体（L3）
└─ 找不到官方源、只剩二手聚合站/选型文/社区帖（L4）
    └─ 只能进「线索」栏，不得作为「已证实」的依据
```

**信源层级定义**：

| 层级 | 是什么 | 典型例子 | 可否单独支撑「已证实」 |
|---|---|---|---|
| L1 | 官方一手源 | 官网、官方文档/定价页、官方新闻稿 | 可以 |
| L2 | 官方陈列源 | 云厂商市场页、产品动态页、集成方官方渠道 | 可以，但需搭配 L1 或 L3 |
| L3 | 独立媒体 | 署名财经/行业媒体，含时间戳 | 可以，但需 ≥2 家且非同源 |
| L4 | 二手聚合 | 选型文、工具目录站、社区帖 | 不可以，只能作线索 |

> **为什么价格类主张必须锁定官方专页？** 实测同一时点上，官方定价文档写 Lite 首月价 ¥25（原价 ¥29），阿里云营销页写「¥9.9/月 ¥29/月」的限时价，另一篇选型文写「Pro 限时 9.9 元/月」。三个数字都是真的，但口径不同（首购价 / 限时活动价 / 二手转述）。价格一旦脱离口径就会变成虚假宣传，所以这类主张的判定源必须是官方专页，并在台账写清口径。

## 6. 执行流程

### 6.1 步骤1：抽取可证伪主张（S0）

逐句扫成稿，抽出**能被外部来源证实或证伪**的陈述，分五类编号：

| 类 | 含义 | 例（来自实战） |
|---|---|---|
| A | 产品能力 | 「支持通过自然语言创建网页应用」 |
| B | 商业条款 | 套餐档位、额度、价格口径 |
| C | 状态与时间 | 「10 月 23 日上线」「处于邀测阶段」 |
| D | 生态与集成 | 「接入阿里云秒悟」「可调用淘宝个人数据」 |
| E | 数字与指标 | 「抽取 3 位朋友送 500 元礼品卡」 |

**不抽**：主观评价（「省心」「直观」）、作者自述的运营机制、平台 UI 噪声（「不喜欢」「知道了」「微信扫一扫」）。

E 类要单独标注「作者自述，不可外部核验」，不要放进待证清单冒充待核验。

> **为什么先抽主张再取证？** 反过来做（先抓页面再想能证明什么）会被抓到的内容牵着走，最后变成「我抓了 5 个页面，所以核验完成了」。先固定待证清单，才能发现**哪条主张根本没有对应证据**——实战里正是这一步暴露出「云端 Pro 调用四家平台数据」只有转载背书。

### 6.2 步骤2：确定平台清单与取证通道（S1）

对每条主张按第 5.2 节决策树定信源层级，汇总成去重后的平台清单，逐个标注取证通道（第 5.1 节）。清单要先落成一张表再开始抓，避免边抓边扩散。

### 6.3 步骤3：逐平台取证并落盘（S2）

每个平台一个 `verify-<平台>.md`，内容是原文摘录。落盘前自检四点：

- 标题、发布时间/时间戳、记者或署名、版权或来源声明是否保留
- 图片链接是否保留
- 页面折叠内容是否展开取全（媒体稿常见「查看余下全文」）
- 摘录里有没有混进自己的话——有就清掉

**幂等**：同名文件已存在时，先比对内容指纹；一致则跳过重抓并在台账记「已有证据，未重抓」；不一致则另存 `verify-<平台>-<日期>.md`，不覆盖旧文件。

> **为什么要保留署名与版权声明？** 它们是「这一页在什么时点、由谁、以何种责任发布」的唯一证据，也是判断媒体稿是否同源转载的关键指纹。把它们当噪声删掉，等于把核验维度本身删掉了。

### 6.4 步骤4：比对台账与冲突裁决（S3 + S4）

产出 `verify-ledger.md`，一行一主张：

| # | 主张（原文摘句） | 类 | 来源文件 | 层级 | 结论 | 差异说明 |
|---|---|---|---|---|---|---|
| C-01 | 「千问Go! 上线"我的应用"，接入秒悟 Meoo」 | D | verify-ce.md、verify-bjnews.md、verify-doit.md | L3 | 已证实 | — |

**结论四态**：

| 结论 | 含义 | 附加动作 |
|---|---|---|
| 已证实 | 至少 1 个 L1/L2/L3 独立源支持，且与主张无实质差异 | 记录来源文件与层级 |
| 部分证实 | 主体成立，但细节/数值/范围与来源有差 | 必须写明差异点 |
| 无法证实 | 未找到任何合格来源 | 必须写明「已检索哪些源、为何无果」 |
| 存疑 | 来源与主张冲突 | 必须给出修订建议（改写或删除） |

**冲突裁决优先级**：`L1 官方当前有效文档 > L2 官方陈列页 > L3 独立媒体 > L4 二手聚合`。

| 冲突形态 | 处置 |
|---|---|
| 官方文档 vs 媒体报道 | 以文档为准，台账注明「媒体为发布时点口径」 |
| 官方首页 vs 官方专页 | 以专页为准（定价页 > 首页），记录首页缺项 |
| 独立媒体 vs 二手聚合 | 以独立媒体为准，把二手口径标为「与官方口径不符，存疑」 |
| 同一 L3 层多源相互矛盾 | 取更新时点者，并在台账标「同层级源冲突」 |

**同源转载检测（不可跳过）**：多家 L3 媒体表述高度雷同、发布集中在同一时段、句式结构一致 → 判为**同源通稿转载，按 1 个信源计**，台账里合并为一行并注明转载链；不得因为「有 4 家媒体都这么说」就判已证实。

> **为什么这一步最容易被做错？** 「多平台」的字面理解是抓得越多越好，于是把 4 篇互相转载的通稿当成 4 个独立背书。真实案例里中国经济网、新京报、潮新闻、上证报、DOIT 五家同时段同结构发稿，底层是同一份通稿——按 1 个信源计之后，真正独立于媒体的官方源只有阿里云产品动态页一个，这直接改变了结论强度。

### 6.5 步骤5：红线检查与交付（S5）

发布前逐项过第 8 节红线清单。交付报告包含四块：台账结论摘要（N 条主张 / N 已证实 / N 存疑）、存疑项的修订建议、未覆盖主张清单、取证时点与来源清单。

**dry-run 门**：本流程只产出证据包与待发清单，**不代替发布动作**。若用户同时要求发布，先把台账摘要与待发清单交出去等确认，再由发布流程接手。

## 7. 核验结论的常见问题处理

| 问题 | 场景 | 处理方式 |
|---|---|---|
| 官方页直取只拿到前端 JSON | SPA 站点 | 改用该页 SEO 兜底文本（title/description/H1+首段），或在浏览器通道取渲染后正文 |
| 媒体稿正文被折叠 | 「查看余下全文」 | 浏览器通道展开全文；若仍不全，换第二家媒体作信源并在台账注明 |
| 同一主张多个价格口径 | 首购价 / 限时价 / 二手转述 | 一律回官方定价专页取准，并写明口径名称 |
| 多家媒体口径一致 | 疑似同源通稿 | 按 1 个信源计，合并行并注明转载链 |
| 找不到任何官方源 | 只有媒体或聚合站 | 结论记「无法证实」或「L4 线索」，不写「已证实」 |
| 摘录与源页内容变了 | 页面更新或重定向 | 记取证时点；重定向时以规范 URL 为准，短链只作来源标注 |
| 成稿正文含平台 UI 噪声 | 复制自公众号页面 | 抽主张时排除，但不改 `article.md` 原件 |

## 8. 安全检查清单（逐项确认）

- [ ] 已确认每条主张在台账中有对应行，且无「无法证实」被省略
- [ ] 已确认价格/额度类主张全部命中官方定价或计费专页，并在台账写明口径
- [ ] 已确认邀测、灰度、内测状态没有被写成「已全面上线」
- [ ] 已确认作者自述（营销承诺、活动机制）标注为「不可外部核验」，未被包装成已核验事实
- [ ] 已确认未公开价格、内部口径、未发布产品信息未进入对外稿件与证据包
- [ ] 已确认引用的图片链接可公开访问，未使用带临时 token 或会话凭证的链接
- [ ] 已确认多个媒体源之间做了同源转载检测，未把转载链计为多源背书
- [ ] 已确认摘录文件只含原文，没有混入自己的评价文字
- [ ] 已确认证据包目录中已有文件未被覆盖（幂等重入安全）
- [ ] 已确认对外发布动作已交回用户确认，本流程未代替发布

> **为什么「作者自述」单列一类红线？** 「抽取 3 位朋友送 500 元礼品卡」这类内容既无法外部证实、也可能在发布后因名额规则变化而失真。它必须以「作者自述」的身份留在稿子里，而不是被台账盖上「已核验」的章。

## 9. Gotchas（陷阱与反直觉行为）

1. **同源转载伪装成多源验证**：多家媒体同时段、同一句式发同一篇通稿，是 1 个信源不是 N 个。实战中五家媒体全属同源链。
2. **一手官网不等于全部事实**：官网首页讲能力、讲定位，不讲价格；能力与条款要分别取证，用一个页面覆盖两类主张会漏。
3. **官方陈列页不是官方文档**：阿里云产品动态页写「秒悟 - 正式发布 2026.04.15」，是陈列快照；当前有效口径要看官方文档页。
4. **短链与规范地址会分叉**：外部给的 `docs.meoo.com/coindesc` 实际跳转到规范地址 `/pricing`，取证记录用规范地址，短链只留作来源标注。
5. **媒体稿的署名与版权声明是核验维度**：编辑/校对/记者名与「本文来源于 X」决定了这份报道的责任主体与转引层级，删掉就断了溯源链。
6. **页面噪声与证据噪声要分开**：公众号 UI 文案（「不喜欢」「知道了」）是噪声；页脚版权、备案号、相关推荐里的时间戳是证据，二者不能一起清。
7. **价格会随活动变动**：同一季度内官方页面自身就有「原价 / 首购价 / 限时价」并存的情况；台账必须记「取证时点 + 口径名」，否则复核时必然对不上。
8. **二手选型文的数据常与官方冲突**：实测有选型文写「Free 5GB 存储、Pro 10 万积分、四档含 Team」，官方文档写 Free 1GB、Pro 4 万积分、团队版独立。这类冲突按官方口径裁决，并把二手口径单独标存疑。
9. **取证文件放在会被 git 忽略的目录里**：实战证据包目录被 `.gitignore` 覆盖，因此 Skill 内的参考案例要镜像关键证据，不能只给一个本地路径。
10. **不要用核验流程去替代发布流程**：核验交付判定，发布交付不可撤销的外部动作，两者混在一起会绕过确认门。

## 10. 快速开始

```bash
# 1) 成稿入包（只读复制，不改原件）
#    article.md ← 公众号正文

# 2) 逐平台取证（通道按第 5.1 节决策树选）
#    官方页   → web_fetch，取 SEO 兜底文本
#    媒体稿   → web_search content 快照，正文不全再走浏览器通道
#    落盘     → verify-<平台>.md（仅原文摘录）

# 3) 出台账
#    verify-ledger.md：主张×来源×结论×差异说明

# 4) 过红线（第 8 节）+ 交付摘要
```

## 11. 依赖与前置准备

- **取数通道**：`web_fetch`（静态页直取）、`web_search`（媒体稿正文快照、候选源发现）、浏览器通道（JS 渲染 / 折叠全文 / 需登录态）、`mcode-tools` connector（数据在第三方 App 内时）
- **前置状态**：成稿文件已存在且可读；目标发布窗口已知（用于时间类主张判定）
- **目录约定**：证据包默认建在成稿同级 `<成稿名>-verify/`；目录已存在走幂等分支
- **权限**：只读取公开可访问页面；不登录、不提交表单、不触发任何写操作

## 12. 错误处理规范

| 异常 | 判定 | 处置 |
|---|---|---|
| 目标 URL 404/已下线 | 信源失效 | 换同层级第二信源；台账记「原源已下线」并给出替代源 |
| 页面被反爬拦截 | 通道失效 | 降级到搜索快照或浏览器通道；仍失败则记「无法取证」，不猜内容 |
| 同一主张所有源互相矛盾 | 同层冲突 | 取更新时点者 + 标注冲突 + 建议人工复核 |
| 官方站改版导致正文定位不到 | 结构变更 | 用 SEO 兜底文本兜底；在参考案例里更新定位锚点 |
| 成稿不是 Markdown/纯图片 | 输入不合规 | 先转正文再入包；图片型成稿需先 OCR 或人工录入 |
| 用户要求直接发布 | 越界请求 | 先交付台账与待发清单，发布动作另行确认 |
