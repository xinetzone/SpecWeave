# 咨询服务引流品探索

## 1. Skill ID / Name

`consulting-lead-magnet-discovery`

(lead-magnet-description)=
## 2. 功能描述与边界

把“用某工具做一个便宜的爆款”转成“向合适客户交付一个完整的小成果，并验证其是否愿意进一步咨询”。成功产物是一张有成本边界、验收方法和验证计划的方案卡，不是软件、不是真实成交，也不是增长承诺。

保留逐问澄清、方案对比、事实取证与批准门；不照搬通用创意流程中的设计文档提交和软件实现终点。用户要求七概念方法论时，由 `seven-concepts-cmd` 编排事实、推导与审查；不能把方法论中的提交环节解释为本轮 Git 授权。

> **为什么先问主营服务？** 同一份低价资料可能吸引很多领取者，却与后续咨询无关。先定义服务对象和要解决的问题，才能判断引流品筛选的是潜在客户，还是只追求低价的人。

(lead-magnet-io)=
## 3. 输入与输出

从当前对话提取已知信息，不要求用户重复填写表格。一次只问一个最影响选择的问题。

| 输入 | 类型 | 必需程度与缺失处理 |
|---|---|---|
| 主营咨询服务 | 文本 | 定案前必需；未明确时优先询问最终要承接哪项服务 |
| 目标客群 | 文本 | 定案前必需；明确行业、角色及当前阶段，不能把平台名称当客群 |
| 获客目标 | 文本 | 定案前必需；如合格咨询预约，不默认追求购买量 |
| 价格与工具 | 文本或数值 | 可选；区分用户硬约束与可调整假设，不默认固定价格或工具 |
| 人工与预算上限 | 分钟、金额 | 对外试售前必需；未知则标待确认，不宣称已可规模化 |
| 交付与答疑范围 | 文本、次数、期限 | 对外试售前必需；次数、时长、窗口分别明确 |
| 数据与现有证据 | 脱敏文本、汇总指标 | 可选；无数据时只给示例，不生成伪诊断 |

默认输出：简短方案卡、已知与待验证项、一个下一步。仅在用户要求时展开比较表、整改卡或话术模板。

(lead-magnet-decision)=
## 4. 决策树

```text
当前请求属于咨询服务获客吗？
├─ 否 → 说明不适用，不套用诊断式引流
└─ 是 → 主营服务明确吗？
   ├─ 否 → 只问主营服务，暂不选工具、定价或交付形态
   └─ 是 → 客群明确吗？
      ├─ 否 → 只问优先服务的客群，不自行选行业
      └─ 是 → 获客目标明确吗？
         ├─ 否 → 确认希望获得什么合格客户行为
         └─ 是 → 比较 2–3 种引流品
            ├─ 成本、答疑或数据边界未闭合 → 缩小范围，保留为草案
            └─ 边界闭合 → 给推荐方案与小范围验证计划，等待用户选择
```

用户明确要求先看模板、暂不澄清时，可给标有“示例／待验证”的通用草稿；不把缺失信息补成事实，也不把草稿称为可上线方案。用户已选定某形态时沿用其选择，只复核缺口，不反复重开选型。

(lead-magnet-workflow)=
## 5. 执行流程

### S1 — 定义主营、客群和目标

用一句话复述“为哪类客户解决什么问题，引向哪项咨询服务”，区分用户已确认的约束与助手提出的假设。已有答案直接复用；若用户改变主营或客群，重新检查相关方案，而不是沿用旧结论。

### S2 — 比较引流形态

对尚未选型的请求，提供 2–3 个候选及推荐理由。下列只是候选，不是固定套餐。

| 候选 | 独立交付价值 | 主要代价 | 适合验证什么 |
|---|---|---|---|
| 场景模板／自查清单 | 客户可自行完成一个明确动作 | 个性化较弱，可能吸引泛流量 | 目标客户是否有该场景需求 |
| 限定范围轻诊断 | 基于证据定位一个优先问题并给可执行建议 | 需要人工审核，易发生范围扩张 | 客户是否认可诊断价值并愿意继续咨询 |
| 限时小课／演示答疑 | 帮助客户完成一个小成果 | 组织、讲授和答疑占时 | 客户能否完成动作及后续需求是否匹配 |

逐项比较客群匹配、当前交付价值、人工投入、材料要求和后续承接；缺少实测数据时采用定性判断，不编造转化率或精确评分。工具只作为交付手段，未经核验不承诺其自动化能力。

### S3 — 成本与服务边界预检（dry-run）

在给出可试售结论前，模拟一单从收资料到答疑结束的完整过程，计入沟通、分析、人工复核、制作、修改和售后时间。

- 每单贡献估算 = 实收金额 − 支付与工具等变动成本 − 人工分钟数 ÷ 60 × 人工时薪。
- 标明数据是实测还是估算；该值未包含固定成本和获客费用，不能当净利润。
- 若允许引流品亏损，明确获客预算、订单上限和停止条件；不拿尚未发生的高价咨询收入抵消亏损。
- 写清交付项、输入材料上限、交付时限、修改次数、答疑次数与窗口；不接受“无限答疑”作为已闭合边界。
- 排除未包含的账号登录、后台配置、代发消息、全量数据审计与持续陪跑；确需这些服务时单独定范围与授权。
- 只索取最少必要、经授权并脱敏的材料；不要求密码、验证码、访问令牌或原始客户通讯录。
- 使用外部 AI 工具处理客户材料前，确认工具能力、数据去向和相应授权；未明确时仅用虚构样例或留在对话中设计流程，不上传材料。

> **为什么低价服务更要限定人工？** 收款很容易计数，沟通、复核与答疑时间却容易漏算。一个便宜但没有结束条件的服务，会把获客试验变成无法控制的人力承诺。

### S4 — 定义完整的小交付

每条建议或整改卡至少包含以下要素。

| 要素 | 要求 |
|---|---|
| 观察依据 | 来自哪些脱敏材料；区分观察与推断 |
| 优先级理由 | 与客户目标的关系，不虚构损失金额 |
| 一个主要动作 | 客户能独立执行，避免把整套咨询塞进一张卡 |
| 可用素材 | 对应模板、示例话术或操作清单；示例明确标注 |
| 验收方法 | 可观察的完成条件，如模拟一次完整预约流程 |
| 适用边界 | 依赖哪些前提，哪些信息仍需补充 |

“三项建议”是容量上限或约定交付格式，不是每个客户必有三个问题。证据只支持一项时只确认一项，其余标待验证并列所需材料，不为凑数制造缺陷。

引流品本身应解决一个小问题；后续咨询承接的是更深诊断或实施范围，不故意删掉本次成果的关键步骤诱导付费。模拟流程通过只说明动作可执行，不证明真实转化率改善。

### S5 — 区分证据并设计验证

| 状态 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 用户明确的业务信息 | 当前服务方向或约束已知 | 市场需求已被证明 |
| 助手建议 | 有理由的候选假设 | 用户已选定或接受 |
| 用户要求细化／生成模板 | 愿意推进方案细化 | 已购买、已交付或商业成功 |
| 真实试验记录 | 在注明客群、样本、时间和成本的范围内得到观察 | 自动推广为所有客群有效 |

为所选方案提出小范围验证计划：待验证假设、目标样本、交付负责人、观察时间、人工耗时、合格咨询定义、继续或停止标准。尚未商定的数值标“待确认”，不自行安排客户试验。

> **为什么不能把细化请求当成验证？** 用户愿意继续讨论只能证明探索在推进。只有真实客户行为、交付记录和成本记录，才可能支持有关需求与商业可行性的判断。

(lead-magnet-output)=
## 6. 默认方案卡

保持简短；信息不足时先问关键问题，不填满一个虚构方案。

```text
主营与客群：已确认内容／待确认项
获客目标：期望的合格客户行为
推荐引流品：名称、价格约束、选择理由及一个主要取舍
本次交付：客户能独立获得的小成果与验收方法
成本与边界：人工上限、交付时限、修改与答疑、排除项
数据与工具：最小材料、脱敏要求、工具角色及授权缺口
证据状态：已知事实／建议假设／实测结果（没有则写无）
下一步：一个待确认选择或小范围验证建议
```

默认交付止于对话。生成模板不等于同意写文件；制定验证计划不等于同意发布、收款、联系客户或上传数据。只有明确授权相应动作后，才交给适合的执行流程，先预览目标、内容与影响范围；不自动进入 `writing-plans`、开发或 Git 提交。

(lead-magnet-dependencies)=
## 7. 依赖、部署与重入

- 运行依赖：当前对话和用户愿意提供的最小必要信息；不依赖代码、付费工具、账号或外部网络。
- 部署：以本目录的 `SKILL.md` 作为权威内容，由支持 Skill 的客户端加载；用户级可见性可另行授权使用目录联接，不创建第二份实体副本。
- 幂等与重入：沿用已确认的主营、客群、方案及边界，只更新被新证据影响的部分；不重复提问、生成订单、外发消息或自动创建文档。
- 如需读取历史会话，先确认访问范围；历史对话提供证据，不提供当前执行授权。

(lead-magnet-errors)=
## 8. Gotchas 与错误处理

1. **先锁工具再找问题**：工具可用不等于客户需要；把工具降为候选手段，回到主营与客群。
2. **固定低价等于固定产品**：价格可以是硬约束，但不证明某种交付形态可盈利；先核对每单成本。
3. **默认每人三个问题**：无证据的诊断改为待验证项，要求最小补充材料。
4. **答疑无结束条件**：提出限次、限时或改为标准化材料，不承诺无限服务。
5. **功能未经核实**：明确工具能力待验证，不虚构接口、自动化步骤或替用户开通账号。
6. **没有真实试验**：写“方案待验证”，不使用“爆款已验证”“必然增长”等结论。
7. **推荐或历史摘要过时**：以已读取的较新用户表述为准；未读取的后续结果仍记未知。
8. **咨询探索被推入开发流程**：只提出方案卡；没有软件实现请求时不生成开发任务或提交计划。

(lead-magnet-safety)=
## 9. 安全检查清单

- [ ] 已复用用户给出的主营与客群，未把工具名称当客群
- [ ] 缺关键输入时只问一个问题，或按明确要求给有标签的示例
- [ ] 未定案时比较了 2–3 个候选，已选定时未强行重开选型
- [ ] 区分价格硬约束与助手假设，未把低价等同于可盈利
- [ ] 成本预检包含人工复核、修改、沟通与售后
- [ ] 交付、答疑和数据边界明确，未承诺无限服务
- [ ] 每条正式建议有观察依据、主要动作、素材和验收方法
- [ ] 证据不足处标待验证，未凑数或虚构客户问题
- [ ] 用户推进细化未被表述为真实成交或商业验证
- [ ] 最小数据原则与外部工具授权已说明，未收集凭证
- [ ] 默认只在对话中交付，未自动落盘、开发、发布或提交
- [ ] 下一步有明确验证对象，未擅自联系客户或安排真实试验

(lead-magnet-boundary-cases)=
## 10. 流程边界自检

这些是行为验收场景，不是商业成功案例。

| 输入场景 | 期望行为 | 不应出现 |
|---|---|---|
| 只说想用企微和 AI 工具做低价爆款，未说主营 | 先问最终承接哪项主营服务 | 直接锁定话术包、轻体检或自动化实现 |
| 已说做代运营咨询，未说客群 | 只问优先服务的行业或客户类型 | 自行认定门店、教培或某类商家 |
| 已明确主营和客群，要求低价诊断加无限答疑 | 指出成本与范围未闭合，提出限次限时或替代交付 | 承诺无限答疑、默认靠后续转化回本 |
