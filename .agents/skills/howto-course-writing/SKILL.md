# 零基础实操课写作法

把一份"我知道怎么做"的素材，改造成"读者照着做能做成"的文档。核心判断只有一句：**读者卡住时，需要的是定位，不是重读。**

## 1. 适用边界

适用于：课程讲稿、新手教程、产品上手文档、新人 SOP、开源 README 的 Quickstart、内部培训材料。

不适用于：PRD / 研究报告 / 竞品分析（走 `doc-writing-guide`）、纯 API 参考手册（读者是来查的，不是来学的）、需要精确坐标的工程文档。

> **为什么？** 六组件的成本很高——每条步骤都要配验收信号，每块画板都要单独设计。用在参考手册上是浪费，用在"读者必须亲手做一遍"的文档上才回本。

## 2. 五步工作流

```text
S0 定组件 → S1 搭骨架 → S2 写正文 → S3 配画板 → S4 过 12 问 → S5 交付
```

| 步 | 动作 | 产出 |
|---|---|---|
| S0 | 确认读者画像与"学完能做什么"，选定主线任务 | 一句话定位 + 4 组收获 |
| S1 | 套九段骨架（见 §5），标出缺口 | 章节清单 |
| S2 | 按六组件逐段写（见 §3） | 初稿 |
| S3 | 每章开头配一块画板（见 §4），先定类型再画 | 图 + 文 |
| S4 | 过交付前 12 问（见 §6），不达标回退到对应段 | 定稿 |
| S5 | 预览确认门：通读一遍"读者视角"路径，确认后交付 | 交付说明 |

改写旧稿走 §7，不要从 S0 重写——先定位缺哪个组件。

> **为什么？** 直接动笔最容易把力气花在"解释原理"上，而读者真正缺的是"做对了没有"。先定组件能把注意力强制分配到验收信号与兜底上。

## 3. 六组件速查

| # | 组件 | 一句话做法 | 失效信号 |
|---|---|---|---|
| 1 | 收获前置 | 开头 4 组 8-10 条，动词开头、结果可观察（能说出 / 能拿到 / 能停在） | 读到第三屏还不知道能拿走什么 |
| 2 | 一步一验收 | 每步 ≤2 条动作 + 1 条可观测 `✓`；开篇声明"共 N 步" | 读者不知道自己做对没有 |
| 3 | 一喻到底 | 一套生活比喻贯穿全文，建"生活名—功能名—代码名"三列表 | 概念堆叠，名词记住了但建不起模型 |
| 4 | 三图配置 | 地图图给总量、解剖图给结构、操作图给动作 | 图是装饰，正文承担全部解释 |
| 5 | 行动块 | 可复制的提示词/命令，五槽：情境、约束、任务、输出、安全句 | 读者理解了但不知道该怎么开口 |
| 6 | 边界前置 | 限制 + 原因 + 降级路径；人机红线；数字带上限与"以什么为准" | 读者把"我不行"归因为自己，默默退出 |

详细做法、反模式与迁移示例见 [references/six-components.md](references/six-components.md)。

> **为什么组件 2 最关键？** 其余五个组件都在降低"开始"的门槛，只有它降低"中途放弃"的概率；而实测中最常见的失败不是学不会，是不知道自己已经做错了。

## 4. 三类画板：先定类型再画

```text
这块图独立回答什么问题？
├─ 一共几步、我在哪        → 地图图（两列/分阶段 + 编号 + 底部带走句）
├─ 有哪些零件、谁归谁管    → 解剖图（放射 / 三列 / 空间隐喻，任选其一）
└─ 这一屏点哪里、看到什么  → 操作图（同构卡片 或 三格实拍）
```

硬规则：

1. 一张图只回答一个问题；答不出就删。
2. 编号与正文清单逐字同号。
3. 颜色只承担四种语义：绿=主线、黄=提示、红=拦截、灰=本期不做。
4. 范围收口写在图内（"其他先不用管：…"），不写进页脚。
5. 每块图必须有主标题（结论句）+ 副标题（视角/范围）+ 底部带走句。

六块可复用蓝图的元素清单与 Mermaid 骨架见 [references/whiteboard-grammar.md](references/whiteboard-grammar.md)。

> **为什么颜色要限四种？** 颜色是唯一能跨图复用的语义通道；一旦同一种绿色在不同图里分别表示"成功/模块/强调"，读者就要重新学习图例，图的信息量反而下降。

## 5. 九段骨架

| # | 段落 | 写成什么 |
|---|---|---|
| 1 | 定位 | 一句话：学完你能做到什么 |
| 2 | 收获 | 4 组，每条可观察 |
| 3 | 路线 | 地图图 + 一句总量说明 |
| 4 | 案例 | 3 例：权威 → 可复现 → 同类 |
| 5 | 概念 | 一套比喻 + 三列对齐表 + 解剖图 |
| 6 | 操作 | N 步 ×（2 动作 + 1 ✓）+ 操作图 |
| 7 | 行动块 | 可复制提示词/命令，每个带安全句 |
| 8 | 兜底 | 限制 + 降级路径 + 人机红线 + 三层 FAQ |
| 9 | 收尾 | 作业模板 + 下一步准备清单（每项附"目的"） |

完整 Before/After 改写示例见 [references/rewrite-playbook.md](references/rewrite-playbook.md)。

## 6. 交付前 12 问

**开场四问**

- [ ] 第一屏是否写清"能拿走什么"，且每条可被外部观察？
- [ ] 三个案例是否覆盖"真的吗 / 我能吗 / 与我有关吗"？
- [ ] 是否有一张路线图交代总量与位置？
- [ ] 展示上限后是否有一句"本期只做哪一小块"？

**过程四问**

- [ ] 操作章开头是否声明"共 N 步，每步一个看得见的结果"？
- [ ] 每步是否 ≤2 条动作、≥1 条可观测 `✓`？
- [ ] 多链路系统（说话 / 动手 / 通知）是否分别自检？
- [ ] 每个行动块是否只做一件事，并带安全句？

**兜底四问**

- [ ] 每类限制是否都配了降级路径？
- [ ] 不可逆 / 涉资金 / 涉身份 / 涉凭据的动作，是否明确由人做？
- [ ] 每个数字是否带上限、有效期与"以什么为准"？
- [ ] FAQ 是否按"通用 / 本产品特有 / 卡住了怎么求助"分层？

> **为什么是 12 问而不是一张长清单？** 每问都绑定一个可回退的段落；问不出"回退到哪"的检查项只会让作者焦虑，不会让文档变好。

## 7. 改写旧稿：四步定位

1. **对承诺**：抄出开场的收获清单，逐条问"结尾作业检查了它吗"。对不上先改结尾，不要先改正文。
2. **切步**：所有操作段落按"一步 ≤2 动作"切开，每步补 `✓`；补不出 `✓` 的步骤说明它不可观测，要拆细或换写法。
3. **配图**：给每章开头配一块图，先定类型（§4），再决定元素；原稿的截图优先归入操作图。
4. **收兜底**：把散落的限制、数字、人工环节收进边界表，再按来源拆 FAQ。

改写前先跑一次预览：把旧稿按新骨架排一遍空标题，确认没有整段无处安放，再动笔。

> **为什么先改结尾再改正文？** 作业是收获的验收单；结尾与开头对不上时，正文改得再顺也只是把错误包装得更好看。

## 9. Gotchas（陷阱与反直觉行为）

1. **"写得细"不等于"可验收"**：把一步拆成五条动作仍然没有 `✓`，读者照样不知道对错——验收信号是独立的一行，不是动作的副产品。
2. **收获写成"了解/掌握"就失效**：这类动词无法被外部观察，结尾作业也就无从检查。
3. **比喻换得越勤，读者越累**：每换一次比喻，读者要重建一次模型；宁可延长旧比喻，也不要引入新体系。
4. **配图放在写完正文之后，通常就配歪了**：图会退化成"正文的插图"；先定图类型能强制正文只写图放不下的部分。
5. **边界写进文末 FAQ 等于没写**：读者在第二章撞墙时就退出了，等不到文末。
6. **代码块越长越没人复制**：行动块控制在一屏内，超过就拆成两步。
7. **"加粗重点"是最弱的信息层级**：真正区分层级的是编号、颜色语义与版式块，不是粗体。
8. **同构卡片是自检工具**：四张卡片里只要有一张缺 `✓`，作者一眼就能发现——保持结构一致本身就是质量控制。

## 10. 安全检查清单

- [ ] 已确认目标读者与主线任务，未把参考手册当教程写
- [ ] 每条收获都能被外部观察，无"了解/熟悉/掌握"
- [ ] 每步都有可观测 `✓`，人工接管点已标注
- [ ] 行动块含安全句（只读 / 由我确认 / 不含凭据）
- [ ] 限制与降级路径写在首次出现该操作的段落旁
- [ ] 所有数字带"上限 / 有效期 / 以什么为准"
- [ ] 画板类型已定，编号与正文一致，颜色语义全篇统一
- [ ] 交付前已过 12 问并记录未达标项与回退位置
- [ ] 改写旧稿时已做预览（空标题排版）再动笔
