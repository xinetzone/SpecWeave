# 七概念方法论编译参考手册

> ⚠️ **编译产物**：本文档由知识编译模式从10个源文件一次性深度提取生成，包含可推理的结构化框架。Agent运行时仅加载此文件即可执行，无需回溯源文件。

## 1. 核心概念速查表

| 缩写 | 全称 | 一句话作用 | 关键产出物 | 对应质量门 | 层级定位 |
|:---:|------|-----------|-----------|:---------:|---------|
| **R** | Retrospective（复盘） | 采集客观事实数据、还原过程 | 事实清单（≥20条，无因果词） | G1 | 感知层 |
| **I** | Insight（洞察） | 根因分析、识别问题本质 | 核心洞察（3条，含四元组） | G2 | 认知层 |
| **E** | Extraction（萃取） | 提炼可复用跨场景模式 | 结构化模式文档（触发+步骤+反模式+迁移） | G3 | 沉淀层 |
| **C** | Atomic Commit（原子提交） | 确保变更单一职责、原子化交付 | Git原子提交+索引更新 | G4 | 执行/沉淀层 |
| **A** | Atomization（原子化） | 大文档/大任务拆分为原子单元 | 拆分方案+原子文件+引用修复 | G4前置 | 执行层 |
| **F** | First Principles（第一性原理） | 本质思考、剥离假设、创新突破 | 公理列表+自下而上重构方案 | V门强制验证 | 认知层 |
| **V** | Adversarial Review（对抗审查） | 多视角证伪、防御认知偏差 | 审查意见+修正后产出 | V门 | 验证层（横切） |

## 2. 场景→链路决策树（可直接if-then执行）

```
IF 用户请求匹配以下特征 THEN 执行对应链路
```

### 场景1：里程碑复盘
- **触发词**：复盘、总结、回顾、Sprint结束、版本交付、上线后
- **标准链路**：R → I → E → [可选V] → A → C
- **执行顺序**：
  1. R：采集≥20条客观事实 → G1检查
  2. I：提炼3条四元组洞察 → G2检查
  3. V（可选，depth=quick跳过）：对抗审查修正洞察
  4. E：萃取1-2个可迁移模式 → G3检查
  5. A：行动项原子化拆分
  6. C：原子提交交付
- **预期产出**：复盘报告 + 3条洞察 + 1-2模式 + 3-5原子行动项

### 场景2：问题解决（故障/Bug）
- **触发词**：Bug、故障、问题、P0/P1、根因、为什么会发生
- **标准链路**：F → V → C → R → I → E
- **执行顺序**：
  1. F：5Why根因分析（≥5层追问）
  2. V：**强制**对抗审查验证根因（不可跳过）
  3. C：修复提交（单一职责+测试验证）
  4. R：事后复盘事实采集
  5. I：问题预防洞察
  6. E：预防模式萃取 → G3检查
- **预期产出**：根因分析 + 修复提交 + 事后复盘 + 1个预防模式

### 场景3：重构优化（技术债/拆分）
- **触发词**：重构、优化、技术债、坏味道、拆分、太大了
- **标准链路**：I → F → A → V → C
- **执行顺序**：
  1. I：洞察重构本质问题
  2. F：第一性原理设计重构方案
  3. A：原子化拆分方案设计
  4. V：**强制**等价性验证（功能不变？依赖完整？）
  5. C：每个拆分点一次原子提交
- **预期产出**：原子拆分方案 + 等价验证报告 + 原子提交序列

### 场景4：知识沉淀（模式/最佳实践）
- **触发词**：总结方法、沉淀模式、经验、最佳实践、怎么做
- **标准链路**：R → I → E → V → C（入库）
- **执行顺序**：
  1. R：收集≥2个独立案例
  2. I：跨案例共性洞察
  3. E：完整模式文档萃取
  4. V：**强制**多视角攻击+跨领域迁移验证 → G3检查
  5. C：模式入库+索引更新+交叉引用修复
- **预期产出**：案例集 + L2+成熟度模式 + 索引更新

### 场景5：创新突破（新方案/架构设计）
- **触发词**：新方案、创新、从零开始、架构设计、怎么设计
- **标准链路**：F → V → I → C
- **执行顺序**：
  1. F：公理识别+假设剥离+自下而上重构
  2. V：**强制**假设攻击（≥3个失败场景已防御）
  3. I：洞察落地路径+边界条件
  4. C：PoC代码/设计文档原子提交
- **预期产出**：公理体系 + 假设攻击报告 + 创新方案 + PoC提交

### 深度裁剪规则
- `depth=quick`：跳过V对抗审查（仅场景1/4允许，问题/重构/创新不可跳V）
- `depth=standard`（默认）：按场景标准链路执行V
- `depth=deep`：多轮对抗审查，强化V
- **不可裁剪最小闭环**：R→I→C（事实→洞察→行动），任何场景不可缺

## 3. G1-G4+V质量门标准（逐项可打勾）

### G1：事实无因果词（R阶段产出检查）
- [ ] 事实数量≥20条（里程碑/知识场景）
- [ ] 无"因为"、"所以"、"导致"、"错误"、"失误"等因果/判断词
- [ ] 所有事实为可验证的客观陈述
- [ ] 关键数据（数字、URL、命令、版本）完整无遗漏
- [ ] 每条事实可追溯到来源，无主观评价
- [ ] 无过度引申，不包含原文未提及的内容
- **不合格处理**：返回R阶段重写，剥离所有判断和推断

### G2：洞察四元组完整（I阶段产出检查）
- [ ] 洞察数量≥3条
- [ ] 每条洞察包含完整四元组：
  - [ ] 陈述：清晰的结论性判断
  - [ ] 证据：引用R阶段事实编号（F-xxx）
  - [ ] 反常识：挑战了什么默认假设
  - [ ] 行动：具体可执行的建议
- [ ] 洞察之间不重叠，维度独立
- [ ] 有反常识性，不是正确的废话
- [ ] 行动建议指向具体行为，不是空泛口号
- **不合格处理**：返回I/F阶段补充缺失部分

### G3：模式可迁移（E阶段产出检查）
- [ ] 模式名称4-8字，好记、有传播性
- [ ] 触发场景清晰：包含"适用于"和"不适用于"边界
- [ ] 核心做法有3-7个具体步骤，可直接执行
- [ ] **至少3个反模式**，且均来自实际案例教训
- [ ] 有明确检验标准（做完怎么知道做对了）
- [ ] 有≥1个非当前领域的跨场景迁移示例
- [ ] 多案例支撑（≥2个→L2）或明确标注"单案例待验证"（L1）
- [ ] YAML frontmatter字段完整，id唯一
- **不合格处理**：返回E阶段重新抽象，提升抽象层级

### G4：行动项原子化（C/A阶段产出检查）
- [ ] 单一职责：每个行动项/提交只做一件事
- [ ] 可独立验证：完成与否有明确验收标准
- [ ] 有Owner：明确谁来做
- [ ] 有时间节点：明确何时完成
- [ ] 可独立交付：不依赖其他未完成项可单独交付/回滚
- [ ] 预提交验证全部通过（链接检查、格式检查、测试）
- [ ] 提交信息遵循Conventional Commits规范，中文描述"为什么"
- [ ] fix类型提交包含预防措施（测试/检查脚本/规则更新）
- **不合格处理**：返回A阶段重写行动项/拆分提交

### V门：对抗审查有实质内容（V阶段检查）
- [ ] 4个视角全部覆盖（魔鬼代言人/新人/老板/未来）
- [ ] 审查意见≥5条，每条有具体攻击点（非"写得很好"类客套话）
- [ ] 至少采纳2条意见对原产出进行修正
- [ ] F（第一性原理）之后V不可跳过
- [ ] 修复后进行了回归对抗（代码审查场景）
- **不合格处理**：重新审查，禁止表演式走过场

## 4. 7个概念执行步骤模板

### R - Retrospective（复盘）
| 项 | 内容 |
|----|------|
| **输入** | scope（project/iteration/task/incident）、主题、时间范围 |
| **核心动作** | 1. 收集执行记录与变更历史<br>2. 提取关键决策节点与时间线<br>3. 汇总问题与异常事件列表<br>4. 按纯客观标准记录事实，剥离所有判断<br>5. 数据验证三查法（查数字/查链接/查结构） |
| **输出** | 事实清单（编号F-001起）、时间线、关键事件表 |
| **常见反模式** | ❌ 先有结论再找事实（确认偏误）<br>❌ 事实中混入因果推断<br>❌ 凭记忆估算数据不实际统计 |

### I - Insight（洞察）
| 项 | 内容 |
|----|------|
| **输入** | R阶段事实清单（必须引用事实编号） |
| **核心动作** | 1. 趋势分析：识别异常波动与拐点<br>2. 根因分析：5-Whys追问到系统性根因<br>3. 提炼四元组：陈述/证据/反常识/行动<br>4. 识别反常识点（挑战默认假设） |
| **输出** | 3条核心洞察（每条含完整四元组） |
| **常见反模式** | ❌ 洞察变成吐槽/抱怨<br>❌ 没有反常识，都是正确的废话<br>❌ 行动建议空泛不可执行<br>❌ 证据不引用事实编号，不可追溯 |

### E - Extraction（萃取）
| 项 | 内容 |
|----|------|
| **输入** | I阶段洞察（必须包含四元组）、≥2个案例 |
| **核心动作** | 1. 跨案例分析：提取成功/失败共同要素<br>2. 本质抽象：剥离具体细节，连续追问"换个项目还成立吗"<br>3. 结构化：填充模式模板（触发/步骤/反模式/检验/迁移）<br>4. 反模式提炼：至少3个来自实际教训<br>5. 迁移验证：想≥1个非当前领域场景<br>6. 索引更新+交叉引用修复 |
| **输出** | 结构化模式文档（含YAML frontmatter）、目录索引更新 |
| **常见反模式** | ❌ 总结"这次怎么做的"而非"下次怎么做"<br>❌ 只写正确做法不提炼反模式<br>❌ 单案例就标记为"已验证"<br>❌ 抽象层级不对（太具体无法复用/太抽象是废话）<br>❌ 强行凑模式过度抽象 |

### C - Atomic Commit（原子提交）
| 项 | 内容 |
|----|------|
| **输入** | 所有前置产出物（报告/模式/行动项/变更文件） |
| **核心动作** | 1. 三查暂存法：查新增/修改/删除文件，确保单一职责<br>2. 预提交验证：链接检查+格式检查+测试<br>3. 构建提交信息：&lt;type&gt;(&lt;scope&gt;): &lt;subject&gt;（中文描述"为什么"）<br>4. 执行提交（Windows用UTF-8方案避免乱码）<br>5. 提交验证：git show --stat确认文件列表<br>6. 编码验证：确认中文无乱码 |
| **输出** | Git原子提交、提交哈希、变更日志 |
| **常见反模式** | ❌ 多个不相关变更混在一个提交<br>❌ 提交信息描述"做了什么"而非"为什么做"<br>❌ 跳过预提交验证/--no-verify<br>❌ Windows下直接git commit -m "中文"导致乱码<br>❌ git add目录不检查文件删除记录 |

### A - Atomization（原子化）
| 项 | 内容 |
|----|------|
| **输入** | 待拆分文件/模块、拆分策略（topic/function/module） |
| **核心动作** | 1. 分析源文件：识别核心主题与依赖<br>2. 制定拆分方案：确定拆分点与新文件路径<br>3. 执行拆分：创建新文件+迁移内容<br>4. 更新引用：内部链接+外部引用+目录索引<br>5. 运行收尾脚本：finalize-atomization.py自动修复断链 |
| **输出** | 原子文件集合（500-5000字符/个）、更新后的引用、验证报告 |
| **常见反模式** | ❌ 过度拆分导致碎片化<br>❌ 拆分后内容丢失或重复<br>❌ 不更新交叉引用造成断链<br>❌ 拆分破坏语义完整性 |

### F - First Principles（第一性原理）
| 项 | 内容 |
|----|------|
| **输入** | 问题陈述、约束条件、待验证假设 |
| **核心动作** | 1. 问题界定：区分症状与根因，明确边界<br>2. 假设剥离：列出所有隐含假设，逐条验证，归零到事实<br>3. 要素识别：拆解到不可再分的基础单元<br>4. 公理提炼：提炼自洽的独立公理<br>5. 自下而上重构：从公理推导解决方案<br>6. 方案验证：覆盖全部边界+成本收益评估<br>**（工程问题用v1六步法，跨领域/价值观问题用v2七步法）** |
| **输出** | 假设清单、要素清单、公理列表、重构方案、验证记录 |
| **常见反模式** | ❌ 为创新而创新，方案不服务原问题<br>❌ 简单问题滥用第一性原理过度拆解<br>❌ 假设没剥干净就跳到重构<br>❌ 否定一切经验价值（第一性原理≠反经验）<br>❌ F之后不做V对抗审查 |

### V - Adversarial Review（对抗审查）
| 项 | 内容 |
|----|------|
| **输入** | 待审查完整产出（不能只给结论）、场景类型 |
| **核心动作** | 1. 明确审查目标与范围<br>2. 并发启动4视角（或5攻击者角色，代码场景）<br>3. 每个角色独立输出具体问题清单<br>4. 汇总交叉验证，去重，关联不同视角发现的关联问题<br>5. 修正产出<br>6. 修复后回归对抗（代码场景） |
| **输出** | 审查问题清单（按P0-P3分级）、修正后的产出、审查记录 |
| **常见反模式** | ❌ 表演式审查：输出"写得很好"无实质内容<br>❌ 角色混同：一个Agent扮演多个攻击者角色<br>❌ V在F之前执行（攻击旧方案而非新方案）<br>❌ 只找问题不修正产出<br>❌ 代码修复后不做回归对抗 |

## 5. 反模式清单（必须避免）

| # | 反模式名称 | 表现 | 后果 | 正确做法 |
|---|-----------|------|------|---------|
| 1 | 跳过场景识别全链路执行 | 不管什么场景都走完R→I→E→C→A→F→V全部7个概念 | 过度工程，浪费时间在不必要环节 | 按决策树选场景，轻量场景2-3个概念即可 |
| 2 | 质量门不通过硬推进 | G1/G2/G3/G4不通过还继续下一阶段 | 垃圾进垃圾出：基于错误事实的错误洞察，不可复用的伪模式 | 质量门是硬关卡，不合格返回当前阶段修复 |
| 3 | 先有结论再找事实 | 带着预设判断做复盘，只找支持性证据 | 确认偏误，复盘变成自证预言 | R阶段纯客观记录，I阶段再分析 |
| 4 | V在F之前执行 | 还没做第一性原理推导就先对抗审查 | 攻击的是旧方案而非新方案，无法验证F推导的正确性 | V必须在F之后执行，先有方案再攻击 |
| 5 | 强行给所有场景加F | 里程碑复盘/知识沉淀也强行用第一性原理 | 简单问题复杂化，过度拆解 | F仅在问题解决/创新突破/重构场景需要 |
| 6 | 萃取=写摘要 | 把萃取当成总结这次怎么做，写书摘式内容 | 产出不可复用，无法跨场景迁移 | 萃取必须去场景化，提炼"下次遇到类似情况怎么做" |
| 7 | 只萃取正确做法不写反模式 | 模式文档只有"怎么做"没有"不要怎么做" | 后人踩同样的坑，反模式比正确做法更有价值 | 反模式对等原则：每个模式至少3个反模式 |
| 8 | 表演式对抗审查 | V阶段输出"写得很棒，没有问题"之类客套话 | 质量门虚设，缺陷漏到线上 | 审查意见≥5条且具体，至少采纳2条修正 |
| 9 | 原子提交混多个变更 | 一个提交包含重构+新功能+Bug修复+文档 | 无法回滚、无法cherry-pick、审查困难 | 三查暂存法，单一职责，每个提交只做一件事 |
| 10 | 忽视顺序原则 | 先做E萃取再做I洞察，先C提交再做V审查 | 经验主义（没想清为什么就总结怎么做），未审查就提交漏测 | 严格遵循R→I→E→A→C顺序，V横切验证 |
| 11 | Windows中文提交乱码 | PowerShell直接git commit -m "中文" | 提交信息乱码不可读 | 用git-commit-utf8.py或UTF-8临时文件+git commit -F |
| 12 | 修复后不回归对抗 | 发现问题修复就完事，不再重新审查 | 修复引入新BUG（常态，不是例外） | 代码场景修复后必须重新执行对抗审查 |
| 13 | 跨领域概念不扫描 | 涉及多领域项目不做术语对齐 | 语义漂移，鸡同鸭讲 | 跨领域项目前置执行术语扫描，约定项目内定义 |
| 14 | 过度原子化拆分 | 文件拆得太碎，每个文件只有几行 | 碎片化，导航困难，维护成本上升 | 文件大小控制在500-5000字符，保持语义完整性 |

## 6. 4视角对抗审查速查表

执行V阶段时，按以下4个视角逐一提问：

### 🔴 视角1：魔鬼代言人（Devil's Advocate）—— 刻意挑刺
- 这个结论有没有可能是错的？反例是什么？
- 数据来源可靠吗？有没有可能是"最优场景数据"？
- 因果关系有没有搞反？相关≠因果？
- 有没有幸存者偏差？只看到成功案例没看到失败？
- 作者/提出者有没有利益冲突？
- 历史上有没有类似方案失败过？为什么失败？

### 🟢 视角2：新人视角（Newcomer）—— 我刚入门，这些我不懂
- 这个概念/术语是什么意思？第一次见，不解释看不懂
- 前置条件是什么？需要先会什么才能用？
- "然后呢？"看完知道了问题，但不知道第一步该做什么
- 有没有Hello World级别的入门示例？
- 不同背景的人（Windows/Mac、前端/后端）选择是否不同？
- 为什么要这么做？不这么做会怎样？有没有更简单的方法？

### 🟠 视角3：老板视角（Boss）—— 这对业务有什么用？
- 投入产出比如何？学习成本 vs 实际收益？
- 企业能用吗？安全/合规/版权/管控问题解决了吗？
- 有没有数据证明效率提升了X%？（token效率≠人的效率）
- 风险是什么？最坏情况会怎样？
- 什么时候能看到效果？短期/中期/长期？
- 不做会怎样？机会成本是什么？

### 🔵 视角4：未来视角（Futurist）—— 一年后回看会怎样？
- 这是不是过渡形态？底层趋势对了但产品形态会迭代？
- 如果环境变化了（技术进步/成本下降/政策变化），这个结论还成立吗？
- 缺失的拼图是什么？现在没人做但未来会成为关键的部分？
- 二阶效应是什么？这么做了之后会引发什么连锁反应？
- 5年后回看，今天认为正确的事会不会变成笑话？

### 代码审查场景5攻击者角色（补充）
| 角色 | 攻击目标 | 典型问题 |
|------|---------|---------|
| 🔴 安全攻击者 | 加密/认证/权限 | 密钥能绕过吗？认证能伪造吗？ |
| 🟢 边界攻击者 | 输入/路径/格式 | 超大文件？畸形输入？路径遍历？ |
| 🟠 完整性攻击者 | 校验/元数据/历史 | 数据能篡改吗？校验和能伪造吗？ |
| 🔵 时序攻击者 | 并发/超时/竞态 | 并发读写会冲突吗？会死锁吗？ |
| 🟣 模糊测试者 | 随机/异常/边界值 | null/空值/乱码输入会崩溃吗？ |

## 7. CMD-LOG规范

### Session命名格式
```
sc-YYYYMMDD-<topic-kebab-case>
示例：sc-20260803-seven-concepts-compilation
```

### 步骤编号约定
| 阶段 | 步骤编号 | 事件类型 |
|------|---------|---------|
| 编排启动 | S0 | CMD_START |
| 场景识别 | S1 | SCENARIO_DETECTED |
| 链路选择 | S2 | CHAIN_SELECTED |
| R阶段 | R0-Rn | CONCEPT_STARTED, CONCEPT_COMPLETED |
| I阶段 | I0-In | 同上 |
| E阶段 | E0-En | 同上 |
| A阶段 | A0-An | 同上 |
| F阶段 | F0-Fn | 同上 |
| V阶段 | V0-Vn | 同上 |
| C阶段 | C0-Cn | 同上 |
| 质量门 | G1/G2/G3/G4/V | GATE_PASSED, GATE_FAILED |
| 子命令调用 | 任意 | SUB_CMD_INVOKED |
| 完成 | S99 | CHAIN_COMPLETED |

### 日志格式
```
[CMD-LOG] | level=INFO | cmd=seven-concepts | step=<Sx/Rx/...> | event=<EVENT_TYPE> | session=sc-... | msg=<描述> | ctx={...JSON上下文...}
```

### 核心事件定义
- `CMD_START`：编排开始，记录scenario/topic/depth
- `SCENARIO_DETECTED`：场景识别结果，记录匹配的触发词和场景类型
- `CHAIN_SELECTED`：概念链路选定，记录链路序列和裁剪决策
- `CONCEPT_STARTED`：单个概念开始执行
- `CONCEPT_COMPLETED`：单个概念完成，记录产出物摘要
- `GATE_PASSED`：质量门通过，记录检查项摘要
- `GATE_FAILED`：质量门不通过，记录不合格项和返工计划
- `SUB_CMD_INVOKED`：调用子命令（R/I/E/C/A/F/V），记录传递的上下文
- `CHAIN_COMPLETED`：全链路完成，记录质量门通过记录和产出物清单

## 9. 顺序不可颠倒原则（强制执行）

1. **R必须在I之前**：没有干净的事实基础，洞察一定有偏差
2. **I必须在E之前**：没想清楚"为什么"就总结"怎么做"，是经验主义
3. **A必须在C之前**：大的东西先拆再提交，保证单一职责
4. **V必须在C之前**：没经过对抗的产出，质量门等于虚设
5. **V必须在F之后**：先有方案再攻击，不能攻击不存在的东西
6. **E必须在V之后（知识场景）**：模式经过对抗验证再入库
7. **C是所有有变更场景的终点**：修复即闭环，所有变更最终原子提交
