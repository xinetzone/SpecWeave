# AI 委托编排 Skill

> 把「帮我交给 AI 去做」从一句话，变成五个可验收动作：**定路线 → 建地图 → 写任务 → 控成本 → 排故障**。

本 Skill 是方法论模式库五篇模式的编排门面（L1），完整论证在 L2 模式文档，本文件只保留可直接执行的判据、卡片与模板。

## 1. 何时使用

### 触发信号分级

| 级别 | 信号 | 动作 |
|---|---|---|
| T0 弱信号 | 只提到「AI」「Agent」「自动化」「让它帮我」「代操作」，未说明对象、副作用或验收方式 | 先问三件事：交给谁、会不会改变外部状态、怎么算完成；确认后才进入编排 |
| T1 中信号 | 用户说「把这件事交给 AI / 让它去做」，但条件与边界缺失 | 直接进入 P3 任务书，把缺口补成四要素 |
| T2 强信号 | 用户明确要求对真实系统执行有副作用的动作（下单、支付、发送、发布、删除、改生产配置、批量改文件），或要求「写个任务书 / 帮我看看 Agent 为什么卡住 / 这个任务怎么拆」 | 按五模式编排并生成任务书或排障记录 |

**不适用**：

- 纯问答、纯生成、可无限重做且无外部副作用的探索；
- 目标本身还不清楚——先做需求澄清，不要用任务书把模糊目标固化（任务书会放大错误目标）；
- 用户要的是「改这个仓库的代码」而不是「委托外部执行者」——那是 TRAE-plan-mode / TRAE-spec-mode 的领域。

## 2. 五条洞察 → 五条判据

本 Skill 的判断层不是规则清单，而是五条从真实案例抽出的判据。洞察原文在上游知识包，这里只保留可执行形态。

| # | 洞察 | 可执行判据 | 落在哪个模式 | 违反时的典型症状 |
|---|---|---|---|---|
| 1 | 真正的分水岭在操作链，不在聊天链 | 出故障先分链，不要先换模型或重填配置 | P4 | 「闲聊有回复、界面却不动」却反复换模型 |
| 2 | 二次开发杠杆在规则/技能/记忆，不在核心代码 | 改动落点按「可声明资产 → 规则/技能 → 界面 → 核心层」自上而下找 | P1 | 一上来就改核心执行器，改动面失控 |
| 3 | 长任务成本由截图次数（步数）决定 | 写任务时就估算步数、分段、前移停点 | P5 | 任务书写得含糊，同一模型多走十几步 |
| 4 | 人类在环是能力边界，不是安全补丁 | 不可逆动作必须位于停点之后或红线之内 | P3 | 停点写在支付页（订单已生成） |
| 5 | 首次接触只讲不改 | 首次勘察以「工作区零改动」为验收条件 | P2 | 边看边改，改坏后无法归因 |

> **为什么？** 洞察是结论，判据是动作。只记「成本由步数决定」不会改变任何一次任务下发；把它写成「写任务时先估步数、把停点前移」才会。判据的价值在于它能在写任务书的那五分钟里被触发。

## 3. 编排总览

```text
委托前                          委托中                失败后
──────────────────────────────────────────────────────────────
P1 定路线 ──→ P2 建地图 ──→ P3 写任务书 ──→ P5 控成本 ──→ P4 排障
                                    ↑                        │
                                    └────── 回到 P3 改任务书 ──┘
```

- **正向（新建委托）**：P1 → P2 → P3 → P5，产出一份可执行任务书。
- **反向（排障）**：P4 先定位坏在哪条链，再按结论回 P3 改任务书（或回 P1 换底座）。
- **可跳过**：P1 仅在「要不要基于现成底座做」尚未决定时需要；P2 仅在执行者第一次接触该系统时需要；P5 仅在任务是图形界面多步任务时需要。

> **为什么允许跳步？** 五模式不是流水线而是候选集。知识沉淀类与纯事务类委托常常只需 P3；把五步全跑一遍，会把一次「发一封邮件」变成一次流程改造。

## 4. 阶段执行卡

### 4.1 P1 定路线（底座先行最小定制）

**输入**：目标能力、候选底座、时间与许可约束。

**动作**：

1. 判断目标能力是否与某个成熟底座高度重合；重合则先跑通最小闭环，并**冻结基线**（可用能力、不可用能力、报错、耗时）。
2. 最小闭环在零改动下就跑不通 → 换底座或先修通，不要把「装不起来」当作定制第一步。
3. 落点按层找：可声明资产（配置/提示词/记忆）→ 规则/技能 → 界面 → 核心操作层。
4. 一次只改一个落点，改完立即在真实环境验证一次。
5. 每条改动登记三元组：改了什么｜怎么证明生效｜怎么退回。

**产出**：基线快照 + 落点表 + 改动台账。

**质量门**：能否在不改核心操作层的前提下完成一次定制，并给出回滚方式？

### 4.2 P2 建地图（只讲不改勘察）

**输入**：陌生系统 + 一个具体需求。

**动作**：

1. 先写三问：关键模块在哪｜一次请求经过哪几步｜改某类行为该动哪里。
2. 在任务描述**末尾**写死否定式约束：「先只讲解，不要修改任何文件」。
3. 要求用非开发者能懂的话复述，暴露理解空洞。
4. 人工核对说法与目录/入口是否一致，重点抓「把不存在的东西说成存在」。
5. 用版本控制状态证明零改动（未跟踪 + 已修改清单为空）；无版本控制时用哈希快照前后比对。

**产出**：系统说明 + 三问答案 + 零改动证据。

**质量门**：三问答案都指向真实文件，且变更清单为空。

### 4.3 P3 写任务书（四要素 + 红线）

| 要素 | 写法 | 常见失效 |
|---|---|---|
| 做什么 | 哪个环境、哪个对象、达成什么可观察结果 | 只有目标没有对象（「整理一下资料」） |
| 条件 | 预算、规格、时间、数量全部换成数字或有限枚举 | 用形容词（「便宜点」「尽快」） |
| 停点 | 用可观察的位置/动作边界描述终点，且早于不可逆动作 | 停点写在不可逆动作之后 |
| 回报 | 3–5 项交接字段，直接对应验收判断 | 要求叙述过程而非回报字段 |
| 红线 | 显式禁止动作 + 越界时停下上报 | 红线只写在人脑里 |

发送前四问自查：第三人能说出「它会在哪停」吗？每条条件都能判真假吗？停点早于所有不可逆动作吗？回报项足以验收吗？

**产出**：可复制、可验收的任务书（模板见 [references/task-brief-template.md](references/task-brief-template.md)）。

**质量门**：四问全为「是」。

### 4.4 P5 控成本（截图成本裁剪）

**输入**：图形界面多步任务（手机/浏览器/桌面 Agent）。

**动作**：

1. 按「一次搜索/一次筛选/进一次详情页/一次表单填写各算一步」估算步数，找出占步数最多的一段。
2. 切成「侦察 → 选定 → 决策」三段，每段有独立完成标志，分别验收。
3. 条件数字化，减少 Agent 来回比较。
4. 停点前移：能停在列表页就不进详情页，能停在详情页就不进结算页。
5. 记录每轮步数、重试次数、费用与验收结果，形成自己的基线。

**产出**：三段任务书 + 步数/费用台账（模板见 [references/step-ledger.md](references/step-ledger.md)）。

**质量门**：第二次执行同类任务时步数下降或明确说明为何不能下降，且验收项没有减少。

> **为什么不能靠换便宜模型降本？** 单价下降但步数不变；弱模型更容易试错，反而增加总步数与失败率。成本的自变量是任务书写法。

### 4.5 P4 排障（分链定位）

**前置**：系统必须存在两条可独立观测的链路——一条只触发理解、不产生外部动作；一条只触发执行、不依赖复杂推理。找不到这类指令时，改用逐部件替换法。

**五步**：

1. 一条最小指令验证理解链（复述要求、解释文本）。
2. 一条最小指令验证执行链（打开固定页面、写固定文件、跑固定命令），**以外部可观察状态为准**。
3. 落到四分支之一：只理解不执行｜只执行不理解｜两条都不通｜执行中途停。
4. 只查该分支的固定三项，一次只改一项，改完用同一条最小指令复测。
5. 重跑两条最小指令做**交叉回归**，确认没有把另一条链弄坏。

**产出**：分支判定 + 单点改动记录 + 交叉回归结果（工作表见 [references/triage-worksheet.md](references/triage-worksheet.md)）。

**质量门**：能说出「这次坏在哪条链、改了哪一项、另一条链是否仍通」。

## 5. 任务书模板（可直接复制）

```text
【做什么】在 <环境/设备/账号/站点> 上，对 <对象> 达成 <可观察结果>。
【条件】<预算 ≤ N 元>；<规格 = 枚举值>；<时间 ≤ 今天 18:00>；<数量 = N>。条件冲突时优先级：<预算 > 规格>。
【停点】停在 <页面/动作> 之前；到达停点后不再深入。
【回报】①<名称> ②<关键属性> ③<价格/数量> ④<你判断所需的其他项>。
【红线】不要 <加购/下单/发送/删除/改配置/代填凭据>；遇到 <验证码/实名人脸/密钥输入> 请停下并告知我。
```

填写示例与三类任务（采购、信息收集、内容处理）的对照见 [references/task-brief-template.md](references/task-brief-template.md)。

## 6. 分链排障卡

| 分支 | 现象 | 固定检查项（按系统替换） |
|---|---|---|
| 只理解不执行 | 有合理回复，外部无变化 | ① 执行侧模型/执行器是否配置 ② 输入模态是否被支持（如能否读屏） ③ 执行所需权限/无障碍是否被关闭 |
| 只执行不理解 | 不听指令但外部有异常动作 | ① 意图路由是否指向错误技能 ② 上下文/记忆是否污染 ③ 提示词或工具描述是否过期 |
| 两条都不通 | 两条最小指令都失败 | ① 凭据与配额 ② 网络与端点 ③ 运行时版本与依赖 |
| 执行中途停 | 跑到一半不动 | ① 是否触发确认闸门等待人工 ② 单步超时/重试上限 ③ 中途错误是否被静默吞掉 |

## 7. 预览确认与幂等

1. **预检**：列出本次将下发的任务书字段、预计步数与不可逆动作清单，逐项标注依据。
2. **预览**：把任务书全文原样贴出，不截断，让用户自己判断停点位置与条件松紧。
3. **确认**：用户明确认可后才视为可下发；用户改动则回到 P3 重出预览。
4. **重复检查**：同一目标若已下发过，先比对旧任务书——停点、条件、红线未变时直接复用并只增量修改；已给出的排障结论不重复推导。

> **为什么？** 任务书一旦下发，执行者就会按它行动；错误停点的代价不是多跑一步，而是不可逆动作被提前执行。预览把「建议」和「已下发」之间的边界固定住，幂等则避免同一委托被重复执行、重复计费。

## 8. 安全检查清单

- [ ] 副作用等级已判定（只读 / 可回退 / 不可逆），且写进任务书
- [ ] 停点早于所有不可逆动作，且位置可观察
- [ ] 红线逐条列出，并写明越界时的上报动作
- [ ] 条件全部可机械判定，无形容词残留
- [ ] 回报项足以在不回放过程的前提下验收
- [ ] 价格、数量、时间等关键数字已由用户确认，未经推断
- [ ] 凭据类输入（密码/验证码/密钥/实名）已排除在委托范围外
- [ ] 预览稿已给出并获用户确认后才下发

## 9. Gotchas：隐性陷阱

| # | 陷阱 | 表现 | 正确做法 |
|---|---|---|---|
| 1 | 「有回复」当作「已执行」 | Agent 说「已为你打开页面」，实际界面没变 | 执行链判定一律以外部可观察状态为证据 |
| 2 | 停点写在不该写的地方 | 写「下单后停在支付页」——订单已生成，回滚成本已发生 | 停点必须是不可逆动作**之前**的位置 |
| 3 | 只写「先看看」 | 正向描述不构成禁止，执行者仍会顺手改 | 用否定式祈使句写死「不要修改任何文件」 |
| 4 | 用形容词当条件 | 「便宜点」「性价比高」「尽快」 | 换成数字区间或有限枚举，并写冲突优先级 |
| 5 | 一次改三项配置 | 恢复了也不知道哪项起作用 | 一次只改一项，改完用同一条最小指令复测 |
| 6 | 只复测故障链 | 修执行链时改了模型配置，把理解链弄坏 | 修复后两条最小指令都复跑，做交叉回归 |
| 7 | 以减少步数为由放宽验收 | 少比一家候选、少核一项回报，却记为降本成功 | 步数下降且验收项不变才算优化；否则是降低目标 |
| 8 | 任务书替代需求澄清 | 目标尚模糊就写四要素，错误目标被放大 | 先澄清到能写出「停点」再写任务书 |

> **为什么？** 这八条的共同点是「看起来都完成了任务」——每份产物读起来都像一份合格的委托。正因如此只能靠停点位置、外部状态证据与交叉回归这三类可核对的锚点拦住，而不能靠结果自检。

## 10. 检验标准

- [ ] 任务书四问自查全部为「是」（可复述 / 可判定 / 不可逆安全 / 可验收）
- [ ] 每次只改一个落点或一项配置，且有一次对应验证
- [ ] 排障结论包含「哪条链、改了哪项、另一条链是否仍通」
- [ ] 图形界面任务有步数与重试次数记录，可回答「贵在哪一段」
- [ ] 首次勘察有零改动证据（状态输出或哈希对照）
- [ ] 全过程未替用户执行不可逆动作，未代填凭据

## 11. 边界与邻近技能

| 邻近资产 | 关系 | 区分判据 |
|---|---|---|
| TRAE-plan-mode | 不同对象 | 它规划**本仓库内**的有界代码变更并等批准；本 Skill 面向**外部执行者**（Agent/外包/自动化）的任务契约，不产出代码计划 |
| TRAE-spec-mode | 不同对象 | 它用于复杂仓库变更的需求-任务-审查闭环；本 Skill 不写 spec，只写委托契约与排障记录 |
| 四要素 vs 子代理文档模板 | 相邻易混 | 子代理模板约束「写哪份文档、frontmatter 是什么」；本 Skill 约束「做到哪停、回来报什么」。给「在电商站买一台指定规格的笔记本」，子代理模板不提供停点与回报字段 |
| 输出行为规范 | 互补 | 输出行为规范约束「说什么、说多少」；本 Skill 约束「做到哪、停在哪」，两者可写进同一份任务书 |
