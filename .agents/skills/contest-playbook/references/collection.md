# 规则采集与结构化规约

> **本文件是 SKILL.md 步骤 1—2 的细则**。这一层的产出（编号事实 + 缺口登记）比任何具体章节都更可复用——**它跨比赛完全通用**，因为它解决的是"如何把不可信的规则文本变成可核验的事实底账"。

---

## 一、采集阶梯（命中即停）

### L1 · 静态 HTML 直读

```bash
curl -sL "<活动页URL>" -o /tmp/act.html
# 找规则容器：常见 id/class 名 rule|detail|content|rules|notice
grep -o '<div[^>]*class="[^"]*rule[^"]*"[^>]*>.*' /tmp/act.html | head
```

**命中标志**：规则正文在 `<div>`/`<table>`/`<ul>` 里，且剥离标签后是成段的自然语言。

**失效标志**：剥离后只剩几十行导航文字，或正文里出现大量 `{{`、`__INITIAL_STATE__`、`window.__` 之类。

### L2 · 平台 API / 开放平台 CLI

若活动发布在有开放平台的社区（如知乎），优先用官方 CLI 取正文——**比浏览器更稳、更快、不消耗额度太多**。

```bash
<cli> search zhihu --query "<活动名> 参赛 规则" --count 5
```

⚠️ **CLI 返回的正文可能是片段**，不含内链 href 与图片 src；需多轮搜索拼接，或配合 L4 补全。

### L3 · SPA 引导数据逆向（实战中最有效的一级）

**识别特征**：静态 HTML 只有一个引导脚本，正文不在 DOM 里。

**步骤**：

```bash
# 1. 从静态 HTML 提取引导数据
grep -o 'window\.__[A-Z_]*__[^<]*' /tmp/act.html | head -c 2000

# 2. 从中提取 nodeId / artifact 清单 / publishVersion
#    典型结构：{"nodeId":"xxx","artifacts":[...],"publishVersion":49}

# 3. 拼出静态托管基址
#    典型模式：https://<host>/page/<nodeId>/<ver>/
#    在 bootstrap 字段里找 baseUrl/host/path 前缀

# 4. 下载该目录下的产物
curl -sL "<基址>/<artifact>.html" -o /tmp/app.html
curl -sL "<基址>/janus.data.json" -o /tmp/janus.json   # 状态树
```

**5. 从状态树取正文**——这是关键一步：

```bash
# janus.data.json 里有大文本节点，正文常在 JS 的函数返回字符串里
python - <<'PY'
import json, re
d = json.load(open('/tmp/janus.json', encoding='utf-8'))
blob = json.dumps(d, ensure_ascii=False)
# 定位形如 function ruleHTML(){ return "...." } 的函数体
for m in re.finditer(r'function\s+(\w*rule\w*|\w*Rule\w*)\s*\(\)\s*\{(.{0,20000}?)\}\s*\n', blob, re.S):
    print('FOUND:', m.group(1))
    print(m.group(2)[:3000])
PY
```

> ⚠️ **实战教训**：用 HTML 标签剥离只能得到几十行噪声，因为正文在 **JS 字符串字面量**里（含转义 `\n` `\"`）。必须从状态树 JSON 的文本节点取，再做反转义。

**6. 顺带提取表单定义**（若比赛用在线表单投稿）：

同一份状态树里通常有 `openForm()` / `FORM_OPTIONS` / `auditSubmission()` / `canSubmit()` / `renderLinkGuide()` 之类的函数。**这是表单型比赛的全部隐性约束来源**——必填星号、字符上限、格式白名单、违规词扫描范围、草稿缓存字段、提交前置条件，全在这里。

**逐项解析必填星号**（极易数错）：

```bash
python - <<'PY'
import json, re
blob = open('/tmp/janus.json', encoding='utf-8').read()
# 找到 label 与星号配对，逐项列出
for m in re.finditer(r'<label[^>]*>(.{0,120}?)</label>', blob, re.S):
    seg = m.group(1)
    txt = re.sub(r'<[^>]+>', '', seg).strip()
    required = ('*' in seg) or ('必填' in seg) or ('required' in seg.lower())
    print(('★' if required else '○'), txt[:40])
PY
```

> ⚠️ **首轮最容易错的一项**：必填项数量。**必须逐项解析星号，不能凭字段数减一**——选填项常常不是最后一项（样本 B 中第 08、09 项都选填，夹在必填项中间）。

### L4 · 渲染后 DOM

用 browser 工具渲染后取 HTML。适合正文在 DOM 里但需要 JS 执行的页面。

### L5 · 官方 PDF / 附件 / 细则弹层

活动页有「下载规则」「活动细则」按钮时优先走这条——PDF 通常比页面更完整（含时间表、奖项表、条款编号）。

### L6 · 截图 + OCR / 评论区补充 / 官方问答

规则只在海报图里时，OCR 后**逐条标为「OCR 待核」**，人工对关键数字。

### L7 · 规则不可得 → 模式切换

**见 SKILL.md 步骤 1**。要点：不猜规则；列必答项清单；每项给保守默认动作；规则确认前不做不可逆投入。

## 二、编号族纪律（六条）

### 1 · 事实与推断分族

| 族 | 含义 | 原文性 |
|---|---|:---:|
| **F-xxx** | 事实 | ✅ |
| **G-xx** | 缺口（官方未给） | ❌ |
| **M-xx** | 采集元数据 | ⚪ |
| **C-xx** | 核验结论 | 混合 |
| **I-xx** | 机制推断 | ❌ |
| **E-xx** | 勘误 | — |

**为什么分族这么细**：因为"官方没说"和"我没查到"是**两种完全不同的东西**。混在一起会导致：① 方案里出现无法追溯的空白；② 后续复核时不知道该去找什么；③ 引用者可能把缺口误读成事实。

### 2 · 事实行不写因果词

事实层只用客观描述，不写「因为/导致/所以/因此」。

**唯一例外**：规则原文本身是条件—后果条款时（「违反者取消资格」），可逐字转录——但要在文档顶部写**豁免声明**，给出可机械复验的判据（如"因果词命中集合恰为 {F-xxx, ...}，均为原文条件句转录"）。

### 3 · 口径分层标注

| 口径 | 含义 |
|---|---|
| 平台口径 | 主办方原文直述 |
| 页面结构 | 从前端代码/页面结构读到的（如表单字段定义） |
| 平台展示值 | 页面显示但口径未定义（如"海量 Token"） |
| 转录 | 由采集者转述的原文 |
| 独立核验 | 采集者亲自验证可达/存在 |

### 4 · 单源标记

**若全部规则只有一个信源**（平台自身），整包标 `status: flagged`，并在包首写明证据等级。

理由：平台规则的**页面与细则弹层一致性**经常成立（样本实测逐项比对无冲突），但**外部佐证几乎为零**——无官方 PDF 直链、无第三方转载。

### 5 · 勘误留痕

发现**原文错误**或**自身错误**都登记，不静默改。

```markdown
| E-01 | 人气加分未列 0—9 档 | 细则只给四档（10—30 起），未说明 0 时的情况 | 按推导记为"零人气档"，正文与核验报告双重标注「推导，非原文」 |
```

**自身错误的勘误同样要留**——它证明底账被复核过。样本 B 的 V 阶段留痕了 15 条自身修正（必填项数、奖项算术、资产数字、合规枚举误列等），每条都能追到具体改动。

### 6 · 复核触发条件写「载体变更」

不要写"日历到期"。规则由主办方随时可改。

**写法**：「活动页任一载体发生变更——① 细则正文改动；② 表单字段定义变化（publishVersion 递增）；③ 公告更新。任一发生即需重跑事实登记与核验。」

**配套**：给一张**可机械执行的复核触发检测表**——每个触发器配一个检测动作和当前基线。

| # | 触发器 | 检测动作 | 当前基线 |
|---|---|---|---|
| T-1 | 细则正文变更 | 重新提取 `ruleHTML()` 与底账逐条 diff | publishVersion 49；细则 146 行 |
| T-2 | 表单字段变更 | 重新解析字段与星号，与 F-xxx 逐项 diff | 13 项字段，11 项带星号 |
| T-3 | 前端常量变更 | 读压缩/上传常量与 F-xxx 比对 | 1600 / 0.82 / 520×1024 |
| T-4 | 作品墙出现作品 | 计数（当前为 0）→ 出现即说明已有投稿过审 | 计数 0 |

## 三、算术自洽性检查（必做）

规则里的数字**经常自相矛盾**，而这类矛盾正是后续争议的源头。必须逐个算一遍。

**实例**：某比赛的奖项表写「参与奖 500 名 / 综合分第 11—511 名」。四个奖项名额之和 = 1+3+6+500 = **510**，与区间上界 511 **差 1 席**。

**处置**：
1. **原文照录**（不改写原文）；
2. 单独登记一条事实记录这个算术关系；
3. 登记为缺口（官方未明确第 511 名是否得奖）；
4. 正文用**名额口径**表述（"前 510 名"），并注明区间原文；
5. 核验结论从 ✅ 改判为 ⚠️；
6. **对外文案不提具体保底名次**。

**其他必查的算术**：
- 评分维度之和（35+40+25 是否等于总分 100）；
- 奖池总额与各奖项金额之和；
- 名额数与排名区间端点；
- 加分上限与总分上限。

## 四、规则不可得时的必答项清单

即使规则拿不到，这 6 项也必须逐项给出保守默认动作：

| # | 必答项 | 保守默认动作 |
|---|---|---|
| 1 | 作品形态（封闭选项还是自选） | 按最常见的网页应用准备；同时准备源码包 |
| 2 | 资格条件（谁能参加） | 按"无门槛 + 账号正常"准备 |
| 3 | 材料清单 | 按"作品链接 + 3 张截图 + 500 字介绍 + 过程记录"准备 |
| 4 | 截止时间 | 按最早可见的时点 |
| 5 | 资格取消情形 | 按最严版本自查（含账号状态、删帖、刷赞） |
| 6 | 评审维度 | 按"作品能用 + 有差异化 + 过程可举证"三条保底 |

**并明确标注**：「以下为保守默认，非规则原文；规则确认后须重核。」
