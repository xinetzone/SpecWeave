# 组合价值评估三原则决策记录模板

> **L1方法论模式集成**：本模板应用 [combination-value-triple-test](../docs/retrospective/patterns/methodology-patterns/governance-strategy/combination-value-triple-test.md) 决策质量门禁模式
>
> **使用说明**：在决定投入资源实现任何技术/概念/产品组合前，强制按顺序回答三个问题，**任一问题答"否"即判定为伪需求**。可直接复制本模板到评审会议、技术方案文档或个人规划笔记中使用。

| **评估人** | [姓名/团队] |
| **评估场景** | ▢ 架构评审 ▢ 技术选型 ▢ 产品决策 ▢ 个人规划 ▢ 创新方案 ▢ 其他：______ |
| **决策截止时间** | [需要在何时前做出决策] |

## 🔴 第一问：真实痛点测试（Pain Point Test）

> **核心问题**：这个组合是否解决了一个真实存在的、有人愿意付费解决的痛点？

| 检查维度 | 填写内容 |
|---------|---------|
| 具体痛点描述 | [谁在什么场景下遇到了什么具体问题？越具体越好，避免"提升效率/更好体验"这类泛泛描述] |
| 目标用户/团队 | [具体是哪些人/团队遇到了这个问题？] |
| 痛点发生频率 | [每天/每周/每月遇到？影响多大？] |
| 付费/投入意愿证据 | [用户是否明确表达过愿意投入时间/金钱解决？有数据/记录支撑吗？] |

### ❌ 红灯信号（出现任一即不通过）

- [ ] "这个组合听起来很创新/很酷/很先进"
- [ ] "X和Y都是热门技术，放一起应该不错"
- [ ] "先做出来再说，总会有人用的"
- [ ] "为了XX理念/未来趋势而做，虽然现在没人用"
- [ ] "竞品做了所以我们也要做"（没有自己的痛点验证）

### ✅ 绿灯信号

- [ ] 能说出具体用户在具体场景下的具体问题
- [ ] 至少1个真实用户/团队明确表达过这个痛点
- [ ] 有明确的需求方愿意承担开发/学习/维护成本
- [ ] 能举出至少1个当前因为这个问题导致的具体损失/浪费

**第一问结论**：▢ ✅ 通过 &nbsp;&nbsp; ▢ ❌ 不通过（伪需求，终止评估）

> 💡 **如果不通过**：不要继续评估后面两问，直接判定为伪需求。回到问题本身，先找到真实用户和痛点再谈方案。

---

## 🟡 第二问：现有方案缺口测试（Gap Test）

> **核心问题**：现有更简单的方案为什么没解决好？真的需要这个新组合吗？

| 现有方案 | 能解决多少问题 | 具体缺口/不足 |
|---------|--------------|-------------|
| 方案1：[最简单的现有方案名称] | ______% | [缺口是什么？为什么解决不了？] |
| 方案2：[次简单的现有方案名称] | ______% | [缺口是什么？为什么解决不了？] |
| 方案3：[小改现有方案，不引入新组合] | ______% | [能不能通过增量改进解决？] |

### 关键思考问题

1. 有没有我没想到的更简单的替代方案？（如：客户端搜索就够的场景不需要GraphQL服务器）
2. 我是不是在追求"100%完美解决方案"而忽略了"80%够用的简单方案"？
3. 现有方案的缺口是真的无法克服，还是我不愿意用/不知道有这个方案？
4. 能不能先在现有方案基础上小改，而不是直接上全新组合？

### ❌ 红灯信号（出现任一即不通过）

- [ ] "现有方案太老了，X技术更新更现代"
- [ ] "我就是想试试Y新技术"
- [ ] 简单方案能解决80%问题，却非要用复杂方案追求100%
- [ ] 没有列出任何现有替代方案，直接认定需要新组合
- [ ] 现有方案只是"不够优雅"而非"真的解决不了"

**第二问结论**：▢ ✅ 通过 &nbsp;&nbsp; ▢ ❌ 不通过（现有方案已足够，终止评估）

> 💡 **如果不通过**：用现有更简单的方案解决问题，不要引入新组合。记住：简单方案优先——如果简单方案能解决80%的问题，就不要用复杂方案追求100%。

---

## 🟢 第三问：复杂度-价值权衡测试（Complexity-Value Test）

> **核心问题**：组合带来的价值是否显著大于增加的复杂度？
>
> ⚠️ **复杂度非线性警告**：多组件组合的复杂度是**乘法关系**而非加法关系——两个技术组合的复杂度不是1+1=2，而是接近1×1=1的量级跃升，因为你需要同时掌握两者、处理边界问题、调试跨栈bug、让团队每个人都理解整个组合。

### 价值评估（尽量量化）

| 价值类型 | 具体描述 | 预估收益（量化） |
|---------|---------|----------------|
| 节省时间 | [能节省多少时间？谁的时间？] | ______人时/周 |
| 减少错误 | [能减少多少bug/错误？] | 减少______%错误 |
| 体验提升 | [用户/开发者体验有多大提升？] | 提升______%满意度 |
| 其他价值 | [其他可量化的收益] | |
| **总价值预估** | | **______分（1-10分）** |

### 复杂度评估（列清单，不要漏项）

| 复杂度类型 | 具体描述 | 预估成本 |
|-----------|---------|---------|
| 学习曲线 | [团队需要学习几个新技术？每人需要多少小时？] | ______人时学习成本 |
| 维护成本 | [上线后每月需要多少人天维护？] | ______人天/月 |
| 新依赖 | [引入多少新依赖包/服务/基础设施？] | ______个新依赖 |
| 认知负担 | [团队理解整个组合需要多久？新人上手成本？] | ______小时培训成本 |
| 集成风险 | [两个/多个技术边界处可能出现什么类型的bug？调试难度如何？] | 风险等级：▢低 ▢中 ▢高 |
| 升级成本 | [未来升级其中一个技术时，会不会破坏整个组合？] | 升级难度：▢低 ▢中 ▢高 |
| **总复杂度预估** | | **______分（1-10分）** |

### ROI判断

- 价值得分：______ / 10
- 复杂度得分：______ / 10
- 价值/复杂度比：______ : 1
- 安全边际要求：≥3:1（价值至少是复杂度的3倍才值得做）

### ❌ 红灯信号（出现任一即不通过）

- [ ] 团队没人会其中某个核心技术，需要全员现学
- [ ] 引入的新依赖树比现有项目所有依赖加起来还大
- [ ] 需要专门写文档解释这个组合怎么用，团队其他成员看不懂
- [ ] 维护这个组合需要一个人全职，而问题每周只发生一次
- [ ] 价值主要是"简历更好看"、"技术更酷"这类虚的收益，没有实质业务价值
- [ ] 价值/复杂度比 < 2:1（没有足够安全边际）

**第三问结论**：▢ ✅ 通过 &nbsp;&nbsp; ▢ ❌ 不通过（复杂度太高，ROI不足，终止评估）

> 💡 **如果不通过**：要么缩小组合范围（先只做1-2个技术的组合），要么降低复杂度（用更简单的实现方式），要么等团队能力/工具成熟后再考虑。

---

## 🎯 最终决策

### 总体结论

- [ ] **✅ 可以做PoC**：三问全部通过，建议从最小切口开始验证
- [ ] **❌ 不做**：判定为伪需求/现有方案足够/复杂度太高，资源投入到更有价值的地方
- [ ] **⏸️ 推迟**：当前时机不成熟，等痛点更明确/团队能力就绪/生态更成熟后再评估
- [ ] **🔄 收缩范围**：原组合太大，建议缩小为______（更小的组合）后重新评估

### 决策理由

[在此填写最终决策的核心理由，3-5句话]

### 后续行动（根据结论选择）

**如果通过（做PoC）**：
- 最小切口PoC方向：[从哪个最小的点开始验证，不要一开始就做全组合]
- PoC成功标准：[用什么指标判断PoC是否验证了价值]
- PoC时间盒：[多长时间内完成PoC，超时则判定价值不足]
- PoC负责人：[谁来做]

**如果不做/推迟**：
