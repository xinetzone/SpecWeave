# 提交暂存区完整性规则（Commit Staging Integrity）

> **一句话**：暂存区是**共享可变状态**——「我核对过暂存区」不等于「提交时暂存区还是那一份」。
> 提交集必须被**点名钉死**（路径级指定），而不是交给索引快照。

---

## 一、问题：核对与提交之间存在时间窗

`git add` 是「把工作区内容写进索引」，而索引是**所有**并发写入者共用的一处状态：同一个仓库里
可能同时有另一个 IDE 窗口、另一个智能体会话、自动化脚本在往索引里写。

| 步骤 | 你以为的状态 | 真实的状态 |
|---|---|---|
| `git add A B` | 索引 = {A, B} | 索引 = {A, B} |
| 核对 `git diff --cached --stat` | 索引 = {A, B} ✅ | 索引 = {A, B} |
| （此间第三方执行 `git add X Y`） | 无从察觉 | 索引 = {A, B, X, Y} |
| `git commit -F msg` | 提交 {A, B} | **提交 {A, B, X, Y}** ❌ |

首次实测：追推子模块指针时，核对 `--cached` 只有 gitlink 一行，提交却落下 4 个文件——多出
并行另一会话暂存的 `apps/AGENTS.md` 与一个 1477 行的新应用。

### 1.1 现有守卫盘点（先看清已经有了什么）

| 层 | 现状 | 它的盲区 |
|---|---|---|
| `git-commit-utf8.py` **带文件清单** | add 前检测清单外的已暂存文件即**中止**；add 后校验暂存集必须等于指定集 | 校验在前、提交在后，且提交调用不带路径级指定——窗口内第三方写入仍会被裹入 |
| `git-commit-utf8.py` **不带文件清单** | 只做编码处理，把当前暂存区原样提交 | 守卫完全不生效，等同于裸提交 |
| `atomic-commit-cmd` 三查暂存法 | 防**工作区脏**（临时文件、无关修改被一并 `add`） | 防不住**索引被并发写入** |
| 裸 `git commit` | 无任何守卫 | 提交「此刻索引里的一切」 |

**本次事故的直接成因不是「没有守卫」，而是「没走已有的守卫」**：两次提交都手写 UTF-8 文件 +
裸 `git commit -F`，把带文件清单的工具路径整个绕开了。因此本规则的价值是**把既有守卫用起来、
并补上它残留的时间窗**，而不是另造一套。

## 二、规则（五条，强制）

### R1 首选既有工具，且必须带文件清单

```bash
# ✅ 工具自带「暂存集 == 指定集」守卫：清单外有他人暂存文件时直接中止
python .agents/scripts/git-commit-utf8.py -F .temp/msg.txt <路径…>

# ❌ 不带文件清单：工具只把当前暂存区原样提交，等同于裸提交
python .agents/scripts/git-commit-utf8.py -F .temp/msg.txt
```

### R2 直连 git 时一律路径级指定

工具不适用时（无中文、子模块 gitlink、工具不可用）直连 git，提交集仍须点名钉死：

```bash
git commit -F .temp/msg.txt -- <路径…>     # ✅ 只提交点名路径
git commit -F .temp/msg.txt                # ❌ 把「此刻索引里的一切」一并提交
```

`git commit -- <pathspec>` 的语义是「按命令行给出的路径提交」，**忽略其它路径上已暂存的内容**，
这正是把「提交集」从「索引快照」降级为「我点名的路径」的杠杆。

**边界（必须知道）**：路径级只挡「别的路径」，**不挡「同一路径内的无关改动」**。若点名的文件
自身混有不相关改动（例如它同时被别人改过），它们仍会一起进提交。此时先 `git diff <该文件>`
逐块确认，再按序取用两种手段：

1. `git add -p` 只暂存该要的块——**相邻行落在同一 hunk 里时它切不开**（表格里紧挨着的
   两行、或同一段内的相邻改动）；
2. 切不开则用**管道暂存**构造精确内容，且提交时必须改用**工作区交换法**：

```bash
# 管道暂存：绕过工作区，把精确内容直接写进索引（工作区保持原样）
blob=$(git hash-object -w --path <文件> .temp/target.md)
git update-index --cacheinfo 100644,$blob,<文件>

# 工作区交换法：路径级提交读的是工作区，必须先让它等于目标内容，提交后立刻还原
cp <文件> .temp/full.md && cp .temp/target.md <文件>
git commit -F .temp/msg.txt -- <文件>
cp .temp/full.md <文件>        # 还原：他人改动回到工作区，未暂存、不丢失
git reset -- <文件>            # 该路径的索引项归位，避免把还原内容留在索引里
```

> ❗ **路径级提交取的是工作区内容，会覆盖管道暂存构造的索引内容**（详见反模式 7）。
> 两者不可直接并用——这是继「索引被并发写入」之后，「用了路径级 ≠ 提交集已钉死」的
> 第二个盲区。

### R3 核对与提交之间不插入可改变索引的动作

核对（`git diff --cached --stat` / `git status --short`）与提交必须**紧邻**。核对之后不得再执行
可能触发第三方写入的动作（长等待、跑构建、切到别的会话干活）。**核对不是保证，只是快照。**

### R4 索引被污染时的处置：软回退 + 摘出，绝不丢弃他人工作

```bash
git reset --soft HEAD~1                     # 只撤提交，工作区与索引原样保留
git restore --staged <他人的路径…>           # 把非本方文件摘回工作区（内容仍在，对方可重新 add）
git commit -F .temp/msg.txt -- <本方路径…>    # 路径级重提交
```

禁止用 `git reset --hard` / `git checkout -- <路径>` / `git clean -fd` 去「清干净」——那是把并发
会话的在途工作**销毁**掉，比误提交严重得多。

### R5 工具路径同样不可省「路径级点名」

工具的守卫在**校验那一刻**成立，而提交发生在之后——窗口内第三方写入仍会被裹入。因此在索引
可能被并发写入的仓库里，R2 的路径级点名在工具路径上同样要落实（工具侧的根治见§五「后续跟踪」）。

## 三、执行清单（提交前逐项打勾）

- [ ] 走了带文件清单的提交入口（`git-commit-utf8.py <路径…>`），或直连 git 时用了 `-- <路径…>`
- [ ] 点名路径逐项对应本次单一职责，没有顺带
- [ ] 点名路径**自身**没有混入不相关改动（`git diff <路径>` 过一遍）
- [ ] 核对暂存区之后未插入其它动作，直接提交
- [ ] 提交后 `git show --stat --oneline HEAD` 与清单逐项核对通过
- [ ] 索引里存在他人暂存文件时：确认归属（摘出需对方知情），**不得 `--no-verify` 绕过钩子**

## 四、反模式

### 反模式 1：「有工具不用，手写 msg 文件 + 裸 `git commit`」

本次事故原形。既有工具带文件清单时本可在 add 前就中止，绕开它等于把守卫关掉。

### 反模式 2：「带工具但省略文件清单」

不带清单时工具只做编码处理，守卫不生效——「用了工具」不等于「走了守卫」。

### 反模式 3：「核对过就放心裸提交」

核对只证明「那一刻」干净；核对与提交之间的时间窗才是事故现场。纠正：一律路径级。

### 反模式 4：「把钩子失败当成该绕过」

路径级提交下，pre-commit 钩子仍会检查**整个索引**，可能因他人暂存的文件（密文、格式违规）
而失败。正确处置是先弄清那些文件该不该在索引里、与文件主人确认后摘出；`--no-verify` 是把
风险留给下游，属禁区。

### 反模式 5：「回退时用 `reset --hard` 清场」

`reset --hard` 连工作区一起回滚，会把并发会话尚未提交的在途工作销毁。用 `--soft` + `restore --staged`。

### 反模式 6：「一枚提交顺带把指针、索引、清单都带上」

把「子模块指针追推 + 索引登记 + 顺手改动」塞进一枚提交即违反单一职责；路径级提交恰好能把它们拆开。

### 反模式 7：「管道暂存 + 路径级提交」直接并用

以为先 `hash-object` + `update-index` 把精确内容写进索引，再用 `git commit -- <路径>` 提交，
就能只提交那一部分。实测结果相反：路径级提交取的是**工作区**内容，索引里精心构造的
内容被整个忽略，文件里的他人改动照旧进了提交（`8+/2-` 而非预期的 `2+/2-`）。路径级挡的是
**别的路径**，不是本路径的索引快照——两者必须经 R2 的工作区交换法衔接。

并发下还有第三种失败：``reset --soft HEAD~1`` 与提交之间若落入他人提交，`HEAD~1` 指向的
就不是你以为的那枚，交换法会退化成 no-op，甚至撤掉的是他人的提交。故并发仓库里，**改写
历史的动作一律不做**——留下一枚名不副实的提交，代价远小于销毁他人在途工作（R4）。

## 五、与现有规范的关系

- [git-commit-utf8.py](../scripts/git-commit-utf8.py)：**本规则的守卫主体已经存在**——带文件清单时它校验暂存集一致性，不一致即中止。本规则把它从「可选的编码工具」升格为「提交集守卫的默认入口」。
- [atomic-commit-cmd SKILL.md](../skills/atomic-commit-cmd/SKILL.md)：其「三查暂存法」防工作区脏，本规则补其未覆盖的「索引被并发写入」；Skill 执行步骤与安全检查清单已同步指向本规则。
- [fix-prevent-close-loop.md](fix-prevent-close-loop.md)：本规则即该 SOP「预防」阶段的产物形态（把一次实测事故变成可执行动作）。
- [global-core-rules.md](../global-core-rules.md)：已作为全局核心规则之一登记。
- [development-standards.md](../../docs/tech/references/development-standards.md)：提交信息规范（Conventional Commits、Windows 中文 UTF-8）不变，本规则只约束**提交集的界定方式**。
- **后续跟踪（尚未立项）**：为 `git-commit-utf8.py` 的提交调用补 `-- <files>`，把守卫从「校验时」推进到「落地时」；在完成前，并发工作区里以 R2 兜底。
