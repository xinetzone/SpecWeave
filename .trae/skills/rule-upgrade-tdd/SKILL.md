# rule-upgrade-tdd

检查规则升级（warn→block、白名单增删、新形态覆盖）的可复用工作流。沉淀自 session `sc-20261018-sensitive-rule-escalation`：敏感信息检查个人路径 MEDIUM→HIGH 升级中，连带甄别出 4 个被误诊为"Windows 平台问题"的存量红灯，根因是政策文档把教材代称纳入白名单后测试夹具未同步。

**分工边界**：

- 规则实现位于 `.agents/scripts/lib/checks/`，入口在 `.agents/scripts/check-*.py`，pre-commit 钩子在 `.agents/scripts/hooks/pre_commit.py`；政策文档通常在 `docs/knowledge/best-practices/`。
- 本技能只管**既有规则的加严/扩展**；从零新建检查工具、修单点 bug（平凡修复走修复闭环即可）不适用。
- 提交统一走 `python .agents/scripts/git-commit-utf8.py -m ... <显式文件清单>`，禁止 `git add .`；工作区有其他会话在途文件时只提交本任务清单。

## 0. 触发与不触发

**使用**：① "把某类告警升级为阻断/HIGH"；② "扩充白名单/占位符名单"；③ "正则覆盖新形态"（如 WSL 路径）；④ 规则改动导致多个既有测试变红，需要判定是回归还是存量。

**不使用**：① 新建全新检查脚本；② 单点 typo/平凡修复；③ 规则不变、只修文档措辞；④ 用户明确要求只快速热修且不要流程。

## 1. 六阶段流程

### 1.1 基线取证（改代码之前）

1. 跑当前目标测试文件记录红/绿基线；全量门禁扫描记录存量命中数（JSON 输出按 type 归类）。
2. 明确退出码语义与调用链：CLI（`check-*.py --json/--only-severity`）与 pre-commit 钩子可能走**不同代码路径**（钩子常直调库函数逐文件扫描，CLI 可能 rglob 目录）——升级阻断行为必须以**钩子实际调用路径**为准验证，不能只验 CLI。
3. 找政策源：规则的"应该怎样"可能写在三处——实现常量/正则、`docs/` 下规范文档、测试夹具断言。三处冲突时进入 1.3 仲裁，不得凭直觉改其中一处。

### 1.2 红绿先行（TDD）

1. 先加/改测试表达新契约：升级区命中 HIGH、豁免区（如 `playground/`、`vendor/`）不升级、构建产物目录（如 `_build/`）不扫描、行尾逃生标记（`# nosec`）仍生效。
2. 确认新测试在旧实现下**确实变红**，再改实现。
3. 白名单类改动必须同时准备两类夹具并断言：**真实名应检出**、**占位名应放行**。"真实名"夹具使用语义无争议的 `realuser`，不要使用在政策上可能被定义为占位符的名字（教材代称、john/jane 等）。

### 1.3 存量红灯甄别（出现既有测试失败时强制执行）

凡改动后出现"自己没动过的测试"失败，禁止直接改测试迎合，也禁止接受"环境问题"解释，按三步定性：

1. **基线对照**：仅 stash 本次代码与测试改动，在 HEAD 上复跑失败用例：
   ```powershell
   git stash push -- <规则实现文件> <测试文件>
   python -m pytest <失败用例节点> -q
   git stash pop
   ```
   HEAD 上同样失败 = 存量红灯（非本次回归）；HEAD 通过 = 本次回归，必须修实现。
2. **时间线仲裁**：测试与政策矛盾时，用 `git log -S "<冲突字面量>" --oneline -- <文件>` 查各自引入提交，晚出的、且有规范文档支撑的一方为现行政策。
3. **按政策统一三方**：若政策正确（如教材代称确属占位符），改测试夹具并在规范文档补记；若政策是误加（污染检测能力），改实现并同步修正把该问题误诊存档的文档。无论选哪边，都要消除双平台/双入口的不对称。

### 1.4 存量命中清场（加严阻断前的必要条件）

规则加严前对全仓目标目录实扫，每个升级后会新增的命中必须三选一处置，不能带着存量红灯合入：

| 命中性质 | 处置 |
|---|---|
| 真实信息泄露 | 脱敏为标准占位符（Windows 用 `%USERPROFILE%`/`$env:USERPROFILE`，Unix 用 `~/`/`$HOME`，文档叙述用 `<用户名>`） |
| 合理的系统性账户名 | 扩充白名单并在规范文档登记（容器账户、CI 账户等，需给出处依据） |
| 非本任务范围的既有问题 | 不改，但必须在汇报中显式登记（文件:行 + 类型 + 为何不动） |

注意代码块语义：PowerShell 块用 `$env:USERPROFILE`（`%USERPROFILE%` 不展开），bash 块用 `$HOME`；占位替换后人工通读一遍语句是否仍成立。

### 1.5 四象限合成验证

在临时文件中构造最小样例直调库函数验证（CLI 单文件路径可能不扫描，见 1.1.2），验后立即删除：

1. 升级区内真实命中 → 新级别（HIGH、退出码 1）；
2. 豁免区内同样命中 → 维持原级别（MEDIUM、不阻断）；
3. 逃生口标记 → 零发现；
4. 白名单占位名（含新增形态如 `/mnt/c/Users/...`）→ 零发现。

再对真实目标目录跑全量门禁：新级别的非本任务命中数应为 0（或仅剩 1.4 已登记项）。

### 1.6 两个原子提交（顺序不可颠倒）

1. **内容提交在前**：`docs(scope): 脱敏/修复存量命中`——只含被清场的内容文件，保证该提交自身能过新钩子；
2. **规则提交在后**：`feat(scripts): <规则升级> [prevent: test-case]`——实现 + 测试 + 规范文档同步 + 被更正的存档文档。
3. 提交后 `git status --short` 核对：只剩其他会话在途文件；合成临时文件零残留。

## 2. Windows / pwsh7+ 操作备忘

- 无 bash heredoc：给 python 传多行脚本用 here-string 管道：`@' ... '@ | python -`。
- JSON 归类：`python check-x.py --json | Out-String | ConvertFrom-Json`，退出码非 0 时先接输出再判断，避免命令中断丢数据。
- stash 必须带显式文件路径，禁止裸 `git stash`（会卷走其他会话在途文件）。
- 全量 pytest 耗时长（约 2 分钟），失败清单用 `Select-String -Pattern '^FAILED'` 提取节点，再按 1.3.1 批量对照。

## 3. 反模式

1. **看到既有红灯就改测试**：不查基线、不查政策，把测试断言改成迁就实现，真实检测能力被悄悄删掉。
2. **把失败归因平台/环境**：以"Windows 预期失败、加 skipif 吧"结案，不复核断言；跨平台不对称问题被永久掩盖。
3. **白名单单点扩充**：只改一个平台的名单或只改常量不改规范文档，制造下一次契约漂移。
4. **带存量命中合入阻断规则**：队友下次提交任意文件即被钩子拦截，规则本身会被视为噪音而被 `SKIP` 绕过。
5. **只验 CLI 不验钩子**：CLI 对单文件路径 rglob 扫空时显示 PASS，与钩子逐文件扫描行为不一致，造成"本地通过提交被拦"。
6. **规则与内容混在一个提交**：无法分别回滚，且内容提交单独过不了新门禁的因果关系被抹掉。
7. **占位替换破坏代码语义**：PowerShell 里写 `%USERPROFILE%`、bash 里写 `$env:X`，读者复制即错。
8. **顺手修无关存量**：把非本任务的红灯一起改了，扩大爆炸半径；正确做法是登记并另开治理事项。

## 4. 完工检验清单

- [ ] 新测试在旧实现下变红、新实现下全绿；真实名/占位名双向夹具齐全
- [ ] 每个非预期失败已用 stash 基线对照定性（回归已修 / 存量已登记）
- [ ] 政策、实现、测试三方一致；双平台/双入口不对称已消除
- [ ] 目标目录全量扫描：新增级别命中为 0（或仅剩已登记的既有项）
- [ ] 四象限合成验证通过，临时文件已删除
- [ ] 规范文档（政策源）已同步变更说明/版本与日期
- [ ] 内容、规则两个原子提交顺序正确，均走 git-commit-utf8.py 显式文件清单
- [ ] `git status` 仅剩其他会话在途文件；汇报中列出未处置的既有问题及建议
