# wording-revision-sync

用户对知识包中**已落盘的结论**提出措辞修正（换口径、去限定、改倾向、改数字体系）时，保证同一事实在包内所有入口表述一致，同时完整保留审查轨迹。沉淀自 session `sc-20260930-openkylin-desktop-wsl` 连续四轮用户驱动修正（磁盘规划分层化、选型倾向显性化、候选区间去点估）的同构流程。

**分工边界**：

- **knowledge-pack-builder** 负责从零建成知识包；**seven-concepts-cmd** 负责方法论编排；**本技能只管一件事**——知识包已交付后，用户点名修改某个已发布结论时的全量同步与轨迹追加。
- 本技能**不产生新事实、不做新调研**；若修正需要新证据，先回到 R 阶段取证，本技能不适用。
- 本技能**不提交 git**；收尾后由用户决定是否转 atomic-commit-cmd。

## 0. 触发与边界

**使用**：用户明确指向知识包内某个已存在结论，要求改措辞，典型句式为"按方案 N 执行""去掉 X 的限定""把 A 改成 B""增加/弱化某倾向"。

**不使用**：① 知识包尚在 R/I/E 阶段（直接走原流程）；② 修正依赖新事实或新实测（先取证）；③ 修改代码或脚本逻辑；④ 纯问答与概念解释；⑤ 用户只让改某一个文件且明确不要扩散（遵从用户，按普通 Edit 处理，但应提示不一致风险）。

## 1. 第一铁律：断言可改，轨迹不改

知识包内每个结论以两种形态存在，修正时待遇完全不同：

| 形态 | 例子 | 修正方式 |
|---|---|---|
| **断言文本** | 正文结论、决策表单元格、概念页引用块、F 编号事实表、范围声明、局限声明、洞察陈述 | 全部改为新口径 |
| **审计轨迹** | V 审查表历史行、CMD-LOG 代码块、已结项台账 | **逐字保留，只追加**；旧口径在新增行中作为被引述对象出现是允许的 |

- F 编号属于断言，措辞要改；编号本身**不回收、不跳号、不复用**。
- 绝不"顺手美化"历史审查行——改写轨迹等于销毁审计证据。

## 2. 执行步骤

### 2.1 冻结修正范围

1. 用户若以"方案 N"形式授权，**只执行被批准的方案**；同批提出但未点名的方案一律不动，并在收尾时声明"方案 X/Y 未改动"。
2. 用一句话写出判据：**旧口径 → 新口径**（例如"点估 16.1 GiB 最可能 → 候选区间不给点估"），后续每个表述点对照此句裁定，不靠临场发挥。

### 2.2 表述点机械定位（禁止凭记忆）

对旧口径做多形态 Grep，至少覆盖三类字面量：

- **精确数字及其排版变体**：`45 GiB`、`≥45`、`45～50`；
- **关键短语**：`最可能`、`推断中值`、`保守预留`、`先评估`；
- **事实编号**：涉及的 F-xxx 编号。

七概念知识包的**必查位置清单**（每轮逐项过）：

1. `references/` 主文档——事实表、各分析小节、决策表、操作清单、I 阶段洞察陈述、局限声明；
2. `concepts/` 概念页——选型表单元格、章末引用块；
3. `index.md`——F 编号事实表、洞察追加指引、质量门表、局限声明、CMD-LOG 代码块；
4. 关联实操指南——文首"范围声明"与指向主文档的交叉引用句；
5. 姊妹文档中引用同一数字/同一结论的段落（用数字形态 Grep 兜底）。

### 2.3 编辑前重读

会话可能经历过上下文压缩，工具回显中的文件内容可能过期。**每个目标行先 Read 取当前原文，再 Edit**，old_string 必须与磁盘现状逐字一致。

### 2.4 按文体同步改写

同一新口径在不同位置用该文体的自然表述，**不是同一句话复制四处**：

- 表格单元格：最短口径；
- 引用块/正文：完整因果与限定；
- F 事实表：客观陈述 + 证据强度标注（如【实测】【推断】【远程核验】）；
- 范围声明：一句带过 + 指向主文档。

两类连带改动最易遗漏：

- **数字体系变更**：源数字一改，所有派生数字同步改（tar → VHD 系数 → 峰值 → 建议预留线），并在矩阵表注明列含义变化；
- **证据强度变更**（如点估降级为区间）：连带删除一切依赖旧强度的措辞——"推荐线覆盖最可能值"要改成"覆盖 k≤N"这类覆盖口径，表头中的"外推/中值"改为"参考列/方向性上限"等中性词。

### 2.5 追加轨迹（两处，缺一不可）

1. **主文档 V 审查表**追加一行：`| ⚪ 第 N 轮修正（用户驱动，YYYY-MM-DD） | 旧措辞的问题（证据强度/口径/倾向性缺陷） | 处理（列出改动的节与同步的文件） |`；并更新表后 V 门结论句为"另完成 N 轮用户驱动修正——二轮…、三轮…（见末 N 行）"。轮次 N 读表现有最大轮次 +1。
2. **index.md 的 CMD-LOG 代码块**追加一行：
   `[CMD-LOG] | level=INFO | cmd=seven-concepts | step=V<N+9> | event=REVISION_USER_DRIVEN | session=<原session> | msg=<一句话修正内容> | ctx={"scope":"<kebab-scope>","files":<文件数>}`
   session 沿用被修正知识包的原 session 号，不新开 session。

### 2.6 门禁、复扫与汇报

1. 重跑链接门禁：`python .agents/scripts/check-links.py --path <知识包目录>`（路径以实际知识包根为准）。
2. 用 2.2 的多形态模式复扫旧口径。每个残留命中必须能归入两类之一，否则补改：
   - **审计轨迹引用**（新增 V 行/CMD-LOG 中引述旧措辞）——允许；
   - **无关同形词**（如别的结论里"内存为最可能解释"）——允许。
3. 汇报内容：改动文件清单、每处前/后口径要点、门禁结果、残留命中的归类说明、**未获批准的方案零改动声明**。
4. 不执行 git commit；用户要求提交时转 atomic-commit-cmd，知识包与其模式库按既有约定拆原子提交。

## 3. 反模式

1. **只改主文档**：漏掉概念页选型表、index 的 F 事实表、实操指南范围声明——读者在不同入口读到互相矛盾的口径。
2. **改写历史**：重写既有 V 审查行或旧 CMD-LOG，销毁"结论如何演化"的审计轨迹。
3. **越权扩散**：用户只批准方案 1，顺手把方案 2/3 也改了。
4. **凭记忆定位**：跳过 Grep/Read，靠会话印象找表述点；压缩后必然漏改或误改。
5. **强度不一致**：数字已改成区间，正文却保留"最可能/中值/推荐押注"等概率措辞。
6. **只派生不溯源**：改了建议线数字，没改上游矩阵与候选表，三层数字互相打架。
7. **虚假完成**：汇报"已全部同步"但未复扫旧口径字面量、未重跑链接门禁。
8. **自行提交**：未经用户明确批准执行 git commit。

## 4. 完工检验清单

- [ ] 旧口径多形态 Grep 的每个命中已归类（断言改写／轨迹引述／无关同形词）
- [ ] 新口径在必查位置清单的全部断言点一致，派生数字与证据强度措辞同步
- [ ] V 审查表追加新行，历史行逐字未动；V 门结论句已更新轮次
- [ ] index.md CMD-LOG 追加 REVISION_USER_DRIVEN 行，session 号沿用原包
- [ ] `check-links.py` 对知识包目录通过
- [ ] 未获批准的方案零改动，并已在汇报中声明
- [ ] 未执行任何 git 提交
