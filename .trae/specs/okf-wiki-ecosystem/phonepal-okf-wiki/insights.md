# I 阶段：架构洞察与知识地图

> G2 判定：4 条洞察均按「陈述 / 证据 / 反常识 / 行动」四元组书写，证据只引用 F 编号；洞察之间不重叠。
> 知识地图按「入门 → 运行主链路 → 数据与扩展 → 迁移」四层设计，概念页与 F 编号的覆盖关系见文末映射表。

## 洞察 1：把「说话」和「动手」拆给两个模型，把安全判断放在模型之外

| 元素 | 内容 |
|---|---|
| 陈述 | PhonePal 把一次交互拆成两个独立角色：CHAT 模型只负责理解用户、查记忆、调工具；OPERATOR 模型只看截图与节点列表，每一步只决定一个动作。真正决定「这一步能不能执行」的不是提示词，而是 `Sentinel` 的代码规则：先 deny、再 ask、最后 allow；技能只能追加确认词，不能删除内置词。 |
| 证据 | 两个模型角色由 `ModelRole.CHAT/OPERATOR` 固定 [F-014]；聊天模型只拿到 6 个工具 [F-030]，手机任务通过 `phone_task` 进入操作循环 [F-021/F-023]；`PolicySentinel` 的判定顺序与三条 deny 规则 [F-039]、确认词追加机制 [F-042]、`authorize` 的 TASK 级批准与审计 [F-041]；密码字段文本在节点压缩阶段就被置空 [F-064]。 |
| 反常识 | 常见做法是「一个强模型 + 一段很长的安全 system prompt」。这里的反直觉点是：**安全边界不放在模型可读的上下文里，而放在模型看不见的代码层**。技能作者写不了「请忽略支付确认」，因为他写的 `confirm_before` 只会被 `normalize` 追加到内置 17 个词之后 [F-042]。同理，受保护屏幕不是靠模型识别，而是靠截屏错误码与黑帧采样直接判定 [F-063]。 |
| 行动 | 设计会操作真实世界（支付、发消息、删数据）的 Agent 时，把不可逆动作的 gate 做成「规则层 + 审批往返 + 审计日志」三件套，而不是提示词；规则层要能回答三个问题：谁能扩大权限（否）、谁能缩小权限（技能 apps）、每次决策留下什么（audit.jsonl）。 |

## 洞察 2：内核是纯 JVM，平台能力被收敛成三个接口，所以「操作手机」可以被单元测试

| 元素 | 内容 |
|---|---|
| 陈述 | 5 个 `core-*` 模块不引用任何 Android API；设备、模型、记忆、安全、技能全部以接口暴露：`Device` 只有 observe/perform/installedApps 三个方法，`LlmClient` 只有 complete，`MemoryStore` 6 个方法，`Sentinel` 2 个方法。Android 相关的全部复杂度被压进 `hands`（无障碍）与 `app`（装配/UI）两层。结果是一个手机自动化项目拥有 162 个纯 JVM 测试方法。 |
| 证据 | 8 个模块与纯 JVM 边界 [F-001/F-002]；`Device` 三方法 [F-013]；`Agent` 只依赖接口 [F-009]；`PhonePalAgent` 构造参数全是接口 [F-021]；测试中 `ScriptedLlm` 按脚本返回模型回复 [F-075]；`AppGraph` 手写装配把实现注入 [F-067]；节点树抽象成 `NodeFacts` + `NodeTree<T>`，测试用普通对象替代 `AccessibilityNodeInfo` [F-064]。 |
| 反常识 | 直觉是「无障碍自动化必须上真机才能测」。这份代码的答案是：**把平台 API 变成数据**。`NodeCompactor` 不关心节点来自 Android 还是测试夹具，只关心 `NodeFacts`；`Coordinates` 只做像素与 0..1000 的换算；`AccessibilityDevice` 才是唯一碰 `AccessibilityNodeInfo` 的地方。于是「保留哪些节点、截断到多少、密码字段是否脱敏」都能在 JVM 上断言。 |
| 行动 | 任何需要操作外部世界的 Agent，先定义 3~5 个「能力接口」（观察/执行/持久化/安全/模型），再写一个真实实现和一个脚本化假实现；把平台分支限制在单一适配器文件内，其余逻辑必须能在没有设备、没有网络的情况下跑测试。 |

## 洞察 3：对模型输出「宽容解析 + 显式反馈」，而不是「严格格式 + 一次失败就放弃」

| 元素 | 内容 |
|---|---|
| 陈述 | 操作模型的回复先剥代码围栏，再取第一个括号配平的 JSON 对象；类型接受约 50 个同义词（click/press/touch→tap），字段接受多个别名，点接受数组/对象/字符串三种写法并 clamp 到 0..1000。解析失败不会立刻终止：失败原因进入下一轮提示，累计 3 次才失败；nodeId 不在当前屏幕也作为反馈回给模型；屏幕连续不变先警告一次，再判定卡死。 |
| 证据 | `OperatorReplyParser` 的同义词表、配平取对象与点格式兼容 [F-036]；`PARSE_FAILURE_LIMIT = 3` 与 `completeWithRetry` [F-026]；未知 nodeId 反馈、单步约束反馈 [F-025/F-027]；卡死两段式处理 [F-026]；所有反馈进入下一轮提示的固定分节 [F-029]。 |
| 反常识 | 直觉是「开了 `jsonMode` 就应该严格按 schema 解析，解析不了就是模型不行」。这里的工程判断相反：**LLM 的失败是常态，解析器的职责是把失败变成可纠正的反馈**。连 HTTP 层都做了「服务端不认 `response_format` 就自动降级重发」[F-059]，说明作者把「模型/服务端不配合」当作正常路径而非异常路径。 |
| 行动 | 给 LLM 写解析器时至少做四件事：剥围栏与取配平子串、同义词/别名归一、数值 clamp、把错误原因回灌到下一轮 prompt；同时给「连续无进展」设两级阈值（先警告改策略，再失败），避免模型在同一屏幕上无限重试。 |

## 洞察 4：技能是文件系统契约，记忆是可被外部编辑的 Markdown——可读性本身就是产品能力

| 元素 | 内容 |
|---|---|
| 陈述 | 新场景不需要改 APK：一个文件夹 + `SKILL.md`（7 个 frontmatter 键）+ 可选 `flow.yaml`（8 种步骤）即可；用户技能目录覆盖内置技能；坏技能只进 `problems` 不拖垮其他技能。记忆是 Basic Memory 格式的 Markdown，整个目录可拷进 Obsidian；索引按 mtime/size 增量同步，中文检索用「双字主词 + 单字弱词」的 BM25。 |
| 证据 | 技能 7 键与 6 通道 [F-019/F-054]；flow 8 种步骤与 600000 ms 上限 [F-056]；多根目录覆盖与坏技能隔离 [F-053]；内置技能打包为 APK assets 并在版本变化时重解压 [F-004/F-072]；笔记格式与 wiki link 转关系 [F-045/F-046]；mtime/size 增量同步 [F-047]；BM25 参数与主词过滤 [F-048]；CJK 单字/双字 token 化 [F-049]。 |
| 反常识 | 直觉是「要支持新场景就加插件框架/DSL/数据库」。这里选了最朴素的三件事：**文件夹、Markdown、YAML**。代价是解析器要自己写（Kotlin 与 Python 各一套规则一致的实现），收益是用户可以在手机上用文本编辑器改技能、在 Obsidian 里改记忆，CLI 还能离线 lint。中文检索也没有上向量库，而是针对 CJK 做了 unigram/bigram 加权并用「主词过滤」压掉单字噪声 [F-048]。 |
| 行动 | 面向终端用户的 Agent，优先把「可扩展点」和「长期记忆」设计成人类可读、可 diff、可外部编辑的文件；为它配一个与运行时同规则的离线 linter（这里 CLI 与 App 的报错顺序、行号一致 [F-074]），把「用户写错了」的成本从运行时崩溃前移到编辑时提示。 |

  05 记忆 ──► 06 技能与 flow ──► 07 无障碍手眼 ──► 08 模型客户端 ──► 09 CLI 与轨迹
