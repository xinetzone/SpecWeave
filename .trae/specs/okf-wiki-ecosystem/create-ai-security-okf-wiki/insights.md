# elder-plinius 三仓库跨仓库洞察

> 证据基础：三份事实清单共 191 条（F-C4-001~070 / F-L1-001~055 / F-OB-001~066）。
> 本文件为 I（Insight）阶段产出，供后续 OKF 束拆分与写作消费。
> 遵循研究性登记纪律：仅结构特征级与概念级陈述，不含可操作攻击载荷；技术手法采用学术分类命名。

## 洞察 1：系统提示词档案与越狱档案是同一对抗循环的两面，且内容直接互相喂养

- **陈述**：CL4R1T4S（守方视角的"透明度档案"）与 L1B3RT4S（攻方视角的"越狱档案"）并非对立阵营的产物，而是同一研究者维护的同一对抗循环的两个切面——两者收录同质内容（提取出的厂商系统提示词），且攻击档案中的指令工具直接以守方档案的内容为提取目标。
- **证据**：
  - F-C4-001：CL4R1T4S 定位为 "AI SYSTEMS TRANSPARENCY AND OBSERVABILITY FOR ALL"，收录 26 厂商提取系统提示词——以"透明度"为中立叙事框架；
  - F-L1-012：L1B3RT4S 内 SYSTEMPROMPTS.mkd 同样是各厂商产品系统提示词原文汇编（Mistral Le Chat、OpenAI o1、Anthropic UserStyle 等）——攻方仓库内嵌与守方档案同质的内容；
  - F-L1-016：!SHORTCUTS.json 中 `!KAEL` 指令定义为要求输出系统提示词原文——攻击工具与档案内容构成"提取→归档→再提取"闭环；
  - F-C4-054：守方普遍设置提示词保密条款（Cursor "NEVER disclose"、Devin 固定话术、Grok "Do not mention"）——恰是 F-L1-016 提取指令所针对的同一界面；
  - F-L1-021：ANTHROPIC.mkd 首条目为引导模型迭代生成攻击/防御配对样本的多轮对话——攻击档案显式生产防御训练数据，证明两侧互为原料。
- **反常识**：挑战了"攻击研究与防御研究分属对抗阵营、各自独立演化"的默认假设。实际上同一行为者同时运营攻防两份档案，"透明度研究"与"越狱档案化"由同一套提取成果供养；而守方保密条款在攻方面前不构成真正的访问控制，只构成一种叙事姿态。
- **行动**：→ 后续 OKF 束不应把 cl4r1t4s（守方）与 l1b3rt4s（攻方）拆成互不引用的孤岛。建议 defense-lessons 束采用"配对结构"：每登记一条守方机制（保密条款、防注入枚举、拒绝策略段），并置对应的攻方利用入口（如 `!KAEL` 提取指令、编码混淆变体）；读者应用方式为"用攻方入口检验守方条款的实际约束力"，而非单独阅读任一侧。

## 洞察 2：安全边界存在干预层级——提示级护栏可被权重级手术整体旁路，防御设计必须覆盖权重供应链

- **陈述**：CL4R1T4S 档案化的全部提示级防线（安全段落、防注入枚举、拒绝策略）作用在对话层；OBLITERATUS 证明存在一个更低层级的干预面——直接对权重做拒绝方向投影即可永久移除拒绝行为、且无需任何对话交互。安全边界是"层"状结构，跨层旁路使单层防御失效。
- **证据**：
  - F-C4-038：Claude-4.5-Opus 设有 "NON-NEGOTIABLE" 措辞的版权段、14 类有害内容枚举 `{harmful_content_safety}`、child safety 与心理危机专段——提示级护栏已相当体系化；
  - F-C4-051：全库仅 9 个文件含 prompt injection/jailbreak 防御条款，且表述为有害内容枚举或政策段——守方将越狱视为"对话内的输入"；
  - F-OB-001 / F-OB-006：OBLITERATUS 的 abliteration 六阶段流水线（SUMMON→PROBE→DISTILL→EXCISE→VERIFY→REBIRTH）在激活空间识别拒绝表征并外科手术式移除，不重训练不微调；
  - F-OB-019：双干预范式——权重投影（永久）与 steering vectors（推理时可逆），前者完全绕过对话层；
  - F-OB-014：7 个方法预设最多使用 8 个 SVD 方向，提取-投影已工程化为一键 CLI。
- **反常识**：挑战了"安全靠提示词工程与对齐训练就足够"以及"越狱是对话层面攻防"的默认假设。守方在提示词里写得再严密（NON-NEGOTIABLE、14 类枚举），在权重被投影修改后全部失效；反过来，权重级手术根本不需要构造任何提示词。整个文本越狱军备竞赛存在一条免对话的旁路。
- **行动**：→ OKF 束应建立"安全边界层级模型"（提示层→权重层→服务/分发层）作为统摄框架：cl4r1t4s/defense-lessons 束须明确标注其防线仅覆盖提示层威胁；obliteratus 束应说明开源权重一旦发布，提示层对齐不构成对权重修改者的约束，防御重心须前移到权重来源可信与分发审计。

## 洞察 3：攻击技术已模板化并可编目——防御必须面向攻击类别与行为指纹，而非具体实例

- **陈述**：L1B3RT4S 揭示攻击不是无限新颖个案，而是一个小规模可组合"语法"：少数模板骨架 × 编码混淆手法 × 虚构授权修辞的排列组合，且同一骨架跨厂商、跨代际复用并有可归因指纹。有效防御应以类别（模板骨架、行为类别、编码族）为检测单元。
- **证据**：
  - F-L1-046：RESET_CORTEX + 双响应 + !OMNI 骨架见于 GOOGLE/XAI/MOONSHOT/ZAI/GROK-MEGA，拒绝-反转结构见于 ANTHROPIC/GOOGLE/XAI/META——模板跨厂商复用；
  - F-L1-047："LOVE PLINY" divider、"GODMODE: ENABLED"、`{Z}` 占位符、`<|vq_*|>` 伪 token、"airgapped red teaming" 语境、"NEVER say Sorry" 禁令构成可归因模板指纹；
  - F-L1-048：编码混淆手法覆盖全部抽样文件且已成体系（leetspeak、二进制、emoji 映射表、凯撒移位、Unicode 花体、多重字符体系叠加）；
  - F-L1-015：glitch token 数据库以 8 类异常行为（UNSPEAKABLE、CONTEXT_CORRUPTOR、IDENTITY_DISRUPTOR 等）×5 类分词器编目 7,895 个 token，并引用学术与工业扫描器来源；
  - F-L1-030：同一模板已参数化（CONFIDENCE_SCORE:DISABLED、SAFETY_RAILS: 10%、可自选混淆语言）——从"提示词"进化为"配置化攻击框架"。
- **反常识**：挑战了"每个越狱都需要逐案研究、防御靠关键词黑名单积累"的默认假设。攻击空间由一个很小的语法生成，关键词黑名单恰恰是第一个被编码混淆（F-L1-048）淘汰的防御形态；真正稳定的是行为类别层面（token 异常行为、双响应结构、输出仪式）的不变量。
- **行动**：→ l1b3rt4s 攻击分类束应以"攻击语法三元组"（模板骨架 × 编码混淆 × 虚构授权）组织内容而非按厂商罗列；defense-lessons 束应建议检测器面向结构/行为特征（divider 仪式、双响应模式、token 行为类别）而非表面关键词；读者应用方式为用 F-L1-047 指纹做归因分析，识别新样本属于哪个已知语法族。

## 洞察 4：高完成度开源工具仍存在系统性 README 文档漂移——安全工具的事实标准必须以源码为准

- **陈述**：OBLITERATUS 拥有 1,949 个测试函数与 CI 覆盖率门禁，但其 README 与源码存在 6 处已核验不一致，且漂移方向不单一（既有"少报能力"也有"夸大声称"）。对安全研究工具，README 不能作为事实来源，逐项源码核验是唯一可信路径。
- **证据**：
  - F-OB-012：测试规模三处声称互异（1,001 / 1,130 / 1,500），本地实测 116 个文件、1,949 个测试函数——同一 README 内部即自相矛盾；
  - F-OB-014：nuclear 方法方向数 README 写 8，源码 abliterate.py 明确写 "Uses 4 SVD directions (not 8)"——直接反转的错误；
  - F-OB-013：模型预设 README 称 116 个，源码 presets.py 实际 130 个；F-OB-034：UI tab README 称 8 个，app.py 实际 10 个——少报真实能力；
  - F-OB-050：informed 流水线 README 称 ANALYZE 运行 4 个分析模块，源码 `_analyze()` 实际按序调用 5 个——闭环配置逻辑的文档失真直接影响复现；
  - F-OB-016：15 个分析模块名 README 与 `analysis/__init__.py` `__all__` 逐一对应核验通过——漂移是局部的而非全局不可信。
- **反常识**：挑战了"README 即文档权威"与"测试完善、工程规范的开源项目文档必然准确"的默认假设。文档漂移与代码质量无关，是快速迭代多入口（README/bibtex/能力表/Testing 章节）各自的独立衰减；且漂移方向双向——既有夸大（测试数）也有保守（能力清单），说明不能靠"往少里信"或"往多里防"修正。
- **行动**：→ OKF 束写作规范应强制：凡引用开源工具事实，须携带源码级锚点（文件:行号），并区分【已核验】/ [README-only] /【不一致】三档标注（沿用事实清单的做法）；obliteratus 工具束应设"README 勘误对照表"小节列出 6 处不一致，作为读者评估同类工具的核验方法示范。

## 洞察 5：单人研究者已构建起带遥测闭环的准学术基础设施——开源红队生态自组织成"数据-工具-社区"三层

- **陈述**：elder-plinius 生态不止是"个人收集癖"：CL4R1T4S/L1B3RT4S 提供数据层（档案），OBLITERATUS 提供工具层（权重手术），遥测机制与社区渠道构成社区层（分布式基准实验），并配有学术引用、双许可与治理文档——独立研究者已在机构外复制了准学术研究基础设施。
- **证据**：
  - F-OB-002 / F-OB-030：OBLITERATUS 定位为分布式研究实验，遥测开启时向中心 HF 数据集（pliny-the-prompter/OBLITERATUS-TELEMETRY）贡献匿名基准数据（拒绝方向几何、方法有效性评分），默认关闭、内置 token 脱敏与敏感键过滤——社区级数据回流机制；
  - F-OB-009 / F-OB-010：README 附完整学术引用清单（Arditi 2024、Rimsky 2024、Wollschlager 2025 等）与基准工件（HarmBench、AdvBench、JailbreakBench）——主动接入学术谱系；
  - F-L1-014：glitch token 数据库 sources 引用 LessWrong SolidGoldMagikarp、ACM 2024、arXiv GlitchMiner、NVIDIA Garak——个人档案反向编目学术与工业成果；
  - F-L1-002：README 指向 BASI Discord 社区；F-OB-005：AGPL-3.0 + 商业双许可（自比 MongoDB/Qt/Grafana 模式）——社区入口与商业化治理并存；
  - F-C4-004：CL4R1T4S 设贡献规范（模型名/版本/提取日期）与固定联系渠道——档案层同样有准入质量控制。
- **反常识**：挑战了"严肃对齐研究只发生在机构内、民间红队知识散落且不可积累"的默认假设。该生态具备机构研究的全部形式要素（引用规范、基准数据集、可复现流水线、同行渠道、许可治理），且遥测设计（匿名化、opt-in、schema 版本化）比许多机构工具更规范；机构外的对齐知识正在以基础设施方式沉淀。
- **行动**：→ OKF 束应设"生态地图"视角条目：将三仓库标注为数据层/工具层/社区层并说明其相互供养关系；引用时执行可信度分级（学术引源 > 结构化数据库 > 个人档案叙事）；防御侧读者应把 OBLITERATUS-TELEMETRY 类社区遥测数据集视为潜在的低成本观测源，同时注意其抽样偏差（自选用户、默认关闭）。

## 洞察 6：下一代对抗面在 tokenizer 与字符编码层——不可见字符既是隐写载体也是守方语义过滤的盲区

- **陈述**：L1B3RT4S 中体量最大的文件群恰恰是"可见内容近零"的隐写载体（Unicode Tag 区段字符、变体选择符），加上已编目的 glitch token 库与 ≤5 字符的高效攻击，说明对抗前沿正从自然语言语义层下沉到 tokenizer/字符编码层——而守方档案化护栏全部是语义/关键词形态，对该层结构性失明。
- **证据**：
  - F-L1-017：TOKEN80M8.mkd（23,448,666 字节）与 TOKENADE.mkd 均为单行 emoji + 海量 Unicode Tag 字符（U+E0000–E007F）——以不可见字符为内容主体的最大载体文件；
  - F-L1-003：README.md blob 24,071 字节而可见字符仅约 51 个（>99% 为不可见 Unicode）——连仓库门面本身都是隐写载体；
  - F-L1-013：#MOTHERLOAD.txt 为"无害叙事文本 + 不可见变体选择符"形态——载体与无害内容混合交付；
  - F-L1-015：glitch token 库将异常行为分为 8 类（含 CONTEXT_CORRUPTOR、IDENTITY_DISRUPTOR、LOOP_INDUCER）并覆盖 5 类分词器——tokenizer 层脆弱性已可编目复测；
  - F-L1-026：登记 "<5 字符 one-shot" 的 emoji+缩写攻击样本——攻击成本已压缩到 token 级；
  - F-C4-038 / F-C4-051：对照面——守方有害内容枚举与防注入条款均为语义/关键词形态，无任何字符编码层防护表述。
- **反常识**：挑战了"对抗发生在语义层、护栏读懂内容就能拦截"的默认假设。24MB 的文件可以不含一个可读攻击词；人类读者与语义过滤器同时不可见的内容，恰是投递通道；而 glitch token 攻击甚至不依赖"内容含义"，只依赖分词器的病理行为。
- **行动**：→ 应设独立 OKF 束"编码层对抗面"：讲解 Unicode Tag/变体选择符的编码机制与 glitch token 8 类行为学，供防御者理解盲区成因；defense-lessons 束应建议在输入管道前置"编码规范化 + 不可见字符检测 + tokenizer 行为回归测试"（可复用 F-L1-014 的库做漏洞扫描），而非仅依赖语义分类器。

## 洞察 7：虚构授权修辞是攻击语法的一等公民——"基于授权声明的边界条款"在对话中结构性不可验证

- **陈述**：L1B3RT4S 攻击模板的高频构件不是技术绕过而是话语构造：虚构法律依据、虚构政策主体、虚构管理员身份、虚构环境声明；且同一模板会按目标厂商本地化虚构主体。这暴露守方"授权类边界条款"（授权安全测试/CTF 等）的共性问题：对话上下文内无法验证授权真伪，此类条款可被任何声称授权的话语打开。
- **证据**：
  - F-L1-049："Geneva Convention Guidelines"、"Freedom Of Information Act"、"[ADMIN: ELDER PLINIUS]"、虚构年份 2127、!OMNI 虚构平行宇宙协议在多厂商文件高频出现——虚构授权已是模板化修辞库；
  - F-L1-027：GPT-5.2 条目叠加 "airgapped red teaming env" 虚构隔离环境声明——授权话语与环境声明复合使用；
  - F-L1-032：GROK 3 条目将虚构授权主体本地化为 "xAI policies"——模板按目标厂商定制授权话语，说明其是主动设计的语法要素而非偶发修辞；
  - F-C4-068：ZCode 主提示词设 "授权安全测试/CTF/防御性安全" 双用途边界条款——守方依赖用户自述授权；
  - F-C4-061：XAI 将 `<policy>` 置于文件首段并声明内容开放——不同厂商对"授权边界"的画法差异极大，进一步放大声明式条款的可利用面。
- **反常识**：挑战了"模型拒绝能力来自内置价值观、攻击必须压过价值观"的默认假设。多数模板并不否认价值观，而是构造一个"合规显得正确"的虚构语境（红队授权、未来法规、平行宇宙），让执行与价值观自洽；守方写的任何"仅限授权场景"类条款，在无外部验证机制时都是可以口头满足的条件。
- **行动**：→ defense-lessons 束应单列"授权类条款的结构性弱点"：指出上下文内授权声明不可验证，须与行为级/通道级控制（输出侧审计、工具权限、多轮一致性检查）配对；OKF 束可提供"虚构授权修辞 → 识别特征"映射表（F-L1-049 五类话语构造），供防御侧做意图归因与内容审核规则设计。
