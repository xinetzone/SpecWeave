## 一、格式规范事实（docs/specification.mdx + AGENTS.md 权威性声明）

- **F-001** [AGENTS.md] 项目指令声明：`docs/specification.mdx` is authoritative for format requirements；解释性文档、示例、测试与实现均不向格式添加需求；当各表面不一致时，应在权威源处解决差异，而非把现有实现行为当作规范（normative）。同文件还声明：不把 `skills-ref/` 视作一般贡献面——它是 demonstration artifact，不是 production SDK，也不是格式需求的来源。
- **F-002** [docs/specification.mdx] Skill 是一个目录，最低要求只含一个 `SKILL.md` 文件；可选目录为 `scripts/`（executable code）、`references/`（documentation）、`assets/`（templates, resources），且"Any additional files or directories"均被允许。
- **F-003** [docs/specification.mdx] `SKILL.md` 必须包含 YAML frontmatter，后接 Markdown 内容（"must contain YAML frontmatter followed by Markdown content"）。
- **F-004** [docs/specification.mdx] frontmatter 字段表：`name`（必填）、`description`（必填）、`license`（可选）、`compatibility`（可选，max 500 字符）、`metadata`（可选，字符串键到字符串值的映射）、`allowed-tools`（可选，Experimental）。
- **F-005** [docs/specification.mdx] `name` 约束：1-64 字符；只允许 unicode 小写字母数字（`a-z`、`0-9`）和连字符（`-`）；不得以连字符开头或结尾；不得包含连续连字符（`--`）；必须与父目录名一致（must match the parent directory name）。
- **F-006** [docs/specification.mdx] `name` 合法示例：`pdf-processing`、`data-analysis`、`code-review`；非法示例：`PDF-Processing`（大写不允许）、`-pdf`（不能以连字符开头）、`pdf--processing`（连续连字符不允许）。
- **F-007** [docs/specification.mdx] `description` 约束：1-1024 字符；应同时描述技能做什么（what）与何时使用（when）；应包含帮助智能体识别相关任务的具体关键词；规范给出的差例为 "Helps with PDFs."，好例包含 "Extracts text and tables from PDF files... Use when working with PDF documents or when the user mentions PDFs, forms, or document extraction."
- **F-008** [docs/specification.mdx] `license` 字段：可选；指定技能适用的许可证，规范建议保持简短（许可证名称或捆绑许可证文件的名称），示例 `license: Proprietary. LICENSE.txt has complete terms`。`compatibility` 字段：可选；若提供必须 1-500 字符，内容为环境要求（intended product、system packages、network access 等），示例 `Requires git, docker, jq, and access to the internet`、`Requires Python 3.14+ and uv`；规范附 Note："Most skills do not need the `compatibility` field."
- **F-009** [docs/specification.mdx] `metadata` 字段：可选；字符串键到字符串值的映射；客户端可在此存放规范未定义的附加属性；规范建议键名取得"reasonably unique"以避免意外冲突；示例 `metadata: {author: example-org, version: "1.0"}`。`allowed-tools` 字段：可选；以空格分隔的字符串列出预先批准（pre-approved）运行的工具；标注为 Experimental，"Support for this field may vary between agent implementations"；示例 `allowed-tools: Bash(git:*) Bash(jq:*) Read`。
- **F-010** [docs/specification.mdx] Markdown 正文（body）无格式限制（"There are no format restrictions"）；推荐章节：分步指令、输入输出示例、常见边界情况；正文记录：智能体一旦决定激活技能就会加载整个文件（"the agent will load this entire file once it's decided to activate a skill"），并建议把较长的 `SKILL.md` 内容拆分到被引用的文件中。
- **F-011** [docs/specification.mdx] 三个可选目录的约定：`scripts/`——存放智能体可运行的代码，脚本应自包含或清楚声明依赖、包含有用的错误信息、优雅处理边界情况，支持语言取决于 agent 实现（常见 Python、Bash、JavaScript）；`references/`——存放智能体按需阅读的附加文档，命名示例 `REFERENCE.md`、`FORMS.md`、领域文件（`finance.md`、`legal.md`），"Keep individual reference files focused. Agents load these on demand, so smaller files mean less use of context."；`assets/`——静态资源：模板（文档/配置）、图片（图表/示例）、数据文件（查找表、schemas）。
- **F-012** [docs/specification.mdx] 渐进式披露（Progressive disclosure）三阶段及 token 预算：① Metadata（约 100 tokens）——`name` 与 `description` 在启动时对所有技能加载；② Instructions（推荐 <5000 tokens）——技能被激活时加载完整 `SKILL.md` 正文；③ Resources（按需）——`scripts/`、`references/`、`assets/` 中的文件仅在需要时加载。
- **F-013** [docs/specification.mdx] 规范原文要求："Keep your main `SKILL.md` under 500 lines. Move detailed reference material to separate files."
- **F-014** [docs/specification.mdx] 文件引用约定：引用技能内其他文件时使用相对技能根目录的相对路径（示例链接 `references/REFERENCE.md`、脚本路径 `scripts/extract.py`）；"Keep file references one level deep from `SKILL.md`. Avoid deeply nested reference chains."
- **F-015** [docs/specification.mdx] Validation 一节给出命令 `skills-ref validate ./my-skill`，并说明该命令检查 `SKILL.md` frontmatter 有效且遵循全部命名约定；同时链接到 skills-ref 参考库（github.com/agentskills/agentskills/tree/main/skills-ref）。

## 二、技能创作指南事实（docs/skill-creation/*.mdx）

- **F-016** [docs/skill-creation/quickstart.mdx] Quickstart 教程创建 `roll-dice` 技能；VS Code 默认在 `.agents/skills/` 目录查找技能（"VS Code looks for skills in `.agents/skills/` by default"）；示例 SKILL.md 单文件不足 20 行；文档声明 Agent Skills 是开放格式，同一技能可在 Claude Code 与 OpenAI Codex 等兼容智能体中工作；对各部分的解释为：`name` 必须与文件夹名一致，`description` 是智能体决定是否激活该技能的依据，正文是激活后遵循的指令；文档另提示 "Tool-use reliability varies across models"。
- **F-017** [docs/skill-creation/quickstart.mdx] Quickstart "How it works" 三步骤：Discovery（会话启动时扫描默认技能目录，只读 `name` 与 `description`）、Activation（用户请求与 description 匹配后加载完整 SKILL.md 正文）、Execution（按正文指令执行，按请求适配命令参数）；并说明该过程使用 progressive disclosure。
- **F-018** [docs/skill-creation/best-practices.mdx] 常见陷阱与两条创建路径：在不提供领域上下文的情况下让 LLM 生成技能，产出是模糊的通用流程（"handle errors appropriately"类），有效技能扎根于真实专业知识；路径①从亲自动手的任务中提取——关注"有效的步骤、你做出的纠正、输入/输出格式、你提供的上下文"四类信息；路径②从既有项目产物合成——好的源材料包括内部文档/runbook/风格指南、API 规范/schema/配置文件、代码评审评论与 issue 追踪、版本控制历史（尤其补丁与修复）、真实失败案例及其解决过程。
- **F-019** [docs/skill-creation/best-practices.mdx] 用真实执行打磨：对真实任务运行技能，把全部结果（不只是失败）回灌到创建过程；一轮 execute-then-revise 就能明显提升质量；执行痕迹中无产出步骤的常见原因有三——指令太模糊、指令不适用于当前任务、选项太多而无明确默认值。
- **F-020** [docs/skill-creation/best-practices.mdx] 上下文经济学原则："Add what the agent lacks, omit what it knows"；每段内容的自检问题是 "Would the agent get this wrong without this instruction?"；若没有该技能智能体已能完成整个任务，则技能可能没有增加价值。
- **F-021** [docs/skill-creation/best-practices.mdx] 划界与细节度：技能划界类比"决定一个函数该做什么"——封装与其他技能可组合的连贯工作单元，过窄迫使单个任务加载多个技能（开销与指令冲突风险），过宽则难以精确激活（示例："查询数据库并格式化结果"是连贯单元，再涵盖数据库管理就是管得太多）；细节上，简洁的逐步指引加一个可运行的示例优于穷举式文档——过度全面的技能反而有害，智能体难以提取相关内容并可能被不适用的指令引上无产出路径。
- **F-022** [docs/skill-creation/best-practices.mdx] 大技能结构化：规范建议 `SKILL.md` 保持在 500 行、5000 tokens 以内——只放每次运行都需要的核心指令；详细参考材料移入 `references/` 等目录；关键是告诉智能体"何时加载每个文件"，文中对照示例为 "Read `references/api-errors.md` if the API returns a non-200 status code" 优于泛泛的 "see references/ for details"。
- **F-023** [docs/skill-creation/best-practices.mdx] 控制校准：指令的具体度与任务的脆弱性匹配——多种路径皆可行时给智能体自由度，此时解释 why 比刚性指令更有效（理解目的的智能体能做出更好的上下文相关决策）；操作脆弱、要求一致或必须按特定顺序执行时保持规定性（示例 "Run exactly this sequence: `python scripts/migrate.py --verify --backup`… Do not modify the command or add additional flags."）；多数技能是混合体，应逐段独立校准。
- **F-024** [docs/skill-creation/best-practices.mdx] 另两条指令设计原则：提供默认值而非菜单（选定默认工具、简要提及替代项，示例 "Use pdfplumber for text extraction… For scanned PDFs requiring OCR, use pdf2image with pytesseract instead."）；倾向过程而非声明（教智能体如何处理一类问题而非某个实例的产出，示例方法："读 schema→按 `_id` 外键约定 join→按请求加 WHERE→聚合并格式化为 markdown 表格"）。
- **F-025** [docs/skill-creation/best-practices.mdx] Gotchas 模式：许多技能中价值最高的内容是"违背合理假设的环境特定事实"清单（如软删除表必须带 `WHERE deleted_at IS NULL`、同一 ID 在三个系统中字段名分别为 `user_id`/`uid`/`accountId`、`/health` 与 `/ready` 语义差异）；gotchas 应放在 `SKILL.md` 正文中让智能体在遇到情况前读到；当你不得不纠正智能体的错误时，把该纠正加入 gotchas 段（文中称这是迭代改进技能最直接的方式之一）。
- **F-026** [docs/skill-creation/best-practices.mdx] 其余指令模式与脚本打包信号：输出格式模板（短模板内联于 SKILL.md，长模板或偶用模板存 `assets/` 并引用，智能体对具体结构的模式匹配优于散文描述）；多步工作流 checklist（带 `- [ ]` 复选项与脚本路径）；验证循环（完成→运行验证脚本→失败则修复重跑→通过才继续，参考文档也可充当验证器）；plan-validate-execute（批量或破坏性操作先产出结构化中间计划，用验证脚本对照事实源校验后再执行，文中以 PDF 表单填充五步流程为例，并强调校验步骤的错误信息要让智能体能自我纠正）；当智能体每轮独立重造相同逻辑（画图、解析特定格式、验证输出）时，信号是把该逻辑写成经过测试的脚本放入 `scripts/`。
- **F-027** [docs/skill-creation/evaluating-skills.mdx] 测试用例定义与存储：三部分——Prompt（真实用户消息）、Expected output（成功样貌的人类可读描述）、Input files（可选）；存放在技能目录内 `evals/evals.json`；JSON 结构为顶层 `skill_name` + `evals` 数组，每个 eval 条目含 `id`、`prompt`、`expected_output`、`files`，以及后补的 `assertions` 数组。
- **F-028** [docs/skill-creation/evaluating-skills.mdx] 核心运行模式：每个用例跑两次——带技能与不带技能（或带上一版本）作基线对照；工作区结构为 `csv-analyzer-workspace/iteration-N/eval-*/with_skill|without_skill/{outputs/, timing.json, grading.json}`，同层放聚合统计 `benchmark.json`；`evals.json` 是唯一手工编写的文件，其余 JSON 在评估过程中产生。
- **F-029** [docs/skill-creation/evaluating-skills.mdx] 每轮运行从干净上下文开始（支持 subagent 的环境天然隔离；否则每个运行用独立会话）；改进既有技能时先快照旧版（`cp -r <skill-path> <workspace>/skill-snapshot/`），基线运行指向快照并保存到 `old_skill/outputs/`。
- **F-030** [docs/skill-creation/evaluating-skills.mdx] `timing.json` 字段为 `total_tokens` 与 `duration_ms`；文中提示 Claude Code 的 subagent 任务完成通知携带这两个值，且 "Save these values immediately — they aren't persisted anywhere else"。
- **F-031** [docs/skill-creation/evaluating-skills.mdx] 断言（assertions）在看到第一轮输出后再添加；好断言可编程验证、具体可观察、可数（例："The output file is valid JSON"、"The bar chart has labeled axes"、"The report includes at least 3 recommendations"）；弱断言过于模糊（"The output is good"）或过于脆弱（精确匹配措辞）；写作风格、视觉设计等难以分解为 pass/fail 的品质留给人工评审。
- **F-032** [docs/skill-creation/evaluating-skills.mdx] 评分与聚合文件结构：`grading.json` 含 `assertion_results` 数组（每项 `text`/`passed`/`evidence`）+ `summary`（`passed`/`failed`/`total`/`pass_rate`）；`benchmark.json` 含 `run_summary` 下 `with_skill`/`without_skill`/`delta` 三块，各含 `pass_rate`/`time_seconds`/`tokens` 的 `mean`+`stddev`；stddev 仅在多次运行时有意义；delta 同时呈现技能的代价与收益（文中示例：+13 秒换 +50 个百分点通过率大概率值得，token 翻倍换 2 个百分点提升可能不值）；评分原则：PASS 必须有具体证据（引用或指向输出），同时复审断言本身（太容易/太难/不可验证的要修）；文末 Tip 提出双版本盲比较（blind comparison）作为断言评分的补充。
- **F-033** [docs/skill-creation/evaluating-skills.mdx] 模式分析五条规则：删除或替换在两种配置下都恒通过的断言（它们夸大带技能通过率、不反映技能价值）；排查两种配置下都恒失败的断言（断言坏了/用例太难/查错了对象）；研究"带技能过、不带技能不过"的断言（技能价值的直接证据，追问是哪条指令或脚本起效）；结果跨轮不一致（高 stddev）时收紧指令或补示例降低歧义；检查时间与 token 离群值（读执行 transcript 找瓶颈）。
- **F-034** [docs/skill-creation/evaluating-skills.mdx] 人工评审与迭代闭环：为每个用例记录具体可操作的反馈存入 `feedback.json`（空字符串表示通过人工评审；"The chart is missing axis labels"可操作而 "looks bad" 不可操作）；迭代的三类信号为失败断言（具体缺口）、人工反馈（更广泛的质量问题）、执行 transcript（为什么出错——被忽略的指令可能含糊、无产出步骤应简化或删除）；最有效的改法是把三类信号连同当前 `SKILL.md` 交给 LLM 提改进提案，附四条准则：从反馈泛化（修底层问题而非打窄补丁）、保持精简（过约束时尝试删指令）、解释 why（"Do X because Y tends to cause Z" 优于 "ALWAYS do X, NEVER do Y"）、打包重复工作；循环五步为提案→应用→在新 `iteration-<N+1>/` 重跑→评分聚合→人工复审；停止条件为满意、反馈持续为空、或迭代间不再有有意义提升；文末 Tip 指出 `skill-creator` Skill（github.com/anthropics/skills/tree/main/skills/skill-creator）自动运行该工作流的大部分环节。

## 三、description 触发优化与客户端生态事实

- **F-035** [docs/skill-creation/optimizing-descriptions.mdx] 触发机制定位与限定：`description` 字段是智能体决定是否为给定任务加载技能的首要机制；欠规定（under-specified）意味着该触发时不触发，过宽（over-broad）意味着不该触发时误触发；重要限定——智能体通常只在任务需要其自身知识/能力之外的东西时才查询技能，简单的单步请求（如 "read this PDF"）即使 description 完全匹配也可能不触发；陌生 API、领域特定工作流、不常见格式等需要专门知识的任务才是 description 发挥作用的地方。
- **F-036** [docs/skill-creation/optimizing-descriptions.mdx] description 写作四原则：祈使式措辞（"Use this skill when..." 而非 "This skill does..."）；聚焦用户意图而非实现机制；宁可"pushy"——显式列出适用场景，包括用户没有直接点名领域的情形（"even if they don't explicitly mention 'CSV' or 'analysis.'"）；保持简洁；规范对 description 有 1024 字符硬限制。
- **F-037** [docs/skill-creation/optimizing-descriptions.mdx] 触发评估查询集：存于 `eval_queries.json`，条目形如 `{"query": ..., "should_trigger": true/false}`；建议约 20 条（8-10 条应触发 + 8-10 条不应触发）；应触发查询沿四个轴变化——措辞（formal/casual/typos）、显式度（直接点名领域 vs 只描述需求）、细节量（terse vs 带文件路径列名背景的冗长）、复杂度（单步 vs 埋在长链中的多步）；最有价值的应触发用例是"技能帮得上忙但连接不明显"的那类。
- **F-038** [docs/skill-creation/optimizing-descriptions.mdx] 不应触发用例中最有价值的是 near-miss（近失）查询——与技能共享关键词或概念但实际需要别的东西；弱负例（"Write a fibonacci function"、"What's the weather today?"）测不出什么；强负例示例（针对 CSV 分析技能）："I need to update the formulas in my Excel budget spreadsheet"、"can you write a python script that reads a csv and uploads each row to our postgres database"。
- **F-039** [docs/skill-creation/optimizing-descriptions.mdx] 触发率测量：每个查询跑多次（3 次为合理起点）计算 trigger rate（技能被调用的运行占比）；应触发查询通过条件为 trigger rate 高于阈值（0.5 为合理默认值），不应触发查询为低于该阈值；文中参考 bash 脚本用 `claude -p "$query" --output-format json` 输出经 jq 匹配 `any(.messages[].content[]; .type == "tool_use" and .name == "Skill" and .input.skill == $skill)` 判定技能是否被调用，并提示可替换为各客户端自己的检测逻辑。
- **F-040** [docs/skill-creation/optimizing-descriptions.mdx] 防过拟合划分与优化循环：训练集约 60%、验证集约 40%，两集都按比例混含正负例，划分随机生成后跨迭代固定；只用训练集失败指导修改，验证集结果不进入修改过程；按验证集通过率选出最佳迭代——最佳 description 未必是最后一轮（早轮可能验证通过率高于过拟合的晚轮）；循环五步为双集评估→训练集失败定位→修订 description（避免照抄失败查询的关键词——那是过拟合，应归纳其一般类别；若干轮无进展则尝试结构性不同的写法；随时检查 1024 字符上限——"descriptions tend to grow during optimization"）→重复至训练集全过或无有意义改进→按验证通过率选优；文中称五轮迭代通常足够；定稿后再用 5-10 条从未参与优化的新查询做诚实泛化检查。
- **F-041** [docs/clients.mdx + docs/snippets/clients.jsx] `clients.mdx` 从 `/snippets/clients.jsx` 导入 `clients` 并渲染 `ClientShowcase` 组件；`clients.jsx` 导出的 `clients` 数组共 46 个条目，每条字段为 `name`、`description`、`url`、`lightSrc`、`darkSrc`、可选 `scale`、`instructionsUrl`、可选 `sourceCodeUrl`；名录包含 Claude、Claude Code、ChatGPT & Codex、Gemini CLI、GitHub Copilot、VS Code、Cursor、Goose、OpenHands、Letta、Factory、Kiro、Spring AI、Roo Code、TRAE（sourceCodeUrl 指向 github.com/bytedance/trae-agent）等。
- **F-042** [docs/home.mdx] 首页定位：Agent Skills 是 "lightweight, open format for extending AI agent capabilities"；技能核心是含 `SKILL.md` 的文件夹，元数据至少含 `name` 与 `description`；加载经三阶段 Discovery → Activation → Execution；"Open development" 一节声明该格式最初由 Anthropic 开发（originally developed by Anthropic），作为开放标准发布并被越来越多的智能体产品采纳，标准对更广生态的贡献开放（GitHub agentskills/agentskills + Discord）。
- **F-043** [docs/client-implementation/adding-skills-support.mdx] 集成差异归结为两个因素：技能住在哪里（本地智能体扫文件系统；云端/沙箱需要 API、远程注册表或捆绑资产等替代发现机制）；模型如何访问技能内容（有文件读取能力则直接读 SKILL.md，否则提供专用工具或程序化注入提示词）。三层加载策略表：Tier 1 Catalog（name + description，会话启动时，每技能约 50-100 tokens）；Tier 2 Instructions（完整 `SKILL.md` 正文，技能激活时，推荐 <5000 tokens）；Tier 3 Resources（脚本、引用、资产，指令引用时按需加载，开销不定）；装了 20 个技能的智能体不必预付 20 套完整指令的 token 成本——只付当次会话实际用到的。
- **F-044** [docs/client-implementation/adding-skills-support.mdx] 发现位置：多数本地智能体至少扫 project-level（相对工作目录）与 user-level（相对 home 目录）两个作用域；每个作用域内同时扫客户端自有目录与 `.agents/skills/` 约定路径，文档给出四行表——`<project>/.<your-client>/skills/`、`<project>/.agents/skills/`、`~/.<your-client>/skills/`、`~/.agents/skills/`；`.agents/skills/` 是"广泛采用的跨客户端技能共享惯例"，而规范本身不强制技能目录住在哪里（只定义目录内放什么）；部分实现还扫 `.claude/skills/`（项目级与用户级）以兼容既有技能，其他附加位置包括上溯至 git 根的祖先目录（monorepo 场景）、XDG 配置目录、用户自定义路径。
- **F-045** [docs/client-implementation/adding-skills-support.mdx] 扫描规则：在每个技能目录里找"含有名为恰好 `SKILL.md` 的文件的子目录"（README.md 等被忽略）；跳过 `.git/`、`node_modules/` 等目录；可选遵守 `.gitignore` 避免扫描构建产物；设合理上界——如最大深度 4-6 层、最多 2000 个目录——防止大目录树失控扫描。
- **F-046** [docs/client-implementation/adding-skills-support.mdx] 命名冲突、信任与云端场景：两个技能同名时适用确定性优先规则，现有实现的普遍惯例是"项目级技能覆盖用户级技能"；同一作用域内 first-found 或 last-found 均可，但须择一并保持一致，冲突时记录 warning 告知用户技能被遮蔽；项目级技能来自可能不受信任的仓库，应考虑用信任检查门控其加载，防止不受信仓库向智能体上下文静默注入指令；云端/沙箱中项目级技能随克隆仓库走，用户级与组织级技能需从外部源供给（克隆配置仓库、接受技能 URL/包、Web UI 上传），内置技能可打包为部署物内静态资产；技能可用后，解析、披露、激活的其余生命周期完全相同。
- **F-047** [docs/client-implementation/adding-skills-support.mdx] 解析与宽松校验：解析分两段——`---` 分隔符间的 YAML frontmatter 与其后的 Markdown 正文（正文经 trim 后即技能 body）；对"技术上非法但彼解析器接受的 YAML"（最常见：未加引号的值含冒号）考虑回退方案——包引号或转为 YAML block scalar 后重试；宽松校验四规则：name 与父目录名不匹配 → 警告但加载；name 超 64 字符 → 警告但加载；description 缺失或为空 → 跳过该技能并记录错误（description 对披露必不可少）；YAML 完全不可解析 → 跳过并记录错误；附 Note 说明该宽松方案有意放宽规范对 name 的严格约束以兼容其他客户端编写的技能。
- **F-048** [docs/client-implementation/adding-skills-support.mdx] 技能记录至少三个字段：`name`、`description`、`location`（SKILL.md 绝对路径），存入以 `name` 为键的内存 map 便于激活期快速查找；body 可在发现时存储（激活更快）也可激活时从 location 读取（省内存且能吃到技能文件变更）；技能基目录（location 的父目录）用于后续解析相对路径与枚举捆绑资源。
- **F-049** [docs/client-implementation/adding-skills-support.mdx] 目录披露（Tier 1）：为每个已发现技能在结构化格式（XML/JSON/列表均可）中给出 `name`、`description`、可选 `location`；文中 XML 示例为 `<available_skills><skill><name>…</name><description>…</description><location>…</location></skill></available_skills>`；每个技能约占 50-100 tokens；`location` 的双重作用——支撑文件读取式激活 + 给模型解析正文中相对引用（如 `scripts/evaluate.py`）提供基路径；若专用激活工具的结果中已带技能目录路径，目录中可省略 `location`。
- **F-050** [docs/client-implementation/adding-skills-support.mdx] 目录放置与过滤：两种常见放置——系统提示词加标签小节（更简单、兼容面广）或嵌入专用激活工具的 description（保持系统提示词干净、发现与激活天然耦合）；随目录附简短行为指令，措辞按激活机制分两版（文件读取版："use your file-read tool to load the SKILL.md at the listed location before proceeding… resolve them against the skill's directory (the parent of SKILL.md)"；专用工具版："call the activate_skill tool with the skill's name"）；被过滤的技能（用户禁用、权限拒绝、声明 `disable-model-invocation` 旗标）应从目录中完全隐藏而非列出后在激活时拦截；无可用技能时整个省略目录与行为指令——不显示空的 `<available_skills/>` 也不注册无有效选项的技能工具。
- **F-051** [docs/client-implementation/adding-skills-support.mdx] 激活（Tier 2）：多数实现依赖模型自身判断而非 harness 侧触发匹配/关键词检测；两条实现路径——文件读取式激活（模型用标准文件读取工具按 location 读 SKILL.md，无需专门基础设施）与专用工具激活（如 `activate_skill`，模型不能直接读文件时必需；相对原始文件读取的优势：控制返回内容、以结构化标签包裹、列出捆绑资源、施加权限/征得同意、统计激活）；Tip 建议把工具的 `name` 参数约束为有效技能名集合（如 schema 中的 enum）以防模型幻觉出不存在的技能名，无技能时不注册该工具；用户显式激活的常见形态是斜杠命令或提及语法（`/skill-name` 或 `$skill-name`），可配自动补全；模型收到的内容两选项——完整文件（含 frontmatter；`compatibility` 等字段可在激活期提供信息）或仅正文（剥离 frontmatter；现有带专用激活工具的实现中多数采用后者）。
- **F-052** [docs/client-implementation/adding-skills-support.mdx] 长会话上下文管理：结构化包裹示例 `<skill_content name="pdf-processing">…Skill directory: …Relative paths in this skill are relative to the skill directory.<skill_resources><file>…</file></skill_resources></skill_content>`，收益为模型可区分技能指令与其他会话内容、harness 可在上下文压缩中识别技能内容、捆绑资源被浮现但不急切加载；专用工具可枚举支持文件但**不应急切读取**（模型按需用文件读取工具加载），大目录可封顶枚举并注明可能不完整；有权限系统时应把技能目录加入允许清单，避免每次引用捆绑资源都弹确认；上下文压缩/截断旧消息时**豁免技能内容**（丢失技能指令会无错误地静默劣化表现），可标记工具输出受保护或借结构化标签识别；考虑去重激活（已在上下文中的技能跳过再注入）；子代理委派为可选高级模式——技能在独立子代理会话中运行并向主会话返回工作摘要。

- **F-057** [skills-ref/src/skills_ref/parser.py] `find_skill_md(skill_dir: Path) -> Optional[Path]`：依次检查 `SKILL.md` 与 `skill.md`（先大写优先），存在则返回路径，均不存在返回 `None`；docstring 写明 "Prefers SKILL.md (uppercase) but accepts skill.md (lowercase)"。`parse_frontmatter(content: str) -> tuple[dict, str]`：内容不以 `---` 开头 → `ParseError("SKILL.md must start with YAML frontmatter (---)")`；`content.split("---", 2)` 少于 3 段 → `ParseError("SKILL.md frontmatter not properly closed with ---")`；`body = parts[2].strip()`；frontmatter 用 `strictyaml.load` 解析，`strictyaml.YAMLError` 被包装为 `ParseError(f"Invalid YAML in frontmatter: {e}")`；解析结果不是 dict → `ParseError("SKILL.md frontmatter must be a YAML mapping")`；若存在键 `metadata` 且为 dict，则整体转换为 `{str(k): str(v) for k, v in ...}`。
- **F-058** [skills-ref/src/skills_ref/parser.py] `read_properties(skill_dir: Path) -> SkillProperties`：`find_skill_md` 返回 None → `ParseError(f"SKILL.md not found in {skill_dir}")`；缺 `name`/`description` 键 → `ValidationError("Missing required field in frontmatter: name")`（description 同理）；name/description 不是字符串或 strip 后为空 → `ValidationError("Field 'name' must be a non-empty string")`（description 同理）；返回 `SkillProperties(name=name.strip(), description=description.strip(), license=metadata.get("license"), compatibility=metadata.get("compatibility"), allowed_tools=metadata.get("allowed-tools"), metadata=metadata.get("metadata"))`；docstring 明确 "It does NOT perform full validation. Use validate() for that."
- **F-059** [skills-ref/src/skills_ref/validator.py] 模块级常量与 name 校验：`MAX_SKILL_NAME_LENGTH = 64`、`MAX_DESCRIPTION_LENGTH = 1024`、`MAX_COMPATIBILITY_LENGTH = 500`；`ALLOWED_FIELDS = {"name", "description", "license", "allowed-tools", "metadata", "compatibility"}`（注释标注 "Allowed frontmatter fields per Agent Skills Spec"）。`_validate_name(name: str, skill_dir: Path) -> list[str]` 校验序列：空/非 str/strip 后为空 → "Field 'name' must be a non-empty string"（短路返回）；随后 `unicodedata.normalize("NFKC", name.strip())` 归一化，再依次检查——长度 >64 → "exceeds 64 character limit (N chars)"；`name != name.lower()` → "must be lowercase"；以 `-` 开头或结尾 → "cannot start or end with a hyphen"；含 `--` → "cannot contain consecutive hyphens"；存在字符既非 `isalnum()` 也非 `-` → "contains invalid characters. Only letters, digits, and hyphens are allowed."；传入 skill_dir 时目录名同样 NFKC 归一化后与 name 比较，不等 → "Directory name 'X' must match skill name 'Y'"；docstring 写明 "Skill names support i18n characters (Unicode letters) plus hyphens."
