# 审查报告（Spec Mode · review.md）

> V 阶段审查记录。审查对象：第二轮源码级增量扩展的全部产出物与修订。

## 1. 四视角对抗审查

### 🔴 魔鬼代言人 —— 「你的源码级结论有多少是站得住的？」

**质疑 1：把「UI 图注单源」判为已坐实，会不会过度宣称？**

反方论证：源码里出现 `PAGE_SPECS` 常量，只能证明**代码中有这四个字**，不能证明**用户在浏览器里看到的就是这四个字**。

**处置**：本轮明确区分了三层证据强度，未把代码常量直接等同于「用户可见行为」：

| 主张 | 证据类型 | 表述强度 |
|------|---------|---------|
| 四入口名 | 代码常量 + 内嵌字符串 + 官方文档 | 「代码与文档三源一致」✅ |
| 移动端 | CSS/HTML 实现 + 截图文件名 | 「实现级证据（同一 HTML 的响应式分支）」 |
| 明暗主题 | 按钮 + JS + localStorage + CSS 变量 | 「完整可运行机制」 |
| 回复草稿 | `_reply_draft` 代码 + `USAGE.md` + `SKILL.md` | 「代码与文档双源」 |
| 检索五维度 | `USAGE.md` 第 4 章逐字 | 「官方文档逐字坐实」 |

未使用「官方验收过的功能名」「实测可用」等超强表述。

**质疑 2：只读真的是结构性保证吗？一个 `read_only: True` 能说明什么？**

反方论证：JSON 元数据里写 `read_only: true` 只是**声明**，执行时未必受限。

**处置**：补了三层独立证据，而不只是信任那个布尔值（F-073~F-075）：

1. `read_only: True` 位于**列表推导式内**，对全部 30 工具统一置位 → 声明与实现同源，无法逐项造假；
2. 源码中**不存在任何写入型函数**（`send_message`/`send_text`/`post_message`/`write_*` 全部零匹配）→ 写能力根本不存在；
3. 数据库以 `sqlite3.connect(f"file:{snapshot}?mode=ro", uri=True)` 只读打开 → 底层强制。

三条同时成立才构成「结构性保证」。**单独任何一条都不够**——这一点在文档中写明了。

**质疑 3：你们把 8 项 ⚠️ 判成「6 项坐实」，是不是在给首轮找补？**

反方论证：首轮判 ⚠️ 是因为**当时只有 README**；现在能坐实，是因为源码里恰好有这些内容——但也可能只是**文档比 README 更全**，官方从来就没在 README 里承诺过。

**处置**：承认这是**信源可得性差异**而非「首轮判断错误」。首轮的措辞是「官方 README 只有语义对应、未逐字给出名称」——**这个陈述本身是准确的**（README 确实如此），首轮错的是把它当作「官方未定义」的暗示。本轮在 `verification.md` 追记与 `source-code-verification.md` 中都明确写为「**审慎保守判定，非官方文档缺失**」，并给出机制解释：首轮读的是 `main` 分支网页视图，而本地 commit 含新增的 `docs/USAGE.md` 与 `SECURITY.md`。

**结论**：首轮**未发现任何造假式断言或事实性错误**；唯一需要方向性修正的是 #18「四种视图风格」。

### 🟠 老板视角 —— 「这些结论对采用决策有什么用？」

**质疑**：源码分析容易变成「为读源码而读源码」，产出一堆技术细节却不改变任何决策。

**处置**：核验每条源码事实是否直接改变采用判断，产出 4 条可执行结论（`concepts/09` §4）：

| 结论 | 决策影响 |
|------|---------|
| 接入助手**不是只读**，且官方已明确标注 | 「日常装 Skill」与「macOS 授权取钥」必须分开评估 |
| 报告安全是**失败关闭**模型，但**加固不追溯旧 HTML** | 升级后须重新生成旧报告，否则仍在旧安全水平 |
| 回复草稿是**确定性模板** | 期待「AI 自由生成」的用法需要调整；期待稳定简短回复的用户不受影响 |
| 计数四口径（30/36/37/73） | 评估工作量与集成面时不再被「73 个命令」误导 |

### 🔵 未来视角 —— 「这些结论什么时候会过期？会不会误导后续读者？」

**质疑**：`v0.9.2-preview.2` 的源码事实可能很快失效。

**处置**：

1. `stale_after: 2027-03-06` 保持与首轮一致；
2. **版本锚点显式化**：所有源码事实锚定 commit `fb6a42c`（完整 SHA 出现在 `source-code-map.md` 与 `source-code-verification.md`），而非「main 分支当前状态」；
3. 登记 tag 与 HEAD 的 13 提交差距（F-060），让读者知道本束快照处于发布版之后的开发态；
4. `references/source-code-verification.md` §6 列出 5 项到期复核项。

**额外处置**：`concepts/08` 的模式 M6 明确指出「对外接口数 vs 源码能力数」的差值**本身是信息**，并给出「差值持续扩大 / 为负」两种信号的含义——让后续读者知道怎么判断文档是否开始腐化。

### 🟣 证据强度 —— 「每条结论的证据链是否完整？」

**逐条走查**：44 条 F 事实、8 项 ⚠️ 对账、13 项计数断言，均可回溯到具体文件与行号级证据。检查中发现并修复的问题：

| # | 问题 | 发现方式 | 处置 |
|---|------|---------|------|
| 1 | `style-previews` 文件数记为 9，实际 10 | 全量计数复核（**非抽样**） | 修正 7 处表述 |
| 2 | AST 脚本漏 `ast.AnnAssign`，字段数返回 0 | 首探结果异常（0 而非偏差） | 修正脚本，重跑得 266 |
| 3 | 首轮摘要中记「HEAD = v0.9.2-preview.2」 | 复核 tag 与 HEAD | 修正为「HEAD 领先 tag 13 提交」，并据此调整 G0 固定策略 |
| 4 | 首轮摘要中记 CLI 子命令 34 / 38 | AST 精确计数 | 修正为 36 / 37 |
| 5 | 首轮摘要中记 `SOURCE_RULES` 11（未区分渲染器） | 双渲染器对照 | 修正为旗舰 11 / HTML 8 |

**元教训**：第 1 条暴露了**抽样复核的不足**——抽 4 项时恰好没抽到 `style-previews`，改为全量复核后发现。故 V 阶段最终执行的是全量计数断言复核而非抽样。
