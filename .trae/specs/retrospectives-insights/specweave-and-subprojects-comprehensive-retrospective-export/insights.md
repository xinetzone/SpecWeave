# I 阶段：洞察四元组

> 每条含「现象 / 根因（5-Whys）/ 影响 / 建议」四元组；根因表述为「与现有事实一致的一种解释」，并列出竞争假设与证据缺口。
> 深度自评（1~5，5 为最深）：I-1 = 4、I-2 = 4、I-3 = 4、I-4 = 4、I-5 = 4。

## I-1 产出结构由「治理规范仓库」位移为「治理 + 应用组合 + 知识工厂」三面并行

- **现象**：基线时 apps 应用 4 个（F-043），采集时点 `apps/AGENTS.md` 路由表登记 40 行（F-031）；OKF 知识束 1083 个（F-062），束内 md 11794 篇；增量窗口内主题含 bundle/知识包/OKF 的提交 469 条（F-059）；同期治理类提交仍居首（retrospective scope 557 条，F-010）。
- **根因（5-Whys）**：
  1. 为什么可见增长集中在 apps 与知识束？→ 因为这两类产出的新增动作在采集时点已有可复制的装配形态（应用自带 `AGENTS.md`/`.agents/rules`/`docs`，知识束自带 `index.md`/`concepts`）。
  2. 为什么装配形态可复制？→ 因为主权区已存在对应的规范与模板（F-023 中 templates 109 个、protocols 18 个）。
  3. 为什么规范与模板先于产出规模化存在？→ 因为基线期（2026-06-23~07-19）的产出以规范体系自身为主（全量 docs 占比 53.3%，F-006；全量提交数见 F-036）。
  4. 为什么规范体系能在 27 天内成形？→ 因为该阶段的产出对象是单一的规范容器（`.agents/` 与 `AGENTS.md`），无外部交付约束。
  5. 为什么后一阶段转向外部交付物？→ 窗口内出现平台化外向动作（Meoo 技能发布、赏金交付、竞赛参与，F-056~F-058、F-060、F-064），产出对象从内部规范扩展为可在外部消费的资产。
- **影响**：治理面（docs/rules）的提交计数仍最高，但新增资产的**消费面**已转向 apps 与知识束；复核重心若仍只放在 `.agents/` 会遗漏主要增长面。
- **建议**：新增应用与知识束时执行「装配清单」（应用路由表登记 + 五要素 + 索引登记）；复盘范围默认包含 apps 与 projects/。
- **竞争假设**：apps 与知识束的增长也可能只是「快照采样差异」（例如采集时点恰逢批量落盘）。证据缺口：未取得 apps 逐月新增时间线。
- **引用事实**：F-031、F-043、F-059、F-062、F-010

## I-2 迁移仍是最高风险的事件类型，其成本以「事后集中修复」形式延后出现

- **现象**：窗口内主题含「迁移」的提交 ≥8 条，其中 3 条为迁移后断链修复（2026-09-28 修复 50 处、2026-09-30 修复模式库迁移遗留、2026-10-17 修复路径迁移后旧引用失效），见 F-061、F-052、F-053、F-051；`.agents/docs/` 迁移至根 `docs/` 于 2026-08-31 完成（F-035），采集时点该旧路径已不存在（F-034）。
- **根因（5-Whys）**：
  1. 为什么迁移后出现集中断链修复？→ 因为单次迁移动作涉及多类引用方（Markdown 相对链接、frontmatter `x-toml-ref`、脚本/配置中的硬编码路径）。
  2. 为什么多类引用方难以在迁移当次穷尽？→ 因为引用方分布在不同区域（主权区、apps、docs、子模块），且部分为生成物或历史归档。
  3. 为什么历史归档也参与扫描？→ 因为归档仍被索引（toctree）与检索路径覆盖。
  4. 为什么索引与检索仍覆盖归档？→ 因为仓库以「索引可达」为正例（F-026 报告与模式规模持续增长）。
  5. 为什么索引可达性与迁移安全耦合？→ 因为可达性依赖路径字符串，而路径字符串在迁移中发生整体改写。
- **影响**：断链以跨天、跨批次的修复提交出现（F-052 → F-053 → F-061），单次迁移的真实成本高于当期提交所呈现的量。
- **建议**：迁移类变更把「三类引用方扫描 + 断链门禁」与迁移同批交付；已有 `migration-cascade-checklist-template` 与 `cascade-update-prerequisite-check` 模式可直接挂载。
- **竞争假设**：这些断链也可能是「新增内容引入」而非迁移引入。证据缺口：未逐条回证 50 处断链的引入提交。
- **引用事实**：F-052、F-053、F-061、F-034、F-035

## I-3 跨期对比存在口径风险：结构治理会改写计数边界，表观差值可能指向错误方向

- **现象**：知识库 md 计数基线 836（口径 `.agents/docs/knowledge`）→ 采集 500（口径 `docs/knowledge`），差 -336（F-044）；Skill 门面 18 → 172（F-041），且窗口内发生过技能目录统一（F-051）；可见模式 493 → 952、报告 1317 → 2269（F-038、F-039）；OKF 知识束本仓实测 1083（F-062）与 apps 自述 1307（F-063）并存。
- **根因（5-Whys）**：
  1. 为什么表观差值方向不一致？→ 因为两次统计的计数边界（目录范围、排除规则）在期间发生过变化。
  2. 为什么计数边界会变化？→ 因为期间执行了文档中心迁移与技能目录统一（F-035、F-051）。
  3. 为什么统计脚本未同步？→ 因为统计命令由报告作者临时书写，而非以固定脚本 + 声明口径执行。
  4. 为什么用临时命令？→ 因为复盘模板未把「口径声明」列为必填项。
  5. 为什么模板缺此项？→ 因为模板成形于结构稳定期，未覆盖结构治理期。
- **影响**：若直接引用表观差值，可能得出「知识库萎缩」「技能暴涨」等方向性结论，而这两者均可能是口径变化的产物（F-044、F-041）。
- **建议**：跨期报告的每个对比指标标注「口径一致 / 口径变更 / 不可比」；口径变更的指标只报存量与边界，不报方向性增减结论。
- **竞争假设**：知识库计数下降也可能反映真实的内容重组（大文件合并为原子文件）。证据缺口：未对两次口径做同一脚本重跑。
- **引用事实**：F-044、F-041、F-038、F-039、F-062、F-063

## I-4 单点维护下的「日均提交下降」不构成产能下降证据，需双轴度量

- **现象**：日均提交由基线的 55.4/天降至全量 37.1/天（F-037）；增量窗口类型分布中 feat 414 条、chore 463 条（F-009）；前两位提交身份合计占 96.5%（F-012），其归属关系未核实（F-013）；贡献者身份数 5 → 7（F-045）。
- **根因（5-Whys）**：
  1. 为什么日均提交下降？→ 因为提交结构从「小步高频补规范」转为「成批交付应用/知识束」。
  2. 为什么转为成批交付？→ 因为窗口内产出对象变为应用组合与知识束（F-059、F-031）。
  3. 为什么成批交付对应更低提交频率？→ 因为单次提交承载的产出量上升（例如 2026-10-18 单日提交同时含技能、规格归档与子模块指针推进，F-056~F-058）。
  4. 为什么这一结构转变可维持？→ 因为装配动作本身已被模板化（F-023 templates 109 个）。
  5. 为什么度量未随之调整？→ 因为既有的度量表述（提交数/日均）在基线报告中已固定，未引入产出物轴。
- **影响**：以提交数单轴衡量产能，会把「产出密度上升」读作「节奏放缓」。
- **建议**：产能度量改用双轴——提交计数（节奏） + 产出物计数（apps 应用数、知识束数、报告数、模式数）。
- **竞争假设**：日均下降也可能反映维护者可用工时下降。证据缺口：无工时或会话时长记录可佐证。
- **引用事实**：F-037、F-009、F-012、F-013、F-045、F-031

## I-5 门禁体系在采集时点覆盖 16 个编号项加 1 个子模块指针漂移守卫，覆盖面向「守恒类破坏」扩展

- **现象**：`ci-quality-gates.yml` 含 `[1/16]`~`[16/16]` 与新增 `[1.5/16] Submodule pointer consistency (S1 drift guard)`（F-033）；基线报告记载为 16 步、无 1.5 项（基线 S1.6）；子模块指针在采集时点无漂移（F-017）。
- **根因（5-Whys）**：
  1. 为什么新增该守卫？→ 因为存在一类变更不修改子模块内部文件、却改写 gitlink 指针。
  2. 为什么这类变更难被发现？→ 因为它在子模块工作树内不可见，只在主仓索引中体现。
  3. 为什么需要门禁而非人工检查？→ 因为指针推进在窗口内高频发生（206 条，F-048）。
  4. 为什么高频？→ 因为知识束与子项目在主仓外独立演进（F-021）。
  5. 为什么独立演进要求守恒校验？→ 因为主仓对子模块内容的可见性依赖指针值本身。
- **影响**：该类「沉默破坏」（指针漂移、生成物未提交）在推送前被拦截，其同类清单在报告中此前未被单列。
- **建议**：把「生成物未提交」「子模块指针漂移」「元数据与正文双轨不一致」归入统一的「守恒类门禁」清单，并在 CI 文档中按类登记。
- **竞争假设**：该守卫也可能因其他区域的同类故障而添加（非子模块动因）。证据缺口：未取得引入该守卫的提交说明。
- **引用事实**：F-033、F-017、F-048、F-021
