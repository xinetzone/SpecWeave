## §1 意见清单

### V-1 结论过强：把「不在 HEAD 祖先链」放大为「无法 diff / bisect」，与实测直接冲突

**视角**：魔鬼代言人

**质询**：
- `insights.md` 第 51 行（I-1 影响段「对使用者」）原文：「用户无法用 diff / bisect 对比升级前后的行为，也无法把 issue 复现到具体历史提交」。
- `e-stage-pattern.md` 第 110 行（§2.3 反模式 1）原文：「11 个 tag 指向的提交不在 HEAD 祖先集合内（F-011），用户无法 diff / bisect / 复现 issue」。
- 两者唯一支撑均为 F-011（11 个 tag 非 HEAD 祖先）。F-011 只证明了「祖先关系不成立」，从未证明「对象内容不可达」。

**风险**：
`git merge-base --is-ancestor v0.3.4 HEAD` 返回退出码 1，这只说明 **v0.3.4 不是 v0.3.4..HEAD 这条路径上的祖先**，与「两个版本之间无法比较」是两件事。实测 `git diff --stat v0.3.4 HEAD` 输出 `69 files changed, 2892 insertions(+), 533 deletions(-)`，`git log --oneline -1 v0.3.4` 输出 `41b6483 feat: 更新版本至0.3.4并添加新功能`，`git cat-file -t v0.3.4` 返回 `commit`——**提交对象完好、内容完全可比**。因此「用户无法用 diff 对比升级前后的行为」是一句可被 3 条 git 命令当场推翻的断言。这条断言是 I-1 的核心影响论述，且是 E 阶段主模式 C1 反模式 1 的立论基础；一旦被读者推翻，整条 I-1 洞察与 C1 的「标签可达性」不变量 I-1 的现实必要性都会被连带质疑。真实的限制是：`git bisect` 依赖**单一祖先链**上的二分，跨 lineage 的历史无法用主线 bisect 定位——这是**工具适用性限制**，不是**内容不可达**。

**修正建议**：
在 `insights.md` 第 51 行将「用户无法用 diff / bisect 对比升级前后的行为」改写为「**版本差异可通过 `git diff <tag> HEAD` 直接比对，但 `git bisect` 这类依赖单一祖先链的回归定位工具在跨谱系历史中不可用，用户难以把 issue 复现到主线上的某一次提交**」；在 `e-stage-pattern.md` 第 110 行反模式 1 的「实际为什么会失败」列，将「用户无法 diff / bisect / 复现 issue」改写为「**`git bisect` 在跨谱系历史上不可用（bisect 依赖单一祖先链），无法把 issue 定位到主线提交**」；同时在 `facts.md` 追加一条 F-088 记录实测证据（`git diff --stat v0.3.4 HEAD` 的 69 files changed 输出 + `git cat-file -t v0.3.4` = commit），使「diff 可用、bisect 不可用」成为可回溯事实而非断言。

**严重度**：P0

**修正后应达到的验收标准**：
1. `insights.md` 与 `e-stage-pattern.md` 中全文检索「无法 diff」**零命中**；
2. `insights.md` I-1 影响段与 `e-stage-pattern.md` 反模式 1 均同时出现「bisect」与「不可用/受限」表述，且明确把 `git diff` 列为**可用**手段；
3. `facts.md` 存在 F-088 或等价编号，其来源列含 `git diff --stat v0.3.4 HEAD` 的实际输出行（69 files changed / 2892 insertions / 533 deletions）；
4. 修正后 I-1 的问题陈述由「历史不可达」收敛为「**单一祖先链断裂导致 bisect/主线复现不可用**」，且该收敛不影响 C1 不变量 I-1（标签可达性）的设立理由——C1 仍成立，但须把理由从「无法 diff」改为「bisect/主线复现链路不可用」。

### V-2 遗漏关键结构：F-011 只记录「非祖先」，未记录「多谱系（lineage）重置」这一真正的成因

**视角**：魔鬼代言人

**质询**：
- `facts.md` F-011（第 47 行）仅记录「11 个早期 tag 非 HEAD 祖先，creatordate 落在 2025-02-05~2025-11-17」。
- `insights.md` I-1 现象段第 34 行、5-Whys 第 43~44 行（Why 1 / Why 2）据此推出「主线起点是一次重置而非连续演进」。
- `e-stage-pattern.md` 第 45 行（§2.1 触发场景信号 2「标签指向不可达历史」）与第 72 行（§2.2 步骤 ②「逐坐标判定可达性 / 谱系」）直接以 F-011 为唯一依据。

**风险**：
R 阶段止步于「结果观测」，未记录「结构成因」，导致 I-1 与 E 阶段把一个**可解释的、有明确边界的工程事件**误判为**不可解释的历史断层**。实测证据：13 个 tag 实际分属 **6 条互相独立的谱系**，每条谱系的根提交 subject 均为「**项目重置**」：

```
root=9b61b35  tags=v0.1.2
root=88e2ff2  tags=v0.3.7,v0.3.8
root=96fbfa9  tags=v0.2.0,v0.2.1
root=3dcd9f5  tags=v0.1.1
root=fb76d06  tags=v0.2.2,v0.3.0,v0.3.1,v0.3.2,v0.3.3,v0.3.4
root=bed5041  tags=v0.1.3
```

更关键的是 `git show v0.3.4:pyproject.toml` 显示 `name = "mystx"`、`version = "0.3.4"`、`requires-python = ">=3.10"`——**旧谱系里仍然是同一个 mystx 项目**，不是另一个项目被误挂在同一 tag 空间。这直接改变 I-1 的定性：不是「13 个 tag 中 11 个指向不可达历史」，而是「**13 个 tag 分属 6 条因项目重置而分裂的谱系，其中 4 条已被当前主线取代，但它们的发布物仍在 PyPI 上可安装**」。两者的行动项完全不同——前者指向「登记断点、无法修复」，后者指向「**谱系映射表 + 重置即需重建版本坐标契约**」。缺了这条结构事实，C1 的「不可修复项显式登记」步骤会把一个**有确定成因、可设计对策**的问题登记为「永久豁免」，从而让门禁从第一天起就漏掉真正该管的部分。

**修正建议**：
在 `facts.md` 追加 F-089（13 个 tag → 6 条谱系的映射表，每条谱系根提交 subject 均为「项目重置」）与 F-090（`git show v0.3.4:pyproject.toml` 证实旧谱系仍为 mystx 项目）；在 `insights.md` I-1 现象段第 34 行之后增补该结构事实，并把 5-Whys Why 1 的表述由「13 个 tag 中 11 个无法从当前主线抵达」改写为「**13 个 tag 分属 6 条独立谱系，4 条已被 '项目重置' 取代**」；在 `e-stage-pattern.md` 第 45 行触发场景信号 2 增补谱系维度，并把第 97 行 §2.2 步骤 ⑤ 的「典型不可修复项」中的「谱系断层」明确限定为「**已被重置取代的谱系（可通过谱系映射表显式登记）**」，与「真正不可修复的断链」区分开。

**严重度**：P0

**修正后应达到的验收标准**：
1. `facts.md` 存在 F-089/F-090（或等价编号），F-089 含 13 tag → 6 谱系的完整映射与每个根提交 subject，F-090 含 `git show v0.3.4:pyproject.toml` 的 `name = "mystx"` 证据行；
2. `insights.md` I-1 的现象段与根因段均出现「6 条谱系」与「项目重置」字样，且不再出现「11 个 tag 指向不可达历史」这一单值表述；
3. `e-stage-pattern.md` §2.2 步骤 ⑤ 的豁免清单区分「已被重置取代的谱系」与「不可修复断链」两类，前者带对策（谱系映射表）、后者带到期条件；
4. C1 主模式全文不出现把「项目重置」导致的谱系分裂与「不可修复的历史断链」混为一谈的句子。

### V-3 归因过强：「变更记录仪式被跳过 12 次」缺乏依据，实为「仪式从未建立」

**视角**：未来

**质询**：
- `insights.md` 第 166 行（I-4 的 Why 4）原文：「13 个 tag 只产出 1 条 CHANGELOG 条目（F-071、F-072），即「每次发布更新变更记录」这一最低成本的对齐动作**被跳过 12 次**；一旦某次仪式被跳过，其余载体也就失去了更新的触发点」。
- 该结论的唯一依据是 F-071/F-072（F-072 记录 13 个 tag 中 12 个在 CHANGELOG 无对应条目）。

**风险**：
「被跳过 12 次」是一个**含因果预设的计数**——它断言「仪式曾经成立过、后来被跳过 12 次」，而 F-071/F-072 只证明了「12 个 tag 没有对应条目」，**并未证明这 12 个发布点当时存在可跳过的仪式**。实测回源：`git show v0.3.4:CHANGELOG.md` 与 `git show v0.2.0:CHANGELOG.md` 的内容均只有模板头两行（「# xyzstyle 项目变更日志 / 本文档记录 xyzstyle 项目的所有重要变更。」），**不含任何版本条目**；`git show v0.1.1:CHANGELOG.md` 直接报 `fatal: path 'CHANGELOG.md' exists on disk, but not in 'v0.1.1'`——该版本根本没有 CHANGELOG 文件。这说明：**变更记录仪式在历史上从未真正建立过**，而不是「建立后被跳过 12 次」。两种归因导向完全不同的行动项：前者指向「补齐 12 条历史记录」（不可能做到，因为旧谱系的变更信息未被保留），后者指向「**把仪式变成门禁，从下一个版本起不再产生新的空洞**」——这正是 E 阶段主模式 C1 步骤 ④/⑥ 真正要解决的问题。归因错误会让行动项被定级为一个无法完成的补录任务。

附带发现：旧谱系的 CHANGELOG 标题为「**xyzstyle 项目**变更日志」，与当前项目名 mystx 不符——这是「项目重置」链路在文档层的又一处残留，与 V-2 互相印证，但同样未被采集。

**修正建议**：
在 `insights.md` 第 166 行将「即……被跳过 12 次」改写为「**该仪式在历史上从未真正建立（旧谱系的 CHANGELOG.md 或不存在、或仅含 'xyzstyle 项目' 模板头而无任何版本条目），而非建立后被跳过 12 次**」；在 `facts.md` 追加 F-091 记录 `git show v0.1.1:CHANGELOG.md` 报错与 `git show v0.3.4:CHANGELOG.md` 的模板头原文；同时在 I-4 影响段补一句限定——**12 个 tag 的变更信息在源头即未被保留，补录不可行**。

**严重度**：P2

**修正后应达到的验收标准**：
1. `insights.md` 全文检索「被跳过 12 次」零命中；
2. `insights.md` I-4 的 Why 4 明确区分「从未建立」与「建立后被跳过」；
3. `facts.md` 存在含 `git show v0.3.4:CHANGELOG.md` 模板头原文与 `git show v0.1.1:CHANGELOG.md` 报错信息的事实条目；
4. I-4 的行动建议不含「补齐历史 12 条变更记录」这类不可执行项。

### V-4 事实表述错误：F-086 的括注「即 docs 组的全部条目」与实测不符

**视角**：新人

**质询**：
- `facts.md` F-086（第 168 行）括注：「并集独有 23 项，**即 docs 组的全部条目**（`ablog`、…、`sphinxext-opengraph`、`invocations>=3.0`）」。
- 该括注是 I-5「声明面冗余且无权威源」与 E 阶段 C2「声明面单一权威源」的直接证据来源（`e-stage-pattern.md` §5.2 第 301 行、§5.3 第 310 行均引用 F-086）。

**风险**：
这是**面向零上下文读者的第一手事实条目**，其括注给出了错误的集合等价关系，会让读者认为「dev 组差集 = docs 组全集」。实测（`tomllib` 解析 `pyproject.toml` 递归展开 `{include-group}` 引用后做双向差集）结论相反：

```
union_only == docs_set ?  False
union_only - docs : ['invocations>=3.0']            # union_only 含 tasks 组的 invocations，docs 组没有
docs - union_only : ['myst-nb', 'myst-parser>=4.0', 'sphinx>=8.0']   # docs 组有 3 项不在 union_only 里
```

即：union_only 是「**docs 组的 22 项 + tasks 组的 invocations>=3.0**」，且 docs 组另有 3 项（`myst-nb` / `myst-parser>=4.0` / `sphinx>=8.0`）不在 union_only 中。F-086 自身列出的 23 项清单里已包含 `invocations>=3.0`（属 tasks 组而非 docs 组），**清单与括注自相矛盾**，读者只要逐项比对就会发现。独立的 PyPI 侧佐证同样否定该括注：mystx 0.3.7 的 `requires_dist` 中 `sphinx>=8.0` / `myst-parser>=4.0` / `myst-nb` 归属 `extra == "docs"`，而 `invocations>=3.0` 不在 docs extra 中。更严重的是，这个错误括注会误导 I-5 的根因判断——真实的分叉是「**tasks 组的包被错误投影进 dev 组的展开并集，同时 docs 组有 3 项核心包未进入 dev 组**」，是一个**双向的投影错位**，而非单向的「复制了 docs 组」。

**修正建议**：
在 `facts.md` F-086 中删除括注「即 docs 组的全部条目」，改为「并集独有 23 项 = docs 组 22 项 + tasks 组的 `invocations>=3.0`；同时 docs 组另有 `myst-nb` / `myst-parser>=4.0` / `sphinx>=8.0` 3 项不在并集内」；在 `insights.md` I-5 现象段同步补入这 3 项的缺席事实（当前该段未提及）；在 `e-stage-pattern.md` §5.2/§5.3 的 F 引用保持不变但复核 C2 主张「冗余不是缺陷，缺真源才是」是否仍被证据支撑（经复核**仍成立**，因为分叉的双向性反而更强地支持该主张，无需改写主张本身）。

**严重度**：P1

**修正后应达到的验收标准**：
1. `facts.md` 全文检索「即 docs 组的全部条目」零命中；
2. F-086 的来源列同时给出 `union_only - docs` 与 `docs - union_only` 两侧差集的实际输出；
3. `insights.md` I-5 现象段出现「docs 组有 3 项不在 dev 组展开并集内」这一事实；
4. 修正后 I-5 与 C2 的核心主张（声明面无权威源）经复核仍然成立——若因修正而动摇，须在本条审查记录中说明并触发 C2 主张复审。

### V-6 影响分级失真：invoke 与 invocations 被并列，实际失败语义相反

**质询**：
- `insights.md` I-2 现象段第 75 行原文：「`src/mystx/tasks/docs.py:34` 为 `from invoke import Collection, Exit, task`，`:37` 为 `from invocations import docs as _inv_docs`（该行带 `try/except ImportError` 包裹，由 `_HAVE_INVOCATIONS` 标志位控制）；**F-041 据此判定 `import mystx` 的导入链包含 `invoke` 与 `invocations`**」。

**风险**：

```python
# src/mystx/tasks/__init__.py:24    ← 无任何保护
from invoke import Collection

# src/mystx/tasks/docs.py:34        ← 无任何保护
from invoke import Collection, Exit, task

# src/mystx/tasks/docs.py:36-41     ← 有保护
try:
    from invocations import docs as _inv_docs
    _HAVE_INVOCATIONS = True
except ImportError:
    _inv_docs = None
    _HAVE_INVOCATIONS = False
```

`invoke` 缺失 = **硬失败**，`import mystx` 直接抛 ImportError；`invocations` 缺失 = **软失败**，仅 `browse/tree/doctest` 功能降级、包本身可正常 import。把两者并列会让老板视角的决策者**误判修复优先级与影响半径**——按当前表述，投入成本最低的「把 invocations 移出 tasks 组」看起来像是能解决问题，实际上完全不动最痛点。老板真正需要知道的是：**任一硬失败依赖缺失就会让主题加载整体失败，而失败会以「主题加载异常」形式出现，不是清晰的依赖缺失提示**（`insights.md` 第 93 行已提到这一点，但未与 invoke/invocations 的分级挂钩）。

**修正建议**：
在 `insights.md` 第 75 行与第 82 行把二者拆为两句话并显式标注失败语义——「`invoke`（`tasks/__init__.py:24`、`tasks/docs.py:34`）**无 ImportError 保护，缺失即导致 `import mystx` 硬失败**；`invocations`（`tasks/docs.py:37`）**有 try/except 保护，缺失仅使 browse/tree/doctest 功能降级**」；在 I-2 影响段第 90 行补一句量化结论——「**只装 `mystx[docs]` 时 docs 组 25 项不含 `invoke`（实测：docs 组无 invoke / invocations），因此该安装路径下 `import mystx` 必然失败**」；在 `e-stage-pattern.md` §5.3 C3「最小可安装单元从未被验证」的依据列补入 docs 组不含 invoke 的实测事实。

**严重度**：P1

**修正后应达到的验收标准**：
1. `insights.md` I-2 的现象段与 Why 1 中，invoke 与 invocations 出现在**分开的句子**中，且分别带有「硬失败/无保护」与「软失败/有保护」的显式限定；
