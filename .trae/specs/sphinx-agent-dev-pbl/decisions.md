## 四、DQ-1：LLM SDK 统一还是抽象？

### 决策

**统一使用 `openai` Python SDK；通过 `LLM_BASE_URL` 环境变量参数化切换到任何 OpenAI 兼容端点（含本地 ollama）。不引入自研 provider 抽象层。**

```bash
# 同一份代码，只改 .env 即可换厂商
LLM_API_KEY=your-key
LLM_BASE_URL=https://api.openai.com/v1        # 或任何兼容端点
LLM_MODEL=gpt-4o-mini                          # 或 hunyuan / deepseek-chat ...

# 本地 ollama（无需 API Key，Key 填占位符）
LLM_API_KEY=ollama
LLM_BASE_URL=http://localhost:11434/v1
LLM_MODEL=qwen2.5:7b
```

### 依据（E — 萃取出的判据）

**判据：中间层的正当性 = 它消解的多厂商差异量 ÷ 它引入的间接层成本。**

- **消解量极小**：ollama、混元、DeepSeek、通义千问均已提供 OpenAI 兼容端点。"协议差异"这一原本需要中间层来抹平的东西，**已由厂商自己抹平了**。此时再写一层 `Provider` 基类 + `OpenAIProvider` / `HunyuanProvider` 子类，消解的是**已经不存在的差异**。
- **间接层成本高**：对零基础学生，多一层抽象 = 多一个"报错栈里出现我没写的文件"的困惑源；对教师 = 排错时要先判断"是 SDK 问题还是抽象层问题"。
- **教学价值错位**：自研 provider 抽象是**架构能力**的训练，属于 G2 之外的范畴。本项目 G2 的表述是"能调用 LLM API 实现最小可运行智能体"——**调用**，不是**抽象**。
- **可迁移性已足够**：`base_url` 参数本身就是教科书级的"配置与代码分离"范例，且与本项目 Task4 的 `.env` / `python-dotenv` 主题**同源**——原来"密钥管理"和"厂商切换"是同一个机制，这反而降低了认知负荷。

> **注**：`openai` SDK 在此场景下**不是"选择了某厂商"**，而是"选择了事实上的协议标准"。把它类比为"使用 HTTP 而不是自己定义传输协议"更准确。

### 被否选项

| 选项 | 为何否决 |
|---|---|
| 自研 `Provider` 抽象层 | 消解的是已不存在的协议差异；增加学生排错负担；偏离 G2 目标表述 |
| 按厂商分别给两套示例代码（如"混元版"/"OpenAI版"） | 代码分叉 → 班级内不通用 → 学生无法互相排障，违反协作学习设计 |
| 直接用 `requests` 手搓 HTTP 调用 | 让学生手写 `tools` schema 的 JSON 序列化与 `tool_calls` 解析，把教学重心从 **Agent Loop** 偏移到 **HTTP 细节**，与本项目核心考点冲突 |

### 可证伪信号（若出现则需重议）

- 交代的任一厂商端点**不再兼容** OpenAI `tools` 字段（尤其是 `tool_calls` 返回结构）→ 此时差异重新出现，中间层恢复正当性
- 学生在 Task4 出现**超过 30% 的比例**卡在 `base_url` / 模型名配置而非 Agent Loop 逻辑 → 说明"配置与代码分离"这一课的成本被低估，需前置到 Task1

### 回滚条件

出现上述任一信号时，改为**在 `agent.py` 内做一个 5 行的 `create_client()` 函数**（已以 `get_client()` 形式存在于模板中），而非引入完整抽象层。**回滚目标是把复杂度压回 5 行，不是把它抬升为架构。**

## 五、DQ-2：CI 部署平台选型

### 决策

采用**三档并行、默认第一档**：

| 档 | 方案 | 适用条件 | 产物 URL |
|---|---|---|---|
| **① 默认** | GitHub Pages（**学生个人账号**的仓库） | 机房可访问 github.com | `https://<学生用户名>.github.io/<仓库名>/` |
| **② 离线降级** | 内网 Git 服务（Gitea / GitLab 自建，或 `git init --bare` + `git daemon`） + 自托管 Actions runner | 机房无法访问 GitHub | `http://<内网地址>/<仓库名>/` |
| **③ 托管替代** | Read the Docs（**学生个人账号**，关联同一仓库） | 希望有稳定托管但不想管 CI 细节 | `https://<项目名>.readthedocs.io/` |

**共同约束（三档都适用）**：CI 步骤中必须包含 `sphinx-build -W --keep-going`，把文档警告视为错误——这是"文档—代码一致性"硬约束（spec.md I-2 修正项），**不因平台切换而豁免**。

### 依据（E — 萃取出的判据）

**判据：基础设施选型的排序目标不是"功能强弱"，而是"项目结束后资产归属谁"。**

- **Github Pages（学生账号）胜出的根本原因不是技术，是归属**：PBL 的最终交付物是学生的**作品集**。用学生本人账号，课程结束后仓库与站点仍然属于学生，可以放进求职材料。若用教师组织账号，期末一旦回收，学生手上只剩一个失效 URL。
- **且它同时消解了审批依赖**：教师账号建 Pages 可能涉及学校实名或组织管理员配合；学生个人账号则**零审批、零等待**。这直接服务于 NFR-1（教师拿到方案即可落地）。
- **RTD 降级为"托管替代"而非"CI 替代"**：RTD 会自动拉取仓库并构建，但它把 CI 配置变成了"平台内配置"，学生**失去了阅读 `.github/workflows/docs.yml` 的机会**。而那个 YAML 文件正是"文档即代码"（Task3 的核心认知）最好的教具。因此 RTD 只在学生不想管 CI 细节时启用。
- **离线档必须给出，且必须真能跑**：spec.md 已有 ollama 的离线降级（for LLM），但 CI 侧原只写了"自建 Read the Docs"——**自建 RTD 的运维成本对教师是不可承受的**。本次替换为"内网 bare repo + 自托管 runner"，因为机房通常已有 Git 服务，成本几乎为零。

### 被否选项

| 选项 | 为何否决 |
|---|---|
| 统一用教师/学校组织账号建 Pages | 审批链路长；期末回收破坏学生资产归属；与 NFR-1"无需额外查资料即可落地"冲突 |
| 统一用 RTD（含学生账号） | 让学生跳过 CI YAML 编写，既丢失 Task3 的核心教具，也使 TR-3.1"检查 Actions 运行记录"失去验证对象 |
| 只在本地 `sphinx-build` 不做部署 | 直接违反 FR-7"须列出已部署 URL"与 AC-3 的 Evidence 要求 |

### 可证伪信号

- 机房实测可访问 github.com 但**登录态无法保持**（如需要反复 SMS 验证）→ 此时学生账号路径的实际成本高于组织账号，应翻转为默认 ①=组织账号 + ②=离线
- 内网 Git 服务不存在且教师无法自建 → 离线档 ② 失效，须改回"本地构建 + 拷贝静态文件到共享盘"，并**相应下调 TR-3.1**（改为验证本地构建产物与共享盘 URL，而非 CI 绿）

### 回滚条件

平台切换**不影响** `docs.yml` 的内容与 `-W` 约束；回滚只需替换 `upload-pages-artifact` / `deploy-pages` 两个 action，其余步骤（checkout / setup-python / install / `sphinx-build -W`）**在三档中完全一致**。

> ✅ **该"回滚成本极低"本身就是选型的加分项**——它意味着教师在决定平台前不必反复权衡，可以先跑通再换。

## 六、DQ-3：元文档闭环的强制属性

### 决策（三档，非二选一）

**原问题"必做还是选做"是一个假二分——它把"这个闭环有没有教学价值"和"学生有没有 Token 配额"两个独立维度压成了一个开关。** 拆解为三档：

| 档 | 形态 | Token 成本 | 强制属性 | 覆盖 AC |
|---|---|---|---|---|
| **A. 核心必做**（教学化形态） | `draft_doc()` 工具 + **手工构造草稿样例** + 强制差异分析（`diff-notes.md` ≥3 条） | **零**（草稿为教师预置样例，不真实调 API） | ✅ **必做** | AC-4, AC-6 |
| **B. 全自动**（原形态） | 学生真实调用 LLM 生成草稿 → 审校 → 差异分析 | 中 | ⭕ **默认选做** | AC-4, AC-6（加分） |
| **C. 强制保底通道** | 配额耗尽 / 无外网时，用 **Task2 已产出的 `api-draft.md`** 与最终 `api.py` 做差异分析 | **零** | ✅ **满足 TR-6.2** | AC-6（AC-4 折半） |

### 依据（E — 萃取出的判据）

**判据：一个教学环节的"强制程度"，应取决于它的不可替代认知价值，而非它的实现成本。**

- **不可替代性检验**：Task6 想让学生得到的认知是——"**AI 看不到我代码背后的设计意图**"。这个认知的**触发条件是"看到 AI 误解我的代码"**，而不是"我的代码真的被 AI 读过"。因此**教师预置的草稿样例同样能触发它**，且触发质量更可控（教师可确保样例中确实存在 3 处典型误解）。
- **Token 成本是真实约束，但不该由"取消环节"来吸收**：原设计中"配额有限就全班共演一遍"（Task6 方案 A）实际上已把成本降到接近零，却仍被标记为"选做"——**成本已解决，属性却未更新**，这是原设计的内部不一致。
- **AC-4 的硬门槛决定了它不能是选做**：AC-4 是 `rubric`、阈值 ≥4、Evidence 为"元文档闭环实现 + 反思"。如果 Task6 选做，则**没做 Task6 的学生 100% 拿不到 AC-4**，而 AC-4 又是终结性评价 10% 的来源。选做环节承载必达标准 = 评估结构自相矛盾。
- **反过来，AC-6 早已有独立送达路径**：AC-6（元认知与反思）的 Evidence 包含 Git 提交历史与现场答辩，`diff-notes.md` 只是其中一环。因此 Task6 的**降级不应牵连 AC-6**——这正是档 C 的设计意图：**用 Task2 的开发文档差异顶替 AI 草稿差异，保持 AC-6 可达**。

### 诚实性红线（三档共同适用）

> 🚨 **若学生使用档 A（教师预置草稿），必须在 `diff-notes.md` 中如实标注"本次草稿来自教师预置样例，非我本人调用生成"。**
> **谎报为"我调用 AI 生成的"属于学术诚信问题，本项直接判 0。**
> 这条红线的存在是为了让降级**没有动机伪装成满配**——降级本身完全正当，伪装才不正当。

### 被否选项

| 选项 | 为何否决 |
|---|---|
| 干脆取消 Task6，AC-4 一并取消 | 会摧毁本项目的核心创新点（三学科真正咬合的唯一机制），并使 AC-4 失去存在意义，项目退化为"普通编程课 + 文档" |
| Task6 纯选做，AC-4 相应改为可选维度 | 评估标准随任务可选性浮动 = 不同学生的成绩不可比，课程无法持续开设（触碰 I-4 的 P0 结论） |
| Task6 必做且必须真实调用 API | 承认 Token 是真实约束；无外网机房直接无法开课，违反 Constraints 的离线降级承诺 |
| 用"教师统一生成一份草稿贴到群里" | 全班草稿相同 → 差异分析趋同 → 失去"发现我这个模块的误解"的个体性，退化为抄写练习 |

### 可证伪信号

- 若档 A 的预置草稿在**两届学生**中产生的差异分析条目高度重复（相似度 > 70%）→ 说明预置草稿未能触发个体化认知，档 A 的教学价值不成立，应改为"每组自选函数 + 教师现场生成一份"
- 若档 B 的实际完成率 > 90% 且教室网络稳定 → 说明 Token 约束被高估，可考虑把档 B 提升为默认必做，档 A 降为纯降级

### 回滚条件

三档之间**共用同一份 `diff-notes.md` 模板与同一套 TR-6.2 判定标准**（≥3 条差异：问题 + 原因 + 修正）。因此档位切换**只影响草稿来源，不影响评分口径**——这是刻意设计，确保教师可在一学期中途自由切换而不产生评分不公。

| **I-8** | 三个待决问题中，DQ-1 与 DQ-2 的"选项列表"都包含了技术上更强或更规范的方案（自研抽象层 / RTD） | 选型时以"技术规范度"排序，而非以"**项目结束后资产归属谁**"排序 | 若选 RTD 或教师组织账号，学生期末拿不到属于自己的作品 URL；若选自研抽象层，学生排错负担上升 | 把"归属"设为基础设施选型的**第一排序键**，技术规范度次之 |
| **I-9** | Task6 原被标记为"选做"，但其承载的 AC-4 是 rubric ≥4 的硬门槛 | "环节的强制程度"被误认为由"实现成本"决定；而 Token 成本其实已在方案 A 中被消解，属性却未同步更新 | 选做环节承载必达标准 → 未做者结构性失分 → 评估结构自相矛盾 | 强制程度应由**不可替代认知价值**决定；成本用**降级档**吸收，而非用"取消环节"吸收 |
| **I-10** | DQ-3 的"必做 vs 选做"二选一，实际对应的是三档实现形态 | 问题被表述为布尔开关，把"教学价值"与"Token 配额"两个独立维度压缩到同一轴上 | 无论选哪个都错：必做则无外网机房不可开课，选做则 AC-4 不可达 | 遇到"必做/选做"争议时，先拆维度；**多数"二选一"其实是"分档"** |

### G3 — 三条可迁移判据

| # | 判据 | 触发场景 | 反模式 |
|---|---|---|---|
| **判据 1** | 中间层的正当性 = 消解的多厂商差异量 ÷ 引入的间接层成本。当差异已被上游抹平时，中间层是净负债 | 技术选型中出现"是否要抽象一层"的争论 | **预防性抽象**：为"将来可能换厂商"而抽象，但厂商已提供兼容端点 |
| **判据 2** | 基础设施选型的第一排序键是"项目结束后资产归属谁"，不是技术规范度 | 教学/作品集类项目选择托管平台、账号主体 | **按规范度选型**：选了技术最优但学生拿不走的方案 |
| **判据 3** | 一个教学环节的强制程度取决于其不可替代认知价值；成本约束应转化为降级档，而非取消环节 | 某环节因成本/条件限制面临"要不要留"的决策 | **用删除吸收成本**：把成本问题误当作价值问题处理 |

### 反模式汇总（G3 要求）

| 反模式 | 症状 | 本项目中的对应 |
|---|---|---|
| 预防性抽象 | 为不存在的差异写适配层 | DQ-1 否决"自研 Provider" |
| 按规范度选型 | 选技术最优但资产留不住的方案 | DQ-2 否决"统一用 RTD/组织账号" |
| 用删除吸收成本 | 因成本高就砍掉教学环节 | DQ-3 否决"Task6 纯选做" |
| 降级伪装满配 | 用降级方案却不声明 | DQ-3 设"诚实性红线"，谎报判 0 |
