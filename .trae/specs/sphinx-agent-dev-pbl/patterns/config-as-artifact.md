# 可迁移模式：配置实物化（Config-as-Artifact）

> 从 R9（档 A 实物）、R10（配置文件实物）两轮实践中萃取。
> 适用场景：任何包含"让学生/用户照着敲一段配置"的教程、方案、手册。

---

## 触发场景

**适用于**：
- 教学材料 / 教程 / 部署手册中，含"在某某路径新建某某文件，内容如下…"
- 配置文件对**格式敏感**（YAML 缩进、JSON 引号、TOML 层级）
- 目标读者是**新手**，配置错误的报错信息**不指向真正原因**
- 该配置是**硬门槛**（错了整个流程跑不起来），而非可选项

**不适用于**：
- 配置本身就是**学习目标**（如"理解 CI 的 trigger 机制"），此时手打是必要的
- 配置极短且不易出错（如一行 `export FOO=bar`）
- 读者是熟手，能自行排查格式问题

---

## 核心做法（5 步）

1. **盘点"承诺"**：全文搜出所有"新建/创建/写入 X 文件，内容如下"的句子，
   逐条列出 **文件路径 → 所属步骤 → 是否硬门槛**。
2. **追问实物**：对每一条，问 **"这个文件现在在磁盘上存在吗？"**
   ——不是"文档里写了内容"，而是**有一个可以直接 `cp` 的文件**。
3. **造实物**：为每个硬门槛配置造一个实体文件，放在统一的 `starters/` 之类目录下。
4. **双向对齐**：实物内容与手册正文**逐字一致**（NFR-4 级要求）。
   加一条自动化检查：抽取手册代码块 vs 实物文件做 `diff`。
5. **保留手打路径**：在手册里同时写"复制现成文件（推荐）"和"手写也完全可以"，
   并说明**手打的风险**（缩进/格式）与**学习价值**（理解结构）。
   ——不要用"复制"替换"手打"，而是**并列**。

## 反模式（≥3 个，均来自实际教训）

| # | 反模式 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | **只在文档里写出内容，不造实物** | 学生必须手工誊抄；YAML 缩进错了 CI 不跑，报错不指向原因，卡在与教学目标无关的地方 | 凡"完整文件内容"都配实物 |
| 2 | **实物与手册正文各改各的** | 两处说法漂移（NFR-4 违规）；学生复制的与老师讲的不一致 | 加自动 diff 检查；把"手册代码块 = 实物文件"变成可验证约束 |
| 3 | **造了实物就删掉手打路径** | 剥夺"理解配置结构"的学习机会，变成纯复制粘贴 | 两条路径并列，不互相替换 |
| 4 | **忽略实物的传递性依赖** | 只发 `docs.yml` 不发 `requirements.txt` → CI 的 `pip install -r` 失败 | 造实物时要顺藤摸瓜：**配置引用了什么，就要一起提供什么** |
| 5 | **实物目录与既有关卡混淆** | 把手热身用的最小依赖清单当成正式项目的依赖清单 → CI 缺 furo 缺 openai | 实物目录要**显式声明与邻近目录的区别**（见下方"检验标准"） |

---

## 检验标准

做完怎么知道做对了？

- [ ] 全文检索"内容如下"，每一条都能指出**对应的实物文件路径**
- [ ] 每个实物文件能被**自动化 diff** 校验与手册正文一致（可接 CI）
- [ ] **传递性依赖闭合**：实物所引用的其他文件，也都有实物
  （例：CI 引用 `requirements.txt` → 必须有 `requirements.txt` 实物）
- [ ] 实物目录的 README 里**显式写明"与邻近目录的区别"**
  （例：`starters/` 与 `warmup-docs/` 的依赖清单不可互换）
- [ ] 手册里"手打路径"仍然存在，且说明了风险与价值
- [ ] 一个不看源码的人，只照手册 + 实物目录，能一次跑通

## 跨场景迁移示例（非当前领域）

**场景：软件交付文档 / 运维手册**

一个"部署到 Kubernetes"的内网 wiki，写着"新建 `deployment.yaml`，内容如下…"。
运维新手复制时把 `resources.limits` 的缩进搞错，Pod 一直 Pending，
报错只说 `Insufficient cpu`——查了半天才发现是 YAML 把 limits 挂到了错误层级。

→ **同一模式**：把 `deployment.yaml` 放进仓库的 `deploy/` 目录，
wiki 只写"`kubectl apply -f deploy/deployment.yaml`"，并保留"想理解就自己看"的路径。
**配置实物化，跨领域完全成立。**

**场景：数据科学教学**

"请新建 `config.yaml` 配置实验超参"——学生把 `learning_rate` 写成了 `learning-rate`，
训练脚本静默用了默认值，实验白跑。

→ 同上：给 `configs/` 实物 + `--config configs/base.yaml`。

## 与既有模式的关系

- 本模式是 **I-15（"发一份 XX"是祈使句不是交付物）** 的工程化落地：
  I-15 给出**判据**（承诺必须有实物），本模式给出**做法**（怎么造、怎么验收）。
- 本模式与 **NFR-4（跨文档一致性）** 咬合：实物与手册正文的一致性，
  正是 NFR-4 要求"操作性事实逐字一致"的具体体现。
- 本模式的检查项 **可直接并入 `scripts/audit_consistency.py`**：
  "抽取手册代码块 vs 实物文件 diff" 是脚本化的天然对象。
