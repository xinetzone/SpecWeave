## 三、教师如何替换为真实截图

1. 按第二节表格的「文件名」列拍摄真实画面，**同名覆盖**本目录下的 PNG
2. 手册中的图片引用**已经写好**（如 `![venv 激活成功](shots/S1-1-venv激活.png)`），
   覆盖文件后无需改动任何 Markdown
3. **6 个按设计留白的位点（第五节）无需补图**——它们在手册中已是"文字规格 + 验收标准"块；
   其中 S7-1/S7-2/S7-3 是**给学生/教师现场填的**，不是给你补的
4. 删除本文件第二节的「内容来源」列，或把整张表换成你的实际截图记录
5. **建议在课程跑完一轮后再做**——学生真实案例（尤其 S6-3 / S7-5）说服力远高于教师自制演示
6. 跑完一轮后，**把 S7-1/S7-2/S7-3 的真实照片补进手册**（那时它们才真正存在）

## 四、拍摄建议（替换时参考）

### 通用要求
- **分辨率**：1920×1080 或更高，与现有示意稿保持一致（当前均为 1440×900）
- **格式**：PNG（截图类内容比 JPG 清晰）
- **隐私脱敏**：涉及 API Key、用户名、邮箱的画面必须打码
- **窗口整洁**：关闭无关标签页、通知弹窗、聊天窗口

### 各类画面的要点

| 类型 | 要点 |
|---|---|
| **终端截图** | 确保提示符、命令、输出都在画面内；重要输出可用红框标注 |
| **编辑器截图** | 左侧文件树 + 编辑区同时可见，便于学生对照 |
| **浏览器截图** | 保留地址栏（能看出是 `file://` 还是 `https://`） |
| **对比类截图** | 如 S5-4，用左右分栏或箭头标出差异处 |

### 关键画面提醒

- **S1-1（venv 激活）**：学生最容易困惑的一步，务必让 `(.venv)` 提示符清晰可辨。
  **强烈建议**连 `where python` 的输出一起截图——这是判断激活是否成功最可靠的方法
- **S3-6 / S5-3**：学生「成就感来源」的关键画面，建议截取完整美观的状态
- **S6-3（差异分析）**：Task6 核心产出，建议用真实学生案例（脱敏后）。
  **画面须包含 `diff-notes.md` 开头的「草稿来源声明」**——该声明是 TR-6.3 的验证对象
- **S4-1（密钥配置）**：`.env` 内容必须打码或用占位符示意
- **S7-5（设计对照）**：建议左右分栏呈现 `api-draft.md` 原本设想与最终代码，
  让「认知变化」一眼可见

## 五、按设计留白的 6 个位点（**不是遗漏**）

> 这 6 个位点**故意不预置图片**。它们分成三类，各有明确理由：

| 编号 | 所属任务 | 画面内容 | 留白理由 | 手册中的替代内容 |
|---|---|---|---|---|
| S7-1 | Task7 | 路演现场演示画面 | **真实课堂照片**——合成等于伪造"课已开过" | 拍摄要点 + 合格判据 |
| S7-2 | Task7 | 答辩场景/记录表 | 记录表须**当场填写**；预置"填好的表"诱导背答案 | 指向 `SCORING-SHEET.md` §六 |
| S7-3 | Task7 | 反思报告文档 | **学生本人产出**；预置范文会让所有人写成一样 | 5 档 rubric + 自检法 |
| S6-1 | Task6 | `draft_doc` 函数实现 | **仅档 B 需要**；预置会让档 A/C 学生以为漏看 | 文字规格 + 验收标准 |
| S6-2 | Task6 | AI 生成的草稿 | **预置"标准草稿"会摧毁差异分析过程** | 三种典型误解预告 |
| S3-7 | Task3 | 内网 Git 仓库页 | **各校界面不同**（Gitea/GitLab）；统一模板必然误导 | 3 条自核对判据 |

**合计 37 个截图位 = 31 个已填（可预填项全覆盖）+ 6 个按设计留白。**

> 📌 **为什么"留白"比"填满"更正确**——三条理由（自上而下越来越强）：
>
> 1. **误导档位**：S6-1/S6-2 只有档 B 用得上。给了图，走档 A/C 的学生会去找一个
>    自己根本不需要的函数，白费时间。**给不该给的图 = 制造假需求。**
> 2. **以校为限**：S3-7 的内网 Git 界面因校而异。任何一张具体截图都会让
>    其他学校的教师怀疑"我是不是配错了"。**给一张图 = 只对一个学校负责。**
> 3. **污染证据链**（最重要）：S7-1/S7-2/S7-3 记录的是**真实发生过的教学现场与学生作品**。
>    合成这些图，等于在材料里植入"这门课已经开过、已有学生产出"的**虚假证据**。
>    教师可能因此以为"已有范例"而不再收集真实作品——**这才是最深的伤害**。
>
> 🎯 **判断原则（可迁移到其他材料）**：
> **一个画面若承担"证据义务"（证明某事真实发生过），它就不能被合成。**
> 只有"操作演示"性质的画面（终端输出、代码、界面）才可以合成。

> 📌 **S3-7 / S7-5 的由来**：
> - `S7-5` 由决策 session `sc-20260929-open-questions` 新增，用于支撑 AC-6 的过程证据。
>   它同时服务两个目的——既是 Task7 答辩的自测材料，也是 Task6 档 C 差异分析的证据来源
> - `S3-7` 由 GitHub 个人账号约束（DQ-2）引入，对应「离线档」路线

## 七、无截图时的替代方案

即使一张图都没有，手册**仍然可用**。因为：
- 每个步骤都有**完整的文字说明 + 可复制的命令**
- 每个任务都有**常见报错表**，比截图更能解决实际卡点
- 截图位是「体验优化」，不是「功能必需」

**特别地**：当前所有示意图都由 HTML 合成，若某张图与你的实际环境差异过大（如
依赖版本号），**直接删掉手册中该处的图片引用即可**——不会破坏文档结构。
