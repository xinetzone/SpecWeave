## 第二部分：I — 洞察落地路径与边界条件

> G2 门要求：洞察 ≥3 条，每条含完整四元组（陈述 / 证据 / 反常识 / 行动）。本节在对抗审查修正**之后**产出，确保洞察建立在被攻击过、更稳固的方案上。

### 洞察 I-1：文档是"理解的检验"，不是"理解的来源"

- **陈述**：把文档写作的位置前移（先写 API 签名与用法文档，再实现代码），其教学价值远高于事后补文档。
- **证据**：V 攻击 A-1 指出原 F 推导存在因果倒置风险；教育学的"生成效应"（generation effect）表明主动产出比被动接收记忆更深。
- **反常识**：挑战了"先做完再写文档"的行业默认流程——正是这个默认流程，让文档沦为负担与粉饰。
- **行动**：Task2 调整为"文档先行"——学生先用 MyST 写出设想的 API 与用例，再进入 Task4 实现；实现与文档不符处即为理解盲点的显影。
- **边界条件**：此策略对**探索性代码**（尚未定型）不适用——探索阶段可先写"设计笔记"而非正式文档。

### 洞察 I-2：融合的深度取决于"依赖方向"，而非"内容并列"

- **陈述**：三学科真正咬合的标志，是彼此形成**双向依赖**——文档约束代码设计，代码反过来生成文档，教育学目标（元认知）由此自然达成，而非靠"加一节反思课"。
- **证据**：spec.md 原设计（AC-4）中元文档闭环是唯一让三者互相咬合的机制；V 攻击 A-6 暴露了若不依赖则评价失真。
- **反常识**：挑战了跨学科 PBL 常见的"拼盘式"融合（语文写文案 + 数学做图表 + 信息科技做 PPT）——那只是**内容并列**，无依赖关系，学生感受不到融合的必要性。
- **行动**：以"文档—代码一致性"作为项目的硬约束（CI 中校验 autodoc 能否成功构建），使文档与代码**互为验收条件**。
- **边界条件**：该约束要求项目规模足够小（建议 ≤1500 行），否则一致性维护成本超过教学收益。

### 洞察 I-3：AI 协作的引入顺序决定能力增损

- **陈述**：必须**先手写、后 AI 协作**，顺序颠倒会导致基础表达能力发育不良。
- **证据**：V 攻击 A-8 的二阶效应分析；A-2 指出 AI 草稿质量可能不可用。
- **反常识**：挑战了"AI 时代应尽早拥抱工具"的直觉——在**能力建构期**，工具提效反而抑制能力形成。
- **行动**：Task2（手写 MyST）必须在 Task6（AI 生成文档草稿）之前，且 Task6 要求记录"AI 草稿 vs 我的最终版"的差异清单。
- **边界条件**：对已有扎实写作基础的高年级/大学生，可放宽顺序，甚至直接以 AI 草稿起始做批判性编辑训练。

### 洞察 I-4：可评估性是创新教学法的隐藏硬约束

- **陈述**：任何引入 AI 的教学设计，若不设计"过程证据"，其评估结果都不可信，课程也无法持续开设。
- **证据**：V 攻击 A-6 判定为 P0；Git 提交历史天然携带过程信息。
- **反常识**：通常认为"评估"是教学设计的收尾环节，实际上它应作为**前置约束**参与设计——否则好方案会死在"没法给分"上。
- **行动**：在 tasks.md 中把"多次原子提交"作为交付要求，并将"现场口头解释任一函数"编入路演环节。
- **边界条件**：小班（≤15 人）可行；大班需改为抽查 + 同伴互评交叉验证。

### 边界条件汇总表（落地约束）

| 维度 | 适用边界 | 越界后的处置 |
|---|---|---|
| 项目规模 | ≤1500 行代码、≤8 周 | 超规模则 Task6 元文档闭环改为选做 |
| 学生基础 | 具备 Python 函数/类/异常 + 命令行 | 不足则插入 2 课时前置微课 |
| 网络环境 | 可访问 pypi 与 LLM API | 无外网：ollama + 内网静态托管 |
| 班级规模 | 小班 ≤15 人（口头答辩可行） | 大班：抽查答辩 + 同伴互评 |
| API 预算 | 每小组每学期有稳定配额 | 配额有限：Task6 全班共演一次 |
| Sphinx 版本 | Sphinx ≥7.0（`sphinx-quickstart` 行为） | 低版本需调整初始化参数 |

## 第四部分：脚手架构建的 F→V（session sc-20260929-sphinx-agent-pbl 第三轮）

> 对象：`warmup-docs/` 可复制脚手架（Task0 配套产物）

### F — 最小可跑骨架的不可约要素

**假设剥离**：❌ 需要 venv（学生不装环境）｜❌ 需要 pip（依赖预置）｜❌ 需要 Git（Task1 才引入）｜❌ 需要理解 conf.py（学生不该看）

**公理**：
1. `conf.py` 必须存在且能定位 source 目录与 master doc
2. 源文件必须能让构建器识别出内容
3. **除以上两项，一切皆可省**

**重构结果**：学生文件区（只看 `index.md`）+ 教师配置区（`conf.py`，标注"别动"）。
**附带决策**：不引入第三方主题（furo 需额外安装），改用内置 `alabaster`——**每多一个依赖即多一个失败点**。

|---|---|---|---|---|

### 🔴 S-4（P0）：虚拟环境不可跨机器复制

**实测证据**：`pyvenv.cfg` 硬编码创建时的绝对路径：
```ini
home = <原机器的Python安装目录>
executable = <原机器的Python解释器路径>
```
将 `home` 指向不存在路径后，运行 `.venv/Scripts/python.exe` 报：
```
did not find executable at 'D:\...\python.exe'（退出码 103）
```

**原设计的致命缺陷**：教师指南原写"把含 `.venv/` 的文件夹复制给学生"——**在任何 Python 安装路径不同的机器上必然失败**。这是会在课堂上 100% 炸掉的问题。

**修复（三条）**：
1. **构建脚本内置自愈**：不只看文件是否存在，而是**实际执行 `python -c "import sphinx"` 验证可用性**，逐候选回退（`.venv` → `python3` → `python` → `py`）
2. **教师指南改写**：明确"分发时**不要带 `.venv/`**"，给出"每台机各自建环境"与"直接用系统 Python"两种方案
3. **失败时给降级路径**：脚本找不到可用解释器时，提示改用在线 Markdown 预览器（承接 Task0 原有降级方案）

### 洞察 I-5（脚手架场景）：脚手架的价值在于"消除失败面"，而非"提供功能"

- **陈述**：脚手架的 KPI 不是功能完备，而是**学生失败点的数量**；每个多余依赖、每处环境假设都是一个潜在失败点。
- **证据**：S-4 实测（跨机 venv 必坏）；主题选择上放弃 furo（少一个 pip 依赖）。
- **反常识**：通常认为脚手架要"给得越多越省事"，实际上**给得越多越容易崩**——内置主题比漂亮主题更适合零基础场景。
- **行动**：`requirements.txt` 只保留 4 个必需包；`conf.py` 主动 `suppress_warnings`；脚本用"实测可用性"而非"文件存在性"判断环境。
- **边界条件**：适用于"首次接触、零基础、时间受限"的场景；一旦学生具备排障能力（如 Task1 之后），即可引入更多依赖与美观主题。

## Part 5 — Task4/5 代码模板的 F→V→I→C

> 增量目标：把"抄写成本"降到零，让学生专注在 **Agent Loop 的理解与修改**。
> 这是唯一直接决定"项目能否跑通"的缺口。

### F — 最小可填骨架的不可约要素

**假设剥离**（每剥离一层，问"没有它学生还能不能写出来？"）：

| 假设 | 剥离结果 |
|---|---|
| ❌ 需要学生自己写 import / 客户端初始化 | **可剥离**——是样板代码，与学习目标（Agent Loop）无关 |
| ❌ 需要学生自己写命令行交互入口 | **可剥离**——`input()` 循环是噪声，不是考点 |
| ❌ 需要学生自己理解 `openai` SDK 的构造参数 | **可剥离**——延迟初始化 + 报错友好化即可 |
| ❌ 需要学生自己写 `ask_simple()` | **可剥离，且必须剥离**——它是 Task4 失败时的保底路径 |
| ✅ 需要学生自己写工具函数 | **不可剥离**——docstring 质量直接决定模型是否调用 |
| ✅ 需要学生自己写工具描述列表（schema） | **不可剥离**——"给模型写文档"是文档工程的迁移点 |
| ✅ 需要学生自己写分发逻辑 | **不可剥离**——理解"函数名字符串 → 真实函数"的映射 |
| ✅ 需要学生自己写 Agent Loop | **不可剥离**——**这是整个项目的核心考点** |

**公理**：
1. 凡是"与 Agent Loop 无关的样板"，一律预填
2. 凡是"决定理解深度的逻辑"，一律留空**并配可执行提示**
3. **留空处必须能独立测试**——不能出现"必须全部写完才能跑一次"

**重构结果 → 三区划分**：

| 区 | 内容 | 理由 |
|---|---|---|
| 🟢 预填区 | imports、`get_client()`、`ask_simple()`、`main()` | 样板，剥离后学习价值不降 |
| 🔴 留空区 | `get_time`、`calculator`、`build_tools`、`call_tool`、`ask` | 全部考点，13 处 TODO 可检索 |
| 🟡 引导区 | 每个留空函数的 docstring + 提示 + 手册章节引用 | 给方向不给答案 |

### 🔴 T-1（P0）：延迟初始化的意图被模块级副作用抹掉

**实测证据**：

**原设计的自相矛盾**：`README.md` 第 84 行白纸黑字写着——

> 💡 模板做了**延迟初始化**：即使 `.env` 还没配好，`import agent` 也不会崩。


1. **真正的延迟初始化**：删除模块级 `client = OpenAI(...)`，改为 `get_client()` 内部首次调用时才构造并缓存到 `_client` 全局变量
2. **报错信息补齐可操作步骤**：`ValueError` 从"未配置 LLM_API_KEY"扩写为分点列出"检查 `.env` 是否存在""检查键名是否为 `LLM_API_KEY`""检查当前目录是否在项目根"，并统一 `ask()` 与 `ask_simple()` 的报错文案（原先两处不一致，学生看到同一个问题有两套说法会困惑）

**复验**：修复后 `import agent` 静默成功，未配密钥调用 `ask_simple()` 才抛错，报错信息含 3 条排查指引。

### I-6（模板场景）：模板的留空边界 ≠ 代码难度边界，而是"考点边界"

- **陈述**：决定一个函数该不该留空的标准，**不是它难不难写，而是它是不是考点**。样板代码即使难写也要预填；核心逻辑即使只有一行也要留空。
- **证据**：`get_time()` 实现只有 1 行（`datetime.now().strftime(...)`），但它是**必须留空**的——因为学生要亲手为它写 docstring，而 docstring 是模型决定是否调用的唯一依据，这是"文档影响行为"的直接体感。相反 `main()` 有 20 余行（`input` 循环 + 异常分支），却**完全预填**。
- **反常识**：直觉认为"简单的让学生自己写，复杂的帮他写好"；实际应按**考点密度**切分——若按难度切分，学生会在 `main()` 的 `input` 循环里耗掉半节课，却在最有价值的 docstring 上照抄了模板答案。
- **行动**：`get_time()`、`calculator()` 等短函数全部留空并配 docstring 要求；`main()`、`get_client()`、`ask_simple()` 全部预填。
- **边界条件**：此原则依赖"考点边界已被明确声明"。若教学目标模糊（如开放式课题），盲目留空会让学生不知道写什么，此时应转为"给可运行示例 + 让学生改造"的模式。

### I-7（模板场景）：模板的验收标准是"可独立测试"，不是"可运行"

- **陈述**：一个好的编程模板，应保证**每个留空函数都能被单独测试**，学生填一个就能验证一个；"必须全写完才能跑一次"的模板会让学生在长反馈延迟中失去方向。
- **证据**：模板设计中 `ask_simple()` 被**刻意预填**——它让 Task4 阶段的学生在 `ask()` 还没实现时，也能跑通完整命令行流程（把 `ask()` 末行临时改成 `return ask_simple(question)` 即可）。T-2/T-3 实测证明工具函数可脱离 Loop 独立验证。
- **反常识**：通常认为"给一个半成品反而添乱，要么全给要么全不给"；实际上**半成品的价值恰恰在于它把长反馈链切成短反馈链**——学生每完成一个 TODO 就获得一次"跑通了"的正反馈。
- **行动**：`README.md` 明确要求学生"**不要一次写完所有 TODO 再测试**——出了错你会很难定位是哪个函数的问题"；`README.md` 步骤 3 专门给出 Task4 阶段的临时降级写法。
- **边界条件**：适用于**有明确分层结构**的任务（函数边界清晰）。若任务本身是强耦合的整体（如一个不可分割的算法），切分反而会伪造出虚假的独立性，此时应改用"给可运行基线 + 让学生逐步替换内部实现"。

### 🔴 V-1 详情（P0）：方式 B 的分数加不出 100

- **现象**：`SCORING-SHEET.md` §五"档 C · 方式 B"表格列出 `40 + 24 + 24 + 5 + 5 + 5`，

### I-9（教师包场景）：评分表的正确性是一种"信任货币"

3. **留白本身可以是教学信号**——"这里需要你自己产出"与"这里忘了填"对学生是两种不同的信息。

**自下而上重构**：由公理 2 推出——**"真实课堂照片/学生作品"必须留白**（合成图无法履行证据义务，且污染证据链）。由公理 3 推出——**留白必须显式标注为"设计留白"**，否则会被读成疏漏。由公理 1 推出——**优先补"学生无法预知画面"的位点**。

### 🔴 V-1 详情（P0）：给学生的第一张构建截图，展示的是"第二次构建"

- **现象**：`S0-5`（Task0 构建成功，面向**零基础学生的第一个成功画面**）中，
  第 2 行写的是 `loading pickled environment... done`。
- **根因**：我从演示环境里顺手复制了一段构建输出，而演示环境**已经构建过多次**，
  因此命中了 Sphinx 的增量构建分支。但学生**第一次**构建时，Sphinx 会走"全新环境"分支，
  输出的是 `loading translations [zh_CN]... done` + `making output directory... done`。
- **后果**：这张图是 Task0 的**核心成就画面**——它的全部意义是"让学生确认自己成功了"。
  学生若逐行核对，会发现**自己屏幕上没有这一行**，从而怀疑"我是不是做错了"。
  **在最不该出问题的位置（第一个成功体验）制造了怀疑。**
- **修复**：清空 `_build/` 后重新真实构建，用实测输出替换。
- **复验**：重跑 `sphinx-build`，确认首次输出为 `[new config] 1 added, 0 changed, 0 removed`
  且**不含** `pickled environment`；重渲染后目视核对通过。

### 🔴 V-6 详情（P0）：留白 ≠ 不给标准

- **现象**：初版对 6 个留白位点只写了"此项需教师/学生自填"，并说明为什么不预填。
- **根因**：我把"决定不填图"当成了工作的终点。但**留白的目的是把产出权交给使用者，
  不是把标准也一起交出去**——没有标准的留白，等于把"做成什么样算对"也丢给了使用者。
- **后果**：`S7-3`（反思报告）最严重——教师没有 rubric，只能凭感觉打分，
  而 `review.md` 3.5 节**明明有 5 档锚点**；`S7-2`（答辩）同理，
  而 `SCORING-SHEET.md` §六**有现成的记录表**。
  **我在留白处丢掉了已经在别处写好的标准。**
- **修复**：每个留白块补"合格标准 / 验收判据"，并**明确指向已有文档**
  （S7-2 → `SCORING-SHEET.md` §六；S7-3 → `review.md` 3.5；S3-7 → 3 条自核对判据；
  S6-1/S6-2 → 函数规格 + 三种典型误解）。
- **复验**：6 个块逐一检查是否含可执行的验收语句，且指向的文档锚点可达。

### I-10（截图位场景）：不是所有留白都该被填满——留白分"缺"与"设计"

- **陈述**：对剩余 16 个截图位按"教师能否 2 分钟内自拍"分类，得到 **10 : 6** 的分裂。
  **该补的是那 10 个**（终端/编辑器/浏览器，内容已存在于演示环境）；
  **不该补的是 6 个**——3 个是真实课堂照片/学生作品（合成 = 伪造证据），
  2 个仅档 B 需要（填了制造假需求），1 个各校界面不同（填了以校为限）。
- **证据**：分类表（Part 7 F 阶段）——10 个位的画面载体全是"终端/编辑器/浏览器"
  且内容源已在演示环境（真实 `agent.py` 230 行、真实 `_build/html/`、真实 `index.md`）；
  另 6 个的载体是"照片"或"学生产出"，演示环境**不存在**此类素材。
- **反常识**：直觉认为"截图位没填就是没完成，填满才叫完成度 100%"。
  **实际相反**——S7-1 若用合成图，等于往教学材料植入"这门课已经开过了"的假证据；
  S7-3 若用合成文本，会让教师误以为有了范文而不再收集真实学生作品。
  **补上这 6 个，不是补齐，是污染。**
- **行动**：只补 10 个可复用位点；对 6 个留白位点，**不合成，改为就地写"文字规格 + 验收标准"块**，
  并说明不预填的理由。同时把 `shots/README.md` 的完成度口径从"已填/N"改为
  **"31/31 可预填项已完成 + 6 项按设计留白"**。
- **边界条件**：此原则依赖"能区分证据性画面与演示性画面"。
  若某材料**全部**是演示性内容（如纯工具手册，不涉及真实教学记录），则无留白必要，填满即正确。
  反之，若某材料**全部**是记录性内容（如实验报告模板），则一张都不该预置。

### I-11（截图位场景）：审核的终点不是"消除所有分歧"，而是"每条分歧都有裁决"

- **陈述**：对抗审查的正确终止条件是**每一条攻击都得到明确裁决**（采纳 / 驳回 / 暂缓），
  而不是"修改数量达到某个标准"。**驳回一条攻击与采纳一条，是同等的产出。**
- **证据**：本轮 9 条攻击中，V-3（`openai 3.20.0` 版本号可疑）**被 venv 实测驳回**——
  该版本号真实存在（3.x 系列）。若按"凡攻击必采纳"的习惯处理，
  我会把一个**正确的版本号改成错误的**，把审查变成破坏。同理 V-5/V-9 经判断后保留原样。
- **反常识**：通常把"对抗审查"理解为"找问题、改问题"，
  于是**把"修改条数"当成审查质量的指标**——这恰好 incentivize 制造无用改动。
  真正的质量指标是**裁决覆盖率**（每条攻击都有结论且附依据）。
- **行动**：V 阶段记录表**必须含"命中？/ 级别 / 处置"三列**，
  处置可填"已修复""驳回（附实测依据）""保留（附理由）"；禁止只列攻击不给裁决。
- **边界条件**：适用于**可验证**的争议（版本号、命令输出、算术、链接——能实测）。
  对**不可实测的审美/风格争议**（如"这段文字太长"），"驳回"应慎用——
  此时应转为"记录分歧、交由使用者定夺"，而非作者单方裁决。
