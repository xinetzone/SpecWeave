## 模式 1：企业级 AI Agent 平台 9 维度选型评估框架

**模式 ID**：P-AGENT-SELECT-001（v2.0，V阶段采纳「供应商锁定风险」维度后升级为9维度）

> **📎 可直接套用工具**：独立评分卡文件（含空白打分表+加权公式+决策矩阵+PoC验证清单+反模式）：
> [P-AGENT-SELECT-001-agent-platform-selection-scorecard.md](../../../.agents/docs/retrospective/patterns/methodology-patterns/governance-strategy/P-AGENT-SELECT-001-agent-platform-selection-scorecard.md)
>
> 使用方法：复制评分卡文件到你的项目目录，填写候选平台信息和分数，自动得出加权总分和决策建议。

### 触发场景

企业需要从 3+ 个候选方案中选择 AI Agent 平台/框架时（采购决策、技术选型、PoC 评估）。

### 核心步骤

9 个评估维度（权重合计 100%），每个维度包含：维度名称 / 权重建议（%） / 1-5 分评分标准（1分最差-5分最优） / AgentKit 示例得分。

| 序号 | 维度名称 | 权重建议 | 1分（最差） | 3分（中等） | 5分（最优） | AgentKit 得分 | 得分依据 |
|------|---------|---------|------------|------------|------------|--------------|---------|
| 1 | 治理能力 | 20% | 治理模块缺失，仅有编排能力，无鉴权/观测/评测 | Identity+Gateway 有其一，Observability/Evaluation 只有基础日志 | Identity+Gateway+Observability+Evaluation 四大治理模块齐全，形成治理外环闭环 | **5** | F010 Identity 统一鉴权+F011/F012 Gateway 接入路由+F017 Observability 全链路观测+F018 Evaluation 质量闭环，四大模块完整定义 |
| 2 | 开发者体验 | 14% | 仅支持1种语言，无CLI，文档缺失 | 支持2种语言SDK，基础CLI，有官方文档 | 支持≥3种主流语言SDK，完整CLI工具链（init/config/build/deploy），兼容主流开源生态 | **4** | F020 Python/Go/Java 三语言SDK + F032-F036 init/config/build/deploy/launch 五条CLI命令 + F024 兼容Google ADK、F025 兼容LiteLLM；但社区规模未见事实陈述 |
| 3 | 部署灵活性 | 13% | 仅支持单一云托管模式，无本地/混合选项 | 支持2种模式，有基础弹性能力 | Local/Hybrid/Cloud 三种模式齐全，Serverless 秒级弹性，多租户硬隔离 | **5** | F037 三种部署模式（Local/Hybrid/Cloud）+ F059 Serverless 秒级扩缩容 + F060 多租户严格隔离 |
| 4 | 企业级安全 | 13% | 无独立鉴权系统，密钥明文配置 | 有基础AK/SK管理，单点权限控制 | Identity 统一身份治理+凭据托管+内容护栏配置+合规审计能力齐全+合规认证 | **4** | F010 Identity 提供受控访问与凭证/权限边界管理；内容护栏能力经V阶段质疑后保守评4分（具体合规认证待验证） |
| 5 | 生态兼容性 | 11% | 私有协议锁定，无标准协议支持 | 支持MCP或A2A其一，基础REST接入 | MCP+A2A双协议兼容，主流框架（ADK/LiteLLM等）兼容，REST/OpenAPI一键转换接入 | **5** | F056 MCP 协议兼容 + F057 A2A 协议兼容 + F012 REST/OpenAPI 快速转换 + F024 Google ADK 兼容 + F025 LiteLLM 兼容 |
| 6 | 可观测与评测 | 9% | 仅有模型调用日志，无评测能力 | 有基础链路追踪，无标准化评测体系 | 全环节 Trace串联+离线/在线评测+成本分析+用户满意度+发布闸门绑定 | **4** | F017 Observability 全链路观测 + F018 Evaluation 上线前验证+持续优化+发布闸门；成本分析和满意度指标事实有限 |
| 7 | 成本可控性 | 7% | 无弹性策略，固定资源包计费，无成本优化工具 | 有基础自动扩缩容，单一计费模式 | Serverless 按需伸缩+智能模型路由优化+多模式计费+免费额度+优化建议 | **3** | F059 Serverless 秒级伸缩 + F053 智能路由+全托管成本优化；免费额度和具体计费模式未见事实陈述 |
| 8 | 可扩展性上限 | 6% | 单Agent上限，无记忆/知识库扩展，无自定义能力 | 支持基础多Agent协作，记忆/知识库有规模上限 | A2A多Agent编排+分层记忆+知识库分片+Harness动态热切换+亿级规模验证 | **4** | F013 A2A 多 Agent 编排 + F014/F015 Session/Memory 分层管理 + F016 Knowledge 知识检索 + F055 Session 内热切换；但亿级规模指标官方未公开（F061） |
| 9 | **供应商锁定风险** ⭐V阶段新增 | 7% | 全栈私有协议，SDK不兼容开源，数据导出困难，迁移需全部重写 | 兼容部分开源标准，核心编排/工具协议为私有，迁移需重写核心逻辑 | 完全开源+全协议标准化（MCP/A2A/OpenAPI）+标准格式数据导出一键迁移，无专有API绑定 | **3** | VeADK兼容Google ADK（加分）降低开发习惯锁定，但Cloud模式深度绑定火山引擎生态（方舟/Viking/VeFaaS），综合评3分（中等锁定） |

> **加权总分计算**（v2.0 九维度）：
> 5×0.20 + 4×0.14 + 5×0.13 + 4×0.13 + 5×0.11 + 4×0.09 + 3×0.07 + 4×0.06 + 3×0.07 = **4.30 / 5.00**（AgentKit 综合得分 v2.0）
>
> 对比 v1.0（8维度 4.25 分）：新增锁定风险维度后得分略有下调，更准确反映云托管模式的绑定成本。

### 反模式

- **反模式 1**：只对比「编排能力」一个维度，忽略治理外环（Identity+Gateway+Observability+Evaluation）的完整度，导致生产化后出现权限失控、问题无法定位、质量无法保障的连锁失败。（对应洞察2：治理外环优先级高于业务内环）
- **反模式 2**：选型前不做 PoC 验证，仅凭供应商 PPT 和报价决策，未在真实企业数据和存量 API 场景下验证 Gateway 接入能力、Identity 权限模型与现有 IAM 系统的兼容性，上线后发现 30%+ 核心能力无法落地。
- **反模式 3**：权重分配倒置（编排能力权重>治理能力权重），将玩具级 Demo 平台误判为企业级生产平台，日均调用破千后治理债务集中爆发，回滚成本是选型阶段的 5 倍以上。
- **反模式 4**：**忽略供应商锁定风险（维度9打1分或不评估）**，第一年觉得"平台好用就好"，第三年想迁移或多厂商策略时发现所有业务代码深度绑定私有 API，迁移成本是重新选型的 5-10 倍，直接形成技术债绑架。（V阶段对抗审查采纳）

### 迁移验证说明（G3关键）

- **迁移场景 A**：可用于评估 Dify / Coze / LangGraph / LlamaIndex / AutoGen / CrewAI 等任何 Agent 框架或平台的选型对比，9 个维度（含锁定风险）无需修改，仅需将「AgentKit 示例得分」替换为对应产品的实际评估分数即可。模式的权重建议和 1/3/5 分评分标准具有普适性。
- **迁移场景 B**：可用于评估 RAG 平台（如 LlamaIndex、Haystack、Weaviate 平台版）、向量数据库（如 Milvus、Qdrant、Chroma 企业版）、AI 网关（如 LiteLLM Proxy、OpenRouter）等 AI 基础设施的选型——只需将 9 个维度中的「A2A多Agent编排」等 Agent 特有表述调整为对应产品领域术语（如 RAG 的「检索准确率」替换「可扩展性」），权重体系和评分方法完全复用。

## 模式 2：存量业务系统智能化改造 5 步 SOP

**模式 ID**：P-LEGACY-AI-UPGRADE-002

### 触发场景

企业已有工单/订单/CRM/审批/ERP/HR 等业务系统（REST/OpenAPI 为主，部分含 gRPC/GraphQL），需要赋予 Agent 自然语言交互能力、工具调用能力、跨系统协同能力。

### 核心步骤

5 步流程，每步包含：步骤名称 / 输入 / 核心动作 / 输出 / 推荐工具。

| 步骤 | 步骤名称 | 输入 | 核心动作 | 输出 | 推荐工具（AgentKit 映射） |
|------|---------|------|---------|------|------------------------|
| 第 1 步 | **API 梳理与分级** | 存量系统 API 文档（Swagger/OpenAPI JSON/YAML、Postman Collection、内部 Confluence 文档） | 1. 收集所有暴露接口（含内部未文档化接口）；2. 按「近 90 天调用频率 × 业务价值（营收影响/合规要求/人工耗时）」二维矩阵打分；3. 分 ABC 三级：A级（Top 20%，高频+高价值）、B级（中间 30%）、C级（剩余 50%，低频低价值）；4. 标记敏感写操作接口（创建/修改/删除/审批通过）单独管控 | A 级 API 清单（Top 20% 核心接口，建议 20~100 个）+ 敏感写操作接口标记清单 | （通用）Swagger Parser、Postman API、API 网关流量日志分析；（AgentKit）无专属工具，此步为业务分析 |
| 第 2 步 | **Gateway 快速接入** | A 级 API 清单 + 敏感写操作标记 | 1. 利用 Gateway 的 REST/OpenAPI 转换能力，批量导入 A 级 API 自动生成 Tool 定义（名称/描述/参数 Schema/示例）；2. 对敏感写操作接口默认设置「只读模式」或「二次确认」包装；3. 为每个 Tool 分配独立的调用超时（默认 30s）和重试策略（最多 2 次指数退避）；4. 逐个 Tool 做连通性测试，确保鉴权头、参数映射、响应解析正确 | 可被 Agent 调用的 Tool 清单（含 Tool 名称/描述/参数/超时/重试/权限标签）+ 连通性测试通过率报告 | AgentKit: F011 Gateway 统一入口 + F012 REST/OpenAPI 快速转换接入；通用替代：LangChain Tool Wrapper、LlamaIndex Tool Spec |
| 第 3 步 | **权限与身份映射** | 业务系统的角色权限矩阵（RBAC/ABAC 模型）+ Tool 清单 + 企业 IAM 系统用户目录 | 1. 定义 Agent 独立身份标签（区别于人类用户账号）；2. 将业务系统角色映射为 Agent 的 Tool 访问白名单（遵循最小权限原则：只授予 A 级 API 中与 Agent 任务场景匹配的子集）；3. 配置凭据托管：业务系统 AK/SK/Token 存入统一 Secret Manager，禁止代码硬编码；4. 定义跨 Agent 权限隔离规则：A Agent 不可通过 B Agent 间接调用自身白名单外的 Tool | Agent-用户-工具的三维权限映射表（Agent 角色 × 人类用户角色 × Tool 白名单）+ 凭据托管配置确认表 | AgentKit: F010 Identity 统一鉴权+凭证/权限边界管理；通用替代：Keycloak、AWS IAM、HashiCorp Vault + 自定义权限中间件 |
| 第 4 步 | **Harness 跑通验证** | Tool 清单 + 权限映射表 + 典型业务场景用例清单（建议 ≥20 条，覆盖 80% 高频诉求） | 1. Harness 配置编排：定义 Agent 模型、System Prompt、Tool 挂载列表、会话配置；2. Local 模式启动调试：Mock 外部依赖、单步跟踪 Tool 调用链路、验证权限拦截是否生效；3. 典型场景批量测试：自动化执行 20+ 条业务用例，记录成功率/平均延迟/Tool 调用正确率；4. 修复通过率 <90% 的场景（优化 Tool 描述、补充 Prompt 约束、增加参数校验） | 测试通过的典型业务场景 Demo（含用例执行报告 + 失败案例根因分析）+ Harness 配置文件 | AgentKit: F037 Local 部署模式 + F054/F055 动态 Harness 编排（配置即部署、热切换）+ F032 init 模板生成；通用替代：LangGraph Studio、Dify Workflow 调试模式 |
| 第 5 步 | **MCP 渐进优化（可选）** | Observability 调用数据（近 2 周 Tool 调用日志/Trace）+ 第 4 步 Demo 报告 | 1. 从 Observability 提取 Tool 调用频率排名，筛选 Top 20% 高频调用接口；2. 对筛选出的接口评估 MCP 改造收益：流式响应需求（>5s 响应优先）、错误码结构化需求（>3 种业务错误优先）、并发安全需求（涉及库存/余额等状态变更优先）；3. 逐个改造为 MCP Server 并灰度切换（新旧双轨并行观察 ≥3 天）；4. 量化收益报告：延迟变化（P95）、错误率变化、Token 消耗变化 | 性能/稳定性提升报告（改造前后对比指标）+ MCP Server 清单 + 灰度切换记录 | AgentKit: F017 Observability 调用链路数据 + F012/F056 MCP Server 接入；通用替代：OpenTelemetry + 自研 MCP SDK + 灰度发布工具（如 Argo Rollouts） |

### 反模式

- **反模式 1**：一开始就要求所有接口（含 C 级 50% 低频低价值接口）都支持 MCP 标准，改造周期拖到 6 个月以上，业务方失去耐心项目终止。正确做法：先用 REST/OpenAPI 转换 1~2 天跑通 A 级，再渐进改造 Top 20% 高频。（对应洞察5：REST/OpenAPI 转换是主路径，MCP 是优化方向非前置）
- **反模式 2**：直接把业务系统管理员密钥（超级管理员 Token）给 Agent 使用，最小权限原则完全失效。一旦 Prompt 注入成功，Agent 可直接调用所有敏感写操作接口（批量删除订单、修改员工薪酬等），造成不可逆生产事故。
- **反模式 3**：跳过 Local 模式验证，直接上生产 Cloud 模式。开发阶段无法单步调试 Tool 调用、无法模拟各种失败场景（超时/429/5xx）、无法快速迭代 Prompt，每次修改都走完整构建部署流程，调试成本翻倍且排错周期从小时级拉长到天级。（对应洞察4：Local 试错 → Cloud 投产的渐进路径）
- **反模式 4**：API 分级时只看业务价值不看调用频率，将一批高价值但季度调用 <5 次的接口纳入 A 级优先接入，浪费 2~3 周在极少使用的接口上，而一线客服每天调用 500+ 次的订单查询接口反而在 B 级迟迟未上线。

### 迁移验证说明（G3关键）

- **迁移场景 A**：可直接用于任何基于 REST/OpenAPI 的存量系统改造（不依赖 AgentKit 专有能力）。任何支持 Tool Calling 的 Agent 框架（LangChain、LlamaIndex、AutoGen、Semantic Kernel、Dify、Coze 等）均适用：第 2 步 Gateway 接入替换为对应框架的 Tool Wrapper，第 3 步权限映射替换为对应框架的权限中间件，第 4 步 Harness 验证替换为对应框架的调试模式，第 5 步 MCP 优化在支持 MCP 的框架中可直接复用。
- **迁移场景 B**：可推广到移动 App（iOS/Android 后端 API）、小程序（微信/支付宝/抖音小程序服务端 API）、第三方 SaaS（Salesforce/钉钉/飞书/企业微信 OpenAPI）的 API 智能化改造场景。SaaS 场景中第 2 步通常需额外处理 OAuth 2.0 授权流程（将 Access Token 纳入凭据托管），小程序场景需额外处理签名校验，核心 5 步流程不变。

## 模式 3：智能体从 Demo 到生产的 12 项检查清单

**模式 ID**：P-DEMO-TO-PROD-003

### 触发场景

智能体 Demo 验证完成（在 Local 模式跑通典型流程，核心场景通过率 ≥90%），需要进入生产环境部署，面对真实用户流量和 SLA 约束。

### 核心检查

12 项检查，覆盖 6 大维度，每项包含：检查项名称 / 通过标准（Pass/Fail 判定依据） / 检查方法 / AgentKit 对应能力映射。

| 维度 | 序号 | 检查项名称 | 通过标准（Pass/Fail） | 检查方法 | AgentKit 对应能力映射 |
|------|------|-----------|---------------------|---------|---------------------|

### 反模式

- **反模式 1**：Demo 在 Local 模式跑通就直接全量上线，缺少上述 12 项中的任一项检查，生产环境出现以下问题概率 >80%：明文密钥泄露、租户间数据串扰、无法定位报错根因、Tool 超时导致整个会话卡死、成本失控（单日成本超预算 10 倍）。出现问题后由于缺乏全链路 Trace，平均排错时间 >4 小时。
- **反模式 2**：为了快速上线跳过发布闸门（Eval 评估），Demo 环境只验证了 10 条 Happy Path 用例，生产环境真实用户输入多样性导致核心场景通过率从 Demo 的 95% 掉到 60%，用户投诉量飙升 5 倍，被迫回滚后返工重新做评测，总延期 2 周。（对应洞察2：Evaluation 与上线闸门绑定是生产化前提）
- **反模式 3**：只关注功能检查（12项里只做了检查1和检查9），忽略成本维度（检查7和检查8）。上线第一周由于无模型路由、无弹性缩容，周末流量下降但资源未回收，小模型能力未启用，云账单超预算 300%，被财务冻结预算后被迫紧急优化。
