## 引子：索引解决"找资料"，但不解决"做判断"

| 编号 | 类别 | 事实内容 | 信源距离 |
|---|---|---|---|
| F-005 | 【事】 | 给一个项目建 Agent 知识库，通常能拿到架构文档、接口说明和历史复盘，代码也在仓库里 | 作者经验陈述 |
| F-006 | 【事】 | 常见做法：把资料整理好、做索引，让 Agent 遇到问题时去查；这解决"资料从哪里找"的问题 | 作者经验陈述 |
| F-007 | 【观】 | 若目的是让 Agent 定位生产故障，还需考虑：查到资料以后，它凭什么判断这次问题发生在哪里 | 作者观点 |
| F-008 | 【事】 | 说明性案例：删除接口返回 HTTP 500，Agent 据此判断删除失败；但检查数据后发现删除已经完成 | 作者设定案例 |
| F-009 | 【观】 | 服务端处理请求时出了错，不代表之前执行的动作都没有生效；只凭状态码决定重试或把结果改回去，都可能处理错 | 作者观点 |
| F-010 | 【事】 | 文章指出：接口说明与错误码解释不缺；要判断此次故障还须知道删除过程经过哪些环节、错误发生前哪些步骤已完成、从哪里能查到实际结果 | 作者论点 |

## 01 先确定需要支持什么判断

| 编号 | 类别 | 事实内容 | 信源距离 |
|---|---|---|---|
| F-011 | 【观】 | 建设知识库之前先确定它要帮 Agent 做什么；文章设定的目标是定位生产问题，并为是否修改、修改哪里提供依据 | 作者观点 |
| F-012 | 【观】 | 目标决定了资料要整理到什么程度 | 作者观点 |
| F-013 | 【事】 | 判断一个行为有没有问题需要预期作为参照：接口原本要完成什么、允许哪些中间状态、出现错误后保证到哪一步 | 作者论点 |
| F-014 | 【观】 | 没有预期时，"当前状态是什么"只是一条记录，不足以判断它是否异常 | 作者观点 |
| F-015 | 【事】 | 同一个结果可能经过多个服务和后台任务；用户看到的错误可能出现在后面的环节，原因却在前面 | 作者经验陈述 |
| F-016 | 【观】 | 只列组件名称没法解释这种关系；需要把过程连起来，写清每一步的输入、结果，以及失败后会发生什么 | 作者观点 |
| F-017 | 【观】 | 作者给出的待分析问题描述结构：哪个机制原本应该完成什么；实际行为在哪个环节偏离了预期；有什么证据，造成了什么影响 | 作者方法论 |
| F-018 | 【义】 | "机制"：系统完成一件事所依靠的过程；可能在一个服务内完成，也可能跨越多个组件 | 作者定义 |
| F-019 | 【事】 | 资料与问题结构的对应方向：架构文档回答过程涉及谁；设计文档解释正常行为；代码和观测资料帮助确认实际执行到了哪里 | 作者论点 |
| F-020 | 【义】 | "槽位"：问题描述中的信息位置；不是固定排查步骤，而是做出判断时需要补齐的信息；刚拿到故障时可只知道现象、其余留空，后续调查即逐步缩小未知 | 作者定义 |

## 02 不熟悉项目，先整理它正常时怎么工作

| 编号 | 类别 | 事实内容 | 信源距离 |
|---|---|---|---|
| F-021 | 【事】 | 有了问题结构，仍不能凭空知道某模块有哪些状态，也不能推导出线上使用了什么配置；第一性原理能帮助确定需要了解什么，项目事实还得去查 | 作者论点 |
| F-022 | 【观】 | 建议从一条完整的业务流程开始，而不是试图一次读懂整个仓库 | 作者方法建议 |
| F-023 | 【事】 | 先用文档确定流程的目的和边界，再沿代码核对实际经过的环节；调用顺序、状态变化和失败处理放在一起看，才能得到正常工作过程的说明 | 作者方法建议 |
| F-024 | 【事】 | 函数所在文件可以作为查证入口，但文档主体应当是过程本身 | 作者方法建议 |
| F-025 | 【观】 | 不熟悉处要留下问题而非猜解释；文档和实现对不上就记录冲突；代码看不出设计原因就找设计记录或请维护者确认 | 作者观点 |
| F-026 | 【事】 | 暂时没有答案，不妨碍先整理已经核实的部分 | 作者观点 |
| F-027 | 【事】 | 逐条补充关键流程后系统整体结构会清楚：哪些过程共享同一项状态、哪些失败会传到其他环节、哪些结果可以重试、哪些动作完成后不能简单撤销 | 作者经验陈述 |
| F-028 | 【观】 | 整理充分性的检查：假设某环节没按预期工作，Agent 能否从文档找到正常行为和查证位置；若只能找到职责介绍、还需重读整个模块，则没整理到位 | 作者方法建议 |
| F-029 | 【观】 | 作者公式①：专家认知 = 问题结构 × 对应的领域知识；作者注明这是设计上的简写，不是数学计算 | 作者自创框架 |
| F-030 | 【事】 | 问题结构帮助确定要回答什么，领域知识提供具体内容；只写一组问题而没有对应内容，Agent 依然需要从头了解项目 | 作者解释 |

## 03 把"文档这样写"变成"有依据的判断"

| 编号 | 类别 | 事实内容 | 信源距离 |
|---|---|---|---|
| F-031 | 【事】 | 沿流程整理后通常会遇到：同一件事，不同资料说法不同 | 作者经验陈述 |
| F-032 | 【事】 | 设计文档写的是当初希望怎样实现，代码反映某个版本实际怎样实现，线上运行的未必是仓库最新版本；不能简单规定"永远以代码为准" | 作者经验陈述 |
| F-033 | 【观】 | 先明确正在确认什么：问当前生产行为就核对部署版本、实际配置和运行记录；问系统应遵守的接口约定就查对应版本契约；实现违反契约也可能正是待修问题 | 作者方法建议 |
| F-034 | 【观】 | 每条重要结论都要保留依据、适用条件和待确认事项；整理者相信它，不足以让另一个 Agent 直接拿去使用 | 作者观点 |
| F-035 | 【观】 | 作者公式②：专家知识 = 专家认知 × 事实验证 | 作者自创框架 |
| F-036 | 【事】 | 专家知识保留稳定的判断依据，把容易变化的值留在事实来源里 | 作者解释 |
| F-037 | 【事】 | 代码入口、接口字段和日志字段若有助于查证就应保留在参考资料中并注明适用范围；需避免把某次查到的值写成长期不变的规律 | 作者方法建议 |

## 04 让 Agent 找得到，也知道怎样使用

| 编号 | 类别 | 事实内容 | 信源距离 |
|---|---|---|---|
| F-038 | 【事】 | 经过核验的知识仍可能分散在很多文件里；Agent 每次从全库搜索开始，容易先命中旧复盘或零散细节，而读不到当前机制的完整说明 | 作者经验陈述 |
| F-039 | 【义】 | "专家底座"：在资料前面放一份较短的入口文档——说明系统关键过程、列出正常行为和重要约束、指向详细资料与查证位置，供优先读取 | 作者定义 |
| F-040 | 【事】 | 专家知识指内容，专家底座指组织和提供这些内容的方式；底座不需要装下全部资料，但不能只剩一张目录：Agent 读完至少应理解问题所在模块正常时怎样工作 | 作者解释 |
| F-041 | 【观】 | 使用方式：Agent 先把现象放到对应流程中；知识库提供正常过程和已知约束，现场调查确认这一次发生了什么；两者不一致时继续取证，不能为让事实符合文档而忽略差异 | 作者观点 |
| F-042 | 【观】 | 求证方法要单独准备：哪些信息只是线索、怎样检查一个解释是否有反例、什么情况下仍不能动手修改；这些不属于某个模块的工作原理；懂得正常流程不保证每次推断正确 | 作者观点 |
| F-043 | 【观】 | 作者公式③：未知问题的解题能力 = 专家知识 × 求证方法 × 当前事实 | 作者自创框架 |
| F-044 | 【事】 | 验收方式（沿用删除请求案例）：Agent 能否把返回错误和动作结果分开、找到检查实际结果的位置，而非看到错误码就直接处理；若必须由使用者反复提醒，说明知识或使用说明还需补充 | 作者方法建议 |
| F-045 | 【事】 | 专家底座提供认知参照，不规定每次都执行同一组命令；成熟的操作手册仍然有用，但只能在适用条件已得到确认时使用 | 作者观点 |

## 05 知识要分开保存，才能按不同速度更新

| 编号 | 类别 | 事实内容 | 信源距离 |
|---|---|---|---|
| F-046 | 【事】 | 整理专家知识不意味着其余项目资料无用；完整实现说明、接口定义和操作记录仍需保存，只是不能当作同一种知识使用 | 作者观点 |
| F-047 | 【义】 | 知识分类①——领域知识：记录不同项目中也能使用的概念和机制；适用条件通常较稳定，但应用到当前项目时仍需核对 | 作者分类 |
| F-048 | 【义】 | 知识分类②——项目设计与实现：记录这个系统自己的组成、流程和约束；不一定能迁移，但定位当前项目问题必不可少 | 作者分类 |
| F-049 | 【义】 | 知识分类③——接口文档：保存精确契约，字段和错误语义需跟版本一起维护 | 作者分类 |
| F-050 | 【义】 | 知识分类④——使用与运维资料：保存操作方法、适用条件和回滚步骤；排期与责任分工也放在这一类，不能当成长期规则 | 作者分类 |
| F-051 | 【义】 | 知识分类⑤——日期目录和草稿区：留下分析过程；尚未确认的猜测可保留，但不应与已核实结论混在一起 | 作者分类 |
| F-052 | 【观】 | 分类判据看一条内容的用途、变化速度以及由什么来源确认；不同分类是维护方式的区别，不是价值高低排序；专家知识也可能来自对项目实现的深入理解，不只来自通用原理 | 作者观点 |
| F-053 | 【观】 | 一份故障复盘不必整篇搬到某个目录：过程记录留在原处，已确认结论分别更新到对应资料，再由索引建立联系；否则同一结论多份并存，后面难保证同时更新 | 作者观点 |

## 06 用新问题检查旧知识

| 编号 | 类别 | 事实内容 | 信源距离 |
|---|---|---|---|
| F-054 | 【观】 | 知识库是否有用，要看它在下一次问题中起了什么作用 | 作者观点 |
| F-055 | 【事】 | 每次排查结束后记录 Agent 从哪里开始走偏：找错模块检查入口是否清楚；正常流程理解错核对相关文档；知道流程却得出无证据结论检查求证要求；一律归为"知识不够"容易又回到增加文档数量 | 作者方法建议 |
| F-056 | 【事】 | 更新不必每次重写整份底座：局部有误修正相关内容，出现原有结构容纳不了的问题再调整结构；改完后重跑之前案例，确认旧问题仍能被正确分析 | 作者方法建议 |
| F-057 | 【事】 | 检查数量可以少，但最好由未参与编写的人或 Agent 独立完成，避免照着已知答案验收 | 作者方法建议 |
| F-058 | 【事】 | 除随问题更新外还需定期复核：依赖版本、关键配置和接口变更之后检查关联结论；日常整理时处理未确认项和日期目录中的新发现 | 作者方法建议 |
| F-059 | 【观】 | 每条正式结论留下来源与最近核验时间；没有新证据的猜测，不因重复出现就升级为事实 | 作者观点 |
| F-060 | 【观】 | 结语：刚接手陌生项目不可能一次写出完整专家知识；能做到的是让每个判断有出处、让不知道的地方清楚可见；新问题沿已有过程继续核对，处理完后下一位使用者少走相同弯路 | 作者观点 |
