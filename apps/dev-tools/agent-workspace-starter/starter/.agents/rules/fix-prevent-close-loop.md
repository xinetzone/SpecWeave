# 修复即闭环：三阶段强制 SOP

> 只修不防，等于白忙。点修复是最常见的认知偏差——解决眼前问题比建立长效机制更"紧急"，但每次跳过预防都在为未来创造同样的问题。

## 一、问题背景

实践中多次出现"修复了问题但未建立预防机制，导致问题以变体形式复发"的模式：

- **渲染问题**：修复语法问题后未建立预防性检查脚本，后续又出现特殊字符转义问题。
- **断链问题**：批量修复断链后未在重构前建立影响范围分析流程，后续重构又产生新断链。
- **事实表述漂移**：修正统计数字不一致后未建立单一数据源，后续又出现类似漂移。

**根因分析（5-Whys）**：问题复发 → 只做"点修复"未建"预防机制" → 修复时急于解决当前问题 → 缺乏标准操作流程 → **根本原因：没有强制流程要求在修复时必须执行预防步骤**。

## 二、三阶段闭环模型

所有 Bug 修复、问题解决、错误纠正必须严格遵循以下三阶段，**禁止跳过任何阶段**：

```mermaid
flowchart LR
    S1["阶段1：被动修复<br/>解决当前问题"] --> S2["阶段2：主动预防<br/>建立防复发机制"]
    S2 --> S3["阶段3：闭环自证<br/>验证预防机制生效"]
```

### 阶段1：被动修复（Fix）
明确问题现象和复现条件 → 定位根因（5-Whys 或等价方法）→ 实施修复 → 验证修复有效。

### 阶段2：主动预防（Prevent）
确保同类问题不再出现。**此阶段禁止跳过。** 预防措施选择矩阵（至少选一项）：

| 预防措施类型 | 适用场景 | 具体操作 |
|-------------|---------|---------|
| **自动化检查脚本** | 问题可通过静态检测发现 | 编写/更新检查脚本，加入 CI 或 pre-commit |
| **规则/规范更新** | 问题源于流程缺失或规范不清 | 更新规则文档、SOP、检查清单 |
| **单元测试用例** | 问题出现在代码逻辑中 | 添加测试用例覆盖该场景，防止回归 |
| **反模式清单** | 问题是常见陷阱/易犯错误 | 将错误模式加入反模式清单，附正例对比 |
| **架构/设计调整** | 问题源于设计缺陷 | 调整架构从根源消除问题产生的可能 |

关键原则：预防措施必须能自动或半自动检测同类问题，不能仅靠"以后注意"。

### 阶段3：闭环自证（Close）
证明预防机制确实有效：①自动验证（运行脚本/测试确认能检测到问题模式）；②实战验证（24 小时内或下次同类操作时观察是否拦截）；③回归验证（故意引入同类错误确认能检测到）。

## 三、触发条件与适用范围

- **RULE-FPC-001：Bug 修复必须执行三阶段**——提交时在 commit message 中注明预防措施类型（如 `fix(scope): 描述 [prevent: test-case]`）。
- **RULE-FPC-002：纯点修复禁止提交**——`fix:` 提交必须包含预防措施或跟踪 Issue 引用。
- **RULE-FPC-003：平凡修复豁免**——拼写错误、格式调整、注释修正、临时文件清理可豁免阶段 2-3。

## 四、反模式识别

| 反模式 | 表现 | 纠正 |
|---|---|---|
| "以后再加预防" | 修复时说"预防以后再加"，但"以后"永远不会来 | 预防措施必须在同一次提交中完成 |
| "这个问题不会再发生" | 认为"情况很特殊"而不加预防 | 问："不了解上下文的人做类似操作是否可能犯同样错误？" |
| 预防等于"加文档" | 只加一句"注意不要 XXX" | 优先自动化检查脚本、测试用例、架构调整 |

## 五、实施检查清单

- [ ] 阶段1完成：当前问题已修复，复现验证通过
- [ ] 阶段2完成：已实施至少一项预防措施
- [ ] 预防措施不是纯文档说明（至少有半自动化检测能力）
- [ ] commit message 中注明了预防措施类型
- [ ] 如属于平凡修复豁免，确认符合豁免条件
