# devcontainer-base conda-libmamba-ft v2.2 构建流水线优化方案

> 方法论：第一性原理（F）→ 对抗审查（V）→ 洞察落地（I）
> 基于 v2.1 里程碑复盘的洞察与萃取模式，规划 v2.2 优化方向

## 一、第一性原理分析（F）

### 1.1 问题界定

v2.1 已实现四层验证流水线（预检→构建内→冒烟→性能基准），但仍存在以下可优化空间：
- 构建速度：冷构建时间较长（conda install 是瓶颈），未充分利用 BuildKit 缓存
- 镜像体积：2.5GB 中双 Python 环境占约 250MB（base py313），可评估精简空间
- 验证深度：verify-cext.sh 覆盖6个核心C扩展，但 NumPy/pandas 等科学计算包未覆盖（free-threading 用户最关心的场景）
- 可复现性：conda install 未完全锁定版本，不同时间构建可能得到不同包版本
- 脚本通用性：verify-cext.sh 和 ft-benchmark.sh 是 devcontainer-base 专用脚本，参数化不足难以复用到其他项目

### 1.2 公理识别

剥离所有假设，识别基础镜像构建流水线的不可再分公理：

| 公理 | 陈述 | 对v2.2的约束 |
|------|------|-------------|
| **A1：构建时间=开发者生产力** | 冷构建每增加1分钟，所有重建镜像的开发者都多等待1分钟 | 优先优化构建速度，ROI最高 |
| **A2：验证深度 ∝ 故障发现率** | 覆盖的C扩展越多，发布后发现"XX包不兼容cp314t"的概率越低 | 增加numpy/pandas深度验证 |
| **A3：镜像体积 ∝ 拉取/分发成本** | 每250MB增加约5-10秒pull时间（国内网络更慢） | 评估可无损精简的空间 |
| **A4：快速失败 > 事后排查** | 在L1预检发现问题的成本远低于L3/L4 | 扩展预检覆盖面 |
| **A5：可复现性是基础镜像的基本要求** | 同一Dockerfile在不同时间构建应该得到相同版本的包 | conda环境锁定 |
| **A6：脚本通用性 > 专用脚本** | 可参数化的脚本可以复用到变体和其他项目 | verify/benchmark脚本抽象 |

### 1.3 假设剥离

| 隐含假设 | 验证 | 处置 |
|---------|------|------|
| "base环境py313必须保留" | conda确实依赖base Python，但Miniforge3的base Python是3.13，conda命令运行依赖它；不可直接删除 | 保留但评估conda-pack方案消除冗余 |
| "Dockerfile内联验证+verify-cext.sh双重验证是冗余" | 不是冗余——Dockerfile内联是构建时门禁（坏镜像不产生），verify-cext.sh是运行时诊断（用户环境可检测） | 保留双层，但统一输出格式 |
| "quick模式50K primes足够验证" | 50K仅3x加速比，2.0x阈值过于宽松，理论上1.0x以上就能通过——单线程有波动可能误通过 | 调整到500K primes（0.2s单线程，4.8x加速），阈值3.0x |
| "conda mirror在Dockerfile里ARG就够了" | 需要mamba install也使用mirror，.condarc需要在Miniforge安装后立即写入 | 修正.condarc写入时机 |
| "numpy/pandas必须在构建时安装" | 安装numpy+pandas会增加约500MB镜像体积和5+分钟构建时间，不适合基础镜像 | 作为--deep-verify可选模式，不内置 |

### 1.4 自下而上重构方案

从公理出发推导v2.2的6项优化：

| # | 优化项 | 对应公理 | 预期收益 | 实现复杂度 |
|---|-------|---------|---------|-----------|
| O1 | BuildKit mount cache 优化 conda/pip 下载 | A1 | 冷构建速度提升40-60%，热构建秒级 | 低（Dockerfile语法修改） |
| O2 | 验证脚本参数化 + 统一JSON输出 | A6 | 脚本可复用到变体/其他项目，便于CI解析 | 中（脚本重构） |
| O3 | --deep-verify 深度验证模式（numpy/pandas） | A2 | 覆盖真实使用场景，防止发布后才发现科学计算包不兼容 | 中（build.sh参数+可选Docker stage） |
| O4 | Conda环境锁定（conda-lock或environment.yml精确版本） | A5 | 构建可复现，避免"昨天构建还好好的" | 中（lock文件维护） |
| O5 | 基准测试规模调整：quick模式500K/3.0x阈值 | A4 | quick模式更可靠地检测GIL是否真正禁用，消除假阳性 | 低（参数调整） |
| O6 | Conda-pack精简评估（非默认） | A3 | 评估消除base py313冗余(250MB)的可行性 | 高（风险评估） |

## 二、对抗审查（V）

> 对v2.2方案进行四视角攻击，识别设计缺陷

### 🔴 魔鬼代言人

1. **BuildKit cache会导致陈旧包**：如果一直用缓存，可能不会拉取安全更新。
   - **修正**：添加 `--no-cache` 选项支持强制刷新；CI 流水线定期（每周）执行--no-cache构建验证最新包可用。
2. **conda-lock会增加维护负担**：每次依赖更新都要重新生成lock文件，开发体验下降。
   - **修正**：conda-lock作为CI门禁（构建时验证lock文件与environment.yml一致），但本地开发允许floating；提供`make lock`命令简化。
3. **--deep-verify模式安装numpy/pandas会拖慢构建**：即使是可选stage，BuildKit也会解析Dockerfile全部stage。
   - **修正**：deep-verify不在Dockerfile中作为target，而是在build.sh中run容器后`conda install numpy pandas && python verify.py`，完全旁路镜像构建。
4. **参数化verify脚本增加使用复杂度**：用户需要传更多参数。
   - **修正**：提供合理默认值（自动检测当前Python SOABI），零参数即可运行。

### 🟢 新人视角

5. **怎么生成conda-lock文件？** 新用户不知道conda-lock是什么。
   - **修正**：在README中添加"可复现构建"章节，提供命令示例。
6. **--deep-verify怎么用？** 不清楚什么时候需要加这个参数。
   - **修正**：build.sh --help中添加说明："首次升级Python版本时使用，日常构建不需要"。
7. **脚本参数化后默认行为变了吗？** 担心升级后现有命令不能用。
   - **修正**：保持向后兼容，所有新参数都有默认值，现有build.sh命令行不变。

### 🟠 老板视角

8. **这些优化的ROI如何？** BuildKit cache优化最显著但需要多少工作量？
   - **评估**：O1（BuildKit cache）<1小时工作量，40-60%构建速度提升，ROI最高，优先实现。
9. **v2.2什么时候能发布？** 给出时间估算。
   - **评估**：O1+O2+O5为P0（核心优化），约4-6小时工作量；O3+O4为P1（增强），约6-8小时；O6为P2（探索），2-4小时评估+实验。一个迭代周期（1-2天）可完成P0+P1。
10. **这些变更会破坏现有用户吗？**
    - **回答**：不会。O1-O5都是增量改进，Dockerfile接口（build-arg、端口、环境变量）完全向后兼容；O6为实验性探索，默认不启用。

### 🔵 未来视角

11. **Python 3.14.7/3.15发布后v2.2的方案还适用吗？**
    - **回答**：O1（BuildKit cache）/O2（脚本参数化）/O4（conda-lock）与Python版本无关，永久有效；O5（benchmark阈值）需要根据新版本重新标定，但机制不变。
12. **如果未来micromamba成熟，替代Miniforge3会怎样？**
    - **回答**：micromamba是单二进制C++实现，无base Python，可直接消除双环境问题（250MB）。O2参数化verify脚本后切换更简单。将micromamba评估纳入O6。
13. **conda-forge的cp314t包覆盖率提升后deep-verify还有必要吗？**
    - **回答**：永远有必要——新发布的包可能尚未适配cp314t，deep-verify是升级前的安全网。

### 9.3 Free-Threading C 扩展编译强制规范

#### 🔴 GIL 声明强制项（最容易遗漏）

每个支持 free-threading 的模块**必须**在 `PyModuleDef_Slot` 中声明：
```c
static PyModuleDef_Slot slots[] = {
    {Py_mod_gil, Py_MOD_GIL_NOT_USED},  // ← 缺少这行则 GIL 自动启用，多线程退化为串行
    {Py_mod_exec, (void*)module_init},
    {0, NULL}
};
```
- 未声明的后果：模块加载后 GIL 自动重新启用，多线程代码串行执行，5x 加速比消失
- 检测方法：`python -c "import sys; print(sys._is_gil_enabled())"` 应为 False（所有模块均声明后）

#### 🔴 线程安全强制项

| 规则 | 正确做法 | 错误做法 | 后果 |
|------|---------|---------|------|
| 共享状态 | `#include <stdatomic.h>` + `atomic_long` | 普通 `long` 全局变量 | 数据竞争，结果随机错误 |
| GIL 释放计算 | `Py_BEGIN_ALLOW_THREADS` / `Py_END_ALLOW_THREADS` | 持有 GIL 做 CPU 计算 | 无法真并行，单线程性能 |
| Python API 调用 | GIL 持有期间调用 | GIL 释放后调用 PyLong_From* 等 | 段错误，解释器崩溃 |
| 模块状态 | `m_size = sizeof(State)` + `PyModule_GetState()` | 全局变量存储状态 | 多解释器/子模块数据竞争 |
| 跨 GIL 变量 | GIL 块外声明变量 | 块内声明 result 等变量 | 编译错误（作用域外不可访问） |

#### 🔴 CMake 配置强制项

```cmake
# 1. 显式 Python 查找策略
set(Python3_FIND_STRATEGY LOCATION)
set(Python3_FIND_IMPLEMENTATIONS CPython)
if(DEFINED ENV{CONDA_PREFIX})
    set(Python3_ROOT_DIR "$ENV{CONDA_PREFIX}")
endif()
find_package(Python3 3.13 REQUIRED COMPONENTS Interpreter Development.Module)

# 2. 使用 python3_add_library
python3_add_library(my_module MODULE src/my_module.c)

# 3. 动态 SOABI 文件名（不能硬编码）
execute_process(
    COMMAND "${Python3_EXECUTABLE}" -c "import sysconfig; print(sysconfig.get_config_var('SOABI'))"
    OUTPUT_VARIABLE PYTHON_SOABI OUTPUT_STRIP_TRAILING_WHITESPACE
)
set_target_properties(my_module PROPERTIES PREFIX "" SUFFIX ".${PYTHON_SOABI}.so")

# 4. 必须定义 Py_GIL_DISABLED=1
target_compile_definitions(my_module PRIVATE Py_GIL_DISABLED=1)

# 5. 优化参数
target_compile_options(my_module PRIVATE -O3 -Wall -Wextra -Wpedantic -fno-semantic-interposition)
```

#### 🔴 依赖版本要求

| 工具 | 最低版本 | conda 安装命令 |
|------|---------|---------------|
| Python | 3.13t+ | `conda install -c conda-forge "python=3.14.*=*_cp314t"` |
| CMake | 3.27+ | `conda install -c conda-forge "cmake>=3.30"` |
| Ninja | 1.11+ | `conda install -c conda-forge "ninja>=1.12"` |
| GCC/Clang | C11 支持 | `conda install -c conda-forge c-compiler` |

**重要**：必须使用 conda-forge 渠道，defaults 渠道缺少 cp314t 构建，混合渠道会导致 ABI 冲突（详见 [TECH-ADVISORY-defaults-channel-abi-risk.md](docs/TECH-ADVISORY-defaults-channel-abi-risk.md)）。

#### 🟡 测试强制项

每个 C 扩展必须包含：
1. **自检函数**：验证基础功能正确性（模板中 `run_self_test()`）
2. **多线程压力测试**：8 线程 × 100K+ 原子操作验证无 race condition（模板中 `thread_stress()`）
3. **ABI 验证**：检查 SOABI 包含 `t` 后缀，编译时 `Py_GIL_DISABLED=1`

### 9.4 已验证的坑点与修复

| 坑点 | 错误现象 | 修复方法 |
|------|---------|---------|
| Py_VERSION 宏名错误 | 编译错误 `'Py_VERSION' undeclared` | 使用 `PY_VERSION`（全大写） |
| Thread 构造参数错误 | `group` 参数非空错误 | 使用关键字参数 `Thread(target=fn, args=(arg,))` |
| 函数指针类型警告 | ISO C 禁止函数指针→对象指针转换 | 添加 `(void*)` 强制转换 |
| shell 中 >= 被解释为重定向 | conda install 命令失败 | 包名+版本用引号：`"cmake>=3.30"` |
| GIL 块内变量声明 | `result` 未声明错误 | 在 `Py_BEGIN_ALLOW_THREADS` 之前声明变量 |
| cp 复制文件到自身 | 错误 "same file" | 目标路径与源路径不能相同 |
