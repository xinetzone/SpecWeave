# 示例驱动模式传播：构建高质量技术示例项目教程

> 本教程从 `apps/samples/` 下四个真实示例项目中萃取经验，教你如何构建一个"不仅能跑，更能传播模式"的高质量技术示例。

## 教程目标

完成本教程后，你将能够：

1. 识别一个值得通过示例传播的架构模式或工程实践
2. 按6步标准流程构建最小可运行的示例项目
3. 编写服务于模式理解的代码注释和README
4. 通过测试同时验证正确性和文档化行为
5. 避免示例开发中的4个常见反模式

## 前置知识

- 基本的 Git 和项目结构认知
- 至少阅读过一个开源项目的示例代码
- 对"设计模式"或"架构模式"有初步了解

---

## 第一步：模式提炼 — 确定示例要传播什么

### 核心原则

一个好的示例项目**只传播一个核心模式**。在写第一行代码之前，先用一句话回答：

> "这个示例要让读者理解什么模式？这个模式解决什么问题？"

### 实操方法

1. **命名模式**：给模式一个4-8字的好记名称（如"零拷贝COW读写分离"、"Workspace-first上下文治理"）
2. **界定问题**：写清这个模式解决什么痛点，不解决什么问题
3. **列出步骤**：将模式分解为3-7个可执行的核心步骤

### 案例对照

| 项目 | 传播的模式 | 模式步骤数 |
|------|-----------|:----------:|
| cow-demo | 零拷贝COW读写分离 | 5步 |
| serial-camera-controller | 三线程分离+自动降级 | 3层架构 |
| short-video-site | AI全栈快速原型流程 | 4阶段（调研→素材→开发→复盘） |
| zleap-workspace-first-prototype | Workspace-first上下文治理 | 5模块 |

### 练习

选择你最近项目中一个值得传播的实践，用一句话写出模式名称和它解决的问题。

## 第二步：最小可运行实现 — 代码是模式的具象化

### 核心原则

用**最少的代码**实现模式的核心机制。零依赖优先，依赖越少，读者越容易跑起来。

### 实操方法

1. **选择轻量技术栈**：能C++17标准库解决的不引入Boost，能Vanilla JS解决的不引入React
2. **单文件或极少文件**：核心实现尽量集中（cow-demo的核心是一个278行的hpp文件）
3. **固定接口**：先定义模式的关键API签名，再实现内部逻辑
4. **零配置启动**：读者clone后应能在3条命令内看到运行结果

### 案例对照

```bash
# cow-demo：3条命令运行
mkdir build && cd build
cmake ..
cmake --build . && ./cow_demo

# short-video-site：1步运行
# 浏览器直接打开 index.html

# zleap：1条命令运行
python main.py
```

### 代码模板（Python示例）

```python
"""
模式名称：XXX模式
一句话说明：这个模式解决什么问题

核心步骤：
  1. ...
  2. ...
  3. ...
"""

class PatternCore:
    """模式核心类 — 实现上述步骤的最小集合。

    设计要点：
    - 每个公开方法对应模式的一个步骤或能力
    - 注释解释'为什么'而非'做什么'
    """

    def __init__(self):
        # 初始化最小必要状态
        pass

    def step_one(self):
        """步骤1：...（说明这一步在模式中的角色）"""
        pass

    def step_two(self):
        """步骤2：..."""
        pass
```

## 第三步：多场景演示 — 覆盖正常路径、边界条件和回退策略

### 核心原则

提供≥3个演示场景，每个场景聚焦模式的**一个方面**，而非堆砌功能。

### 场景设计框架

| 场景类型 | 目的 | cow-demo中的对应 |
|----------|------|------------------|
| 正常路径 | 展示模式典型工作方式 | TestExclusiveAccess（独占读写） |
| 边界条件 | 展示模式在极端情况的行为 | TestEmptyBuffer（空缓冲区） |
| 分层策略 | 展示模式的条件分支 | TestN1IdentityPassthrough + TestN2MultiConsumerCOW |
| 回退机制 | 展示模式失效时的安全降级 | TestRuntimeSwitch（运行期开关） |
| 显式控制 | 展示用户主动干预模式行为 | TestExplicitUnshare |

### 实操方法

1. 列出模式的所有关键决策点
2. 为每个决策点的每个分支创建一个演示场景
3. 每个场景有明确的名称和输出说明
4. 场景之间有逻辑递进关系（从简单到复杂）

## 第四步：双向链接 — 模式文档与示例代码互相引用

### 核心原则

模式文档（抽象描述）和示例代码（具体实现）必须**双向可导航**。

### 实操方法

1. **示例README → 模式文档**：在README末尾添加"模式文档"链接
2. **模式文档 → 示例代码**：在模式文档中添加"参考实现"链接
3. **代码注释 → 模式步骤**：代码关键位置注释标注"对应模式第N步"
4. **提交信息 → 模式**：相关提交信息中标注影响的模式步骤

### 案例对照

cow-demo 的代码注释直接标注了模式步骤：

```cpp
// 第一步：const/non-const 读写API分离
const float* data() const { ... }
float* mutable_data() { ... }
```

README 末尾链接到完整模式文档：

```markdown
## 模式文档
- [zerocopy-cow-readwrite-separation.md](...) — 完整模式文档
```

## 第五步：测试即文档 — 单元测试同时是行为规范

### 核心原则

测试不仅验证正确性，更是**模式行为的可执行说明**。读者通过阅读测试了解模式在各种条件下的预期行为。

### 实操方法

1. **测试命名即行为描述**：`COW_N2MultiConsumer_WriteTriggersCopy` 比 `test_cow1` 有信息得多
2. **每个演示场景对应至少一个测试**：cow-demo 的7个演示场景在28个单元测试中都有对应
3. **测试边界条件和异常路径**：空缓冲区、并发访问、禁用开关等
4. **测试注释说明验证意图**：`// COW disabled: o1 writes to shared memory — 验证污染行为`

### 测试结构模板

```python
def test_pattern_name_condition_expected_behavior():
    """测试名称即文档：当[条件]时，[模式行为]应当[预期结果]"""
    # Arrange: 设置模式场景
    # Act: 触发模式关键操作
    # Assert: 验证模式合约（不仅是返回值，还包括状态变化）
```

### 测试覆盖率参考

| 项目 | 测试数量 | 覆盖范围 |
|------|:--------:|----------|
| cow-demo | 28个单元测试 | 构造/共享/COW/Unshare/Resize/开关/线程/空缓冲 |
| zleap | 4个单元测试+2个压测 | 记忆/模型提供/路由/工作区/延迟压力/路由压力 |
| serial-camera | 0个 | — （改进项：协议解析层可mock测试） |
| short-video-site | 0个 | — （改进项：数据加载和筛选逻辑可测试） |

## 第六步：复盘沉淀 — 记录决策过程和踩坑经验

### 核心原则

示例开发完成后，编写复盘记录"为什么这样设计"和"踩了什么坑"。这比代码本身更有传播价值。

### 复盘文档结构

1. **项目概述**：名称、时间、技术栈、定位
2. **事实记录**：开发过程中的客观事件（无因果推断）
3. **核心洞察**：从实践中提炼的3条关键认知
4. **反模式记录**：开发中犯过的错误或观察到的问题
5. **行动项**：后续改进的具体任务

### 案例对照

short-video-site 的复盘记录了关键洞察：

> "素材生成是AI全栈开发的关键瓶颈——代码生成不是瓶颈，多模态素材生成才是。"

这种来自实践的洞察，是纯理论文档无法产生的。

## 反模式清单（必须避免）

### ❌ 反模式1：功能堆砌而非模式聚焦

**表现**：示例项目试图展示登录、数据库、API、UI等所有特性，核心模式被淹没。

**正确做法**：无情裁剪不服务于模式传播的功能。cow-demo 没有文件I/O、网络、GUI——它只做COW一件事。

### ❌ 反模式2：文档声明但未交付

**表现**：README列出 `docs/tutorial.md`、`docs/api.md` 但文件不存在。

**正确做法**：要么创建文件，要么从README中移除引用。使用链接检查工具验证README中所有路径可达。

### ❌ 反模式3：示例无测试

**表现**：代码写好了但没有测试，读者无法确定示例行为是否正确，也无法在修改后验证回归。

**正确做法**：核心逻辑层测试覆盖率≥60%。硬件/UI相关部分可通过mock抽象层测试。

### ❌ 反模式4：重实现轻注释

**表现**：代码能跑但只有 `// 构造函数` 这类无意义注释，没有解释设计意图。

**正确做法**：注释解释"为什么"。cow-demo 中 `// 某些UVC摄像头的cap.set()会静默失败，因此必须实际read()验证` 这种注释才是有价值的。

## 质量自检清单

完成示例项目后，逐项检查：

- [ ] 能用一句话说清这个示例传播什么模式
- [ ] 读者可以在3条命令内运行示例
- [ ] 有≥3个演示场景，覆盖正常/边界/回退
- [ ] 核心代码有解释"为什么"的注释
- [ ] README链接的所有文件实际存在
- [ ] 有自动化测试验证核心行为
- [ ] 测试名称本身就是行为描述
- [ ] 有复盘文档记录决策和踩坑
- [ ] 模式文档和示例代码双向链接
- [ ] 无第三方依赖或依赖数量最小化

## 进阶：从示例到模式库

当你积累了3个以上高质量示例后，可以：

1. **创建模式索引**：一个表格映射每个示例到其传播的模式
2. **抽象共享基础设施**：将示例间重复的测试框架、构建脚本抽取到共享目录
3. **建立贡献模板**：为新示例提供标准化的README模板、项目骨架、复盘模板
4. **交叉引用**：相关模式之间建立链接，形成模式网络
