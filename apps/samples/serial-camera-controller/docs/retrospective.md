7. 实现文本行协议解析（CR/LF 分隔）和二进制帧协议解析（AA 55...55 AA + XOR 校验）

10. 编写 e2e 自动化测试脚本，依次发送 PING/CAP/REC/STOP/STAT 五条命令，全部通过

12. Windows COM 端口独占特性导致外部串口助手无法在控制器运行时同时打开 COM4，采用进程内模拟方式等效验证

14. 将项目整理到 apps/samples/serial-camera-controller/，包含代码、复盘、教程、协议文档

## 四、核心洞察（G2：四元组）

### 洞察 1：UVC 摄像头的 cap.set() 会静默失败

- **现象**：设置 1280x720 后 cap.set() 返回 True，但后续 read() 返回损坏的 Mat 并触发 OpenCV 断言
- **证据**：`cv2.error: (-215:Assertion failed) _step >= minstep in function 'cv::Mat::Mat'`，VID_FFFF 设备在 720p 下复现率 100%
- **反常识**：`cap.set(cv2.CAP_PROP_FRAME_WIDTH, 1280)` 返回 True 不代表设置成功；不同 UVC 芯片对 set() 的处理差异很大，部分设备静默忽略不支持的分辨率
- **行动**：任何 `cap.set()` 后必须 `read()` 一帧验证实际分辨率，不能信任返回值；实现分辨率候选列表自动降级

### 洞察 2：OpenCV 后端优先级影响设备兼容性

- **现象**：同一摄像头在 MSMF 后端正常工作，在 DSHOW 后端无法按索引打开
- **证据**：DSHOW 输出 `VIDEOIO(DSHOW): backend is generally available but can't be used to capture by index`；MSMF 成功打开 640x480@20fps
- **反常识**：DirectShow 作为 Windows 传统多媒体框架，对某些 UVC 设备的兼容性反而不如 MediaFoundation；后端选择不应按"新旧"判断，而应按实际兼容性排列
- **行动**：后端尝试顺序设为 MSMF→DSHOW→ANY，每个后端都尝试全部分辨率候选

### 洞察 3：Windows COM 端口独占是设计约束而非 Bug

- **现象**：控制器打开 COM4 后，串口助手打开 COM4 报"端口被占用"
- **证据**：Windows API CreateFile 对 COM 设备以独占方式打开，不支持多个进程同时访问
- **反常识**：Linux 下可以通过 flock  advisory lock 实现多进程协调访问，Windows 的串口独占是内核级强制的，无法绕过
- **行动**：测试时使用进程内 `_handle_text_cmd()` 调用模拟串口数据到达（代码路径完全一致）；产品部署时外部 MCU 直连 CH340 的 TX/RX 引脚，不存在 PC 端双进程问题

### 洞察 4：三线程分离比串行轮询更可靠

- **现象**：摄像头 30fps 采集循环中的 `cap.read()` 阻塞时间不确定（5-33ms），若与串口读取在同一线程，会导致串口命令响应延迟
- **证据**：单线程版本中串口命令最大响应延迟超过 100ms（等待一帧读取完成）；三线程版本中命令解析延迟 <10ms
- **反常识**：对于 I/O 密集型应用，增加线程数反而能降低延迟——因为不同 I/O 设备的等待时间可以重叠
- **行动**：摄像头采集、串口读取、命令解析分属三个线程，通过线程安全的 deque 和 Lock 传递数据

### 洞察 5：帧同步+校验和是嵌入式通信的必需品

- **现象**：MCU 启动时 bootloader 输出的杂散字节可能包含 "CAP" 等 ASCII 字符串，若纯文本匹配会误触发抓图
- **证据**：回忆经验库中类似案例（Experience 188935），STM32 启动信息中的随机字节曾导致误触发
- **反常识**：文本协议看起来"简单可靠"，但在噪声环境中比二进制帧更容易误触发；二进制帧的帧头同步+校验和提供了更强的抗干扰能力
- **行动**：实现双协议设计——文本协议用于调试（方便串口助手手动发送），二进制帧协议用于生产环境（帧头 AA 55 + XOR 校验 + 帧尾 55 AA）

## 六、对抗审查（V）

### 新人视角
- **Q: 我没有 CH340 硬件，能运行吗？**
- A: 控制器启动时会自动探测 CH340，若未找到会报错退出。可以修改 `_find_ch340()` 返回虚拟端口名配合 com0com 虚拟串口对测试，或直接在代码中实例化后调用 `_handle_text_cmd()` 测试。

- **Q: 摄像头在 Linux 上能用吗？**
- A: 代码使用 OpenCV 跨平台 API，Linux 上后端自动选择 V4L2。但自动探测 CH340 的 VID:PID 匹配逻辑可能需要调整（Linux 串口设备名为 /dev/ttyUSB0）。

### 老板视角
- **Q: 这个系统能直接用于产品吗？**
- A: 核心功能（抓图/录像/命令解析）已经验证可用，但产品化还需考虑：摄像头断连恢复的完善、录像文件的原子写入（防断电损坏）、命令鉴权（防止未授权访问）、配置文件持久化、日志轮转等。

### 魔鬼代言人
- **Q: 三线程架构是否过度设计？单线程 + 非阻塞 I/O 不行吗？**
- A: 对于这个具体场景，单线程 + select/poll 确实可行。但三线程设计的优势在于：(1) cap.read() 是阻塞调用且超时不确定，放独立线程不影响串口响应；(2) 代码逻辑清晰，每个线程职责单一；(3) Python GIL 对 I/O 密集型场景影响很小，线程切换开销可忽略。如果追求极致资源占用，可改为 asyncio 架构。

- **Q: 二进制帧协议的 XOR 校验太弱，为什么不用 CRC16？**
- A: XOR 校验可以检测所有单比特错误和大部分多比特错误，对于短帧（通常 <100 字节）和串口短距离通信已经足够。CRC16 更强但需要查找表或计算循环，在 8 位 MCU 上开销更大。如果通信环境干扰严重或帧较长，可以升级为 CRC8/CRC16。

### 未来维护视角
- **Q: 如何添加新命令？**
- A: 三步：(1) 在 _handle_text_cmd 添加文本命令别名和处理分支；(2) 如需二进制协议，在 _handle_binary_cmd 添加 CMD 常量和处理；(3) 更新 HELP 应答和协议文档。

- **Q: 如何支持多个摄像头？**
- A: 当前架构假设单个摄像头（VideoCapture(0)）。多摄像头需要将 _camera_worker 和帧缓存改为字典结构（按 camera_id 索引），命令中增加 camera_id 字段。

## 八、可复用模式萃取

### 模式 1：共享资源 + 多工作线程架构

**场景**：多个 I/O 设备需要并行服务，且各设备的阻塞时间不确定。

**核心步骤**：
1. 识别共享资源（摄像头帧、串口缓冲区）
2. 为每个 I/O 设备创建独立工作线程
3. 用 Lock 保护共享数据，用 deque/queue 做线程间传递
4. 工作线程只做 I/O + 缓冲，不做业务逻辑
5. 单独的解析/调度线程处理业务逻辑

**反模式**：在同一线程中交替轮询多个设备——一个设备阻塞会拖慢所有其他设备的响应。

### 模式 2：硬件能力探测 + 自动降级

**场景**：硬件 API 的 set() 方法可能静默失败，无法通过返回值判断是否真正生效。

**核心步骤**：
1. 准备候选值列表（从期望到保底）
2. 对每个候选值：set() → 实际操作验证 → 检查实际结果
3. 第一个通过验证的值作为最终配置
4. 全部失败则抛出明确异常

**反模式**：信任 set() 返回值，不做实际验证——导致运行时才暴露问题。

### 模式 3：双协议设计（调试协议 + 生产协议）

**场景**：同一通信通道需要兼顾人工调试便利性和机器通信可靠性。

**核心步骤**：
1. 文本行协议用于调试——串口助手直接输入，无需编码
2. 二进制帧协议用于生产——帧头同步 + 校验和 + 帧尾
3. 解析器优先尝试二进制帧，未匹配时回退到文本行
4. 两种协议调用相同的业务处理函数

**反模式**：只用文本协议（噪声环境误触发）或只用二进制协议（调试困难）。

## 十、经验总结

本次里程碑验证了从硬件识别到端到端功能验证的完整嵌入式视觉控制系统开发流程。关键经验：

1. **硬件兼容性靠实测不靠文档**：UVC 摄像头的分辨率支持和后端兼容性必须实际测试，set() 返回值不可信
2. **I/O 线程分离是低延迟的关键**：摄像头阻塞读取不应影响串口命令响应
3. **协议设计兼顾调试和生产**：文本协议 + 二进制帧协议双轨制，开发效率和运行可靠性兼得
4. **异常恢复设计不可省**：摄像头可能因 USB 挂起、带宽不足等原因临时断流，需要自动恢复
5. **Windows 串口独占需在架构设计阶段考虑**：测试方案不能假设两个 PC 进程同时访问同一端口
