# 设计依据

本页记录架构是怎么定下来的：先用第一性原理拆出不可再分的公理，再对假设做对抗攻击，
最后由存活下来的假设推出架构。**结论可以商榷，推导过程必须可复核。**

## F · 第一性原理：四条公理

剥掉「Web 应用」「Agent」「云端」这些词，剩下什么是不可再分的？

| 公理 | 表述 | 推论 |
|---|---|---|
| **A1 录入摩擦必须趋近于零** | 用户愿意记下来的前提是「不用先想清楚」 | 录入界面只有一个文本框；类型/标题/摘要/标签全部后补 |
| **A2 检索要先于分类成立** | 人记不住自己记过什么，分类是他想不起来的东西 | 关联只能由机器建立，且必须**可解释**（给不出理由的关联等于噪音） |
| **A3 能力不能依赖单一外部依赖** | 首次打开时用户还没有任何密钥 | 每个智能能力都要有等价的本地实现，降级后仍产出**可用结果** |
| **A4 私人数据不可被托管方读取** | 内容是想法与待办，含个人隐私 | 密钥不下发浏览器；BYOK 凭据不落盘；数据库可启用 RLS |

## V · 对抗性审查：四视角攻击

### 魔鬼代言人

> 「Sphinx 是静态站生成器，你拿它做需要**写操作**的应用？」

攻击成立的部分：Sphinx 产物确实不能执行服务端逻辑。
**防御**：职责切分——Sphinx 只负责**界面与文档**（这部分天然静态、且可搜索、可版本化），
写操作全部走独立的 Python 3.14 常驻服务。两者只通过 `/api/*` HTTP 契约耦合，
任一侧单独重写都不影响另一侧。

### 新人

> 「我 clone 下来什么都不配，能跑吗？」

攻击成立：多数同类项目首次运行必然报「缺少 API Key」。
**防御**：`config.py` 把「缺配置即降级」写成硬约定；`store` 无 Supabase 时退回内存；
所有提示词路径都有启发式分支。构建期守卫 `_check_app_shell` 防止改页面时
悄悄删掉前端挂载点——那正是新人最常踩的坑。

### 老板

> 「这套东西的持续成本是多少？」

攻击成立：常驻服务意味着有账单。
**防御**：静态站放 GitHub Pages（零成本、零运维）；**服务无状态**，
可跑在任何最小规格实例上，甚至关掉也不影响站点可访问（只是功能降级）。
关联分析不使用 embedding 端点，避免把 API 成本绑进最频繁的路径。

### 未来

> 「半年后数据从 100 条涨到 10 万条怎么办？」

攻击成立：当前检索取候选集后在应用层打分，是全量扫描。
**防御**：检索边界被显式封装在 `Store.list_items` 里，换成数据库侧全文检索
（Supabase 的 `tsvector` / pg_trgm）只需改这一个方法，调用方零改动。
这是**刻意留的缝**，不是遗漏。

## I · 洞察：三条决定架构的判断

1. **静态与动态的边界要画在"谁持有密钥"上**，而不是画在"哪个框架更趁手"上。
   界面不需要密钥 → 静态；写库与调模型需要密钥 → 动态。这条线一旦画错，
   要么把 Key 塞进前端（安全事故），要么为纯展示页养一台服务器（成本事故）。
2. **降级不是兜底，是第二实现。** 同类产品把「未配置」当错误弹出，
   等于把首屏体验交给用户的配置意愿。本应用把启发式实现与模型实现
   写成**同签名、同返回结构**的两条路径，降级时前端渲染代码一行都不用改。
3. **关联必须自带理由。** 相似度分数对用户没有意义，「共享标签：产品、定价」
   才有。宁可给一条朴素的统计理由，也不要给一个无法解释的高分。

## 能力矩阵与降级行为

| 能力 | 入口 | 无大模型时的行为 |
|---|---|---|
| 随手录入 + 分类/摘要/标签 | `POST /api/items` | 启发式判定，仍派生待办 |
| 自动关联 | `POST /api/items` | 相似度 + 标签重合，理由为统计口径 |
| 关键词检索 | `GET /api/items?q=` | 不受影响（本就不走模型） |
| 智能问答 | `POST /api/ask` | 返回相关度最高的原文片段 |
| 重点信息提取 | `POST /api/extract` | 统计摘要，章节结构与有模型时一致 |
| 待办整理 | `GET /api/todos` | 按首个标签分组 + 优先级排序 |
| 阶段总结 | `POST /api/summary` | 统计总结 + 未完成待办转行动建议 |
