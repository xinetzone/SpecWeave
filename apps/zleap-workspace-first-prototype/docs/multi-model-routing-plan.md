# Workspace-first 架构扩展：多模型路由规划

> 基于 `apps/zleap-workspace-first-prototype/` 现有架构，规划如何扩展支持多模型路由。
> 场景：创新突破（F→V→I→C）| 日期：2026-07-06

## 1. 第一性原理分析（F）

### 1.1 现状：单一模型绑定

当前架构中，每个 Workspace 绑定一个 `model` 字段，模型选择是**静态的、工作区级**的：

```python
Workspace(workspace_id="finance", model="local-model")
```

问题：同一工作区内的不同任务可能适合不同模型，静态绑定无法适应任务复杂度差异。

### 1.2 多模型路由的本质

多模型路由的核心是**"在正确的时机，把正确的任务，交给正确的模型"**。它需要解决三个问题：

| 问题 | 本质 | 当前架构的缺口 |
|------|------|---------------|
| 何时路由 | 任务复杂度/类型判定 | 无任务级判定 |
| 路由到哪 | 模型能力与任务匹配 | 只有工作区级静态绑定 |
| 如何路由 | 路由策略（规则/成本/能力） | 无路由层 |

### 1.3 分层推断

第一性原理下，路由应拆为三层：
1. **感知层**：判断任务类型与复杂度（是否需要强模型）
2. **策略层**：基于约束（成本/速度/数据边界）选择模型
3. **执行层**：调用目标模型，记录轨迹

## 2. 架构扩展设计

### 2.1 新增 Router 模块

在现有五大模块之上，新增 `Router` 前置层，介于 Workspace 与模型调用之间：

```
┌──────────────────────────────────────────────┐
│                    Router                    │
│  (感知层: 任务分类 → 策略层: 模型选择 → 执行层) │
├──────────────────────────────────────────────┤
│              Workspace Registry             │
│  (工作区级静态绑定 作为 兜底默认模型)          │
├──────────┬──────────┬──────────┬─────────────┤
│ Context  │  Tools   │  Memory  │  Boundary   │
└──────────┴──────────┴──────────┴─────────────┘
```

### 2.2 核心组件

```python
        # 4. 执行层：返回模型名
```

### 2.3 路由策略（策略层）

| 策略 | 触发条件 | 目标模型 | 优先级 |
|------|---------|---------|:---:|
| 数据边界策略 | 任务涉及敏感数据 | 强制本地模型 | 高 |
| 复杂度策略 | 任务复杂度 > 阈值 | 强模型 | 中 |
| 成本策略 | 任务类型为简单查询 | 便宜模型 | 中 |
| 兜底策略 | 无匹配 | 工作区默认模型 | 低 |

### 2.4 与现有边界整合

多模型路由必须**复用现有 Boundary 的模型边界检查**，确保路由结果不越权：

```python
# 路由后校验
chosen = router.route(ws_id, task)
boundary.check_model_boundary(ws)  # 校验 chosen 在 ws 白名单内
```

## 3. 对抗审查（V：魔鬼代言人视角）

对上述设计进行对抗审查，暴露潜在风险：

### 3.1 挑战：路由策略冲突
- **攻击**：多个策略同时命中时，如何保证优先级正确？数据边界策略恒优先，但复杂度策略可能更经济。
- **加固**：明确策略优先级排序，数据边界策略为硬约束（最高优先级），其余按成本-收益排序。

### 3.2 挑战：路由会增加延迟
- **攻击**：路由判定本身是额外开销，简单任务不值得。
- **加固**：提供"直通模式"（round-robin 旁路），当任务类型明确时跳过路由判定，直接使用工作区默认模型。

### 3.3 挑战：模型能力边界模糊
- **攻击**：复杂度阈值是主观设定的，无法精确衡量任务复杂度。
- **加固**：用可观测信号（token 数、工具调用数、历史轨迹耗时）作为复杂度代理，而非纯主观判断。

## 4. 扩展路线图

| 阶段 | 内容 | 验收标准 |
|------|------|---------|
| **P0 骨架** | 新增 `router.py`，实现 `ModelRouter` 类 + 基础策略接口 | 可路由到工作区默认模型 |
| **P1 策略** | 实现数据边界/复杂度/成本/兜底四种策略 | 策略优先级正确，边界不越权 |
| **P2 整合** | 接入 main.py 与 Boundary 校验 | 路由结果通过模型边界检查 |
| **P3 测试** | 新增 `test_router.py` 单元测试 | 覆盖各策略与边界交互 |

## 5. 与现有接口的兼容性

扩展**不破坏**现有接口，遵循向后兼容：
- 工作区 `model` 字段保留为**兜底默认模型**
- 现有 `BoundaryChecker.check_model_boundary()` 复用，不修改
- 新增 `Router` 为可选前置层，不改变 `ContextAssembler` 装配逻辑
