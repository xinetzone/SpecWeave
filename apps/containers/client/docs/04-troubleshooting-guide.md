# 30 秒修复速查表

`invoke` 失败时终端会自动匹配以下条目（W-I1~W-I10 为 Windows/WSL 原生坑；C-I1~C-I5 为容器/运行时坑且**与平台无关**），每个条目末尾附一行命令级修复：

| ID | 触发异常 | 根因 | 修复（30秒） |
|----|---------|------|------------|
| **W-I1** | `FileNotFoundError: .../run/user/.../podman/podman.sock No such file` | podman-py 无参构造回退是纯 Linux 路径，Windows 原生不存在该目录 | 三选一：a) 脚本改在 WSL2 内跑  b) 打开 Podman Desktop 初始化 Machine  c) `$env:CONTAINER_HOST="unix:///mnt/wsl/Ubuntu/run/user/1000/podman/podman.sock"` |
| **W-I2** | `ValueError: Unsupported URL scheme 'npipe'` | docker-py 老用户粘贴 `npipe:////./pipe/docker_engine`；podman-py 合法 scheme 中不含 npipe | 改成：`unix:///mnt/wsl/<Distro>/run/user/<UID>/podman/podman.sock` / `ssh://...` / `tcp://127.0.0.1:8888` |
| **W-I3** | `Timeout: Waiting on podman-forward-*.sock`（SSH Machine） | SSH 首次 StrictHostKeyChecking 交互阻塞在 stdin yes/no，SDK SSHSocket shell-out 的 `ssh -N -L` 子进程永不返回 | PowerShell 先跑一次：`podman machine ssh true`，提示 `Are you sure you want to continue connecting (yes/no/[fingerprint])?` 时敲 **yes** 回车，把 Machine HostKey 写入 `~/.ssh/known_hosts` |
| **W-I4** | `AttributeError: module 'os' has no attribute 'getuid'` 或 `module 'socket' has no attribute 'AF_UNIX'` | **podman-py 在 Windows 原生 CPython 结构性不可用**：`from_env()` 回退链调用 `os.getuid()`（[path_utils.py](https://github.com/containers/podman-py/blob/main/podman/api/path_utils.py)），unix/ssh 适配调用 `socket.AF_UNIX`（[uds.py](https://github.com/containers/podman-py/blob/main/podman/api/uds.py)），Windows 原生 Python 两者皆无 → 任一候选必然 AttributeError，与配置无关 | 本工具已**自动降级 CLI fallback**（`podman.exe` 子进程，正常可用）；确认可用后无需操作。如需**强制 SDK**：a) 改在 WSL2 内跑本脚本（100% Linux 行为）b) 显式设 `CONTAINER_HOST=ssh://user@127.0.0.1:<MachinePort>/run/user/1000/podman/podman.sock`（端口用 `podman system connection list --format json` 查询）。P2-machine 候选在 Windows 原生已由 `machine_connection_uri()` 自动填充该 ssh:// 值 |
| **W-I5** | `podman-compose` 任何子命令（含 `--version`）报 `ModuleNotFoundError: No module named 'podman_compose'`，但 `Scripts\podman-compose.exe` 垫片存在；`pip show` 显示 `Editable project location` 指向不存在的目录，或 pip 报警 `Ignoring invalid distribution ~odman-compose` | **僵尸 editable 安装**：dist-info/finder/console 垫片残留，但 finder 的 MAPPING 指向已删除的源码目录（历史从临时/外部目录 `pip install -e` 后目录被删；pip 中断卸载还会留下 `~odman_compose-*.dist-info`） | ①`python -m pip uninstall -y podman-compose`；②删除残留 `Lib/site-packages/~odman_compose-*.dist-info` 与 `Scripts/podman-compose.exe(.deleteme)`（TRAE 沙箱保护 conda `Scripts\`，agent 改不了时在用户终端执行）；③按宿主约定从 PyPI 正常安装 `python -m pip install "podman-compose>=1.0.0"`（**不要**从 `jupyter-podman-rootless/upstream/podman-compose` 装——那是镜像内固定 commit 的单文件快照，仅供镜像构建）。预防：编排器永远 PyPI 常规安装，禁止从临时/外部目录 editable 装 |
| **W-I6** | 裸 `podman-compose up -d` / `build` 报 `Error: no Containerfile or Dockerfile specified or found in context directory, D:\...: The system cannot find the file specified.`（退出码 125）；但同目录手工 `podman build -f <绝对路径 Containerfile.xxx> <绝对 context>` 正常 | **podman-compose 1.6.0 上游盘符误判 bug**：`podman_compose.py::is_context_git_url()`（约 L3240）用 `urllib.parse.urlparse` 识别 git URL，Windows 绝对路径被解析出 `scheme='d'`（盘符），L3245 条件 `r.scheme != "" and r.netloc == "" and r.path != ""` 误判为 git URL → 构建参数组装跳过 `-f <dockerfile>` 注入 → podman 只按默认名找 `Containerfile`/`Dockerfile`。compose 里 `build.dockerfile` 为默认名的栈不受影响，自定义名（如 xmnn 栈的 `Containerfile.xmnn-dev`）必现 | 站点包打一行补丁（重装/升级 podman-compose 后须重打）：`Lib/site-packages/podman_compose.py` 的 `is_context_git_url` 内，将 `if r.scheme != "" and r.netloc == "" and r.path != "":` 改为 `if len(r.scheme) > 1 and r.netloc == "" and r.path != "":`（盘符 scheme 恒为单字母，真实 URL scheme 均多字母；git/https/ssh/scp 判定用例不变）。**镜像内 Linux 构建无盘符不触发此 bug，vendored 1.6.0 快照保持固定 commit 不动**。验证：`podman-compose build` 下发 argv 必须含 `-f <abs>\\Containerfile.<栈名>`，随后 up -d 双端口可达 |
| **W-I7** | `inv xmnn.build-tvm` / `podman-compose exec xmnn bash /opt/xmnn-builder/scripts/build-tvm.sh` 在配置阶段报 `PermissionError: [Errno 13] Permission denied: PosixPath('/workspace/npu_tvm/build/CMakeFiles')`（`shutil.rmtree` → `os.unlink`）；容器内 `ls -lan` 显示 build/ 旧内容属主 **`65534:65534`**、目录 755，而 build/ 本身是 `0:0 777` | **9p/drvfs 跨上下文无主旧产物**：build/ 残留了**其他映射上下文**（早期 WSL/容器构建）生成的文件，在当前容器属主为 nobody(65534)。9p 服务端在 Windows 侧做权限判定——容器内 root 无 DAC 绕过、对这些文件 `chmod` 直接 EPERM，devuser(1000) 同样无法写入；新建文件恒为 0:0 777 可正常删，故**只有这批旧文件卡死**。tasks.py 旧版用裸 `shutil.rmtree` 无容错 | **一次性解封**：在宿主 PowerShell 删除构建目录（NTFS ACL 允许，容器内 9p 即时同步）：`Remove-Item -Recurse -Force "$env:...\external\chaos\npu_tvm\build"`（即 compose 挂载的宿主 NPU_TVM_PATH），随后重跑 build-tvm。**已加固**：npu_tvm `tasks.py::_clear_directory_contents` 加 onexc（只读位 chmod 重试；9p 无主文件再失败时抛中文宿主清理指引）。预防：不要在 WSL 发行版/其他容器与本栈之间混用同一宿主 build/ 目录；增量构建不加 `-f` 不清空。性能/根治：把 NPU_TVM_PATH 指向 WSL 原生克隆避开 9p（见 docs/11） |
| **W-I8** | 栈内 `exec`（如 `inv xmnn.wheel`/`build-tvm`）报 `crun: container <id> does not exist: open /mnt/wslg/runtime-dir/crun/<id>/status: No such file or directory: OCI runtime attempted to invoke a command that was not found`，退出 127；但 `podman ps -a` 显示容器 **Up**、`podman inspect --format '{{.State.Pid}} {{.State.Status}}'` 给出 PID+running、Jupyter 端口 curl 甚至仍返回 302 | **假 Up（libpod 状态与内核进程脱节）**：conmon/容器进程在 WSL 发行版回收循环中已被杀（inspect 给出的 PID 在宿主 `ps -p` 不存在、`$XDG_RUNTIME_DIR/crun/` 下只剩 `.cache`/`.empty-directory`），但 libpod sqlite 仍记 running；**stale conmon 与 rootlessport 作为孤儿进程存活**，继续 accept 端口并转发——故 ps/HTTP 均为假象。`podman ps` 与端口可达都不能证明可 exec | **定向清理（免 `wsl --shutdown`，不影响同发行版其他栈）**：①`invoke <ns>.down`（会伴随 `conmon exited prematurely`、`netavark: open container netns ... IO error`、pasta dbus 告警，均为预期，容器记录会删除）；②`wsl -d <distro> -- ss -ltnp \| grep -E '<SSH端口>\|<JUPYTER端口>'` 取孤儿 **rootlessport** PID 并 `kill`；③`wsl -d <distro> -- ps -ef \| grep <容器ID>` 取 **stale conmon** PID 并 `kill`；④复查端口 free；⑤`invoke <ns>.up --skip-build`，浸泡 70~90s 后以 `podman exec <name> echo ok` + 端口 curl 双验证。预防：exec 长任务前先跑活体探针；长会话持有 `wsl -d <distro> -- sleep infinity` 保活锚 |
| **W-I9** | Windows 原生 `invoke <ns>.*` 自动 WSL 桥接报 `bash: line 1: invoke: command not found`（exit 127）；在发行版内手动装 client 又报 `No module named pip`，或 `ERROR: No matching distribution found for jpman-common` | **桥接发行版（podman-machine-default，Fedora 43 Container Image）未备 client 运行环境**：该镜像自带 `/usr/sbin/python3` 3.14 但**不含 pip**；而 jpman-common 是 `apps/containers/shared` 的纯本地兄弟包（PyPI 无发布），直接 `pip install -e '.[compose]'` 解析依赖必失败 | 发行版内三步安装（均 `--user`，invoke/podman-compose 落 `~/.local/bin`，桥接器已自动前置 PATH）：①`python3 -m ensurepip --user`；②`cd /mnt/d/spaces/SpecWeave/apps/containers/client && python3 -m pip install --user -e ../shared -i https://pypi.tuna.tsinghua.edu.cn/simple`；③`python3 -m pip install --user -e '.[compose]' -i https://pypi.tuna.tsinghua.edu.cn/simple`。验证：`ls ~/.local/bin/invoke` 后重跑原任务 |
| **W-I10** | `podman-compose up -d` 报 `rootlessport listen tcp4 0.0.0.0:2223: bind: address already in use`（exit 125），前序日志含 `conmon exited prematurely: conmon process killed`，且同一次 up 先打印旧容器 ID 又打印新容器 ID（2222/2224、8888/8892 同族） | **跨控制平面标签分歧**（2026-09-15 三次确定性复现）：在 overlay 目录裸跑 Windows 原生 `podman-compose` 给容器打 `com.docker.compose.project.config_files=D:\...`，而 Windows `invoke`（透明桥接）/WSL 内 invoke 固定用 `--file /mnt/d/...`；compose 把该标签**原文**纳入 config-hash，两平面交替操作即判配置漂移强制 recreate；podman-compose 1.6 pod 模式强拆 infra conmon 时 rootlessport 已被 WSL `/init` 收养成为孤儿继续监听，新 pod bind 失败（**即使先优雅 down 也可能留同样孤儿**，真机实证） | **invoke 路径已自动自愈**：`invoke <ns>.up` 前过 `overlay_core.up_preflight` 三道——① Created/Exited 项目残留先 `compose down`；② 活体容器 config_files 标签原文与本平面 `--file` 不一致先优雅 down（禁止做 `/mnt/d`↔`D:\` 路径等价归一，hash 按原文算）；③ 无活体项目容器仍有 rootlessport 监听本栈端口则 `ss -ltnp` 定位定点 kill（只认进程名 rootlessport，绝不碰他栈 pasta），随后 up。裸 compose 翻车后直接重跑 `invoke <ns>.up --skip-build` 即可恢复。**纪律**：同一栈固定单一控制平面，勿在 Windows 裸 compose 与 invoke 之间来回切换；手工定向清理见 compose-overlay-ops SOP §9；`wsl --shutdown` 仅作最后手段（波及同发行版全部栈） |
| **C-I1** | 同一 `FileNotFoundError: .../run/user/.../podman/podman.sock No such file`，但出现在**容器内** SDK 调用（bootstrap `env.run-cmd`/`env.shell` 或常驻容器 JupyterLab Web Terminal）；容器内 CLI `podman images` 同时报 `open ${XDG_RUNTIME_DIR}/libpod/tmp/pause.pid: no such file or directory` 与 `error creating temporary file: Permission denied` | 容器内两个根因叠加：① 从无运行中的 podman daemon（bootstrap 用 `--entrypoint /usr/bin/tini` 跳过 `entrypoint.sh::setup_podman()`，或常驻容器旧版从不拉起 service），`from_env()` 回退到纯 Linux 默认路径连不存在的 rootless UDS socket → `APIError`；② rootless podman 初始化时未预建 `${XDG_RUNTIME_DIR}/libpod/tmp/`（`pause.pid` 落盘目录），缺目录触发 ENOENT / `Permission denied`（devuser 自 2026-09-11 起固定 UID 1000） | bootstrap 由 `PODMAN_SERVICE_BOOT` 自动拉起 `podman system service --time=0` 并预建 `libpod/tmp`（见 `src/jpman_client/tasks/env_in_container.py`）；常驻容器由方案 A 保证：`entrypoint.sh::setup_podman()` 默认拉起 service + 预建 `${XDG_RUNTIME_DIR}/libpod/tmp` + `jupyter.conf` 改 `user=devuser` 并以 `%(ENV_CONTAINER_HOST)s` / `%(ENV_XDG_RUNTIME_DIR)s` 继承 entrypoint 导出的运行时路径（路径以 `id -u` 动态派生，**不在配置里写死 `/run/user/<uid>`**） |
| **C-I2** | 同上 `PermissionError` 类，但为 **`[Errno 13] Permission denied` / EACCES**（非 ENOENT）：SDK 报 `podman/api/uds.py::UDSSocket.connect() → PermissionError: [Errno 13] Permission denied`；CLI 报 `dial unix /run/user/<uid>/podman/podman.sock: connect: permission denied` | **容器内 devuser 无权访问宿主直通 socket**：宿主 rootless socket（宿主 `<uid>:<gid>` 0660）经 bind-mount + userns 映射进容器后呈现为 `root:root 0660`，而 devuser 是非 root UID（固定 1000，≠0）且镜像基线未将其加入 socket 属组（`/etc/group` 的 `root:x:0:` 无成员）→ `socket.connect()` 直接 EACCES。**与 C-I1 的语义差异**：C-I1 是 socket/目录不存在（ENOENT），C-I2 是存在但无权限（EACCES）。**代价与红线**：让 devuser 入 socket 属组会扩大其组权限；**严禁 `chmod 666`/`chown` 宿主 socket**（会改到宿主 socket 本体、破坏宿主侧权限） | `entrypoint.sh::setup_podman()` 的 **B-scheme** 分支自动 `stat -Lc '%G' <host_sock>` 解析属组并 `usermod -aG <socket组> ${NON_ROOT_USER}`，随后以 devuser 身份实测 socket 可读写（`su - devuser -c "test -r/-w ..."`，失败仅告警不阻断）。**时机关键**：该步骤必须早于 `exec /usr/bin/supervisord`——supervisord 的 `drop_privileges()` 在 spawn 子进程时才用 `grp.getgrall()` 派生补充组，已在运行的 jupyter 进程不受后续 usermod 影响，故须重建镜像/重启容器生效。自检：容器内 `supervisorctl status jupyter` 取 PID 后 `/proc/<pid>/status` 的 `Groups` 应含 socket 属组 |
| **C-I3** | podman 原生报错 `Error: statfs <路径>: no such file or directory`（卷缺失）或 `Error: stat <路径>: no such file or directory`（设备缺失），退出码 125 | **运行时透传资源在 daemon 宿主上不存在**：`--wayland` / `--gpu` / `--usb` / `--dbus` 挂载的 socket 或设备节点是 **WSL2 / Podman Machine 内**的路径，而 podman 对缺失路径**硬失败且不会自动创建**（`:ro`/`:rw`/裸挂载表现一致）；客户端可能跑在 Windows 原生 CPython 上，本机 `Path.exists()` 对这些路径必然为假，**故不做本机预检**（否则会误判并拒绝正确的透传请求） | 先确认资源在 daemon 宿主真实存在：`podman machine ssh "test -e <路径>"`（Machine）或 `wsl -d <Distro> -- test -e <路径>`（WSL2）；路径不同则用 `HOST_XDG_RUNTIME_DIR` / `HOST_WAYLAND_DISPLAY` / `DBUS_SESSION_BUS_PATH` / `GPU_DEVICE` / `USB_DEVICE` 覆盖；宿主本就不具备该资源时**去掉对应开关**（详见 [09-passthrough.md](09-passthrough.md)） |
| **C-I4** | `Error: payload does not match any of the supported image formats (oci, oci-archive, dir, docker-archive)`，退出码 125（`invoke load`） | 三种成因按概率排序：① POSIX shell 误用 `type <tar> \| podman load`——`type` 在 bash/zsh/dash 是"显示命令类型"内建而非 Windows cmd 的读文件命令，喂给 podman 的是文本/空流（本工具 2026-09-12 前的跨平台回归，已修复）；② `cat <tar> \| podman load` 在 **podman 3.4.x**（RHEL8/Ubuntu22.04 自带）stdin 路径对未压缩 docker-archive 误报本错误，同一文件 `podman load -i` 正常；③ 归档真的损坏或被新版 podman 特性写入而旧版无法解析 | 本工具在 POSIX 已自动改用 `podman load -i <tar>`（Windows 原生保留 `type \|` 管道）。仍报错时依次执行：`tar tf <tar> \| head`（应列出 `manifest.json`）→ `podman load -i <tar>` → 升级 podman（建议 ≥4）或在构建端重新 `invoke save` |
| **C-I5** | `invoke run` 报 `Error: statfs /run/user/<uid>/podman/podman.sock: no such file or directory`，退出码 125 | B-scheme **必选核心挂载**源缺失（与 C-I3 的 opt-in 透传不同），两类根因：① UID 漂移——socket 路径 UID 默认取**本机事实**（`$XDG_RUNTIME_DIR` 末段 → `id -u`，可用 `PODMAN_RUNTIME_UID` 显式覆盖），daemon 宿主 UID 不同即路径错；② 宿主用户级 API socket 单元未启动（`podman.socket` inactive；本机 podman CLI 直连不需要它，但容器 B-scheme 经 REST socket 复用宿主 daemon，必需） | 原生 Linux 上工具会自动执行 `systemctl --user start podman.socket` 后重试；自动修复失败时：①`id -u` 核对并 `export PODMAN_RUNTIME_UID=<值>`；②手工 `systemctl --user start podman.socket`；③重启丢失则 `sudo loginctl enable-linger $USER`。无 systemd 环境手工运行 `podman system service --time=0 unix:///run/user/$(id -u)/podman/podman.sock` |
