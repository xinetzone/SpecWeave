# 30 秒修复速查表

`invoke` 失败时终端会自动匹配以下条目（W-I1~W-I19 为 Windows/WSL 原生坑与栈侧语义坑；C-I1~C-I10 为容器/运行时坑且**与平台无关**），每个条目末尾附一行命令级修复：

| ID | 触发异常 | 根因 | 修复（30秒） |
|----|---------|------|------------|
| **W-I1** | `FileNotFoundError: .../run/user/.../podman/podman.sock No such file` | podman-py 无参构造回退是纯 Linux 路径，Windows 原生不存在该目录 | 三选一：a) 脚本改在 WSL2 内跑  b) 打开 Podman Desktop 初始化 Machine  c) `$env:CONTAINER_HOST="unix:///mnt/wsl/Ubuntu/run/user/1000/podman/podman.sock"` |
| **W-I2** | `ValueError: Unsupported URL scheme 'npipe'` | docker-py 老用户粘贴 `npipe:////./pipe/docker_engine`；podman-py 合法 scheme 中不含 npipe | 改成：`unix:///mnt/wsl/<Distro>/run/user/<UID>/podman/podman.sock` / `ssh://...` / `tcp://127.0.0.1:8888` |
| **W-I3** | `Timeout: Waiting on podman-forward-*.sock`（SSH Machine） | SSH 首次 StrictHostKeyChecking 交互阻塞在 stdin yes/no，SDK SSHSocket shell-out 的 `ssh -N -L` 子进程永不返回 | PowerShell 先跑一次：`podman machine ssh true`，提示 `Are you sure you want to continue connecting (yes/no/[fingerprint])?` 时敲 **yes** 回车，把 Machine HostKey 写入 `~/.ssh/known_hosts` |
| **W-I4** | `AttributeError: module 'os' has no attribute 'getuid'` 或 `module 'socket' has no attribute 'AF_UNIX'` | **podman-py 在 Windows 原生 CPython 结构性不可用**：`from_env()` 回退链调用 `os.getuid()`（[path_utils.py](https://github.com/containers/podman-py/blob/main/podman/api/path_utils.py)），unix/ssh 适配调用 `socket.AF_UNIX`（[uds.py](https://github.com/containers/podman-py/blob/main/podman/api/uds.py)），Windows 原生 Python 两者皆无 → 任一候选必然 AttributeError，与配置无关 | 本工具已**自动降级 CLI fallback**（`podman.exe` 子进程，正常可用）；确认可用后无需操作。如需**强制 SDK**：a) 改在 WSL2 内跑本脚本（100% Linux 行为）b) 显式设 `CONTAINER_HOST=ssh://user@127.0.0.1:<MachinePort>/run/user/1000/podman/podman.sock`（端口用 `podman system connection list --format json` 查询）。P2-machine 候选在 Windows 原生已由 `machine_connection_uri()` 自动填充该 ssh:// 值 |
| **W-I5** | `podman-compose` 任何子命令（含 `--version`）报 `ModuleNotFoundError: No module named 'podman_compose'`，但 `Scripts\podman-compose.exe` 垫片存在；`pip show` 显示 `Editable project location` 指向不存在的目录，或 pip 报警 `Ignoring invalid distribution ~odman-compose` | **僵尸 editable 安装**：dist-info/finder/console 垫片残留，但 finder 的 MAPPING 指向已删除的源码目录（历史从临时/外部目录 `pip install -e` 后目录被删；pip 中断卸载还会留下 `~odman_compose-*.dist-info`） | ①`python -m pip uninstall -y podman-compose`；②删除残留 `Lib/site-packages/~odman_compose-*.dist-info` 与 `Scripts/podman-compose.exe(.deleteme)`（TRAE 沙箱保护 conda `Scripts\`，agent 改不了时在用户终端执行）；③按宿主约定从 PyPI 正常安装 `python -m pip install "podman-compose>=1.0.0"`（**不要**从 `jupyter-podman-rootless/upstream/podman-compose` 装——那是镜像内固定 commit 的单文件快照，仅供镜像构建）。预防：编排器永远 PyPI 常规安装，禁止从临时/外部目录 editable 装 |
| **W-I6** | 裸 `podman-compose up -d` / `build` 报 `Error: no Containerfile or Dockerfile specified or found in context directory, D:\...: The system cannot find the file specified.`（退出码 125）；但同目录手工 `podman build -f <绝对路径 Containerfile.xxx> <绝对 context>` 正常 | **podman-compose 1.6.0 上游盘符误判 bug**：`podman_compose.py::is_context_git_url()`（约 L3240）用 `urllib.parse.urlparse` 识别 git URL，Windows 绝对路径被解析出 `scheme='d'`（盘符），L3245 条件 `r.scheme != "" and r.netloc == "" and r.path != ""` 误判为 git URL → 构建参数组装跳过 `-f <dockerfile>` 注入 → podman 只按默认名找 `Containerfile`/`Dockerfile`。compose 里 `build.dockerfile` 为默认名的栈不受影响，自定义名（如 native 栈的 `Containerfile.native-dev`）必现 | 站点包打一行补丁（重装/升级 podman-compose 后须重打）：`Lib/site-packages/podman_compose.py` 的 `is_context_git_url` 内，将 `if r.scheme != "" and r.netloc == "" and r.path != "":` 改为 `if len(r.scheme) > 1 and r.netloc == "" and r.path != "":`（盘符 scheme 恒为单字母，真实 URL scheme 均多字母；git/https/ssh/scp 判定用例不变）。**镜像内 Linux 构建无盘符不触发此 bug，vendored 1.6.0 快照保持固定 commit 不动**。验证：`podman-compose build` 下发 argv 必须含 `-f <abs>\\Containerfile.<栈名>`，随后 up -d 双端口可达 |
| **W-I7** | `inv native.build-tvm` / `podman-compose exec native bash /opt/native-builder/scripts/build-tvm.sh` 在配置阶段报 `PermissionError: [Errno 13] Permission denied: PosixPath('/workspace/npu_tvm/build/CMakeFiles')`（`shutil.rmtree` → `os.unlink`）；容器内 `ls -lan` 显示 build/ 旧内容属主 **`65534:65534`**、目录 755，而 build/ 本身是 `0:0 777` | **9p/drvfs 跨上下文无主旧产物**：build/ 残留了**其他映射上下文**（早期 WSL/容器构建）生成的文件，在当前容器属主为 nobody(65534)。9p 服务端在 Windows 侧做权限判定——容器内 root 无 DAC 绕过、对这些文件 `chmod` 直接 EPERM，devuser(1000) 同样无法写入；新建文件恒为 0:0 777 可正常删，故**只有这批旧文件卡死**。tasks.py 旧版用裸 `shutil.rmtree` 无容错 | **一次性解封**：在宿主 PowerShell 删除构建目录（NTFS ACL 允许，容器内 9p 即时同步）：`Remove-Item -Recurse -Force "$env:...\external\chaos\npu_tvm\build"`（即 compose 挂载的宿主 NPU_TVM_PATH），随后重跑 build-tvm。**已加固**：npu_tvm `tasks.py::_clear_directory_contents` 加 onexc（只读位 chmod 重试；9p 无主文件再失败时抛中文宿主清理指引）。预防：不要在 WSL 发行版/其他容器与本栈之间混用同一宿主 build/ 目录；增量构建不加 `-f` 不清空。性能/根治：把 NPU_TVM_PATH 指向 WSL 原生克隆避开 9p（见 docs/11） |
| **W-I8** | 栈内 `exec`（如 `inv native.wheel`/`build-tvm`）报 `crun: container <id> does not exist: open /mnt/wslg/runtime-dir/crun/<id>/status: No such file or directory: OCI runtime attempted to invoke a command that was not found`，退出 127；但 `podman ps -a` 显示容器 **Up**、`podman inspect --format '{{.State.Pid}} {{.State.Status}}'` 给出 PID+running、Jupyter 端口 curl 甚至仍返回 302 | **假 Up（libpod 状态与内核进程脱节）**：conmon/容器进程在 WSL 发行版回收循环中已被杀（inspect 给出的 PID 在宿主 `ps -p` 不存在、`$XDG_RUNTIME_DIR/crun/` 下只剩 `.cache`/`.empty-directory`），但 libpod sqlite 仍记 running；**stale conmon 与 rootlessport 作为孤儿进程存活**，继续 accept 端口并转发——故 ps/HTTP 均为假象。`podman ps` 与端口可达都不能证明可 exec | **定向清理（免 `wsl --shutdown`，不影响同发行版其他栈）**：①`invoke <ns>.down`（会伴随 `conmon exited prematurely`、`netavark: open container netns ... IO error`、pasta dbus 告警，均为预期，容器记录会删除）；②`wsl -d <distro> -- ss -ltnp \| grep -E '<SSH端口>\|<JUPYTER端口>'` 取孤儿 **rootlessport** PID 并 `kill`；③`wsl -d <distro> -- ps -ef \| grep <容器ID>` 取 **stale conmon** PID 并 `kill`；④复查端口 free；⑤`invoke <ns>.up --skip-build`，浸泡 70~90s 后以 `podman exec <name> echo ok` + 端口 curl 双验证。预防：exec 长任务前先跑活体探针；长会话持有 `wsl -d <distro> -- sleep infinity` 保活锚 |
| **W-I9** | Windows 原生 `invoke <ns>.*` 自动 WSL 桥接报 `bash: line 1: invoke: command not found`（exit 127）；在发行版内手动装 client 又报 `No module named pip`，或 `ERROR: No matching distribution found for jpman-common` | **桥接发行版（podman-machine-default，Fedora 43 Container Image）未备 client 运行环境**：该镜像自带 `/usr/sbin/python3` 3.14 但**不含 pip**；而 jpman-common 是 `apps/containers/shared` 的纯本地兄弟包（PyPI 无发布），直接 `pip install -e '.[compose]'` 解析依赖必失败 | 发行版内三步安装（均 `--user`，invoke/podman-compose 落 `~/.local/bin`，桥接器已自动前置 PATH）：①`python3 -m ensurepip --user`；②`cd /mnt/d/spaces/SpecWeave/apps/containers/client && python3 -m pip install --user -e ../shared -i https://pypi.tuna.tsinghua.edu.cn/simple`；③`python3 -m pip install --user -e '.[compose]' -i https://pypi.tuna.tsinghua.edu.cn/simple`。验证：`ls ~/.local/bin/invoke` 后重跑原任务 |
| **W-I10** | `podman-compose up -d` 报 `rootlessport listen tcp4 0.0.0.0:2223: bind: address already in use`（exit 125），前序日志含 `conmon exited prematurely: conmon process killed`，且同一次 up 先打印旧容器 ID 又打印新容器 ID（2222/2224、8888/8892 同族） | **跨控制平面标签分歧**（2026-09-15 三次确定性复现）：在 overlay 目录裸跑 Windows 原生 `podman-compose` 给容器打 `com.docker.compose.project.config_files=D:\...`，而 Windows `invoke`（透明桥接）/WSL 内 invoke 固定用 `--file /mnt/d/...`；compose 把该标签**原文**纳入 config-hash，两平面交替操作即判配置漂移强制 recreate；podman-compose 1.6 pod 模式强拆 infra conmon 时 rootlessport 已被 WSL `/init` 收养成为孤儿继续监听，新 pod bind 失败（**即使先优雅 down 也可能留同样孤儿**，真机实证） | **invoke 路径已自动自愈**：`invoke <ns>.up` 前过 `overlay_core.up_preflight` 三道——① Created/Exited 项目残留先 `compose down`；② 活体容器 config_files 标签原文与本平面将下发的 `--file` **原文集**不一致先优雅 down（**期望集含 `--gpu` 的覆盖文件**，与 `compose_argv` 同源推导，C23——写死单文件会让 `up --gpu` 每次都假判「他平面创建」而强制重建；禁止做 `/mnt/d`↔`D:\` 路径等价归一，hash 按原文算，且必须精确同集比较、不得放宽为前缀/子集匹配）；③ 无活体项目容器仍有 rootlessport 监听本栈端口则 `ss -ltnp` 定位定点 kill（只认进程名 rootlessport，绝不碰他栈 pasta），随后 up。裸 compose 翻车后直接重跑 `invoke <ns>.up --skip-build` 即可恢复。**纪律**：同一栈固定单一控制平面，勿在 Windows 裸 compose 与 invoke 之间来回切换；手工定向清理见 compose-overlay-ops SOP §9；`wsl --shutdown` 仅作最后手段（波及同发行版全部栈） |
| **W-I11** | Windows 原生 `inv <ns>.build`（或任何桥接任务）没有执行任务，终端却出现 shell 提示符/wslmotd 文案（*automatically entered into a nested process namespace... to log out you need to exit twice*），原构建命令丢失 | **桥接误用登录 shell 被 enterns 劫持**（2026-09-16 实证）：桥接器曾用 `wsl -d podman-machine-default -- bash -lc <任务>`，Fedora-WSL 系发行版的 `/etc/profile.d/enterns.sh` 在检测到嵌套 systemd（非 PID 1）时无参执行 `/usr/local/bin/enterns`，对普通用户走 `sudo nsenter -m -p ... su -l $USER`——拉起一个交互式登录 shell，`bash -lc` 携带的任务串被丢弃；同目录 `docker-host.sh` 还会在 podman 未就绪时污染 `DOCKER_HOST=unix://` | **已自动修复（升级后零操作）**：桥接改用非登录 `bash -c`（PATH 显式前置 `~/.local/bin`、LANG 兜底 C.UTF-8），不再读 profile，enterns 与 docker-host 均不触发。手工验证：重跑 `inv <ns>.build` 应直接出现 `podman build` 流式输出。**纪律**：在该发行版内手工执行命令时不要用 `wsl -d <d>` 裸开登录会话跑自动化；脚本路径用 `wsl -d <d> -- bash <script>`（非登录，与 `.temp/xmnn-launch/run-inv.sh` 同构） |
| **W-I12** | 任何 `podman`/`inv <ns>.*`（含 WSL 内原生 invoke）报 `creating events dirs: mkdir /run/user/1000: permission denied`（exit 125），前序 warning `RunRoot is pointing to a path (/run/user/1000/containers) which is not writable`；常发生在 WSL/终端一段时间空闲、容器呈 `Exited (0) 292 years ago` 之后 | **VM 回收后 tmpfs 运行时目录未重建**：`/run/user/<uid>` 位于 tmpfs，正常由 systemd-logind/pam 登录会话创建；podman-machine-default 无 systemd 于 PID 1，VM 被 WSL 回收重启后会话若未经 enterns 进入 systemd 命名空间，该目录不重建，rootless podman 硬编码回退到此即崩（注意：仅设置 `XDG_RUNTIME_DIR=/mnt/wslg/runtime-dir` 不能替代该目录，events dir 仍走 `/run/user/<uid>`） | **已自动修复（零操作）**：`inv <ns>.*` 的 Linux 放行路径调用 `ensure_wsl_rootless_runtime()`，在 WSL2 下用 `sudo -n` 幂等 `mkdir/chown/chmod 700` 重建（免密 sudo 不可用时打印手工命令不阻断）。一次性手工修复：`sudo mkdir -p /run/user/$(id -u) && sudo chown $(id -u):$(id -u) /run/user/$(id -u) && sudo chmod 700 /run/user/$(id -u)`，随后 `inv <ns>.up --skip-build` 恢复被回收的栈；会话期间持有 `wsl -d podman-machine-default -- sleep infinity` 保活锚 |
| **W-I13** | `inv <ns>.wheel`/`build-tvm`/`build` 等长任务经透明桥接执行，**容器内任务实际成功**（日志末尾可见 🎉/COMPLETE、产物已生成），但终端抛 `invoke.exceptions.ThreadException`，线程栈指向 `invoke/terminals.py bytes_to_read → fcntl.ioctl(input_, termios.FIONREAD, b"  ")` → `SystemError: buffer overflow`，桥接层报 `WSL 桥接命令失败 (exit=1)` | **invoke 3.0.3 × Python 3.14 stdin 转发线程崩溃（假失败）**：invoke 对 TTY stdin 用 **2 字节**缓冲调 `FIONREAD`（按 signed short 解析），而 Linux 内核固定写回 `sizeof(int)`=4 字节；Python 3.14 加固 fcntl 后越界写直接 `SystemError`（与输入队列字节数无关，0 字节也必崩，py3.14.2 实证）。WSL 透明桥接的 stdin 是 console 中继 pty（`isatty=真`），`pty=True` 启动的 stdin 转发线程在长任务收尾（中继 fd 半关闭/可读）时必触发；重定向（`> log`）不影响，退出码恒 1 造成脚本/CI 假失败 | **已自动修复（升级后零操作）**：① `jpman_common.proc.run_cmd` 默认注入 `in_stream=False`——编排命令全部非交互，invoke 因此根本不创建 stdin 转发线程（Ctrl+C 仍经 KeyboardInterrupt→send_interrupt 信号路径传播）；② 同时打兼容补丁（`apply_invoke_stdin_compat`，4 字节缓冲重做 `FIONREAD`，**同时替换 `invoke.terminals` 与 `invoke.runners` 的 from-import 名字绑定**），为真交互式入口（`env.shell`、builder `interact.shell`/exec，显式 `forward_stdin=True` opt-in）兜底 py3.14 键盘输入。手工逃生：WSL 内 `pip install --user --upgrade invoke`（上游修复后）；判别要点——构建日志成功却 exit 1、栈中有 `FIONREAD`/`buffer overflow` 即本条，勿误判为构建失败而重跑长任务 |
