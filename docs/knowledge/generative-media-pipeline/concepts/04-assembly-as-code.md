# 04 组装即代码

## 1. 核心主张

**成片不是一次性的操作结果，而是一段可以从参数重跑的程序。**
这条主张带来三个直接好处：
1. 改一个时间码就能重出片，不用重搭一遍剪辑流程；
2. 段落表本身就是文档——它比任何描述性文档都更接近"实际发生了什么"；
3. 参数是数据，因此可以对数据做机械校验（帧数配平、规格对读）。

## 2. 段落表：时间轴的唯一表达

把成片表达为「类型 + 源 + 帧数」的序列：

```python
plan = []

def add(kind, src, n):
    plan.extend([(kind, src)] * n)

add("clip", "V01", 120)     # 素材段：视频
add("black", None, 120)    # 有信息空段：黑场（承载台词）
add("kb",   "KF03", 120)   # 无信息空段：静帧延展拍
add("card", "C08", 16)     # 卡片段：字幕卡 / 标题卡
add("black", None, 24)

assert len(plan) == TOTAL, len(plan)     # 帧数配平的最后一道关
```

段落类型至少要区分这几类：

| 类型 | 含义 | 帧数来源 |
|---|---|---|
| `clip` | 视频素材段 | 素材实际时长 |
| `kb` | 静帧延展拍（Ken Burns） | 目标时长（通常 5s 一段） |
| `black` | 黑场（承载台词或呼吸） | 目标时长 |
| `card` | 文字卡片 | 目标时长，多张叠化时共享 |

**段落表是唯一的时间轴来源。** 文档里的时间码表应当由它生成，而不是手写。

### 2.1 assert 的价值：拦下配平错误

本教程的实践里，段落表曾因三行卡片各写 60 帧（应为 16×3=48）导致总长 2172 ≠ 2160。这个错误**肉眼完全看不出来**——它在 `add()` 调用里分散着，只有累加才知道。

`assert len(plan) == TOTAL` 就是那道关。**每一条会改变总时长的路径，最后都要经过同一个累加点。**

## 3. 缺口显式化

### 3.1 先算缺口

```
缺口 = 目标时长 − 素材总时长
```

**这个数必须在组装之前落到文档里。** 本教程的实践：目标 90.00s，素材 50.32s，缺口 39.68s。

不先算这个数，就会出现两种坏结果：要么开工后发现不够，要么中途才发现不够——两种都会导致赶工。

### 3.2 空段分两类

| 类别 | 定义 | 本教程实践中的形态 | 作用 |
|---|---|---|---|
| **2a 有信息空段** | 承载新增叙事信息 | 黑场 + 字幕（台词） | 推进叙事 / 落声音点 |
| **2b 无信息空段** | 同一画面的时间延展，无新增信息 | 静帧延展拍（Ken Burns） | 视觉系统切换 / 呼吸 / 补时长 |

**必须分开统计。** 合并会让"无信息延展占比偏高"被叙事性黑场掩盖——黑场占 23.3% 看着是风格选择，但里面若有一半是无台词的纯延时，问题的性质完全不同。

### 3.3 空段的最小规格

空段不是"随便填满"。每类空段都要有最小参数：

| 空段 | 最小规格 |
|---|---|
| 静帧延展拍 | 缩放 1.00→1.08 + smoothstep 缓动 + 12 帧淡入淡出斜坡 |
| 黑场 + 台词 | 与字幕帧区间一一绑定，字幕有 12 帧淡入 / 淡出 |

**Ken Burns 缓推的实现**：

```python
def ken_burns(img, i, n):
    t = i / max(1, n - 1)
    s = 1.00 + 0.08 * (t * t * (3 - 2 * t))     # smoothstep 缓动
    nh, nw = int(img.shape[0] * s), int(img.shape[1] * s)
    r = (nh - img.shape[0]) // 2
    c = (nw - img.shape[1]) // 2
    return img[r:r + img.shape[0], c:c + img.shape[1]]
```

`smoothstep`（`t²(3−2t)`）比线性缓动好在**两端速度为零**：延展拍不会"啪"地开始或"啪"地停住。

### 3.4 空段用途：类型默认 + 例外手写

逐段手写用途理由在赶工时第一个被牺牲。折中做法：

- `kb` 的**默认用途** = 视觉系统切换 / 呼吸；
- `black+subtitle` 的**默认用途** = 台词承载；
- **只有超出默认用途时**才需手写理由。

这把写作量从"逐段"降到"逐例外"，而设计意图仍然留在文档里。

## 4. 单一手写源：规格与产物不再分叉

### 4.1 分叉是怎么发生的

本教程的实践里，成片完成后做了一次规格—产物对读，发现四处不一致：

| 项 | 规格写的 | 实际是 |
|---|---|---|
| 帧率 | 30fps | 24fps |
| 素材时长 | 5s | 5.04s |
| 资产状态 | "待关键帧" / "制作中" | 全部已落盘 |
| 字幕文本 / 卡片点位 | 手写在规格表 | 又手写了一份在源码里 |

**根因是同一个事实有两处手写。允许同一事实有两处手写，就等于允许它有两处不同的值。**

更值得注意的是：**这些分叉没有任何一方主动报错**。因为交付核对表覆盖的是"文件是否落盘"——那是最容易自动化的部分，于是给了"已收口"的错觉。

### 4.2 最小改造

把所有会变的事实抽到**一个**手写文件，其余全部由它生成：

```
single-source.json          ← 唯一手写处
  { fps, width, height, total_frames,
    segments: [ {type, src, frames} ],
    subtitles: [ {text, from_frame, to_frame} ],
    cards:     [ {file, from_frame, to_frame} ] }

generate.py  →  ① 生成组装用的 plan（供脚本 import）
              →  ② 生成规格表（Markdown）
              →  ③ 组装前 assert(plan 累加 == total_frames)
              →  ④ 组装后 diff(生成的规格表 ↔ 实际产出的参数)
```

关键点：**规格不再手写，它是被生成的**。这样"规格与产物不一致"在结构上就不可能发生。

### 4.3 机械对读

对读的目标必须是**实际产出的参数**，不能是源码常量——否则是自己验自己。

```
差异数 = 0   →  允许标记"已收口"
差异数 > 0   →  报告里逐条列出，不允许标记收口
```

**存在性 vs 有效性**：检验标准写成"表里有这一行"是存在性判定，很容易被形式化满足。真正要的是**有效性判定**——差异数 = 0。

### 4.4 交付核对表的正确形态

核对表要分两类，不能只列第一类：

| 类别 | 例子 | 判定 |
|---|---|---|
| 资产完整性 | 卡片 12/12、关键帧 4/4、视频段 8/8 | 文件存在且可读 |
| 知识同步性 | 规格版本 ↔ 产物版本、最后对读时间、差异数 | 差异数 = 0 |

只列第一类，就会用"文件都在"冒充"已收口"。

### 4.5 对读器本身必须被攻击，否则「差异数 = 0」是空的

上面 4.3 说"对读目标必须是实际产出的参数，不能是源码常量——否则是自己验自己"。
这条只解决了**对读对象**的诚实性，还有另一半：**对读器自己是否真的在检查**。

一个从没被攻击过的对读脚本和一个空函数是同一种东西：它同样输出 `差异数 = 0`。
所以必须有一层**攻击回归**——主动做坏，然后要求对读器报出差异：

| 攻击 | 做法 | 合格的对读器必须报出 |
|---|---|---|
| 手改生成物 | 把规格里的帧率从 24 改成 30 | 差异数 > 0，且指出第几行不同 |
| 改源不重渲染 | 改了源却没重跑管线 | 差异数 > 0（源指纹 ≠ 产物指纹） |
| 产物截断 | 把成片截断到 1/3 | 帧数差异（必须**实际解码**数帧，不能只信容器头） |
| 产物字节篡改 | 改一个字节 | sha256 差异 |
| 生成器说谎 | 让生成器输出一个**自洽但错误**的值，再重新生成规格 | 差异数 > 0（靠独立断言，不靠重渲染比对） |

最后一类是最关键的一类。**重渲染比对是自比对**：生成器既写又判，它写错的时候两边会
一起错，比对必然通过。所以必须另有一组**不经过生成器**的独立断言——
直接从源读出值，用另一套代码去规格里找，找不到就报错。

三条实践判据：

1. **攻击要打在磁盘副本上**，不是内存对象——否则你测的是 mock 不是护栏；
2. **模块必须确认从沙箱载入**（比对 `__file__` 目录）。
   静默 import 到真实项目是最隐蔽的假阳性：攻击"生效"了，测的却是一份没被改动的护栏；
3. **必须有元测试**：把护栏函数体整个删掉，再跑攻击，套题必须**变红**。
   若此时仍显示通过，说明套题在骗你——所谓"全部通过"只是巧合。

### 4.6 信任锚要选篡改代价高的位置

要证明"产物对应这份源"，就得在产物里存一份源的指纹。存哪里？

| 位置 | 可否被重签 | 判定 |
|---|---|---|
| 旁边的 sidecar（`.json`） | **能**——手改一行就"自洽"了 | 不可单独作为信任锚 |
| 容器元数据（mp4 `comment`） | 难——改元数据必然改字节，与 sidecar 记录的 sha256 矛盾 | 可作信任锚 |

做法：两处都写，但**以容器元数据为准**。sidecar 是可改的，所以它只能用来做交叉校验，
一旦 sidecar 与容器不一致，就说明有人动过其中一处。

同理，成片指纹要记两样：**容器头声称的帧数**和**实际解码数出来的帧数**。
只信容器头，截断攻击就检测不到（容器头还在，moov 里还写着 2160 帧）。

### 4.7 派生量优先于手写，第二手写处要受控

同一事实**两处手写**是分叉的根源，但要真正消掉它，得把它变成**派生量**——
在源头声明一次，别处由代码算出（时间码 = 帧数 ÷ 帧率、卡片重叠 = 相邻窗口推导）。

若确实需要第二处手写（比如规格里的声音蓝图、执行红线），不要假装它不存在，
而是**显式承认并加反向检查**：遍历源里声明的每一个事实，
一旦它在叙事区被复述，就报错。这样"参数与叙事分离"从约定变成可判定条件。

反向检查还要覆盖**书写变体**，否则会漏：
全角数字（`２１６０`）、冒号时间码（`0:05`）、帧区间（`144-228`）、
以及字幕原文照抄（标点也要一起归一化，否则全角逗号能绕过匹配）。

**反向检查的边界要写进注释。** 语音文本的反查是"标点锚定"的：
`「欢迎回家。」` 带句号会被拦，`「欢迎回家」` 不会——因为后者是**片名本身**，
叙事区合法地会提到它。这类取舍若不写明，下一个人会以为是漏掉的规则而"补上"，
把一个有意的边界改成到处误报。判定标准很简单：**这条检查想拦的是"规格与成片
可能对不上"的情形，还是"任何提及"？** 前者才值得拦。

### 4.8 中间产物也会陈旧，不只是最终产物

最容易漏的是** pipeline 中间的生成物**。以为只有最终成片需要防陈旧，
于是改了源头声明、重跑组装器，新成片就带着**旧中间件**宣称新指纹——
和规格陈旧完全同构，只是发生在更深的层。

处置与最终产物一样：**把指纹写进中间件自己的容器**，而不是旁边的记录文件。
WAV 有 LIST/INFO 的 `ICMT` chunk、mp4 有 `comment` 标签，都能由 ffmpeg
`-metadata` 写入；旁边的 sidecar 可以被人手改，容器字节不能。

更普适的一条：**凡是由源生成的产物，都该带"我是被哪个源版本生成的"这个标记**，
并且**消费者（下一步）必须在消费前校验它**。只生成不校验，等于没生成。

### 4.9 新加的检查，自己也会有 bug

每次给管线加一类检查，都要假定**这个检查本身是错的**。两个真实教训：

1. **大小写与格式假设**：判断"有没有音频流"时，正则只匹配 `#0:1: Audio:`，
   而 ffmpeg 实际输出 `Stream #0:1[0x2](und): Audio:`；捕获组返回大写的 `Audio`，
   判断却用小写的 `"audio"`。两处叠加的结果是**文件明明有音轨，检查恒报没有**。
   它不是漏报攻击，而是把好状态判成坏状态——比漏报更危险，因为它会让人
   去"修"那个没问题的产物。
2. **攻击被错的护栏拦下**：测"音轨被剥离"时，剥离必然改文件字节，于是 sha256
   护栏先拦住了它，`errors > 0` 照样通过——**即使流检查彻底坏掉，攻击依然是绿的**。
   修法是把断言从"有差异"改成"**指定那条差异必须出现**"。

由此得到两条硬规则：

- **新检查必须配一个专门打它的攻击**，且断言要指明**是哪条护栏报的**，
  不能只断言 `errors > 0`；
- **解析外部工具输出时，先打印一次真实输出再写正则**。
  凭对格式的印象写正则，是本项目重复次数最多的一类错误。

### 4.10 元数据面全覆盖，不等于内容被读过

这是"差异数 0"最会骗人的一次。一条音频轨的对读可以覆盖六项——
流存在、采样率、声道数、编码、中间产物内嵌指纹、床时长——**六项全绿，
而耳语在成片里的位置错了两秒，对读报 0 差异。**

原因：这六项都是**元数据面**，没有一项读内容。于是"成片里的耳语在哪一刻出现"
这件事既没被声明，也没被测量，**只被假设**。

> **差异数 0 只证明被对读的面一致，不证明被对读的面选对了。**
> 本项目在两条不同的面上撞过同一条：一次是侧车两个字段说谎（谁都不问它描述的文件
> 是否存在），一次是整个音频内容面缺席。

判据很机械：**把每一条断言列出来，逐条问"这条断言能被哪个攻击打破"。**
答不出攻击的那条，要么是不可证伪的，要么是重复的；而**某个产物属性若没有任何
一条断言能被它打破，它就没有被对读**。

内容面怎么读（有损编码下）：

- **比包络，不比样本。** 成片经过 AAC，逐样本比对会把一次忠实混流判成分叉。
  取每 100 ms 的 RMS 能量序列，比对相关系数与活跃窗口位置。
- **静音段要压平，不要参与比对。** 两侧的静音只差量化噪声，这噪声会把相关
  从 1.000 拉到 0.982——距阈值只剩 0.002，换一个编码器版本就跌破，
  **把一个正确的产物报成分叉**。静音是状态不是电平，不该被 diff。
  压平后实测相关回到 1.000000。
- **阈值要留余量。** 定完阈值回头看实测值与阈值的距离；贴着阈值通过的断言，
  等价于一个会在别人机器上误报的断言。

### 4.11 藏在生成器里的常量，是伪装成代码的参数

一个决定产物长什么样的值，如果写在生成器的常量里而不是源声明里，
它就同时满足三个坏性质：**规格显示不出来**（读者看不到）、
**验证器断言不了**（它不在唯一手写处）、**改它要动代码**（改完还要靠人记得重跑全套）。

判据：**这个值改了以后，产物会变，但规格不会变、对读也不会报——
那它就是被藏起来的参数**，应提升为源里的声明值，纳入封闭 schema。

本例：`make_voice.py` 里的 `SILENCE_FLOOR_DB = -50.0` 决定耳语的气声保留多少，
是可听的产物属性，却硬编码在生成器里。提升为 `audio.voice.trim_floor_db` 之后，
调它只需改一个数字，规格会跟着显示，重跑全套即可——**这就是公理 4
（参数与叙事分离）在"处理参数"上的落点**。

### 4.12 声明值不等于实测值：规格显示了它，不代表它被测过

给管线加第二个声明面（配乐）时自审发现：`peak_dbfs` 在源里声明了三处、
被渲染进规格的三张表格里，**却没有一条断言去读文件的真实峰值**。
规格可以写一个产物并不具备的电平，而这正是这套管线存在的理由要消灭的分叉类型——
只不过发生在一条从没人对读的面上。

判据：**源里每一个数值型的产物属性，都要有一条断言去读产物的实测值。**
只被声明、只被渲染、从未被测量的值，和一个注释没有区别。

一个具体的坑：**别拿统计代理量当真值**。校验电平时若用"每 100 ms 的 RMS 包络"
去比声明的峰值，会系统性偏低约 4 dB（本例：音乐床 RMS −33.8 dBFS vs 真峰值
−30.0 dBFS），于是**任何偏差都测不出来，断言一路放行**。体积、时长、码率同理——
先确认你测的那个量，定义上就等于你声明的那个量。

配套地，**派生值校验不了产物**：骤停帧由节拍派生，只能保证声明自洽；
一份为别的时间轴生成的（或事后被手改的）产物仍然能通过。
位置与电平这类"产物身上的事实"，必须在文件里量，不能从源推导。

### 4.13 攻击只能破坏比较的一侧

构造"成片音轨与中间产物分叉"的攻击时，第一版把 wav 和成片**都**改成了
"耳语前移 2 秒"的版本。结果两侧一致，对读报 0 差异——**这是正确判定**，
但显示成了 FAIL，看起来像护栏有缺口。

> **改动比较两侧的攻击，测不到那个比较。**
> 它测的是恒等式 `x == x`，无论护栏好坏都成立。

处置：攻击必须只动一侧（本例改为只换掉成片的音轨，中间产物保持原样）。
配套地，攻击被拦下后要问一句：**它是不是因为两侧真的分叉才被拦的？**
——这正是 §4.9 第 2 条"精确断言"在构造阶段的对应物。

### 4.14 误报比漏报更危险

给竖屏变体加"黑区必须纯净"的版式护栏后，首次对读报了 4 项 error。查下来
**其中 2 项是护栏太严，不是产物有问题**：yuv420p 的色度是半分辨率存储的，
跨画面区边界的那个 2×2 块会把画面色度带进黑区——实测上黑区末 6 行达到灰阶 29，
而真墨（字幕）是 255。

```python
BAR_INSET     = 16   # 边界内缩：色度溢出带（实测 6 行）之外才可信
BAR_NOISE_MAX = 8    # 实测 0（上）/ 1（下）；画面与字幕都 ≥ 64
BAR_INK_MIN   = 64   # 真墨阈值，与噪声容差间隔 8 倍
```

> **一条把正确产物报成分叉的护栏，比一条什么都不报的护栏更坏。**
> 漏报只是没拦住；误报会训练所有人忽略它——第二次、第三次红灯响起时，
> 没有人会去看，因为它"一直都这样"。

所以护栏的阈值**必须实测标定，不能拍脑袋写 0**：先量正确产物的实际分布，
再在"噪声上限"与"缺陷下限"之间取一个有量级间隔的阈值，并把**测不出的范围
（本例是 < 16 px 的位移）如实写进遗留**，而不是假装护栏无所不能。

同类还有一处：`_container_comment` 读 ffmetadata 时没反转义（`=` `;` 在
ffmetadata 里被反斜杠转义），于是 `source_digest\=ab12\;` 与 digest 比对不过，
**正确文件被报成分叉**。解析层的格式假设错误，最终都会伪装成产物的错。

### 4.15 重渲染会静默降级保护等级

逐帧内容链（最强的那一层内容指纹）是**可选项**，因为它慢。它存在 sidecar 里，
于是出现这条路径：

```
例行重跑（没带 --deep-fingerprint）
  → sidecar 被重写
  → decoded_chain 消失
  → 只剩一条 warning：「逐帧内容检查处于关闭状态」
```

重渲染这个动作**不该降低保护等级**，而且这里是安静地降级——唯一信号是一条
没人会在绿色结果里注意看的 warning。

> **把"上一份记录里已经有的"当作要求的强度：留存是默认，降级要显式。**

```python
deep = args.deep_fingerprint
if prev_record_has_chain and not args.shallow_fingerprint:
    deep = True            # 并打印一行说明本次沿用了什么
```

这条同样适用于任何"默认关闭的强校验"：codec 严格模式、全量抽帧、深度 schema
校验。凡是能被一次例行执行悄悄关掉的保护，都要反过来默认打开。

### 4.16 第二件产物如果没有攻击对准它，护栏等于注释

竖屏变体在源里声明了、规格里渲染了、也真的产出了文件——但**在此之前没有任何
攻击对准它**。所有检查都只看 `output.container`，于是"把横屏主成片盖到竖屏路径上"
这种最可能发生的漂移（源改了、主成片重渲染了、手机端的那份是旧的）**全程绿灯**：
主成片确实是对读过的、确实没分叉，错的是那份没人看的文件。

```python
def check_variants(src, diffs):     # 第四面对读：源 ↔ 变体
    ...                              # 分辨率 / 帧率 / 解码帧数
    ...                              # 容器内嵌 variant 标记 + 源指纹
    ...                              # 音频 ↔ 混音床包络
    ...                              # 版式像素测量（元数据看不见的那部分）
```

补 A21（竖屏被横屏覆盖）/ A22（画面区位移 40 px）/ A23（重签为陈旧指纹）+ M4。

**判定口径**：A21 断言的是"分辨率护栏报了它"，**不是 `errors > 0`**。
换掉整个文件必然同时改变字节，sha256 护栏会顺带拦下——只数错误条数的话，
分辨率护栏就算整个烂掉也照样通过（§4.9 第 2 条）。

### 4.17 派生几何：变体只声明"意图"，不声明坐标

同一叙事要出两种画布时，最省事的做法是另存一份工程手改——那会立刻造出第二个
手写处。正确的做法是**变体只声明意图，几何全部派生**：

```json
"vertical": {"aspect": "9:16", "frame_aspect": "4:5",
             "width": 1080, "subtitle_size": 52}
```

画布高 1920、画面区 1080×1350 @y285、裁切窗 864×1080 @x528、缩放 1.25×、
黑区 570、字幕基线 1794——**声明里没有一个像素坐标**。改 `frame_aspect`，
整版跟着走，规格表格也跟着重新渲染。

两个配套决定：

* **渲染器单独写，不加 `if variant:` 分支**。两种画布在几乎每个像素操作上都
  不同（画面区在哪、字幕在哪、有没有遮幅），折进一个函数会变成分支迷宫，
  **而没被走到的那个分支就是会悄悄腐烂的那个**。它们共享的应该是源与段落表
  ——那才是分叉风险真正所在的地方。
* **构图代价要写进产物文档**。4:5 居中裁切裁掉左右各 528 px，**合计 55% 横向
  视野**。这是选择的真实成本，不是缺陷；但不写出来，下一个人会以为竖版和横版
  "看到的是同一幅画"。

另外，**变体与母版之间无法做逐帧像素等价**（画布不同）。公理 5 在这里的含义
要改口径：不是"像素一致"，而是"同一段落表 + 同一素材 + 同一音频 + 几何由同一份
声明派生"，靠对读面、攻击与音轨相关来证明。这个边界要写明，不能含糊过去。

## 5. 2.39:1 遮幅的计算

生成端普遍是 16:9，成片要 2.39:1 宽银幕。**不要重新生成素材**——在后期统一加上下遮幅。

```
画面 1920×1080，目标可见区宽高比 2.39
可见高度 = 1920 / 2.39 = 803
上遮幅 = (1080 - 803) / 2 = 138      （下遮幅同）
```

```python
BAR_TOP, BAR_BOT = 138, 941        # 可见区 y 范围 [138, 941)
frame[BAR_TOP:BAR_BOT, :] = black_bar
```

**遮幅是加在成品上的，不是拍进去的。** 这样素材仍可用常规 16:9 交付与复用，遮幅是成片阶段的一次性操作。

另一个配套决策：**字幕位置锚定在可见区内**（下三分之一），不是画面绝对底部。否则遮幅会把字幕切掉或压到黑边上。

## 6. 多行卡片的叠化实现

三行文字卡逐行出现，实现上就是三张图片的交叉叠化：

```python
def three_line_layers(f):
    layers = []
    for img, start, dur in [(C08, 1200, 16), (C09, 1216, 16), (C10, 1232, 16)]:
        w = 1.0 - abs(f - start) / dur
        if w > 0.001:
            layers.append((img, w))
    return layers
```

每张卡占 16 帧（24fps 下约 0.67s），相邻两张重叠 16 帧形成叠化。三张共 48 帧。

## 7. 二十三条反模式

| # | 反模式 | 为什么错 |
|---|---|---|
| R-1 | 把缺口当缺陷隐瞒，重复镜头拉长凑时长 | 表面达标，实为注水 |
| R-2 | 空段无标注（无台词、无声音设计、无运动参数） | 这类"无设计的空"会被读作偷工减料 |
| R-3 | 有信息空段与无信息空段合并统计 | 用叙事性黑场掩护无信息延展偏高 |
| R-4 | 同一事实两处手写 | 允许它有两处不同的值 |
| R-5 | 规格与产物从不机械对读 | 规格退化为"看起来像契约的文档" |
| R-6 | 交付核对表只覆盖文件存在性 | 用"文件都在"冒充"已收口" |
| R-7 | 规格不随资产落盘回写状态 | 过期状态让人按不存在的待办去等 |
| R-8 | 组装靠手工拖拽而非代码 | 不可复跑、不可校验、改一处要重做全片 |
| R-9 | 从没被攻击过的对读脚本 | 它输出 `差异数 = 0` 和空函数无法区分 |
| R-10 | 重渲染比对当唯一防线 | 生成器既写又判，写错时两边一起错，比对必然通过 |
| R-11 | 用可重签的 sidecar 当唯一信任锚 | 手改一行就"自洽"了 |
| R-12 | 只信容器头声称的帧数 | 截断后 moov 仍写着完整帧数，检测不到 |
| R-13 | 只给最终产物加信任锚，忽略中间生成物 | 改了源头，新成片带着旧中间件宣称新指纹 |
| R-14 | 新检查不加专门打它的攻击 | 它可能被别的护栏顺带拦下，坏了也看不出来 |
| R-15 | 凭对工具输出的印象写解析正则 | 大小写/格式假设一错，就把好状态判成坏状态 |
| R-16 | 对读只覆盖元数据面，从不读内容 | 格式全对而内容错位，差异数仍是 0（"面选错了"） |
| R-17 | 影响产物的处理参数硬编码在生成器里 | 规格显示不出、验证器断言不了、改它要动代码（违反公理 4） |
| R-18 | 攻击同时改动比较的两侧 | 测的是恒等式，护栏好坏都成立；0 差异却显示 FAIL |
| R-19 | 声明的量化值只被渲染、从未被实测 | 规格可以写一个产物并不具备的值；用 RMS 等代理量比对还会系统性放行 |
| R-20 | 护栏阈值拍脑袋写 0，不实测标定 | 编码噪声/色度溢出会把正确产物报成分叉；误报会训练所有人忽略它，比漏报更坏 |
| R-21 | 强校验设为默认关闭，且可被例行执行悄悄关掉 | 重渲染一次就静默降级保护等级，唯一信号是一条没人看的 warning |
| R-22 | 声明了第二件产物却不给它对读面与攻击 | 它从未被对准过，护栏等于注释；最可能发生的漂移全程绿灯 |
| R-23 | 变体里写像素坐标，或把两种画布折进同一渲染器的 `if` 分支 | 坐标会随声明漂移；没被走到的分支会悄悄腐烂 |

## 8. 检验标准

| 编号 | 标准 | 判定类型 | 典型未满足情形 |
|---|---|---|---|
| C1 | 缺口在文档中显式出现且可复算 | 有效性 | 只写"约 90 秒" |
| C2 | 每类空段有最小规格参数 | 存在性 | 静帧延展拍无缓动参数 |
| C3 | 空段在时间轴上为独立类型 | 有效性 | 全部记作 `fill` |
| C4 | 段落表长度自校验存在 | 存在性 | 手工拼帧无累加点 |
| C5 | 规格与产物做过机械对读，差异入报告 | 有效性 | 只做过目视比对 |
| C6 | 交付核对表含"知识同步性"行 | 存在性 | 只有文件计数 |
| C7 | 无信息空段占比可统计且有上限 | 有效性 | 从未单独统计 |
| C8 | 规格与产物的差异数 = 0 | 有效性 | 存在任意一处不一致 |
| C9 | 对读器经过攻击回归（每类破坏都有用例） | 有效性 | 从未主动做坏过 |
| C10 | 存在不经过生成器的独立断言 | 存在性 | 只有重渲染比对（自比对） |
| C11 | 元测试：阉割护栏后套件变红 | 有效性 | 套件无法变红 |
| C12 | 信任锚不可被单侧重签 | 有效性 | 只信可手改的 sidecar |
| C13 | 帧数按实际解码计数，不信容器头 | 存在性 | 只读 moov 声明值 |
| C14 | 中间生成物内嵌源指纹，且下一步消费前校验 | 存在性 | 只给最终成品加锚，中间件可陈旧 |
| C15 | 每条新检查都有专打它的攻击，且断言指明护栏名 | 有效性 | 只断言 `errors > 0`，可能被别的护栏顺带拦下 |
| C16 | 每条断言都能被某个攻击打破；产物属性无断言可破即未被对读 | 有效性 | 元数据面全绿而内容错位仍报 0 差异 |
| C17 | 影响产物的处理参数均在源中声明（改值→规格变且可断言） | 存在性 | 生成器里有常量决定产物属性 |
| C18 | 有损编码下的内容比对用包络而非样本，静音段不参与 | 有效性 | 逐样本比对把忠实混流判成分叉 |
| C19 | 源里每个数值型产物属性都有断言读产物实测，且量定义与声明一致 | 有效性 | 只声明只渲染从不测量；拿 RMS 当峰值比对 |
| C20 | 护栏阈值由正确产物的实测分布标定，并登记测不出的范围 | 有效性 | 阈值拍脑袋写 0；声称无所不能而实际有盲区 |
| C21 | 强校验的留存是默认、降级要显式，且降级会打印 | 存在性 | 例行重跑一次就把逐帧内容链悄悄删掉 |
| C22 | 源声明的每件产物都有对读面，且至少一条攻击专打它 | 有效性 | 第二件产物从未被对准，改坏了也全绿 |
| C23 | 变体只声明意图（比例/宽度/字号），几何全部派生并回写规格 | 有效性 | 变体里写死像素坐标；改一处要人肉重算整版 |

> C9–C23 是 4.5/4.6/4.8–4.17 节的落点。**C8 单独存在是不够的**：一条从不报错的对读脚本
> 永远满足 C8，因此 C8 必须与 C9–C13 一起判定；而**即使 C9–C15 全满足，C16 仍可能不成立**
> ——对读的每一面都被攻击过，不等于该对读的面覆盖了产物的全部属性；
> **再往下，C22 提醒的是"面"本身可能漏了一件产物**——每一面都绿，不等于每件产物都被看过。



## 9. 落地顺序建议

第一次搭这条管线时，按这个顺序做，每步都能独立跑通：

1. 先做**单段拼接**（两个 clip 首尾接），确认编码链通；
2. 加**段落表 + assert**，把已有的一段手工拼接迁进表里；
3. 加**空段类型**（黑场、延展拍），把目标时长补齐；
4. 加**字幕层**（用选定的字体与基线锚点）；
5. 加**遮幅**；
6. 最后做**单一手写源 + 机械对读**——这一步需要前面都稳定下来才好做。

先做第 6 步是常见错误：规格还没稳定时就上对读，会天天报差异。
