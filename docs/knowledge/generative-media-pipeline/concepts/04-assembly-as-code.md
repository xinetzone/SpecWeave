# 04 组装即代码

## 1. 核心主张

**成片不是一次性的操作结果，而是一段可以从参数重跑的程序。**
这条主张带来三个直接好处：
1. 改一个时间码就能重出片，不用重搭一遍剪辑流程；
2. 段落表本身就是文档——它比任何描述性文档都更接近"实际发生了什么"；
3. 参数是数据，因此可以对数据做机械校验（帧数配平、规格对读）。

## 2. 段落表：时间轴的唯一表达

把成片表达为「类型 + 源 + 帧数」的序列：

```python
plan = []

def add(kind, src, n):
    plan.extend([(kind, src)] * n)

add("clip", "V01", 120)     # 素材段：视频
add("black", None, 120)    # 有信息空段：黑场（承载台词）
add("kb",   "KF03", 120)   # 无信息空段：静帧延展拍
add("card", "C08", 16)     # 卡片段：字幕卡 / 标题卡
add("black", None, 24)

assert len(plan) == TOTAL, len(plan)     # 帧数配平的最后一道关
```

段落类型至少要区分这几类：

| 类型 | 含义 | 帧数来源 |
|---|---|---|
| `clip` | 视频素材段 | 素材实际时长 |
| `kb` | 静帧延展拍（Ken Burns） | 目标时长（通常 5s 一段） |
| `black` | 黑场（承载台词或呼吸） | 目标时长 |
| `card` | 文字卡片 | 目标时长，多张叠化时共享 |

**段落表是唯一的时间轴来源。** 文档里的时间码表应当由它生成，而不是手写。

### 2.1 assert 的价值：拦下配平错误

本教程的实践里，段落表曾因三行卡片各写 60 帧（应为 16×3=48）导致总长 2172 ≠ 2160。这个错误**肉眼完全看不出来**——它在 `add()` 调用里分散着，只有累加才知道。

`assert len(plan) == TOTAL` 就是那道关。**每一条会改变总时长的路径，最后都要经过同一个累加点。**

## 3. 缺口显式化

### 3.1 先算缺口

```
缺口 = 目标时长 − 素材总时长
```

**这个数必须在组装之前落到文档里。** 本教程的实践：目标 90.00s，素材 50.32s，缺口 39.68s。

不先算这个数，就会出现两种坏结果：要么开工后发现不够，要么中途才发现不够——两种都会导致赶工。

### 3.2 空段分两类

| 类别 | 定义 | 本教程实践中的形态 | 作用 |
|---|---|---|---|
| **2a 有信息空段** | 承载新增叙事信息 | 黑场 + 字幕（台词） | 推进叙事 / 落声音点 |
| **2b 无信息空段** | 同一画面的时间延展，无新增信息 | 静帧延展拍（Ken Burns） | 视觉系统切换 / 呼吸 / 补时长 |

**必须分开统计。** 合并会让"无信息延展占比偏高"被叙事性黑场掩盖——黑场占 23.3% 看着是风格选择，但里面若有一半是无台词的纯延时，问题的性质完全不同。

### 3.3 空段的最小规格

空段不是"随便填满"。每类空段都要有最小参数：

| 空段 | 最小规格 |
|---|---|
| 静帧延展拍 | 缩放 1.00→1.08 + smoothstep 缓动 + 12 帧淡入淡出斜坡 |
| 黑场 + 台词 | 与字幕帧区间一一绑定，字幕有 12 帧淡入 / 淡出 |

**Ken Burns 缓推的实现**：

```python
def ken_burns(img, i, n):
    t = i / max(1, n - 1)
    s = 1.00 + 0.08 * (t * t * (3 - 2 * t))     # smoothstep 缓动
    nh, nw = int(img.shape[0] * s), int(img.shape[1] * s)
    r = (nh - img.shape[0]) // 2
    c = (nw - img.shape[1]) // 2
    return img[r:r + img.shape[0], c:c + img.shape[1]]
```

`smoothstep`（`t²(3−2t)`）比线性缓动好在**两端速度为零**：延展拍不会"啪"地开始或"啪"地停住。

### 3.4 空段用途：类型默认 + 例外手写

逐段手写用途理由在赶工时第一个被牺牲。折中做法：

- `kb` 的**默认用途** = 视觉系统切换 / 呼吸；
- `black+subtitle` 的**默认用途** = 台词承载；
- **只有超出默认用途时**才需手写理由。

这把写作量从"逐段"降到"逐例外"，而设计意图仍然留在文档里。

## 4. 单一手写源：规格与产物不再分叉

### 4.1 分叉是怎么发生的

本教程的实践里，成片完成后做了一次规格—产物对读，发现四处不一致：

| 项 | 规格写的 | 实际是 |
|---|---|---|
| 帧率 | 30fps | 24fps |
| 素材时长 | 5s | 5.04s |
| 资产状态 | "待关键帧" / "制作中" | 全部已落盘 |
| 字幕文本 / 卡片点位 | 手写在规格表 | 又手写了一份在源码里 |

**根因是同一个事实有两处手写。允许同一事实有两处手写，就等于允许它有两处不同的值。**

更值得注意的是：**这些分叉没有任何一方主动报错**。因为交付核对表覆盖的是"文件是否落盘"——那是最容易自动化的部分，于是给了"已收口"的错觉。

### 4.2 最小改造

把所有会变的事实抽到**一个**手写文件，其余全部由它生成：

```
single-source.json          ← 唯一手写处
  { fps, width, height, total_frames,
    segments: [ {type, src, frames} ],
    subtitles: [ {text, from_frame, to_frame} ],
    cards:     [ {file, from_frame, to_frame} ] }

generate.py  →  ① 生成组装用的 plan（供脚本 import）
              →  ② 生成规格表（Markdown）
              →  ③ 组装前 assert(plan 累加 == total_frames)
              →  ④ 组装后 diff(生成的规格表 ↔ 实际产出的参数)
```

关键点：**规格不再手写，它是被生成的**。这样"规格与产物不一致"在结构上就不可能发生。

### 4.3 机械对读

对读的目标必须是**实际产出的参数**，不能是源码常量——否则是自己验自己。

```
差异数 = 0   →  允许标记"已收口"
差异数 > 0   →  报告里逐条列出，不允许标记收口
```

**存在性 vs 有效性**：检验标准写成"表里有这一行"是存在性判定，很容易被形式化满足。真正要的是**有效性判定**——差异数 = 0。

### 4.4 交付核对表的正确形态

核对表要分两类，不能只列第一类：

| 类别 | 例子 | 判定 |
|---|---|---|
| 资产完整性 | 卡片 12/12、关键帧 4/4、视频段 8/8 | 文件存在且可读 |
| 知识同步性 | 规格版本 ↔ 产物版本、最后对读时间、差异数 | 差异数 = 0 |

只列第一类，就会用"文件都在"冒充"已收口"。

## 5. 2.39:1 遮幅的计算

生成端普遍是 16:9，成片要 2.39:1 宽银幕。**不要重新生成素材**——在后期统一加上下遮幅。

```
画面 1920×1080，目标可见区宽高比 2.39
可见高度 = 1920 / 2.39 = 803
上遮幅 = (1080 - 803) / 2 = 138      （下遮幅同）
```

```python
BAR_TOP, BAR_BOT = 138, 941        # 可见区 y 范围 [138, 941)
frame[BAR_TOP:BAR_BOT, :] = black_bar
```

**遮幅是加在成品上的，不是拍进去的。** 这样素材仍可用常规 16:9 交付与复用，遮幅是成片阶段的一次性操作。

另一个配套决策：**字幕位置锚定在可见区内**（下三分之一），不是画面绝对底部。否则遮幅会把字幕切掉或压到黑边上。

## 6. 多行卡片的叠化实现

三行文字卡逐行出现，实现上就是三张图片的交叉叠化：

```python
def three_line_layers(f):
    layers = []
    for img, start, dur in [(C08, 1200, 16), (C09, 1216, 16), (C10, 1232, 16)]:
        w = 1.0 - abs(f - start) / dur
        if w > 0.001:
            layers.append((img, w))
    return layers
```

每张卡占 16 帧（24fps 下约 0.67s），相邻两张重叠 16 帧形成叠化。三张共 48 帧。

## 7. 八条反模式

| # | 反模式 | 为什么错 |
|---|---|---|
| R-1 | 把缺口当缺陷隐瞒，重复镜头拉长凑时长 | 表面达标，实为注水 |
| R-2 | 空段无标注（无台词、无声音设计、无运动参数） | 这类"无设计的空"会被读作偷工减料 |
| R-3 | 有信息空段与无信息空段合并统计 | 用叙事性黑场掩护无信息延展偏高 |
| R-4 | 同一事实两处手写 | 允许它有两处不同的值 |
| R-5 | 规格与产物从不机械对读 | 规格退化为"看起来像契约的文档" |
| R-6 | 交付核对表只覆盖文件存在性 | 用"文件都在"冒充"已收口" |
| R-7 | 规格不随资产落盘回写状态 | 过期状态让人按不存在的待办去等 |
| R-8 | 组装靠手工拖拽而非代码 | 不可复跑、不可校验、改一处要重做全片 |

## 8. 检验标准

| 编号 | 标准 | 判定类型 | 典型未满足情形 |
|---|---|---|---|
| C1 | 缺口在文档中显式出现且可复算 | 有效性 | 只写"约 90 秒" |
| C2 | 每类空段有最小规格参数 | 存在性 | 静帧延展拍无缓动参数 |
| C3 | 空段在时间轴上为独立类型 | 有效性 | 全部记作 `fill` |
| C4 | 段落表长度自校验存在 | 存在性 | 手工拼帧无累加点 |
| C5 | 规格与产物做过机械对读，差异入报告 | 有效性 | 只做过目视比对 |
| C6 | 交付核对表含"知识同步性"行 | 存在性 | 只有文件计数 |
| C7 | 无信息空段占比可统计且有上限 | 有效性 | 从未单独统计 |
| C8 | 规格与产物的差异数 = 0 | 有效性 | 存在任意一处不一致 |

## 9. 落地顺序建议

第一次搭这条管线时，按这个顺序做，每步都能独立跑通：

1. 先做**单段拼接**（两个 clip 首尾接），确认编码链通；
2. 加**段落表 + assert**，把已有的一段手工拼接迁进表里；
3. 加**空段类型**（黑场、延展拍），把目标时长补齐；
4. 加**字幕层**（用选定的字体与基线锚点）；
5. 加**遮幅**；
6. 最后做**单一手写源 + 机械对读**——这一步需要前面都稳定下来才好做。

先做第 6 步是常见错误：规格还没稳定时就上对读，会天天报差异。
