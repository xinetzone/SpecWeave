# openKylin 3.0 架构适配评估草案

> 一句话摘要：3.0 是 openKylin 的**创新版**（非 LTS，仅 12 个月被动维护），同时带来内核与工具链跨代（Linux 7.0 / glibc 2.42 / GCC 15）、磐石不可变系统、四架构同源与智能体底座四类结构性变化——它适合作为**新能力验证与前向兼容靶场**，不适合在未持有商业发行版合同的情况下直接作为规模化生产基线；本文给出分维度评级、12 项风险与一套 6 阶段 POC 方案，供适配立项评审使用。

## 0. 文档状态与使用方式

| 项 | 说明 |
|---|---|

| 证据基础 | 同知识包两份已验证报告 + 1 份 WSL 本机实测；**未**在 3.0 Desktop/Server 上做应用级实测，**未**跑通 AI SDK 与 MCP 任一接口 |

本评估回答三个问题：3.0 相对 2.0 SP2 改变了哪些适配前提？哪些风险必须在立项前认知对齐？花多大成本、按什么顺序验证才能把决策从纸面落到实测？

## 2. 适配主体与评估范围

三类主体的适配工作内容不同，风险敞口也不同，本评估对三者分别给结论。

| 适配主体 | 典型目标 | 主要工作 |
|---|---|---|
| 应用软件提供方 | 现有 Linux 桌面/服务端应用在 3.0 可安装、可运行、可升级 | 安装包形态选择（deb / 开明 / KARE 兼容）、glibc 与图形栈兼容、商店或 PPA 分发、兼容认证 |
| 硬件与整机厂商 | 板卡/整机/外设安装启动、驱动可用、性能达标 | 内核驱动适配（含 Rust 驱动选项）、SIG 补丁合入、板级镜像、硬件适配认证 |
| AI 应用与智能体开发方 | 模型应用或智能体在 3.0 上调系统能力、可分发 | AI SDK 对接、MCP 工具与权限模型、模型来源（云/局域网/本地）配置、技能上架 |

不在本草案范围内：具体商务与授权条款、银河麒麟商业版 V11 的功能差异、3.0 之外的历史版本适配；这三项需另取商业版材料评估。

## 3. 七维度架构适配评估

### 3.1 内核与工具链跨代

3.0 从 6.6 LTS 跨到 Linux 7.0.0 代际，且镜像在 7.0 发布当月即推出（F-024/F-025）；工具链同步跨到 glibc 2.42、GCC 15.2、JDK 25。对适配工作的直接影响有三层：任何只提供预编译二进制的闭源软件都要按新 glibc 重新验证（glibc 向后兼容旧程序，但依赖私有构建符号、捆绑旧库或老旧 JNI 的程序是常见例外）；随 7.0.0 首发内核存在回归窗口，驱动与文件系统相关问题概率高于 LTS 点版本；JDK 25 移除部分遗留 API，老 Java 客户端需要回归。

- 就绪度：**中**　置信度：**中**（版本号为官方口径，回归幅度无第三方数据）
- 必做验证：目标软件清单中全部二进制在 3.0 上的安装/启动/主流程；自研 C/C++ 组件以 GCC 15 重新编译的告警与 ABI 回归；内核驱动在 7.0 上的 out-of-tree 编译。

### 3.2 不可变系统与软件分发形态

磐石架构下系统目录按 OSTree 版本化部署，支持原子更新与失败回滚（F-037）；应用分发有三条并存路径：传统 deb（受不可变模式约束，FAQ 已收录"当前模式禁止执行 unpack 操作"报错）、开明包（base+runtime+app 三层、crun/OCI 沙箱、带包签名，F-036）、KARE 跨版本兼容环境（官方口径 1.0 应用在 2.0 的安装加启动综合成功率 94%，F-019，**待复测**）。系统级改动可经 `mm-cli` 维护模式临时或永久放开（D-F-030）。

- 就绪度：**中高**（机制齐备且 2.0 起已有一个版本周期沉淀）　置信度：**中**
- 适配影响：安装器写 `/usr`、开机脚本改系统配置、依赖固定系统库版本的产品形态都要改设计；面向多发行版的产品优先走开明包（OCI 沙箱天然隔离系统代际差异），只在能力不足时回退 deb；运维侧需要把"现场手工改系统文件"的服务方式改为维护模式加声明式配置。
- 必做验证：三种路径各选一个代表性产品包安装；模拟一次 OSTree 更新与回滚后应用数据与授权状态不丢失。

### 3.3 多架构（X86 / ARM / RISC-V / LoongArch）

3.0 四架构同源发版并对齐 RVA23，是 openKylin 投入最重的差异化方向（F-030、源报告 I-4）。官方口径 RVV 优化后 RISC-V 平台 AI 推理 FP32 提速 2–5 倍、FP16 最高 36.5 倍（F-030，**待复测，源报告 V-01 禁止直接引用为结论**）。镜像矩阵中 RISC-V 目前集中在 SpacemiT K3 等指定板卡与 qemu RVA23（F-031、[D 版 03](../concepts/03-install-paths.md)），历史上板级文档多为社区投稿、刷写与跳线随板卡变化。

- 就绪度：X86 **高** / ARM **中高** / LoongArch **中** / RISC-V **中**（板卡绑定明显）　置信度：X86 **中**，其余 **低—中**
- 适配影响：纯 Java/Python/解释型应用跨架构成本主要在依赖中的原生库；含原生代码的产品需在 OKBS 按架构出包；RISC-V 场景须把"具体板卡 + 镜像日期 + 烧录工具版本"作为绑定配置管理，不能假设通用镜像通吃。
- 必做验证：每架构至少一台目标设备的完整安装与主流程；AI 推理场景自采 FP32/FP16 benchmark 替换官方数字。

### 3.4 图形与桌面栈

UKUI 4.24 基于 Qt 技术栈，显示合成走社区自研 wlcom（Wayland）（F-029/F-038/F-040）；2.0 组件清单中 Qt 5.15 与 GTK 3.24 并存（F-040），3.0 引入三岛模式、隔空手势等新交互。

- 就绪度：**中**　置信度：**低**（3.0 桌面对 X11 遗留应用的兼容行为无实测）
- 适配影响：依赖 X11 截图、全局热键、输入注入、窗口枚举的应用（远程协助、录屏、自动化测试、安全管控类）是 Wayland 迁移的传统高风险区；自研 UKUI 应用应按社区 22 篇 UKUI4 设计规范走原生交互（D 概念页 06 §6.7）。
- 必做验证：在 wlcom 会话下逐项验证窗口管理、截图、剪贴板、多屏与远程桌面；确认应用在 XWayland 回退路径下的表现。

### 3.5 安全与密码体系

3.0 集成 NIST 三项后量子标准（ML-KEM、ML-DSA、SLH-DSA），经 openHiTLS 提供系统级调用，配合 TPM 可信启动链（F-026）；内核支持 Rust for Linux 且首批系统工具完成 Rust 重写（F-027）。

- 就绪度：**中高**（标准实现已进入系统级组件）　置信度：**中**
- 适配影响：对绝大多数应用透明——现有 TLS/签名链路不应因 PQC 默认开启而中断，这本身是必测项；计划用新密码能力做长周期保密（密钥封装、固件签名）的产品可开始对接 openHiTLS，但应把混合密码套件作为过渡期方案，避免与尚未支持 PQC 的对端互操作失败。Rust 驱动适合新外设的增量尝试，存量 C 驱动无重写必要，且 Rust for Linux API 在 7.0 窗口期仍可能变动。
- 必做验证：与既有服务端/网关的 TLS 握手矩阵；TPM 绑定场景的密钥证明流程；Rust 驱动仅做试点不计入关键路径。

### 3.6 智能体底座与 AI 能力

3.0 的关键变化是智能体经 MCP 协议直接调用桌面能力，模型、记忆、工具、系统权限纳入统一底座；KylinBot、WorkBuddy、OpenClaw、Raccoon Work 等可运行，技能经 openkylin-skills 仓库分发，系统预装 Token 中心（F-047）。开发者侧已有成文资产：137K 字符的 AI SDK 手册覆盖 8 个能力域（OCR、音频、向量化、文本/图像生成、两类分割、错误码），接口为会话生命周期加异步回调（D-F-029）；模型支持云 API、局域网端点、本地模型包三类来源，本地模型经 modelscope.cn 获取（D-F-022、[D 版 05](../concepts/05-ai-stack.md)）。

- 就绪度：**中**（三层成文齐备，但 MCP 为 3.0 新平台层）　置信度：**中低**（SDK 接口未实测，MCP 权限模型细节待官方更新文档）
- 适配影响：这是 3.0 上唯一在 2.0 无法等价获得的能力，AI 团队的 POC 应直接以 3.0 为靶场；企业接入必须回答权限边界与审计问题——智能体误操作系统应用的 blast radius、技能签名与下架机制、云端模型的数据出境与凭据管理（API Key 不得入库或写入脚本，社区 AI 守则同此要求，D-F-035）；Token 中心的免费额度是运营资源，不能当作企业 SLA 的一部分（源报告 V-07）。
- 必做验证：跑通一个最小闭环（装包 → 调通 OCR 或文本生成中一个接口 → 经 MCP 完成一次桌面操作回写）；验证私有化模型替换路径与离线环境可用性。

### 3.7 工程供应链与认证

社区供应链是逐命令文档化的：OKBS 编译平台（注册 PPA、SSH/PGP 公钥、dput 经 sftp:2121 上传）、factory 版本构建平台（livebuild 任务、软件源快照继承、hooks/includes/packages 定制目录）、CLA 三类签署（个人/员工/企业）（D-F-027、D-F-031、[D 版 06](../concepts/06-developer-infrastructure.md)）。软件与硬件适配认证流程同构：官网入口提交腾讯文档申请表，按模板编测试报告（硬件另需 1080p 以上演示视频），7 个工作日内审核发证并公示（D-F-038）。

- 就绪度：**高**（流程与平台均可复现）　置信度：**高**（官方手册成文，平台地址明确）
- 适配影响：企业贡献应提前安排员工或企业 CLA 签署的法务周期；官方源入库需先向技术委员会申请包权限，个人/团队 PPA 可作为先行分发渠道；定制镜像应优先"继承软件源快照"而非拉最新源，保证构建可复现。
- 必做验证：完成一次"源码包 → OKBS PPA → factory 继承式镜像"的全链路演练，再启动正式适配。

| R-08 | MCP 协议与智能体权限模型后续变动，技能需返工 | 中高 | 中 | **中** | 技能层薄封装、业务逻辑与协议解耦；关注 openkylin-skills 仓库接口变化 | 2026-12-31 前协议复查（源报告 A3） |
| R-09 | AI 数据治理风险：modelscope 下载依赖、云端模型出境、Token 额度不可控 | 中 | 中 | **中** | 企业用局域网/本地模型源；凭据走系统通道；明确免费 Token 不进生产架构 | 私有化模型最小 POC 完成 |
| R-10 | 社区版无 SLA，安全可靠测评等资质主体是商业版 | 确定 | 中高（限政企场景） | **中** | 等保/关基场景直接评估银河麒麟 V11，不以社区版投标或承诺 | 商业版适配评估单独立项 |
| R-11 | 镜像与文档时效不均：分阶段上架、新手文档陈旧、WSL 预置弱口令 | 高 | 低中 | **中** | 以镜像日期与校验和为准确认版本；首次登录即改 openkylin/openkylin 默认口令，xrdp 3390 不映射公网 | 每次镜像刷新 |
| R-12 | Rust for Linux 生态早期，API 变动与人才稀缺 | 中高 | 低（除非关键路径押注） | **低** | 仅在新外设驱动做试点，不阻塞 C 驱动主线 | 内核 Rust API 稳定声明 |

## 5. 分场景适配路径

### 5.1 应用软件

先按依赖盘点把软件分为三档：解释型或容器友好型 → 优先打**开明包**（OCI 沙箱隔离系统代际，一次打包多处运行，F-036）；深度依赖系统库或需要系统服务的 → 出 deb 并在不可变模式下验证安装路径；历史版本软件 → 借 KARE 兜底但记录其 94% 为官方口径、不作为交付承诺。分发先上个人/团队 PPA 跑通 OKBS 链路，再申请官方源权限；需要市场背书时走 7 个工作日审核的软件适配认证（D-F-038）。

### 5.2 硬件与整机

早期就接入对应 SIG 并把补丁合入作为目标，自维护外树补丁在 7.0 跨代窗口维护成本最高。板级镜像经 factory 以继承快照方式构建；RISC-V 客户场景绑定具体板卡（K3 等）与烧录工具版本，软件层可用 qemu RVA23 提前并行开发。认证材料中的演示视频（安装过程、AI 助手、UKUI 功能、兼容性，1080p 以上 MP4/AVI）应在 POC 阶段同步拍摄，避免立项后补拍。

### 5.3 AI 应用与智能体

POC 顺序：本地模型（ollama 跑通小规格，参照[文档导读 5.1](../concepts/05-ai-stack.md)）→ AI SDK 单能力域（建议从文档最完整的 OCR 章节入手）→ MCP 桌面操作闭环 → 技能打包入 openkylin-skills。架构决策上把模型接入做成三源可切换（云/局域网/本地），权限上默认最小授权并保留全量审计日志；在 MCP 接口稳定前，业务代码与协议间保留适配层（R-08）。

## 6. 版本策略矩阵

| 场景 | 建议基线 | 3.0 的角色 |
|---|---|---|
| 个人尝鲜、开发者跟进新特性 | openKylin 3.0 | 主力（WSL 或虚拟机起步，见[实测指南](wsl-install-sparse-vhd-guide.md)） |
| 企业存量应用的维护性适配 | 2.0 SP2 LTS | 前向兼容验证靶场，确认下一 LTS 升级无债 |
| AI 智能体、RISC-V/RVA23 新能力立项 | openKylin 3.0 | 主力验证平台，但生产化需等待 LTS 或转商业版 |
| 政企生产、等保/关基、要求 SLA 与资质 | 银河麒麟商业版 V11 | 技术预研参考，不作为投标与交付主体（R-10） |
| 大规模桌面量产 | 2.0 SP2 LTS 或商业版 | 仅实验室验证 |

## 7. POC 方案：六个阶段门

每阶段设退出标准，任一阶段不通过即回退评估、不进入下一阶段；全部产出归档为适配报告的证据章节。

| 阶段 | 目标 | 主要工作 | 退出标准 |
|---|---|---|---|
| P0 准备 | 环境与供应链就绪 | 锁定镜像日期与 MD5；搭建软件源镜像或本地快照；完成 CLA 主体签署与 OKBS/factory 账号；冻结软硬件清单 | 清单评审通过；"源码包→PPA→继承式镜像"演练成功一次 |
| P1 安装启动 | 全形态可装机 | 各目标架构/形态安装（物理机/虚拟机/WSL/板卡）；默认口令整改；启动链与 TPM 核查 | 清单内设备全部可安装启动，安装记录与镜像校验和归档 |
| P2 功能兼容 | 应用可运行 | deb/开明/KARE 三路分包验证；主业务流程；图形专项（截图/多屏/远程）；AI SDK 一个能力域跑通 | 每产品有通过/失败/规避结论；缺陷可复现并上报 Gitee |
| P3 性能与稳定性 | 指标可承诺 | 自采 benchmark（含 RISC-V FP32/FP16，替换官方口径）；不少于 72 小时浸泡；资源与长稳监控 | 形成对外可引用的自有数据；无 P0/P1 未决缺陷 |
| P4 运维与安全 | 可交付运维 | OSTree 更新/回滚演练；维护模式操作手册化；TLS/PQC 互操作矩阵；智能体权限与审计验证；凭据与离线模型方案 | 回滚后应用数据与授权无损；安全检查项全部有结论 |
| P5 分发认证 | 可上市 | PPA/商店上架材料；软件或硬件适配认证申请与测试报告（硬件含演示视频） | 取得兼容证书或明确认证排期 |

成本提示：P0–P2 为两周内可完成的最小验证环，足以裁决"是否继续投入"；P3–P5 才涉及规模化投入。不建议跳过 P0 直接在开发机散测——账号、CLA 法务周期与源快照是最常见的进度意外。

## 8. 待核查信息缺口

以下事实在现有公开材料中无答案，立项材料应显式列为假设并在 P0/P1 阶段销项：

1. 3.0 首个 SP 的发布时间与 Linux 7.0 回归修复清单（R-02）；
2. 智能体经 MCP 调用桌面能力的完整权限粒度、确认机制与审计日志格式（R-08）；
3. 开明包在 3.0 的商店上架比例与实际沙箱限制清单（2.0 时为 100 款，F-036）；
4. KARE 94% 成功率的测试集定义，以及在 3.0 上的复测值；
5. AI SDK 在 LoongArch/RISC-V 上的可用性与本地模型文件在 modelscope 的当前可下载性（源导读 I-3 已登记同类缺口）；
6. 捐赠后非麒麟系企业的代码贡献占比与 SIG 主导权分布（源报告 V-05 数据缺口）——影响长期供应链博弈判断；
7. 3.0 Server 镜像的容器与云原生兼容性认证清单（仅有"20 余款 Docker 镜像"的官方列举，F-032）。

## 9. 结论

3.0 的适配价值集中在两个 2.0 无法替代的点：智能体底座加 MCP 的系统级 AI 能力，以及 RVA23 对齐的四架构同源硬件支持；它的适配成本也集中在两个跨代：内核工具链跨代与不可变系统下的分发方式跨代。叠加"创新版 12 个月被动维护"的轨道属性，总体裁决为：

- **可立即启动**：面向 3.0 新能力（智能体、RISC-V）的探索性 POC，以及全部存量产品在 3.0 上的前向兼容验证（P0–P2，轻量）；
- **有条件推进**：开明包化改造与 factory 定制镜像流水线，作为面向下一 LTS 的技术储备；
- **暂不建议**：以社区版 3.0 承担规模化生产与资质型项目交付，此类需求走 2.0 SP2 LTS 或银河麒麟商业版。

本草案的结论在两个事件发生后必须复查：3.0 首个 SP 发布（校验 R-02/R-03 的实际修复），以及 2026-12-31 前 MCP 生态标准化进展（校验 R-08）。P3 阶段产出的自有性能数据回填后，本文升版为 v1.0 正式评估。
