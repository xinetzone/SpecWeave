# 06 最小权限与隔离：账户、文件、容器与网络

> 即使某个服务被攻破，合理的权限与隔离设计也能把影响限制在局部。本文覆盖账户与 sudo、文件权限、容器安全、网络隔离四个方面。

## 6.1 账户与 sudo 策略

- 每个服务以独立的低权限系统用户运行（如 Web 服务使用 `www-data`），不用 root 直接运行业务应用；
- 人员账户一人一户，通过用户组授权；闲置账户及时锁定：`sudo passwd -l <用户名>`；
- sudo 需要口令；按最小范围授权，避免 `ALL=(ALL) NOPASSWD: ALL`；
- 定期清理 `~/.ssh/authorized_keys` 中不再使用的公钥；人员离职立即收权（账户、密钥、云控制台、VPN）。

## 6.2 文件权限

- 通用原则：目录 755、文件 644；私钥与含口令的配置文件 600/640；
- Web 目录中需要写入的目录（上传、缓存）单独授权，且与可执行脚本目录分离；
- 临时目录（/tmp、/var/tmp）可按需挂载 noexec；属主设置为对应服务账户而非 root 之外的可写账户混用；
- 配置文件中的敏感信息（口令、API Key）通过环境变量注入，文件权限限制为仅运行账户可读。

## 6.3 容器安全

| 风险配置 | 说明 | 建议 |
|---|---|---|
| `--privileged` | 向容器授予近似宿主机 root 的操作能力 | 禁止使用，按需添加具体 capability |
| 挂载 `/var/run/docker.sock` | 容器获得对 Docker 守护进程的控制权，等同宿主 root | 不对普通业务容器挂载 |
| 以 root 运行容器内进程 | 逃逸后权限更高 | Dockerfile 中创建并切换非 root 用户 |
| 端口发布为 `0.0.0.0` | 直接对公网暴露 | 绑定 `127.0.0.1` 并经反向代理，或仅绑定内网地址 |

**Docker 与 ufw 的已知陷阱**：Docker 发布端口时直接写入 iptables 规则，该规则不受 ufw 命令管理——可能出现"ufw 未放行但外部仍可访问容器端口"的情况。约束手段应放在云安全组（第一层拦截）、Docker 网络与绑定地址上，而不能只依赖 ufw。

其他要点：使用精简基础镜像并持续更新镜像内软件；构建阶段不把私钥、口令写入镜像层；多容器业务通过自定义内网通信，数据库容器不发布公网端口。

## 6.4 网络隔离

- 数据库、缓存等后端服务放在无公网 IP 的内网/VPC 实例，应用服务器经内网地址访问；
- 利用云平台的子网与安全组划分层次（公网层 / 应用层 / 数据层），数据层仅接受应用层地址；
- 同一主机多业务之间，除容器隔离外也可使用独立系统用户、文件隔离与独立的反向代理入口；
- 管理面（SSH、面板、监控）与业务面使用不同的访问路径与来源控制。

## 6.5 验收标准

- `ps -eo user,comm` 抽查业务进程均非 root 运行；
- 不存在 privileged 容器与 docker.sock 挂载：`docker inspect` 核对；
- 数据库主机无公网 IP、公网端口不可达；
- 容器映射端口经外部 nmap 验证暴露面符合预期。
