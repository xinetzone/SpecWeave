# 可迁移的工程模式与边界

PhonePal 是一个样本，不是标准答案。它的价值在于把「LLM 操作真实设备」这件事拆成了可以独立讨论的五条模式；它的边界同样清楚，照抄之前要先知道自己需不需要这些边界。

## 模式一：双模型分工——让「说」和「做」用两套上下文

**做法**：CHAT 模型拿到人设、技能索引、记忆摘要与工具定义；OPERATOR 模型只拿到目标、技能正文、相关记忆、最近几步和当前屏幕，每步输出一个动作 [F-014/F-022/F-029]。

**为什么有效**：

- 聊天上下文不被几十个技能正文和截图撑爆；
- 操作模型的提示词可以针对「单步决策」优化，不必兼顾闲聊；
- 两个模型可以选不同档位：聊天用便宜的大上下文模型，操作必须用能看图、听话的模型。

**什么时候别用**：任务很简单、只有一个模型额度，或操作模型需要理解长对话时。拆两个模型也意味着两套失败模式、两份费用。

## 模式二：模型外的闸门——安全规则不写进提示词

**做法**：`PolicySentinel` 先 deny 再 ask 最后 allow；deny 覆盖受保护屏幕、密码字段、技能 apps 边界；ask 由 17 个内置确认词和技能追加词触发；每次决策写审计 [F-039/F-042/F-041]。

**为什么有效**：

- 模型被页面文字诱导时，规则仍然生效；
- 技能作者无法通过写 `confirm_before: []` 关掉内置词——`normalize` 只有合并，没有减法 [F-042]；
- 审计让「为什么点了支付」可回溯。

**什么时候别用**：纯只读 Agent（搜索、总结）不需要审批往返；但「受保护页面不操作」「不向密码框输入」这类 deny 仍然值得保留。

## 模式三：纯 JVM 内核——把平台能力压成三个接口

**做法**：`Device` 三方法、`LlmClient` 一方法、`MemoryStore` 六方法、`Sentinel` 两方法；5 个 `core-*` 不引用 Android，第三方运行时依赖只有 OkHttp 与 snakeyaml [F-013/F-017/F-018/F-077/F-078]。

**为什么有效**：

- 162 个 Kotlin 测试方法不需要设备 [F-075]；
- 换平台（桌面、车机、浏览器）只需实现 `Device`；
- 节点压缩、坐标换算、提示词拼装这些最容易出 bug 的逻辑都能在 CI 里跑。

**什么时候别用**：一次性脚本、强依赖平台 UI 框架的项目。分层本身有成本（接口、装配、测试替身）。

## 模式四：宽容解析 + 显式反馈——把模型失败当正常路径

**做法**：剥围栏、取配平 JSON、同义词/别名归一、坐标 clamp；解析失败、未知节点、被拦截、执行失败都进入下一轮反馈；连续无进展两级处理 [F-036/F-026/F-029]。

**为什么有效**：

- 兼容不同模型的「小毛病」，不因为一个多余字段就整轮失败；
- 模型能看到自己的错误并纠正，而不是让用户重说一遍；
- 卡死两级阈值避免「一次不动就放弃」与「无限重试」。

**什么时候别用**：输出要直接进数据库/支付系统的场景。那时应该严格 schema 校验 + 失败即拒绝，宽容解析反而危险。

## 模式五：文件即契约——技能与记忆都是人类可读文件

**做法**：技能是 `SKILL.md` + `flow.yaml`；记忆是 Basic Memory Markdown；CLI 与 App 用同一套校验规则 [F-019/F-045/F-053/F-074]。

**为什么有效**：

- 用户能看、能改、能 diff、能备份；
- 新场景不用发版，坏技能不会拖垮其他技能；
- 记忆可直接用 Obsidian 打开，降低「黑盒感」。

**什么时候别用**：需要强一致事务、多端并发写、细粒度权限的场景。文件 + 原子替换解决不了这些。

## 反模式：这份代码刻意没做的事

| 反模式 | PhonePal 的选择 | 代价 |
|---|---|---|
| 让一个模型同时聊天和点屏幕 | 拆成 CHAT/OPERATOR | 两套模型配置与费用 |
| 把安全规则写进 system prompt | 规则层 + 审批 + 审计 | 规则维护成本，需测试覆盖 |
| 把 Android 调用散落在业务逻辑里 | 收敛到 `hands` + `Device` | 多一层接口与装配 |
| 解析失败就抛异常 | 反馈给模型重试 | 可能多消耗几轮 token |
| 用数据库/向量库存记忆 | Markdown + 内存 BM25 | 无语义召回，规模受限 |
| 让技能执行任意脚本 | 只有声明式 `flow.yaml` | 复杂场景要靠 `ai` 步骤 |
| 在 release 包保留调试桥 | 只在 debug 清单导出 | 真机调试必须装 debug 包 |

## 它不解决的六类问题

1. **跨 App 的长流程编排**：没有全局计划器，只有逐步决策与单层子目标；
2. **视觉理解**：节点树优先，截图是补充；纯自绘界面只能靠坐标试错；
3. **多任务并行**：`AgentSession` 一次只跑一个任务 [F-069]；
4. **多设备/云端同步**：记忆与技能都在单机外部存储；
5. **权限提升与对抗**：无障碍权限一旦被滥用，应用层规则挡不住；
6. **模型成本控制**：没有预算、配额、缓存层；每一步都是一次模型调用。

## 如果你要复用，建议的最小改造顺序

```mermaid
flowchart LR
    A[先抄 Device/LlmClient 接口] --> B[写一个假 Device 跑通循环]
    B --> C[加 Sentinel 的 deny 规则]
    C --> D[再加 ask 与审计]
    D --> E[最后接真机与真模型]
```

先让循环在假设备上跑通，再接真实平台；先有 deny，再加 ask。这个顺序能让你在每一步都有可验证的失败边界，而不是一次性把所有复杂度接进来。
