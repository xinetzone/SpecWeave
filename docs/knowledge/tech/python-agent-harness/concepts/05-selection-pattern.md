# 05 模式：最小充分脚手架选型法（Minimal Sufficient Scaffold）

> 本文是 E 阶段萃取的可迁移模式（G3 通过）。读完你会得到一套六步选型流程、五个反模式、一组检验标准，以及一个跨领域迁移示例。

## 5.1 模式卡

| 要素 | 内容 |
|---|---|
| **一句话** | 为一个 agent 任务选框架时，不从功能清单或热度榜出发，而是先明确任务的失败成本与最小执行环，用同一任务的小规模实测记录"上手时间/代码量/治理缺口"，再按缺口反向选择生命体征健康的最薄脚手架 |
| **适用于** | ① 要在 2 个以上 agent 框架/SDK 间做引入决策；② 新 agent 应用立项，团队对"用多重的框架"有分歧；③ 已有 agent 原型要走向生产，需要补齐治理部件 |
| **不适用于** | ① 已被公司平台强制指定技术栈（合规/采购前提已定）；② 一次性脚本且无副作用（smolagents 直接用即可，选型成本高于框架成本，F-025）；③ 纯 RAG 检索类应用（RAG 型框架问题域不同，F-045） |
| **成熟度** | **L1-draft（3 个外部独立案例支撑，待本项目实战验证）**：mini-swe-agent vs SWE-agent 的 131 行/65% 对 4161 行/67%（F-032）、七框架同任务 TTFA/LOC 实测（F-003）、AutoGPT/BabyAGI 全自主循环退潮与原语留存（F-006/F-007）三个外部案例同向支撑；按方法论模式库等级标准，L2-validated 另需"已在本项目验证"，故暂定级 L1-draft，本团队一次真实选库实战后可升 L2。模式已于 2026-09-30 入库：[最小充分脚手架选型法（方法论模式库）](../../../../retrospective/patterns/methodology-patterns/governance-strategy/minimal-sufficient-scaffold-selection.md) |

## 5.2 核心步骤（六步）

### ① 任务分级：先算失败账，再选技术栈

用三个维度给任务定级：

| 维度 | 低端 | 高端 |
|---|---|---|
| 单次失败成本 | 只读分析、可丢弃 | 会改生产代码/花钱/对外发消息 |
| 任务时长 | 分钟级，一轮对话 | 小时级，跨会话 |
| 可并行性 | 单线程即可 | 子任务天然可切分、各自有验收标准 |

- 全低：脚本级——薄栈（smolagents/直接 SDK 调用）。
- 任一为高：进入步骤②时把对应治理部件标为**必需**（失败成本高→审批/权限；时长高→检查点恢复；并行高→tracing 先行）。
- 编排决策另设三条硬门槛（可并行切分 + 子任务独立验收 + 价值密度覆盖约 15 倍 token 成本，F-005），三条缺一不引入多智能体。

### ② 定义最小执行环（四件套底线）

无论最终用什么框架，一个能干活的 agent 至少需要：**模型客户端 + 工具面 + 文件/产物空间 + 执行隔离**。把四件套写下来，再对照 [02 九大部件](02-harness-anatomy.md) §2.1 标出"本任务必需/可选/不要"——显式写下"不要"和写下"要"同等重要，它是抵制满配诱惑的依据。

### ③ 同任务小赛（pattern 的核心动作）

- 选 ≥2 个候选框架，用**同一个真实任务**（不是 hello world）各做一遍；
- 记录三个数：**TTFA**（从建虚拟环境到首次成功运行的分钟数）、**LOC**（自己写的胶水代码行数）、**治理缺口清单**（对照步骤②的必需部件，缺几个）；
- 参考基线（他人单点实测，仅作量级假设，须自行复验，F-003）：七框架 TTFA 7–26 分钟、LOC 18–84 行。若你的实测数量级与此严重不符，先怀疑任务定义或候选姿势，而不是怀疑自己；
- 编码 agent 赛道可用同一真实 issue 复现 F-032 的对照思路（薄栈 vs 厚栈，记录成功率与成本）。

### ④ 生命体征检查（防选中"明日维护模式"）

对小赛胜出的候选做四项检查（依据 F-040/F-041）：

1. 最近发版日期与发版频率（0.x 高频发版不是坏事，但要配套读 CHANGELOG）；
2. 是否存在合并/更名/继任公告（AutoGen→MAF、Swarm→Agents SDK、Phidata→Agno、OpenDevin→OpenHands 均有此类事件，F-040）；
3. 官方文档/cookbook 是否 pin 版本并警告 API 变动（OpenAI cookbook pin 0.9.3 即是信号，F-016）；
4. issue 区与发版说明中"maintenance mode / archived"关键词（AutoGen 维护模式、SWE-agent maintenance-only 为前车之鉴，F-013/F-031）。

任一检查亮红灯，要么选择其官方继任者，要么准备好抽象层与迁移预案。

### ⑤ 按缺口选最薄栈，治理三件套不可省

- 在满足必需部件的候选中选**最薄**的（胶水代码最少、抽象层数最浅），把复杂度预算留给环境与模型；
- 无论栈多薄，治理三件套不可省：**权限/审批**（谁能拦危险动作）、**检查点/可恢复性**（进程死了怎么办）、**执行边界**（进程内沙箱还是容器，按失败成本选派别，F-039）；
- 模型绑定按战略选择（F-043）：深度用单一厂商可选运行时绑定型；要保留议价权选多 provider 抽象型或 LiteLLM 兼容型。

### ⑥ 锁版本、留预案

- 生产依赖精确锁定版本（`==` 而非 `>=`），0.x 包把框架升级当作独立变更走完整回归；
- 预留迁移锚点：业务代码与框架 API 之间保留一层薄适配（agent 定义、工具签名、消息格式不要散落在业务代码各处）——这是从四起合并/更名事件（F-040）中得出的保险费。

## 5.3 反模式清单（五个）

1. **按热度/star 选型**。AutoGen 约 58.9K stars 进入维护模式、SWE-agent 被 131 行项目替代（F-013/F-031/F-032）；star 是滞后指标且时点敏感，不反映生命状态。
2. **demo 同质就上线**。所有框架在客服/研究助理 demo 上看起来都能跑；真正分化的是长任务、恢复、审计与成本——这些只在步骤①的高端维度上才暴露（与 I-2 一致）。
3. **跳过同任务小赛直接押注**。TTFA 差异可达约 4 倍（7 对 26 分钟，F-003），别人的"顺手"不可替代自己团队的实测；小赛成本通常是半天，选错的成本是一个季度。
4. **把维护模式/0.x 频变栈当稳定基座**。表现为：不锁版本、不读 CHANGELOG、业务代码直接继承框架基类。症状出现于每次发版后（F-016/F-041）。
5. **一上来就多智能体编排**。在没有子任务独立验收标准时上 orchestrator-worker，等于花 15 倍 token 购买最难调试的交接面故障（F-005/F-007）。正确顺序永远是单 agent + 工具跑通，再按步骤①的三门槛决定是否升级。

## 5.4 检验标准（怎么知道这个模式被正确执行了）

- 产出一份**任务分级记录**（三个维度各有定级与依据）；
- 一份**最小执行环清单**，其中每件部件标注必需/可选/不要；
- 一份**同任务小赛记录**（≥2 候选 × TTFA/LOC/治理缺口三个数）；
- 一份**生命体征检查表**（四项均有结论与日期）；
- 最终架构中每个被启用的厚部件都能回答"它对应哪个失败案例或高端维度"；
- 依赖清单里所有 0.x/1.x 早期包均为精确版本锁定。

## 5.5 跨领域迁移示例

**迁移到"工作流编排引擎选型"（Temporal/Airflow/Celery 类决策）**：步骤①的失败成本/时长/并行三维直接通用；步骤②的最小执行环换成"队列 + worker + 状态存储 + 幂等边界"四件套；步骤③同任务小赛换成用同一订单履约流程跑两个引擎；步骤④生命体征检查（发版频率、维护公告、商业化归属）在 Airflow 生态分叉史中同样有效；步骤⑤的"治理三件套"对应重试幂等、超时策略、死信队列。模式结构不变，替换的只是部件名词表。

**反向不适用的边界**：选型对象是硬件设备或封闭商业软件时，步骤③的"同任务小赛"成本可能高到不可行（采购周期），此时模式退化为①②④三步，③以 POC 合同条款替代——这是本模式已知的适用边界，不强行外推。
