## 〇、最重要的发现：企业命题各有一张"专属评分表"

大赛统一评审是技术创新 30%/场景落地 30%/开源治理 20%/长期发展 20%（见 [03 参赛指南](03-participation-guide.md)），但**四份任务书都给出了本题独立的评分维度与权重**，且互不相同：

|------|-----------------|---------|
| openKylin 记忆评测 | 通用性15 / 数据设计25 / 自动评分25 / 稳定复现15 / 指标完整10 / 创新落地10（F-075、F-076） | **方法学导向**：数据+评分机制占半壁江山 |

## 二、openKylin 题：智能体长期记忆自动化评测 Benchmark

### 2.1 官方任务

智能体进入办公、研发、个人助理场景后，"长期、稳定、可控地记住用户信息"成为可用性关键；记忆既包括偏好、路径、模板等应保留信息，也包括临时信息、敏感信息、风险指令、噪声等应排除内容（F-067）。openKylin 生态已有 KylinBot、kylin-agent、OpenClaw、Hermes Agent 等框架，唯独缺一套系统级自动评测工具（F-068）。

现状三大痛点直接指明了作品要消灭的敌人（F-069）：

1. 评测依赖人工检查，无法规模化；
2. 简单问答验证覆盖不了**冲突更新、相似干扰、行动复用**；
3. 自动评分语义偏移，分不清"记住了 / 误记了 / 不该记却记了"。

目标产物：把**对话、记忆记录、行动轨迹、文件及其他运行产物统一组织为证据**，自动评估六类能力——长期保持、记忆调用、动态更新、相近区分、边界识别、任务复用（F-070）。

### 2.2 交付清单（逐项对照，缺一即失分）

| # | 交付物 | 验收要点 |
|---|--------|---------|
| a | 方案说明文档（F-071） | 测试目标/前提/数据生成/用例设计/结果收集/自动评分全流程；可扩展数据集结构；少人工、评分理由可解释 |
| b | 样例数据与样例结果（F-072） | 示例任务+运行证据+评分结果，证明方案可行 |
| c | 可复现材料（F-072） | 脚本/配置/README/代码，**openKylin 上直接编译运行** |
| d | 工具封装（F-073） | 一键 CLI（或 GUI），导入不同智能体配置**批量对比**；建议 .deb 软件包 |
| e | 演示视频 3–5 分钟（F-074） | openKylin 桌面下**至少两款智能体**实测 + 多维对比雷达图 |

### 2.3 评分对位（15/25/25/15/10/10）

- **数据设计 25%**：多种记忆情形 × 多种证据来源；样本有区分度与扩展空间（F-075）。
- **自动评分 25%**：必须能区分五种结果——正确记忆、遗漏、混淆、错误持久化、错误复用（F-075）。
- **稳定可复现 15%**：同输入结果稳定、批量运行、结果可追踪、标准环境复现（F-076）。
- **通用性 15%**：跨智能体、跨证据来源、与 openKylin 架构集成（F-075）。
- **指标完整 10% + 创新落地 10%**：多维指标而非单一总分；针对 openKylin 架构做优化（F-076）。
- 评审一句话定调：在**真实运行证据**上自动完成评测、稳定区分不同系统的记忆能力差异（F-077）。

### 2.4 💡 编者：创新切入点（非官方，按评分权重排序）

1. **证据流数据模型（对位 25% 数据设计）**：设计一套"记忆事件 DSL"——每个样本声明注入事实、干扰事实、更新序列、期望行为与判定断言；证据不限于文本，把记忆库快照、工具调用轨迹、文件变更都纳入统一 Evidence Schema。这是把"六能力"变成可执行用例的关键工程。
2. **双轨判分器（对位 25% 自动评分，直击"语义偏移"痛点）**：规则断言（精确事实、拒绝写入、覆盖更新）与 LLM-as-Judge（语义相似、调用合理性）双轨并行并设仲裁规则；评分输出结构化证据链（命中哪条证据→为何判为混淆/错误持久化）。
3. **记忆因果追踪**：不只比对最终答案，而是追踪"注入事实 → 后续检索 → 行动复用"的因果链，天然区分"记住但没调用"与"误调用"，比问答式评测高一个维度。
4. **稳定性量化（对位 15%）**：每个用例重复执行 N 次，输出通过率的置信区间与抖动率——"同一输入结果稳定"被显式写进细则，这是低成本高区分度的加分项。
5. **适配层即通用性（对位 15%）**：定义 Agent Adapter 接口（发消息、读记忆、读轨迹），先适配官网点名的 KylinBot/kylin-agent/OpenClaw/Hermes Agent 中至少两款，批量对比雷达图直接成为演示视频主线。
6. **.deb 分发（对位 10% 落地）**：任务书"建议产出 .deb 便于软件源分发"是命题方明示的期望，照做即拿到差异化印象分。

### 2.5 💡 风险提示

- 纯做"题库 + 人工标注答案 + 调模型打分"会同时丢掉数据设计与自动评分两档分（占 50%）。
- 视频只跑一款智能体不满足"至少两款"硬要求（F-074）。
- 评委要在 openKylin 复现，Windows/macOS 独占开发的团队需尽早准备 openKylin 环境（虚拟机/实体机）。

## 三、百度地图题："15 分钟生活圈"智能体检与规划助手

### 3.1 官方任务

政策背景是国家"15 分钟便民生活圈"建设（步行 15 分钟覆盖医疗、教育、购物、养老）。现有规划依赖人工普查与静态数据，致命缺陷是忽略"真实可达性"——**道路非直线，红绿灯、过街天桥、施工围挡都会改变步行范围**，传统手段成本高、更新慢、发现不了服务盲区（F-079）。

目标产物：基于百度地图开放能力（地理编码/逆地理编码、POI 检索、路径规划与距离计算等）开发 **Web 或小程序**；选定任一真实社区/街道，输入中心点坐标，自动计算**基于真实路网**的 15 分钟步行等时圈，统计圈内民生设施覆盖，输出可视化体检报告并自动标注"灰色区域"（F-080）。

### 3.2 交付清单

| # | 交付物 | 验收要点 |
|---|--------|---------|
| ① | 开源源码（F-081） | Gitee/GitHub + Apache 2.0/MIT |
| ② | 一键构建与自动化测试（F-082） | 编译/部署脚本+示例数据，Docker 或环境配置保证快速跑通 |
| ③ | 技术设计文档与报告（F-083） | API 调用策略、**等时圈生成算法**、多源 POI 清洗、盲区识别算法、**特定社区真实对比测试报告** |

### 3.3 评分对位（40/30/15/15）

- **功能正确性 40%（地板分，必须全拿）**（F-084）：
  - 坐标转换、POI 检索、路径规划三类 API 稳定调用；
  - 等时圈热力图准确渲染；
  - 盲区判定有量化定义：**周边 1 公里内没有菜市场、药店或小学**的点位。
- **API 深度与工程优化 30%（主要拉分区，官方直接给了创新方向）**（F-085）：
  - 大量 POI 点用"批量距离矩阵"或并发策略降耗时；
  - POI 缺失/API 异常/QPS 限流的容错与降级；
  - **官方明示鼓励**：不获取底层路网，仅凭分散点位 API 测时结果做**空间插值或扇形采样**推导近似连通区域。
- **交互体验 15%**：热力图/柱状图/雷达图、自定义中心点、流畅美观（F-086）。
- **开源规范 15%**：代码规范、README 含 API Key 脱敏说明、GitHub Actions/Gitee Go CI（F-087）。

### 3.4 💡 编者：创新切入点

1. **扇形采样 + 空间插值等时圈（官方钦定方向，必做）**：以中心点放射 N 个方向、沿不同距离设采样点，批量步行路径 API 测时，对"时间场"做 IDW/克里金插值并以 900 秒等值线成面——既省调用量又平滑，报告里附上与精确逐路计算、与直线缓冲区两种基线的误差对比。
2. **真实对比测试报告做出学术感（交付③）**：同一社区分别用"直线 1.25 km 圆"（约步行 15 分钟的朴素近似）与你的路网等时圈计算覆盖率，量化展示红绿灯/天桥/围挡导致的偏差——这正是命题痛点的实证，直接呼应 40% 功能分。
3. **阻抗人性化扩展**：给过街天桥、地下通道、施工点附加步行阻抗系数；进一步可做"适老模式"（老年人步速 + 无障碍设施加权）。注意标注为扩展功能，核心仍以官方 15 分钟定义为准。
4. **灰色区域 → 规划建议闭环**：识别盲区后自动生成"建议新增设施类型与候选位置"，把"体检工具"升级为"规划助手"（题名副标题），提升完成度叙事。
5. **时变等时圈（亮点向）**：路况/时段维度（工作日早晚高峰）对比，若 API 配额允许可作为加分演示；配额不足则在架构上预留。

### 3.5 💡 风险提示

- 这是四题中确定性最高、最适合学生/全栈团队的题，但正因为门槛清晰，**40% 功能分人人能拿，胜负在 30% 工程优化与插值创新**——只做"画圆+POI 打点"的朴素方案上限很低。
- API Key 脱敏被写进评分细则（F-087），提交前检查 git 历史中是否误提交密钥。
- 尽早申请百度地图开放平台 Key 并确认步行路径规划、批量距离矩阵接口的配额。

## 四、魔珐科技题：让 AI"活"起来——具身交互智能体

### 4.1 官方任务

痛点是当前 AI 交互停留于文本框/单向语音，缺形象、表情与肢体，难以传递温度与信任；展厅讲解、情感陪伴、教育科普、文旅导览、人形机器人陪伴等场景需要多模态同步、多硬件兼容、实时反馈与拟人人格，而传统开发成本高、只是"文本+形象"简单拼接、设备效果参差、**语音表情动作时序错位**（F-089、F-090）。

魔珐星云 SDK（XmovAvatar）已提供端到端底座：WebGL GPU 加速实时 3D 渲染驱动，支持 TTS（SSML）、口型同步、情绪表情、关键动作、行走动画，Web 与 Android 双端接入（F-091）。参赛者凭邀请码 **XJKA436Y6J** 注册得 1000 免费积分（F-092）。

### 4.2 三层自由度：作品的纵深档位

| 层 | 定位 | 可选能力（由浅入深） |
|----|------|---------------------|
| 表达层（**至少覆盖**） | 有温度的多模态呈现界面 | TTS/SSML、流式分段播报、字幕、形象与音色配置（F-093） |
| 交互层 | 可双向沟通的对话载体 | 接入任意大模型、RAG 问答、多轮对话、情绪匹配、聆听与打断（F-093） |
| 行动层 | 能执行任务的 Agent 载体 | Function Calling/MCP 工具调用、行走与动作编排、多模态 Widget 呈现结果（F-093） |

官方给了四个选题方向：知识服务型、效率助手型、普惠无障碍型、前沿探索型（F-094）。

**核心加分项（官方原文级要求）**：必须论证该场景下具身交互相比纯文本/纯语音的**不可替代价值**——"为什么该场景需要多模态双向交互，而不是对话框就能完成"（F-095）。

### 4.3 评分对位（25/25/35/15）

- **场景创意与价值 35%，是全场最高单项权重**：需求真实性、不可替代性论证、创意新颖度、社会与商业价值（F-099）。
- 产品完成度 25%：端到端顺畅；**客户端打断、断网自动降级、重连、弱网**等边界；Docker Compose 一键部署；视觉质量（F-097）。
- 智能交互深度 25%：大模型多轮对话；记忆/RAG/个性化（不能每次从零）；Listen/Think/Speak/emotion/关键动作(KA)/interrupt 状态与对话有机协同，明确反对"文本框+形象"浅层组装；行动层工具调用实现"能办事"（F-098）。
- 开源规范 15%：许可证、README 配置脱敏、提交记录、CI/CD、Issue/PR 社区机制（F-099）。

### 4.4 💡 编者：选题与创新策略

**选题决定 35% 的上限。选题前先做"删去数字人，功能是否崩塌"测试**：

| 选题方向 | 💡 不可替代性强弱评估 |
|---------|----------------------|
| 普通智能客服/通用问答 | 弱——对话框即可完成，不建议 |
| 多语种展厅/博物馆导览 | 强——形象+口型+手势指引天然多模态，知识服务型首选 |
| 听障沟通助手（实时语音→数字人手语/字幕） | 很强——感官障碍补偿，纯文本无法替代，社会价值满格 |
| 适老陪伴/健康提醒 | 强——老年群体对拟人形象与语音的接受度、情感依赖有现实依据 |
| 应急/医疗问诊沟通、教育教学带动作示范 | 强——表情安抚、动作示范是刚需 |
| 数字人调度机器人/虚实融合/多智能体协作 | 前沿探索型，创意分高但工程与演示风险大，适合有积累团队 |

**技术差异化（对位交互深度 25%）**：

1. **时序编排引擎**：针对官方点名的"时序错位"痛点，用 SSML 时间戳/事件回调驱动口型、表情、关键动作的精确同步，做成可复用编排层——这是最贴痛点的创新点。
2. **状态机而非回调堆砌**：显式建模 Listen→Think→Speak→emotion→KA→interrupt 六状态（F-098 原文列出的六个词），支持打断时优雅中止 TTS 与动作，视频中重点演示"被打断"。
3. **三层做满才稳拿交互分**：表达层是门票；RAG 知识库（选一个真实语料，如某博物馆导览词）支撑交互层；MCP/Function Calling 接 1–2 个真实工具（查展厅位置、预约、查天气/路线）支撑行动层。
4. **弱网/断网演示提前录进视频**：评分细则列举的"客户端打断、断网降级、重连、弱网"（F-097）几乎等于发了考试大纲，逐条演示。
5. **起步资源**：先用官方"SDK 开发助手 Skill"和教学演示项目（F-100）跑通最小闭环，把 1000 积分花在正式演示录制上。

### 4.5 💡 风险提示

- 3–5 分钟视频（F-096）要展示端到端流程，避免全程 PPT 式讲解；现场演示型作品还要为决赛路演准备稳定网络与备用录屏。
- 1000 积分有额度上限，开发期注意用量管理，避免正式录制时额度耗尽。
- 选题先过"非数字人不可"自问，无法自圆其说的方向技术再炫也丢 35% 的主分。

## 五、DaoCloud MatrixHub 题：模型制品恶意内容扫描与安全准入（智算云赛道）

### 5.1 官方任务与威胁模型

模型仓库不只有权重，还含配置、Tokenizer、Python 代码、动态库、压缩包与多种序列化文件；**PyTorch Pickle 加载即可触发任意代码执行**；未检查模型一旦进入研发终端或推理节点，风险即从仓库扩散至企业内网（F-102）。访问控制管得住"谁能传/下"，管不住"内容是否安全"（F-103）。

对标 Hugging Face Hub 的做法：提交后做恶意软件扫描 + Pickle 静态导入分析，并展示扫描中/通过/感染/错误状态。命题方同时提醒：扫描不是一次性绝对安全证明，还要解决超大文件、重复分片、扫描器故障、规则更新、误报、结果过期等工程问题（F-104）。

任务：为 MatrixHub（开源、自托管、兼容 Hugging Face 客户端的模型仓库）构建扫描与准入能力，在**不执行不可信模型代码**的前提下完成文件级检测、风险汇总与下载控制，给出可解释、可审计、可重扫的安全结论（F-101、F-105）。

### 5.2 九项必备能力（能力清单即合同）

| # | 能力 | 关键验收点 |
|---|------|-----------|
| ① | 扫描触发与版本关联（F-105） | 上传/代理缓存/同步后按明确版本或修订建任务；**内容变化必须产生新结论** |
| ② | 分层内容检测（F-105） | ≥1 种通用恶意软件检测 + ≥1 种危险序列化静态检测；Pickle **只静态分析、不反序列化** |
| ③ | 六状态汇总（F-106） | 待扫描/扫描中/通过/警告/阻断/失败六态可区分；**失败不得显示为通过**；文件级→版本级汇总 |
| ④ | HF API 兼容（F-106） | 支持 `HfApi.model_info(securityStatus=True, files_metadata=True)`；返回 `ModelInfo.security_repo_status` |
| ⑤ | 安全准入策略（F-107） | 按策略决定下载/同步/发布；阻断时客户端拿到明确稳定错误信息 |
| ⑥ | 可解释报告（F-107） | 命中文件/摘要/类型/规则/严重级别/扫描器及规则版本/时间/处置建议；**不展开恶意载荷** |
| ⑦ | 重扫与复用（F-108） | 人工重扫、规则更新重评；按可信摘要复用结果，但上下文/规则版本/租户不得混用 |
| ⑧ | 安全与可靠性（F-108） | 隔离+CPU/内存/磁盘/网络/超时五限；抗压：超大文件、压缩炸弹、异常格式、取消、扫描器挂、重启 |
| ⑨ | 审计与治理（F-108） | 任务/决策/复核/准入全记录，API+Web 可查，定位到操作者/项目/模型/版本/文件 |

### 5.3 交付清单

1. **需求与设计说明**：威胁模型、扫描边界、任务状态机、版本文件关联、策略决策、隔离方式、失败语义、结果保留、已知限制（F-109）。
2. **MatrixHub 开源代码贡献**：服务端/任务执行/数据模型/API/界面/部署的必要改动 + 公开 Issue/设计提案/PR + 可审查最终代码（F-109）。
3. **端到端原型**：纳入扫描→文件级+版本级结论→策略允许/阻断 HF 兼容下载；直接上传路径必做，代理缓存/同步为扩展（F-110）。
4. **检测与策略四项核心**：通用恶意软件扫描、危险序列化静态检测、版本结论汇总、下载准入，警告/阻断规则可配置（F-110）。
5. **自动化测试**：安全模型、EICAR 样本、危险 Pickle 静态样本、文件更新、重复内容、超时、扫描器不可用、重启、越权查询（F-111）。
6. **性能稳定性报告**：吞吐、等待、资源占用、复用效果、对上传下载链路影响、大文件高并发容量边界（F-111）。
7. **可复现材料**：部署清单或 Helm Chart、扫描器与规则配置、样本生成方式、测试脚本、README、版本清单、许可证、3–5 分钟视频（F-111）。

### 5.4 红线（触碰即不合格）

- **必须基于 MatrixHub 公开仓库实质贡献**：外部独立扫描脚本、无法关联版本、无法影响准入决策的，不视为完成（F-112）。
- **绝不执行不可信内容**：不加载模型、不反序列化、不导入模型自带模块、不执行仓库脚本；低权限隔离、默认禁凭据与外网（F-113）。
- **测试禁用真实恶意软件**：通用检测用 EICAR 无害样本，Pickle 用只供静态识别、不会执行的受控样本（F-113）。
- **状态不得折叠**：`securityRepoStatus` 必须与请求 revision 对应，未扫描/扫描中/失败/完成不能合并为空值（F-113）。
- **范围边界**：不要求检测输出有害性、数据投毒、模型后门、对抗样本——不要超范围承诺（F-112）。
- 集成 ClamAV 或公开 Pickle 静态工具即可，不要求自研引擎，但必须说明各扫描器覆盖范围与误报漏报边界，不得把单次通过表述为绝对安全（F-112）。
- **先对齐再开发**：先提公开 Issue/设计提案，获维护者或社区有效认可即进入完整评审；**不要求截止前合并，合入状态不是获奖必要条件**（F-113）。

### 5.5 评分对位（25/25/15/15/10/10）

- 检测覆盖与准确 25%：两类检测完成、类型识别/风险分级/版本汇总正确、安全/危险/误报/失败可靠区分（F-114）。
- **MatrixHub 集成与安全准入 25%**：与仓库/版本/文件/摘要正确关联；`securityStatus`+`files_metadata` 组合能被**官方 huggingface_hub 客户端**正确解析；策略真正控制下载流转（F-114）。
- 扫描执行安全 15% + 可靠规模 15%：隔离、资源受控、压缩炸弹不破坏平台；故障/重试/重启状态一致，大文件与重复分片处理合理，性能影响可量化（F-114）。
- 可解释治理 10% + 工程社区 10%：证据链完整、状态清晰可见；可复现易维护、符合项目结构并获社区认可（F-114）。

### 5.6 💡 编者：技术路线与创新切入点

1. **本周就做的第一件事（最高优先级）**：克隆 MatrixHub 仓库，读 `api/openapiv2/v1alpha1` 与 `hf-api-status.md`（F-114），跑通本地环境，按任务书指引提 Issue/设计提案。"社区认可"占 10% 且是进入完整评审的前提，越早暴露在维护者视野中越有利。
2. **参考实现坐标系**：Hugging Face Malware/Pickle Scanning 文档与样例仓库 `mcpotato/42-eicar-street`（仅参考展示效果，F-114）；通用扫描器选 ClamAV，Pickle 静态分析可选社区开源工具，用适配器模式封装以便多扫描器并存。
3. **六态状态机先行**：把待扫描/扫描中/通过/警告/阻断/失败（F-106）作为系统骨架，所有 API、UI、审计都围绕状态机；失败语义（fail-open 受控放行或 fail-closed 严格阻断）做成策略可配，但决策必须四处一致呈现（F-113）。
4. **结果复用缓存（区分度高的创新）**：以文件可信摘要为键、规则版本为失效条件的跨任务复用，严格隔离租户与扫描上下文（F-108）——大仓库重复分片多，缓存命中率可以写进性能报告，是少见的能同时拿下"规模适应性"与"性能数据"的设计。
5. **协议兼容自测**：直接用官方 `huggingface_hub` 库黑盒测试——端点指向你的 MatrixHub，跑 `model_info(..., securityStatus=True, files_metadata=True)` 并断言 `security_repo_status` 按 revision 正确变化、阻断下载时错误信息稳定。把这段脚本录进视频，25% 集成分就有了铁证。
6. **Worker 隔离方案**：容器/sandbox 执行扫描器，五限（CPU/内存/磁盘/网络/超时）+ 流式扫描防压缩炸弹；越权查询测试用例预置两个租户互相访问。

### 5.7 💡 风险提示

- 本题是四题中**唯一要求上游协作与真实协议兼容**的题，时间盒要前置：Issue 对齐与环境搭建至少留两周，不要把时间全花在扫描算法上。
- 专项奖金"具体以 DaoCloud 要求为准"（F-114），不要在材料中写死金额承诺。
- 安全类项目最忌演示事故：视频中绝不加载真实恶意样本，全部用 EICAR 与受控静态样本。
