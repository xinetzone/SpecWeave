# AtomGit 选型评估报告：对标 GitHub / 极狐 GitLab / Gitee

> **方法论**：七概念编排 **R（事实）→ I（洞察）→ E（萃取）→ V（对抗审查）**。R 阶段完成公开事实采集（F-001~F-040），I 阶段形成 4 条四元组洞察，E 阶段沉淀选型模式，V 阶段 4 视角对抗审查并落地 5 条修正。
> **评估范围**：代码托管平台选型（代码协作 / CI-CD / 成本 / 主权 / 生态 / 退出），面向国内研发团队与开源项目。
> **非评估范围**：厂商安全渗透测试、SLA 实测、商务谈判条款。

---

## 一、执行摘要（结论先行）

**结论**：AtomGit 在「数据主权」与「AI 算力供给」上具备差异化优势，在「CI/CD 生态兼容」与「迁移/退出成本」上显著偏弱，**综合加权得分 71/100，低于极狐 GitLab（86）、GitHub（80）与 Gitee（80）**。

**推荐使用场景**

- 主体在中国的国内开源项目，需要中文社区曝光与 G-Star 类运营扶持；
- 需要免费/低成本 AI 算力（AtomCode CodingPlan、Notebook 核时）作为开发辅助；
- 承接开放原子开源基金会生态项目（开源鸿蒙、openEuler、OpenTenBase 等主仓已在 atomgit.com，F-028）。

**不推荐作为唯一主仓的场景**

- 面向国际社区贡献的项目（网络效应在 GitHub，F-025/F-026）；
- 重度依赖 GitHub Actions 生态（Marketplace、`uses:` 复用）的项目（F-031/F-033）；
- 有私有化部署 / 信创 / 等保硬要求的企业（AtomGit 公开资料未见私有化方案，而 Gitee 与极狐 GitLab 均明确提供，F-040）。

**核心行动建议**：不应把 AtomGit 当作「GitHub 替代品」来选型，而应定位为**国内镜像 + 自有项目主托管**，以双远端拓扑与 GitHub 并存。

## 三、评估方法

采用 E 阶段萃取的模式 **`pat-code-hosting-four-filter-001`「代码托管四筛法」**，落为六个可打分维度：

| 维度 | 权重 | 打分锚点 |
|---|---:|---|
| 数据主权与合规 | 25% | 运营主体属地、私有化能力、资质 |
| 功能完备度 | 15% | 代码协作 / 项目管理 / 权限 / 安全特性 |
| CI/CD 与生态兼容 | 20% | 语法兼容度、Runner、Marketplace 复用 |
| 成本效益 | 15% | 免费额度、计量口径、AI 算力 |
| 生态与网络效应 | 15% | 社区规模、上游项目密度 |
| 迁移与退出成本 | 10% | 导入能力、私有资产可带走性、数据删除条款 |

四筛法六步：①主权筛 → ②生态筛 → ③用量筛 → ④退出筛 → ⑤定拓扑 → ⑥试点。

## 五、洞察（I 阶段·四元组）

### 洞察 1：分水岭是「数据主权」，不是功能表

- **陈述**：四家功能已高度同质（F-008~F-013），真正不可替代的差异是代码存放地的管辖权与合规约束。
- **证据**：F-001 / F-005 / F-007 / F-023 / F-040。
- **反常识**：厂商引导用户比「功能对比表」，但功能表里没有一行是「数据出境」。
- **行动**：选型第一步先做管辖权筛选，不合格者直接出局，再进功能比较。

### 洞察 2：成本拐点由「计量单位」决定，不由「价格/人/年」决定

- **陈述**：Gitee 与极狐的 CI 额度分别用「核分/年」和「分钟/月」计量，且 Gitee 两处页面口径互相矛盾，直接比单价会得出错误结论。
- **证据**：F-015 / F-016 / F-018 / F-022。
- **反常识**：同一家官网对同一档套餐给出两种计量口径，说明「价格/人/年」这一最常用比较口径本身不可靠。
- **行动**：按「构建时长 × 并发数 × 月构建次数」折算真实用量；对 Gitee 须向销售书面确认「核分 ↔ 分钟」换算关系。

### 洞察 3：网络效应无法用镜像复制

- **陈述**：国内平台的「GitHub 加速」解决读取速度，不解决贡献回流——Issue/PR/Review 仍发生在 GitHub。
- **证据**：F-025（第三方提供 GitHub 加速）与 F-026（基金会项目仍以 github.com 为主仓）并存；F-029/F-030 显示本工作区本身即为「GitHub 上游 + GitCode/本地镜像」双远端结构。
- **反常识**：「访问快」常被当作选择国内平台的理由，但上游在 GitHub 的项目，镜像只让读者更快，不会让社区看见贡献。
- **行动**：对开源项目采用 canonical + mirror 双远端拓扑，canonical 跟随社区所在平台；「贡献回流路径」作为独立设计项。

### 洞察 4：退出成本由「平台私有资产」决定，不由 Git 决定

- **陈述**：`git clone --mirror` 只能搬走代码，PR 评论、CI Secrets、权限模型、CodeOwners、AI Credits 属平台私有资产，不可迁移。
- **证据**：F-008 / F-023 / F-024 / F-035。
- **反常识**：人们默认「代码托管平台可随时迁移」，实际锁定发生在 Git 之外的那一层。
- **行动**：选型时列「平台私有资产清单」计入退出成本；优先选择 API 标准化程度高的平台（AtomGit 支持 OpenAPI，F-008）。

> **G2 检验**：4 条洞察（≥3 ✅）｜四元组完整 ✅｜维度不重叠（管辖权/成本/生态/退出）✅｜均有具体行动 ✅。

## 六、萃取（E 阶段·模式）

```yaml
id: pat-code-hosting-four-filter-001
name: 代码托管四筛法
maturity: L2
evidence: 本工作区 gitcode + GitHub + SMB 三远端结构（F-029/F-030）；开放原子基金会项目跨三平台分布（F-026~F-028）
```

**适用于**：为团队/项目选择代码托管平台，或评估从现有平台迁移。

**不适用于**：已由合规或客户强制指定的平台（此时无选型空间）。

**核心步骤（6 步）**

1. **主权筛**：判定代码是否可出境、是否需信创/等保/密评 → 划掉不合规平台。
2. **生态筛**：确认协作者与目标社区在哪 → 决定 canonical 平台。
3. **用量筛**：统计 CI 分钟/并发/存储真实用量，按各平台计量单位折算，而非比标价。
4. **退出筛**：列平台私有资产清单，估算迁移工时。
5. **拓扑定**：确定 canonical + mirror 双远端及同步方向。
6. **试点**：拿一个真实仓库跑通 PR → CI → 权限 → 发布全链路，再全量铺开。

**反模式**

| # | 反模式 | 证据 |
|---|---|---|
| 1 | 只比功能对比表，忽略管辖权 | F-011 这类表格无一行涉及数据存放地 |
| 2 | 只比「价格/人/年」，忽略计费口径差异 | F-015 vs F-016 同档两种口径 |
| 3 | 认为 `git mirror` 可完整迁移 | F-008/F-023/F-024 私有资产不可迁移 |
| 4 | 把「访问加速」当成「生态迁移」 | F-025 vs F-026 贡献仍在 GitHub |

**检验标准**：选型结论能一句话回答四问——代码在哪、谁可访问、月成本多少、退出要多久。任一答不出即为未完成。

**跨场景迁移**：同一四筛法可迁移到 **AI 模型/权重托管平台选型**（HuggingFace vs ModelScope vs 魔搭）：主权筛 = 模型可否出境与备案，生态筛 = 目标使用者在哪，用量筛 = 存储与推理配额，退出筛 = 数据集/评测结果可否带走。

> **G3 检验**：名称 7 字 ✅｜适用/不适用边界 ✅｜6 步可执行 ✅｜4 个反模式（≥3）✅｜有检验标准 ✅｜有跨域迁移 ✅｜多案例 L2 ✅。

## 七、六维详细评估

### 7.1 数据主权与合规（4/5）

**优势**：境内主体运营，代码默认存放境内（F-001）；与开放原子基金会深度绑定，具备承接国内开源生态的合规叙事（F-003/F-028）。

**缺口（关键）**：公开资料**未见私有化部署方案**。Gitee 明确提供私有化部署 + 信创适配 + 信创一体机，极狐 GitLab 提供私有化专业版/旗舰版（F-040）。若企业有「数据不出域 + 信创」硬约束，AtomGit 目前无法满足；亦未找到等保/密评资质的公开披露。

**风险条款（需法务过目）**：ToS 明确注销账号会同时删除 AtomGit 与 GitCode 两平台的个人信息与项目数据（F-035）——代码资产的「退出即清除」语义需在采用前评估。

### 7.2 功能完备度（4/5）

已具备：WebIDE、自定义 Issue 模板、GPG 签名验证、多级 CodeOwners、组织级自定义权限、组织看板、OpenAPI、超级仓、内置 CI/CD、AI 模型仓/数据仓（F-008/F-009/F-010）。

缺口：未见 SVN 支持（Gitee 支持 Git + SVN，F-011）；未见测试管理与制品管理（Gitee 企业版与极狐 GitLab 均有，F-012/F-017）；生态插件绝对数量与 GitHub Marketplace 不在同一量级。

### 7.3 CI/CD 与生态兼容（3/5）— 最大摩擦点

| 事实 | 编号 |
|---|---|
| workflow 目录为 `.gitcode/workflows/<name>.yml`，非 `.github/workflows/` | F-031 |
| 步骤引用语法为 `uses: checkout`，非 `actions/checkout@v4` 形式 | F-031 |
| Runner 标签为 `[ubuntu-latest, x64, small]` 三元素形式 | F-032 |
| 特有 `stages`（阶段串行 + fail_fast）与 `post` 机制 | F-033 |
| 权限令牌为 `ATOMGIT_TOKEN`（非 `GITHUB_TOKEN`） | F-033 |
| GitHub 官方提供 Actions Importer 自动迁移工具（目标转换率 80%），AtomGit 侧未见对等工具 | F-039 |

**判断**：AtomGit Action 与 GitHub Actions **形似而非兼容**。含义有三：

1. 现有 `.github/workflows/*.yml` 不能直接复用，需改目录、改 `uses` 语法、改令牌名；
2. 反向迁移（AtomGit → GitHub）同样无自动化工具（F-039 显示工具只朝 GitHub 方向）；
3. 若团队核心资产是数百条成熟 Actions 流水线，迁移摩擦成本将成主导性成本项。

### 7.4 成本效益（4/5）

**优势**：AtomCode CodingPlan Lite 档据称永久免费，含 DeepSeek-V4-Flash、Qwen3.6-35B-A3B、Qwen3-VL-8B，采用 5 小时滚动窗口限流、30 天需续领；平台据称另提供 Notebook/Space 每月 1000 核时免费算力（F-037/F-038，低置信）。

**缺口**：公开资料**未见 AtomGit 的定价页与配额表**。对照之下，Gitee（F-014~F-017）与极狐 GitLab（F-022/F-023）均有明码标价。AtomGit 的成本无法在选型阶段量化，只能走询价流程。

### 7.5 生态与网络效应（3/5）

正向：依托 CSDN 社区，官方称覆盖 5200 万开发者（F-004）；承接开放原子基金会项目（F-028）。

负向（关键）：AtomGit 提供的「GitHub 加速服务」恰恰说明上游源在 GitHub（F-025）；同一基金会项目列表里 XuperCore/hapjs/Tongsuo 仍在 github.com（F-026），openKylin/GreatSQL 仍在 gitee.com（F-027）——镜像解决读取速度，不解决贡献回流。

结论：AtomGit 的网络效应是「借势」而非「自有」，短期内无法复制 GitHub 的社区密度。

### 7.6 迁移与退出成本（3/5）

**入向（较友好）**：支持导入 Git 项目（含私有仓库），提供「导入所有分支」选项，可设置可见性（F-034）；账户与 GitCode 打通（F-004）。

**出向（需警惕）**：PR 评论、CI Secrets、权限模型、CodeOwners、AI Credits 属平台私有资产，`git clone --mirror` 带不走（洞察 4）；无对等的反向 CI 迁移工具（F-039）；ToS 的「注销即双平台数据删除」条款（F-035）抬高了退出的不可逆性。

## 十一、落地实施建议

1. **定拓扑**：canonical 依社区位置定；本工作区已实测为 gitcode 为 origin、另有 UNC/SMB 远端（F-029），建议保留该双远端结构并补一条 GitHub 上游。
2. **PoC 试点**：选 1 个真实仓库，用「导入所有分支」迁移（F-034），实测三件事：
   - `.github/workflows/*.yml` → `.gitcode/workflows/*.yml` 的改写工时；
   - `uses:` 引用在 AtomGit 的替代方案（Marketplace 动作是否可用）；
   - `GITHUB_TOKEN` → `ATOMGIT_TOKEN` 的权限模型差异。
3. **成本量化**：索取配额表，按真实用量折算；与 Gitee 标准版（¥299/人/年，F-015）做同口径对比。
4. **合规确认**：书面确认私有化部署、等保资质、数据留存与导出策略。
5. **备份兜底**：建立平台外的裸仓镜像，规避 R-4。
6. **再决策**：PoC 通过则全量迁移镜像仓；不通过则保持「国内镜像 + GitHub 主仓」。

```bash
# 查看当前远端布局（本工作区实测结果见 F-029）
git remote -v

# 双远端：github 为 canonical，atomgit 为镜像
git remote add atomgit git@atomgit.com:<org>/<repo>.git
git remote set-url --add --push origin git@github.com:<org>/<repo>.git
git remote set-url --add --push origin git@atomgit.com:<org>/<repo>.git
```
