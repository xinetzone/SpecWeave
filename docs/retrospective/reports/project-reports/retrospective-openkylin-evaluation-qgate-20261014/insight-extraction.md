# 洞察萃取：openKylin 评估里程碑复盘

> 本文件承载元层复盘的核心中间产出：第一节为三条洞察的完整四元组（G2 PASS），第二节说明本批洞察与原评估四条对象层洞察的层级关系，第三节为模式萃取与去重裁决（G3 PASS），第四节为 V 阶段四视角对抗审查摘要。R 阶段 30 条事实（F-001~F-030，G1 PASS）见 [README.md](README.md) 第二节，行动项见 [actionable-items.md](actionable-items.md)。

## 第一节：三条洞察（G2 PASS）

### I-1 证据经济学：缺口关闭的最优证据在供给侧，不在用户路径硬复现

- **现象描述**：二轮关闭 Q-2（跨版本升级路径）时，没有下载 4.8GB ISO、没有导入虚拟机、没有点击 GUI，而是枚举 cdimage 发布目录确认 2.0/2.0-SP1/2.0-SP2 均无 WSL 镜像（F-014），一次 HTTP GET 取得升级通道配置 sources.json——sources 数组仅 1 条（Beta1→2.0）、HTTP Last-Modified 冻结于 2024-08-26（F-015），再解包升级器 kylin-revision-manager 1.0.3.0 确认其为 2023-12 构建的 ISO/initramfs 物理机流程（F-016）。Q-8 同理：91 个 deb 全部以 apt-get download 落独立数据盘 /mnt/ai 解包、用后即删（F-018），取证前后 dpkg -l 均无 Gen2 包、根分区两次记录均为 3.0G（F-019）。
- **根因分析（5-Whys）**：①为什么不按用户路径硬复现？完整路径成本是 GB 级下载加 GUI 操作，且一次复现只能得到样本级结论（"这台机器这次没升成"）；②为什么服务端配置证据更强？通道配置是总体性证据——唯一通道且时间戳冻结，直接回答"官方从未开放过该通道"，样本级失败回答不了这个命题；③为什么敢只看配置就下结论？并非只看配置：先取服务端观测点，再补客户端侧取证（升级器包内 changelog 止于 2023-12、流程为 initramfs 重启升级），两侧拼合才闭环；④为什么"先复现"是普遍直觉？"真跑一遍才放心"的实证本能把亲手复现当作黄金标准，忽视了观测点的证据层级差异；⑤**系统性根因**：证据采集存在成本—强度曲线，供给侧观测点（服务端配置、目录清单、包元数据）以接近一次 HTTP GET 的成本提供总体级证据，用户路径复现以 GB 级成本提供样本级证据。默认顺序应当反转：先穷尽供给侧观测点，功能复现只留给"实现是否存在、真实表现如何"这类观测点回答不了的问题。
- **影响评估**：时间上 Q-2/Q-8 在单会话内完成过去需要数天环境搭建的核验；质量上升级路径结论从样本级提升到总体级；成本上对被验系统零污染（F-019）；残余风险是服务端证据与客户端消费之间可能脱节（见 V-1，已固化为模式反模式 5）。
- **改进建议**：①把"供给侧观测点枚举"设为启动重成本复现前的强制前置门；②大体积下载一律落独立数据盘，用后即删并做前后对账；③服务端证据必须补客户端侧消费链验证，不得单凭同名配置断言客户端行为。
- **证据**：F-014、F-015、F-016、F-018、F-019

### I-2 证据等级阶梯：能力结论必须锚定 L0~L3 档位，禁止跨档表述

- **现象描述**：Q-8 对 Gen2 能力的核验天然呈现四个台阶：模拟安装给出闭包规模（全装 267 包、base2 闭包 88 包约 330MB）并提示会移除 libcurl3-gnutls（F-017）；解包二进制免安装运行，--version 输出 kylinbot 0.7.5、--help 列 27 子命令、providers 实跑输出 66 家、ldd 无缺库（F-020）；strings 取到 mcp_client.rs/mcp_transport.rs、tools/call、JSON-RPC、mcp.servers 等实现痕迹（F-021）；包内 12 个桌面技能为 gdbus 调 org.ukui.Framework 示例、模型清单列 47 个文件且经 ModelScope 匿名下载（F-022）；而模型实际推理、外部 MCP tools/call 往返、语音端到端三项显式登记为未验证（F-023），7.6 维评分维持 4 分不上调。
- **根因分析（5-Whys）**：①为什么做到只读运行还不宣称"AI 功能可用"？包在仓库里、实现存在、只读链路可运行、端到端产出真实结果，是四个不同命题；②为什么跨档表述如此常见？厂商材料与媒体稿本身跨档（"内置大模型"的实际含义往往只是包在仓库中）；③为什么要把未验证项写出来？乐观补全不可审计，下一轮复核无从知道还差什么；④为什么评分不跟着新事实走？架构级证据只够确认"实现存在"（L2），加分需要 L3，事实更新与评分裁决必须分离；⑤**系统性根因**：能力类事实天然分层，"有/无"布尔表述压缩掉了证据强度信息，使报告在传播中必然失真。必须引入显式档位词汇表（L0 无／L1 制品级／L2 架构级／L3 功能级），强制结论措辞与证据同档，双向防错：既防 L1→L3 的虚报，也防"未测"被写成 L0 的漏报。
- **影响评估**：VF-61 三项未验证成为明确的用户接管点而非报告缺陷；7.6 维维持 4 分的算式可审计；档位词汇表让第二人复核时能快速定位"差一级证据"的具体位置。
- **改进建议**：①评估模板中每条能力结论强制标注 L0~L3 之一；②未达 L3 的项单列边界声明（差什么、需要什么条件、谁接管）；③评分变动必须引用档位变化并留算式。
- **证据**：F-017、F-020、F-021、F-022、F-023

### I-3 未知项负债化：Open Questions 显式编号加复核窗口，把"不知道"变成可偿还的债

- **现象描述**：初始报告交付时显式登记 Q-1~Q-8 清单，每行含验证方式与复核窗口（90 天/季度/持续/随版本，F-008）；首轮以 4 路并行调研代理加本机只读实测执行，网络抓取集中在约 63 分钟内（F-009、F-010），结果高度异构——Q-1 部分推翻原判断、Q-6 证伪、Q-4 强化单源结论、Q-3/Q-5/Q-7 取得新事实（F-011）；评分仅 7.2 一个维度 2→3、总分 70→73，其余五维不动，V 门历史意见以追加方式保留不改写（F-012）；二轮在用户明确授权后约 57 分钟启动（F-013）。
- **根因分析（5-Whys）**：①为什么初版敢带着 8 个缺口交付？缺口不是隐藏缺陷，而是登记在册、带验证方式与到期日的负债；②为什么两轮之间设置用户授权点？二轮涉及解包与下载，授权点本身是成本与边界的质量闸；③为什么异构结果能被有序消化？每项在 Q 表中预定了验证方式，结果回来对号入座为闭环/证伪/部分闭环；④为什么评分只动一个维度？事实层更新与评分裁决分离，证伪与推翻只改对应事实不改全局印象；⑤**系统性根因**：未知项若不负债化，会以"据说""可能""暂无公开数据"等模糊措辞潜伏在正文里，既无法追踪也不会到期，报告在交付的瞬间开始过时。显式编号＋验证方式＋复核窗口把未知从"语气"变成"台账"，使报告成为可增量清偿的活文档，而非一次性快照。
- **影响评估**：单日内两轮增量核验有序归位 61 条新事实；证伪项（Q-6 九份安可公告零在列）反向增强报告可信度；评分净变动最小且每分可审计（70→73→73）；窗口机制把未来的复核成本前置定价。
- **改进建议**：①所有评估类报告交付前必过"Open Questions 表"门禁（编号/问题/验证方式/窗口四列缺一不可）；②窗口到期即触发复核，结论并陈不裁决者须显式标注；③把证伪与部分推翻视为报告增益而非失败，保留历史判断与核销轨迹。
- **证据**：F-008、F-009、F-010、F-011、F-012、F-013

**G2 检验**：3 条洞察（≥3 ✅）｜四元组完整（现象/根因/影响/建议）✅｜维度不重叠（取证顺序/证据表述/未知项管理）✅｜均有反常识点与可执行行动 ✅。

## 第二节：与原评估四条洞察的层级关系

> 原报告第五章四条洞察的对象是 **openKylin**（对象层）；本复盘三条洞察的对象是**这次评估的生产过程本身**（方法层）。两层不冲突、不互证，关系如下。

| 原评估对象层洞察（报告第五章） | 对应本批方法层洞察 | 关系 |
|---|---|---|
| 洞察 1：规模指标六个来源但独立信源数为零 | I-3（未知项负债化） | Q-4/Q-5 正是把"独立信源缺失"登记为可核验负债并清偿的实例 |
| 洞察 2：基金会治理形式化、贡献集中于单一公司 | I-2（证据等级阶梯） | 麒麟占比 85.2%/96.1% 属看板枚举的制品级证据，结论按档表述未跨档 |
| 洞察 3：跟版最快、LTS 政策成文晚且口径冲突 | I-1（供给侧观测优先） | NC-01 的三文本并陈与 Q-2 的通道配置取证，均由供给侧观测点直接产出 |
| 洞察 4：两千万用户与排名八十万开外可同时为真但不可互验 | I-2（证据等级阶梯） | 自报口径与弱旁证不互相升级，正是"禁止跨档表述"的适用案例 |

**小结**：对象层洞察回答"openKylin 是什么样"，方法层洞察回答"这类结论应以什么证据成本与证据等级产出"。原报告四条洞察的评分含义在本复盘后保持不变（73/100 维持）。

## 第三节：模式萃取（G3 PASS）

### 3.1 新模式：缺口双轮核验法

> 已入库（L1-draft，单案例验证，待第二个非同谱系案例升级 L1.5）：[gap-two-round-verification](../../../patterns/methodology-patterns/research-knowledge/gap-two-round-verification.md)。

**一句话定义**：评估报告的缺口清单逐项执行两轮——第一轮公开信源轮（换环境复述访问＋供给侧观测点优先＋负证据强制留痕），第二轮零变更功能轮（模拟安装/下载解包/二进制静态取证/免安装冒烟/会话总线只读探测）；每项结论锚定 L0~L3 四档证据等级之一，并以"结论与评分解耦、未验证显式留痕、环境前后对账"三道收口防止过度宣称。

案例挂载：Q-2 三重坐实（F-014/F-015/F-016）、Q-8 架构级闭环（F-017~F-023）、DistroWatch 403 换 UA 得 #107（首轮）、Q-6 九份公告零在列的高强度负证据（首轮）。

### 3.2 去重裁决：与「社区指标三查法」互补，不并入

| 候选 | 解决的问题 | 裁决 |
|---|---|---|
| community-metric-triple-check（同里程碑上午已入库，L1-draft） | 规模数字"能不能信"（自报/转引/独立审计三查） | 保留独立，两模式已互链 |
| gap-two-round-verification（本次） | 缺口清单"怎么关闭"（两轮＋四档＋三收口） | **G3 PASS，新建** |

裁决理由：两者共享"证据强度分级"思想，但输入与机制不同——前者输入是单个数字主张，机制是引用链追源；后者输入是一张未知项台账，机制是分层取证流程。合并会使任一模式的触发条件模糊。另核查相关模式：adversarial-review-protocol（V 门流程）、falsifiable-claim-evaluation（主张可证伪性）、credibility-dual-track（可信度双轨）均不覆盖"负证据留痕＋供给侧优先"的组合机制，无重复。

### 4.3 不采纳 4 条与理由

- **V-4（不采纳）**：模式适用边界已明确排除性能/容量/主观体验/长期稳定性四类问题，第二轮触发条件为"当且仅当第一轮回答不了实现是否存在"，L3 功能级证据只能由端到端实测获得，机制本身不允许跳级。
- **V-5（不采纳）**："零变更"的宾语是**被验系统**而非宿主环境；F-019 的 dpkg 与根分区前后对账已证明被验系统零污染，三道收口第 3 条对该边界有明确定义。
- **V-6（不采纳）**：两套 L0~L3 分属不同语义域（本模式为证据强度档，上游怪癖分级为断言强度档），各自携带定义表且模式已在 related_patterns 交叉引用；若第三个非同谱系案例应用时仍出现混淆，再行更名。
- **V-7（不并入模式，由行动项承接）**：窗口触发依赖台账外的执行机制，不属于模式内流程；90 天复核（ACT-01）、季度抽查（ACT-05）与模式升级条件（ACT-03）已把本次全部窗口登记为带 owner 的可执行项，机制有效性由行动项层保证。
