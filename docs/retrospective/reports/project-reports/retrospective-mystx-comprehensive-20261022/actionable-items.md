# 原子行动项：mystx 主题包全面复盘

> 本文件承载本轮复盘的 **A 阶段（G4 行动项可判定）** 产出：**10 条原子行动项**，编号 `ACT-01` ~ `ACT-10` 连续无跳号。每条单一职责、可独立验证，含 6 个字段：**描述 / 优先级 / Owner / 触发条件·时间节点 / 验收标准（标注 rule 或 rubric 类型）/ 来源**。
>
> 其中 `ACT-01` ~ `ACT-09` 为面向 **mystx 工程侧**的可执行改进项；`ACT-10` 为 V 阶段对抗审查得出的**方法论侧**守门动作（Owner 为复盘方法论维护者，非 mystx 维护者），二者不混合。
>
> 洞察全文见 [insight-extraction.md](insight-extraction.md)，主报告见 [README.md](README.md)。全部内容来自 Spec 中间产物（`facts.md` / `insights.md` / `e-stage-pattern.md` / `v-adversarial-review.md`），未引入新的事实断言。

## 行动项清单

### ACT-01 发布资格不变量清单落盘为可执行检查（8 条不变量 + 豁免登记）

- **描述**：把 E 阶段主模式 C1 的「发布资格不变量」集（I-1 ~ I-8 共 8 条）写成 mystx 仓库内一份**可判定的检查清单**，每条不变量给出明确的判定方式（命令判定而非人工核对），并配套一份**豁免登记**用于显式登记不可修复的历史断层。当前 mystx 的全部质量关卡与版本坐标校验均不存在，此项是后续所有发布侧动作的前提资产。
- **优先级**：高
- **Owner**：mystx 维护者
- **触发条件·时间节点**：在下一次版本发布（v0.3.9 或之后）打 tag 之前完成清单落盘；且必须早于任何新的公开 Release 发布动作
- **验收标准（rule）**：① 仓库内存在一份「发布资格不变量清单」文件，逐条对应 I-1 ~ I-8 共 8 条不变量，每条标注其判定方式为「命令判定」而非「人工核对」；② 其中至少 I-1（标签可达性）、I-2（版本序列连续性）、I-3（变更记录存在性）、I-5（成熟度分类一致）、I-7（action ref 钉版本）5 条落地为可自动执行的脚本或 CI job，且失败时以非零退出码阻断；③ 存在独立的豁免登记文件，逐条登记 4 类已知豁免（谱系不可达 tag、版本序列缺号、变更记录缺失 tag、成熟度分类），每条含豁免理由与到期条件；④ 清单中每条不变量至少绑定 1 个 F 编号作为依据
- **来源**：I-1、I-3；C1 模式步骤③与不变量表 I-1 ~ I-8；F-009、F-011、F-018、F-071、F-072、F-092、F-097

### ACT-02 发布触发链改造：去人工旁路、action ref 钉版本、挂载不变量校验

- **描述**：改造 `.github/workflows/python-publish.yml`，把发布触发从「人工点一次 GitHub Release」改为「标签推送」，把 3 处浮动 action ref（`actions/checkout@main`、`actions/setup-python@main`、`pypa/gh-action-pypi-publish@unstable/v1`）钉到不可变 commit SHA，并把 ACT-01 的不变量校验与测试执行挂到发布触发链上，消灭「未校验旁路」。
- **优先级**：高
- **Owner**：发布流程负责人（mystx 仓库 `.github/workflows/` 维护者）
- **触发条件·时间节点**：与 ACT-01 的清单同时落地；不晚于下一次公开发布
- **验收标准（rule）**：① `python-publish.yml` 的触发条件包含 `push: tags:`，且不再包含 `release: types: [published]`；② 该文件内全部 action 引用的 ref 均为 40 位 commit SHA，不存在 `@main` / `@unstable` / `@v*` 形式的浮动引用；③ 发布 job 的依赖图中包含 ACT-01 不变量校验 job，且后者失败时发布 job 不执行；④ 发布 job 在上传前执行 `pytest`，测试失败时阻断发布
- **来源**：I-1、I-3；C1 模式步骤④；F-055、F-056、F-058、F-059、F-060、F-061

### ACT-03 历史版本坐标显式登记：谱系映射表 + 豁免清单（含到期条件）

- **描述**：生成「tag → 谱系根提交 → 是否已被取代」的**谱系映射表**，把 13 个 tag 分属 6 条互相独立谱系、其中 11 个非 HEAD 祖先这一结构显式登记；并把 12 个无变更记录条目的 tag、2 个版本序列缺号作为**不可回填豁免**逐条登记（含到期条件或「不设到期条件」的显式声明），使历史断层从「静默保留」转为「可查的显式事实」。
- **优先级**：高
- **Owner**：mystx 维护者
- **触发条件·时间节点**：与 ACT-01 同一批次交付；不晚于下一次发布
- **验收标准（rule）**：① 存在谱系映射表文件，13 个 tag 全部有行，每行含 tag 名、指向提交、谱系根提交、根提交 subject、是否 HEAD 祖先 5 列；② 非 HEAD 祖先 tag 的处置结论（已被取代 / 待确认）标注数量与 F-011 实测一致（11 个）；③ 12 个缺变更记录条目的 tag 在豁免清单中全部登记并标注「不可回填」及原因，无空缺行；④ 每条豁免均带到期条件，或带「不设到期条件」的显式声明，二者必居其一
- **来源**：I-1；C1 模式步骤①②⑤；F-008、F-009、F-011、F-072、F-089、F-090、F-091；V 阶段遗留问题 4

### ACT-04 最小可安装单元验收 job + `import mystx` 导入面解耦

- **描述**：解除 `src/mystx/__init__.py` → `tasks/__init__.py` → `tasks/docs.py` 导入链对 `invoke` 的硬依赖（改为延迟导入或 `__getattr__` 保护），使 `import mystx` 在仅有 runtime 依赖的环境中成立；并新增一个只安装 runtime 依赖集的 CI job 作为**最小可安装单元验收**，区分「硬失败依赖（invoke）」与「软失败依赖（invocations）」两级失败语义。
- **优先级**：高
- **Owner**：mystx 维护者
- **触发条件·时间节点**：下一次发布前；触发信号为任一用户按 README 执行 `pip install "mystx[docs]"` 后 `import mystx` 失败
- **验收标准（rule）**：① 在仅安装 `pyproject.toml` runtime `dependencies` 的干净环境中，`python -c "import mystx"` 退出码为 0；② `src/mystx/tasks/__init__.py` 与 `src/mystx/tasks/docs.py` 对 `invoke` 的导入改为延迟导入或置于保护之下，缺失时不抛 `ImportError`；③ CI 中存在一个只安装 runtime 依赖集并断言 `import mystx` 成功的独立 job；④ `invocations` 缺失时 browse / tree / doctest 仍为软失败降级，行为与现状一致
- **来源**：I-2；C3（不入库候选）；F-024、F-041、F-084、F-095

### ACT-05 运行时依赖契约单一真源化（`dependencies` 与 README 核心依赖段对齐）

- **描述**：以 `pyproject.toml` 为运行时依赖契约的**唯一真源**，把真实的运行时依赖写入 `[project].dependencies`，README「核心依赖」段改为派生内容或由校验脚本守护，并消除两处版本下界写法分叉（`>=1.1.4` vs `>=1.1`、`>=8.0.0` vs `>=8.0`）。当前 `dependencies = []` 而 README 声称 5 项核心依赖，同一事实存在两套口径且无人负责消除。
- **优先级**：高
- **Owner**：mystx 维护者
- **触发条件·时间节点**：与 ACT-04 同一批次（两者共同决定 runtime 依赖面），不晚于下一次发布
- **验收标准（rule）**：① `[project].dependencies` 非空，且每项都能追溯到 `src/mystx` 中的实际 import；② README「核心依赖」段的依赖名与版本下界与 `pyproject.toml` 逐字一致；③ 存在一个校验脚本比对两者，不一致时以非零码退出；④ 新发版本在 PyPI 上的 `requires_dist` 中，runtime 侧（无 extra 标记）计数大于 0
- **来源**：I-2、I-4；C2 模式（声明面单一权威源）；F-024、F-066、F-067、F-095

### ACT-06 测试与覆盖率门禁进入发布路径

- **描述**：把当前仅以本地 pre-commit hook 形式存在的 51 个测试与覆盖率下限、产物校验，合并为**发布路径上的单一关卡序列**（lint + 测试 + 覆盖率 + 产物 + 版本不变量）；补齐 `[tool.coverage]` 段与 `fail_under`，使 RTD 的 `fail_on_warning` 从「唯一高标准关卡」降为附加关卡而非唯一关卡。
- **优先级**：高
- **Owner**：mystx 维护者
- **触发条件·时间节点**：与 ACT-02 同一批次；不晚于下一次发布
- **验收标准（rule）**：① `pyproject.toml` 存在 `[tool.coverage]` 段且 `fail_under` 取值不低于 80；② 至少一个 workflow 步骤执行 `pytest --cov` 且失败时阻断；③ 覆盖率分母口径与 F-049 实测一致（51 个 test 函数）；④ 产物校验不再只判 `doc/_build/html/index.html` 是否存在，同时校验至少一个非空资源文件
- **来源**：I-3；C1 模式步骤④；F-035、F-036、F-049、F-054、F-056、F-059、F-060、F-061

### ACT-07 工具链约束与依赖声明的单一权威源（PEP 735 为真源 + 行长 / Python 目标对齐）

- **描述**：以 PEP 735 `[dependency-groups]` 为**开发侧依赖的唯一真源**，`[project.optional-dependencies]` 由其派生或对每一处差异登记理由（当前 dev 组已分叉：group 侧展开并集 42 项 vs optional 侧 21 项，双向不相等）；同时把工具链参数收敛到单一真源——pre-commit 的 flake8 `--max-line-length` 与 ruff / black 的 `line-length = 120` 对齐，black 的 `language_version` 与 `requires-python >= 3.14` 对齐，`version_file` 与 `write_to` 双写等重复声明逐项收敛。
- **优先级**：中
- **Owner**：mystx 维护者
- **触发条件·时间节点**：下一轮依赖声明调整时；触发信号为 `optional-dependencies` 或 `dependency-groups` 任一组内容发生变化
- **验收标准（rule）**：① dev 组在两侧的差异被逐项登记理由或消除，登记表中 dev 组差异条目数不超过当前实测的 23 + 3 + 2 项，且每条均写明理由；② `.pre-commit-config.yaml` 中 flake8 的 `--max-line-length` 与项目 `line-length = 120` 相等；③ pre-commit 中 black 的 `language_version` 与项目 `requires-python >= 3.14` 对齐；④ 存在一条命令可输出「重复声明清单」（`version_file` / `write_to` 双写、仓库根 `tasks.py` 与包内 `src/mystx/tasks/` 双入口、`src/mystx/tools/__init__.py` 空壳），且清单中每项均有收敛结论
- **来源**：I-3、I-5；C2 模式；F-021、F-025、F-026、F-027、F-028、F-063、F-064、F-085、F-086、F-087

### ACT-08 文档-实现一致性检查 job + CHANGELOG 仪式门禁

- **描述**：新增一个 CI 检查 job，校验 README / `CONTRIBUTING.md` 中出现的依赖名、版本下界、目录路径在仓库中真实存在（当前 README 的 `locale_dirs = ['../locales/']` 指向全仓不存在的目录，`CONTRIBUTING.md` 六关键词命中数为 0）；并恢复 CHANGELOG 仪式——保留 `Unreleased` 段、每个新 tag 必须有对应条目。
- **优先级**：中
- **Owner**：mystx 维护者
- **触发条件·时间节点**：与 ACT-01 同一批次（不变量 I-3「变更记录存在性」依赖本项提供校验器）；下一次发布前
- **验收标准（rule）**：① 存在一个 CI job，对 README 中出现的每个依赖名与版本下界、每个目录路径做存在性判定，缺失时以非零码退出；② `CHANGELOG.md` 含 `Unreleased` 段；③ 新增 tag 时由 CI 校验该 tag 在 `CHANGELOG.md` 中有对应条目，缺失时阻断；④ `CONTRIBUTING.md` 至少含 pytest、ruff、invoke 三条可直接复制执行的上手命令
- **来源**：I-4；C1 模式步骤⑥与不变量 I-3；F-069、F-071、F-072、F-082、F-091

### ACT-09 `doc/_ext/` 第三方实现的归属与许可登记

- **描述**：对 `doc/_ext/` 下内嵌的第三方实现（`sphinx_docx/`、`gallery_directive.py`、`live-preview/` 等）建立**逐目录归属登记**：上游来源、许可、修改点；并明确仓库根唯一 Apache-2.0 `LICENSE` 的覆盖边界。该实现会经 RTD 的 htmlzip / epub / pdf 进入对外产物，当前 `sphinx_docx/writer.py` 901 非空行且无许可证头与上游归属声明。
- **优先级**：中
- **Owner**：mystx 维护者
- **触发条件·时间节点**：下一轮对外构建发布前（RTD 产物格式含 htmlzip / epub / pdf）
- **验收标准（rubric）**：维度 4 项各 1 ~ 5 分并取均值，均值 ≥ 4 且单项不低于 3——① 归属登记完整性（`doc/_ext/` 下每个第三方实现目录均有登记条目）；② 许可标识准确性（登记的许可与上游实际许可一致，且与仓库根 `LICENSE` 的关系有显式说明）；③ 可追溯性（每条登记可指回上游仓库与具体版本 / commit）；④ 阻断效力（登记缺失时对外构建流程可被阻断）。锚点：1 = 无登记；3 = 有登记但不可追溯或不阻断；5 = 四项齐备
- **来源**：I-4；D-5；F-060、F-075、F-076、F-078、F-080；V 阶段遗留问题 6

### ACT-10 R→I 转译的结论强度守门（前置检查）

- **描述**：在七概念方法的 R→I 转译环节加入一道**前置检查**：每条洞察的根因表述须标注所依据的事实编号及其证据强度，当表述强度高于所引事实的可回溯强度时，须降级表述或显式标注为竞争假设。V 阶段抽验 18 条事实发现「事实准确、推论过强」的系统性模式（3 条需降级：F-011、F-086、F-041），问题不在取证诚实度而在转译环节缺少守门动作。
- **优先级**：中
- **Owner**：复盘方法论维护者（七概念 R→I 环节负责人），非 mystx 维护者
- **触发条件·时间节点**：下一次使用七概念方法论的复盘任务启动时即启用，在 R 阶段完成、I 阶段开始之前执行
- **验收标准（rule）**：① 复盘规范中在 I 阶段入口定义「结论强度等级」与事实证据强度三档（可回溯 / 需降级 / 不可回溯）的对应关系；② I 阶段每条洞察的根因句旁标注所引 F 编号及其证据强度档位；③ 存在一次可核验判定：当某条洞察的根因强度高于其全部所引事实的最高强度时，该条被标注为「需降级」并给出降级后的表述；④ 本报告自身的 I-1（谱系结构）与 I-2（导入失败路径）两条洞察完成一次回溯校准并留下标注痕迹
- **来源**：V-1、V-2、V-4、V-6、V-11 与 V 阶段 §4.3 系统性结论；F-011、F-041、F-086
