# 「双轨演进制」模式 L1→L2 升级验证计划

> 本计划为 [insight-extraction.md](insight-extraction.md) 第二节萃取的「双轨演进制」模式（当前成熟度 **L1，单案例待验证**）提供从 L1 升级至 L2 的完整验证方案：验证目标 → 验证命题 → 验证方法与判定标准 → 候选验证场景 → 执行步骤与时间线 → 检验清单 → 反模式验证 → 升级判定 DoD → 责任与追踪 → 失败与降级路径。

---

## 0. 模式现状概述

| 项 | 内容 |
|----|------|
| 模式名称 | **双轨演进制** |
| 一句话定义 | 依赖生态尚不成熟时，采用"内部化实现先行、外部依赖后置"的双轨策略，按依赖成熟度渐进切换轨道 |
| 当前成熟度 | **L1**（`validation_count = 1`，仅 xuanspace 单案例） |
| 来源案例 | xuanspace monorepo：scikit-build-core 构建链统一先行 → COW/Backward 机制内部实现 → vendor 子模块后置 |
| 模式文档位置 | [insight-extraction.md#第二节](insight-extraction.md) |
| 升级目标 | **L2**（`validation_count ≥ 2`，模式稳定） |

### 模式核心要素速查（验证时的对照基准）

- **触发边界**：monorepo 初始化与主链路打通阶段；外部依赖有可用性/稳定性风险；主链路关键路径依赖外部组件；内部具备替代实现能力。不适用于：已进入稳态迭代、外部依赖稳定可依赖的成熟仓库。
- **核心做法（5 步）**：①盘点外部依赖成熟度，标记高风险轨道；②对高风险依赖先铺设内部内聚实现轨道；③契约（测试）先行锁定轨道接口；④渐进切换（外部依赖就绪一项、切换一项，以全量测试通过为准入）；⑤记录切换台账。
- **反模式（4 个）**：外部依赖先行 / 双轨并行永不合轨 / 切换无验收 / 轨道未记录。
- **检验标准（3 条）**：①主链路在外部依赖缺失状态持续演进（可构建、可测试）；②每一轨道切换有测试通过证据与台账记录；③仓库骨架（构建后端、目录结构、多包管理）先行统一，再叠功能开发。

## 1. 验证目标与验证命题

### 1.1 验证目标

| 目标 | 说明 |
|------|------|
| G-主 | 通过 ≥1 个新的独立案例验证，使 `validation_count` 达到 ≥2，升级 L2 |
| G-次1 | 至少 1 次验证落在**跨领域场景**（非 Python monorepo 领域），确认模式抽象层级可迁移 |
| G-次2 | 校准模式四项要素（触发边界 / 核心步骤 / 反模式 / 检验标准），发现偏差即修订 |
| G-次3 | 为 L2 升级后的模式文档补充"实际案例"章节与跨领域验证数据 |

### 1.2 核心命题（可证伪假设）

> 每次验证必须针对以下命题逐条给出"成立 / 部分成立 / 不成立"判定，防止笼统的"模式有效"结论。

| 编号 | 命题 | 验证锚点 |
|------|------|---------|
| P1 | 外部依赖不成熟时，内部实现先行比强推外部依赖更快打通主链路 | 对比：主链路打通耗时；阻塞天数 |
| P2 | 外部依赖就绪后逐项切换（非批量切换）能避免行为漂移 | 切换后回归测试通过率；行为差异数 |
| P3 | 契约（测试）先行锁定接口，可降低切换成本 | 切换时接口改动量；重写测试数 |
| P4 | 切换以全量测试通过为准入条件可以保证切换安全 | 切换后故障数；回滚次数 |
| P5 | 五步做法可按序直接执行，无需依赖原案例特有条件 | 执行记录完整性；卡点数量 |

## 2. 验证方法与判定标准

### 2.1 什么是"一次成功验证"

在候选场景中**完整应用五步核心做法**，且满足：

1. 主链路在外部依赖缺失状态下可构建、可运行、可测试（模式检验标准①）
2. 至少完成 1 项"外部依赖就绪 → 切换"闭环，具备测试全量通过证据与台账记录（模式检验标准②）
3. 产出**案例报告**：场景描述 → 前置条件核对 → 五步执行记录 → 反模式对照 → 五条命题判定 → 检验标准核对 → 结论

### 2.2 验证结果判定

| 结果 | 条件 | 处置 |
|------|------|------|
| ✅ 通过 | 命题 P1-P5 全部成立（或仅 P5 部分成立但可解释） | `validation_count +1`，案例写入模式"实际案例"章节 |
| ⚠️ 部分通过 | 核心做法 ≤3 步成立，其余有偏差 | 记录差异，修订模式边界/步骤，计入验证但标记"待复核" |
| ❌ 不成立 | 命题 P1/P4 任一不成立（模式失效） | 记录反例，退回 L1 并修订触发条件；连续 2 次失败则降级为候选洞察 |
| 🚫 场景不适用 | 案例未命中"适用于"边界 | 不计入验证，更换场景 |

## 3. 候选验证场景（按优先级）

| 编号 | 候选场景 | 场景类型 | 优先级 | 验证要点 | 前置条件 |
|------|---------|---------|:------:|---------|---------|
| DTP-V1 | **多包 Python monorepo 新子包初始化**（如 xuanspace 内新立 libs/* 子包，或同类多包仓库） | 同领域（相邻项目） | 🔴 高 | 复制"构建链统一先行 + 子模块后置"路径是否成立 | 确定目标子包/仓库；外部依赖存在未就绪项 |
| DTP-V2 | **前端 monorepo 组件库兜底**（组件库 + 业务包；图标库/UI 基础库未发版时先用内部组件，发版后按接口契约切换） | 跨领域 | 🔴 高 | 内部组件兜底 + 契约测试切换；检验 P2/P3 | 目标前端项目处于初始化阶段；候选外部 UI 库未稳定 |
| DTP-V3 | **微服务上游 SDK 适配层**（核心服务依赖的上游 SDK 未稳定时，先以内部桩/适配层打通链路，上游稳定后替换正式 SDK） | 跨领域 | 🟡 中 | 桩/适配层 + 契约测试切换；检验 P1/P4 | 目标服务依赖的上游 SDK 存在版本波动 |
| DTP-V4 | **历史仓库回溯验证**（选取已有仓库 git 历史，分析其开发路径是否吻合"内部先行→外部后置"结构） | 回溯分析 | 🟡 中 | 低成本校验模式存在性；作为 V1/V2 的补充证据 | 目标仓库有完整 git 历史且存在外部依赖后置证据 |
| DTP-V5 | **反模式故障注入**（在受控实验/沙箱仓库中故意违反各反模式，验证负面结果复现） | 故障注入 | 🟢 低 | 验证 4 个反模式的准确性（见 §6） | 构造沙箱仓库；时间预算允许 |

> **优先级规则**：优先完成 DTP-V2（跨领域，对升级 L2 的价值最高）；DTP-V1 作为同领域复验；DTP-V4 可并行低成本开展；DTP-V5 在其余验证完成后视需要执行。

## 4. 执行步骤与时间线

```
Phase 0  准备           建立验证台账模板；选定 DTP-V2 目标项目；登记 V1/V4 候选
Phase 1  首验证         执行 DTP-V2（跨领域，目标升级 L2 的关键证据）→ 产出案例报告
Phase 2  次验证         执行 DTP-V4 回溯验证 +（可选）DTP-V1 复验 → 产出报告
Phase 3  反模式校准     （可选）DTP-V5 故障注入，核验反模式清单
Phase 4  L2 升级评审    汇总案例 → 修订模式四要素 → 模式文档升级 L2 → 索引与交叉引用更新
```

### 各阶段交付物与完成标准

| 阶段 | 交付物 | 完成标准 |
|------|--------|---------|
| Phase 0 | 验证台账模板（含 §6 检验清单 + §1.2 命题判定表） | 模板可复制到任何新案例直接使用 |
| Phase 1 | DTP-V2 案例报告 | 五步执行记录完整；五条命题逐条判定；检验标准三项核对 |
| Phase 2 | DTP-V4（及 DTP-V1）案例报告 | 回溯证据链完整；结论可复核 |
| Phase 3 | 反模式核验记录（若执行） | 每个反模式给出"复现/未复现 + 证据" |
| Phase 4 | 升级后的模式文档 + 索引更新 + 链接验证 | 见 §7 升级判定 DoD |

## 5. 检验清单（复制即用）

> 以下清单可直接复制到任务追踪系统。每个案例验证时逐项勾选。

| 序号 | 检验项 | 验证方法 | 通过标准 | 阶段 | 状态 |
|-----|--------|---------|---------|------|:----:|
| C1 | 适用边界核对 | 案例场景与模式触发边界比对 | 命中"适用于"条件，未落入"不适用于" | 验证前 | ⬜ |
| C2 | 前置条件核对 | 检查外部依赖风险 + 内部替代能力 | 外部依赖存在风险且内部具备替代实现能力 | 验证前 | ⬜ |
| C3 | 五步做法可执行 | 按 5 步逐步执行并记录 | 5 步均可直接执行，无卡点（或卡点已记录） | 验证中 | ⬜ |
| C4 | 主链路独立性（检验标准①） | 在外部依赖缺失状态尝试构建+运行+测试 | 构建成功、测试通过 | 验证中 | ⬜ |
| C5 | 切换有验收（检验标准②） | 检查切换时是否执行全量测试 | 全量测试通过后方切换，有证据 | 验证中 | ⬜ |
| C6 | 切换有台账（检验标准②） | 检查台账记录 | 每项依赖记录初始化/切换日期与验收依据 | 验证中 | ⬜ |
| C7 | 骨架先行（检验标准③） | 检查构建后端/目录结构/多包管理统一时机 | 骨架统一先于功能开发 | 验证中 | ⬜ |
| C8 | 反模式对照 | 按 §6 逐一对照 | 未触发任何反模式（或触发后记录为新反模式） | 验证中 | ⬜ |
| C9 | 命题判定完整 | 按 §1.2 表逐条判定 | P1-P5 均有成立/部分成立/不成立的明确判定 | 验证后 | ⬜ |
| C10 | 案例报告归档 | 按 §2.1 产出案例报告 | 报告完整、结论可复核 | 验证后 | ⬜ |

## 6. 反模式验证

对 4 个反模式逐一核验其"负面结果"是否可复现，确认反模式清单的准确性：

| 反模式 | 预期负面结果 | 验证方法 | 判定 |
|--------|------------|---------|:----:|
| AP1 外部依赖先行 | 主链路阻塞、空窗期延长 | 回溯 DTP-V4 历史案例中"强推未就绪依赖"的提交段，观察阻塞时长 | ⬜ |
| AP2 双轨并行永不合轨 | 长期维护两套轨道、维护成本翻倍 | 检查是否存在"内部实现完成但未切换"的滞留轨道 | ⬜ |
| AP3 切换无验收 | 引入行为漂移、回归测试失败 | 回溯"跳过全量测试直接切换"的事件，观察后续故障 | ⬜ |
| AP4 轨道未记录 | 事后无法追溯"为什么用内部实现" | 检查台账缺失导致的追溯困难案例 | ⬜ |

> 若 AP-验证中发现反模式失准（如负面结果未复现），需修订反模式清单并在 L2 升级评审中说明。

## 7. 升级判定 DoD（L2 升级完成定义）

- [ ] `validation_count ≥ 2`（原 xuanspace 案例 + 至少 1 次新验证通过）
- [ ] 至少 **1 次跨领域验证成功**（DTP-V2 前端 monorepo 或 DTP-V3 微服务场景）
- [ ] 模式四要素（触发边界 / 核心步骤 / 反模式 / 检验标准）经第 2 案例校验，必要处已修订
- [ ] 模式文档升级 L2：`maturity: L1 → L2`、`validation_count +1`、新增"实际案例"章节
- [ ] 与既有双轨类模式完成边界区分（见 §7.1）
- [ ] 模式目录索引更新 + `python .agents/scripts/check-links.py --path <模式目录>` 链接验证通过

### 7.1 与既有"双轨"类模式的边界区分（避免模式库重复）

| 既有模式 | 定位 | 与「双轨演进制」的边界 |
|---------|------|----------------------|
| [legacy-integration-dual-track.md](../../../patterns/architecture-patterns/legacy-integration-dual-track.md) | 存量系统接入：REST 快速接入 + MCP 标准协议优化，两阶段"先接入再优化" | 关注**接入方式的双轨并存**；双轨演进制关注**依赖成熟度的渐进切换**。前者重接入、后者重演进 |
| [dual-track-sdk-strategy-framework.md](../../../patterns/analysis-cards/dual-track-sdk-strategy-framework.md) | 平台 SDK 策略 4 级成熟度识别框架（分析工具） | 关注**平台生态战略观察**（分析卡片）；双轨演进制是**工程实践方法**（执行模式） |

> 升级入库时应在前两者的"相关模式"字段与「双轨演进制」的"相关模式"字段互加交叉引用，并各自补充一句边界说明。

## 9. 失败与降级路径

| 情形 | 处置 |
|------|------|
| 第 1 次验证判定"场景不适用" | 不计入验证，更换候选场景（V1/V3）重试 |
| 第 1 次验证判定"命题不成立" | 分析是场景问题还是模式错误：场景问题则换场景；模式错误则修订触发边界后重试 |
| **连续 2 次验证失败** | 模式标记"高失效风险"，**降级为候选洞察**（不升级）），失败案例归档作为反模式素材 |
| 跨领域验证（V2/V3）均无法开展 | 以 2 次同领域验证（V1+V4）升级 L2，但模式文档显著标注"跨领域待验证" |
| 反模式核验发现失准 | 修订反模式清单，更新 insight-extraction.md 第二节与模式文档对应内容 |
