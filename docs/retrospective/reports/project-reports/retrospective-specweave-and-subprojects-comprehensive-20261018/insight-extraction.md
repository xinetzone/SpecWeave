# 洞察萃取：SpecWeave 与其第一方子项目全面复盘

> 5 条洞察，四元组（现象 / 根因 5-Whys / 影响 / 建议）齐全；根因表述为「与现有事实一致的一种解释」，并附竞争假设与证据缺口。
> 深度自评（1~5）：I-1 = 4、I-2 = 4、I-3 = 4、I-4 = 4、I-5 = 4。

## I-1 产出结构由「治理规范仓库」位移为「治理 + 应用组合 + 知识工厂」三面并行

- **现象**：apps 应用由基线 4 个增至采集时点路由表 40 行登记（F-043、F-031）；知识束 1083 个、束内 md 11794 篇（F-062）；窗口内 bundle/知识包/OKF 主题提交 469 条（F-059）；同期治理类提交仍最高频（retrospective 557 条，F-010）。
- **根因（5-Whys）**：① 可见增长集中于 apps 与知识束，因这两类新增动作已有可复制装配形态（应用自带 `AGENTS.md`/`.agents/rules`/`docs`，知识束自带 `index.md`/`concepts`）→ ② 装配形态可复制，因主权区已存在对应规范与模板（templates 109、protocols 18，F-023）→ ③ 规范先于产出规模化，因基线期产出对象为单一规范容器（docs 类占 53.3%，F-006）→ ④ 规范体系 27 天成形的条件是产出对象无外部交付约束 → ⑤ 后一阶段转向外部交付物，对应窗口内平台化外向动作（F-056~F-058、F-060、F-064）。
- **影响**：治理面提交计数仍最高，但新增资产的消费面已转向 apps 与知识束；复核重心只放 `.agents/` 会遗漏主要增长面。
- **建议**：新增应用与知识束执行「装配清单」（路由表登记 + 五要素 + 索引登记）；复盘范围默认包含 apps 与 projects/。
- **竞争假设**：apps 与知识束增长也可能仅反映快照采样差异。**证据缺口**：未取得 apps 逐月新增时间线。

## I-2 迁移仍是最高风险事件类型，成本以「事后集中修复」形式延后出现

- **现象**：窗口内主题含「迁移」提交 ≥8 条，其中 3 条为迁移后断链修复（2026-09-28 修复 50 处、2026-09-30 模式库迁移遗留、2026-10-17 旧引用失效），见 F-061、F-052、F-053、F-051；`.agents/docs/` 于 2026-08-31 迁移至根 `docs/`（F-035），采集时点旧路径不存在（F-034）。
- **根因（5-Whys）**：① 集中断链修复出现，因单次迁移涉及多类引用方（相对链接 / `x-toml-ref` / 硬编码路径）→ ② 多类引用方难以当次穷尽，因其分布在主权区、apps、docs 与子模块 → ③ 历史归档也参与扫描，因归档仍被 toctree 与检索路径覆盖 → ④ 归档需保持可达，因仓库以「索引可达」为正例（报告 2269 篇、模式 952 篇，F-026）→ ⑤ 可达性依赖路径字符串，而该字符串在迁移中整体改写。
- **影响**：断链以跨天跨批次修复提交出现（F-052 → F-053 → F-061），单次迁移的真实成本高于当期提交呈现量。
- **建议**：迁移类变更把「三类引用方扫描 + 断链门禁」与迁移同批交付，可直接挂载 `migration-cascade-checklist-template` 与 `cascade-update-prerequisite-check` 模式。
- **竞争假设**：断链也可能由新增内容引入。**证据缺口**：未逐条回证 50 处断链的引入提交。

## I-3 跨期对比存在口径风险：结构治理改写计数边界，表观差值方向不可直接采信

- **现象**：知识库 md 计数 836（口径 `.agents/docs/knowledge`）→ 500（口径 `docs/knowledge`），差 -336（F-044）；Skill 门面 18 → 172（F-041），期间发生技能目录统一（F-051）；模式 493 → 952、报告 1317 → 2269（F-038、F-039）；知识束本仓实测 1083（F-062）与应用自述 1307（F-063）并存。
- **根因（5-Whys）**：① 表观差值方向不一致，因两次统计的计数边界（目录范围、排除规则）期间发生变化 → ② 边界变化对应两次结构治理（文档中心迁移、技能目录统一，F-035、F-051）→ ③ 统计脚本未随之更新，因统计命令由报告作者临时书写 → ④ 采用临时命令，因复盘模板未把「口径声明」列为必填项 → ⑤ 模板缺此项，因模板成形于结构稳定期。
- **影响**：直接引用表观差值可能得到「知识库萎缩」「技能暴涨」等方向性结论，而两者均可能为口径变化产物（F-044、F-041）。
- **建议**：跨期报告每个对比指标标注「口径一致 / 口径变更 / 不可比」；口径变更指标只报存量与边界，不报方向性增减。
- **竞争假设**：知识库计数下降也可能反映真实内容重组（大文件合并为原子文件）。**证据缺口**：未以同一脚本重跑两次口径。

## I-4 单点维护下的「日均提交下降」不构成产能下降证据，需双轴度量

- **现象**：日均提交由 55.4（基线）降至 37.1（全量）（F-037）；窗口类型分布 feat 414、chore 463（F-009）；前两位身份合计占 96.5%（F-012），归属未核实（F-013）；贡献者身份数 5 → 7（F-045）。
- **根因（5-Whys）**：① 提交频率下降，因提交结构从「小步高频补规范」转为「成批交付应用/知识束」→ ② 转为成批交付，因窗口产出对象变为应用组合与知识束（F-059、F-031）→ ③ 成批交付对应更低频率，因单次提交承载产出量上升（如 2026-10-18 单日含技能、规格归档与子模块推进，F-056~F-058）→ ④ 该结构可维持，因装配动作已模板化（templates 109，F-023）→ ⑤ 度量未随之调整，因既有度量表述（提交数/日均）在基线报告已固定。
- **影响**：以提交数单轴衡量产能，会把「产出密度上升」读作「节奏放缓」。
- **建议**：改用双轴度量——提交计数（节奏）+ 产出物计数（应用数、知识束数、报告数、模式数）。
- **竞争假设**：日均下降也可能反映可用工时下降。**证据缺口**：无工时或会话时长记录佐证。

## I-5 门禁体系向「守恒类破坏」扩展

- **现象**：`ci-quality-gates.yml` 含 `[1/16]`~`[16/16]` 与新增 `[1.5/16] Submodule pointer consistency (S1 drift guard)`（F-033）；基线记载 16 步且无该项；采集时点子模块指针无漂移（F-017）。
- **根因（5-Whys）**：① 新增该守卫，因存在不修改子模块内部文件却改写 gitlink 指针的变更类型 → ② 该类变更难被发现，因其在子模块工作树内不可见 → ③ 需门禁而非人工检查，因指针推进在窗口内高频（206 条，F-048）→ ④ 指针推进高频，因子模块在主仓外独立演进（F-021）→ ⑤ 独立演进需要守恒校验，因主仓对子模块内容的可见性依赖指针值。
- **影响**：该类「沉默破坏」在推送前被拦截，其同类清单此前未单列。
- **建议**：把「生成物未提交」「子模块指针漂移」「元数据与正文双轨不一致」归入统一的「守恒类门禁」清单并按类登记。
- **竞争假设**：该守卫也可能因其他区域同类故障而添加。**证据缺口**：未取得该守卫的引入提交说明。
