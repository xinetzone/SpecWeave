# SpecWeave 核心痛点诊断：哪些维护工作该交给 Agent

> 目标不是再写一套规范，而是回答一个问题：**从现状证据看，最该被 agent 接管的维护工作是哪几块，哪些必须留给人。**
> 本报告所有量化结论均来自 2026-11-09 在本仓库的实测命令，命令与原始结果见「附录 A · 取证命令」。

## 结论速览

| 排序 | 痛点 | 建议归属 | 判断依据（频次/耗时/后果/机械性） |
|---|---|---|---|
| P0 | 门禁发现问题后的「修复—复验」闭环无人执行 | **Agent 接管（高）** | 每次提交频发；单轮 20–40 分钟；阻断交付；修复动作 80% 机械 |
| P0 | Skill/报告/能力注册的「多处登记面」靠人同步 | **Agent 接管（高）** | 每次新增资产必触发；遗漏后果隐蔽（计数漂移、不可达）；纯机械比对 |
| P1 | 双入口规范文档（`AGENTS.md` / `CLAUDE.md`）同源不同步 | **Agent 巡检 + 人定策** | 低频但后果为"规则自相矛盾"；已实证 1 处失效路径 |
| P1 | 每次会话的启动协议与上下文重建 | **Agent 接管（高）** | 每任务一次；5–10 分钟；重建偏差导致返工；可固化为简报 |
| P1 | 报告/文档落位与索引更新 | **Agent 建议 + 人确认** | 每次产出物一次；归位错误触发断链；分类判断含语义 |
| P1 | 子模块指针与多层提交推送 | **Agent 预检 + 人授权** | 24 个子模块；现存 1 处漂移；误推后果高 |
| P2 | 并行会话对共享工作树/索引的争用 | **Agent 协调 + 人裁决** | 高频于多会话期；冲突返工；语义冲突需人判断 |
| P2 | 元治理资产自身的膨胀（技能/报告） | **人决策（Agent 只出账）** | 224 技能、486 报告目录；取舍属价值判断 |

**一句话结论**：本仓库缺的不是规范，而是一个「执行者」——把已有的检查脚本串成「发现 → 分级修复 → 复验 → 记账」的闭环。Agent 应优先接管**可机械判定、可自动复验**的维护面（链接、登记、索引、指针、启动简报），把**口径、分类法、授权、内容敏感度**留给人。

## I · 洞察（现象 + 根因 + 影响 + 建议）

### I1 门禁只覆盖「发现问题」，未覆盖「修复与复验」

- **现象**：116 个断链 + 35 个目录链接警告集中在单一子树，且仓库自带 24 个 `fix/add/migrate/repair` 脚本，检查与修复分属两套入口，需人手动串接并重跑。
- **根因**：执行机制呈三态割裂——规范是文本（人读）、检查是脚本（只报错）、修复是脚本（需人记得调用）。三者之间没有状态传递，也没有"修完必须复验"的强制环节。
- **影响**：门禁从"质量保障"退化为"交付前的心理负担"；断链存量持续累积（当前 116），每次改动都在旧债上叠加。
- **建议**：把 `check-links` / `check-report-categorization` / `check-submodule-pointer` 统一纳入一个「修复闭环执行器」，按错误类型分级：机械类自动修、语义类给建议、跨模块移动只出提案。

### I2 登记面是「一处事实、四处抄写」

- **现象**：224 个 Skill 需要在 `skills/README.md` 分类计数、`capability-registry/02-skills.md` 表行、`skills/CHANGELOG.md` 版本条目、`.meta/toml/**/SKILL.toml` 镜像四处登记；报告同理（分类目录 + README 索引 + toctree + TOML 镜像）。仓库已为此专门沉淀 35 个治理语义 Skill。
- **根因**：用"多处声明"代替"单一事实源"，一致性只能靠人逐处同步；缺少从目录实况反推登记面的生成器。
- **影响**：计数漂移与不可达文档成为高频历史问题；发现问题时往往已过若干次提交，定位成本高于修复成本。
- **建议**：建立"目录实况 → 登记面"的单向生成/校验器，把四处登记降级为一次生成 + 一次门禁；人只负责分类命名这类判断。

### I3 双入口规范的「影子副本」会滞后

- **现象**：`AGENTS.md`（143 行）与 `CLAUDE.md`（92 行）描述同一套四大区域与开发规范；`CLAUDE.md` 内部一处已废止路径与另一处废止声明并存。
- **根因**：同一事实存在两处独立维护的副本，且两者都没有被任何门禁做"交叉一致性"检查。
- **影响**：不同 agent 入口读到冲突规则，按哪个执行取决于先读哪份；错误路径导致规范读取失败，进而绕过方法论。
- **建议**：明确单一权威（`AGENTS.md`），其余入口只保留路由指针；增加"入口文档路径可达性"门禁。

### I4 启动协议的成本落在每一次任务上

- **现象**：每次任务需完成读 `AGENTS.md` → 路由 → 敏感度预检 → 6 项自检 → 选 Skill；对应 1,536 个 `.agents` 文档与 834 个规格目录。
- **根因**：路由知识以自然语言规则存在，未编译成可执行的分诊表；每次执行都是一次"人工重新推导"。
- **影响**：启动耗时与偏差直接转成返工（格式/路径/结构三类错误在仓库复盘中反复出现）。
- **建议**：做一个"启动简报器"：输入任务描述，输出应读文件清单、敏感度级别、可用 Skill 与产出路径，并附带校验结果。

### I5 落位决策依赖记忆而非查证

- **现象**：`docs/` 4,235 个文档、486 个报告目录、20+ 个报告分类；`check-report-categorization` 当前有 38 项未归类错误。
- **根因**：分类法写在 README 文本里，落盘时靠人回忆"落盘前三查"。
- **影响**：错位产出触发后续断链与索引返工，形成 I1 的输入。
- **建议**：把分类法变成可查询的落位建议器（输入标题/主题 → 输出候选目录 + 现有同类样本），人对最终位置签字。

### I6 子模块与多层提交是「顺序敏感」的高风险操作

- **现象**：24 个子模块，指针检查当前 1 处漂移；仓库已有多个专门 Skill 处理共享分支、合并推送、子模块指针校验。
- **根因**：提交顺序（子模块 → 父仓 gitlink → 推送）与状态校验没有固化为一条可执行流水线，靠 Skill 文档提示人按序执行。
- **影响**：顺序错误造成远端指针不指、CI 拉不到代码等隐蔽故障。
- **建议**：agent 承担"预检 + 编排 + 复验"，人只保留推送授权与冲突语义裁决。

### I7 元治理资产自身在膨胀

- **现象**：224 个 Skill 里 35 个用于修治理问题；486 个报告目录；近 90 天 508 次提交触及 `.agents/`。
- **根因**：治理问题的解法偏向"再写一条规范/再建一个 Skill"，而每条新规范又增加下一次启动与同步的负担。
- **影响**：维护成本增速高于被治理对象的增速，形成"规范越全、执行越难"的反直觉现象。
- **建议**：设"资产预算"与"退役机制"，由人决定；agent 只负责出账（哪些 Skill 90 天未被触发、哪些规则无门禁覆盖）。

## F · 第一性原理：Agent 该接管什么

回到本质，维护工作只有三种形态：

1. **判定**：给定规则与事实，输出"对不对"（可机械、可复验）。
2. **执行**：给定判定结果，改变仓库状态（可编排、可回滚）。
3. **取舍**：在冲突价值间做选择（不可机械化，需责任主体）。

由此得到接管边界：

| 形态 | 典型工作 | 归属 |
|---|---|---|
| 判定 | 断链、登记计数、指针一致、路径可达、索引可达、frontmatter 完整 | **Agent** |
| 执行 | 批量改链、生成登记行、同步 toctree、修正 gitlink 记录、出简报 | **Agent（需可回滚与台账）** |
| 取舍 | 内容敏感度、分类法调整、许可/合规口径、破坏性操作授权、对外发布 | **人** |

**推论**：Agent 系统的第一版不应是"更强的规范阅读器"，而应是"判定 + 执行"两层的闭环执行器；规范层的增量应暂停，直到执行器把存量债务清到可控水位。

## V · 对抗审查（四视角）

| 视角 | 攻击 | 回应 / 收敛条件 |
|---|---|---|
| 魔鬼代言人 | 自动修链会把链接改到"看起来存在但语义错误"的目标，批量制造错误 | 分级：确定性目标（同文件重命名、锚点缺失）自动修；需推断目标语义的只出建议并附候选，人工确认后执行 |
| 新人视角 | 自动化后人对仓库结构的认知进一步退化，规范腐化更隐蔽 | 每次自动变更输出可读台账 + 周度抽样审计；台账进版本控制，可回溯 |
| 老板视角 | 投入产出不明，可能只是把人工换成调试 agent 的时间 | 先做单点闭环（链接）验证净收益：以"门禁从红到绿的耗时"和"人工介入次数"为唯一验收指标，不达标不扩展 |
| 未来视角 | 即使全自动化，4235 文档 / 486 报告的熵增仍会压垮检索与审查 | 自动化必须与"产出预算 + 归档退役"同步；后者是人的决策，agent 只提供数据 |

**审查结论**：方向成立，但需三条硬约束——①自动修复必须可回滚且留台账；②先单点验证再横向扩展；③自动化不与资产膨胀解耦就只是延迟问题。

## C · 原子行动项

| ID | 行动 | 归属 | 验收标准 |
|---|---|---|---|
| A1 | 链接修复闭环执行器：`check-links` 输出 → 分级 → 修复 → 复验 → 台账 | Agent | `docs/retrospective` 断链从 116 降到 0；目录链接警告从 35 降到 0；全程 1 次人工确认以内 |
| A2 | 登记面一致性执行器：目录实况 → 四处登记生成/校验 | Agent | 224 个 Skill 的四处登记可由一条命令校验并给出可执行补丁；连续两次运行零差异 |
| A3 | 启动简报器：任务描述 → 必读清单 + 敏感度 + Skill + 产出路径 | Agent | 对 10 个历史任务回放，路由结果与人工判定一致率 ≥ 90% |
| A4 | 落位建议器：标题/主题 → 候选目录 + 同类样本 + 需更新的索引 | Agent 建议 / 人确认 | 38 项未归类报告全部归位，且 `check-report-categorization` 归零 |
| A5 | 子模块提交编排器：预检 → 顺序提交 → gitlink 校验 → 推送前门 | Agent 执行 / 人授权 | 指针漂移在提交前被拦截；演练中 24 个子模块零误推 |
| A6 | 治理资产台账：Skill 触发频次、无门禁规则、90 天未用资产 | Agent 出账 / 人决策 | 月度可产出退役候选清单，且每条附使用证据 |
| A7 | 明确不接管清单并写入规则：敏感度判定、分类法变更、合规口径、破坏性授权、对外发布 | 人 | 规则文件落地，且执行器中存在显式人工闸门 |

**建议实施顺序**：A1 → A2 → A3 →（A4/A5 并行）→ A6。理由：A1/A2 存量债务最大且判定最机械，能最快证明"agent 减少人工"这一核心假设。

## 哪些必须留给人

| 事项 | 理由 |
|---|---|
| 内容敏感度判定（公开/私域） | 判定错会导致私域内容外泄，属不可逆风险，且"就高不就低"本质是价值权衡 |
| 分类法与目录结构调整 | 影响所有历史链接与读者预期，需承担长期一致性责任 |
| 许可、合规、对外口径 | 涉及法律责任，agent 只能提供事实与候选 |
| 破坏性 git 操作与远端推送授权 | 不可回滚，需明确责任主体 |
| 对外发布与公告 | 品牌与关系风险 |
| 资产退役决策 | 涉及"哪些知识还有价值"的判断，无法由频次数据单独决定 |

## 已知例外（登记口径优先于链接可达）

| 项 | 内容 |
|---|---|
| 涉及技能 | `alipay-aipay` |
| 已入库的登记面 | `.agents/skills/README.md`、`.agents/capability-registry/02-skills.md`、`.agents/skills/CHANGELOG.md`、`.meta/toml/.agents/skills/alipay-aipay/SKILL.toml` |
| 未入库的正文 | `.agents/skills/alipay-aipay/`（含 `SKILL.md`），由 [.gitignore](../../../../.gitignore) 第 39 行声明为本地开发目录 |
| 可观测后果 | 远端仓库中 `alipay-aipay/SKILL.md` 的链接不可达（404），本地检查不会复现 |

**这是刻意保留的例外，不是登记错误。** 保留登记的理由是维持「磁盘有原生技能 → 四处登记面有对应行」的口径统一：若为单个技能开洞，判定器的 `unregistered` 与分类计数核对就会长期挂一项假债，把真实漂移淹没掉。

约束：

1. **不要以「链接不可达」为由删除该登记行**，也不要顺手把该技能从 `.gitignore` 挪进来以消除 404。
2. 若要真正消除死链，须先决定该技能正文是否改为入库，再同步调整登记面与忽略规则；两件事分开授权、分开提交。

