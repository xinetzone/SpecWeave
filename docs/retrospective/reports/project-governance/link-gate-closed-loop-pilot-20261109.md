# 链接门禁「从红到绿」闭环单点验证：docs/retrospective 试点

> 本报告验证的不是「数字能否清零」，而是**闭环本身能否成立**：同一口径能不能复跑、修复能不能自动落地、复验能不能证伪、人工介入能不能计数、缺口能不能归因到「脚本 / 判定 / 编排」。
> 全部数字来自 2026-11-09 在本仓库的实测；复跑命令见「附录 A」，临时脚本说明见「附录 B」。

## 结论速览

| 问题 | 结论 |
|---|---|
| 这条链现在能一次跑完吗？ | **不能。** 检查与复验可全自动且稳定（14–17s）；**修复环节不可用**——仓库内置 `--fix` 在 180s 内无法返回，被迫自建替代器 |
| 数字是否下降？ | 是。116 断链 + 35 目录警告 → **107 + 21**，净关闭 9 断链 + 14 目录；**未新增任何断链**（`ADDED = 0`） |
| 缺口在哪？ | **脚本（主因）**：`--fix` 无作用域、O(N×M)、目录目标无策略、误报无识别、无基线 diff/回滚；**判定（次因）**：29 个"断链"是 Markdown 误解析、21 个目录目标需选入口文件；**编排（结构性）**：无 `check→classify→fix→verify→ledger` 单入口 |
| 能否交给 agent？ | 检查 + 复验 + 分类计数 **可交**；修复写入 **需前置规则表**；真缺文件与语义改写 **必须留给人** |

**一句话判断**：门禁的「发现」和「复验」已经足够工程化，缺的是中间那段的**执行器与策略表**——不是缺脚本数量，而是缺一个带作用域、带分类、带回滚的修复入口。

## 3. 修复：内置 `--fix` 不可用，改用确定性替代器

### 3.1 内置修复器实测失败

```
python .agents/scripts/check-links.py --path docs/retrospective --fix --dry-run
```

| 观察 | 数据 |
|---|---|
| 结果 | **> 180 s 未返回**，被强制终止（两个进程累计 CPU 502 s / 181 s） |
| 根因 | [processor.py](../../../../.agents/scripts/lib/link_fixer/processor.py) 逐文件调用 [finder.py](../../../../.agents/scripts/lib/link_fixer/finder.py) 的 `_find_all_matches`，**每个断链执行一次全仓 `rglob`**，复杂度 O(N×M) |
| 单次全仓 `rglob` 实测 | **113.7 s** |
| 另一缺口 | `--path` 只限制"扫描源文件"，不限制"查找目标文件"的范围，**作用域未传导到修复阶段** |

结论：**内置 `--fix` 在当前仓规模下不可用**，不是"慢一点"，而是无法完成。

### 3.2 替代器：确定性规则 + 双重安全边界

自建临时修复器（`%TEMP%\specweave-link-fix-pilot.py`，dry-run 默认，`--apply` 才写入），只做两类**不改变语义**的路径修复：

| 修复类型 | 触发条件 | 动作 | 本轮命中 |
|---|---|---|---|
| 目录链接 → 入口文件 | 目标为**已存在目录**且目录内有 `README.md` | 追加 `/README.md`（保留锚点） | 14 |
| 层级偏移 | 去掉 1–3 个 `../` 后**唯一**命中仓内已存在文件 | 重写前缀层数 | 9 |

安全边界：

- 跳过 `http/https/mailto/tel/#/file:///`、含 `{` 的模板占位、代码围栏内链接；
- 层级修复**只接受唯一命中**，多义即拒绝（避免"修成另一个同名文件"）；
- 不处理锚点、不新建文件、不删除链接；
- 先 dry-run 输出清单（`scanned_files` / `proposed_changes` / 分类计数与样例），人工过目后再 `--apply`。

### 3.3 应用与回滚

| 阶段 | 数据 |
|---|---|
| dry-run 提案 | 56 处 |
| 实际写入 | 57 行（含代码围栏内 4 行，未造成破坏） |
| 首次复验 | 仅关闭 9 断链 + 14 目录 → 与提案数不符 |
| 差异定位 | **33 行改动不在基线集合内**：这些链接被检查器"看不见"（越界 `..` 被截断、`external/` 段被整体跳过），修复器比门禁更严格 |
| 处置 | 按 `git diff` 逐行配对**回退 33 行（14 文件）**，保留基线内 23 处；回退误伤 1 行索引（`README.md` 第 11 行），已恢复 |
| 最终工作树（本轮足迹） | 11 个文件，+26 / −24 行；其中 23 行为链接修复，3 行为本报告登记（`README.md` 1 行 + `index.md` 2 行） |

> 纪律：**只修门禁报告过的项**。修复器"多修"的那 33 处虽可能是真断链，但不在本轮口径内，纳入会污染前后对照——这正是闭环必须具备"基线 diff 写入闸门"的直接证据。

### 5.2 耗时结构

| 阶段 | 耗时 | 属性 |
|---|---|---|
| 基线检查 | 17 s | 实测，稳定 |
| 内置 `--fix` 尝试 | >180 s（失败） | 实测，不可用 |

| 应用修复 | 秒级 | 实测 |

## 6. 缺口归因

### 6.1 脚本缺口（主因）

| 缺口 | 证据 | 影响 |
|---|---|---|
| `--fix` 作用域未传导 | `--path` 只约束扫描源，目标查找仍全仓 `rglob` | 子树修复仍付全仓代价 |
| O(N×M) 查找 | 单次 `rglob` 113.7 s | 修复不可完成 |
| 目录目标无入口策略 | 21 个警告全部停在"链接到目录" | 需人工逐条选 README/SKILL/index |
| 误报无识别 | 29 条说明文字被当链接 | 永久占用"红灯"，污染门禁可信度 |
| 无锚点校验 | 报告只查文件存在性 | `#section` 失效不会被发现 |
| 越界 `..` 被截断 | 探针验证：`../../../../../knowledge/README.md` 被解析为 `<repo>\knowledge\README.md` | **假绿**：真实越界断链不报 |
| `external/` 等段整体跳过 | 代码内 `LINK_CHECK_SKIP_SEGMENTS` | 该区间链接不参与检查，且报告未显式声明"已跳过 N 条" |
| 无基线 diff / 回滚 | 本轮靠自建脚本比对 | 修复可能改动基线外内容而无告警 |

### 6.2 判定缺口（次因）

1. **目录链接的入口优先级**未定义：`README.md` → `SKILL.md` → `index.md` 的顺序与例外（本轮 21 个目录中大量是 Skill 目录，只有 `SKILL.md`）。
2. **Markdown 语法的"伪链接"**无豁免规则：`[TAG](说明)` 这类表格/行内标注被误判，需要一条可配置的忽略规则而非逐条人工判定。
3. **真缺失文件的处置策略**未定义：删除引用、改写为纯文本、还是补建索引页，属内容决策。
4. **代码围栏内链接**：本轮有 4 行改动落在围栏内，虽未破坏，但说明"围栏内是否应修"尚未成为显式规则。

### 6.3 编排缺口（结构性）

- 无单入口：`check` / `fix` / `verify` / `classify` 各自为战，无一条命令产出完整闭环。
- 无产物落盘：基线与复验结果只存在于终端，无法作为门禁证据留存。
- 无写入闸门：没有"只改基线内 / 只改允许子树 / 跳过围栏与锚点 / 变更前快照"的统一约束。
- 无台账：介入次数、耗时、关闭数/新增数没有结构化记录，无法判断 agent 是否真的减轻了负担。

## 7. 做成 agent 可执行闭环，还差这几件

| # | 待补件 | 内容 | 归属 |
|---|---|---|---|
| 1 | 作用域内索引 | 一次遍历建立"文件名 → 相对路径"映射，在 `--path` 作用域内完成解析，把 O(N×M) 降到 O(N) | 脚本 |
| 2 | 结构化报告 | 输出 JSON：`file / line / text / target / class / confidence / fixable`，供下游分类与计数 | 脚本 |
| 3 | 分类器 + 策略表 | 六类默认动作：`markdown-misparse`（忽略）/ `dir-with-readme`（补 `/README.md`）/ `dir-without-readme`（按入口优先级）/ `depth-off`（唯一命中级联）/ `truly-missing`（授权后处置）/ `escaped-root`（报错而非截断） | 判定 |
| 4 | 写入闸门 | 仅基线集合内、仅白名单子树、跳过围栏与 `#anchor`、写入前快照、`--rollback` 一键还原 | 编排 |
| 5 | 闭环编排器 | 单命令 `check → classify → propose → apply → verify → ledger`，自动产出前后对照、介入计数、耗时与"新增断链"断言 | 编排 |

> 最小可行路径：先做 **#1 + #2**（脚本层，收益最大且无判定风险），再做 **#4**（防越界），最后补 **#3 + #5**（策略与编排）。#3 中的"策略表"必须由人一次性拍定并入库，否则每轮都要重新判断。
