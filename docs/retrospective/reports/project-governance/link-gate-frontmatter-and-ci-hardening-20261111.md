## 1. Agent 接管痛点诊断：三类痛点与「必须留人」的边界

诊断结论按优先级分两层，详细证据见 [接管痛点报告](agent-takeover-pain-points-20261109.md)。

**P0（不修就无法闭环）**

- 链接修复闭环缺中间环节：检查能跑、复验能跑，**修复环节不可用**。
- 登记面与磁盘事实不同步：技能目录存在，但 README / capability-registry / CHANGELOG / TOML 镜像四处登记面可能同时缺行。

**P1（可绕过，但会让你做错判断）**

- 双入口文档存在过期规范：`AGENTS.md` 与 `.agents/` 内规范并存时，Agent 可能只读到其中一份。
- 启动路由对「工作目录不在 vendor/ 内」的情形没有强制预检。
- 保存位置（`docs/` 公开 / `playground/` 私域 / `.trae/specs/` 规划）判断依赖内联副本，容易过期。
- 子模块编排（父仓 → 子模块的提交顺序与 gitlink 前移）缺少机械校验。

**必须留人的判断项（按设计不做自动化）**

| 判断项 | 为什么不自动 | 本次实际处置 |
|---|---|---|
| 某条断链是「文件已移动」还是「内容已删除」 | 只有读语义才知道；`reason` 选错会让基线失去审计价值 | 入账时逐条指定，缺 `--reason` 直接拒绝写入 |
| 散文化 `source` 要不要改写成路径 | 改写会改变文档语义，不是纯机械替换 | 只报数、不改写 |
| 镜像技能归到哪个分类 | 分类是产品判断，脚本只能枚举候选 | 判定器只读输出，写入需显式 `--assign` |
| 某篇模式文档是不是「创新类」 | 边界样本（如 `knowledge-as-code-paradigm.md`）语义上真是范式迁移 | 保留显式章节优先，兜底只做保守判定 |
| 批量路径修复存在多个同名目标时选哪个 | 后缀锚定可能命中多义 | 歧义即放弃该条，交人确认 |
| 是否改写已存在的混合提交 | 涉及他人历史与并行会话 | 未改写，只披露 |

## 3. 技能登记面判定器与受边界约束的写入器

### 3.1 判定器（只读）

`check-skill-registration.py` 的定位是**只读判定 + 退出码分级**：`0` 全通过，`1` 仅漏登记（可以带着问题提交但必须可见），`2` 计数漂移或 TOML 字段不一致（视为基线损坏）。

判定面覆盖四处：`README.md` 表行、`capability-registry/02-skills.md` 表行、`CHANGELOG.md` 版本条目、`.meta/toml/.agents/skills/<name>/SKILL.toml`。

工作当时（2026-11-09）的口径与结果：

| 指标 | 数字 | 说明 |
|---|---|---|
| 技能总数 | 224（原生 68 / 镜像 156） | 磁盘目录去除隐藏项 |
| 原生漏登记 | 7 | 任一登记面完全缺行 |
| 缺 TOML 镜像（原生轨） | 4 | 已登记但无 `SKILL.toml` |
| 本轮新建 TOML 镜像 | 10 | `080ff48d0`，共 13 文件改动 |
| 计数漂移 | 0 | 表头 `（N个）` 与数据行一致 |

### 3.2 「计数漂移 = 0」不等于登记完成

这是本条工作线最重要的判断：**计数自洽只能证明表头与行数对齐，不能证明「磁盘上的技能都在表里」**。一个技能完全缺行时，表头和数据行会一起少，计数依然为 0 漂移。

因此判定器把「漏登记」单列为独立信号，且不自动修复——**因为补行需要先知道归入哪个分类，这是人的判断**。写入器因此被设计成「受边界约束」：必须显式 `--assign` 指定分类，默认 dry-run，`--write` 才落盘，落盘前做哈希校验与备份。

### 3.3 本轮复跑（2026-11-11）

| 指标 | 今日实测 | 与工作时对比 |
|---|---|---|
| 技能总数 | 225（原生 68 / 镜像 157） | +1 镜像 |
| 原生漏登记 | **0** | 7 → 0，已闭环 |
| 原生缺 TOML 镜像 | **0** | 4 → 0，已闭环 |
| 计数漂移 | **0** | 保持 |
| 跨面不一致 | **0** | 保持 |
| 镜像轨缺 `SKILL.toml` | **38** | 新增欠账，见 §10 |

## 4. 模式文档质量检查：把「归类兜底」收紧

### 4.1 问题

模式文档若没有 `## 模式类型` 章节，检查器会扫描开头 1000 字符做兜底归类。旧实现用**裸关键词**，于是：

- 标题或开头含「迁移」的操作速查、SOP、兼容手册 → 被判为创新类 → 强制要求「失败案例」「反目标用户/场景」两章 → 阻断提交。
- 「反向」在工程语境里多为计算方向（前向/反向计算、反向传播、反向依赖）→ 同样被误判。

典型被误伤样本：WSL 发行版迁移速查手册、Numpy 参考实现优先类文档。

### 4.2 处置与实测

兜底分支改为**短语级关键词**，显式 `## 模式类型` 章节内的宽口径完全不动：

| 指标 | 改前 | 收紧「迁移」后 | 再收紧「反向」后 |
|---|---|---|---|
| 兜底判为创新类 | 92 | 39 | **31** |
| 兜底阻断 | 64 | 27 | **22** |
| 显式章节分支（创新/非创新） | 263 / 216 | 263 / 216 | 263 / 216 |
| 总阻断 | — | — | 243 → 238 |
| 样本规模 | — | — | 914 篇模式文档 |

「反向」一次改判 8 篇，逐篇核对为计算方向、动词性表达、工程术语或统计口径噪声，其中 5 篇原被阻断。

口径说明：本报告采用提交 `41008e7fb` / `11f89a86b` 内的实测记录（92 → 39 → 31）。任务书口述的「95→42、39」未能在这两个提交的记录中复现，差异原因未验证，故不采用。

### 4.3 边界取舍：`knowledge-as-code-paradigm.md`

该文档没有 `## 模式类型` 章节，标题为「知识即代码：软件工程范式向知识管理迁移法」。按语义它是真正的**范式迁移**，旧兜底恰好靠裸「迁移」命中它；收紧后不再判为创新类，也就失去「失败案例 / 反目标」两章的强制要求。

这是一次**用少量漏判换大量误判清除**的取舍：

- 收益：约 61 条兜底判创新被消解，阻断从 64 降到 22。
- 代价：真正需要创新类严格检查、但没写 `## 模式类型` 的文档会被放过。

**缓解方式**：这类文档应显式声明 `## 模式类型`（显式分支的判定口径没有收窄）；兜底只作为「没声明时的保守近似」，不应承担精确判定职责。

## 6. 链接门禁的工程化：五类机制

```mermaid
flowchart LR
    A["源文件扫描"] --> B["跳过集过滤"]
    B --> C["链接提取器"]
    C --> D["本地路径校验"]
    D --> E["frontmatter 路径校验"]
    E --> F["基线比对"]
    F --> G["退出码 0 或 1"]
```

| 机制 | 解决什么 | 代码位置 |
|---|---|---|
| 源目录跳过集 | 未跟踪语料/工具/缓存贡献上万个假断链 | `LINK_CHECK_UNTRACKED_SKIP_DIRS` + `filter_untracked_paths` |
| 生成器修复 | docgen 为不存在的主题 README 造链接，一次产出 114 条死链 | `48614cef3`、`c3600e546` |
| 提取器修误报 | 占位符、正文短语、行内代码被当链接 | `d56f8f43e`、`d7dbe1046` |
| 测试夹具排除 | 测试里刻意构造的假路径被当真断链 | `filter_test_fixture_paths` |
| 基线机制 | 存量断链不阻塞新提交，但不能无限期挂着 | `lib/link_baseline.py`、`.agents/config/link-baseline.json` |

### 6.1 基线机制的「四道锁」

| 锁 | 规则 | 违反后果 |
|---|---|---|
| 1 | `reason` 必须属于 `moved / deleted / depth / other / unclassified` | 拒绝写入 |
| 2 | `kind` 必须属于 `link / frontmatter` | 拒绝写入 |
| 3 | `source` 必须是 git 跟踪文件 | 拒绝写入 |
| 4 | `source` 不得以 `projects/` 或 `vendor/` 开头（`target` 不受限） | 拒绝写入 |

另外两道防线：

- `--update-baseline` 只对**新增指纹**要求 `reason`，缺 `--reason`/`--reason-map` 直接拒绝，防止把未分类断链塞进基线。
- 基线更新**只允许全仓扫描**；`--path` 与 `--update-baseline` 同时出现会被拒绝（`check-links.py` 的早期校验），防止用局部扫描生成「只覆盖一个目录」的假基线。

指纹 =（规范化 source, 规范化 target, kind），**不含行号**——行号会随编辑漂移。`kind` 参与指纹是为了区分「正文链接」与「frontmatter 路径字段」：同一个字符串在两种语境下语义不同，不能共用一条账。

### 6.2 子模块三态：unknown 不是断链

子模块未检出时无法判定目标是否存在。实现把状态分为四类：`not_initialized`（目录不存在）、`empty`（空目录）、`checked_out`（已检出，缺失即真断链）、`outside`（不在任何子模块内）。

关键纪律：**未知态跳过，但不入基线**。入基线等于把「暂时看不到」固化成「永远豁免」，等子模块检出后这条账就再也不会被报出来。

## 9. 判断成本 vs 执行成本

| 维度 | 机械判断（可全自动） | 策略判断（必须留人） |
|---|---|---|
| 典型问题 | 目标文件是否存在？指纹是否在基线？计数是否等于行数？TOML 文件是否缺失？子模块指针是否一致？ | 这条断链是「移动」还是「删除」？这个技能归哪类？这篇文档算不算创新类？两个同名目标选哪个？ |
| 单条成本 | 毫秒级，可全量跑 | 每条需读语义，分钟级 |
| 失败模式 | 判据写错 → 漏检或误报（可回归测试锁住） | 判断标准漂移 → 同类问题不同结论（需文档化口径） |
| 本轮做法 | 全部脚本化，并配回归夹具 | 只输出候选与证据，写入需显式参数 |
| 数字例证 | 621 条 `source` 里 334 条路径形态可机械判定；225 个技能四处登记面可机械对账 | 287 条散文化 `source` 不逐条读，用一次规则判定；91 个未登记镜像技能不自动补 |

**核心经验**：策略判断不该被「自动化掉」，而应被「压缩成一次性规则 + 可复跑的判定器」。例如「哪些 `source` 是散文」本来是 621 次人判断，收敛成一条判据后变成 0 次；但「某条散文要不要改写成路径」仍然是 287 次人判断，脚本只能报数。

## 12. 可复用做法（照着做）

### 12.1 全仓断链三账分诊

1. 先跑一次全仓扫描，拿到候选总数，**不要直接开始修**。
2. 按源文件是否被 git 跟踪分成两堆。不在 git 的那堆先排除，它不构成仓库缺陷。
3. 对在 git 的那堆，按「工具缺陷 vs 真断链」再分一次：抽出 20 条样本人工看，若多数是占位符/正文短语/行内代码，先修提取器。
4. 只有剩下的才是真断链，进入修复或基线。

### 12.2 门禁接入基线（四步）

1. 全仓扫描，确认基线更新只允许全仓（局部扫描会生成假基线）。
2. 逐条指定 `reason`；缺省即拒绝写入。
3. 加四道锁：`reason` 枚举、`kind` 枚举、`source` 必须是 git 跟踪文件、`source` 不得在 `projects/`/`vendor/`。
4. 指纹不含行号；`kind` 入指纹。
5. CI 加 `--baseline`，并用**与 CI 完全相同的命令**在本地跑一次，记录真实退出码。

### 12.3 frontmatter 字段分治

1. 先分账：按字段统计「路径形态 / 散文化 / 占位符」，不要整体放开或整体收紧。
2. 路径形态判据必须**只看锚点之前的 head**；`../x.md#中文锚点` 是路径，不是散文。
3. 散文化跳过必须三处报数：终端、汇总、`--json`。
4. 写三条防吞断言：路径形态写错要报、散文不报但要计数、严格字段（如 `x-toml-ref`）缺失要报。
5. 断言要验证「改前红、改后绿」，否则不知道测的是不是新行为。

### 12.4 登记面判定器与写入器

1. 判定器只读，退出码分级（0 全过 / 1 仅漏登记 / 2 结构损坏）。
2. 判定「漏登记」看并集，不看计数——计数对齐不代表没漏。
3. 写入器默认 dry-run，必须显式 `--assign` 分类，`--write` 才落盘，落盘前哈希校验 + 备份。
4. 分类留给人，脚本不要猜。

### 12.5 归类收紧的回归法

1. 改前跑一次全量，记录分类分布与阻断数。
2. 只改兜底分支，不动显式声明分支。
3. 改后再跑一次，确认显式分支计数**零变化**。
4. 对改判样本逐篇核对，区分「真误判」与「真漏判」，写入报告。

### 12.6 批量路径修复的安全阀

1. 严格解析目标路径，不做字符串拼接猜测。
2. 每条替换后必须满足：解析结果是真实文件、且不等于源文件本身。
3. 后缀锚定出现多义（命中 >1）即放弃该条。
4. 先 `git checkout HEAD --` 回滚演练，再批量落地。

### 12.7 CI 接线验证

1. 本地用与 CI 一字不差的命令跑一次。
2. 记录真实退出码与首尾各若干行输出。
3. 检查 CI 的环境差异（submodules、Python 版本、依赖），把差异写进报告。
