## 洞察 1：架构洞察先行源码学习法（P0）

### 5-Whys 根因分析

- **问题**：学习一个 20 文件的陌生代码库，逐文件通读效率低、且易"只见树木不见森林"
- **Why1**：为什么逐文件通读低效？→ 因为需要从每个文件的实现细节反推出整体架构，属于"自底向上"的逆向工程
- **Why2**：为什么需要反推？→ 因为没有优先找到项目自带的"架构骨架"（README 定位 + 入口文件启动流程 + 集成点边界）
- **Why3**：为什么这三个文件是骨架？→ README 定"是什么"，入口文件（shell/app.py）定"怎么跑起来"，唯一集成点（api.js）定"边界在哪"，三者揭示核心架构原则（零逻辑客户端）
- **Why4**：为什么先提炼原则再看细节更高效？→ 有了核心架构原则作为"纲"，后续每个文件都能快速归类（属于展示层/服务层/持久层），而非孤立理解
- **Why5**：为什么这是可复用模式？→ 任何"学习代码库生成知识"类任务（wiki 教程、架构文档、上手指南）都适用，核心是"先建立全局框架，再填充细节"

### 模式描述

**名称**：架构洞察先行源码学习法
**触发条件**：需要学习/研究任何陌生代码库并产出知识文档时
**核心动作**：
1. 第一步：并行读取「README（定位）→ 入口文件（启动流程）→ 唯一集成点（边界）」，提炼核心架构原则
2. 第二步：以核心架构原则为纲，规划知识文档的章节骨架
3. 第三步：按章节所需补充读取相关源码（而非逐文件通读）
4. 第四步：写文档时始终回到核心架构原则做校验（每个章节是否服务于该原则）

**预期收益**：陌生代码库的理解效率提升 3-5 倍，产出文档结构更聚焦

**反模式**：按目录 `/` 顺序逐文件通读后再组织知识（自底向上，易迷失于细节）

## 洞察 2：零逻辑客户端桌面应用可冻结架构（P0）

### 5-Whys 根因分析

- **问题**：如何把成熟的 CLI 工具链转化为可打包单文件的桌面 GUI 应用？
- **Why1**：为什么不能直接给 CLI 包个 GUI？→ 直接在 GUI 里实现业务逻辑会导致双份维护、背离"单一事实源"
- **Why2**：为什么用零逻辑客户端？→ GUI 只做展示与转发，业务逻辑 100% 留在后端，后端升级 GUI 自动受益
- **Why3**：为什么用单源无 CORS？→ 后端同时托管 UI 静态资源（`/`）与 API（`/api`），前端同源请求，规避桌面 webview 跨域痛点
- **Why4**：为什么用进程内服务器？→ 用线程（而非子进程）跑服务，PyInstaller 才能把「Python 后端 + React 前端」冻结成单一可执行文件
- **Why5**：为什么这是可迁移架构？→ 大量"本地优先"工具（本地检索、本地知识库、本地模型对话）都可沿用此三支柱模式

### 模式描述

**名称**：零逻辑客户端桌面应用架构
**触发条件**：把成熟 CLI/服务端工具链封装为桌面 GUI 应用时
**核心三支柱**：
1. **零逻辑客户端**：GUI 只做展示与转发，业务逻辑留在工具链（单一事实源）
2. **单源无 CORS**：后端同时托管 UI 静态资源与 API，前端同源请求
3. **进程内服务器**：线程跑服务（非子进程），支持 PyInstaller 单文件冻结
**关键技术细节**：随机回环端口 + 每次启动随机 Bearer token + 就绪轮询 + 约束 uvicorn 选项（asyncio/h11/ws-none）避免打包原生扩展
**预期收益**：轻量化交付、随工具链升级免费进化、可单文件分发

**反模式**：在 GUI 里重写业务逻辑（双份维护）；子进程跑服务（无法干净冻结单文件）

## 洞察 3：格式一致性优先 + 显式排除质量双门（P1）

### 5-Whys 根因分析

- **问题**：知识库写入与 git 提交常出现风格割裂与无关文件混入
- **Why1**：为什么风格割裂？→ 从零设计 frontmatter/章节结构，而非参考同目录既有格式
- **Why2**：为什么应从零设计？→ 实际上不应，同目录必然已有同类文档可作为格式权威
- **Why3**：为什么无关文件会混入？→ 使用 `git add .` 一次性暂存所有变更，未做三查
- **Why4**：为什么会用 `git add .`？→ 图省事，忽略了工作区可能同时存在多任务遗留（本次的 jira-skill-wiki）
- **Why5**：为什么需要双门？→ 写前门保证"风格对"，提交前门保证"范围对"，两者缺一质量就崩

### 模式描述

**名称**：知识产出质量双门
**门 1（写前）**：写入知识库前，先 LS 目录、再读同目录 1-2 个同类文件确认实际格式（frontmatter 风格、章节编号、导航表、相对路径层级），以既有做法为权威标准
**门 2（提交前）**：三查暂存法（查新增/修改/删除）→ 显式 `git add` 目标目录/文件（禁止 `git add .`）→ 中文提交走 UTF-8 安全通道（git-commit-utf8.py）

**触发条件**：写入知识库 / 执行 git 提交前
**反模式**：凭记忆或抽象规范决定格式（而非读现有文件）；`git add .` 一次性暂存
