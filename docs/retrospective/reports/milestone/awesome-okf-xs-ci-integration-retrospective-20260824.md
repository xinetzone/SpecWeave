## 三、核心洞察（I：洞察四元组完整 ✅）

### 洞察 1：CI 是编码损坏的「放大器」而非「源头」

- **陈述**：文档库编码损坏长期潜伏在 git 历史中，只有引入 CI 构建 gate 后才被暴露为阻塞性故障。
- **证据（F-3/F-4/F-5）**：首版 CI run 失败即触发于 Sphinx 解析非法 UTF-8 字节；此前本地编辑未触发编译期解码错误。
- **反常识**：损坏内容不是本次 CI 集成制造的，却在构建阶段「首次被看见」；本地浏览工具对损坏字符有容错，Sphinx 严格解码才暴露。
- **行动**：将「构建前的格式/编码完整性」视为 CI 的第一道检查，而非等构建报错再排查。

### 洞察 2：损坏侵入点与修复基线分离，需「正文可取信源 + 元数据保留」双通道修复

- **陈述**：正确修复的关键不是「逐字猜中文」，而是找到未损坏的历史正文基线，外加保留后续合法元数据编辑。
- **证据（F-7~F-11）**：`6fe904e` 提供完好正文，`f78d5c4` 提供合法元数据追加；两者结合完成无损重建。
- **反常识**：git 历史不仅是「改坏」的记录，也是「修复所需完好内容」的备份来源；`git log --follow` 可定位损坏引入点，`git show <rev>` 可提取基线。
- **行动**：修复编码类数据损坏时，优先用版本历史取信源而非凭语义重写。

### 洞察 3：gate 有效性须「双向验证」——既要拦得住，也要放得行

- **陈述**：质量门脚本若只测「正常通过」而未测「异常拦截」，可能形同虚设。
- **证据（F-19/F-20）**：用探针坏文件验证拦截（exit 1），移除后验证放行（exit 0），双向闭环。
- **反常识**：CI gate 的价值不在于「通过时静默」，而在于「破坏时非零退出」；未验证拦截分支的 gate 与不存在等价。
- **行动**：新增质量门脚本必须附「破坏性探针测试」，且探针文件需自动清理，避免污染仓库。

## 四、可复用模式萃取（E：G3 模式可迁移验证 ✅）

### 模式 E-1：跨提交「正文基线 + 元数据保留」文档修复法

- **触发场景**：Markdown/YAML 文档出现编码损坏（UTF-8 截断、U+FFFD），且损坏提交前存在完好历史版本。
- **核心步骤**：
  1. `git log --follow` 定位损坏引入提交与完好基线提交。
  2. 用 `git show <baserev>:<path>` 提取完好正文（权威信源）。
  3. 用 `git show <corruptrev>:<path>` 对比，分离「仅编码损坏」与「合法编辑」（如 frontmatter 元数据追加）。
  4. 以基线正文全量重建，仅补插合法编辑内容。
  5. 三层验证（工作区/暂存区/提交）比对正文一致性与 U+FFFD 缺失。
- **反模式**：逐字符猜中文重写（易错）、直接全量回退到基线（丢失后续合法编辑）。
- **迁移验证**：适用于任何有 git 历史的文本型数据损坏修复（如 JSON、README、配置文件），不限于本项目。

### 模式 E-2：CI 质量门「破坏性探针双向验证」法

- **触发场景**：为 CI 新增任何校验性脚本（格式检查、编码检查、lint、门禁）。
- **核心步骤**：
  1. 编写脚本：正常输入 → exit 0；异常输入 → exit 1 并输出定位信息。
  2. 构造异常探针输入，断言返回非零（拦得住）。
  3. 移除探针，断言返回零（放得行）。
  4. 探针文件用 `finally`/`missing_ok` 自动清理，不落库。
  5. 在 CI 中置于被保护步骤之前。
- **反模式**：仅做正向冒烟（只测放行）、探针文件残留仓库、gate 放被保护步骤之后。
- **迁移验证**：适用于任何 CI 平台（GitHub Actions / GitLab / Jenkins）的任意门禁脚本。

## 六、关键决策与问题根因（数据验证三查法已执行）

- b7a6e16 将 `html_baseurl`/`ogp_site_url` 指向 `https://awesome-flexloop.github.io/awesome-okf/`，`sitemap_url_scheme = "{link}"`。
- 数据验证：conf.py 已核对三处 URL 字段一致（Grep 确认）。

### 关键决策 2：UTF-8 gate 放置于构建前
- 155d35f 将 `python scripts/check-utf8.py` 置于 `Install dependencies` 前。
- 数据验证：pages.yml 步骤顺序 Read 确认。

### 根因 1：中文编码损坏
- 根因：`f78d5c4` 写入非法 UTF-8 字节，Sphinx 严格解码失败。
- 复现证据：12 文件无法 `.decode('utf-8')`。
- 影响：阻塞首版 CI。
- 建议：CI gate 前置 + 提交前编码校验（见 E-2）。

### 根因 2：GBK 显示陷阱
- 根因：Windows 终端以 GBK 误显示 UTF-8 输出。
- 证据：`git log` 中文乱码，但字节级校验 True。
- 影响：误导未经验证的开发者误判为存储乱码。
- 建议：涉及编码判断一律用字节级比对脚本，不凭终端显示（本已沉淀至 project_memory）。
