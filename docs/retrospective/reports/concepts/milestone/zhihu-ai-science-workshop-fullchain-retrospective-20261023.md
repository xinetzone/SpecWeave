## 四、E 阶段：可迁移模式（2 个 L1，G3）

### 模式 1：收官状态对账

- **触发场景**
  - 适用于：一条链路被拆成多份子报告分别收口、需要在终点确认「全部产出物真正落地」；报告自述完成度与仓库/平台真实状态可能分离的任何场景。
  - 不适用于：单份产出、无版本控制载体的场景（无可对账对象）；探索期任务（尚无「完成」定义）。
- **核心做法**（5 步）
  1. 列全子里程碑与其声明的完成项（读各报告行动项状态列）。
  2. 对执行载体取当前状态快照（`git status --porcelain -uall <scope>` / 部署平台状态查询），记录基线时点。
  3. 逐项比对：声明完成项在载体上是否有对应实体（文件在库？提交存在？链接可达？）。
  4. 对未落地项按「应入库 / 候选入库 / 排除入库」三分类，并给出排除理由（二进制、构建产物、隐私件、他人在途变更）。
  5. 输出「未入库清单」小节（路径 / 分类 / 处置 / 责任人），闭环标记只在剔除显式挂起项后状态为空时给出。
- **反模式**
  - ❌ 以报告勾选框作为完成判据收工（本日 CF-022/CF-023 实证）。
  - ❌ 把全部未入库项一律当作缺口，不区分构建产物与他人 in-flight 变更（CF-017），导致门永久失败被整体绕过。
  - ❌ 对账不记基线时点，并发迁移（CF-012）被误判为数据错误。
  - ❌ 只报「有 N 条未入库」的条目数，不给分类与处置路径，读报告的人无法行动。
- **检验标准**：未入库清单中每一条都有分类与处置责任人；执行载体状态快照在剔除显式挂起项后为空；基线时点与 HEAD 提交哈希同时留档。
- **成熟度**：L1（单案例：本次工作坊收官；待第二个多子报告链路验证）。
- **迁移示例**：多模块代码 PR 合并后核对（CI 绿 + 产物发布 + 文档更新三态对账）；营销活动上线后核对「素材/落地页/埋点/合规声明」是否真正生效；跨部门交接清单签收核对。

### 模式 2：门声明机械校验

- **触发场景**
  - 适用于：产出物自带「质量门通过」自声明且门内含计数类判据（事实条数、冲突项数、意见采纳数）；同一数字在正文/摘要/frontmatter/索引行多处出现。
  - 不适用于：无自声明结构的自由文本；判据为纯定性判断的门（无可机械比对对象）。
- **核心做法**（4 步）
  1. 抽取声明值：从 frontmatter、执行摘要、索引登记行中提取声明的计数（正则匹配「N 条 / N 事实 / 采纳 N」）。
  2. 重算实际值：对正文条目做机械计数（如事实条目行 `grep -c`、V 意见表行数、行动项表行数）。
  3. 比对并判域：声明值 ≠ 实际值 → 报告退回同步；正文引用的编号超出自身编号域 → 检查是否跨源同形，要求加来源域前缀。
  4. 把校验挂到交付前执行位（提交前脚本 / CI 文档门），失败即阻断而非提示。
- **反模式**
  - ❌ 只做人工目视核对（本日三份复盘均自声明通过而其中一份计数漂移，CF-018）。
  - ❌ 改了正文不改摘要/frontmatter/索引行，只同步「看起来是源头」的那一处。
  - ❌ 把跨源同形编号（CF-019 的知识包 F-047）判为报告内部错误，产生虚假缺陷清单。
  - ❌ 校验脚本只输出警告不阻断，门与无门等效。
- **检验标准**：对同一报告族的全部声明位与正文实际计数逐项相等，输出 0 差异；编号引用全部落在带来源域前缀的集合内。
- **成熟度**：L1（单案例：本次首次识别并给出执行位；与既有「证据链工程化」「跨文档口径漂移」反模式条目互补，入库时需交叉引用）。
- **迁移示例**：财务月报「摘要数字 vs 明细表合计」自动对账；API 文档「示例响应字段数 vs schema 字段数」一致性校验；测试报告「用例声明数 vs 实际收集数」比对。
