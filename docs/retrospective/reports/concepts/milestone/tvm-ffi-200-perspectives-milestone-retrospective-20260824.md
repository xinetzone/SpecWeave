| 维度 | 内容 |
|------|------|
| **陈述** | 200 篇文档的成功交付高度依赖于自动化验证脚本对"字数/链接/frontmatter/NPU"四项硬指标的反复校验与修复闭环，生成过程的原始产物并非一次达标 |

| **反常识** | 直觉上"大批量生成"的核心是让模型一次写对；实际单次生成的错误率随量级放大（30/200=15% 字数不达标 + 90+ 虚构 API），真正保证质量边界的是脚本化的"生成→校验→修复"循环，而非依赖一次性正确性 |

## 四、E 阶段：可复用模式萃取

> G3 质量门：✅ 通过（模式含触发场景+核心步骤+反模式+迁移验证）

### 模式一：大批量 OKF 知识生成的「事实库-模板-分批-验证」四段式

**触发场景**：需要对一个真实代码库/源码目录/文档集生成超大批量（>50 篇）同构结构化知识文档（OKF/教程/API 手册），并保证内容真实、格式一致、可链接时。

**核心步骤**（4 步）：
1. **建事实库（R）**：先系统性采集源码事实，编号 F-xxx，每事实含文件+行号引用，零推测。这是批量一致性与真实性的唯一底座
2. **设计结构模板（I）**：提炼核心架构洞察，设计 OKF frontmatter、概述/源码分析/设计解读/NPU 建议/相关概念的标准节结构，建立 knowledge-map 的视角→事实映射
3. **分批生成（E）**：每批 ≤7 篇，从共享事实库差分注入，借助模板保证跨篇格式一致
4. **脚本验证+修复（V）**：先建验证脚本骨架再批量生成，对数量/字数/链接/frontmatter/NPU 设硬断言，检出即修复、修复即复验

**反模式**（应避免）：
1. ❌ **不建事实库直接写**：无共享信源，批量内容才会"车联网"式失孤、虚构 API 滋生
2. ❌ **一批写完再统一校验**：错误量随批次放大（30 篇字数不达标一次暴露），返工成本高；应边生成边校验
3. ❌ **把 AC-6/AC-7/AC-10 语义项当脚本断言**：脚本无法判断"是否虚构/是否合理/是否中文规范"，需人工 judgment 兜底

**迁移验证**：
- ✅ 已验证于 TVM FFI 200 视角项目（380 事实、200 文档、57 NPU、90+ 虚构 API 修复、5 项硬检查全通过）
- ✅ 核心逻辑（事实库→模板→分批→验证）与具体领域无关，适用于任何"大规模结构化知识生产"
- ✅ 可复用于后续的源码解读/API 文档/教程批量生成任务

### 模式二：验证脚本「先剥离语义噪声再解析」的健壮性设计

**触发场景**：对含代码的 Markdown/文档进行链接、字数、引用等自动校验时，纯字符串正则容易把代码块/内联代码内容误判为缺陷。

**核心步骤**（3 步）：
1. **预处理**：解析前先剥离围栏代码块（```...```）与内联代码跨度（`...`）
2. **差异化解析**：`/` 开头按 bundle-relative 解析，相对路径按源文件目录解析，排除 http(s)/mailto/#锚点
3. **疑似项人工复核**：脚本输出"疑似断裂"清单后，逐一确认是否为代码内符号，真实断裂=0

**反模式**（应避免）：
1. ❌ **正则直接扫全文**：把 `Foo[i]`、`operator[]`、lambda 捕获误判为断裂链接
2. ❌ **脚本全绿即收工**：不区分"结构性硬断言"与"语义性疑似项"，牺牲真缺陷或保留误报

**迁移验证**：
- ✅ 已验证于 verify_full.py 修正（F23-24）
- ✅ 适用于任何含代码/公式/特殊标记的文档静态分析
