## 三、洞察环节

### 3.1 关键发现（三条四元组洞察，G2 通过）

**洞察 1：过程可举证性是评审维度本身，不是附属品**

| 四元组 | 内容 |
|---|---|
| 陈述 | 评审把「AI 工具实际使用情况」列为与功能完整度并列的维度（F3），投稿要求强制工具截图（F4）——过程证据是评分项，不是作品之外的可选项 |
| 证据 | F3（F-051 四维评审）；F4（F-041~F-044 含工具截图）；F13（过程记录与证据清单先行建立） |
| 反常识 | 默认假设「作品做好即可，过程无所谓」；实际「工具实际使用」直接计入评审，且 F-047 全程工具绑定 |
| 行动 | 发布前清零 3 项待补材料（豆包截图 3-5 张、AI Works 链接、运行截图），使证据链完整 |

**洞察 2：单文件形态是「部署即达」的结构性优势**

| 四元组 | 内容 |
|---|---|
| 陈述 | 上传源码（F21）要求作品可运行、可检查；单文件零依赖把部署环节的风险（构建、依赖、路径）全部消除，是跨过 F-047 门槛的稳妥形态 |
| 证据 | F8（单文件红线）；F21（上传源码方式）；知识包机制洞察「成本从生成代码转移到把功能跑通」 |
| 反常识 | Vibe Coding 语境下「工程越复杂越显技术含量」；实际部署复杂化反而提高 F-052 审核环节的失败面 |
| 行动 | 保持单文件；打包 ZIP 上传时按教程规范（根目录含入口文件） |

**洞察 3：9 天窗口下「先发布再迭代」优于「打磨完美再发布」**

| 四元组 | 内容 |
|---|---|
| 陈述 | v1 当日完成并自检通过，v2 半小时闭环（F15-F17）；先发布可尽早积累互动表现（F3 评审参考项），迭代收益大于延迟发布收益 |
| 证据 | F11/F16（两次自检 pass）；F17（v1 备份可回退）；F3（互动参考） |
| 反常识 | 默认「作品要打磨到完美才发布」；活动窗口有限且互动计入评审，发布节点比完美度更关键 |
| 行动 | 10-27 前完成部署与发布；发布后按反馈迭代 v3，_backup 继续留痕 |

### 3.2 规律认知

参赛类任务的通用节奏：**先建立「要求→证据」映射 → 再创作 → 验证动作留痕 → 逐条核对后发布**。证据资产与作品资产同等重要，且必须在创作当刻产生（F13）。

### 3.3 潜在机会

- **自动化上传半闭环**（附录 B）：浏览器登录态可用、「科学季」选项确认，可将「打包 ZIP → 填表单 → 上传 → 取链接」固化为半自动流程，用户仅保留发布确认环节。
- **AI Works 作品页即互动阵地**：作品链接发布后，AI Works 作品页与介绍文章的互动表现计入评审（F3），可在文章发布后引导体验。
- **过程记录复用**：参赛过程记录可作为「创作过程叙事」直接迁移进介绍文章，减少重复写作（F13 → F18 已部分复用）。
