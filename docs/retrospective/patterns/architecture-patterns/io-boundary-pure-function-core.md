# IO边界抽象隔离·纯函数核心：后端可插拔的依赖倒置架构模式

## 模式概述

在设计需要与外部世界交互的系统（爬虫、数据存取、第三方服务集成）时，应把「IO 边界」（输入输出边界，即程序对外读写网络/文件/数据库的地方）用抽象接口隔离，使上层核心逻辑只依赖接口、不依赖具体实现；同时把核心逻辑写成纯函数（给定相同输入总是返回相同输出、且不产生副作用的函数），把一切副作用推到 IO 边界之外。这样替换后端实现（如从 HTTP 抓取换成浏览器渲染）时，核心逻辑零侵入。

**核心洞察**：「会变的 IO 实现」应沉到底层适配器，「不变的核心规则」应上浮为纯函数。核心爬取流程与具体抓取实现解耦后，新增/替换 Fetcher 不影响 crawl 逻辑。

该模式由 okf-kit v0.3.3 的 Fetcher 抽象层实践验证（单案例，L1 待验证）。

**术语说明**：IO（输入输出）＝程序对外部世界的读写操作；后端＝完成某一外部交互的具体实现（如 HTTP 抓取器、浏览器渲染器）；可插拔＝后端可像插头一样随意替换而不影响核心；抽象接口＝只定义"能做什么"、不规定"怎么做"的契约；纯函数＝无副作用的确定性函数；副作用＝函数之外对环境产生的改变（写文件、改全局状态、发网络请求等）；适配器＝把具体 IO 实现包成接口实现、接入核心的"插座"；装配点＝程序启动时决定"注入哪个具体实现"的地方（如 main 函数或工厂）。

## 问题现象

当核心逻辑与 IO 实现耦合时，会出现以下失败模式：

1. **核心逻辑被 IO 细节污染**：爬取流程里到处是 `requests.get()`、`time.sleep()`、异常重试等 IO 细节，核心业务规则淹没在副作用中，无法独立阅读与测试
2. **后端替换成本爆炸**：新增一种抓取方式（如从静态 HTTP 换成 JS 渲染）需要改动核心 crawl 逻辑，牵一发动全身
3. **核心难以单测**：核心逻辑依赖真实网络/文件，测试必须 mock 一堆环境，甚至无法离线测试
4. **副作用不可控**：IO 副作用（网络延迟、失败重试、磁盘写入）散布在核心逻辑各处，难以统一管理

根因：把「具体 IO 实现」当作核心逻辑的固定依赖，而非可替换的边界；把「有副作用的操作」当作核心规则的一部分，而非推到边缘。

## 核心设计模型

### 分层结构

```
┌─────────────────────────────────────┐
│  核心层（纯函数，零副作用，易测试）      │  ← 不变的业务规则
│  如：crawl 流程、结果解析、去重逻辑      │
└──────────────────┬──────────────────┘
                   │ 依赖抽象接口（fetch/close）
┌──────────────────▼──────────────────┐
│  IO 适配层（唯一允许副作用的地方）      │  ← 会变的实现
│  HttpFetcher / BrowserFetcher / ...   │
└─────────────────────────────────────┘
```

| 层 | 职责 | 是否允许副作用 | 变化频率 |
|----|------|--------------|---------|
| **核心层** | 业务规则、流程编排、纯计算 | ❌ 禁止（纯函数） | 低 |
| **IO 适配层** | 网络请求、文件读写、进程管理 | ✅ 唯一允许 | 高 |

### 两个设计支点

1. **接口隔离 IO 边界**：核心层依赖 `Fetcher` 抽象接口（如 `fetch(url)` / `close()`），不 import 具体实现。`HttpFetcher` 与 `BrowserFetcher` 都实现同一接口，上层 `crawl` 逻辑无感知
2. **核心纯函数化**：把能写成纯函数的部分（去重、解析、状态推进）从 IO 中剥离，让核心逻辑确定性、可单测、可复用

## 与现有模式的区分

模式库中 `content-type-routing`（内容类型路由）同样产生"统一接口 + 可插拔"的表层形式，但与本模式在**本质意图**上不同：

| 维度 | content-type-routing（策略选择） | io-boundary-pure-function-core（本模式） |
|------|-------------------------------|------------------------------------------|
| 核心问题 | 多种异构输入该用哪种处理逻辑 | IO 副作用如何与核心逻辑隔离 |
| 决策时机 | **运行时**按输入类型动态分派 | **装配时**注入后端，核心不感知 |
| 接口关系 | 多个策略并行，分类器选一个 | 一个端口多个适配器，注入一个实现 |
| 核心价值 | 每个类型用最优算法（专家池） | 核心纯函数化，后端可替换（依赖倒置） |
| 经典溯源 | GoF 策略模式（Strategy） | 端口-适配器 + 依赖倒置 + 纯函数核心 |

**一句话区分**：`content-type-routing` 解决「多个算法选哪个」，本模式解决「IO 副作用放哪、后端怎么换」。

## 标准实施步骤

### 步骤1：识别 IO 边界

- 找出系统中所有产生副作用的地方：网络请求、文件读写、数据库访问、进程调用、随机性、系统时间
- 这些就是需要隔离到适配层的「IO 边界」

### 步骤2：定义抽象接口（端口）

- 为每类 IO 定义一个最小接口，只暴露核心层真正需要的能力（如 `fetch(url)` / `close()`）
- 接口以「能力」而非「实现」命名（`Fetcher` 而非 `HttpFetcher`）

### 步骤3：核心逻辑上浮为纯函数

- 把可确定性的业务规则从 IO 中剥离，改写成纯函数（同输入必同输出、无副作用）
- 核心流程通过接口调用 IO，通过依赖注入传入具体实现

### 步骤4：实现具体适配器

- 每个后端实现一个适配器（`HttpFetcher` / `BrowserFetcher`），实现同一接口
- 新增后端只需新增适配器类，核心逻辑零修改

### 步骤5：依赖注入装配

- 在装配点（main/工厂/配置）选择注入哪个后端实现，核心层不直接实例化具体类
- 保证替换后端是「改一行装配代码」而非「改核心逻辑」

## 反模式（不要这么做）

- ❌ **反模式1：核心直接调用 IO**——核心逻辑里写死 `requests.get()`、`open()`、`sqlalchemy` 调用。后果：核心无法离线单测，换后端要改核心。应通过接口调用，IO 沉到适配层

- ❌ **反模式2：副作用潜伏在核心**——核心逻辑里夹带 `time.sleep()`、随机数、写日志、改全局状态。后果：核心变得非确定性、难测试、难推理。应把副作用全部迁出到适配层或显式管理

- ❌ **反模式3：接口按实现命名**——接口叫 `HttpFetcher`、`MysqlRepository`，把实现细节暴露给核心。后果：换后端时接口名也变，抽象形同虚设。接口应按能力命名（`Fetcher` / `Repository`）

- ❌ **反模式4：为"未来可能换"过度抽象**——只在一个后端、且无换后端需求时，也强行抽出多层接口。后果：不必要的间接层，增加理解成本。遵循 YAGNI（You Aren't Gonna Need It，意为"你还用不着它"）——真有第二个后端需求时再抽象

- ❌ **反模式5：核心逻辑纯函数化走火入魔**——把有真实副作用、且本质就是做 IO 的流程（如"边抓边存"）硬拆成纯函数，反而割裂语义。纯函数化只应作用于确定性计算部分

## 实战案例

### 案例1：okf-kit v0.3.3 Fetcher 抽象层（2026-08-18，主验证案例）

**来源**：[okf-kit Wiki 七概念执行报告 · 洞察5](../../../../projects/awesome-okf-xs/doc/bundles/meta/okf-ecosystem/index.md#L78-L82)

okf-kit 源码研读确认了「IO 边界抽象隔离 + 核心纯函数化」的真实落地：

1. **统一接口**：`HttpFetcher` 与 `BrowserFetcher` 实现统一的 `fetch` / `close` 接口
2. **根因匹配**：静态站点和 JS 渲染站点需要不同抓取策略，但上层 crawl 逻辑完全相同
3. **效果**：核心爬取流程与具体抓取实现解耦，新增 Fetcher 不影响 crawl 逻辑

这是本模式的主验证案例，当前为单案例（L1 待验证）。

### 同构先例（未计入 validation_count，作为原则佐证）

- **操作系统 VFS（虚拟文件系统）**：内核通过统一「文件操作接口」访问文件，EXT4/XFS/NTFS 等具体文件系统作为适配器可插拔——「核心逻辑依赖抽象接口，后端实现可替换」
- **Repository 模式 + 数据库后端**：业务层依赖 `Repository` 接口，MySQL ↔ PostgreSQL 切换时业务逻辑零改动——「IO 边界（数据库）隔离，核心业务纯函数化」
- **编译器的前端/后端分离**：前端生成中间表示（IR，Intermediate Representation），后端针对不同 CPU 架构生成代码——「核心（IR 生成）与后端（代码生成）解耦」

这三个先例说明「IO 边界抽象 + 核心纯函数化」是成熟系统架构的通用直觉，但尚未在本项目内形成独立验证案例，故本模式保持 L1。

## 适用边界

### 适用场景

- ✅ 需要与多种后端/数据源交互的系统（爬虫抓 HTML vs 渲染、多数据库、多文件系统、多云厂商 API）
- ✅ 核心逻辑需要离线单测、且 IO 是主要测试障碍
- ✅ 预期未来会扩展后端（如从 HTTP 抓取扩展到浏览器渲染、从 REST 扩展到 gRPC）
- ✅ 核心业务规则复杂且相对稳定，而 IO 实现频繁变化

### 不适用场景 / 需权衡场景

- ❌ 只有一个后端、且无任何扩展预期的简单脚本——过度抽象增加成本（见反模式4）
- ⚠️ 核心逻辑本身就是 IO 密集型（如纯粹的数据搬运/管道），纯函数化收益有限，强行剥离会割裂语义
- ❌ 对极致性能要求、抽象层的间接调用开销不可接受的底层热路径

## 检验标准

| 维度 | 检验点 |
|------|-------|
| 接口隔离 | 核心层通过抽象接口调用 IO，不 import 具体实现类 |
| 纯函数核心 | 核心业务规则可写成纯函数，同输入必同输出、无副作用 |
| 后端可替换 | 新增/替换后端仅新增适配器 + 改装配点，核心零改动 |
| 可测试性 | 核心逻辑可用 mock/假后端离线单测，无需真实网络/文件 |
| 命名抽象 | 接口按能力命名（Fetcher），而非实现命名（HttpFetcher） |
| 无过度抽象 | 抽象层数量与后端种类、替换需求成正比，不臆造未来需求 |

**经典模式溯源**（遵循经典模式优先复用启发式，未假装创新）：
- **端口-适配器架构（Ports & Adapters，又称六边形架构）**：核心与外部世界通过「端口」（接口）+「适配器」（实现）隔离
- **依赖倒置原则（DIP，SOLID 之 D）**：高层核心不依赖低层 IO 实现，两者都依赖抽象接口
- **纯函数核心/命令式外壳（Functional Core, Imperative Shell）**：核心写成纯函数，副作用推到边缘「外壳」
