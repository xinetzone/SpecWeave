# 多平台同构缺陷修复模式（Multi-Variant Isomorphic-Defect-Fix）

## 背景与动机

芯片/编译器/运行时类工程中，同一份算法逻辑常以"拷贝变体"形式存在于多个平台目录（如 `sim_vta2_topi`、`sim_vta3_topi`、`sim_vta4_topi`），或存在于同一仓库的 apps/产物目录与顶层源码两处。缺陷往往**同构传染**：在一个变体中定位并修复后，其它变体仍带同一缺陷。

本次复盘的直接证据（R2/R3）：1×1 stride>1 i16 shortcut conv 的 `split error` 同时存在于 `sim_vta3_topi/vta_topi.cc` 与 `sim_vta4_topi/vta_topi.cc`；且官方预编译产物（内嵌 commit 不同）与源码树基线也不一致——只修可见的那一个文件会导致"另一平台/另一构建仍报同样错"。

> **反常识**：同一缺陷的多个拷贝不会自动同步修复；官方发布二进制的源码基线（内嵌 git hash）甚至可能与当前分支不同，因此"修复某个文件"与"修复所有承载它的构建"是两件需要分别枚举的事。

---

## 触发场景

- 同一缺陷（同特征报错串、同函数名、同错误行）在多平台/多目录的拷贝变体中出现
- 修复了某个可见变体，但切换平台（仿真/硬件、V2/V4）后缺陷复现
- 需要以"平台×能力矩阵"为视角核对修复覆盖范围
- 拷贝变体之间由共享一段过滤规则/调度逻辑（如 tiling 约束）引发

**不适用于**：
- 各变体实现已分化（结构不同），仅错误文案相同——需逐一确认是否同一根因
- 单一实现、无拷贝变体的代码
- 源码与发布产物解耦且官方 CI 已统一重建的场景（仍建议用覆盖矩阵确认）

---

## 核心步骤

1. **定位一处根因**：在任一变体里定位缺陷函数与具体条件（记录错误串/行号/符号指纹）。
2. **全仓枚举同构变体**：
   - 用缺陷锚点（函数名、条件表达式、特征错误串）grep 整仓，找出所有候选文件
   - 用 `git log -- <文件路径>` 看各变体/各基线的源码增量，识别"拷贝关系"与"分叉基线"
3. **逐一确认为同一根因**：核对每个候选是否命中相同缺陷结构（不是只看错误文案相同）。
4. **原子化修复全部变体**：一次变更集内改完所有同构文件（每文件单点修改），并记录覆盖矩阵 `文件 × 平台/产物`。
5. **分仓库/分产物验证**：不同变体常分属不同仓库或不同发布产物（tools_cpp/模拟器二进制），逐个重建验证"不再复现"，再分别原子提交。

---

## 反模式（不要这么做）

- ❌ **只修可见变体**：缺陷在其它拷贝仍存在，换平台即复现
- ❌ **全局替换不做结构核对**：把文案相同但根因不同的代码一并改掉，引入回归
- ❌ **忽略发布产物与源码树的基线差**：官方二进制内嵌 commit ≠ 当前分支时，源码修复不会自动进入已发布产物
- ❌ **不维护覆盖矩阵**：事后无法回答"还有哪个平台/哪个构建没修"
- ❌ **修复后只在单一平台验证**：同构缺陷必须在每个承载变体的平台上各验一次

---

## 检验标准

- 全仓 grep 缺陷锚点结果为 0 或全部命中已修复文件
- 覆盖矩阵（文件×平台/产物）完整，缺失项有明确结论（不需要修/已确认无此缺陷）
- 每个承载变体的构建在修复后复跑通过（不再报同特征错误）
- 涉及多个仓库/发布产物时，各自完成原子提交且可追溯
