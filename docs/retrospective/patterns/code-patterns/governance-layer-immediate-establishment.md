# 功能完成后立即建立治理层（AGENTS.md + .agents/）模式

## 触发场景

- 完成一个功能/构建模块（如 Docker 变体体系），但未同步建立对应的治理路由与规范
- 遇到以下任一痛点：
  - 后续维护者（或 AI 智能体）无法快速理解该模块的约束和约定
  - 新成员/新智能体不知道从哪个入口了解模块规则，只能翻源码
  - 模块规则分散在各 Dockerfile/脚本注释中，无统一权威来源
  - 路由链断裂，父级路由表未同步更新导致无法到达子模块

**适用于**：新增功能模块/子项目/应用时，作为交付的一部分同步建立治理入口。
**不适用于**：一次性脚本、无后续维护需求的临时功能。

## 问题本质

功能模块实现的"代码"只是能力本身，而**治理层（AGENTS.md 路由 + .agents/ 规范）是能力的可理解性**。没有治理层，能力虽存在但不可发现、不可约定、不可约束——维护者只能靠猜测和翻源码理解设计意图，AI 智能体也无法按路由正确装载该模块的规则。功能完成与治理建立之间若存在时间差，这段"治理真空期"的约定会散落丢失。

## 解决方案（功能完成即治理建立）

### 四个动作

1. **功能模块完成后第一时间建立 AGENTS.md 入口**
   - 与功能代码同批次交付，不留治理真空期
   - 入口文档声明模块职责、关键约束、使用方式，让维护者/智能体首屏可理解

2. **规则文件按单一职责原子化拆分**
   - 按关注点拆分（如 `build-orchestration` / `testing` / `conventions`），而非塞进单个大文件
   - 每个规则文件聚焦一件事，便于复用与演进

3. **嵌套路由从根级到模块级清晰定义加载顺序**
   - 从根 AGENTS.md → 区域入口 → 子模块，逐级定义加载顺序
   - 每一级都明确"进入该级后应读什么"

4. **父级路由表同步更新，确保路由链不断裂**
   - 新增子模块时同步更新父级路由表，加入新入口
   - 保证任意节点都能沿路由链到达目标，避免"子模块有文档但父级找不到"

## 反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 功能完成很久后才补治理层 | 治理真空期约定散落丢失，维护者靠猜测理解 | 与功能同批次立即建立治理层 |
| 规则塞进单个大文件 | 规则耦合难复用、难演进 | 按单一职责原子化拆分 |
| 只建子模块入口不同步父级路由 | 路由链断裂，父级找不到子模块 | 父级路由表同步更新 |
| 治理层只写代码不写约束约定 | 维护者理解不到"为什么这么设计" | 入口文档声明职责+约束+使用方式 |

## 迁移验证

本模式可迁移到以下场景：
- ✅ 新增功能模块/构建体系/子应用交付时
- ✅ 需要 AI 智能体按路由装载模块规则的仓库
- ✅ 多子模块嵌套的治理体系（app/project/vendor 分层）
- ✅ 团队交接、新成员 onboarding

- [ ] 功能模块完成后已第一时间建立 AGENTS.md 入口（同批次交付）

- [ ] 规则文件已按单一职责原子化拆分
