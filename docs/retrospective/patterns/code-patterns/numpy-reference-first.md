# Numpy参考实现先行

## 触发场景

- 当编写数值计算层/算子的正确性测试时
- 当需要验证深度学习框架前向/反向计算正确性时
- 当担心"测试代码本身写错"导致错误期望时
- 适用于：所有涉及浮点数值计算的单元测试、算子验证、跨框架一致性测试
- 不适用于：纯结构测试（如图拓扑、命名检查）、错误路径测试、性能基准测试

## 核心做法

1. **参考实现先行**：在编写C++/目标框架测试代码之前，先用numpy实现该算子的纯Python参考版本
2. **独立验证参考**：用简单已知值（手算可验证）测试numpy参考实现本身的正确性，确认参考是对的
3. **最小化参考实现**：numpy参考只实现核心逻辑，不包含框架特定的参数处理/内存管理/性能优化
4. **双路对比**：使用相同输入分别运行numpy参考和目标实现，用`np.allclose`对比输出
5. **覆盖所有分支**：参考实现应与目标实现有相同的分支逻辑（如不同pool_type、不同axis）
6. **保留参考函数**：将numpy参考函数保留在测试文件顶部，作为文档和未来调试参考

## 反模式（不要这么做）

- ❌ **反模式1：直接写C++测试**：不写numpy参考，直接凭直觉在测试中写期望值。后果：测试和被测试代码可能犯同样的逻辑错误（如P3-B中Accuracy手动计数错误）
- ❌ **反模式2：参考实现过度复杂**：在numpy参考中复刻框架的所有边界处理/内存布局/性能优化。后果：参考实现本身容易引入bug，失去"独立基准"价值
- ❌ **反模式3：不验证参考正确性**：写完numpy参考直接用，不先用简单已知值验证。后果：参考本身有错，导致所有后续测试都在验证"错误的正确"
- ❌ **反模式4：用目标实现的输出反推期望值**：跑一次目标实现，把输出作为期望值硬编码。后果：这不是测试，是快照，实现错误时测试也会通过

## 失败案例

### 案例：caffe-ffi P3-B里程碑Accuracy层测试错误（2026-07-31）

**背景**：caffe-ffi P3-B测试里程碑中，需要验证Accuracy层的top-k精度计算正确性。

**错误做法**：
1. 开发者直接在C++测试中手动编写top-k计数逻辑，硬编码expected = 0.75
2. C++实现也采用了类似的手动比较计数逻辑
3. 测试通过了，开发者以为Accuracy层实现正确

**问题爆发**：
- 后续添加Python端测试时，用numpy实现了参考的top-k计数
- numpy参考给出的结果是0.625，与C++测试期望值不一致
- 深入排查发现：C++测试和C++实现**犯了完全相同的逻辑错误**——在处理多标签top-k时重复计数了同一类别的预测
- 两个错误相互抵消，导致"测试通过但实现错误"的假阳性

**修复与教训**：
- 用numpy参考版本作为基准，修正了C++实现中的计数逻辑
- C++测试改为对比numpy参考输出而非硬编码值
- 后续所有算子测试强制要求先写numpy参考

**根本原因**：没有独立参考基准时，测试代码和实现代码容易共享相同的心智模型缺陷，导致"错错得对"的测试假阳性。

## 不适用场景/反目标用户

本模式虽然价值明确，但并非所有测试场景都适用。以下三类场景强行使用numpy参考先行反而会降低效率或引入问题：

### 1. 纯结构性/拓扑测试（反目标场景）

**特征**：测试目的是验证网络结构、层命名、blob连接、参数解析，不涉及数值计算。
**例子**：
- 验证prototxt解析后层名正确
- 验证blob的top/bottom连接关系
- 验证参数shape推断（如Conv输出shape）
- 验证错误路径（非法参数是否抛出异常）
**为什么不适用**：这些测试的预期结果要么是确定的结构属性，要么是异常，没有浮点数值对比需求。numpy参考在这里没有额外价值，反而增加代码量。

### 2. 性能基准测试（反目标场景）

**特征**：测试目的是测量吞吐量、延迟、内存占用，而非验证数值正确性。
**例子**：
- Forward/Backward的QPS基准测试
- 不同batch size下的延迟曲线
- COW启用前后的内存占用对比
**为什么不适用**：性能测试关注的是"跑多快"，numpy参考是Python实现，速度慢几个数量级，作为基准没有意义。性能测试应该在正确性验证通过后单独进行。

### 3. 已有可信黄金参考的场景（反目标场景）

**特征**：目标是对比已有成熟框架的行为，该框架输出本身就是可信基准。
**例子**：
- PyTorch算子→TensorRT部署一致性验证（直接以PyTorch输出为基准）
- 旧版caffe→新版caffe-ffi迁移验证（以旧版输出为基准）
- ONNX Runtime→自定义实现对比（以ORT输出为基准）
**为什么不适用**：此时"参考实现"已经存在（旧版/其他框架），重写numpy参考是重复劳动。应该直接用现有框架输出作为基准，但仍需遵循"已知值验证基准正确性"原则。

### 4. 边界适用：极简单算子（灰度场景）

**特征**：算子逻辑极其简单，1-2行代码，数学上不可能写错。
**例子**：
- Identity层（output = input）
- 简单的标量乘法（y = alpha * x）
- Dropout inference模式（直接pass-through）
**建议**：这类算子可以只写2-3行简单numpy参考（甚至一行lambda），不必完整遵循五步骤流程，但仍应保留参考作为文档。

## 早期预警信号

当出现以下信号时，说明你的测试可能需要引入numpy参考实现先行模式：

| # | 预警信号 | 说明 |
|---|---------|------|
| 1 | 测试中硬编码超过3个浮点期望值 | 手动推导浮点结果容易出错，应改用numpy生成 |
| 2 | 发现bug时第一反应是"是测试错还是实现错？" | 没有独立基准时无法快速定位问题来源 |
| 3 | 同一个算子的测试被反复修改expected值 | 说明期望值是"调"出来的而非"算"出来的，缺乏独立基准 |
| 4 | 测试代码和实现代码有相似的循环/计数逻辑 | 两者可能共享相同的心智模型bug |
| 5 | 代码审查时无法快速验证测试期望值的正确性 | 审查者无法心算验证时，需要可运行的参考实现 |
| 6 | 新增算子测试前先写prototxt而非Python参考 | 违反了"参考先行"的核心原则 |
| 7 | 对比两个框架的输出时差异来源无法解释 | 缺少numpy中间参考层来定位差异发生在哪一步 |

## 前提条件与适用边界

使用本模式前需确认：
- ✅ 团队成员熟悉numpy数组操作（否则参考实现本身成为负担）
- ✅ 算子逻辑可以用纯Python/numpy在合理时间内实现（<50行代码）
- ✅ 测试运行时间可接受（numpy参考比C++慢10-100倍，但单元测试规模下可接受）
- ✅ 不需要精确到bit-exact的浮点一致性（np.allclose允许rtol/atol误差）
- ❌ 如果算子涉及大量C++专有优化（如in-place操作、自定义内存布局），参考实现需要额外适配成本

## 检验标准

做完之后怎么知道做对了？
- 标准1：测试文件顶部有清晰的numpy参考函数，有docstring说明参数和返回值
- 标准2：numpy参考函数本身有简单已知值的验证（如1x1卷积、identity case）
- 标准3：所有数值断言都通过`np.allclose(actual, expected_np, rtol, atol)`而非硬编码
- 标准4：发现bug时，能通过对比numpy输出来快速定位是参考错还是实现错
- 标准5：新增算子测试时，第一个写的是numpy参考而不是prototxt

## 迁移示例

这个模式还能用在什么其他场景？
- 场景1（跨框架验证）：PyTorch算子→TensorRT部署验证，先用PyTorch写参考，再对比TensorRT输出
- 场景2（数据库查询）：复杂SQL聚合查询，先用pandas在内存DataFrame上实现参考逻辑，再对比SQL结果
- 场景3（编译器优化）：新的编译优化pass，先用Python实现未优化的参考解释器，再对比优化后输出
- 场景4（信号处理）：C++实现的FFT/滤波器，先用scipy/numpy实现参考版本对比输出
- 场景5（金融计算）：量化策略的C++实现，先用numpy/pandas在历史数据上验证参考逻辑正确性
