# 单元测试驱动Bug发现与修复闭环模式（测试即修复）

## 触发场景

- 为已有代码（尤其是脚本/解析器）补充单元测试，但代码只测试过"正常路径"
- 遇到以下任一痛点：
  - 运行时才会暴露的 Bug 在测试前未被发现，上线/构建才爆
  - 测试数据只覆盖一种输出格式，遗漏其他格式变体导致解析错误
  - 发现 Bug 后测试与修复脱节，反复出现同一问题
  - 测试脚本本身质量无人审查，测试数据漂移

**适用于**：解析器/格式化器/日志提取器、CLI 脚本、构建流水线的核心函数单元测试、"为已有代码补测试"场景。
**不适用于**：无需解析边界、逻辑极简的一次性脚本。

## 问题本质

代码编写时只关注"正常路径"，而**解析边界（多个代码路径的交汇点）最容易遗漏**。例如 final stage 的计时输出与 wrapper 的总构建时长输出是两个代码路径的交汇点——正常路径各走各的，交汇点才暴露格式不一致。测试编写时才被迫关注这些边界，因此补测试本身就是发现 Bug 的契机。

## 解决方案（测试即修复闭环）

### 核心闭环：为每个核心函数编写不依赖运行环境的单元测试

```bash
# 1. 从源脚本动态提取核心函数（不依赖 Docker，测试可在任意环境跑）
#    source build.sh 后调用 parse_timer_logs()，但先拦截 echo 输出
# 2. 构造 mock 数据覆盖所有输出格式变体
# 3. 运行测试 → 发现 Bug → 修复 → 更新 mock → 全部通过
```

### 四步操作

1. **为每个核心函数编写不依赖运行环境的单元测试**
   - 从源脚本动态提取函数（source 后调用），避免复制粘贴导致测试与实现脱节
   - 断言针对纯函数输入/输出，不依赖 Docker/网络/系统状态

2. **使用 mock 数据覆盖所有输出格式变体（而非只测一种）**
   - 覆盖多变体格式（如 conda 与 conda-llvm 两种 Dockerfile 计时格式）
   - 覆盖边缘情况（空输入、缺字段、异常格式）
   - 每种变体一个独立 mock 用例

3. **测试脚本本身也作为代码审查对象**
   - mock 数据需与真实输出格式持续对齐，防止测试"假通过"
   - 测试脚本纳入 git review，作为 CI 门禁的一部分

4. **发现 Bug 后立即更新 mock，形成"发现→修复→验证"闭环**
   - 先复现（mock 触发失败断言）→ 定位根因 → 修复 → mock 通过
   - 修复后保留该用例作为回归防护，防止问题复活

## 反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 只测一种输出格式 | 其他格式变体解析错误遗漏，运行时才暴露 | mock 覆盖所有格式变体 + 边缘情况 |
| 测试依赖运行环境（Docker/网络） | 测试无法在无环境处快速回归，反馈周期长 | 为纯函数写不依赖环境的单元测试 |
| 复制粘贴函数到测试而非动态提取 | 测试与实现脱节，实现更新后测试仍测旧逻辑 | 从源脚本 source 后动态调用 |
| 发现 Bug 后不更新 mock | 修复无法被验证，问题可能复活 | 立即更新 mock 形成闭环 + 回归防护 |
| 测试脚本不审查 | mock 数据漂移，测试假通过 | 测试脚本纳入代码审查与 CI 门禁 |

## 迁移验证

本模式可迁移到以下场景：
- ✅ 为已有脚本/解析器补充单元测试
- ✅ 构建流水线的日志/计时/格式解析函数测试
- ✅ 任何"为既有代码补测试以发现隐藏 Bug"的场景
- ✅ CI 门禁中的轻量单元测试层（L0，无环境依赖）

## 检查清单

- [ ] 已为每个核心函数编写独立单元测试，且不依赖运行环境
- [ ] mock 数据已覆盖所有输出格式变体 + 边缘情况（非仅一种）
- [ ] 测试函数从源脚本动态提取，而非复制粘贴
- [ ] 已检查测试脚本本身质量并纳入审查
- [ ] 发现的每个 Bug 均已走完"发现→修复→更新mock→验证"闭环
- [ ] 修复后的用例已作为回归防护保留
