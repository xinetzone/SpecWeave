# 运行时数值金标准模式（Runtime-Numerics-Golden-Binary）

## 背景与动机

涉及**厂商/上游预编译 C/C++ 运行时**（模拟器、编译后端、NPU/GPU runtime、FFI 扩展等）的项目，本地往往具备源码与 Makefile，理论上"同源码重建"应得到等价二进制。但当本地构建环境（编译器版本、宏集合、构建参数、基础提交）与发布方不一致时，**重建产物可能出现数值性差异**——例如同一网络图推理的 `conv1` 输出恒为 0（cos=0），而官方二进制为 0.99998。

本地重建与官方二进制数值不一致时，肉眼可见的"跑通"（无 crash、无报错）极具欺骗性：全部节点正常 dump、耗时正常，但**每个数值都是错的**。

> **反常识**：编译型工具链里"同源码重建"≠"数值等价"。crash 类缺陷（如 split error）用"是否跑通"即可判定；**数值类正确性必须以官方发布二进制为金标准做同图对照**，本地重建的"能跑"不能作为交付证据。

本次复盘的直接证据（R2 对照实验表）：同一官方图分别跑官方二进制与本地重建二进制，官方 `conv1` 余弦 0.99998，重建版恒为 0——源码、图、量化全相同，唯一变量是二进制本身。

---

## 触发场景

- 需要修复/增强某个厂商或上游预编译运行时（C/C++），本地重建后准备替换发布产物
- 修复后"功能上跑通"（不再 crash），但精度/数值指标异常或需要基准验证
- 本地构建环境（gcc/宏/基础 commit）与发布方不一致，且无法获得官方 CI
- 推理/仿真/编译器类工具链，数值正确性无法用"是否报错"判断

**不适用于**：
- 纯 Python / 解释型代码（源码即产物，无重建差异）
- 二进制仅作传递搬运（不修改源码，不重建）
- 有官方 CI 可一键重建并跑通数值回归的场景（直接用官方产物）

---

## 核心步骤

1. **固定金标准**：替换前把官方/发布二进制备份到独立目录（含可回溯路径），记录其内嵌版本指纹（编译日期、嵌入 git commit、`--version` 等）。
2. **固定对照图**：取一份**同一个**已发布网络图（network + param + 运行日志/调度文件），分别用官方二进制与重建二进制推理。
   - 变量只能有一个：二进制。图、量化配置、输入、调度日志全部冻结。
3. **数值比对**：对关键中间节点计算余弦/MSE 等指标；以官方二进制结果为零点。
4. **判定与归因**：
   - 若同一图下重建版指标显著劣化 → 二进制差异，先查**基础提交**（内嵌 git hash → `git log -- <路径>` 看源码增量），再查编译器/宏/构建参数；不要先怀疑图与量化。
   - 若官方二进制本身在该图上 crash/异常 → 该能力可能本就不支持，先查**能力矩阵**（平台×量化/数据类型约束），再决定修哪一侧。
5. **不交付劣化产物**：数值不通时回滚官方产物；把源码修复以 patch/commit 形式交付官方构建；保留可复现实验脚本与对照日志作为移交证据。

---

## 反模式（不要这么做）

- ❌ **本地重建成功即替换发布产物**：不跑数值对照就上线，可能静默引入全链路数值错误
- ❌ **用"不再 crash / 能跑通"作为唯一验收**：crash 消除与数值正确是两个独立维度
- ❌ **跨图、跨平台、跨量化配置做"等效"对比**：变量不冻结，无法归因（应固定图×换二进制、固定代码×换平台分开做）
- ❌ **只比对时间戳/大小**：二进制大小接近不等于数值等价；数值差异常由编译器/宏引起，必须跑指标
- ❌ **把"同源码"当结论而非假设**：须核对二进制内嵌 git hash/编译日期与本地树是否一致（本次官方产物内嵌 commit 与本地 HEAD 相差多个提交，是归因关键线索）

---

## 检验标准

- 同一冻结图下，重建二进制与官方二进制的关键节点指标一致（如余弦≥官方×0.9999）
- 替换前官方二进制已备份，备份路径与恢复记录可审计
- 若数值不通：已产出"官方备份已恢复 + 源码 patch 已交付 + 对照实验证据"三件套
- 归因记录区分了"图/量化问题"与"二进制问题"（通过单变量对照证明）
