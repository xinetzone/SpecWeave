# 生成-登记同步法（Nav Co-Registration Pattern）

## 模式概述

**本质公理**：在"内容产物"与"消费入口"分离的系统中，**存在 ≠ 可达**——文件/实例/接口只有同步注册到消费侧的导航层（文档的 toctree/索引表、微服务的注册中心、路由表、插件清单），才对消费者可见。生产侧的生成能力与消费侧的注册行为必须保持**事务性同步**：同生、同灭、同改。

**术语速查**（新人视角）：
- **导航登记层**：让读者/构建器"找得到内容"的元数据层。Sphinx 文档中即 toctree（目录树指令）与索引表；等价物包括服务注册中心、路由表、插件入口清单。
- **门禁增量**：一次变更引入的新问题数（区别于存量问题总量）。验收只看增量，存量另行建账。
- **未收录（不可达）**：文件物理存在但未被任何导航条目引用，读者经正常导航路径无法到达。

该模式从 docs 文档中心全量审计（3,491 文件、2,245 处导航问题）的失败侧证据萃取：内容生产已规模化批量生成，而导航登记仍依赖手工跟随，两者速率失配形成随内容量线性增长的结构性债务。

## 触发场景

**适用于**：
- 批量生成结构化内容（知识包、Wiki、报告、代码骨架）且内容需通过导航层（toctree/索引表/注册表）才能被消费的场景
- 一次生成 ≥10 个文件，或导航层级 ≥2 级（此时手工漏登记概率显著上升，机制成本低于漏登记成本）
- 具备可机器执行的导航门禁（断链/未收录可脚本检出）的工程体系

**不适用于**：
- 单文件手工创作（登记成本高于机制成本）
- 导航层与内容同文件自包含的场景（如单页应用、单文件报告）
- 导航由文件系统自动发现（autogenerate）且无手工注册环节的系统——此时同步义务由生成器内部保证，本模式退化为生成器自身的正确性测试

## 核心做法（5 步）

1. **清单随变更**：生成管线的输出除内容文件外，必须附带"导航登记清单"，且清单覆盖文件的**全生命周期**——每个新增文件对应一条注册条目（toctree 条目/索引表行/注册表记录），每个删除文件对应一条**注销**条目，每个移动/重命名文件对应一条路径更新条目。登记清单是管线的强制产物，不是可选附件。

2. **幂等登记**：变更完成后立即执行登记脚本，幂等追加（已存在条目跳过）。脚本内置"目录 → 登记位置"归属映射（决定每个文件登记到哪一级导航，防止只登记顶层、漏登记层级）；**无法判定归属的条目必须进入人工队列并留痕，禁止静默跳过**；禁止绕过脚本手工散点修改索引。

3. **门禁伴随**：登记后立即运行导航门禁（如 [check-toctrees.py](../../../../scripts/check-toctrees.py)），以"**本次变更引入的问题增量 = 0**"为硬放行条件。门禁作为管线拦截器自动执行，登记正确性由机器校验而非人工审查兜底。

4. **原子交付**：内容文件与登记变更合并为一次原子提交，禁止"内容先提交、登记后补"——后补不会发生（见反模式 AP-1）。

5. **增量验收**：交付验收标准写入门禁增量（本次引入的导航问题数 = 0；注销条目与删除文件一一对应），**而非门禁总量**。存量债务另行建账分流清理，不阻塞增量验收（见"落地路径"）。

## 反模式（4 个，均来自实际案例教训）

### AP-1：内容先行导航后补

- **来源**：docs 全量审计 F-012——2,187 个文件未收录（不可达）
- **表现**："内容先产出，导航回头再登记"
- **后果**："回头"不会发生——未收录债务随每批生成线性累积，2,187 个文件存在但读者经导航不可达
- **正确做法**：步骤 1+4，登记清单与内容同批原子交付

### AP-2：只登记顶层不登记层级

- **来源**：docs 全量审计 F-017——learning 下 10 个编号目录整体不在 toctree 中
- **表现**：只更新上级索引（如 knowledge/index.md），不更新下级索引（learning/index.md）的导航条目
- **后果**：整目录内容不可达，且顶层门禁/人工巡检不易发现——断链报错，沉默的不可达不报错
- **正确做法**：步骤 2 的归属映射必须覆盖每一级导航，门禁从根索引做全链路可达性校验

### AP-3：门禁报警不灭火

- **来源**：docs 全量审计 F-010/F-013/F-031——门禁合计检出 3,849 处问题但无修复提交，log.md 无修复记录
- **表现**：门禁只在事后 CI 拦截/报警，检出结果没有对应的修复行动流
- **后果**：门禁结果退化为被忽略的背景噪音；30 条 Sphinx 警告曾被集中清零（F-026）证明修复能力存在，缺的是"检出 → 台账 → 批量修复 → 复验归零"的闭环管道
- **正确做法**：门禁前移为生成时伴随校验（步骤 3）；存量问题建台账分批消费，每批复验归零并留痕

### AP-4：只注册不注销

- **来源**：docs 全量审计 F-011——7 处断链全部位于 docs-separation-guide，注册条目残留但目标文件缺失
- **表现**：删除/移动文件时只处理内容侧，不清理导航侧的注册条目
- **后果**：导航断链——等价于微服务下线后不注销，流量继续路由到死实例
- **正确做法**：步骤 1 的清单覆盖删除/重命名场景，注销条目与文件变更同批提交

## 检验标准

- [ ] **增量归零**：生成任务完成后运行导航门禁，本次变更引入的问题增量 = 0（断链、未收录均为 0）
- [ ] **全链路可达**：任一新生成文件可从根索引经导航链路到达；任一删除文件无残留注册条目
- [ ] **无静默跳过**：归属映射无法判定的条目全部进入人工队列并有处置记录
- [ ] **导航可消费**：批量生成物配有聚合索引页（分组/摘要），导航层不平铺膨胀——登记是手段，可发现性才是目的
- [ ] **最小示例（Hello World）**：新增 1 个文件 → 门禁报 1 处未收录 → 登记脚本按归属映射自动补录 → 重跑门禁增量归零 → 内容与登记一次提交完成

## 落地路径

**路径 A：新建管线接入（一步到位）**
在生成管线末尾增加登记步骤 + 门禁增量硬拦截，此后每批生成都满足"增量 = 0"。

**路径 B：存量债务清理（分流消费，不要求一次清零）**
1. 先修断链（确定性最高、量最小，等价于先注销死条目）
2. 批量生成物用登记脚本按归属映射自动补录
3. 手写文档人工核对后补录
4. 每批修复后复验门禁、在变更日志留痕
存量清理期间，新模式义务只管增量；路径 B 的首批执行本身即构成本模式的首次正向验证。

## 跨场景迁移示例

| 领域 | 内容产物 | 导航登记层 | 本模式对应 |
|------|---------|-----------|-----------|
| 微服务治理 | 服务实例（容器启动） | 服务注册中心 | 启动即注册；**下线必须注销**（健康检查/自动摘尸等价于步骤 1 的注销清单），否则流量打到死实例——即"文件存在但 toctree 不可达"的同构问题 |
| API 工程 | 生成的接口实现 | OpenAPI 路由表 | 生成接口必须同步注册路由，否则接口存在但流量不可达 |
| 插件系统 | 插件产物 | 插件入口清单（manifest） | 插件必须同步注册入口，否则不被宿主加载 |

**反例边界**：单页应用、单文件手工报告等"内容与入口自包含"场景无需此模式；注册机制本身会随技术演进变化（如 autogenerate 自动导航），但"生产侧产物与消费侧注册表事务性同步"的原则不变。
