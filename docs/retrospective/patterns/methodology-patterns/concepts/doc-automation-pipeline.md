# 文档自动化生成与验证流水线模式（Doc Automation Pipeline）

> **简称：文档流水线模式**（G3 传播名，4-8 字场景使用）。

## 模式概述

**本质洞察**：文档规模扩大后，**瓶颈不是内容创作，而是索引维护与链接保真**——当文档条目达到数百量级（本项目经验阈值约 500，**该数字为经验断言而非测量值**，真实拐点随条目交叉引用密度与变更频率变化），人工维护索引、导航、链接既不准确（易断链）也不可持续（维护成本随条目数近似线性增长）。本模式以"统一元数据规范 + 自动化脚本生成 + 链接/索引验证门禁"构成生产流水线，用机器替代高频重复劳动，让人专注于内容创作。

**不变内核**：机器生成物必须有机器可执行的验证契约——"元数据契约 + 自动生成 + 门禁验证"三位一体。README/索引等具体产物形态会随工具演进（例如 AI 按需生成可能替代部分固定索引），但"凡机器生成必有契约校验、凡入库必过门禁"的内核不变。迁移时应迁移内核而非照搬具体脚本。

该模式从 SpecWeave 智能文档系统里程碑（2026-07-01 ~ 08-31）萃取：docs/ 承载 1000+ Markdown 文件、1288 条知识库条目、380+ 模式，通过 generate-readme.py（模板生成与自动索引）、check-links.py（断链检查）、generate_index.py 系列（索引生成）等脚本支撑规模化。

## 触发场景

**适用于**：
- 文档规模达到数百条目（经验阈值约 ≥500，**非测量值**，以"人工一轮全量索引维护已无法在一次工作会话内可靠完成"为真实判据），或目录数持续增长（本项目实测 589 个含 md 目录）
- 需要批量维护索引/链接/导航（README 补全、标签分片、分类索引）
- 团队协作产出多份文档，需要统一的元数据与质量基线
- 存在可机器执行的验证门禁（断链/格式检查）的工程体系

**不适用于**：
- 单篇文档、条目数 <100、无索引维护需求的场景（全流水线投入产出比低）
- 一次性的临时文档（无长期维护诉求）
- 无 CI/脚本执行环境的纯本地单机场景

> **最小起步（化解"≥500 才适用"与"尽早建设"的矛盾）**：本模式各组件成本不同，不必等到拐点才全部上马。**元数据规范（步骤 1）从第一篇文档就值得建立**——此时成本极低、后期补全成本极高；脚本化（步骤 2-4）随规模分批投入；强制门禁（步骤 5）在团队协作或条目破百后再启用。即"规范先行、脚本随行、门禁后立"。

## 核心步骤（5 步）

1. **建立统一元数据规范**：为每个文档定义 YAML frontmatter（title/type/source/date 等），作为后续脚本与门禁的共同输入契约
2. **配置模板生成脚本**：开发/接入 README 生成脚本（如 generate-readme.py），支持模板生成（Strategy B）与自动索引（Strategy C）两种模式，覆盖"目录说明 + 目录索引"双重需求
3. **建立链接验证脚本**：接入 check-links.py 类工具，在提交前自动检查本地引用/断链/锚点，将链接保真从人工抽查转为全量机器扫描
4. **建立索引生成脚本**：接入索引生成脚本（generate-knowledge-index.py / generate-categories.py / generate-nav.py 等），批量更新分类索引、标签分片与导航表
5. **设置质量门禁**：分两层接入产出流程，不合格即返工——
   - **通用机器门禁（任何文档体系适用）**：链接有效性（断链/file 绝对路径）、元数据契约（必填 frontmatter 字段）、格式规范、覆盖率基线
   - **内容类型专用门禁（按产物类型选配）**：方法论产出可挂"事实无因果词→洞察四元组→模式可迁移→行动项原子化"类语义门（SpecWeave 实例为七概念 G1-G4）；普通技术文档则挂术语一致性、代码示例可运行等检查。**迁移时只照搬通用层，专用门按自身产物类型重新定义**

## 反模式（请勿这样做）

❌ **人工维护大规模索引**：规模达到数百条目后人工索引必然产生遗漏与漂移，维护成本近似线性增长且不可审计

❌ **跳过验证直接发布**：不跑链接检查就提交，断链/格式不一致随批次累积；实测该项目曾一次修复 481 个断链、批量修复 26 个文件 file:/// 绝对路径

❌ **脚本与文档分离**：脚本产出文档后不关注脚本演进，脚本更新后输出未同步（如 generate-readme.py 里程碑时点 690 行 vs 创建时 1221 行，版本漂移产生口径不一致）

❌ **多生产者无单一事实源（契约漂移）**：同一份索引/导航同时存在"脚本生成"与"手写 Hub"两个生产者且口径不同源，一次全量重生成即大面积断链。实测教训：generate_index.py 产出与手写 toctree Hubs（categories/index.md、tags/index.md）口径分叉（1288 旧快照 vs 248 现状、旧分片仍被 toctree 引用），重生成后断链，修复涉及 39 个文件（2026-09-11，提交 53a82f8c3）。正确做法：每个派生产物只允许一个生产者，手写 Hub 必须从生成器派生（或显式声明边界并纳入同一契约检查），参见关联模式 [导航共注册](nav-co-registration.md)

❌ **自动化脚本自身无测试护栏**：脚本替代了人工，但脚本的 bug 会被批量放大到所有生成物——无单测、无 dry-run、无幂等复验的"自动化"只是把错误规模化。实测教训：A2 执行中发现 generate_index.py 目录迁移后路径缺陷（提交 c6b98309d）。生成脚本应配最小单测与"重复执行结果不变（幂等）"复验

## 检验标准

- [ ] **0 断链**：全量扫描本地引用 0 断链（新变更引入增量 = 0）
- [ ] **README 覆盖率目标**：目录 README 覆盖率向 100% 收敛（当前基线：含 md 目录 589 个中 109 个缺失，作为待偿债务而非已达成事实）
- [ ] **索引更新延迟**：索引生成脚本单次执行 <1 小时，增量更新即时生效
- [ ] **门禁自动化**：验证门禁可嵌入提交前流程（CI/预提交脚本），不依赖人工自觉
- [ ] **单一事实源**：每个派生产物（索引/导航/README）只有一个生产者；手写 Hub 与脚本生成物无口径分叉；生成脚本重复执行结果幂等（连跑两次无 diff）

> 注意（V 阶段校验）：覆盖率类标准应表述为"目标标准"而非"已达事实"——是否达成需以实测为准并记录基线。

## 落地路径

- **路径 A（新文档系统）**：从第一个文档开始就建立元数据规范（低成本先行），脚本骨架随条目增长分批补齐，让流水线与内容同步生长
- **路径 B（存量文档系统）**：先跑全量审计建立基线（断链数/覆盖率/索引缺失），再分批清偿：优先修复断链（确定性高）→ 补齐 README（模板生成批量）→ 统一索引（最后做，须先确定单一生产者）；每批修复后复验门禁并留痕

> **成本提示**：自动化脚本本身是需要维护的资产——脚本会随目录迁移、口径调整而腐化，其 bug 经批量执行放大。建设脚本时同步配最小单元测试、dry-run 预览与幂等复验；无测试护栏的宁可以小规模脚本起步，不要一次性铺开全自动流水线。

## 跨场景迁移示例

| 领域 | 内容产物 | 自动化组件 | 验证门禁 |
|------|---------|-----------|---------|
| 开源项目文档 | 项目 Wiki/README | mdbook/Sphinx 自动索引 | 断链检查 CI |
| 技术知识库 | 教程/知识包 | 索引生成脚本 | 元数据格式校验 |
| 产品手册 | 多版本手册 | 模板生成器 | 内容完整性检查 |
| 数据仓库 | 数据目录/血缘文档 | 元数据同步脚本 | 引用一致性检查 |
| 企业 ISO 9001 质量体系（非软件域） | 程序文件/SOP/作业指导书 | 编号元数据 + 模板发放 + 受控文件清单生成 | 过期版本回收检查、引用文件现行有效性校验、发放记录一致性 |
| 医疗机构/合规文档库（非软件域） | 制度/规程/知情同意书模板 | 模板库 + 版本索引 | 废止文件残留扫描、法规引用时效检查 |
