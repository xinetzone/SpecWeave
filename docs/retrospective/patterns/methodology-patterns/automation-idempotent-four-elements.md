# 自动化幂等四要素

## 触发场景

- 当编写"部署 / 启用 / 验证"类操作脚本（环境初始化、插件安装、依赖引导、CI 引导）时，使用这个模式
- 适用于：一键安装脚本、环境引导、配置启用、CI 初始化
- 不适用于：一次性不重复执行的任务、纯只读查询（无副作用风险）、需要人工决策的复杂编排

## 核心做法

把自动化流程建模为「面向结果」的原子命令，而非复刻手动步骤：

| 要素 | 名称 | 说明 | 关键标准 |
|:---:|------|------|---------|
| E1 | 面向结果建模 | 抽象为「装好 install」与「确认装好 verify」两个结果命令 | 每个子命令对应一个可判定的结果 |
| E2 | 幂等 | 重复执行无副作用、不重复注入/覆盖 | 二次运行输出 already-xxx 且配置不变 |
| E3 | 备份可回滚 | 改写任何配置前先备份 | 存在 config.bak-<ts>，可一键还原 |
| E4 | 声明式常量 + 可判定 verify | 插件名/路径/关键词集中声明；verify 输出机器可读 + 退出码 | 单点修改，verify 有 PASS/FAIL + 退出码 |

**执行要点**：

1. **面向结果而非复刻步骤**：人脑要 4 步，本质只需"装好"与"确认装好"两个结果——不要逐条复刻手动命令。
2. **幂等是生命线**：重复执行不产生副作用，否则自动化比手动更危险。
3. **改配置前备份**：对用户既有配置文件做最小侵入（仅追加缺失项），改写前备份可回滚。
4. **保留注释与无关配置**：用行级最小编辑而非整体重写 YAML/TOML，避免破坏用户注释与迁移机制。
5. **verify 输出双格式**：人读（PASS/FAIL）+ 机器读（JSON），并设置退出码供 CI 判定。

## 为什么需要这个模式

**解决"自动化比手动更危险"的悖论**：一次性的手动操作即使出错也可回退，而自动化脚本会在每次运行时以同样方式破坏配置。幂等 + 备份 + 可判定是把"自动化"从高风险工具变成"可靠工具"的三道保险。

**让自动化可纳入 CI 门禁**：只有脚本提供可判定的退出码与 verify 通道，才能作为 CI 前置检查或安装后校验被可靠调用，否则无法断言成功。

**最小侵入保护既有配置**：用户配置文件常含注释、迁移版本号、无关选项。整体重写会破坏这些内容；行级最小编辑 + 备份是保护用户资产的正确粒度。

## 反模式（不要这么做）

- ❌ **复刻手动步骤**：脚本逐条模仿人敲的命令——无法判断结果，失败点不可定位
- ❌ **重写整个配置文件**：读取→重排→整体写出——破坏用户注释与迁移机制，格式漂移
- ❌ **无备份直接改**：改配置前不备份——出错后无法回滚，用户资产不可逆
- ❌ **无 verify 判据**：装完没有"是否生效"的判定——成功与否不可断言，无法进 CI
- ❌ **硬编码散落**：插件名/路径/关键词散落各函数——换名/换路径要全局改，易漏

## 检验标准

做完之后怎么知道做对了？

- **标准1（幂等）**：连续运行两次，第二次输出 already-xxx 且配置未被二次修改
- **标准2（可回滚）**：存在 `config.bak-<ts>` 备份，误改后可一键还原
- **标准3（可判定）**：verify 输出人读 PASS/FAIL + 机器读 JSON，退出码 0/非 0 可判定
- **标准4（最小侵入）**：仅追加缺失项，用户原有注释与无关配置保留
- **标准5（常量集中）**：插件名/路径/关键词集中声明，单点可改

## 迁移示例

这个模式还能用在什么其他场景？

- **场景1（环境初始化）**：新机器引导脚本（安装依赖 + 配置环境变量 + 验证），幂等可重跑
- **场景2（插件安装器）**：任何 Agent 平台的插件安装器（部署 + 启用 + 校验），支持反复执行
- **场景3（CI 引导）**：CI 前置检查脚本（装工具 + 验证版本 + 退出码判定），纳入流水线门禁
- **场景4（配置迁移）**：配置文件结构升级脚本，备份旧版 + 幂等迁移 + 校验新结构
