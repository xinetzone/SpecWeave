# 缺口双轮核验法（公开信源轮+零变更功能轮 Gap Two-Round Verification）

## 模式类型

方法论模式（研究尽调/证据质量流程）

## 成熟度

L1-draft 假设级（单案例：openKylin 全面评估 Q-1~Q-8 缺口核验，2026-10-14；首日首轮公开信源+傍晚二轮功能实测，关闭/部分关闭/证伪 8 个缺口，新增 61 条带 URL 事实。待第二个非同谱系案例验证后升级 L1.5/L2）

## 适用边界

- **适用于**：公开信息可得的选型/竞品/尽调类缺口；判断「能力/政策/数据是否客观存在」的事实型问题；复现成本高、需快速关闭清单的场景。
- **不适用于**：①性能/容量/时延类问题（供给侧文件证明不了真实表现，必须基准测试，功能轮不可省）；②纯主观体验（可用性、美观度、音色自然度）；③仅组织内部可查的事实（私有仓、内部系统、合同价格），应直接取内部权威源；④需长期观察的稳定性结论（崩溃率、MTTR 需时间窗数据，一次只读冒烟不可替代）。
- **与配套模式分工**：规模数字「能不能信」用社区指标三查法；缺口清单「怎么关闭」用本模式。

## 问题陈述

严肃评估报告交付时，几乎必然带着一份「这次没拿到的东西」清单。对这份清单的处置质量，决定报告的可决策性。常见失败形态：

1. **访问失败误判为事实不存在**：页面 403、API 500、需要特定 UA/网络环境，被直接写成「无公开数据」。本案例中 DistroWatch 在默认环境 403，换浏览器 UA 后 HTTP 200，拿到 6 个月排名 #107。
2. **复刻用户路径作为默认核验手段**：要验证「能否跨版本升级」，第一反应是下载镜像、导入虚拟机、把升级流程点一遍。一次复现只能证明「这台机器这次没升成」（样本级），而服务端升级通道配置可以直接证明「官方从未开放过该通道」（总体级），成本从 GB 级下载+GUI 操作降为一次 HTTP GET。
3. **证据等级跨档表述**：「软件包在官方仓库里」（制品级）被写成「该能力可用」（功能级）；反过来，WSL 切片里没装 GUI 就把能力写成「不可得」（无/未测）。两个方向都会产出错误结论。
4. **负证据不可复现**：「经检索未找到」不附检索路径、关键词、时点与环境，第二个人无法复验，也无法在窗口到期后重跑。
5. **核验污染环境或顺手改结论**：为验证直接安装整包子系统，替换掉系统库；核验出新事实后不经独立依据就上调评分。

## 解决方案

对缺口清单逐项执行两轮，任一缺口必须落到一个**明确的证据等级与状态**（闭环/证伪/部分闭环/维持缺口+窗口），不允许停留在「大概有/大概没有」。

### 第一轮：公开信源轮（供给侧观测优先）

按以下顺序枚举观测点，能用观测点回答的不做复现：

1. **换环境复述访问**：换浏览器 UA、换网络出口、重放请求头，区分「访问失败」与「资源不存在」；记录 HTTP 状态码与访问环境。
2. **供给侧观测点（优先级最高，成本最低、证据最强）**：
   - 服务端配置/清单文件（升级通道 JSON、feature flags、下载目录枚举、`Last-Modified`/ETag 时间戳）
   - 包仓库元数据（包版本、依赖闭包、Installed-Size、changelog、维护者）
   - 官方 API/看板（含免鉴权只读接口）与定时发布物（年报、鉴定公告、测评公告全文）
   - 引用链追溯：把「多个媒体来源」追到同一个原始自报点，判定来源独立性。
3. **负证据强制留痕**：写明检索路径（站点/接口/目录）、关键词、时间窗、环境（UA 等）、结果数；穷尽多条独立路径后可登记为「高强度负证据」，但仍标注「非穷尽」。
4. **时间类争议以事件源为准**：公告/ISO 文件名/发行说明优先于网页展示时间戳（网页时间戳可能被批量重导）。

### 第二轮：零变更功能轮（当且仅当第一轮回答不了「实现是否存在」）

在不修改被验系统的前提下取证，命令矩阵及各自能证明的边界：

| 手段 | 命令示例 | 能证明 | 不能证明 |
|---|---|---|---|
| 模拟安装 | `apt-get install -s --no-install-recommends <pkg>` | 依赖闭包规模、冲突/被移除包 | 不实际落地任何文件 |
| 仅下载解包 | `apt-get download <pkg>` + `dpkg-deb -x` | 包内文件、配置、脚本、desktop/service 单元 | 安装脚本是否成功执行 |
| 二进制静态取证 | `strings`/`nm -D`/`objdump` | 协议实现痕迹（crate/符号）、导出 API 面、硬编码端点 | 运行时行为与性能 |
| 免安装冒烟 | 直接执行解包出的二进制 `--version`/`--help`/只读子命令 | CLI 可运行、子命令面、只读列举类输出 | 写操作、端到端业务结果 |
| 会话总线探测 | `gdbus`/`dbus-send` introspect/call 只读方法 | 桌面/系统服务接口存在及可调 | 需 GUI 交互/外设的链路 |

### 证据等级四档（禁止跨档表述）

| 档位 | 含义 | 允许的措辞 |
|---|---|---|
| L0 无 | 未观测到任何制品/接口 | 「未见，检索路径见…」（负证据留痕） |
| L1 制品级 | 包/镜像/文件存在于官方渠道 | 「包级可得、默认未装」 |
| L2 架构级 | 解包见实现、接口/CLI 只读运行通过 | 「实现存在且只读链路可运行」 |
| L3 功能级 | 端到端真实输入产出真实结果 | 「功能可用（附输入/输出/版本）」 |

### 三道收口

1. **结论与评分解耦**：核验新事实只更新事实层与缺口状态；评分变更必须另有独立依据并单独记录算式。
2. **未验证显式留痕**：做到哪一档就写到哪一档，剩余项单列「边界声明」（如：推理未跑、需账号/GUI），给出用户接管点，不静默忽略也不乐观补全。
3. **环境前后对账**：取证前后各跑一次包状态（`dpkg -l`）与磁盘占用对账；临时文件用后即删；需要大空间时落独立数据盘，不污染被验系统。

## 反模式（均来自实战教训）

1. **403 即不存在**：不区分访问环境与资源有无，把网络/UA 问题登记成事实缺口。正确动作是换环境复述（本案例 DistroWatch 403→#107）。
2. **用户路径硬复现优先**：不下 4.8GB ISO、不导入虚拟机、不点 GUI 就觉得「没真测」。先问「供给侧有没有一个配置/清单能总体性回答这个问题」（本案例升级通道 JSON 冻结于 2024-08，证据强度高于实跑一次失败升级）。
3. **双向跨档表述**：包在仓里就宣称能力可用（L1→L3），或 GUI 没跑通就写不可得（未测→L0）。能力结论必须标注四档之一。
4. **真安装式取证污染系统**：模拟安装已提示会移除关键库（本案例全装会移除 libcurl3-gnutls 影响 git），仍直接 `apt install`。一律 download+解包到私有目录。
5. **服务端证据不验消费链**：找到服务端配置就断言「客户端必然如此行为」。配置文件与客户端同名是强关联而非直证；必须补做客户端侧字符串/代码检索，仍不能证明时显式登记残余不确定性与补证行动项。
6. **核验顺手改分**：新事实一出来就调评分/改推荐结论。事实更新与评分裁决分离，评分只在有明确维度依据时变动并留算式。
7. **负证据一句话收尾**：「未找到相关评测」不可审计。必须附路径+关键词+时点+环境+结果数。

## 检验标准（怎么知道做对了）

- [ ] 原缺口表每一行都有：状态（闭环/证伪/部分闭环/维持）+ 证据编号 + 下一复核窗口。
- [ ] 每条能力结论可映射到 L0~L3 之一，且报告措辞与档位一致。
- [ ] 每条负证据可由第二人按记录的路径复现。
- [ ] 至少尝试过一个供给侧观测点后，才允许启动重成本的功能复现。
- [ ] 功能轮取证前后有包状态/磁盘对账记录，临时文件已清理。
- [ ] 评分/推荐结论若变动，有独立依据与算式；未验证项有显式边界声明。

## 跨场景迁移

- **SaaS/企业软件采购尽调**：先查 status page 历史、公开 API 文档/OpenAPI、定价与套餐 JSON、安全合规白皮书、开源版仓的提交频度（供给侧），再决定是否开 POC 账号走业务流程（功能轮）。
- **二手车/二手设备评估**：维保记录、保险出险记录、召回公告、配件供应链状态（供给侧总体证据）优先于预约实车试驾（样本级复现）。
- **供应商/供应链审计**：供应商公开 SBOM、仓公开度、CVE 响应历史、认证证书名录（可枚举的客观清单项）先行，现场审厂留给清单项覆盖不了的流程性问题。
- **招聘/团队尽调**：公开作品、提交记录、技术演讲（制品级/架构级）先核，现场面试与背调（功能级）验证剩余项；不把「有 GitHub」等同「工程能力强」。
