# 同源产物形态坍缩法

> 对应模式：ARTIFACT-COLLAPSE-001
>
> **一句话概括**：当一个逻辑资产在磁盘上以多种形态并存（源归档 → 解包工作树 → 副本安装 → 缓存派生物），且形态之间存在**确定性再生关系**时，处置单位不是「逐条目独立分诊」，而是**再生依赖图 + 最小可复现集（支配集）**——围绕「哪个形态是该资产的最小自包含源、其余形态可否由它再生」整体坍缩，而非按目录逐个判断。

---

## 模式概述

工程任务的中间产物目录很少是「并列的独立条目」的集合。更常见的形态是：**同一份东西被复制/解包/安装/缓存了很多遍**。回放一个真实的临时区（2026-10-20，`.temp/openkylin-wsl-pytest`，5,149 文件 / 435.8 MB）：

- 一个 CPython 3.14 解释器同时以 **三种形态**存在——`cpython314.tar.gz` 源归档（71.6 MB）、`wsl-py314/` 解包工作树（249.7 MB）、`wsl-venv314/` 用 `venv --copies` 复制出的解释器（74.7 MB）——合计约 396 MB，其中至少 2 份是可由另 1 份确定性再生（或本已废弃）的冗余；
- 依赖包同时以 **两种形态**存在——`wsl-wheels/` 的 14 个 wheel（3.1 MB）与 `wsl-spk/` 的已解包安装树（11.0 MB）；
- 816 个 `.pyc` 缓存（14.3 MB）散布在 113 个 `__pycache__/`，是编译期的纯派生物；
- 「保留什么」的证据（`wsl-test-logs/` 的 48 个脚本与日志）与「跑起来需要什么」（解包树、依赖树）**混放在同一目录**，没有形态标记。

这类目录用「逐条目分诊」处理会陷入两个困境：一是**条目数爆炸**（5,149 个文件无法逐条裁决）；二是**看不见关系**——`wsl-venv314` 单看只是 3 个文件的空壳 venv，看不出它与 `wsl-py314` 是同一解释器的两个形态、且已脱离权威复跑路径。

本模式给出的单位转换：**从「条目」上升到「形态」，从「分类」上升到「再生关系」**。具体是三步收敛：

1. **标注再生关系**：对每个「源候选」找出它能否由目录内某个**确定性命令**再生（`tar -xzf`、`zipfile.extractall`、`venv`、编译）。
2. **求支配集**：在「源 → 派生」有向图上，求能覆盖全部形态的最小源集合（最小可复现集）——它既是删除的非破坏性上界（删掉所有能被它再生的形态），也是「必须保留」的下界（它自身不可去）。
3. **按层处置**：源层（保留）/ 派生层（可删，附再生命令）/ 证据层（迁出，不混放）/ 死路层（无消费者且不可再生者，走裁决）。

核心判据一句话：**「可由目录内已有确定性命令再生」且「不被消费者引用为唯一副本」者为可去项；「不可再生」或「被引用为唯一副本」者为保留项。**

## 触发场景

**适用于：**

- 一个工程/构建/测试产物目录中，同一资产以多形态并存（归档 + 解包树 + 安装副本 + 缓存）
- 目录条目数远超人工可逐条裁决的规模（如数千文件），但其中大量条目存在确定性再生关系
- 需要在不破坏「可复跑 / 可复现 / 可离线重建」能力的前提下回收空间
- 需要向他人证明「保留哪些是必要的、删除哪些是无损的」

**不适用于 / 边界条件：**

- **条目之间无关系、彼此独立的混合资产堆** → 用[临时目录「可再生分级」清理法](temp-directory-recoverability-triage.md)做条目型横向分诊；本模式是它的**关系型补充层**，不是替代（见「与相关模式的关系」）
- **生产/共享存储的产物** → 走运维变更流程与备份策略，本模式仅适用于个人/团队工作区的约定产物区
- **仅有单一形态、无派生冗余的目录** → 退化为普通「能不能删」判断，本模式的关系层无对象
- **再生代价不可接受时**（离线/计费网络、再生耗时数小时、源已不在手）→ 「可再生」不等于「可删」，须把再生代价纳入判据；离线场景下源归档（如 `cpython314.tar.gz`）反而是**必保项**（见反模式4）
- **仍在运行的任务产物** → 等任务结束后再盘点

## 核心做法（六步）

### 第1步：全量普查，只记录事实

对目标目录做递归统计，产出四个客观量：文件数、目录数、总字节、以及**每个一级子树的**文件数与字节数。不做判断、不写因果词。

> 断言式前态：普查数据须固化为「删除前态快照」（文件数 / 目录数 / 字节和），作为后续验收的唯一基准。示例实测值：`TOTAL_FILES=5149, TOTAL_DIRS=413, TOTAL_BYTES=435754689`。

### 第2步：逐子树体量与占比，定位「大形态」

按子树体量排序，标出占大头的形态。经验分布：**空间高度集中在「可再生的派生形态」而非散落的小文件**——实测样本中，三形态解释器（396 MB）+ 解包依赖树（11 MB）+ 编译缓存（14.3 MB）合计约 421 MB，占 96.6%；而 48 个复跑脚本与日志合计不足 0.2%。

**含义**：坍缩收益由少数「源-派生对」决定，收拾散落文件对空间几乎无贡献。

### 第3步：标注可再生物（建立再生关系）

对每个「可能是派生形态」的子树，找到并**记录**能把再生它的确定性命令；找不到命令的，标注为「不可再生」。

| 形态 | 判定问题 | 再生命令（示例） |
|---|---|---|
| 解包工作树 | 是否有对应源归档？ | `tar -xzf <src>.tar.gz` |
| 已安装依赖树 | 是否有一组 wheel 可解包？ | `zipfile.extractall(wheel, dest)` |
| `venv` 副本 | 是否有可用的基础解释器？ | `<base-python> -m venv --copies <venv>` |
| 编译缓存（`.pyc`/`__pycache__`） | 是否由源码编译？ | 首次导入自动重建 |
| 构建快照 | 源是否在版本库？ | 重新构建 |

**关键区分**：能再生 ≠ 删了更好。须同时判断该形态是否**被消费者引用为唯一副本**（下一步）。

### 第4步：识别唯一副本与死路分支

两类特殊形态**优先于再生性判断**：

1. **唯一副本**：某资产只在磁盘上存在一份，且被消费者当作输入引用（如离线场景下的源归档 `cpython314.tar.gz`——删了就失去离线复现能力）。**唯一副本一律保留**，无论它多大。
2. **死路分支（Dead-end branch）**：某形态「不可再生」但**也无任何消费者**——它由一条**已废弃**的路线产生，权威路径已改走别的形态。这类形态的删除理由不是「可再生」，而是「无消费者 + 死路」。

> 实测案例：`wsl-venv314`（78,298,359 字节）不可再生（在 9p/drvfs 挂载上 `venv` 创建以 `Errno 1 Operation not permitted` 失败，`setup_venv.log` 留有证据），但权威复跑路径 `env.sh`/`r4_full.sh` 用的是 `PYBIN=wsl-py314` + `PYTHONPATH=wsl-spk`，**从不引用 venv**；且其 `site-packages` 为空（无 pip、pytest 不可导入）⇒ 功能性废弃。删除理由 = **无消费者 + 死路分支**，与「可再生」无关。

### 第5步：构建再生依赖图，求最小可复现集（支配集）

把「源 → 派生」画成有向图，求支配集：

```
{cpython314.tar.gz} ──tar -xzf──▶ wsl-py314（解包树）
{wsl-wheels/*.whl}  ──extractall─▶ wsl-spk（解包依赖树）
{wsl-py314}         ──venv───────▶ wsl-venv314（死路分支，无消费者）
{任意源码}           ──compile───▶ __pycache__/*.pyc
```

得到的**最小可复现集**分两套能力，须显式区分（它们对应不同的删除授权）：

| 能力 | 最小集（保留） | 含义 |
|---|---|---|
| **即时复跑集** | 解包树 + 依赖树 + 驱动脚本/日志与证据 | 立刻能跑，不需要重建步骤 |
| **离线重建源集** | 源归档 + wheel 集 + 驱动脚本 | 无网也能从零重建出即时复跑集 |

> 判据：删除个别形态后，「即时复跑集」或「离线重建源集」两者中**至少一套完整**，则该删除不破坏可复现性。

### 第6步：按层处置 + 断言式执行与验收

处置按「源层 / 派生层 / 证据层 / 死路层」分层：

| 层 | 判定 | 默认处置 |
|---|---|---|
| **源层** | 处于最小可复现集中（源归档、wheel 集） | **保留**（不可去） |
| **派生层** | 可由源层确定性再生，且非唯一副本 | 可删；删除记录须附再生命令 |
| **证据层** | 复跑脚本、日志、证据（成果已固化，不参与再生） | 保留并**迁出**，勿与运行时解包树混放 |
| **死路层** | 不可再生且无消费者 | 裁决后删（附「无消费者」证据） |

执行采用断言式五段：**前置断言 → 记录前态 → 执行 → 后置验证 → 差异归因**，三重不变式（文件数 / 字节和 / SHA 清单）逐项核验。

> 前置断言示例：删除前重新普查，若 `TOTAL_FILES/TOTAL_DIRS/TOTAL_BYTES` 与固化快照不符即中止。后置验证示例：删除后重新普查，校验 `POST_BYTES == PRE_BYTES − Σ(删除集字节)`；本例 `435,754,689 − (15,000,130 + 78,298,359) = 342,456,200`，实测精确吻合。

## 反模式（不要这么做）

### ❌ 反模式1：同一资产多形态并存而不标注关系

让源归档、解包树、副本安装在目录中并列堆放，互不标注去向。结果是无人知道哪份是「源」、哪份可删——冗余长期存在（实测解释器三形态合计约 396 MB，达单形态的 3 倍）。

**替代**：每个派生形态落盘时即在目录头或台账登记「源 → 命令 → 派生」三元组。

### ❌ 反模式2：把派生形态当独立条目逐一分诊

对 5,149 个文件逐条判断「留还是删」。派生形态的正确处置**由源决定**，逐条判断既低效又容易把「删了源、留了派生」这类组合做成不可复现。

**替代**：先求支配集，再按层批量处置；派生层整层删除由源再生。

### ❌ 反模式3：把「可再生」当作「可删」的充分条件

「反正能重建」就删掉。若再生需要**不可接受的代价**（离线无源、耗时数小时、源已不可得），删了源/唯一副本即造成真实损失。

**替代**：删除授权 = 可再生（派生层）+ 非唯一副本（唯一性检查）+ 再生代价可接受。三者缺一不可。

### ❌ 反模式4：把「污染性/可再生的缓存」纳入交付或存量盘点单位

把 `__pycache__`、`.pytest_cache`、解包中间物当作「交付内容」统计与保留。这类物**不承载信息**，只会让「产物目录到底有多少真资产」失真。

**替代**：缓存与中间物单列为派生层，按契约排除在存量统计之外。

### ❌ 反模式5：证据与驱动混放在运行时目录

把复跑脚本、日志证据和运行时解包树放在同一目录，导致清理时不敢动运行时目录（怕误删证据）、或重建时污染证据。

**替代**：证据层与运行时层分目录，或至少以命名/台账显式标注；证据层不参与再生图。

### ❌ 反模式6：删除前不做最小可复现集判定与唯一副本检查

直接删「看起来冗余」的形态，直到删掉某个唯一副本，事后才发现可复现性已被破坏、且无法从外部恢复。

**替代**：任何删除动作前先完成第4、5步——唯一副本清单 + 支配集；删除后执行断言式后置验证，以实测数据为唯一验收依据。

## 检验标准（做完怎么知道做对了）

| # | 标准 | 验证方法 |
|---|---|---|
| 1 | 每个被删形态都能归入「派生层/死路层」且有对应证据 | 处置台账中每条附「再生命令」或「无消费者证据」 |
| 2 | 最小可复现集在删除后仍完整（即时复跑集或离线重建源集至少一套） | 复跑入口存在性检查 + 关键二进制/源归档存在性检查 |
| 3 | 无任何形态「唯一副本」被删 | 唯一副本清单与剩余清单比对，差额为空 |
| 4 | 删除前后字节差 = Σ(删除集字节)，精确相等 | 前置/后置普查三元组对账（文件数/目录数/字节和） |
| 5 | 证据层未被误删、未被再生操作覆盖 | 证据层文件计数与清单一致 |
| 6 | 每个删除动作单一职责、可独立验证 | 批次记录可追溯到「层 + 源 + 再生命令」 |

## 迁移示例（跨场景验证）

模式的本质是「**同一资产的多形态收敛到最小自包含源：源层保留 → 派生层按再生命令坍缩 → 唯一副本与死路层裁决**」。剥离软件产物细节后：

| 迁移场景 | 源层（保留） | 派生层（可删/可坍缩） | 唯一副本/死路层 |
|---|---|---|---|
| **数据科学项目** | 原始数据集（唯一副本） | 清洗中间表、特征缓存、`__pycache__`、notebook 输出内嵌图 | 早期废弃的建模分支产物（无消费者） |
| **摄影/设计工作流** | RAW 原件（唯一副本） | JPEG 导出、缩略图、Camera Raw 缓存、历史版本 PSD 副本 | 已弃用风格的旧排版副本（无客户引用） |
| **文献/知识管理** | 原始 PDF（唯一副本） | 转出的 Markdown、OCR 文本、索引缓存、笔记导出 html | 早期已废弃格式的转换残留 |
| **容器/镜像构建** | `Dockerfile` + 源 tar（唯一副本） | 镜像层 tar、构建缓存、`--copies` 复制的解释器树 | 已被多阶段构建取代的旧中间镜像残留 |

> L1 成熟度声明：以上跨域迁移为结构化推演，未经实际执行验证；首个软件工作区案例已实测（5,149→4,330 文件，回收 93,298,489 字节，最小可复现集双套完整）。

| [可逆性保障](../../architecture-patterns/reversibility-guarantee.md) | 支撑原则 | 本模式的「派生层可删」之所以无损，前提是**再生能力本身可逆**；可逆性四层级（备份/双写/COW/可逆变换）中的「可逆变换」正是「确定性再生命令」的一般化。删除前固化前态快照是其中的备份级保障 |
| [溯源自包含](../../architecture-patterns/provenance-self-contained.md) | 支撑原则 | 「最小可复现集」要求再生命令可被独立定位；溯源 bundle-relative 自包含思想要求把「源 → 命令 → 派生」三元组随产物留存，供他人复算 |
