# 安全基线跨实例统一：多实例默认姿态的对齐拉平法

## 模式类型

治理策略/安全治理模式（多环境实例间权限/网络默认姿态的对齐统一，属安全流程类）

## 成熟度

L1-draft（**单案例待验证**：仅 Trae 双版本安全姿态对齐 2026-09-01 一个完整案例；2026-08-29 Containerfile 合并"取更严格权限值"仅覆盖子原则，不构成完整第二案例。待第二个多实例对齐案例出现后升级 L2）

## 触发场景

- 当同一用户在多个环境实例上运行同类工作流（双版本 IDE、多开发机、多容器、多 CI runner），但各实例的权限/网络默认姿态不一致时，使用这个模式
- 适用于：实例间配置独立演化、无集中配置管理、宽松实例构成实际风险敞口的场景
- 不适用于：①各实例姿态差异是合规要求（如生产/测试环境本就分级）；②已有集中式策略下发机制（应改机制而非手动拉平）

## 核心做法

1. **姿态盘点**：导出各实例的安全配置，对齐比较维度（文件系统默认、网络默认、命令白名单、沙箱开关），产出姿态对照表
2. **基线选定**：以「最严格且可用」的实例为基线——严格保证安全下限，可用保证白名单经过实践检验
3. **基线移植**：将基线配置移植到宽松实例，按目标实例的生态差异调整白名单（增删域名/路径），移植前备份原配置
4. **可用性验证**：冒烟测试逐项验证白名单不阻断日常工作流（网络请求/包管理/客户端自身）；失败项补白名单而非整体回退
5. **噪声清理**：清理陈旧/重复授权条目（路径归一化去重），保留回滚路径（删除移植文件即恢复原状）

## 反模式（不要这么做）

- ❌ **以最宽松实例为基线拉平**：安全姿态向下对齐，等于主动扩大风险敞口（案例中国际版 network allow 若反向移植将摧毁国内版的沙箱防护）
- ❌ **移植白名单后不做可用性验证**：deny 默认会静默阻断合法请求，不验证则用户在工作流中断时才发现，且倾向整体回退而非定点修复
- ❌ **白名单照搬不做生态适配**：不同实例的上游生态不同（如国际版无国内 CDN 域名），照搬会引入无效条目或遗漏必需条目
- ❌ **放任重复/陈旧授权条目积累**：同一路径大小写重复登记、废弃路径残留，增加审计噪声并掩盖真实授权面

## 检验标准

做完之后怎么知道做对了？

- 标准1：姿态对照表覆盖全部比较维度，各实例默认姿态已一致（或差异有书面豁免理由）
- 标准2：冒烟测试全通过，或失败项已补白名单并复测——无"未验证即上线"
- 标准3：授权条目无重复（归一化后唯一），无确认废弃的残留
- 标准4：回滚路径已验证可行（删除/还原单文件即恢复移植前状态）

## 迁移示例

这个模式还能用在什么其他场景？

- 场景1（本案例）：Trae 国际版/国内版——国内版 sandbox.json（deny+白名单+内网黑名单）移植至国际版，按国际版生态调整域名清单
- 场景2（待验证）：多开发机防火墙姿态对齐——以配置最严的开发机为基线，统一入站规则后验证 SSH/服务端口可用
- 场景3（待验证）：多 CI runner 的 secret 暴露面与网络出站策略对齐——以最严格 runner 为基线移植出站白名单
