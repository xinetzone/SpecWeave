01

为什么文档即产品

Docere, delectare, movere — 教之、悦之、动之。

文档不是代码的副产品，而是产品对外的第 N 个界面。它承担与前端、API、命令行同等的用户职责， 因此需要与产品同一套经营方式：读者画像、可衡量指标、发布节奏、质量门与复盘。

价值论断

文档是产品最便宜的一次交付、最昂贵的一次失误。一次写作可以服务成千上万次任务；一次错误引导也可以被放大成千上万倍。

文档的读者不只是人。
还有 IDE、AI Agent、搜索爬虫、下游集成方——
他们都在以你无法看见的方式引用你的文字。 — 本页主张；参照 Write the Docs 社区「Docs as Product」议题[1]，以及 docs.python.org 由 Sphinx 自证构建的公开范例[4]

因此文档产品化不是「多写点文档」，而是把 Docs-as-Product 作为一等公民纳入工程治理。写作一次可服务成千上万次任务，成本 O(1)；一次错误引导可沿下游集成方 × AI Agent 引用 × 搜索排名放大成千上万倍，成本 O(N·M)。这一不对称性是把文档当产品经营的经济学理由。

四类读者

  • 终端用户带着一个具体任务而来，需要在 5 分钟内完成 install / auth / query 之一。
  • 集成方 / SDK 消费者读 Reference 与 Changelog，关心兼容性、SLA 与 objects.inv 交叉引用。
  • 内部工程师读 Explanation 与 ADR，需要理解「为什么这样做」，而不只是「怎么用」。
  • AI Agent / 检索系统通过语义分块、锚点稳定与结构化 metadata 引用你的文档，是新一代沉默读者。

五项可衡量指标

  • 任务完成率读者进入 How-to 页后是否完成目标任务。
    采集：页脚反馈组件 + GA4 事件    M1[2]
  • 首次响应时间从读者进入站点到第一个可执行片段被复制的时长。
    采集：sphinx-copybutton 事件埋点    M2
  • 搜索命中率Sphinx 内置 search 或 Algolia 的 zero-result 比例与 top-3 点击率。
    采集：DocSearch analytics / 自建搜索日志    M3
  • 文档回滚率合入后 7 天内被 revert / 更正的文档提交占比，反映 V 门是否失效。
    采集：git log --grep='^Revert.*docs' 计数    M4
  • AI 引用命中率文档被 LLM 检索/引用时的锚点稳定性与语义完整度。
    采集：/llms.txt 访问日志 + 引用抽样审计    M5

指标不是 KPI，而是「读者是否被服务」的信号。任何数字都必须有采集方式与解读边界，否则不如不写。

Nulla dies sine linea — 一日不写，一日无功。

Festina lente — 缓步疾行，慢即是快。

搜索日志 + searchindex.js 命中率分析；htmlhelp 索引 diff；DocSearch analytics 的 zero-result 报表。

在文档产品中做什么

04

Diátaxis 四型 × A 原子化

Divide ut regnas — 分而治之。

「原子化」不是把长文切短，而是按读者意图切分。Diátaxis 用两个正交维度（学习 / 工作 × 获取 / 应用） 把文档分成四种不可混合的类型——这正是七概念中 A 在文档产品里的落地框架[3]。

Tu

Tutorial 入门导引 · 学习 × 行动

带读者完成一次真实的成功体验，重点在「让他能走完」，不在「解释原理」。

Sphinx 承载
有序 toctree 章节；sphinx-design 的 tab-set / dropdown 分步组织；每步一个可复制代码块。
验收标准
陌生读者 < 15 分钟内可完成；每一步都有可验证输出；不掺杂 Explanation。
A → C 映射
一个 Tutorial = 一个原子文件 = 一次 docs(tutorial): 提交。
Ho

How-to Guide 任务指南 · 工作 × 行动

面向已入门的读者，解决一个具体问题；标题即任务：「How to rotate API keys without downtime」。

Sphinx 承载
编号列表 + .. admonition:: 提示框（note / warning / tip）；末尾 seealso 指向 Reference。
验收标准
标题以动词开头；每一 How-to 只解决一个问题；给出「不适用场景」的边界说明。
A → C 映射
How-to 是最适合原子提交的单元——一次 PR 一篇，独立预览，独立回滚。
Re

Reference 参考手册 · 工作 × 认知

结构一致、可预测、可查询；由源码生成，不与源码分离维护。

Sphinx 承载
autodoc + napoleon 从 docstring 生成；intersphinx 引用外部 objects.inv；viewcode 提供源码链接。
验收标准
docstring 覆盖率 ≥ 90%；每个公开符号必须有返回类型与异常说明；结构在所有页面一致。
A → C 映射
Reference 的原子性由代码模块天然提供；docs(api): 提交必须与代码变更同批。
Ex

Explanation 解释说明 · 学习 × 认知

回答「为什么这样设计」；允许离题、允许讨论替代方案、允许表达观点。

Sphinx 承载
长文 + 边注 + footnote；mermaid 画架构决策图；ADR 目录独立编号。
验收标准
不出现操作步骤；引用具体决策记录（ADR / RFC 编号）；作者与日期显式可见。
A → C 映射
Explanation 最难原子化——按「一个决策 = 一篇 ADR」拆分，避免长文漫谈。
05

指标与质量门 G1–G4

Pondere, non numero — 以分量计，不以数目计。

质量门是文档产品的免疫系统。它们不是「检查清单」，而是不合格必须返工的强制约束—— G1 拦事实污染，G2 拦空洞洞察，G3 拦无效模式，G4 拦不可执行行动，V 门拦客套式评审。

G1

事实无因果词

检查
事实清单中是否出现「因为 / 所以 / 导致 / 错误 / 失误」等判断词。
不合格
返回 R 阶段重写事实，把判断剥离到 I 阶段处理。
落地
CHANGELOG.md 与 retrospective 页只写「发生了什么」，不写「因为某人失误」。
G2

洞察四元组完整

检查
每条洞察是否包含：陈述 / 证据（引用事实编号）/ 反常识 / 下次行动。
不合格
返回 I 或 F 阶段补充缺失部分；无证据的洞察直接删除。
落地
Explanation 类文档中的每一条论断都必须有脚注或 ADR 编号支撑。
G3

模式可迁移

检查
模式是否能迁移到 ≥ 1 个非当前领域场景；否则抽象层级不够。
不合格
返回 E 阶段重新抽象，剥离领域特定语言，提炼通用结构。
落地
自研 Sphinx directive 必须在 ≥ 2 个不同项目中被验证过，才允许进入 _ext/ 共享库。
G4

行动项原子化

检查
行动项是否符合：单一职责 / 可验证 / 有 owner / 有时间 / 可独立交付。
不合格
返回 A 阶段重写；「优化文档」不是行动项，「为 auth 模块补 5 篇 How-to」才是。
落地
GitHub issue 拆分标准：每个 issue 对应一个原子文件变更，可独立 PR。

示例数据 · illustrative

V

V 门（对抗审查）最低门槛：审查意见 ≥ 5 条且具体，至少采纳 2 条修正。 「写得很好」「没有问题」类客套话不计入。对文档产品，V 门的具体形式是： sphinx-build -W 把 warning 当 error、doctest 让文档中的代码真的跑起来、 vale / sphinx-lint 拦风格漂移，加上一位未参与写作的 reviewer 走一遍新手路径。

06

三阶段落地路线图

Paulatim sed firmiter — 一步一步，稳稳当当。

从零到「文档即产品」不需要一次性重写。三个阶段、24 周节奏，每一阶段有明确的入口条件、 原子行动项与退出条件；每一阶段都产出可运行的 Sphinx / Python 交付物，而不是 PPT。

P1

Phase 1 · 治理修复

0–4 周·Focus: 让文档能可信地构建

入口条件

  • 存在 docs/ 目录但构建常失败或缺少 CI
  • 死链、孤儿页、混合风格并存
  • 没有统一的 conf.py 与主题

原子行动项

  1. ORCH建立 docs/ 边界与 owner 名单
  2. ARCH统一 conf.py、主题、扩展清单
  3. DEV接入 sphinx-build -W + linkcheck 到 CI
  4. DEV清理孤儿页与死链（首批 < 20 处）
  5. REV制定文档 style guide 初版（1 页 A4）

退出条件 & 交付物

  • CI 全绿 ≥ 5 个工作日
  • Broken link 数量 = 0
docs/conf.py .github/workflows/docs.yml STYLE.md
P2

Phase 2 · 结构化沉淀

5–12 周·Focus: 把文档拆成 Diátaxis 四型原子单元

入口条件

  • Phase 1 完成，CI 稳定
  • 已识别 top-10 高频任务与 top-10 搜索无结果词
  • 有 ≥ 1 位文档 owner 与 reviewer

原子行动项

  1. ARCH按 Diátaxis 重构 toctree：tutorial / howto / reference / explanation 四分区
  2. DEV为 top-10 任务补 How-to（1 PR 1 篇）
  3. DEV接入 autodoc + napoleon，docstring 覆盖率 ≥ 90%
  4. DEV抽取 2–3 个自研 directive 进 _ext/（含单测）
  5. REV建立 V 门流程：每 PR 一位非作者 reviewer

退出条件 & 交付物

  • 四型分区完成，无 :orphan: 页面
  • 搜索 zero-result 率 < 15%（示例阈值）
  • 文档回滚率相对 Phase 1 基线下降
docs/_ext/*.py docs/{tutorial,howto,reference,explanation}/ REVIEW_CHECKLIST.md
P3

Phase 3 · 产品化与外化

13–24 周·Focus: 让文档像产品一样被度量、被版本化、被 AI 消费

入口条件

  • Phase 2 完成，四型骨架稳定
  • 已具备指标采集能力（M1–M5 至少 3 项）
  • 产品 / 工程 / 文档三方对路线图达成共识

原子行动项

  1. ORCH发布文档版本化策略（随 release 冻结）
  2. ARCH接入 DocSearch + 导出 /llms.txt 与语义分块 JSON
  3. DEV搭建可观测面板：M1–M5 周报自动生成
  4. REV启动季度 retrospective：R→I→E→C 完整闭环
  5. DEV把可复用 directive 抽为独立 Python 包发布

退出条件 & 交付物

  • 文档站独立域名 + 版本切换器上线
  • AI Agent 可通过稳定锚点引用文档
  • 季度复盘形成 ≥ 2 个可复用模式入库
docs/_build/observability/ llms.txt + chunks.json specweave-sphinx-ext (PyPI)
07

术语表与生态关系

Verba volant, scripta manent — 言语飞逝，文字长存。

Glossary · 术语表

  • Docs-as-Product把文档视为独立产品线来经营的方式：有读者画像、指标、路线图、质量门与发布节奏。
  • SphinxPython 生态的文档生成器，将 reStructuredText / Markdown 编译为多格式站点，核心是 doctree 中间表示。
  • doctreeSphinx 内部的文档对象树，由 docutils 解析源文件后生成，是所有 builder 的公共输入。
  • toctreeSphinx 的目录树指令，定义章节层级与导航顺序，是信息架构的一等公民。
  • Diátaxis按读者意图划分文档的四型框架：Tutorial / How-to / Reference / Explanation，作为 A 原子化的落地。
  • Seven-ConceptsR 复盘 / F 第一性原理 / I 洞察 / E 萃取 / V 对抗审查 / A 原子化 / C 原子提交，SpecWeave 方法论体系。
  • G1–G4七概念的四道质量门：事实无因果词 / 洞察四元组完整 / 模式可迁移 / 行动项原子化。
  • autodocSphinx 扩展，从 Python 源码的 docstring 自动生成 Reference 文档；配合 napoleon 支持 Google / NumPy 风格。
  • linkcheckSphinx builder 之一，扫描所有外链并输出 broken / redirected / unchecked 报告，是文档 SLA 的核心工具。
  • objects.invSphinx 生成的对象清单文件，供 intersphinx 跨项目引用；文档产品对外 API 的稳定锚点。
  • Adversarial Review对抗性审查：以魔鬼代言人视角攻击自己的产出，最低门槛是 ≥ 5 条实质意见且至少采纳 2 条。

Ecosystem · 与 SpecWeave 的边界

文档产品在 SpecWeave 中的位置

本页所述「文档即产品」是 SpecWeave 治理体系中「对外可读层」的具体实践。SpecWeave 用两条清晰的边界承载它：

  • docs/ 是唯一对外文档中心（OKF v0.2，Sphinx 构建）：Wiki 教程、知识包、复盘报告、模式库与最佳实践。
  • .agents/ 是智能体规范容器：角色、规则、协议、工作流、脚本与模板等规范与执行资产。
  • 边界规则：.agents/ 引用 docs/ 时使用 ../docs/... 相对路径；对外可读文档一律入 docs/；.agents/docs/ 已废止。
  • 七概念方法论源自 .agents/commands/seven-concepts.md；模式库落地在 docs/retrospective/patterns/methodology-patterns/。

本页作为「方法论主张」，是 docs/ 层的对外入口；具体规范与可执行脚本仍以 .agents/ 为准。
