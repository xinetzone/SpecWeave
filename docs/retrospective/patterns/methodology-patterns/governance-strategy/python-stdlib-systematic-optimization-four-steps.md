# Python 标准库系统优化四步法

> 一句话说明：当一个 Python 项目需要「利用新版标准库能力 + 保证高代码覆盖率」做系统性优化（重构/性能/内存/健壮性多维度）时，用「基线采集→能力映射→量化验证→测试兜底」四步闭环，避免"为凑模块数而改造""只改代码不改测试""无脑省内存"三类典型翻车。

## 触发场景

- 项目升级到更新的 Python 版本（如 3.13/3.14），需要把新标准库能力（`contextlib`/`contextvars`/`annotationlib` 等）系统性落地到既有代码时
- 任务明确要求"保证 100% 代码覆盖率"且需要做重构/性能/内存优化，二者需同时达成时
- 优化涉及**多个维度**（重构 + 性能 + 内存 + 健壮性），而非单一性能瓶颈时
- 需要产出可量化的"优化前/优化后/变化量"指标作为交付证据时

**识别信号**：

- 任务描述里同时出现"利用标准库模块"和"覆盖率 100%"两个目标
- 既有代码存在 monkey-patch、`list.pop(0)`、无 `slots` 的数据类等可优化点，但没有量化基线
- 优化结束后不知道从哪证明"确实变好了"

**适用于**：

- 以「标准库能力升级 + 覆盖率攻坚」为核心的系统性优化项目
- 优化结果需要可回滚、可量化、可审计
- 数据类实例量大、有内存敏感场景（用 `slots=True` 收益明显）

**不适用于**：

- 单一性能瓶颈的定位与归因（应改用 [性能优化五步法](performance-optimization-five-step-method.md)，其核心是"测量定位瓶颈 + 单变量归因"）
- 纯功能开发（无既有基线可采集，四步法中"基线采集"失去意义）
- 紧急线上故障修复（先止血，无需为了走流程而采集基线）

## 问题本质

系统性优化的常见失败模式有三类：

1. **凑数式改造**：把"用了几个标准库模块"当作 KPI，而非"每项改造是否有可量化收益"，引入零收益甚至有害的改动
2. **只改不测**：重构（如 monkey-patch 迁移、数据结构改造）后不补边界测试，覆盖率回落，等价性无法验证
3. **盲目省内存**：无脑给所有数据类加 `slots=True`，忽略需要 `__dict__` 动态属性或 `__weakref__` 弱引用的场景，埋下 `AttributeError`

四步法通过强制"先采基线、再诚实映射、逐项量化、最后测试兜底"的顺序化流程，把"拍脑袋优化"变成"可回滚、可归因、可兜底"的工程实践。

## 核心做法（四步法）

### 步骤1：基线采集（可回滚）

**目标**：在改动前取得客观基线数据，确保随时可回滚、事后可对比。

```bash
# 1. 恢复改动前状态（若有未提交改动）
git stash
# 2. 采集基线数据
pytest -q                 # 测试通过数与耗时
pytest --cov=src          # 覆盖率（语句总数/未覆盖数/百分比）
ruff check .              # 静态检查告警数
python bench_memory.py    # 一次性内存基准（sys.getsizeof）
python bench_queue.py     # 一次性微基准（deque vs list.pop(0)）
# 3. 采集完成后恢复改动
git stash pop
```

**关键检查点**：

- ✅ 基线必须是**客观数字**（行数、语句数、覆盖率、字节数、耗时），不能是"感觉还可以"
- ✅ 用 `git stash` 隔离"改动前的干净状态"，采集完再 `git stash pop` 恢复，避免基线被未完成的改动污染
- ✅ 一次性基准脚本（内存/微基准）运行完即弃，不纳入最终交付物

---

### 步骤2：能力映射（诚实记录）

**目标**：把目标标准库模块逐一映射到代码落点，对"无明确收益"的模块诚实记录为"暂不改造"，**不强行引入**。

| 目标标准库模块 | 代码落点 | 是否改造 | 收益判断 |
|---|---|---|---|
| `contextlib` | 上下文管理器协议 | ✅ 改造 | 消除 monkey-patch 隐式耦合 |
| `collections.deque` | 拓扑排序队列 | ✅ 改造 | `pop(0)` O(n)→`popleft` O(1) |
| `dataclasses(slots=True)` | 全部 `@dataclass` | ✅ 改造 | 消除实例 `__dict__`，内存 −70%~81% |
| `traceback` | 插件装配失败路径 | ✅ 改造 | 结构化错误诊断 |
| 某无收益模块 | — | ⏸ 暂不改造 | 无明确收益，强行引入只会增加复杂度 |

**关键检查点**：

- ✅ 映射表是**决策记录**，不是"展示用好几个模块"的成绩单
- ✅ 对"无明确收益"的模块，显式写"暂不改造"及原因——这比"强行用上"更能体现工程克制
- ✅ 每一次"改造"都必须能回答"它带来什么可量化的变化"（对应步骤3）

---

### 步骤3：量化验证（前后对比）

**目标**：逐项落地优化，每项产出"优化前/优化后/变化量"三列指标，一次只改一类变量。

| 优化项 | 优化前 | 优化后 | 变化量 |
|---|---|---|---|
| 代码覆盖率 | 91% | 100% | +9 个百分点 |
| `Concept` 实例内存 | 344 字节（含 `__dict__`） | 104 字节 | −240 字节（−69.8%） |
| `Bundle` 实例内存 | 344 字节 | 64 字节 | −280 字节（−81.4%） |
| 拓扑排序弹出（N=50000） | ~0.24s（`list.pop(0)`） | ~0.004s（`deque.popleft`） | 约 60× |

**关键检查点**：

- ✅ 每个优化项都有**可测量的前后对比**，不存在"感觉快了"
- ✅ 类别清晰可归因：内存优化、算法复杂度优化、健壮性修复分别记录，不混在一起
- ✅ 源码变更与测试变更分开统计（本次源码净增 +29 行、测试净增 +654 行），暴露"这是测试主导的结构化重构"这一本质

---

### 步骤4：测试兜底（100% 覆盖）

**目标**：对未覆盖语句分类处理，达成 100% 覆盖率且确保无回归。

对每一处未覆盖语句按三类处理：

| 未覆盖语句类型 | 处理方式 | 示例 |
|---|---|---|
| **防御分支/边界条件** | 逐条补测试 | YAML 解析器转义/折叠边界、`runtime` 字段非法值、插件 `KeyError`、非法日期 |
| **入口豁免** | 标 `# pragma: no cover` | `__main__.py` 的 `if __name__ == "__main__": main()`（逻辑已由 `cli.main()` 覆盖） |
| **死代码** | 直接删除 | 重构后遗留的不可达分支 |

**关键检查点**：

- ✅ 覆盖率攻坚前先**分类**未覆盖语句，而非"为凑 100% 硬写低价值测试"
- ✅ 核心业务主链路在优化前通常已接近全覆盖，攻坚重点在防御分支
- ✅ 唯一豁免必须有明确理由（入口转委托），不滥用 `pragma: no cover`

## 反模式（不要这么做）

### ❌ 反模式1：为凑齐模块而强行改造

- **错误**：把"用了几个标准库模块"当作 KPI，而不是"每项改造是否有可量化收益"
- **后果**：引入零收益甚至有害的改动（例如为用 `contextvars` 而强行重构本不需要上下文隔离的代码）
- **正确做法**：严格执行步骤2的能力映射——"无明确收益"的模块显式记录为"暂不改造"

### ❌ 反模式2：只改代码不改测试

- **错误**：重构（如 monkey-patch 迁移、`slots=True` 改造）后不补边界测试，直接宣称完成
- **后果**：覆盖率回落，重构的"等价性"无法验证，隐蔽回归被放过
- **正确做法**：每项重构都配套补测试，用"测试通过数不减 + 覆盖率不降"验证等价重构

### ❌ 反模式3：环保式省内存 vs 动态属性冲突

- **错误**：无脑给所有数据类加 `slots=True`，忽略需要 `__dict__` 动态属性或 `__weakref__` 弱引用的场景
- **后果**：运行时触发 `AttributeError`（动态属性无处存放）或 `__weakref__` 缺失
- **正确做法**：先在内存敏感的高频实例化类上应用 `slots=True`，用 `hasattr(instance, "__dict__")` 确认确实消除了字典；需要动态属性/弱引用的类保留默认行为

### ❌ 反模式4：无基线就优化

- **错误**：不先 `git stash` 采集基线，直接开始改代码，最后无法量化"优化了多少"
- **后果**：优化后声称"提升了"，但没有前后对比数据支撑，出现退化也无法发现
- **正确做法**：先执行步骤1的基线采集，确保每个优化项都有可比对的前值

## 检验标准

做完之后怎么知道做对了？

- [ ] 标准1：优化前已通过 `git stash` 采集客观基线（测试数/覆盖率/内存/耗时），且采集后已 `git stash pop` 恢复
- [ ] 标准2：能力映射表完整，对"无收益"模块有显式"暂不改造"记录
- [ ] 标准3：每个优化项都有"优化前/优化后/变化量"三列量化数据
- [ ] 标准4：源码变更与测试变更分开统计，能辨认优化本质（如"测试主导的结构化重构"）
- [ ] 标准5：覆盖率达标（100% 或目标值），且未覆盖语句已按"防御分支/入口豁免/死代码"分类处理
- [ ] 标准6：测试通过数不减（无回归），静态检查告警不增（`ruff check` 保持 0）
- [ ] 标准7：豁免（`pragma: no cover`）有明确理由，无滥用

## 迁移示例

### 场景1：OKF 工具链 Python 3.14 标准库优化（本项目，源案例）

- **初始状态**：覆盖率 91%（126 条未覆盖语句），`events.py` 使用 monkey-patch，数据类无 `slots`，拓扑排序用 `list.pop(0)`
- **执行步骤**：
  1. `git stash` 采集基线（187 tests / 91% 覆盖 / 内存 344 字节 / 队列 0.24s）
  2. 能力映射：`contextlib`/`deque`/`slots=True`/`traceback` 四类改造 + 无收益模块"暂不改造"
  3. 量化验证：覆盖率 +9pp、内存 −70%~81%、拓扑排序 60×
  4. 测试兜底：防御分支补测试、`__main__.py` 标豁免、死代码删除
- **结果**：覆盖率 91%→100%，测试 187→259（无回归），源码净增 +29 行、测试 +654 行

### 场景2：Python 2→3 或跨大版本标准库迁移（推断）

- **场景**：老项目从旧 Python 版本迁移，需要落地 `dataclasses`/`pathlib`/`enum` 等新标准库能力
- **应用方式**：基线采集旧版本行为 → 能力映射列出可替换模块与"暂不迁移"清单 → 逐项量化（代码行数/性能）→ 测试兜底保证迁移等价性
- **预期收益**：避免"为迁移而迁移"，只迁移有量化收益的部分

### 场景3：任何"多维优化 + 覆盖率攻坚"的 Python 项目（跨项目）

- **场景**：某个 Python 库需要同时做性能优化、内存优化、健壮性加固，并达成高覆盖率
- **应用方式**：四步顺序照搬——先采基线，再诚实记录能力映射，逐项量化，最后覆盖率分类兜底
- **预期收益**：把多维优化从"凭感觉"变成"可归因、可回滚、可审计"

### 场景4：跨领域——硬件/生产流程的"升级 + 质检"（跨领域）

- **场景**：产线设备升级（引入新设备能力）同时要保证"质检全通过"
- **应用方式**：基线采集（升级前产量/良率）→ 能力映射（哪些工序值得用新设备、哪些不值得）→ 量化验证（前后产量/良率对比）→ 质检兜底（逐项质检 + 明确豁免项）
- **预期收益**：避免"为上新设备而上新设备"，只升级有量化收益的工序，且不牺牲质检达标

## 与其他模式的关系

- [性能优化五步法](performance-optimization-five-step-method.md)：**互补而非重复**。五步法（测量→诊断→优化→验证→萃取）聚焦"单一性能瓶颈的定位与单变量归因"，四步法聚焦"标准库能力映射 + 覆盖率分类兜底"。四步法的"基线采集"对应五步法的"测量"，但四步法独有的"能力映射（诚实记录无收益模块）"与"覆盖率分类兜底（防御分支/入口豁免/死代码）"是五步法不具备的。
- [分层渐进优化策略](phased-incremental-optimization.md)：步骤3/步骤4落地时的风险控制补充——当单次改造涉及内存语义或行为变更时，用其"安全场景先行 + 复杂场景后置"原则渐进推进。
- [测试覆盖率边际收益递减拐点](test-coverage-diminishing-returns.md)：与步骤4形成对话——该模式主张"90% 以上边际价值低，不必强求 100%"，而四步法在**任务明确要求 100%** 时提供"如何不凑数地达成"的路径（分类兜底 + 显式豁免）。两者适用的前提不同（是否强制要求 100%）。

## 待验证场景（升级 L2 需确认）

本模式目前为 L1-draft（单案例，OKF 工具链）。建议在以下场景验证后升级 L2：

1. 另一个 Python 项目的标准库能力升级（如 `dataclasses`/`enum`/`functools.cache` 的系统落地）
2. 跨 Python 大版本迁移（如 3.11→3.14）的系统优化
3. 非纯性能、偏"标准库生态化改造"（如引入 `tomllib` 替代第三方 TOML 解析）的优化
