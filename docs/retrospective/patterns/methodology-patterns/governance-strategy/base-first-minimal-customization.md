# 底座先行最小定制法（Base-First Minimal Customization）

## 模式类型

技术采纳实施路线（执行类）。作用于**底座选定之后**的定制落地阶段，产出为落点表、改动台账与逐项验证证据；不负责选型决策，也不产出新方案设计。

## 模式概述

想得到「完全符合自己习惯」的系统时，最自然的做法是**从核心重写**或**直接改核心层**：既然要定制，就改最根本的地方。这条路在成熟底座上系统性失效——底座的核心层承载了它全部的稳定性投入，改动它等于把底座的维护成本转嫁给自己，而收益只是少数几条个性化规则。

本模式的核心转向是：

> **不重写系统：先让成熟底座跑通最小闭环并留基线，再按「可声明资产 → 规则/技能 → 界面 → 核心操作层」的落点顺序逐层尝试最小改动，每改一处立即在真实环境验证一次并记录回滚方式。**

支撑证据来自一个手机 Agent 课程知识包（[上游知识包](../../../../../projects/awesome-okf-xs/doc/bundles/jishu/ai/ecosystems/trae/trae-agent-camp-01/index.md)）：

1. 个性化能力的实际载体是**文字资产**——一份规则文件、一个技能目录、一份记忆，而不是核心代码（F-018、F-020）；
2. 一个具体功能（设闹钟 + 定时提醒）是沿「先让 AI 讲清该动哪里 → 写 → 测 → 装回设备验证」完成的（F-039）；
3. 同一项目被划分为四个改动落点区（界面层 / 记忆层 / 技能说明书 / 读屏点击层），技能区只是文字规则（F-091）。

> 为什么把「跑通再改」放在第一步？没有基线时，任何异常都无法归因到「底座本来如此」还是「我改坏了」——这是定制类任务最大的返工来源。

## 触发场景

**适用于**：

- 目标能力与某个成熟底座（开源框架、可配置平台、带扩展点的产品）**高度重合**，自研全套的边际收益低于成本；
- 时间与人力有限，优先要「能用」而不是「完全可控」；
- 底座提供可读的文字/配置资产层（规则文件、提示词、技能目录、配置文件），核心层非必需改动；
- 需要把定制结果长期维护，因而必须能回滚、能归因。

**不适用于**：

- 底座缺少关键能力（例如必须对接只对特定主体开放的系统）——此时应换底座，而不是硬改；
- 许可证、服务条款或合规不允许二次开发与再分发；
- 底座已停止维护、或核心层无版本控制——「最小改动」失去可回滚保障；
- 目标就是研究或教学（要理解内部实现），此时重写或通读核心层才是目的。

## 核心做法（6 步）

### 步骤 1：跑通最小闭环并冻结基线

用底座官方给出的最短路径完成一次端到端可用（安装 + 自检 + 一条最小任务），并把当时的行为写成基线：哪些能力可用、哪些不可用、报什么错、耗时多少。

- **主手段**：按官方快速开始执行；**替代手段**：无官方快速开始时，用一条覆盖主链路的样例任务代替。
- 基线必须是**可复现的记录**（命令、输出、截图、日志），不是「我记得当时能用」。
- 若最小闭环在**不做任何改动**的前提下就跑不通，本模式的前提不成立：应先修通或更换底座，不得把「装不起来」当成定制的第一步。
- 此步产出：基线快照 + 已知缺陷清单（用来区分「本来坏」与「改坏」）。

### 步骤 2：只读勘察，定位改动落点

在改动任何文件之前，先让协作者（人或 AI）只做解释：关键模块在哪、一次请求经过哪几步、改某类行为该动哪里。约束为**零改动**（详见 [只讲不改勘察](../ai-collaboration/explain-only-reconnaissance.md)）。

- 勘察结论应落到一张「落点表」：

  | 需求 | 候选落点（层） | 可回滚性 | 待验证问题 |
  |---|---|---|---|
  | 改一条个性化规则 | 规则/配置文件（资产层） | 可直接还原 | 该规则是否被运行时缓存 |
  | 加一个自定义动作 | 技能/脚本目录（技能层） | 删文件即回滚 | 是否需要注册/重装 |
  | 调一个默认值 | 配置项（资产层） | 改回原值 | 是否被版本升级覆盖 |

- 此步产出：落点表，且工作区无改动。

### 步骤 3：按「资产层 → 规则层 → 界面层 → 核心层」的顺序尝试最小改动

从**可声明资产**（配置、提示词、记忆、技能说明书等文字层）开始，逐层向下；只有上一层确实表达不了需求时，才动下一层。

| 顺序 | 落点层 | 典型形态 | 改动代价 |
|---|---|---|---|
| 1 | 可声明资产层 | 配置项、提示词、记忆文件 | 可读、可回滚、无需回归核心 |
| 2 | 规则/技能层 | 规则文件、技能说明、脚本 | 可审计，需一次功能验证 |
| 3 | 界面/呈现层 | 布局、文案、入口 | 需视觉回归 |
| 4 | 核心操作层 | 执行器、调度、协议实现 | 需完整回归，成本最高 |

- **主手段**：优先找底座预留的扩展点（hook、plugin、配置文件）；**替代手段**：无扩展点时，用「包装而非侵入」的方式在外围补齐。
- 此步产出：单点改动（一次只改一层的一个点）。

### 步骤 4：每改一处，立即在真实环境验证一次

在真实运行环境（真机、真实账号、真实数据）跑一次与本次改动直接相关的最小验证，而不是等全部改完再统一测。

- 验证项必须能判「通过/不通过」，不能是「看起来差不多」。
- 一项改动对应一次验证；多项混改会使失败无法定位到具体改动。
- 此步产出：每条改动的验证证据（输出、截图、日志）。

### 步骤 5：记录改动点、验证证据与回滚方式

为每条改动登记三元组：**改了什么（文件 + 位置）｜怎么证明它生效（证据）｜怎么退回（回滚操作）**。

- 三元组是后续判断「升级底座是否要重做定制」的唯一依据。
- 此步产出：改动台账。

### 步骤 6：触及核心层时升级验证强度

一旦必须改核心层，把验证从「功能验证」升级为「回归验证」：覆盖基线快照中的全部可用能力，逐项确认未被破坏。

- 核心层改动仍需回滚方案；无回滚方案时，先补版本控制再改。
- 此步产出：回归结果对照基线快照的差异清单。

## 反模式

1. **跳过基线先改代码**：没有基线就动手，出问题时分不清「底座本来如此」与「我改坏了」，排查范围从一处扩散到全系统。
2. **一上来就改核心操作层**：把最稳定的层当作最容易改的层，改动面不可控，且每次底座升级都要重做。
3. **把底座当框架重写**：以「反正要定制」为由重写核心，最终成本反超自研，还继承了底座的复杂度。
4. **多项混改后统一验证**：一次改五处再跑一次，失败时无法定位是哪一处引入，只能逐项回退试探。
5. **无回滚记录的改动**：只记「改好了」，不记改在哪、怎么退，下一次升级即失控。
6. **用「体验更好」代替可判定的验证**：把主观感受当作验收依据，改动是否生效无法复核。

## 检验标准

1. **最小侵入达成**：能在不修改核心操作层的前提下完成至少一次个性化改动，并有验证证据。
2. **可归因**：每个异常都能回溯到基线快照，说明是既有缺陷还是本次改动引入。
3. **台账完整**：每条改动都有「改动点—验证证据—回滚方式」三元组，第三人可据此复现或退回。
4. **落点顺序被遵守**：改动发生在能满足需求的最上层，跳层有书面理由。
5. **升级可承受**：底座版本更新后，能凭台账判断哪些定制需要重做。

## 迁移示例

- **企业内部工具建设**：先在成熟 SaaS 上配置跑通，再针对差异做插件式开发，而不是自研全套；步骤 3 的「可声明资产层」对应 SaaS 的配置与工作流，核心层对应其不可改的服务端。
- **开源框架二次开发**：优先用官方扩展点（hook/中间件/配置）而非 fork；步骤 5 的台账在 fork 场景下退化为「与上游的 diff 清单」。
- **数据管道选型后落地**：先跑通一条最小链路再改算子，避免把「链路没通」误判为「算子写错」。
- **已知边界（不可外推）**：底座缺少关键能力、或许可禁止二次开发时，本模式不适用——此时正确动作是换底座或自研，而不是把改动做到核心层。
