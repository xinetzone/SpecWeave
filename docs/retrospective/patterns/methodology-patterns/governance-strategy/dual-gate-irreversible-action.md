# 双闸门不可逆动作防护（Dual-Gate Irreversible Action Guard）

## 模式类型

安全边界设计（治理类）。作用于**自动化系统执行不可逆动作之前**的防护设计，产出为不可逆动作清单、双层闸门位置与反证测试记录；不负责人类在环的整体交互设计，也不负责失败降级策略。

## 模式概述

让自动化系统更自主时，最自然的做法是**在提示词或规则文件里写「执行前必须确认」**：既然模型很聪明，写清楚它就会遵守。这条路在「一次违规即造成不可逆损失」的场景系统性失效——规则层是**可被绕过、可被遗忘、可被改写**的软约束：模型可能因为上下文过长而忽略、可能被用户一句「别问了直接做」说服、也可能被一次错误改写整段删除；而损失（扣款、误发、删除）已经发生，无法回滚。

本模式的核心转向是：

> **把不可逆动作的确认写两遍：规则层写「应该确认」，能力层写「不确认就执行不了」；并以「故意移除规则层确认后，能力层仍能拦住」作为验收测试。**

支撑证据来自一个手机 Agent 课程知识包（[上游知识包](../../../../../projects/awesome-okf-xs/doc/bundles/jishu/ai/ecosystems/trae/trae-agent-camp-02/index.md)）：

1. 程序层改造时，「确认关卡写在程序里——不管助理写出什么技能，没有用户回复『确认』都存不进手机」（F-078）——规则层之外的强制约束由能力层承担；
2. 技能层也保留了确认：设闹钟前把时间列给用户确认，设完逐条核对，且不删除、不修改原有闹钟（F-054）；
3. 比价场景明确「不加购、不下单、不领需要付费的券」，登录与滑块验证由用户本人完成（F-060、F-062）——凭据类与不可逆动作被排除在自动化范围外；
4. 卸载重装会清掉 App 内记忆与技能，课程要求在卸载前先备份（F-081）——不可逆动作的代价被显式登记。

> 为什么规则层单独不够？规则层的作用是「告诉执行者该停」，能力层的作用是「让它根本走不过去」。前者依赖执行者的服从与记忆，后者依赖系统的结构。只有前者时，一次指令改写或一次上下文截断就能让闸门失效；两者都有时，规则层负责体验（提前告知、减少往返），能力层负责底线。

## 触发场景

**适用于**：

- 自动化系统会执行付款、下单、发送、删除、安装、登录、改生产配置等不可逆动作；
- 系统由一个可改写的规则层（提示词/技能/策略文件）与一个相对固定的执行层（程序/API/权限系统）组成；
- 违规代价显著高于多一次确认的成本；
- 需要向他人证明「即使模型判断错误也不会造成不可逆损失」。

**不适用于**：

- 纯只读系统（没有不可逆动作，闸门无对象）；
- 所有动作都可回滚且回滚成本极低的系统（规则层提醒已足够）；
- 紧急止损场景（此时需要的是快速阻断通道，而不是逐项确认）；
- 规则层与执行层由同一方可随意同时修改、且无审计的场景（双闸门退化为单闸门）。

## 核心做法（5 步）

### 步骤 1：列不可逆动作清单

穷举系统中「一旦发生就无法撤销或撤销代价高」的动作，按代价分级。

- 典型清单：付款/扣款、下单、对外发送（消息/邮件/发布）、删除、覆盖写入、安装/卸载、登录与授权、修改生产配置、代填凭据。
- 分级依据：能否回滚、回滚需要谁参与、回滚窗口多长。
- 此步产出：不可逆动作清单（动作 + 代价 + 可回滚性）。

### 步骤 2：在规则层写入确认步骤与话术

在提示词、技能说明书或策略文件中，为每个不可逆动作写明「执行前展示什么、等什么回复、没回复怎么办」。

- 确认必须是**具体项确认**：展示时间、金额、收件人、将删除的对象，而不是「是否继续」。
- 同时写明「被要求跳过确认时怎么办」——正确动作是拒绝跳过并说明原因。
- 此步产出：规则层确认条款（逐动作）。

### 步骤 3：在能力层实现强制闸门

让执行层在**缺少确认凭据时根本拒绝执行**，而不是依赖执行者自觉。

- **主手段**：接口要求一次性确认令牌/二次确认参数；**替代手段**：无接口控制权时，用权限最小化（只给只读或受限账户）+ 独立审批环节实现同等效果。
- 凭据类动作（密码、验证码、支付口令）应整体排除在自动化范围外，由人直接完成。
- 此步产出：能力层闸门位置清单（接口/权限/审批环节）。

### 步骤 4：做反证测试——故意绕过规则层

移除或改写规则层的确认条款，验证能力层是否仍能拦住不可逆动作。

- 测试要覆盖清单中的每一类动作，而不是只测付款一项。
- **未通过反证的动作视为没有闸门**，无论规则层写得多完整。
- 此步产出：反证测试记录（动作 / 绕过方式 / 是否被拦住 / 拦截位置）。

### 步骤 5：登记闸门位置与维护责任

为每道闸门记录位置、覆盖动作、验证方式与改动责任人。

- 闸门与代码/配置同源维护：改动能力层时必须重跑反证测试。
- 此步产出：闸门台账。

## 反模式

1. **只在提示词里写「不要付款」**：没有能力约束，一次指令改写即失效。
2. **闸门只覆盖付款，漏掉发送与删除**：不可逆动作不止一类，漏一类等于留一个后门。
3. **把确认做成「可一键跳过」的弹窗**：默认值或快捷键让确认形同虚设。
4. **让自动化系统自己输入密码或验证码**：凭据一旦进入自动化链路，闸门与审计同时失效。
5. **只做规则层不做反证测试**：无法证明闸门有效，验收建立在「应该没问题」之上。
6. **双闸门由同一方可随意同时修改**：缺少审计时，双闸门退化为一次改动即可拆除的单闸门。

## 检验标准

1. **清单完备**：不可逆动作清单覆盖付款/发送/删除/安装/授权/改配置等类别，并标注代价。
2. **双层齐备**：每个不可逆动作在规则层有确认条款、在能力层有强制拦截点。
3. **反证通过**：移除规则层确认后，能力层仍拒绝执行，且有测试记录。
4. **凭据隔离**：密码、验证码、支付口令等输入不经过自动化链路。
5. **台账可查**：每道闸门的位置、覆盖动作、验证方式与责任人可被第三人核对。

## 实施检查清单

- [ ] 不可逆动作清单覆盖付款、发送、删除、安装、授权、改配置等类别并标注代价
- [ ] 每个动作在规则层都有具体项确认条款（展示时间/金额/收件人/对象）
- [ ] 每个动作在能力层都有强制拦截点，缺确认凭据即拒绝执行
- [ ] 已完成「移除规则层确认后仍被拦住」的反证测试并留记录
- [ ] 密码、验证码、支付口令等凭据不经过自动化链路
- [ ] 闸门台账登记了位置、覆盖动作、验证方式与责任人
- [ ] 能力层或权限变更后已重跑反证测试

## 正例

「在手机上自建技能并保存」的双闸门：

- **规则层**：技能说明书要求「保存前先展示技能名与触发语，等用户回复确认」；
- **能力层**：保存接口要求请求携带本次会话的确认凭据，缺参数或凭据过期直接拒绝写入；
- **反证测试**：临时删除规则层的确认段后重试保存，接口仍拒绝，说明闸门真实存在；
- **凭据隔离**：账号密码与验证码由用户本人输入，不进入技能与自动化链路。

## 迁移示例

- **数据库写操作**：应用层校验之外，数据库权限与审批流是能力层兜底；反证测试为「用应用账号直接执行删除」应被权限拒绝。
- **CI/CD 发布**：流水线里的「发布前确认」之外，生产环境凭据只在受保护分支可用，反证测试为「从普通分支触发发布」应失败。
- **内容发布系统**：编辑器里的「发布前预览」之外，发布接口要求二次确认参数，缺参数直接拒绝。
- **已知边界（不可外推）**：纯只读系统、全可回滚系统、紧急止损场景，双闸门会带来不必要的摩擦。
