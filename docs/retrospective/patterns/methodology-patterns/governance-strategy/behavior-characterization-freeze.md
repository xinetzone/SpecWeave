# 行为取证固化测试法

## 模式类型

方法论模式 → 治理策略（行为基线的建立与保护）

## 成熟度

L1（单案例：xuan-compose 翻译搬迁中 10+ 次怪癖纠正，2026-09-16）。
跨项目验证缺失前标 L1。

## 问题背景

遗留系统与翻译式搬迁的共同点是：**没有可执行的行为规格**，只有「看起来应该是这样」的
直觉。重构者接手时面对的是一段会跑出奇怪结果的代码——`"1m:30s"` 解析失败、
`is_list(bytes)` 判真、`--service-ports` 先删后建。直觉会说这些显然都是缺陷、应当顺手
修掉；但在对等迁移或历史数据迁移场景中，「顺手修正」等于制造不对等：一次看似显然的
修复会把上游 CLI 的可观测行为与历史单据的计算语义一起改掉，且改动分散在多处、事后
难以逐条审计。

问题的另一半是保护网缺失。重构前没有行为安全网，等于裸奔；而「哪些怪癖被有意保留、
凭什么保留」如果只存在于某个工程师的脑子里，后续开发者会据怪癖构建新逻辑，同一怪癖
则被不同会话反复重新发现、反复重新争论。

本模式要解决的不是「修 bug」，而是：在**明确要保留什么**之前先有一层可信的行为基线，
并让「有意保留」这件事有据可查、有分级口径、可随上游同步复核。

## 一句话

实际行为与"合理预期"冲突时，先怀疑测试、回代码取证；确认是真实行为后，
按真实输出写断言（特征测试）并登记台账——以测试固化"**是什么**"，不以
"**应该是什么**"改代码。

## 术语：特征测试（characterization test）

刻画系统**当前实际行为**、用于保护该行为不被意外改变的测试。断言对象是沿真实
入口观察到的具体输出（结果、退出码、副作用），而非规格、文档或直觉；它不回答
"对不对"，只回答"变没变"。

## 适用场景

**适用于：**

- 翻译式搬迁中遭遇上游怪癖，需要既保持对等又让怪癖可解释；
- 为无文档、无测试的遗留系统重构前补行为安全网；
- 跨版本迁移时锁定历史数据/单据的真实计算结果。

**不适用于：**

- 该行为是已确认缺陷、且本次任务目标就是修复它——修复后断言新行为，旧行为留作
  历史记录即可；
- 行为无法稳定复现（并发/时序/外部依赖）——先消除不确定性或用受控桩复现；
- 纯文档勘误类任务。

## 核心内容（5 步核心做法）

1. **冲突出现，先假设测试错**：不以直觉改生产代码，回到源代码沿**真实入口**取证，
   确认行为位点与触发条件。
2. **最小复现**：构造最小输入确认实际输出（源案例示例：`1m:30s` 非法、
   sub_dir 不剥 `./`、`--service-ports` 删端口后重建、bytes 被 is_list 判真、
   OverrideTag scalar 无类型解析等）。
3. **按真实输出写特征断言**：断言具体值（结果文本、退出码、命令行内容），
   禁止只断言"不抛异常"；怪行为同时命名登记台账（位点、触发条件、保留依据、
   标注"怪癖非设计契约"）。
4. **随片固化**：对等迁移中怪癖测试随对应切片移植，成为片门禁的一部分。
5. **修复分流**：若决定改变该行为，另立"偏离对等"变更与提交，与固化测试不在
   同一变更；先更新验收标准，再改代码。

> **为什么断言必须落在"真实输出"而不是"应当如此"**：断言是行为的观测点，一旦写成
> "应当如此"，它就变成了规格——而对等迁移场景里没有规格可依，只有上游真实行为可依。

> **台账载体与同步门禁**：怪癖台账已落地为对等迁移目录下的独立文件
> `libs/xuan-compose/doc/dev/parity/upstream-quirks.md`；并增设门禁纪律——
> **上游同步时强制复核台账条目的新增 / 升级 / 失效，输出台账 diff 复核结论**。

## 固化强度分级（L0-L3）

「有测试」不等于「已固化」：保护强度取决于断言对怪癖点的**变异敏感度**。
登记怪癖时按四级标注，并追求 L0：

| 级别 | 判定标准 | 典型形态 |
|---|---|---|
| **L0** 精确断言 | 断言直接落在怪癖输出值上，怪癖点变异即变红 | 退出码、报错全文、编码后字符串的等值/集合断言 |
| **L1** 弱断言 | 仅断言异常类型、返回码等粗粒度形态，细节变异不红 | `assertRaises(SomeError)` 而不校验文本 |
| **L2** 注释固化 | docstring/代码注释登记，无行为测试 | 模块 docstring 点名的空序列行为 |
| **L3** 清单固化 | 仅台账文本登记（深层编排、无单测可达点） | 信号处理循环、重建判定分支 |

- **L1 是最危险级别**：与 L0 同样全绿，却给怪癖「受保护」的假象；
  升级方式是补全文等值/正则断言（源案例 2026-10-10 已完成一次 L1→L0 升级）。
- L3 不等于禁止改动：改动须沿「人工对拍上游基线输出」通道进行并登记结果。
- 级别可随 fake/桩能力增强而升级（L3→L0），随上游正式修复而关闭条目。

## 失败案例

### 案例 1：弱断言把残缺报错文案「保护」了下来（L1 → L0）

- **背景**：`create_secrets` 处理非法输入时拼接错误串，其中第二个片段漏了 f 前缀
  （台账条目见 [upstream-quirks.md](../../../../../projects/xuanspace/libs/xuan-compose/doc/dev/parity/upstream-quirks.md)）。
- **失败表现**：最初只断言「抛出异常 / 返回码非 0」，测试全绿；但真实报错文案中缺失的
  片段让下游排障与用户指引读到残缺信息，直到人工逐字比对上游输出才被发现。
- **根因**：断言落在粗粒度形态（L1 弱断言）上，怪癖点的文本变异不敏感——全绿不等于
  被保护，只等于没被看见。
- **教训**：怪癖点的断言必须落在具体输出值上（L0 全文等值/正则）；「有测试」与「已固化」
  是两件事。源案例已于 2026-10-10 完成该条 L1→L0 升级。

### 案例 2：以「合理预期」改写上游行为，制造不对等

- **背景**：时间解析 `str_to_seconds` 的正则 `[m:]` 只认 `"1:30"`/`"1m30s"`，
  `"1m:30s"` 反而解析失败返回 None。
- **失败表现**：直觉上这是缺陷，直觉驱动下的「顺手修正」会直接改写上游可观测行为。
- **根因**：未先取证即以「合理预期」为基准改代码，等于在对等迁移中制造不对等，且改动
  与迁移主体混在同一提交，事后无法独立审查与回滚。
- **教训**：冲突出现先假设测试错，回到源码沿真实入口取证；确认为上游行为则按真实输出
  断言并登记台账。

### 案例 3：同一行为缺少统一基线，跨 Task 重复实现（D13）

- **背景**：多个 Task 迁移同一单体的相邻区域，上游函数本就散落。
- **失败表现**：T4 已迁入 `dependencies.py` 的 `check_dep_conditions`，T7 又按 handler 区域
  逐字节重译一份，直到 T11 符号盘点才暴露（源案例 §3 记为 D13，
  见 [2026-09-16-refactor-patterns.md](../../../../../projects/xuanspace/libs/xuan-compose/doc/dev/patterns/2026-09-16-refactor-patterns.md)）。
- **根因**：行为基线没有被当作唯一事实来源在每片执行，重复实现各自补断言，断言口径分裂。
- **教训**：固化纪律必须落到「每片执行」——去重与基线核对不能只放在最后审计。

## 反目标用户与场景

本模式以「保留上游真实行为」为前提，天然不适用于以下用户与场景：

| 反目标用户/场景 | 为什么不适配 | 该走哪条路 |
|---|---|---|
| **本次任务目标就是修复该缺陷的开发者** | 固化测试会把旧行为写成「应当保持」的契约，与修复目标直接冲突 | 先修、断言新行为，旧行为留作历史记录 |
| **需要消除不确定性的并发 / 时序 / 外部依赖场景** | 行为无法稳定复现时断言不稳定，固化测试自身成为假绿/假红来源 | 先消除不确定性，或用受控桩复现后再固化 |
| **纯文档勘误类任务** | 没有可执行行为，取证无对象 | 走文档修订流程 |
| **希望「统一心智模型、消灭历史怪癖」的架构师** | 本模式目标恰恰是保留怪癖并使其可解释，与「消灭不一致」目标相反 | 另立「偏离对等」变更，与固化测试分属两个提交 |
| **上游已停服、数据不可达的历史系统** | 取证依赖的真实入口消失，固化测试只能基于存档输入维持 | 见「失效条件与演进」，须显式注明证据级别 |

一句话概括：哪些人不该用本模式、哪些场景该换路——**目标包含「改变行为」的人**，
以及**行为本身不稳定的人**。

## 早期预警信号

出现下列任一信号时应暂停推进，回到取证与台账环节，而不是继续按「合理预期」改代码：

| 预警信号 | 含义 | 处置 |
|---|---|---|
| **断言只校验异常类型或返回码**（L1 弱断言） | 怪癖点的文本/顺序变异不敏感，测试形同虚设 | 升级为 L0 全文或正则等值断言 |
| **同一行为在两处被重复实现**（如 D13 的 `check_dep_conditions` 双份重译） | 缺统一行为基线，断言口径必然分裂 | 先合并到唯一实现，再补行为基线 |
| **上游同步后行为与台账不一致，且未输出台账 diff 复核结论** | 怪癖清单已与真实上游脱节 | 走「上游同步强制复核台账 diff」门禁 |
| **「这显然是 bug，顺手修掉」成为默认动作** | 危险信号：对等迁移场景中这是不对等的起点 | 强制回到源码沿真实入口取证并登记台账 |
| **固化测试与修复出现在同一个提交里** | 无法独立审查、独立回滚 | 拆分为两个原子提交 |
| **台账条目只有描述，没有触发条件与「怪癖非契约」标注** | 后续开发者会据怪癖构建新逻辑 | 补全台账四要素（位点/触发条件/保留依据/非契约标注） |

## 适用边界

- **前提一：存在可稳定复现的真实入口**。取证必须沿真实调用路径走一遍并观察具体输出；
  并发、时序、第三方服务不可达等不可复现场景不满足前提。
- **前提二：上游基线可固定**。对等迁移需能锚定上游版本（源案例 pinned
  `1f1cb09bfee4d79857ed23bfe2699febd7d20a53`），否则「真实行为」缺乏可比对基准。
- **前提三：本次任务不以修复该行为为目标**。若目标是修复，固化测试与修复必须分属
  两个变更，且先更新验收标准再改代码。
- **前提四：台账载体可写且会被复核**。无台账的固化等于「只留测试不留证据」，后续必然
  重复取证与重复争论。
- **例外处理**：行为不可复现但确需保护时，降级为 L3 清单固化（仅文本登记），并在台账
  标注「须人工对拍上游基线输出」，同时注明证据级别。

## 反模式与反例警示

- ❌ **为让断言符合直觉而改生产代码**：在对等迁移中即制造不对等；在遗留重构中
  可能改变大量历史数据的语义。
- ❌ **把怪癖当设计契约**：不标注、不登记，后续开发者据怪癖构建新逻辑。
- ❌ **断言空心化**：只验证"调用过/不报错"，行为改变时测试照样绿。
- ❌ **反复取证不留台账**：同一怪癖被多个会话重新发现、重新争论。
- ❌ **固化与修复混入一个提交**：无法独立审查、独立回滚。

## 与错误黑名单模式的区别

| 维度 | error-blacklist-monotonic-evolution | 本模式 |
|---|---|---|
| 固化对象 | 本系统曾犯、被人工拒绝的错误 case | 外部/遗留系统**现存**的真实（含怪癖）行为 |
| 目的 | 防止重犯已知错误 | 防止行为在不知情下被改变 |
| 断言立场 | 错误输出**不应**再出现 | 真实输出**确实**是这个值 |

## 实施检查清单（检验标准）

模式被正确执行后，应满足以下可审计条目：

- [ ] 每个固化测试可由最小输入独立复现；
- [ ] 断言落在具体可观察输出，行为改变时测试会变红（L0 级不出现粗粒度断言）；
- [ ] 台账含位点、触发条件与"怪癖非契约"标注；
- [ ] 对等迁移中，上游怪癖逐一可在测试与台账中双向查到；
- [ ] 上游同步类 spec 须输出 `upstream-quirks.md` 台账 diff 复核结论（条目新增 / 升级 /
  失效各有明确结论）。

## 正例与迁移示例

- **法律修订**：修订前先以真实案例固化现行执行口径（即使口径间有张力），修订
  草案再针对被固化的具体行为逐条改动；新旧口径差异可审计。
- **财务系统替换**：以历史单据的真实计算结果（含历史规则怪癖）建立特征测试，
  新系统平行试算对拍；旧规则怪癖登记，不视为新系统设计。
- **待验证方向**：医疗诊疗流程数字化、海关申报系统升级。

## 失效条件与演进

- 取证依赖的真实入口消失（外部系统停服、数据不可达）时，固化测试只能基于存档
  输入维持，需注明证据级别；
- 怪癖被正式修复后，对应特征测试转为"修复确认测试"，台账条目标记关闭；
- 分级口径应从单文件约定上升为仓库级规范，使新迁入包默认遵循同一 L0-L3 分级与台账
  登记要求；
- 出现跨项目验证案例后可升 L2。
