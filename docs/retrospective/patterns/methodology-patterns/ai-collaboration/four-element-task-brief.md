# 四要素任务书法（Four-Element Task Brief）

## 模式类型

委托契约设计（执行类）。作用于**任务下发之前**，产出为可执行、可验收的任务书；不负责需求澄清与执行过程控制。

## 模式概述

把任务交给一个**有外部副作用**的执行者（AI 助理、外包、自动化脚本、实习生）时，最自然的写法是描述目标：「帮我把笔记本买了」「把这份资料整理一下」。目标式写法在可回退的纯生成任务上够用，但一旦执行者的动作会**改变外部世界**（下单、发送、删除、改配置），它会系统性失效：执行者不知道在哪停、不知道回来该报什么、也不知道哪些动作越界——于是要么停在错误的地方，要么一路做到不可逆的那一步。

本模式的核心转向是：

> **把「帮我做某事」改写成四项齐全的任务书：做什么（环境 + 对象 + 结果）、条件（全部换成可判定的数字或枚举）、停点（停在哪一页/哪一个动作之前）、回报（回来要核对哪几项）；再补一行红线，列出不许做的越界动作。**

支撑证据来自一个手机 Agent 课程知识包（[上游知识包](../../../../../projects/awesome-okf-xs/doc/bundles/jishu/ai/ecosystems/trae/trae-agent-camp-01/index.md)）：

1. 课程把自写任务的要求归纳为四件事：做什么、条件（预算/规格/时间）、停在哪一步、回来告诉你什么（F-054）；
2. 官方示例把四要素写满：预算「30 元以内」、规格「3 层」、停点「停在商品页」、回报「店名/规格/价格」、红线「不要加购、不要下单」（F-055）；
3. 执行期间用户只做两件事：确认弹窗时点「允许一次」，以及停下后按四项核对——说明停点与回报项是**分工契约**而不只是描述（F-052）；
4. 不可逆动作被产品层直接挡住（付款、发送、删除前先问，密码框不可输入，F-067），代实名/代开通/代建 Key 被明确排除（F-072）——红线不是礼貌用语，而是可被系统强制的边界。

> 为什么把「停点」单列而不是并进「条件」？条件约束的是**过程取值**（多少钱、几分钟），停点约束的是**过程终点**。二者失效方式不同：条件缺失导致结果不可验收，停点缺失导致不可逆动作被提前执行——后者往往无法回滚。

## 触发场景

**适用于**：

- 任务交给执行者后会**改变外部状态**（下单、支付、发送、删除、发布、改生产配置）；
- 任务包含**不可逆或高代价**动作，需要明确「做到哪为止」；
- 委托方与执行方之间存在信息差（外包、新人、AI），无法依赖隐含偏好；
- 需要事后验收：必须预先约定「回来报什么」才能判断是否完成。

**不适用于**：

- 纯问答、纯生成、可无限重做且无外部副作用的探索性任务；
- 双方已有长期默契且失败成本极低的一次性小事；
- 目标本身尚不清晰——此时应先做需求澄清，而不是把模糊目标写成四要素（四要素会放大错误目标）。

## 核心做法（6 步）

### 步骤 1：写「做什么」——环境、对象、结果

指明在哪个环境（设备/账号/目录/站点）、对哪个对象、达成什么可观察的结果。

- 反例：「整理一下资料」；正例：「在本机 `docs/` 下，把 20 份会议纪要合并为一份带日期索引的文档」。
- 此步产出：一句可被第三人复述的目标陈述。

### 步骤 2：写「条件」——全部换成可判定的数字或枚举

预算、规格、时间、数量、格式，一律写成数字区间或有限枚举；**形容词不算条件**。

- 「便宜点」→「30 元以内」；「性价比高」→「同价位内重量最轻」；「尽快」→「今天 18:00 前」。
- 条件之间若可能冲突，先写下优先级（如「预算优先于规格」）。
- 此步产出：条件清单（每条都可判定真/假）。

### 步骤 3：写「停点」——停在哪一页、哪一个动作之前

用**可观察的位置/动作边界**描述终点，并把停点放在不可逆动作之前。

- 正例：「停在结算页确认前」「停在发布按钮之前」「只读不写」。
- 停点必须早于红线动作；若停点在不可逆动作之后，等于没有停点。
- 此步产出：一句停点描述 + 该点上执行者应处的状态。

### 步骤 4：写「回报」——回来要核对哪几项

列出交接时需要回报的字段，让验收方不必回放全过程。

- 回报项应直接对应验收判断（店名/规格/价格/数量），而不是过程叙述。
- 此步产出：回报清单（3–5 项，可逐项打勾）。

### 步骤 5：补一行红线——不许做哪些越界动作

显式列出禁止动作（不要加购、不要下单、不要发送、不要删除、不要代填凭据），并说明越界时应停下并上报。

- 红线与停点互补：停点说「做到哪」，红线说「绝不做什么」。
- 遇到红线场景（验证码、实名人脸、密钥输入）时，正确动作是**交回人类**，而不是尝试绕过。
- 此步产出：红线清单 + 越界时的上报动作。

### 步骤 6：四问自查后再发出

发出前自问：① 第三人读完能说出「它会在哪停」吗？② 每个条件都能判真假吗？③ 停点早于所有不可逆动作吗？④ 回报项足以验收吗？

- 任一问为否，回到对应步骤重写。
- 此步产出：可交付的任务书。

### 完整示例（采购类，可直接对照填写）

> **做什么**：在某电商站为办公室采购 1 件键盘托，适配桌面深度 ≤ 60cm。
> **条件**：单价 ≤ 200 元；宽度 ≤ 60cm；颜色不限；今天 18:00 前完成比价。
> **停点**：停在商品详情页，不进入结算页。
> **回报**：前 3 个候选项的名称、宽度、价格、店铺。
> **红线**：不要加购、不要下单、不要填写任何收货或支付信息；遇到验证码或实名人脸请停下并告知。

对照检查：条件四条全为数字/枚举；停点早于「加购/下单」两个不可逆动作；回报项足以在不动手的前提下验收。

## 反模式

1. **只有目标、没有停点**：写「帮我买好」，执行者只能自行决定做到哪一步，极易越过不可逆边界。
2. **用形容词代替阈值**：「便宜点」「快一点」「专业一些」无法判定，执行者与验收方各自解释。
3. **多目标混写**：一个任务里同时搜索、比价、下单、写总结，失败时无法定位是哪一段出的问题。
4. **依赖隐含偏好**：假定执行者知道你的预算习惯、口味、账期，每次都要重新推断且推断结果不可复核。
5. **停点写在不可逆动作之后**：如「下单后停在支付页」——此时订单已生成，回滚成本已发生。
6. **红线只写在人脑里**：没有写进任务书的禁止项，在压力下最容易被「为了完成任务」而跨越。

## 检验标准

1. **可复述**：任意第三人读完任务书，能说出「它会在哪停下、回来给你什么」。
2. **可判定**：每条条件都能被机械判真/假，无形容词残留。
3. **不可逆安全**：所有不可逆动作都位于停点之后或红线之内，没有「先做再问」的路径。
4. **可验收**：回报项覆盖全部验收维度，验收方无需回放过程即可判断完成与否。
5. **单目标**：一次任务书只承载一个可独立验收的目标（复合目标已拆分）。

## 迁移示例

- **外包/实习生派活**：四要素即交付边界，停点写明「初稿发我确认后再改」，回报项写明交付物清单与自检结果。
- **自动化脚本/RPA 任务**：把停点写成脚本的 dry-run 边界（只生成计划不执行），红线写成显式拒绝的分支。
- **内容处理类任务**：条件写成字数/引用数/格式枚举，停点写成「初稿完成、待人工定稿」，回报项写成「改动点 + 待确认项」。
- **已知边界（不可外推）**：目标是创意发散、探索或纯问答时，四要素会压缩探索空间，此时只需「做什么 + 回报」。
