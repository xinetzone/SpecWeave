# 单产出拆分法（Single-Output Work Slicing）

## 模式类型

多段工作流编排设计（执行类）。作用于**把一条长流程拆成多段并交给多个执行者**的编排阶段，产出为分段表、交接单与验收门；不负责单段任务书的字段写法，也不负责任务本身的执行质量。

## 模式概述

任务变长、可以并行时，最自然的做法是**按人头拆**：几个人各领一块，或者让调度者把任务分给几个执行者同时做。这条路在「产出之间有依赖」的流程上系统性失效——按人头拆会把同一份产出切给两个人，交接时没人说得清哪一版是准的；缺少验收门时，坏结果会一路下传，最后整链返工。

本模式的核心转向是：

> **按「一段一个可验收产出」切段，为每段写六字段交接单（目标、输入、能改什么、不能做什么、交回什么、怎么验收），在人工确认处设关口，并让调度者按「怎么验收」自核——不过就退回，不往下传。**

支撑证据来自一个手机 Agent 课程知识包（[上游知识包](../../../../../projects/awesome-okf-xs/doc/bundles/jishu/ai/ecosystems/trae/trae-agent-camp-02/index.md)）：

1. 课程区分单 Agent 串行与多 Agent 并行，并给出并行形态的分工：调度者拆开大任务、分给几个助理同时做、最后回收汇总检查（F-084）；
2. 讲师自述的实践是：大任务由主助理拆块，各助理在单独副本里做，交回后主助理逐块检查、通过才合入（F-085），并总结「先单后多、每一步留下能检查的结果、交接写清楚、人守住关键关口」（F-086）；
3. 内容生产实践把六个环节按四条规则拆成五段（F-092、F-093），进度表只有调度者能改、执行者只拿交接单与上一段文件（F-094），并设四个必须人工确认的关口（F-095）；
4. 交接单被写成六项：目标、输入、能改什么、不能做什么、交回什么、怎么验收（F-096）；调度者按最后一项自核，过了打勾并留证据再派下一段，没过打回重做、不往下传（F-097）；
5. 实施建议是先挑最费劲的一环用四问写成技能跑通，再接下一环，两三环稳定后才交给调度者串联（F-098）。

> 为什么按产出切而不是按人数切？人头是可替换资源，产出是验收单位。按产出切，每段都有唯一负责人和唯一验收物；按人头切，同一个人可能产出一半的 A 和一半的 B，失败时既不能单独验收，也不能单独回滚。

## 触发场景

**适用于**：

- 流程步骤多、可并行或可分段交付，且每段有可检查的中间产出；
- 多个执行者（人或 Agent）需要协作，且彼此没有共享上下文；
- 流程中存在必须由人确认的节点（选题、定稿、发布、付款）；
- 需要在中途打回返工而不影响全链。

**不适用于**：

- 强顺序依赖、中间产出不可分离的任务（切段会制造假接口）；
- 只有一两步的任务（切段成本高于收益）；
- 单条工作流尚未跑稳——先跑通再拆，否则拆出来的是同一条错误路径的多份副本；
- 产出无法验收的任务（此时应先定义验收物，而不是拆分）。

## 核心做法（7 步）

### 步骤 1：列出全流程动作与每个动作的产出

把流程拆到动作级别，为每个动作标注产出物（文件、表格、页面、报告）与可检查位置。

- 产出物要能被独立交出，而不是「做到一半的状态」。
- 无法命名的产出通常是动作过粗，需要再拆。
- 此步产出：动作—产出对照表。

### 步骤 2：按四条规则切段

用固定规则而不是直觉切分：

| 规则 | 判据 | 目的 |
|---|---|---|
| 单一产出 | 一段只交一件可验收物 | 保证可单独验收与回滚 |
| 人工确认处切开 | 在需要人决定的节点处分段 | 让关口成为段边界 |
| 触发时间不同就分开 | 定时任务与即时任务不同段 | 避免调度耦合 |
| 同一产出合并 | 多个动作产出同一件东西时合并 | 防止按人头切碎 |

- 切完后自检：是否出现「两个人共同负责同一产出」的段——出现即切分错误。
- 此步产出：分段表（段名 + 产出 + 负责人类型）。

### 步骤 3：为每段写六字段交接单

每段一张交接单，六项缺一不可：

1. **目标**：这段要达成什么可验收结果；
2. **输入**：允许读取哪些文件/信息（通常只含上一段产出与必要的规范）；
3. **能改什么**：允许修改的范围；
4. **不能做什么**：越界红线（不改他人产出、不发布、不删除）；
5. **交回什么**：交付物的形式与位置；
6. **怎么验收**：可逐项判断的验收条件（数量、字段、来源要求）。

- 第 6 项是最容易漏的一项，也是调度者自核的唯一依据。
- 此步产出：每段一张六字段交接单。

### 步骤 4：标注人工关口

在分段表上标出必须由人确认的节点（选题、定稿、封面、发布、付款等），并规定确认时必须展示的信息。

- 关口应落在段边界上；落在段内部的关口会造成「段做完了但不能交」。
- 此步产出：关口清单 + 每个关口需展示的信息。

### 步骤 5：先跑最费劲的一段

不要从最简单的一段开始，先挑不确定性最高或最耗时的一段跑通。

- 理由：最难的一段失败概率最高，它对交接单与验收条件的检验最严格；先跑简单段会给出虚假的稳定感。
- 此步产出：首段实跑记录（含交接单是否够用、验收条件是否可判）。

### 步骤 6：段稳后引入调度者

两三段稳定后，再让调度者（人或总管 Agent）负责拆、派、验。

- 调度者只改进度表，执行者只写自己的产出——写权限分离是防止互相覆盖的前提。
- 此步产出：调度职责说明（谁改进度表、谁验收、谁打回）。

### 步骤 7：按「怎么验收」自核，不过不传

调度者对每段产出执行验收：通过则记录证据并派下一段；不通过则打回重做，**不往下传**。

- 打回时要指出未通过的具体验收项，而不是笼统「再改改」。
- 记录「打回次数」是判断交接单质量的关键指标：同一段反复打回说明第 6 项写得不可判。
- 此步产出：验收记录（通过项/未通过项/打回次数）。

## 反模式

1. **单条工作流没跑稳就拆**：拆出来的是同一条错误路径的多份副本，返工面更大。
2. **按人数拆而不是按产出拆**：同一产出被切成两半，交接时版本无法对齐。
3. **交接单缺「怎么验收」**：下游无法判断是否接得住，调度者只能凭感觉放行。
4. **坏结果继续下传**：为赶进度跳过验收，最后整链返工，成本远高于当段打回。
5. **让执行者改进度表**：写权限不分离，进度与事实脱节。
6. **第一步就跑最简单的一段**：得到虚假稳定感，最难的一段仍在最后爆炸。
7. **关口设在段内部**：段完成了却交不出去，调度者无法判断该段是否结束。

## 检验标准

1. **可独立验收**：每段都有唯一产出与可判定验收条件，第三人能只凭交接单判断通过与否。
2. **失败不外溢**：任一段失败只影响自己，不污染下游；打回不会引发全链重做。
3. **切分合规**：不存在两人共担同一产出的段；触发时间不同的任务已分开。
4. **关口在边界**：所有人工关口都落在段边界上，且展示了必要信息。
5. **打回可度量**：有每段打回次数记录；反复打回的段能定位到交接单哪一项不可判。

## 实施检查清单

- [ ] 每个动作都标注了可独立交出的产出物
- [ ] 切段后不存在「两人共担同一产出」的段
- [ ] 每段交接单六项齐全，尤其「怎么验收」可逐项判定
- [ ] 人工关口都落在段边界上，并规定过关口时需展示的信息
- [ ] 首段选的是最费劲或最不确定的一段，而不是最简单的一段
- [ ] 调度者与执行者的写权限已分离（进度表只由调度者改）
- [ ] 有打回记录，且能定位到交接单哪一项写得不可判

## 正例

内容生产五段（选题 → 写稿 → 排版 → 封面 → 发布）：

1. 每段一张六字段交接单，例如写稿段的「怎么验收」＝字数 1500–2500、每个数据带来源链接；
2. 发布为人工关口，调度者把结果推到手机等确认才继续；
3. 首轮先跑写稿段（最费劲、最易返工），跑稳后再接排版与封面；
4. 执行者只拿交接单与上一段产出，只写自己的文件；进度表由调度者维护；
5. 写稿段验收未过则打回重做，不把未过稿传给排版段。

## 迁移示例

- **内容生产线**：选题 → 写稿 → 排版 → 封面 → 发布 → 统计，按产出切段，人工关口为选题、定稿、封面、发布。
- **软件流水线**：需求拆解 → 实现 → 测试 → 发布，按可交付制品切段；验收条件是测试通过率与制品可运行性。
- **数据加工链**：采集 → 清洗 → 聚合 → 报表，每段产出独立数据集，可用行数与字段完整性验收。
- **已知边界（不可外推）**：强顺序依赖且中间产物不可分离的任务（如单次编译链），切段会制造假接口，应按单段处理。
