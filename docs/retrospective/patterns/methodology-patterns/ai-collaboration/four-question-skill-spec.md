# 四问成技法（Four-Question Skill Spec）

## 模式类型

流程资产化方法（执行类）。作用于**把口头流程写成可复用技能**的内容生成阶段，产出为一份四问齐备的技能说明书；不负责技能文档的质量审查，也不负责技能的分发与安装。

## 模式概述

把一件反复要做的事交给 AI 时，最自然的做法是**写一段更长的提示词**：把要求说得更细、把注意事项补进去，然后每次复制粘贴。这条路在「同一流程要跑很多次」的场景系统性失效——长提示词没有触发边界（不知道该不该用）、没有检查点（做完不知道算不算完成）、没有确认闸门（不可逆动作会被一路执行），于是每次执行结果不一致，失败时也无法判断是哪一段没说清。

本模式的核心转向是：

> **把流程写成技能前先回答四个问题——何时开始（触发）、怎么做（步骤）、怎么检查（验收点）、哪里要确认（闸门）；再补一行红线，最后用同一句触发语复测改前改后。**

支撑证据来自一个手机 Agent 课程知识包（[上游知识包](../../../../../projects/awesome-okf-xs/doc/bundles/jishu/ai/ecosystems/trae/trae-agent-camp-02/index.md)）：

1. 课程在写技能前要求先回答四个问题：什么时候开始、一步步做什么、怎么检查、哪一步交给用户确认（F-036）；
2. 四问被展开成可填写的口径：开始＝说了哪句话或到了什么时间；步骤＝先读什么、再做什么、最后交什么；检查＝去页面、列表、记忆还是通知核对，没做到要如实告知；确认＝付款、删除、对外发消息必须等确认（F-037）；
3. 五个场景技能统一走「手机先试一次 → 改技能并推送 → 回手机把第一步那句话原样再发一次验收」（F-042）；
4. 推送前先做格式校验（lint）再复制进设备，回复中出现约定字符串才算通过（F-046）——检查点不只写在技能里，也写在发布动作上。

> 为什么四问里必须有「怎么检查」这一问？只写步骤的技能在失败时无法自证：执行者可以「按步骤走完」却没有任何产出，而委托方只能靠回放过程判断。把检查点写成「去哪个页面/列表看什么」，验收就从叙述变成了观察。

## 触发场景

**适用于**：

- 同一流程会重复发生，且每次的触发语或时间点大体固定（如每周报表、每日排程、定期比价）；
- 流程包含多个步骤，步骤之间有先后依赖；
- 结果可在某个界面、列表、文件或通知里被观察到；
- 流程中存在不可逆动作或对外发送动作，需要人工确认。

**不适用于**：

- 一次性任务（写提示词直接做更快，不必资产化）；
- 结果无法观察、只能靠执行者自述的任务（此时应先设计可观察产物，而不是写技能）；
- 触发条件仍在剧烈变化的任务（此时固化会把错误前提写死）；
- 只是想提升单次任务质量——那是任务书写法（见 [四要素任务书法](four-element-task-brief.md)）的领域。

## 核心做法（6 步）

### 步骤 1：写「何时开始」——触发语或时间点

写出用户会说出的那句话，或明确的触发时间。触发语要写成**可直接匹配的原句**，而不是意图描述。

- 正例：「说『出题』时」；反例：「当用户想要练习时」——后者需要执行者猜测。
- 若同一流程有多种说法，全部列出，并指定其中一句为验收复测用句。
- 此步产出：1–3 条触发语句 + 一条复测句。

### 步骤 2：写「怎么做」——读什么、做什么、交什么

按执行顺序写出三类动作：先读哪些输入、再执行哪些步骤、最后交付什么。

- 输入要指明来源（哪个文件、哪段记忆、哪个服务），不写「根据用户情况」。
- 步骤要能对应到可观察动作，避免「智能处理」这类黑箱动词。
- 此步产出：有序步骤清单 + 每步的输入与产出。

### 步骤 3：写「怎么检查」——去哪看、没做到怎么报

为交付物指定**观察位置**与**核对项**，并写明未达成时的如实告知义务。

- 观察位置示例：某个列表页、某个文件路径、某条通知、某段记忆。
- 核对项应与交付物的价值直接相关（数量、字段完整性、排序规则），而不是格式美观。
- 显式写「看不清就写『页面未显示』，不要猜」这类反编造条款。
- 此步产出：验收清单（3–5 项，可逐项打勾）+ 未达成时的报告话术。

### 步骤 4：写「哪里要确认」——不可逆动作前停

列出流程中所有不可逆或对外可见的动作（付款、下单、发送、删除、安装、登录），每个动作前插入确认步骤。

- **主手段**：在技能里写「先列出将执行的内容，等用户回复确认后再执行」；**替代手段**：无对话能力时，把确认实现为参数缺失即拒绝执行（见 [双闸门不可逆动作防护](../governance-strategy/dual-gate-irreversible-action.md)）。
- 确认必须是**具体项确认**（时间、金额、收件人），不是「是否继续」。
- 此步产出：确认点清单 + 每个确认点需要展示的信息。

### 步骤 5：补一行红线——不能做什么

用否定式祈使句写出越界动作，并写明越界时的正确动作（停下并上报）。

- 红线与确认点互补：确认点说「做之前问」，红线说「绝不做」。
- 常见红线：不代填凭据、不绕过验证码、不删除原有数据、不修改他人资产。
- 此步产出：红线清单。

### 步骤 6：同句复测——用触发语原样再发一次

技能写完后，用步骤 1 的复测句原样执行一次，对比改前改后的输出。

- 复测句必须与首次尝试完全一致，否则无法区分「技能改动」与「输入变化」。
- 复测要同时看交付物与检查点：交付物对不对、检查项是否真的能观察到。
- 不达标就回到对应问（触发/步骤/检查/确认）修改，一次只改一处。
- 此步产出：改前/改后对照记录。

## 反模式

1. **只有目标没有步骤**：写「帮我安排好」，执行者只能自行发明流程，每次结果都不同。
2. **没有检查点，验收靠感觉**：交付物无法被观察，失败只能靠回放过程发现。
3. **只有正向要求，没有红线**：压力下最容易为完成任务而跨越边界。
4. **一次写十条规则**：失败时无法定位是哪条规则导致的行为变化。
5. **用意图描述触发**：写「当用户需要时」，执行者要么不触发、要么乱触发。
6. **跳过同句复测**：改完直接进入下一个需求，无法证明改动真的生效。
7. **把 lint 通过当作行为正确**：格式校验只证明文件结构合法，不证明流程按预期执行。

## 检验标准

1. **可复述**：任意第三人读完技能，能说出「它什么时候开始、在哪停、回来给你什么、你怎么验收」。
2. **触发可判定**：触发语是可直接匹配的原句或明确时间点，不含意图猜测。
3. **检查可观察**：每个检查项都指向具体的页面/文件/列表/通知，不依赖执行者自述。
4. **闸门前置**：所有不可逆动作之前都有具体项确认，红线写明越界后的上报动作。
5. **复测有对照**：有一次同句复测记录，能说明改了什么、输出变了哪里。

## 实施检查清单

- [ ] 触发语是可匹配原句或明确时间点，没有「当用户需要时」这类意图描述
- [ ] 步骤写明每步的输入来源与交付物，无「智能处理」式黑箱动词
- [ ] 每个检查项都指向可观察位置（页面/文件/列表/通知），并写明未达成时的报告话术
- [ ] 所有不可逆动作前都有具体项确认（展示时间、金额、收件人）
- [ ] 红线用否定式写死，并写明越界后停下上报
- [ ] 已用同一句触发语完成一次改前/改后复测
- [ ] 发布前已跑格式校验，且没有把校验通过当作行为正确

## 正例

「每周一导出销售报表」的四问填写：

- **何时开始**：「说『出周报』时；每周一 9:00」；
- **怎么做**：「读上周订单表 → 按区域汇总 → 生成一页 Markdown 写到 reports/」；
- **怎么检查**：「打开报表确认 4 个区域齐全、合计等于明细之和；缺区域就写『某区无数据』」；
- **哪里要确认**：「发送给主管前先贴出收件人与三行摘要，等回复确认」；
- **红线**：「不修改原始订单表、不代发未确认邮件、找不到表就停下说明」。

## 迁移示例

- **外包/实习生 SOP**：四问对应「什么时候开始做、按什么步骤、交付前自查什么、哪些事必须问我」，红线即禁止越权事项。
- **自动化脚本/RPA 任务**：触发对应定时或事件，检查对应日志断言与输出文件，确认对应 dry-run 与人工审批节点。
- **个人知识管理流程**：触发对应「收到某类材料时」，检查对应「归档路径与索引是否更新」，确认对应「是否覆盖原文件」。
- **已知边界（不可外推）**：一次性任务、结果不可观察的任务、触发条件仍在变化的任务，均不适合资产化，写提示词直接做更快。

- **沉淀会话**：`sc-20261116-trae-agent-camp-02-pattern`（2026-11-16，E→V→C 入库；C 只出提交提案）。
- **去重判定**：入库前比对 6 个候选模式（`skill-five-elements-model`、`skill-standardized-workflow-pattern`、`skill-progressive-disclosure-encapsulation`、`four-element-task-brief`、`output-behavior-specification`、`subagent-atomic-task-template`），从作用对象（可复用流程资产 vs 文档质量 / 操作可靠性 / 一次性委托）／核心动作（四问结构化 vs 质量审查 / 重试设计 / 停点回报）／所处层级（内容生成阶段 vs 质量门 / 执行可靠性 / 下发阶段）三维度裁定不重复。
- **成熟度校验（沉淀 V 门）**：维持 **L1-draft**；「四问减少返工」为上游推断而非对照测量，升级条件写入 `maturity_note`。
- **抽象化纪律**：正文只保留四问的通用动作，课程中的五个场景技能与具体提示词保留在上游知识包未复制。
- **共同证据基座说明**：本模式与同批入库的 `evidence-first-repair`、`single-output-work-slicing`、`dual-gate-irreversible-action` 共享同一上游知识包，属同一案例族，**互不构成独立验证**；库内成熟度不得因同批入库或相互引用而抬升。
- **沉淀 V 门（4 视角）**：① 魔鬼代言人——四问可能退化为「填表仪式」，且填全不等于触发语选对；已在步骤 1 要求「原句而非意图」并在检验标准 2 设可判定条件；② 新人视角——原稿未说明四问之间关系，已补「确认点是做之前问、红线是绝不做」的分工；③ 老板视角——检验标准对准「第三人能否复述起止与验收」，不以文档完整度替代行为可控性；④ 未来视角——当平台把技能模板内建为表单并强制四问时，本模式退化为「填表指导」，模式重心转向触发语选择与检查点设计，复查触发器为「平台是否已内置技能四问模板」。
