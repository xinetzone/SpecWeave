# 只讲不改勘察法（Explain-Only Reconnaissance）

## 模式类型

协作纪律（执行类）。作用于**首次接触陌生代码库**的认知阶段，产出为系统地图、落点判断与零改动证据；不负责后续改造。

## 模式概述

第一次把协作者（尤其是 AI）引入既有代码库时，最自然的做法是「边看边改」：看到一个能优化的地方顺手改掉，用改动证明理解。这条路在陌生代码库上系统性失效——**理解尚未建立时的改动，其正确性无法自证**：改的人不知道自己破坏了什么，审查的人没有基线可比，回滚又依赖本来就不熟的工具链。

本模式的核心转向是：

> **首次接触只做解释、不做修改，并以「工作区零改动」作为本次勘察的验收条件；只有当三问都能答清、且改动清单为空时，才允许进入改动阶段。**

支撑证据来自一个手机 Agent 课程知识包（[上游知识包](../../../../../projects/awesome-okf-xs/doc/bundles/jishu/ai/ecosystems/trae/trae-agent-camp-01/index.md)）：

1. 讲师给出的经验是「第一次让 AI 看项目时，只让它讲，不让它改」（F-038）；
2. 课程给出的首次勘察提示词以三问开头、以「先只讲解、不修改任何文件」收尾（F-041）；
3. 连排障求助模板也保留了同一收尾约束：「先只分析、不修改文件」（F-074）；
4. 课程的落点讲解只描述各目录职责（界面 / 记忆 / 技能说明书 / 读屏点击），不含任何改动动作（F-091）。

> 为什么把「零改动」而不是「讲得对」当验收条件？「讲得对」无法机械判定，「改动清单为空」可以——把不可判定的目标换成可判定的目标，是把纪律变成门禁的关键一步。

## 触发场景

**适用于**：

- 协作者（人或 AI）**第一次**接触一个既有代码库/工程；
- 代码库没有完整测试保护，或测试覆盖未知——此时误改的代价高于慢一点；
- 需要先产出「系统地图」（模块职责、请求链路、改动落点）供后续决策；
- 交接、审计、尽调等**只读目的**的进入场景。

**不适用于**：

- 已有基线、有版本控制与测试保护的小范围改动——直接改 + 跑测试更快；
- 紧急故障处置中「先看再改」会错过止损窗口（此时先止血，事后补勘察）；
- 目标本身是产出文档/教程（那是另一个模式：把源码转成可读产物）；
- 工作区不在版本控制下——无法机械证明「零改动」，本模式退化为口头约束。

## 核心做法（5 步）

### 步骤 1：先定义三问

在让协作者开口之前，先把「勘察要回答什么」写成三个问题：

1. **关键模块在哪**：负责核心职责的目录/文件分别是哪些；
2. **一次请求经过哪几步**：从入口到副作用落点的链路（含跨进程/跨设备边界）；
3. **改某类行为该动哪里**：给定一个具体需求，落点在哪个文件/目录。

- 三问必须绑定**具体需求**，否则回答会正确但无用（「这个项目分为若干模块」）。
- 此步产出：三问清单。

### 步骤 2：把「不要改」写死在提示词末尾

约束放在结尾而不是开头，且用否定式祈使句：「先只讲解，不要修改任何文件」。

- **主手段**：在任务描述末尾追加固定句；**替代手段**：无提示词控制能力时（如直接给人交接），改为「本阶段交付物是讲解，不含提交」的书面约定。
- 「先看看」「了解一下」不构成约束——正向描述不会阻止写操作，只有显式禁止才会。
- 此步产出：带约束的勘察任务。

### 步骤 3：要求用非开发者能懂的话复述

让协作者把系统讲成「给新人听」的版本，而不是术语堆砌。

- 复述的意义在于**暴露理解空洞**：能讲清「一句话从输入到落地经过哪几步」，说明链路真的通了；只会罗列目录名，说明只做了文件系统扫描。
- 此步产出：一段可被第三方理解的系统说明。

### 步骤 4：人工核对说法与目录/入口是否一致

拿复述直接对账：提到的文件是否存在、链路描述与入口代码是否吻合、落点判断是否指向真实文件。

- 核对重点不是「说得对不对」，而是「**有没有把不存在的东西说成存在**」——这是最典型的错误形态。
- 此步产出：核对记录（不一致项清单）。

### 步骤 5：用版本控制的变更列表确认零改动

以版本控制状态（未跟踪文件 + 已修改文件）作为零改动的证据，而不是凭印象判断。

- **主手段**：读取工作区状态，确认除勘察记录外无新增/修改；**替代手段**：无版本控制时，用文件哈希快照前后比对。
- 核查范围要**覆盖工作目录之外**：临时目录、缓存、用户配置目录中的落盘同样算改动；「本次只读了代码」这类**自述不构成证据**，以状态输出为准。
- 此步产出：零改动证据（状态输出或哈希对照）。

## 反模式

1. **只写「先看看」，不写「不要改」**：正向描述不构成禁止，协作者仍可能顺手改动，且事后无从追溯。
2. **把「讲解」理解成「改完再解释」**：先改再讲，讲的是改动后的系统，原始结构永久丢失。
3. **不做零改动核对，靠感觉判断**：没有证据的「没动过」在出问题时无法自证。
4. **三问不绑定具体需求**：得到的是一份正确的目录说明书，对「该改哪里」没有信息量。
5. **在无版本控制的目录做勘察**：无法证明零改动，模式的核心验收条件失效。
6. **勘察阶段就开始「顺手优化」**：哪怕改动很小，也把「零改动」这个唯一可判定的验收条件破坏了。

## 检验标准

1. **三问可答且可核对**：每个答案都指向真实存在的文件/目录，不含不存在的路径。
2. **零改动可证**：变更列表为空（或仅含勘察记录），有可复核的状态输出/哈希对照。
3. **可转述**：非开发者读一遍系统说明，能说出主要模块职责与一次请求的大致链路。
4. **落点可执行**：给定一个新的小需求，勘察结论能指出落点文件，而不是「需要进一步调研」。
5. **不含隐性改动**：没有新增临时脚本、备份文件、调试代码被留在工作区。

## 迁移示例

- **新成员入职**：先让其画系统地图并口头讲解，暂不分配改动任务；步骤 5 的零改动证据对应「第一周无提交」。
- **遗留系统交接**：交接期内只做只读勘察与讲解录像，验收标准是「接手方能在不看代码的情况下讲清主链路」。
- **第三方代码尽调**：只读进入，产出落点表与风险清单，不给任何 PR。
- **已知边界（不可外推）**：已有测试保护的小范围改动、紧急止血场景，以及目标就是产出可读文档的场景，均不适用本模式。

| [no-touch-list](../governance-strategy/no-touch-list.md) | 相邻易混 | 对方是**重构阶段**的禁改边界清单（哪些模块本次不动），本模式是**首次接触阶段**的交互约束（这一轮完全不动）；在情形「已建立基线、要规划本轮重构范围」下应使用对方，本模式此时退化为冗余 |

| [base-first-minimal-customization](../governance-strategy/base-first-minimal-customization.md) | 上位调用 | 本模式是该模式步骤 2 的独立化；对方把「勘察」放在「已跑通基线」之后，顺序不可颠倒 |
