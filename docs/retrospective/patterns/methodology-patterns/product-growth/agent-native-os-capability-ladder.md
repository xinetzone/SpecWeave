# 终端操作系统智能体原生化四级演进（Agent-Native OS Ladder）

> 桌面、移动、嵌入式等终端操作系统的 AI 化不是一次发布会完成的功能切换，而是一条有严格先后依赖的四级阶梯：**应用插件 → AI 子系统 → 模型枢纽 → 智能体底座**。跳级营销会在交付时被权限模型与安全审计打回原形。

## 一、核心定义

终端平台的 AI 能力沿四个层级演进，每一级以前一级的工程能力为前提：

| 级别 | 名称 | 核心形态 | 关键新增能力 | 典型标志 |
|---|---|---|---|---|
| **L1** | 应用级插件 | 用户自带 API Key，单个应用调云端聊天模型 | 需求验证 | 应用商店里的"AI 助手插件" |
| **L2** | 子系统级 | 系统提供统一 AI 接口，系统应用共用能力层 | 统一接口、系统应用智能化、权限审计起步 | 搜索/剪贴板/截图等系统应用普遍 AI 化 |
| **L3** | 模型枢纽级 | 同时纳管多家云端模型与本地模型，支持私有知识库与离线推理 | 多模型可替换、本地推理、知识库 | 设置中可选模型供应商，本地小模型可离线运行 |
| **L4** | 底座级 | 模型/记忆/工具/系统权限/桌面能力收敛为统一架构，智能体以**开放协议**直接调用系统 | 智能体运行时、开放协议（MCP 类）、技能签名仓库、自研与第三方智能体权限对等 | 第三方智能体不经私有 SDK 即可完成"读屏→调用应用→写回"全链路 |

> 命名注意：此处 **L1-L4 是能力演进阶梯标签**，描述平台 AI 化所处阶段，与模式库 frontmatter 中表示模式验证成熟度的 L1-L4（以及四层架构/四层防御等同名分层）含义不同，引用时勿混用。

**反直觉的核心判断**：到了 L4，竞争对象从"自带哪个大模型"或"应用商店有多少应用"变为**智能体运行时生态**——谁定义智能体调用系统能力的协议、权限弹窗与审计规则，谁掌握下一代入口。因此 L4 的本质决策不是 AI 功能多少，而是**协议开放性与权限对等性**。

## 二、适用边界

**适用于**：

- 桌面/移动/嵌入式终端 OS、浏览器、IDE、机器人控制平台等**持有系统能力可暴露**的平台型产品
- 需要把 AI 从营销卖点变为可审计系统能力的团队
- 需要判断某竞品"Agent OS"宣传处于真实哪一级的评估工作

**不适用于**：

- 无系统能力可暴露的纯云端/纯网页应用（其演进路径参考 [vertical-saas-mcp-capability-exposure.md](vertical-saas-mcp-capability-exposure.md)）
- 实时性或安全隔离要求禁止任何 Agent 调用系统能力的封闭设备（如特定工控/医疗控制器）
- 尚处 PMF 验证前、AI 需求真实性未知的产品（停在 L1 验证即可，勿提前建底座）

## 三、核心步骤（逐级条件，不建议跳级）

1. **L1 应用级——先验证需求，不建平台**：允许用户自配 Key 调用外部模型，以最小投入观察真实使用频次与场景。此级不承诺系统级能力。
2. **L2 子系统级——抽象统一 AI 接口**：把模型调用收敛为系统接口层，搜索、剪贴板、助手等系统应用共用；**同步启动权限审计**，记录每个 AI 功能访问了哪些系统资源。
3. **L3 模型枢纽级——纳管多模型与本地推理**：统一接口向上屏蔽供应商差异，同时接入多家云端模型与可离线的本地模型，支持私有知识库；此级必须允许企业/高级用户替换与私有化部署模型，避免供应商锁定。
4. **L4 底座级——建设智能体运行时**：将模型、记忆、工具、系统权限、桌面/窗口能力纳入统一架构；智能体经**开放协议**（MCP 或同类标准）发现与调用工具；技能/工具以签名仓库方式分发；自研智能体与第三方智能体走同一权限弹窗与审计链路。
5. **每级补齐安全侧（贯穿条件）**：L2 起做权限审计；L3 做模型与数据边界管理；L4 必须前置 Agent 行为边界（误操作回滚/确认机制）、技能签名与供应链治理（SBOM、依赖审计），否则底座能力越强事故面越大。

**级间跃迁的检验门槛**：

- L1→L2：AI 功能散落在多个独立应用中、各自管理 Key 与错误处理，重复建设成本已可观测。
- L2→L3：出现多模型并用、离线/私有化诉求与知识库诉求，单一模型接口开始限制交付。
- L3→L4：第三方智能体需要操作系统级能力（不只是对话框），且权限模型足以支撑开放调用。

## 四、检验标准（L4 是否名副其实）

让一个**第三方**开发者在不使用厂商私有 SDK 的前提下，接入一个新智能体并完成全链路：

1. 读取屏幕/上下文 → 2. 调用系统应用或设置完成操作 → 3. 写回结果；

且该智能体与厂商自研智能体：① 走同一套用户授权弹窗；② 进入同一条审计日志；③ 技能包经同一签名与供应链检查分发。三条全部满足才是 L4；只能模拟点击、或只允许自有智能体调用系统能力的，仍属 L2-L3。

## 五、证据案例

| 案例 | 四级对应 | 证据强度 |
|---|---|---|
| openKylin（1.0→2.0→SP2→3.0；自 1.0 起四个大版本约三年、自 2022 社区发起计约四年） | L1：1.0 开始菜单上架大模型插件、用户自配 Key（F-044）；L2：2.0 建 AI 子系统与统一接口、系统应用智能化（F-045）；L3：SP2 接入六家云端模型 + 本地模型 + 文档知识库（F-022/F-046）；L4：3.0 智能体开放底座，智能体经 MCP 调桌面能力，技能仓库 openkylin-skills，预装 Token 中心（F-047）。**L4 为部分达标**：按第四节判据，开放协议与签名技能仓库有证据，但自研/第三方权限对等弹窗、统一审计、签名供应链分发三条件尚无公开事实闭合 | 强（L1-L3 官方版本特性逐版可查；L4 仅协议层证据充分，事实链见[源调研报告](../../../../knowledge/tech/openkylin/index.md)） |
| 统信 UOS V25（2026-04） | 内置不可变系统并向 Agent OS 演进，AI SDK V2、支持 MCP 与 Skills 外挂 | 中（源调研 F-057 单源记录同方向，未做逐版本回溯） |

> 引用纪律：openKylin 官方给出的性能类数字（如 RISC-V AI 推理提速倍数）与本模式无关，模式只采用**能力形态**事实；"3.0 是智能体原生操作系统"为厂商定位措辞，L4 判定以第四节的第三方全链路检验为准，不以厂商命名为准。

## 六、反模式

| # | 反模式 | 后果 | 正确做法 |
|---|---|---|---|
| 1 | **跳级营销**：只有 L1 插件水平即发布"Agent OS"，没有系统级协议与权限模型 | 第三方无法接入、企业无法验收，宣传反噬产品信任 | 用第三节逐级条件自查，定位宣传措辞不超过实际级别 |
| 2 | **私有协议围墙**：只允许自有智能体调用系统能力，第三方只能模拟点击 | 智能体生态退化为一家应用，L4 的网络效应不成立 | 采用开放协议，自研与第三方权限对等 |
| 3 | **模型绑定单一供应商**：L3 仍不能替换模型或本地部署，用 Token 补贴制造"开机即用" | 补贴即锁定；数据合规与成本谈判均无退路 | L3 起支持多模型与本地/私有化部署，补贴与解耦分开表述 |
| 4 | **只讲智能不讲审计**：Agent 可操作桌面与文件，却无签名、SBOM 与行为日志 | 误操作与恶意技能无法追责，企业市场无法准入 | 步骤 5 安全侧前置：行为边界、签名分发、供应链审计 |

## 七、与相邻模式的边界

- 与 [vertical-saas-mcp-capability-exposure.md](vertical-saas-mcp-capability-exposure.md)：该模式是**外向**视角——SaaS 厂商如何通过 MCP 把自身能力开放给外部通用大模型；本模式是**内向**视角——终端平台如何把 AI 能力逐级内化进系统，其 L4 才涉及 MCP。两者在协议层相遇，方向相反。
- 与 [four-layer-ai-capability-architecture.md](../../architecture-patterns/four-layer-ai-capability-architecture.md)：后者是 AI 能力开放平台的**静态分层架构**（协议—技能—CLI—视觉，按使用者分层）；本模式是平台 AI 化的**时间演进阶梯**（按成熟度分级）。可用本模式判断"现在在哪一级"，用四层架构设计"这一级怎么对外分层"。
- 与 [vertical-scenario-ai-three-elements.md](vertical-scenario-ai-three-elements.md)：后者讲 AI 产品竞争力三要素（行业功能/工作流/合规风控），回答"做什么 AI 功能"；本模式回答"以什么系统形态承载"。
- 与 [ai-reliability-four-layer-defense.md](ai-reliability-four-layer-defense.md)：后者为 AI 可靠性的纵深防御设计，是本模式步骤 5 安全侧在 L3-L4 的展开参考。

## 八、跨域迁移

- **浏览器与 IDE 的 Agent 化**：从内置聊天侧边栏（L1）到统一工具接口（L2）、多模型路由（L3）、MCP 工具调用权限分级（L4），可直接用本阶梯自评。
- **手机厂商系统级智能体**：语音助手插件 → 系统 AI 服务 → 端云多模型 → 智能体调系统设置/跨应用操作，权限弹窗与审计是 L4 准入线。
- **机器人与具身智能操作系统**：openKylin 3.0 已出现人形机器人、机械臂等适配镜像；L4 的"工具调用"在该域即"动作调用"，权限与安全侧要求更高。
- **本仓 Skill/MCP 工具体系**：工具能力是否以开放协议暴露、第三方 Skill 与内置 Skill 是否同权、分发是否有签名审计，均可借 L1-L4 做能力成熟度自评。

## 九、成熟度与升级条件

- **L1（单案例完整证据链 + 1 个同向佐证）**：openKylin 四个大版本逐级跃迁的形态证据完整但来自单一项目官方材料；统信 V25 仅记录到同方向，未做逐版本回溯；跨域（浏览器/IDE/手机 OS）迁移为推断，尚待第二案例填充。
- 升级 L2 的条件：在终端 OS 之外的一个平台品类（如手机 OS 或 IDE）完成同样四级证据链回溯，并记录至少一个**跳级失败案例**（L1 宣传 L4 后回退），为反模式 1 提供反面实证；另需跟踪 MCP/ACP 等开放协议的标准化结果（协议更替将修订 L4 判据）。
