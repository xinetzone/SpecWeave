# 统一契约工具编排层（Unified-Contract Tool Orchestration Layer）

## 模式概述

当一个系统需要让**同一个消费者**（AI agent、上层服务、业务进程）使用多个异构外部工具时，最自然（也最常见）的做法是"每个工具单独接入"：为 Ghidra 写一套调用、为 ADB 写一套命令、为 EVM 写一套接口——结果消费者要学 N 套协议，每新增一个工具就要从头写集成，工具的返回值格式各异也无法统一消费。这条路径在目标域越多、工具越异构时越快地失效：单套 MCP 服务被拆成 N 个碎片，agent 的编排与证据理解成本随工具数线性膨胀。

该模式把连接从"逐工具吸管"改为"统一契约适配层"：

> **不改造各工具、也不为每工具做独立接入，而是在消费者与所有异构工具之间插入一层统一契约：每个工具经一个适配器（Provider）接入，适配器把"工具结果 + 元数据 + 运行时观测"规整为该契约下结构化的工具与证据，消费者只经这一个入口、一套契约消费全部工具；能力全集以契约为准，CLI/前端只是该契约的一个投影。**

"统一契约"的厚度不在分析/计算引擎，而在**编排与证据标准化**：真正计算发生在被适配的工具内，编排层只负责发现工作、发起调用、收束输出、把结果规整为消费者可消费的证据，并上报"分析了什么、覆盖到哪、还有哪些未知"。

支撑该模式的案例证据（详见[上游 REA 知识包](../../../../../projects/awesome-okf-xs/doc/bundles/jishu/ai/products/rea/index.md)事实编号）：

1. **分析计算落在被适配工具内、编排层只做规整**：REA 把 Ghidra/IDA/Hopper/JADX/ADB/EVM/WASM 等经 Provider 适配器接入，依赖第三方引擎；它自己是"适配编排层"而非反编译器（F-030/F-031/F-032/F-042）。
2. **能力以契约单一事实源聚合**：所有工具契约聚合为 `TOOL_CONTRACTS`（24 组 spread、100+ 契约化工具、15 种 kind ），CLI 129 命令经别名映射到这些契约工具，存在"仅有 MCP 工具、无 CLI 命令"的能力（契约全集 ⊇ CLI 子集，F-013/F-016/F-017/F-019~F-024）。
3. **本地优先 + 有界证据**：不托管运行时、不沙箱目标、被动附着而非拉取，并把 evidence/unknowns 随结果上报（F-045/F-050/F-051/F-053/F-043）。

## 触发场景

**适用于**：

- 一个消费者需要统一使用**多个、异构**外部工具（不同厂商、不同协议、不同返回值形态），且目标域数量在增长；
- 这些工具由用户/下游**自备**（无法或不应被改造集成进你的引擎），你只负责发现、发起、规整；
- 消费者（agent）的编排与理解成本已随工具数上升，需要把"每工具一套协议"降为"一套契约"；
- 需要新增目标域时希望以"加一个适配器 + 加一个契约 kind"的方式扩展，而非改消费者端。

**不适用于**：

- 工具数量少且形态同构、一次接入成本已低——统一契约层的设计与维护成本高于它省下的连通成本，单个或同类两三个工具直接用原生接口即可；
- 工具之间无任何可统一的返回值或调用形态，硬造契约会引入无谓抽象（此时退化为各自接入 + 上层分别处理）；
- 你有权改造并愿意长期维护工具本体——此时直接内建更适合，编排层反而多一环。

## 核心做法（五步）

### 步骤 1：识别"消费者—工具"边界，锁定统一入口

确定单一消费者（agent/上层服务）与它需要消费的全部目标域，明确要给消费者**一个**入口（在 Agent 工具场景即一个 MCP 服务名/一组统一工具命名空间）。产出：一份目标域清单与单一入口名。

### 步骤 2：为每个工具写适配器（Provider），而非改造工具

对每个目标域写一个独立适配器，暴露统一的"发现工作—发起调用—收束输出"接口（如 `AnalysisProviderCandidate` 这类可插拔接口）。适配器持有外部工具句柄（客户端/启动器/传输），不嵌入引擎本体。产出：每个目标域一个 `*Provider` 适配器。

### 步骤 3：用"契约单一事实源"聚合全部能力

把全部工具契约（名称、入参 schema、出参 schema、副作用）集中为一份只读的契约聚合表（如 `TOOL_CONTRACTS`），作为能力全集与类型约束的权威来源；所有入口（CLI、MCP、运行时）都从这份契约派生，而非各自维护一份能力清单。契约全集应当 ⊇ 任一前端子集。产出：统一契约聚合表。

### 步骤 4：让前端只是契约的投影

CLI/脚本等交互型前端通过"命令→契约工具"的映射表触达工具；若某个能力仅在 API/契约暴露而无需命令，可保留"仅契约、无 CLI"；会话健康与"当前哪些工具可用"的权威判断放契约层。产出：入口路由 + 命令别名映射 + 会话健康源。

### 步骤 5：规整证据、声明边界

每条调用结果在返回消费者前规整为统一证据结构（结果 + evidence + 未知项），并明确声明"本地优先、不托管运行时、沙箱与否、是否被动附着"等边界责任落在何处。产出：统一证据结构 + 边界声明。

## 反模式

1. **逐工具吸管接入**：为每个工具写一套独立调用与返回值解析，消费者要学 N 套协议——工具越多，编排与理解成本线性膨胀，是统一契约层要消除的核心成本。
2. **契约与前端各自为政**：CLI 命令清单与 MCP 工具定义分开维护、不对齐——用户与 agent 看到的"能力全集"不一致（如存在 CLI 有而契约无、或契约有而 CLI 无却无人知晓），契约形同虚设。
3. **黑盒整合 / 过度封装**：把工具内部机制完全隐藏、或把每个工具都包一层自己的 API——要么出问题无法下钻到底层工具排查，要么把"学到的工具知识"破坏掉，用户既学不到工具又无法迁移。
4. **强行造契约为异构而异构**：对无统一形态、一次接入成本已低的场景也硬塞抽象层——过度工程，维护成本高企，反模式地增加而非降低复杂度。
5. **沙箱/托管承诺越界**：自称"沙箱化/安全托管"却并非如此（如进程捕获非沙箱）——边界声明与真实能力不符时，信任瞬间崩塌（对应"有界证据"被伪装成"安全保证"）。

## 失败案例

> 本模式为 L1-draft（单一 REA 案例）。下面三条为同构反案例——均在未应用本模式的相邻场景中反复观察到的失败形态，转述为可对照的失败样本，非 REA 本身失败。

1. **"逐工具吸管接入"的系统性失败（数据编排场景）**：某数据服务平台接入多个异构数据源（数据库/文件/消息队列）时各自独立读写、各自解析返回值，结果每个数据源一套连接与格式转换代码，新增第六个数据源时改动横跨消费端全部分支，随后因"功能重叠"触发重构——正是本模式反模式 1 在现实中的等价物，未设统一 IO 契约所致。
2. **"黑盒适配器"信任崩塌（CLI 工具集成场景）**：某内部研发平台把第三方 CLI 各自封装、隐藏内部机制，用户侧既能执行却无法下钻定位输入来源与失败点，遇到一次"吞掉错误但仍返回成功"的边界后整体弃用该适配层——对应反模式 3"黑盒整合"的代价：一旦适配器掩盖了工具真实失败，信任即断。
3. **"契约漂移"成空壳（MCP/服务集成场景）**：某团队同时维护订单 API 的 OpenAPI 定义与前端 TypeScript 类型两份"能力清单"，两者由不同人维护、长期不对齐，某字段仅契约有而另端无、无人察觉，线上联调才暴露——正是反模式 2"契约与前端各自为政"直接导致的隐性漂移。

## 反目标用户/场景

本模式明确**不服务**以下用户/场景，识别到这些特征即应放弃引入（对应"不适用于"）：

1. **工具少且同构的小型脚本宿主**：只有一两个工具、且返回形态一致——统一契约层的设计与维护成本高于它省下的连通成本，直接用原生接口更短。
2. **有权长期改造工具本体的平台方**：工具属于你、愿意持续维护其内部——此时直接内建能力更合适，插入编排层反多一环（本模式假设"工具为用户/下游自备、不可改造"）。
3. **强实时/极低延迟的紧耦合路径**：要求纳秒级内联调用、无任何适配回传空间——每一层适配都引入回传、证据规整的时延，紧耦合直连更优。
4. **一次性的临时整合任务**：目标域不会增长、只跑一次就散——为一次性需求搭建可持续编排层是过度工程，直接用一次性脚本完成更经济。

### 早期预警信号表

| # | 信号 | 行为 |
|---|---|---|
| 1 | "每新增一个工具都改消费端"——新增目标域要同时动消费者/入口代码 | 已出现逐工具耦合，应立即引入统一契约 |
| 2 | 消费端代码里出现"按工具名分支"的 return 解析（`if 工具A … elif 工具B …`） | 返回值形态分裂，需契约归一 |
| 3 | 存在多份并行维护的"能力清单"（CLI 命令表 / API 文档 / 类型定义）且正交不一致 | 契约漂移前兆，收敛为单一事实源 |
| 4 | 适配层把工具真实失败吞掉、只回成功 | 黑盒隐患，须保留 evidence 下钻与失败透传能力 |
| 5 | 宣称"沙箱/托管"但其边界声明与真实行为不符 | 边界越界信号，须回退到诚实声明 |

## 检验标准

模式被正确执行后应满足主要标准并留下可审计产物：

1. **单一入口可用**：消费者只经一个入口/一套契约即可触达全部已接入目标域，无需分别了解各工具协议；
2. **新增成本受限**：新目标域只需"加适配器 + 加契约 kind"，消费者端与既有已接入目标域零改动；
3. **能力全集一致**：契约聚合表与所有前端（CLI/MCP）导出的能力清单一致，无"仅某端有"的隐含漂移；
4. **证据可审计**：每条结果带 evidence/unknowns，可信度可判断；分析覆盖率与未知边界对消费者可见；
5. **边界诚实**：沙箱/托管/离线/附着等边界声明与真实行为一致，无越界承诺。

## 迁移示例

- **统一 LLM 网关**：把 OpenAI/Anthropic/本地模型统一到一个 `ModelProvider + ChatContract` 适配层，上游服务经单一补全契约消费，新增模型只加 Provider——正是本模式在"模型编排"领域的同构；
- **数据处理流水线的统一 IO**：把多源数据接入（数据库/消息队列/文件）统一到一个 IO 契约与 Reader 适配器，计算框架经单一读取契约消费，避免每数据源一套读写逻辑；
- **IDE 扩展系统**：把调试器/Git/语言服务器统一到 `Provider + 能力契约`，插件经单一命令契约调用，与 REA 的 Provider-Contract 结构同构；
- **已知边界（不可外推）**：工具少且同构、或你有权长期改造工具本体时不应引入本模式；本模式聚焦"消费编排"，不涉及工具本身的分析能力。

## 与现有模式的关系

| 相关模式 | 关系 | 说明 |
|---|---|---|
| [integration-over-invention](../concepts/integration-over-invention.md) | 层级互补 | integration-over-invention 是**部署交付面**：把多个工具打包成一键部署方案给终端用户；本模式是**能力消费契约面**：把外部工具统一到单一契约供一个消费者经单入口消费。一个面向"方案可部署"，一个面向"能力可消费"，不在同一层级 |
| [vertical-saas-mcp-capability-exposure](../product-growth/vertical-saas-mcp-capability-exposure.md) | 方向互补 | vertical-saas 是**外向**：SaaS 把自己的能力封装为 MCP 工具开放给外部大模型；本模式是**反向整合**：把用户自备的第三方工具经适配器接入统一契约供自身消费。都在 MCP 协议层相遇但方向相反 |
| [agent-native-os-capability-ladder](../product-growth/agent-native-os-capability-ladder.md) | 相邻易混 | 该模式是终端平台把 AI 能力**逐级内化**进系统的自评阶梯（L1-L4，L4 才涉及开放协议）；本模式是**工具编排消费**的横向契约层，聚焦"多异构工具的单一消费入口"，二者不在同一维度 |
| [offline-first-architecture](../concepts/offline-first-architecture.md) | 目的区分 | offline-first 是保证离线完整可用；本模式的"本地优先 + 不动用户资产"是可信边界设计而非功能目标，二者关注点分离 |
