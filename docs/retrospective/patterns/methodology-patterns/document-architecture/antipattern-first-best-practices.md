# 反模式优先最佳实践写作法

## 模式概述

撰写技术教程、规范文档或API指南的"最佳实践"章节时，采用**先列反模式（不要做什么）、再列检查清单（应该做什么）**的双轨结构，而非传统的"最佳实践清单"。该方法由Knowledge Catalog Wiki最佳实践章节验证，核心洞察是：告诉人"不要做什么"比告诉"要做什么"信息密度更高、记忆更强、边界更清晰。每个反模式必须包含典型表现、主要后果、正确做法三要素，与分级检查清单配合使用效果最佳。

## 问题现象

传统"最佳实践"章节的常见问题：

1. **正确的废话**：写了一堆"应该写清晰的代码"、"应该做好测试"这类人人都知道但无法执行的建议
2. **没有边界**：只说"应该怎么做"，不说"什么情况下不该做"，读者无法判断适用场景
3. **无法自检**：没有检查清单格式，读者看完无法对照自己的代码/文档是否合规
4. **记忆薄弱**：正面建议容易遗忘，踩坑的痛苦记忆远比正确做法深刻
5. **缺乏优先级**：所有建议并列，读者不知道哪些是致命错误、哪些只是优化建议

## 核心逻辑

```
最佳实践章节 = N个反模式（负面边界） + 分级检查清单（正面指引） + FAQ（高频疑问）
```

### 为什么反模式优先？

1. **信息密度更高**：指出一个错误做法，隐含了正确方向；正面建议需要更多文字说清边界
2. **记忆锚点更强**：踩坑的痛苦记忆是天然锚点，读者更容易对号入座
3. **快速诊断价值**：读者可以快速扫描反模式列表判断"我是不是在坑里"
4. **隐含边界条件**：反模式天然定义了最佳实践的适用范围——"在X条件下做Y是反模式"
5. **心理抵触更低**：告诉人"不要做什么"比"你应该怎么做"说教感更弱

## 标准写作流程

### 第一步：收集反模式（先做这个！）

在写任何正面建议之前，先列出5-7个反模式。来源：

| 来源 | 收集方法 |
|------|---------|
| 自己踩过的坑 | 回忆实践中犯过的错误 |
| 常见问题/Issue | 扫描GitHub Issues、Stack Overflow高频问题 |
| Code Review评论 | 总结CR中反复出现的问题 |
| 官方文档中的"警告" | 官方文档中⚠️标注的注意事项 |
| 新手误区 | 观察新人常犯的错误 |

**反模式四象限筛选**：
- 频率高 + 后果严重 → 必须列入（P0）
- 频率高 + 后果轻微 → 建议列入（P1）
- 频率低 + 后果严重 → 选择性列入（P2，标注"罕见但致命"）
- 频率低 + 后果轻微 → 不列入

### 第二步：为每个反模式写三个要素

每个反模式必须包含三个部分（缺一不可）：

```markdown
### 反模式N：<一句话名称>

**典型表现**：<怎么识别这个反模式？具体行为、代码、写作方式是什么样的？>
（给出可观察的特征，让读者能对号入座）

**主要后果**：<为什么不应该这样做？会导致什么问题？>
（列出2-4个具体后果，最好有严重程度区分）

**正确做法**：<应该怎么做？>
（给出正面指引，和前面的表现/后果对应）
```

### 第三步：编写分级检查清单

反模式写完后，提供可勾选的检查清单，按要求级别分类：

| 分类 | 标记 | 使用场景 |
|------|------|---------|
| 基础合规（必填） | 无特殊标记 | 必须满足，不满足就是格式错误/功能错误 |
| 推荐字段/做法 | 💡 强烈建议 | 建议满足，不满足不影响正确性但影响质量 |
| 生产环境必填 | 🔒 生产环境必填 | 开发/测试可以放宽，上线前必须满足 |
| 场景特定 | 📐 涉及XX时必填 | 只有在特定场景（如涉及指标/涉及安全）才需要 |
| 建议/优化 | ✅ 建议 | 优化项，根据情况采用 |

清单格式使用 `- [ ]` 可勾选Markdown语法，方便读者复制后实际打勾。

### 第四步：补充FAQ（可选但推荐）

检查清单之后，用FAQ回答5-8个高频疑问：
- 新手最常问的"为什么要这样？"
- 容易误解的概念澄清
- "如果我不这样做会怎样？"
- 和其他工具/方法的关系

## 标准模板

```markdown
## 一、N个必须避免的反模式

### 反模式1：<一句话名称>

**典型表现**：<可观察的行为描述>

**主要后果**：
- <后果1>
- <后果2>
- <后果3>

**正确做法**：
- <做法1>
- <做法2>

### 反模式2：...

（重复上述结构）

---

## 二、<主题>检查清单

发布/提交/上线前，对照以下清单检查：

### 基础合规（必填）
- [ ] 检查项1
- [ ] 检查项2

### 推荐项（强烈建议）
- [ ] 检查项3

### 生产环境必填
- [ ] 检查项4

### <特定场景>（涉及XX时）
- [ ] 检查项5

---

## 三、常见问题FAQ

### Q1: 问题？
A: 回答。

### Q2: ...
```

## 实战案例

### 案例：Knowledge Catalog OKF最佳实践（本次验证）

来源：[05-best-practices.md](../../../../../projects/awesome-okf-xs/doc/bundles/jishu/viz/animejs-threejs-adapter/concepts/05-best-practices.md)

**产出结构**：
- 5个反模式（frontmatter缺失/巨型Bundle/信任元数据造假/认证计算缺失/链接混乱）
- 24项分级检查清单（基础合规4项+推荐5项+信任5项+认证计算8项+链接3项）
- 6个FAQ
- 术语速查表

**验证效果**：
- 反模式部分被用户选中导出为表格（见对话记录），说明信息密度高、可直接复用
- 检查清单可勾选格式适合复制到笔记/PR模板中使用
- FAQ覆盖了"OKF和Obsidian关系"、"必须用Reference Agent吗"等真实疑问

## 反模式的反模式（写作时的常见错误）

### 反模式A：反模式写成"坏人坏事"

把反模式写成道德批判（"愚蠢的人才会XXX"）。**问题**：读者抵触，不愿意对号入座。

**正确做法**：反模式描述的是"行为→后果"，不评价人。用"如果做X会导致Y"而非"不应该做X"。

### 反模式B：反模式和正面建议不对应

反模式说的是A问题，正确做法说的是B方案。**问题**：读者无法建立"错在哪→怎么改"的对应关系。

**正确做法**：每个反模式的"正确做法"必须直接回应"典型表现"中描述的问题。

### 反模式C：清单太长不分级

列出30+项检查项，没有优先级区分。**问题**：读者望而生畏，不知道哪些必须做、哪些可选。

**正确做法**：分级分类，P0项控制在10项以内，其他按场景标注。

### 反模式D：反模式数量为0或太多

最佳实践章节没有反模式，或者反模式>10个。**问题**：0个反模式变成"正确的废话"，>10个读者记不住。

**正确做法**：5±2个反模式最佳，最多不超过7个。

### 反模式E：没有真实案例支撑

反模式是想象出来的，不是从真实错误中总结的。**问题**："看起来对"但实际没人会犯，或者描述的错误根本不存在。

**正确做法**：每个反模式至少有一个真实案例支撑（自己踩过的坑、见过的错误、GitHub issue中报告的问题）。

## 适用边界

### 适用场景

- ✅ 技术教程的"最佳实践"或"避坑指南"章节
- ✅ API文档/SDK文档的"使用注意事项"
- ✅ 代码规范/PR检查清单
- ✅ 运维SRE的"上线检查清单"
- ✅ 配置指南的"常见配置错误"
- ✅ 安全规范文档

### 不适用场景

- ❌ 纯概念介绍/理论讲解（不需要实践指引）
- ❌ Quickstart/Hello World（入门教程只需要正确步骤，不需要反模式）
- ❌ 发布说明/Changelog（格式不同）
- ❌ 新闻/资讯类内容（不需要指导性）

## 检验标准

| 维度 | 检验点 |
|------|-------|
| 反模式数量 | 3-7个，最佳5±2 |
| 三要素完整 | 每个反模式有"表现→后果→做法"三要素 |
| 对号入座 | 读者能在30秒内判断自己是否犯了某个反模式 |
| 清单分级 | 检查清单按优先级分类，P0项≤10 |
| 可勾选格式 | 使用`- [ ]`语法，可复制直接使用 |
| 真实来源 | 反模式基于真实错误，非凭空想象 |
| FAQ覆盖 | 覆盖新手最常见的3-8个疑问 |
