# 分链排障法（Split-Chain Triage）

## 模式类型

故障定位流程（执行类）。作用于**排障入口**，产出为分支判定、单点改动记录与交叉回归结果；不负责修复动作本身失败时的兜底。

## 模式概述

多组件系统（模型 + 工具 + 权限 + 运行时）出故障时，最自然的反应是「一报错就重装/重配」：既然不知道哪里坏了，就把所有环节重来一遍。这条路在**部分可用**的故障上系统性失效——系统往往还能回复、还能报错、还能跑到一半，只是不能完成目标；此时重装会把现场破坏掉，而真正的原因（某个通道被系统关掉、某个模型不支持某类输入）并不会因为重装而改变。

本模式的核心转向是：

> **先用两条最小指令把故障二分成「理解链」或「执行链」，落到四条固定分支之一，再只查该分支的固定项；修完必须重跑两条最小指令，确认没有把另一条链弄坏。**

支撑证据来自一个手机 Agent 课程知识包（[上游知识包](../../../../../projects/awesome-okf-xs/doc/bundles/jishu/ai/ecosystems/trae/trae-agent-camp-01/index.md)）：

1. 自检被拆成两条独立指令：一条只验证聊天/理解链（「介绍一下你自己」，F-049），一条只验证执行链（「打开设置里的 Wi-Fi 页面」，F-050）；
2. 课程把「闲聊有回复、手机却不动」单列为典型故障，并给出固定检查面：操作模型配置、模型是否支持图片、无障碍服务是否被系统关掉（F-066）；
3. 求助模板要求先说明「停在哪一步」再按从简单到复杂列检查项（F-074）——即先定分支再排查，而不是罗列所有可能原因；
4. 课程把系统部件显式分为记忆、技能、工具、闸门、运行时五类（F-023），为「按链归属」提供了部件级坐标系。

> 为什么必须先分链？因为在多组件系统里，「谁坏了」和「哪里坏了」是两个问题。分链先回答「哪条链坏了」，把候选集合从一个系统的全部部件压缩到一条链的几个固定项——这一步的收益远大于任何单点排查技巧。

## 触发场景

**成立前提**：两条链可被**独立观测**——即存在「只触发理解链、不产生外部动作」的最小指令，以及「只触发执行链、不依赖复杂推理」的最小指令。任一类指令找不到时（例如执行结果本身就是下一次理解的唯一输入），本模式退化为「全链路可用性判断」，应改用逐部件替换法。

**适用于**：

- 系统由**多条可独立观测的链路**构成（如「理解/规划」与「执行/工具调用」、前端与后端、构建与测试）；
- 故障表现为**部分可用**：有响应但不动、能执行但不理解、执行到中途停住；
- 故障现象不指向明确错误码，或错误码存在但有多处可能来源；
- 修复后需要保证「没有引入新的链路故障」。

**不适用于**：

- 单组件故障且错误码直接指向根因（如纯 API 返回明确鉴权错误）——直接按错误码处理更快；
- 系统只有一条链路，分链退化为「是否可用」的单一判断；
- 需要的是「为什么这个问题会反复出现」的层级判断（那是问题解决层级跃迁），或「修复动作失败后如何降级」（那是工具故障降级）。

## 核心做法（5 步）

### 步骤 1：用一条最小指令验证理解链

选一条**只依赖理解链、不产生外部动作**的指令（自我介绍、复述要求、解释一段文本），观察是否有合理响应。

- 指令必须尽量短且无歧义，避免把「指令本身写得不好」误判为理解链故障。
- 此步产出：理解链的通过/不通过。

### 步骤 2：用一条最小指令验证执行链

选一条**只依赖执行链、不依赖复杂推理**的指令（打开某个固定页面、写一个固定文件、跑一条固定命令），观察外部状态是否真的改变。

- 关键区分：有回复 ≠ 执行成功。必须核对**外部可观察状态**，而不是以「模型说它做了」为准。
- 此步产出：执行链的通过/不通过 + 外部状态证据。

### 步骤 3：落到四条固定分支之一

| 现象 | 分支 | 故障归属 |
|---|---|---|
| 有合理回复，外部无变化 | 只理解不执行 | 执行链 |
| 不理解指令但外部有异常动作 | 只执行不理解 | 理解链 / 指令解析 |
| 两条最小指令都失败 | 两条都不通 | 共同前置（凭据、网络、运行时） |
| 执行到中途停住 | 执行中途停 | 权限/确认闸门/单步失败 |

- 分支不是诊断结论，而是**候选集合的限定**：先归链，再在链内查。
- 此步产出：分支判定 + 判定依据（两条最小指令的观察结果）。

### 步骤 4：每条分支只查该分支的固定项

为每条分支预先固定 3 项检查，**不跨分支乱改**：

| 分支 | 固定检查项（示例，按系统替换） |
|---|---|
| 只理解不执行 | ① 执行侧模型/执行器是否配置；② 输入模态是否被支持（如是否支持读屏图像）；③ 执行所需权限/无障碍是否被系统关闭 |
| 只执行不理解 | ① 指令解析与意图路由是否指向错误技能；② 上下文/记忆是否污染；③ 提示词或工具描述是否过期 |
| 两条都不通 | ① 凭据与配额；② 网络与端点；③ 运行时版本与依赖 |
| 执行中途停 | ① 是否触发确认闸门等待人工；② 单步超时/重试上限；③ 中途错误是否被静默吞掉 |

- 一次只改一项，改完立即用同一条最小指令复测；同时改三项会导致成功也无法归因。
- 此步产出：命中项 + 单点改动记录。

### 步骤 5：重跑两条最小指令，做交叉回归

修复后必须**同时复跑**理解链与执行链的最小指令，确认另一条链没有被本次改动弄坏。

- 只复跑故障那条链是最常见的遗漏：修复执行链时改了模型配置，往往会把理解链弄坏。
- 此步产出：双向复测结果 + 交叉回归记录。

## 反模式

1. **一报错就重装/重配**：破坏现场，且对「通道被关掉」「模型不支持某输入」这类根因无效。
2. **同时改三个配置**：即使恢复了，也无法知道哪一项真正起作用，下次同类故障仍要重新试错。
3. **只看错误码不看现象**：「有回复但不动」常常不报错，只按错误码排查会完全漏掉执行链故障。
4. **只修当前分支，不做交叉回归**：修复引入另一条链的回归，表现为「越修越坏」。
5. **把「模型说它做了」当作执行成功**：缺少外部状态证据，验收建立在自述之上。
6. **分支未定就开始罗列全部可能原因**：候选集合不收敛，排查变成清单巡检。

## 检验标准

1. **可归链**：能明确说出「这次坏在哪条链」，并给出两条最小指令的观察结果作为依据。
2. **单点改动**：每次只改一项，且改动与所判分支的固定检查项对应。
3. **双向复测**：修复后两条链的最小指令都复跑通过，有交叉回归记录。
4. **外部证据**：执行链的判定基于外部可观察状态，而非执行者自述。
5. **可复用**：最小指令与分支检查表被固化下来，下次同类故障可直接复用而不重新设计。

## 迁移示例

- **网络排障**：先分层（物理/链路/网络/应用）再在单层内做替换验证；步骤 1/2 的「两条最小指令」对应 ping 与 DNS 查询，步骤 5 的交叉回归对应「换完网线后复测应用层」。
- **CI 失败分诊**：把流水线分为「构建链」与「测试链」，用两条最小 job 分别验证；「执行中途停」对应某一步骤超时或被手动审批阻塞。
- **Agent 工具调用故障**：理解链用「复述任务」验证，执行链用「只读工具调用」验证；中途停常见于审批闸门。
- **已知边界（不可外推）**：单组件且错误码明确的故障、以及只有一条链路的系统，直接按错误码或可用性判断即可。

## 与现有模式的关系

| 相关模式 | 关系 | 说明 |
|---|---|---|
| [root-cause-diagnosis](../governance-strategy/root-cause-diagnosis.md) | 不同问题域 | 对方处理「收到纠错反馈后先诊断自己缺了什么知识」，作用于协作者的认知缺口；本模式处理「系统哪条链坏了」，作用于运行中的系统。可证伪区分：情形「AI 输出格式不合规」下，对方要求先读规范再全量重写，本模式会先跑两条最小指令判断是理解链还是执行链——结论与动作完全不同 |
| [three-level-problem-solving](../governance-strategy/three-level-problem-solving.md) | 层级互补 | 对方判断「这次修复停在症状/病因/免疫哪一层」，本模式判断「故障落在哪条链」；先分链定位（本模式），再决定修到哪一层（对方） |
| [tool-failure-three-tier-degradation](tool-failure-three-tier-degradation.md) | 相邻易混 | 对方是**修复动作本身失败**时的降级阶梯（换工具/换路径），本模式是**还不知道坏在哪**时的候选压缩；可证伪区分：情形「执行链工具超时」下，对方直接降级到备用工具，本模式先判断这是执行链权限问题还是网络问题——若为权限被关，降级换工具同样失败 |
| [signal-identification-four-step](signal-identification-four-step.md) | 上下游 | 对方把人工检查项转化为自动化信号，本模式的分支检查表可作为其输入清单 |
| [symptom-prescription-qa](../ai-collaboration/symptom-prescription-qa.md) | 表现层 vs 定位层 | 对方按症状给药方（面向用户问答），本模式面向排障者做链路二分；对方的症状分类可作为分链的入口索引 |
