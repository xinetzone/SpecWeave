# 证据先行修复法（Evidence-First Repair）

## 模式类型

故障处置纪律（执行类）。作用于**失败已经发生、原因尚不明确**的处置入口，产出为证据包、最小复现与最小修复记录；不负责链路二分定位，也不负责根因推导链。

## 模式概述

多步自动化任务失败时，最自然的反应是**再跑一次**：也许是网络抖动、也许这次就过了。这条路在非确定性系统上系统性失效——重跑会覆盖现场，成功也无法归因，失败则累积费用与时间；更糟的是，反复重跑之后，执行者往往已经改过几处配置，连「原来是什么样」都说不清。

本模式的核心转向是：

> **失败时先冻结现场并取三类运行证据（运行 ID、最后几步日志、当前界面状态），让分析者先解释失败发生在第几步，再写最小复现、做最小修改；未达成就是未达成，不得改写成已完成。**

支撑证据来自一个手机 Agent 课程知识包（[上游知识包](../../../../../projects/awesome-okf-xs/doc/bundles/jishu/ai/ecosystems/trae/trae-agent-camp-02/index.md)）：

1. 一次真实排错的做法是把**截图、运行 ID 与执行轨迹**交给协作者，并区分「技能改动 lint 后立即生效」与「界面改动要重新构建安装包才生效」（F-063）；
2. 讲师总结的原则包含：每一步留下能检查的结果；失败先留证据（运行 ID、截图、最后几步日志），先分析再改，一次只改一处（F-086）；
3. 改程序时交给协作者的四件事里，最后一条被替换为「先有测试，测试全部通过并能构建出新安装包才算改完」（F-076）——完成标准被前移到可执行的验证。

> 为什么证据要包含「运行 ID」而不只是截图？截图证明现象，运行 ID 才能定位到那一次执行的完整轨迹。只有现象没有轨迹时，分析者只能猜测，而猜测的修复往往同时改动多处，下一次失败又无法归因。

## 触发场景

**适用于**：

- 多步执行、跨设备或跨组件的自动化任务失败，且失败现象不完全可复现；
- 同一次失败可能由多个层面引起（配置、权限、模型能力、程序逻辑、界面渲染）；
- 修改存在生效成本差异（有的改动即时生效，有的需要重新构建/安装）；
- 需要向他人（同事、上游维护者、外部支持）描述问题时。

**不适用于**：

- 确定性脚本的编译或语法错误——错误信息直接指向位置，按信息修复更快；
- 生产事故正在扩大、需要先止损——先恢复服务，事后补证据与根因；
- 已经明确知道原因的单点问题——直接修复并复测即可，不必走完整取证流程。

## 核心做法（7 步）

### 步骤 1：冻结现场，保留可回退状态

在改动任何配置之前，记录当前版本与关键配置，必要时先回退到最近一个已知可用状态。

- **主手段**：版本控制或安装包副本；**替代手段**：无版本控制时，导出配置与关键文件快照。
- 「先回退再排查」与「在故障态上排查」是两种策略：可回退时优先回到已知可用态，缩小变量。
- 此步产出：可回退点（提交号、包版本或配置快照）。

### 步骤 2：取三类运行证据

收集运行 ID、最后几步日志、当前界面/输出状态。

- 运行 ID 用于定位完整轨迹；日志用于确认最后成功的一步；界面状态用于确认现象。
- 缺哪类就如实标注缺口，不要用推测补位。
- 此步产出：证据包（三类证据 + 缺口说明）。

### 步骤 3：让分析者先解释，不直接改

把证据包交给分析者（人或 AI），要求先说明「失败发生在第几步、依据是哪条证据」，暂不产出修改。

- 无把握时允许写「可能原因 A/B，需要用 X 区分」，但必须给出区分方法。
- 此步的交付物是解释，不是补丁——先解释可以防止「边猜边改」。
- 此步产出：失败位置判断 + 依据 + 待区分项。

### 步骤 4：写最小复现

把触发条件压缩到能稳定复现的最小步骤集，并记录「复现了几次、失败几次」。

- **主手段**：从原任务中删减步骤直到现象消失，最后保留的那组即最小复现；**替代手段**：无法稳定复现时，记录触发频率与触发时的环境特征。
- 不可复现的故障也应记录，但结论要降级为「现象级」，不宣称已定位。
- 此步产出：最小复现步骤或触发频率记录。

### 步骤 5：做最小范围修改

一次只改一处，改动点必须对应步骤 3 的失败位置判断。

- 改多处会让成功与失败都无法归因；若确需多处，拆成两轮，每轮都复测。
- 改动生效方式要写清：即时生效（如规则文件）还是需要重新构建/安装（如程序）。
- 此步产出：单点改动记录 + 生效方式。

### 步骤 6：复测并与证据包对照

用最小复现步骤重跑，对比失败现象是否消失，同时确认没有引入新问题。

- 复测不通过就回退到步骤 3 重新解释，而不是继续叠加改动。
- 此步产出：复测结果（通过/不通过 + 观察项）。

### 步骤 7：如实登记状态

未达成的项写「未达成」，已达成但未验证的写「待验证」，不得把半成品写成已完成。

- 需要区分「找到」与「完成」：停在候选页面只能算找到，不能说成已购买/已发布。
- 此步产出：状态登记（已完成 / 待验证 / 未达成 + 各自证据）。

## 反模式

1. **反复重跑同一任务，期待偶然成功**：覆盖现场、累积费用，且成功也无法说明原因。
2. **让执行者直接改，改完仍不知道原因**：修复不可复用，同类故障下次照旧。
3. **顺手重构**：在排障提交里夹带无关变更，失败时无法区分是修复引入还是重构引入。
4. **把「没跑通」写成「已实现」**：状态失真会污染后续所有判断，比故障本身更危险。
5. **把 lint 通过当作行为正确**：格式校验通过只说明文件结构合法。
6. **混淆生效方式**：以为改了程序目录就生效，实际需要重新构建安装，导致复测结论错误。
7. **一次改三处**：即使恢复，也不知道哪一项起作用，下次同类故障仍要重新试错。

## 检验标准

1. **可定位**：能指出失败发生在第几步，并说明依据是哪条证据。
2. **可复现**：有最小复现步骤，或明确记录「不可稳定复现 + 触发频率」。
3. **单点改动**：每次修复只改一处，且改动与失败位置判断对应。
4. **有对照**：复测结果与证据包逐项对照，能说明现象是否消失、是否引入新问题。
5. **状态诚实**：完成/待验证/未达成三分清楚，没有把未完成改写为完成。

## 实施检查清单

- [ ] 改动前已记录可回退点（提交号、包版本或配置快照）
- [ ] 证据包含运行 ID、最后几步日志、界面/输出状态三类，缺口已如实标注
- [ ] 分析者先给出「失败在第几步」及依据，再动手修改
- [ ] 有最小复现步骤，或明确记录「不可稳定复现 + 触发频率」
- [ ] 本次修复只改一处，并写明生效方式（即时生效 vs 需重新构建安装）
- [ ] 复测用最小复现原样执行，同时确认没有引入新问题
- [ ] 状态按「已完成 / 待验证 / 未达成」三分登记，未把未完成写成完成

## 正例

一次比价任务只回了价格、缺店铺名与表格：

1. 取截图、运行 ID 与执行轨迹，判定失败发生在「结果整理」一步，而不是检索一步；
2. 只改技能里的表格与字段要求，lint 后推送，用原句「在淘宝搜…比较前 3 家」复测；
3. 复测通过后另行处理界面渲染问题（需重新构建安装），不混在同一次改动里；
4. 状态登记为「技能部分已完成、界面待验证」。

## 迁移示例

- **线上故障排查**：先取日志、指标与链路追踪（运行证据），再定位，再做最小变更；止血优先时事后补证据。
- **CI 流水线失败**：保留 run ID 与失败 job 日志，本地复现同一门禁，只改触发失败的那一处。
- **浏览器/移动端自动化**：截图给现象，运行记录给轨迹，最小复现压缩到单页/单步。
- **已知边界（不可外推）**：编译错误、语法错误、生产事故止血阶段，都不适合走完整取证流程。
