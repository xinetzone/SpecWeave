# caffe-ffi 性能瓶颈分析报告（RQ-3）

> 数据源：`bench_caffe_ffi.json`（caffe-ffi）与 `bench_caffex.json`（pycaffe），各 11 算子、30 次迭代。
> 生成方式：本地 Python（3.13.9）读取 JSON 计算比值/方差，纯数据分析，未修改任何源代码。

## ① 环境说明（重要前提）

- **caffe-ffi 与 pycaffe 运行于两个不同的容器/环境**，基础算力、CPU 拓扑、线程绑定、内存分配策略均可能不同。
- **绝对延迟（mean_ms）仅作相对参考**，不能直接当作两者的"本机算力差距"。
- **`ratio = ffi.mean_ms / cx.mean_ms` 是归一化后的相对比值**，可跨环境抵消部分基础算力差异，是判断"算子级落后"的主要依据。
- `ratio > 1` 表示 caffe-ffi 相对更慢；`ratio < 1` 表示 caffe-ffi 相对更快。
- 结论的可信度排序：**比值（ratio）> 高方差（长尾）> 绝对延迟差异**。

## ④ 高方差（长尾）算子分析

| 算子 | mean_ms | std_ms | min_ms | max_ms | CV(std/mean) |

| **pooling** | 5.0059 | 2.7276 | 1.659 | 15.469 | **54.5%** |
| **eltwise_sum** | 8.0150 | 2.5281 | 4.217 | 16.033 | **31.5%** |
| batchnorm | 0.6104 | 0.2180 | 0.408 | 1.528 | 35.7% |
| lrn | 0.6443 | 0.1515 | 0.479 | 0.973 | 23.5% |
| relu | 0.4559 | 0.1030 | 0.367 | 0.910 | 22.6% |

- **pooling 与 eltwise_sum 是明显的长尾算子**：CV 达 54.5% / 31.5%，且 max 约为 min 的 9.3x / 3.8x（pooling: 15.47ms vs 1.66ms；eltwise_sum: 16.03ms vs 4.22ms）。
- 长尾表明存在**偶发性高延迟**（触发 GC、跨线程调度抖动、动态内存分配、首次调用冷启动等），并非稳定分布。
- batchnorm CV 35.7% 但绝对延迟小（mean 0.6ms），影响有限；lrn/relu 方差中等但绝对量小，可暂不优先。
- 注意：pooling/eltwise_sum 的**均值本身已被长尾拉高**，其真实稳态性能可能低于表格中的 mean_ms，需结合 p50/p95 进一步确认。

## ⑤ 优化建议

### 5.1 算子级 OpenMP 并行
- **inner_product（4.56x / +3.63ms）**：矩阵-向量乘（GEMV）是最适合并行规约的算子。核对 caffe-ffi 的 `InnerProductLayer` 是否开启 OpenMP 行并行/列分块；pycaffe 端通常已启用并行，建议对齐线程数与环境变量（`OMP_NUM_THREADS`、`MKL_NUM_THREADS`）。
- **pooling（11.14x / +4.56ms）**：MaxPool 在整个 batch 上做通道独立并行，具备天然并行度。检查 pooling 是否退化为串行循环，并用 OpenMP `#pragma omp parallel for collapse` 并行空间/通道维。
- **eltwise_sum（14.46x / +7.46ms）**：多输入逐元素相加，可对输出张量做块切分并行，规避串行逐元素循环。

### 5.2 FFI 边界开销
- 低开销算子（convolution 1.02x、sigmoid 0.84x、tanh 0.82x）说明 FFI 单次调用本身开销很小，**FFI 边界不是全局限速因素**。
- 但 eltwise_sum/pooling 若存在**每迭代重复的输入/输出张量拷贝、shape 元数据重建、异常分支检查**，会在循环内放大开销。建议：
  - 复用预分配输出缓冲区，避免 per-call 分配；
  - 批量传递 shape/strides，避免逐层重建元数据；
  - 将多次小调用合并为一次批量调用（batch FFI）。

### 5.3 长尾分配 / GC
- pooling（max 15.47ms）与 eltwise_sum（max 16.03ms）的偶发尖峰高度疑似**动态分配触发内存整理/GC**。
- 建议：将热点路径的中间张量改为**预分配池**（arena/内存池），统计 p50/p95/p99 确认长尾来源；若为 GC 延迟，可改为显式释放或复用缓冲。

### 5.4 针对三个重点算子的具体建议
- **eltwise_sum**：优先排查是否逐元素串行 + per-call 分配；改为输出块并行 + 预分配缓冲，预期可收敛至接近 pycaffe 的亚毫秒级。
- **pooling**：优先排查是否缺并行 + 长尾分配；并行化 + 缓冲复用。
- **inner_product**：优先排查 OpenMP 并行度与线程绑定；对齐线程数与 CPU 亲和性。

### 5.5 验证闭环
- 优化后重跑同一 `bench_caffe_ffi.json` 基准，对比 ratio 是否下探至 <2x（目标区），并确认 pooling/eltwise_sum 的 std 显著下降（长尾收敛）。
